# 2026.6.11 下阶段开发进度安排

## 文档定位

本文档用于梳理“方案高参”下一阶段的产品与开发推进顺序。重点不是继续堆功能，而是按商业闭环排序：先让一个用户能顺畅进入、理解、信任并选择版本，再保证正式交付结果可靠，最后再扩展空间类型和知识规模。

适用对象：

- 产品负责人
- 后端开发
- 前端开发
- 知识库维护人员
- 管理后台维护人员
- 后续新加入团队成员

当前判断：下一阶段不应按“模块完成度”推进，而应按“可销售、可交付、可扩展”的顺序推进。

## 当前基线

截至 2026.6.11，系统已经具备以下基础：

- 方案高参入口流程已能处理“深圳南山区来福士广场负一楼 30 平米奶茶店，半年回本”这类正式问题。
- 系统能识别为茶饮小店相关场景，并进入茶饮/咖啡小店入口判断流程。
- 首轮和第二轮追问已经改为面向终端用户的人话表达。
- 阶段结论和版本选择已进一步去除“本体包、知识包、front of house、back of house”等内部词。
- 后端服务测试和 API 集成测试已通过回归验证。
- 系统已经具备项目类型 Registry、本体论、子域、激活包、知识包、context_packet、Missing Slots、Approved Knowledge Cards 等治理模块的基础框架。

当前主要缺口：

- 茶饮/咖啡小店商业闭环尚未形成稳定可销售产品。
- P0 茶饮研究包尚未完成正文级入库。
- 正式任务书目录与三档版本交付边界还需要产品化定稿。
- 管理后台的人工复核、知识批准、证据链治理还需要进一步串起来。
- 120 个研究包还没有建立正文级消费矩阵。

## 总体路线

推荐路线：

```text
茶饮/咖啡小店商业闭环 MVP
→ P0 茶饮知识包正文入库
→ 标准版任务书跑通
→ 后台复核闭环
→ 再扩第二个空间类型
```

核心原则：

- 先做一个能卖、能交付、能复盘的垂直场景。
- 不把 120 个研究包一次性倒入系统。
- 不把内部治理概念暴露给终端用户。
- 不用硬编码代替知识治理。
- 不用 RAG 直接替代知识资产审核。
- 不先追求全空间类型覆盖。

## P0：打通可销售闭环

目标：让用户从首页输入真实需求后，能顺畅进入入口判断、完成两轮关键确认、看到合理版本推荐，并理解为什么值得继续。

### 1. 锁定首个商业场景

第一阶段只聚焦：

```text
茶饮 / 咖啡小店开店设计建议
```

优先覆盖：

- 商场小铺
- 地铁口铺位
- 社区店
- 写字楼店
- 外卖自提店
- 低预算试水店
- 高租金压力店
- 30-80 平米小面积店

不在本阶段扩展：

- 别墅
- 酒店
- 办公总部
- 医疗空间
- 复杂复合商业
- 大型餐饮旗舰店

验收标准：

- 正式输入能稳定进入方案高参入口流程。
- 系统能识别茶饮/咖啡小店，而不是泛化成普通餐饮。
- 首轮输出先给判断框架，而不是要求 CAD 或工程资料。
- 两轮追问后能进入阶段结论和版本选择。

### 2. 明确三档产品到底卖什么

需要定稿基础版、标准版、高级版的用户价值。

建议产品边界：

| 版本 | 用户目的 | 应交付内容 | 不应包含 |
|---|---|---|---|
| 基础版 | 判断能不能启动 | 项目成立判断、主要风险、基础目录 | 深度平面推演、设备落位、完整预算模型 |
| 标准版 | 指导设计推进 | 回本逻辑、客流转化、动线策略、门头吧台取餐建议、投入优先级 | 施工图、精确设备清单、现场测量替代 |
| 高级版 | 支持决策与协作 | 面向决策人表达、风险边界、版本取舍、正式任务书深化框架 | 代替设计院完整交付、代替审批结论 |

验收标准：

- 用户能看懂三档差异。
- 推荐标准版时，理由是“匹配项目压力”，不是强行推高价。
- 每档都明确“不包含什么”，避免后续交付纠纷。

### 3. 完善首页到买单前体验

入口体验目标：让用户感觉系统懂这门生意，而不是进入一个工程问卷。

需要持续压缩：

- 专业术语
- 英文词
- 后台概念
- 工程后期细节
- 不必要的资料索取

保留高价值判断：

- 半年回本是否成立
- 地铁/商场连接口的人流能否转化
- 门头和菜单能否截流
- 高峰出杯是否拖死成交
- 排队是否堵住通道
- 投入是否花在最影响回本的位置

验收标准：

- 用户第一眼看到的是生意判断，而不是系统术语。
- 首轮问题不超过 4 组。
- 第二轮问题不超过 3 组。
- 进入正式阶段前不要求上传 CAD。

### 4. 建立 20 条黄金测试问题

需要建立一组固定回归样例，用于判断系统体验是否稳定。

样例类型：

- 深圳南山来福士 30 平米奶茶店，半年回本
- 地铁口 20 平米外带咖啡店
- 写字楼大堂 40 平米咖啡快取店
- 社区底商 60 平米茶饮店
- 商场中庭 35 平米轻饮店
- 高租金铺位，预算紧张
- 无排水铺位
- 低电量铺位
- 无排烟铺位
- 首店试水，希望控制投入
- 已有品牌，需要提升转化
- 外卖占比高
- 排队容易外溢
- 门头可见性差
- 只有面积和位置，没有平面图

验收标准：

- 每条样例都有期望识别结果。
- 每条样例都有期望追问方向。
- 每条样例都有禁止出现的内部词清单。
- 每次关键改动后都能回归测试。

### 5. 先入库 P0 茶饮知识包

不要一次性处理 120 个研究包。第一阶段先处理 10-15 个最关键 P0 包。

优先入库方向：

- 行业边界
- 商业模型
- 经济边界
- 选址语境
- 物业工程条件
- 产品结构
- 外卖骑手作为空间使用者
- 面积段空间程序
- 前场/后场/吧台/取餐/座位配比
- 运营动线
- 四流合一冲突
- 高峰 15 分钟压力
- 核心设备系统
- 给排水与排污
- 消防与疏散

标准吸收流程：

```text
正文文件
→ ResearchDossier 原文归档
→ CandidateCard 候选知识卡
→ EvidenceMap 证据链
→ 人工复核
→ ApprovedKnowledgeCard
→ KnowledgePackage / ActivationPack / Ontology / context_packet
→ 正式问题回归测试
```

验收标准：

- 每个正文至少拆出核心判断、适用条件、不适用边界、风险红线、证据来源。
- 未复核内容不能进入运行时调用。
- 已批准知识能被茶饮小店场景命中。
- 知识命中后不能直接把研究原文堆给用户。

## P1：让正式交付结果站得住

目标：用户选择版本后，系统能生成稳定、有边界、可用于设计推进的正式任务书。

### 6. 定义茶饮小店标准版任务书目录

建议标准版目录：

1. 项目成立判断
2. 回本逻辑与投资压力
3. 场地位置与客流转化
4. 门头、菜单与第一眼识别
5. 点单、制作、取餐、外卖自提动线
6. 前场/后场/吧台/座位比例建议
7. 高峰出杯与排队控制
8. 材料、灯光与低成本记忆点
9. 物业工程与正式校准清单
10. 风险边界与下一步资料需求

验收标准：

- 目录不是模板堆砌，而是由用户输入、知识命中和缺口判断共同生成。
- 每章都能说明“为什么需要这一章”。
- 工程条件放在正式校准阶段，不在入口阶段阻断用户。

### 7. 建立知识入库后台工作流

管理后台需要承接需要人工复核的内容。

必须具备：

- 候选知识卡列表
- 待复核队列
- 已批准知识卡
- 已拒绝知识卡
- 证据不足卡
- 回滚记录
- 来源与证据链查看

验收标准：

- 任何需要人工复核的知识，都能在后台找到对应窗口。
- 运行时只读取已批准知识。
- 审核状态可追踪、可回滚。

### 8. 完善 context_packet 可解释性

后台要能解释系统为什么这样判断。

后台可见：

- 空间分类
- 子域
- 激活包
- 知识包
- 已命中知识卡
- Missing Slots
- 版本推荐理由
- 风险边界

前台不可见：

- ontology
- context_packet
- knowledge_package
- activation pack
- 本体包
- 内部对象 ID

验收标准：

- 管理后台能看懂系统判断链路。
- 终端用户只看到自然语言判断。

### 9. 做一次全链路文案巡检

巡检范围：

- 首页输入框
- 首轮回复
- 第一轮追问
- 第二轮回复
- 第二轮追问
- 阶段结论
- 版本选择
- 版本确认
- 任务书预览
- 错误提示

禁用表达：

- ontology
- context_packet
- knowledge_package
- activation pack
- 本体包
- 知识包
- front of house
- back of house
- hard constraint
- formal calibration

验收标准：

- 用户可见文案全部是中文。
- 不出现后台系统概念。
- 不出现买单前不必要的工程术语。

## P2：让系统可扩展

目标：知识越来越多时，系统不变乱，开发者能清楚知道每类知识应该落在哪里。

### 10. 建立 120 个研究包正文级消费矩阵

每个正文都要拆成系统可消费的结构。

字段建议：

| 字段 | 含义 |
|---|---|
| package_id | 研究包编号 |
| 正文标题 | 研究包名称 |
| 优先级 | P0/P1/P2/P3 |
| 核心判断 | 可复用的专业结论 |
| 适用条件 | 什么情况下成立 |
| 不适用边界 | 什么情况下不能用 |
| 风险红线 | 不能误导用户的部分 |
| 证据来源 | 来源、强度、缺口 |
| 空间分类落位 | 是否影响类型识别 |
| 本体论落位 | 绑定哪些维度 |
| 知识卡类型 | 生成哪些 CandidateCard |
| 激活包触发 | 什么用户输入会触发 |
| 知识包归属 | 进入哪个 Knowledge Package |
| Missing Slots | 会产生哪些待确认项 |
| 任务书章节 | 影响哪些正式章节 |
| 版本推荐影响 | 是否影响基础/标准/高级判断 |
| 复核状态 | 待复核/已批准/需补证据 |

验收标准：

- 每个研究包都有明确系统落位。
- 不能只做摘要。
- 不能直接把正文作为运行知识。

### 11. 建设混合知识架构

推荐方向不是单纯 RAG，也不是只靠图谱，而是治理型混合知识网络。

分工：

| 机制 | 作用 |
|---|---|
| Registry | 管项目类型、空间类型、子域、别名 |
| Ontology | 管维度、关系、推理骨架 |
| Approved Knowledge Cards | 管已审核、可调用的知识 |
| RAG | 管正文证据检索和补充解释 |
| Knowledge Graph | 管跨包关系、机制链路、证据网络 |
| Activation Pack | 管特定场景下启动哪些能力 |
| context_packet | 管运行时综合上下文 |

验收标准：

- 运行时优先使用 Approved Knowledge Cards。
- RAG 作为证据检索，不作为未经审核的最终判断来源。
- 图谱服务于关系和解释，不先做炫技可视化。

### 12. 准备第二个空间类型

茶饮/咖啡小店跑稳后，再扩第二个类型。

建议候选：

1. 餐饮小店
2. 零售体验店
3. 社区生活服务店

不建议马上扩展：

- 高端酒店
- 复杂总部
- 大型复合商业
- 别墅精神叙事型项目

验收标准：

- 第二个类型复用同一套入口、知识治理和任务书机制。
- 不为第二个类型重新硬编码一套流程。

## P3：运营与规模化

目标：建立可持续运营机制，让系统能长期迭代，而不是靠临时修补。

### 13. 建立产品数据看板

核心指标：

- 首页输入转入口流程比例
- 首轮完成率
- 第二轮完成率
- 阶段结论到版本选择比例
- 版本点击率
- 版本确认率
- 用户在哪一步流失
- 哪些问题识别失败
- 哪些知识未命中
- 哪些内部词被误展示

验收标准：

- 每个关键节点都有数据。
- 能根据数据判断下一轮优化重点。

### 14. 沉淀人工复核机制

需要明确：

- 谁复核
- 复核什么
- 通过标准是什么
- 证据不足怎么处理
- 错误知识如何回滚
- 新知识如何进入正式运行

验收标准：

- 知识卡有复核记录。
- 审核过程可追踪。
- 未通过知识不会影响用户结果。

### 15. 整理新团队成员入口文档

文档分工建议：

- `README.md`：项目总地图
- `QUICKSTART.md`：启动步骤
- 系统地图：整体模块关系
- 模块边界：各模块职责
- 治理规则：哪些硬编码，哪些可配置，哪些需审核
- 知识网络：研究包如何进入知识系统
- 管理后台覆盖：哪些治理对象在哪个页面维护

验收标准：

- 新程序员 30 分钟内能理解系统主线。
- 新产品/知识维护人员能理解知识入库流程。
- 文档不只解释概念，还指向真实文件和入口。

## 暂不优先推进事项

以下事项不建议排在下一阶段前列：

- 一次性导入 120 个研究包正文。
- 同时扩展所有空间类型。
- 优先做复杂知识图谱可视化。
- 优先做大而全管理后台。
- 优先做自动扫描所有 cleaned 文档。
- 优先让模型直接根据未审核正文回答用户。
- 优先追求完整工程交付，而不是买单前决策体验。

## 主要风险

| 风险 | 表现 | 应对 |
|---|---|---|
| 系统越改越乱 | 模块边界不清，所有东西都互相调用 | 坚持 Registry / Ontology / Knowledge Card / Activation Pack / context_packet 分工 |
| 内容堆积但不可用 | 研究包很多，但运行时不知道怎么消费 | 先做正文级消费矩阵 |
| 用户体验过重 | 买单前问太多工程问题 | 入口只问决策级问题 |
| 知识未经审核进入运行 | 模型直接使用不可靠正文 | 运行时只读 Approved Knowledge Cards |
| 过早扩类型 | 每个类型都半成品 | 先跑通茶饮/咖啡小店闭环 |
| 技术炫技压过产品闭环 | 先做图谱、RAG、可视化，但用户不买单 | 优先完成可销售路径 |

## 建议排期

### 第 1 周：茶饮/咖啡小店闭环稳定

- 定稿三档产品边界。
- 建立 20 条黄金测试问题。
- 完成全链路文案巡检。
- 固化正式问题回归测试。

### 第 2-3 周：P0 知识包入库

- 处理 10-15 个核心研究包正文。
- 生成 CandidateCard。
- 建立 EvidenceMap。
- 完成人工复核。
- 形成第一批 Approved Knowledge Cards。

### 第 4 周：标准版任务书跑通

- 定稿标准版任务书目录。
- 打通用户输入到任务书预成型。
- 验证知识命中对目录和内容的影响。
- 跑 20 条黄金样例。

### 第 5 周：管理后台复核闭环

- 补齐候选知识卡复核页面。
- 补齐批准、拒绝、证据不足、回滚流程。
- 确认运行时只读取批准知识。

### 第 6 周：准备扩展第二空间类型

- 复盘茶饮/咖啡闭环。
- 确认哪些机制可复用。
- 选择第二个空间类型。
- 制定第二类型最小激活包和知识包计划。

## 下一步建议

下一步最应该先做：

```text
茶饮/咖啡小店三档产品定义 + 20 条黄金测试问题
```

原因：

- 这是距离商业闭环最近的工作。
- 它能直接检验入口体验是否足够好。
- 它能倒逼知识包入库优先级。
- 它能防止后续开发继续围绕内部模块打转。

完成这一项后，再进入 P0 茶饮知识包正文级入库，系统才会从“能识别”走向“真懂业务、能交付”。
