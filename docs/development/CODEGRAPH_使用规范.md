# CodeGraph 使用规范（团队执行版）

> 版本：v1.0  
> 更新日期：2026-06-19  
> 适用范围：本仓库所有代码分析、重构与评审场景

---

## 1. 定位

CodeGraph 的最佳定位是**代码结构雷达**。

它负责快速回答：

1. 代码在哪
2. 谁调用谁
3. 改动影响面有多大
4. 某个子系统如何连接

它不是最终事实源。编辑与验证以实时文件和运行结果为准。

---

## 2. 标准用法

### 2.1 定位定义

优先使用 `codegraph_search` 定位类、函数、组件、路由。

典型问题：

- `run_advisor` 在哪里定义
- `DemandReconstructionService` 是否有多处定义
- `ConversationChat` 组件位于哪个文件

### 2.2 理解子系统

使用 `codegraph_explore` 看一片区域的结构关系。

适用场景：

- 功能链路梳理
- 页面到 API 路径追踪
- 后端服务依赖关系分析
- 一组符号之间的连接关系

### 2.3 读取单符号上下文

使用 `codegraph_node` 查看定义、签名、源码片段、调用与被调用关系。

适用场景：

- 修改函数前确认上下游关系
- 判断某符号是否属于核心链路

### 2.4 重构前查调用方

使用 `codegraph_callers` 查“谁在调用它”。

以下改动必须先做 callers 分析：

- 改函数签名
- 调整返回值结构
- 删除旧函数
- 收敛多个同名能力

### 2.5 补齐影响面与索引状态

若 MCP 能力未覆盖，使用 shell 命令：

```bash
codegraph callees <symbol>
codegraph impact <symbol>
codegraph status .
codegraph sync .
```

---

## 3. 使用纪律（强制）

1. 结构关系问 CodeGraph，精确代码看实时文件。
2. 核心改动前必须先看 callers 和 impact。
3. CodeGraph 与磁盘内容冲突时，以磁盘文件为准。
4. 字符串、配置、注释、Markdown、YAML 细节优先用 `rg`。
5. 大范围摸排先用 CodeGraph 缩范围，再读关键源码。
6. 行为正确性不能由 CodeGraph 证明，必须通过测试与运行验证。

---

## 4. 执行流程（最小闭环）

1. `codegraph_search` / `codegraph_explore` 找入口与边界
2. `codegraph_node` / `codegraph_callers` 明确上下游
3. `codegraph impact` 估算改动半径（必要时）
4. 回到实时文件确认后再编辑
5. 运行对应测试、构建或 smoke
6. 在变更说明中写清影响面与验证结果

---

---

## 6. 常见误区

1. 只看单函数，不看上下游。
2. 用全文检索推断结构关系。
3. 未查调用方直接改签名。
4. 仅凭索引结论不回读实时文件。
5. 不做运行验证就判断“改好了”。

---

## 7. 一句话原则

**CodeGraph 用来建立结构判断，实时文件用来确认事实，测试运行用来证明行为。**

---

## 8. 变更前强制检查清单（6条）

在提交代码前请逐项确认：

- [ ] 我已使用 CodeGraph 明确本次改动入口与关键链路。
- [ ] 我已在核心符号上查看 callers（必要时包含 impact）。
- [ ] 我已回读实时文件并确认实现细节与当前索引一致。
- [ ] 我已补充或执行与影响面对应的测试（而非仅局部 happy path）。
- [ ] 我已在变更说明中写明影响模块、风险点与验证结果。
- [ ] 如存在索引漂移，我已执行 `codegraph status .`，并在必要时执行 `codegraph sync .`。

建议：将本清单直接粘贴到 PR 描述，并在提交前自检打勾。
