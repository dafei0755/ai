# 代码版本管理规则

本文档是本项目后续代码修改、文档修改、测试补充、资料库整理时必须遵守的 Git 版本管理规则。目标不是把 Git 用复杂，而是让每一次修改都能被理解、追溯、验证和回退。

## 一、核心原则

Git 管理的不是“文件夹”，而是一组组有明确意图的变更快照。

本项目提交代码时，不能按“我今天改了哪些文件”来提交，而要按“这一批变更解决了什么问题”来提交。

一个合格的提交必须满足四个条件：

1. 能说清楚为什么改。
2. 能独立验证。
3. 出问题能单独回退。
4. 三个月后别人看历史仍能理解。

如果一个提交同时包含前端、后端、文档、资料库、临时脚本、删除文件和配置变更，通常说明它已经过大，需要拆分。

## 二、提交单位怎么划分

本项目不按单纯“模块”提交，也不按单纯“文件类型”提交，而按“可解释、可验证、可回退的变更意图”提交。

模块是边界参考，功能意图才是提交单位。

推荐提交单位示例：

- `方案高参需求重构运行时`
- `方案高参入口运行时基础`
- `诚实边界机制`
- `管理后台取消爬虫/日志/配置页面`
- `README / QUICKSTART 启动说明`
- `空间分类 Registry 治理`
- `茶饮激活包与知识包绑定`
- `数据库多用户空间治理`
- `sf 资料库归档确认`

不推荐提交单位示例：

- `更新代码`
- `修复问题`
- `前后端一起改`
- `今天的所有修改`
- `杂项整理`

## 三、分支规则

每个较明确的任务都应使用独立分支，不要长期在 `main` 上直接堆积修改。

推荐分支命名：

- `feat/scheme-entry-runtime`
- `feat/honesty-boundary`
- `fix/admin-dashboard-route`
- `docs/startup-guide`
- `chore/worktree-cleanup`
- `data/sf-corpus-review`

分支命名要能看出目的，不追求花哨。

如果当前工作树已经很脏，先做安全整理报告和分批清单，再决定从哪里开始收敛。

### 并行线程规则

当两个开发线程同时推进时，不能只靠口头约定隔离，必须建立明确的线程边界文档。

当前 Golden 复核线与茶饮专项线的边界文件：

```text
docs/development/2026-06-16-并行线程协作边界-golden-vs-tea.md
```

执行规则：

1. 两个线程暂不直接合并，先各自稳定。
2. 每个线程只修改自己边界内的文件。
3. 共享高风险文件必须在合并前逐项看 diff。
4. 不能用整文件覆盖解决冲突。
5. 合并前必须分别跑 Golden 复核线和茶饮专项线的验证命令。

如果后续再出现新的并行线程，也必须按同样方式新增边界说明，并在本规则中挂接入口。

## 四、日常修改流程

每次开始新任务前：

1. 查看当前分支。
2. 查看 `git status`，确认当前工作树是否干净。
3. 如果不干净，先判断已有变更属于哪一批，不能直接继续叠加。
4. 明确本次修改目标。
5. 只改与本目标直接相关的文件。
6. 改完只暂存本批次相关文件。
7. 跑本批次相关测试。
8. 提交。

如果中途发现牵出另一个问题，不要顺手改进同一个提交。先记录，再另起批次。

## 五、VS Code 三个 Git 视图怎么用

### 1. 更改

这是工作台，用来看当前有哪些文件被修改、新增或删除。

使用规则：

- 不要全选提交。
- 先按批次筛选文件。
- 对大文件或不确定文件，先查看 diff。
- 新增文件要特别注意，因为 `git diff` 默认看不到未跟踪文件的正文变化。

### 2. 图表

这是时间线，用来看提交历史和分支关系。

使用规则：

- 看本分支从哪里分出来。
- 看是否落后或领先主线。
- 看提交历史是否清晰。
- 合并或回退前先看图表，避免误操作。

### 3. GitLens

这是追溯工具，用来看一行代码是谁、什么时候、为什么改的。

使用规则：

- 修改不熟悉代码前，先看最近提交。
- 删除文件前，先看历史用途。
- 遇到不理解的逻辑，先查 blame 和历史提交说明。
- 不要只看当前代码，要看它为什么变成现在这样。

## 六、暂存规则

暂存区不是“准备全部提交”的篮子，而是一次提交的边界。

允许暂存：

- 同一功能目标下的源码。
- 同一功能目标下的配置。
- 同一功能目标下的测试。
- 与本功能直接相关的简短文档。

不应混入：

- 临时脚本。
- 本地数据库。
- Playwright 截图输出。
- 上传缓存。
- `node_modules`。
- 与本任务无关的格式化变更。
- `sf/` 资料库变更，除非本批次就是资料库治理。

## 七、文件归属规则：跟踪、忽略、本地保留

防止误删的前提，是先判断文件属于哪一类。不要用“当前在不在本地目录里”判断安全性，要看它是否应该进入 Git、是否只应本地保留、是否应被忽略。

### 1. 必须 Git 跟踪

这些是项目资产，丢失会影响交接、运行、测试、追溯或知识体系完整性。

必须跟踪：

- 正式源代码：`intelligent_project_analyzer/`、`frontend-nextjs/` 中的业务代码。
- 正式测试：`tests/`、前端 `.test.tsx`、`.test.ts`。
- 核心项目文档：`README.md`、`QUICKSTART.md`、`docs/architecture/`、`docs/development/`、`docs/system-completeness-audit/` 中的正式文档。
- 产品定义资料：`sf/2026.5.23/`、空间分类、本体论、知识资产、方案高参定义类正文文档。
- 配置模板：`.env.example`、`.env.*.example`、不含真实密钥的示例配置。
- 系统契约与数据结构：schema、migration、registry YAML、ontology、activation pack、knowledge package。
- 小型、稳定、可复用的样例数据。

判断标准：

```text
别人拉代码后是否需要它？
三个月后是否还要追溯它？
它是否代表系统定义、知识资产、产品规则或测试保护？
```

如果答案是“是”，就应该纳入 Git 跟踪。

### 2. 必须忽略

这些是机器生成、本地环境、缓存、运行时产物或敏感信息，不应进入 Git。

必须忽略：

- `node_modules/`
- `.venv/`、`.conda/`
- `.pytest_cache/`
- `.next/`、`build/`、`dist/`、`coverage/`
- 本地数据库：`*.db`、`*.sqlite`、`*.sqlite3`
- 上传缓存：`.uploads/`
- Playwright 截图、测试输出、浏览器运行记录
- 日志文件
- 临时脚本和临时文本：`_patch*.py`、`_test*.py`、`temp.txt`
- 真实密钥、真实 token、cookie、credentials、`.env`

判断标准：

```text
能否重新生成？
是否只属于本机？
是否包含隐私、密钥、缓存或运行结果？
```

如果答案是“是”，就应该进入 `.gitignore`。

注意：`.gitignore` 不是备份机制。被忽略的文件仍可能被 `git clean -fdx` 删除，所以重要资料不能只靠“本地存在 + 被忽略”保护。

### 3. 应该本地保留，但不一定进 Git

这些文件可能重要，但不一定适合直接进入代码仓库。

包括：

- 大型压缩包：`.rar`、`.zip`
- 原始资料备份
- 未整理研究材料
- 本地导出物
- 私有客户资料
- 版权不明确的外部素材
- 体积很大的语料、图片、PDF

处理方式：

```text
本地保留 + 建清单 + 必要时放网盘/对象存储/备份盘
Git 只跟踪索引、说明、来源记录
```

示例：

- `sf/2026.5.23/` 下的正文 Markdown：建议 Git 跟踪。
- `sf/2026.5.23.rar`：可以本地保留，不一定进 Git，但必须有来源和备份清单。

### 4. 本地存在与 Git 跟踪的区别

本地存在，只说明文件现在在硬盘目录里。

Git 跟踪，才说明文件进入版本历史，可追溯、可回退、可协作。

常见状态：

```text
已跟踪 + 本地存在：正常项目文件。
已跟踪 + 本地被删：Git 显示 D，可从历史恢复。
未跟踪 + 本地存在：Git 显示 ??，容易被 stash -u 或 clean 影响。
未跟踪 + 本地不存在：Git 不知道它，普通历史无法恢复。
```

因此，重要文档生成后要么尽快提交，要么进入“本地保留清单”。不能长期停留在 `??` 状态。

### 5. `docs/` 与 `sf/` 的特别保护规则

`docs/` 和 `sf/` 是本项目的知识与产品定义资产，不按普通临时文件处理。

规则：

1. `docs/` 下正式文档应尽快 Git 跟踪。
2. `sf/2026.5.23/` 下方案高参核心定义正文应 Git 跟踪。
3. `sf/` 下压缩包、大体积备份、原始资料可以不进 Git，但必须有清单和备份位置。
4. 清理工作区时，不允许把 `docs/`、`sf/` 一并粗暴 stash 或 clean。
5. 如果必须暂存未跟踪文件，先列出清单，再单独确认每个目录。

默认规则：

```text
重要 + 应共享：git add + commit
重要 + 不适合入 Git：本地备份 + 清单记录
不重要 + 可再生成：.gitignore
临时不确定：先别删，放待确认清单
```

## 八、测试规则

每个提交都应有对应验证方式。

测试不一定每次都跑全量，但必须跑能证明本批次有效的测试。

推荐规则：

- 后端服务改动：跑对应 `pytest`。
- 前端页面改动：跑对应单测或至少启动页面检查。
- 启动命令改动：实际按文档命令启动验证。
- 管理后台路由改动：验证页面能打开，旧路由有明确处理。
- 资料库或知识包改动：跑 schema 校验或对应 runtime smoke。

提交说明里应能看出验证方式。

## 九、回退规则

回退必须区分三种情况。

### 1. 未提交的改动

可以按文件或代码块丢弃，但必须先确认不是用户或其他任务的改动。

禁止在脏工作树中随意丢弃全部改动。

### 2. 已提交但未共享的改动

可以根据情况修改提交或重排提交，但必须确认不会影响他人。

### 3. 已提交并可能被他人使用的改动

优先使用 `revert`，生成一个反向提交。这样历史仍然完整，别人能看清楚发生过什么。

默认不要使用 `reset --hard`。

## 十、禁止动作

在没有明确确认前，禁止执行：

```bash
git add .
git clean -fd
git clean -fdx
git reset --hard
git checkout -- .
git stash -u
git stash --all
```

这些命令都可能把不同批次的工作混在一起，或直接抹掉尚未确认的修改。

其中：

- `git stash -u` 会把未跟踪文件也从工作目录移走。
- `git stash --all` 会连被忽略文件也一起处理。
- `git clean -fd` 会删除未跟踪文件和目录。
- `git clean -fdx` 会连被忽略文件也删除，风险最高。

如果确实需要恢复单个文件，只能针对明确路径执行，并先确认该文件不属于主动修改范围。

## 十一、本项目当前分批建议

当前项目已有大量既有修改，后续整理应按以下顺序推进：

1. 忽略规则和临时文件治理  
   处理 `.gitignore`、本地数据库、Playwright 输出、临时脚本等噪声。

2. 方案高参入口运行时基础  
   收敛需求重构、entry service、context intelligence、空间分类、知识包、激活包、相关测试。

3. 诚实边界机制  
   如果能从入口运行时基础中拆清楚，则单独提交；如果拆不清楚，应并入入口基础批次说明。

4. 管理后台清理  
   下线外部数据、爬虫、日志、配置管理页面及相关路由测试。

5. README / QUICKSTART  
   只放项目入口和启动命令，不承载长篇架构说明。

6. `sf/` 资料库  
   单独确认、单独归档，不和运行代码混提交。

## 十二、提交前检查清单

每次提交前必须回答：

1. 这次提交解决的具体问题是什么？
2. 这批文件是否属于同一个变更意图？
3. 有没有混入临时文件、本地缓存、无关文档或资料库内容？
4. 有没有未跟踪整文件需要单独确认来源？
5. 有没有删除文件？删除是否已确认是主动下线而不是误删？
6. 跑了什么验证？
7. 如果这次提交出问题，能否单独回退？
8. `docs/`、`sf/` 下是否有未跟踪但重要的文档或资料？
9. 是否误把应本地保留的压缩包、原始资料、客户资料混入代码提交？

如果上述问题答不清楚，不提交。

## 十三、提交说明格式

提交说明要短，但要说明意图。

推荐格式：

```text
feat: add demand reconstruction entry layer
feat: add scheme advisor entry runtime foundation
fix: restore admin dashboard route
docs: update quickstart startup command
chore: ignore local generated artifacts
test: cover honesty boundary policy
data: organize sf source corpus batch
```

中文提交说明也可以，但要清楚：

```text
feat: 增加方案高参入口运行时基础
docs: 更新启动说明
chore: 清理本地生成物忽略规则
```

不要使用：

```text
update
fix
修改
临时提交
```

## 十四、长期维护原则

版本管理的目标不是让提交数量最少，而是让历史清楚。

宁可多几个边界清晰的小提交，也不要一个巨大提交把系统改乱。

以后所有较大修改，都应先形成：

1. 目标说明。
2. 涉及范围。
3. 文件清单。
4. 验证方式。
5. 回退方式。

再进入实际修改。

这份规则作为本项目后续 Git 操作和代码整理的默认准则。
