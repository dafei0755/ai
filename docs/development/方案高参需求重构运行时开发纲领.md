# 方案高参需求重构运行时开发纲领

版本：v1.0
日期：2026-06-16
状态：当前开发基线

## 1. 定位

需求重构已经替代原入口前置概念。

它不是普通问答，不是第二产品，也不是轻版任务书。它是设计任务书 2.0 的购买前理解力证明阶段：

```text
用户模糊表达
↓
需求重构：先把真实需求说清楚
↓
少量探索性追问：只问会改变判断的问题
↓
用户确认进入设计任务书
↓
正式一二轮追问：冻结任务书方向与交付边界
↓
设计任务书 2.0
```

需求重构的前台目标是让用户产生：

> 对，这才是我真正想说的。

工程目标是把模糊输入编译成可承接的 `demand_reconstruction_context`，并无损交给正式任务书入口。

## 2. 与原流程的关系

原有一二轮追问保留，但位置后移。

| 阶段 | 用户状态 | 系统动作 | 输出 |
|---|---|---|---|
| 需求重构 | 只有零星问题、模糊念头、情绪或方向感 | 重构真实需求、指出关键变量、暴露未知边界 | 行动蓝图 |
| 一二轮追问 | 用户已经明确要整理为设计任务书 | 正式问诊、确认显性锚点与隐性矛盾 | 首轮/二轮引导卡 |
| 设计任务书 2.0 | 方向已冻结到可交付状态 | 完整展开、依据补齐、缺口治理 | 任务书正文 |

入口只有一条路：所有新项目输入都必须先进入需求重构。用户说“完整设计建议”“完整概念框架”“设计任务书”，只代表任务书意向更强，不代表可以跳过需求重构。正式一二轮追问只能由需求重构 handoff 触发。

需求重构阶段可以问，但不是问卷式问诊。它的问题必须是探索性、低压力、带判断前提的，例如：

```text
你更想解决的是返乡居住、精神寄托，还是家族关系？
```

正式一二轮追问可以使用明确的任务书语气，例如：

```text
请确认项目对象、使用方式、场地条件和交付意图。
```

## 3. 复用原则

需求重构不是新建一套空间分类、意图识别或本体论算法。它必须复用现有系统能力。

必须复用：

- 项目语义理解器：`SchemeAdvisorContextIntelligence`
- 空间分类：`project_type_detector.py` / `SpaceClassificationService`
- 语义轴与主矛盾：`scheme_advisor_semantic_axes.py`
- 前台公共标签：`scheme_advisor_public_labels.py`
- 知识治理：Activation Pack / Knowledge Package / Approved Knowledge Cards
- 缺口治理：context packet / Missing Slots
- 正式任务书入口：`SchemeAdvisorEntryService`

需求重构新增的只是编排层：

| 模块 | 职责 |
|---|---|
| `DemandReconstructionContextAdapter` | 把现有语义理解、空间分类、主矛盾、公共标签压成需求重构上下文 |
| `DemandReconstructionOutputPlanner` | 根据项目语义选择动态输出模块，不使用固定栏目模板套所有问题 |
| `DemandReconstructionInsightProtocol` | 集中管理 LLM 洞察 prompt、JSON 解析、蓝图合并、质量门与反套话规则 |
| `DemandReconstructionBoundaryGuard` | 防止需求重构滑成完整任务书、完整方案或伪证据研究 |
| `DemandReconstructionService` | 处理入口消息、生成行动蓝图、维护 handoff 状态 |

禁止重新开发：

- 独立空间分类器；
- 独立本体论；
- 独立知识库；
- 独立任务书入口；
- 固定模板式“万能问答”。

### 3.1 受控 LLM 洞察层

需求重构不能只靠规则模板，否则面对开放式问题会显得“整理得很快，但不够懂”。因此运行时采用混合结构：

```text
规则/本体论层：分诊、空间类型、语义轴、主矛盾、缺口、任务书承接
↓
LLM 洞察层：只负责真实需求重写、核心判断、头号风险、一个关键追问
↓
边界守卫：拒绝完整方案、完整任务书、施工级建议、伪证据
↓
规则兜底：LLM 不可用、低质或越界时返回规则蓝图
```

LLM 不决定是否进入任务书，不改写 `brief_handoff_slots`，不负责证据结论。它只在系统已生成的结构化上下文和规则蓝图上，完成前台第一屏的认知重构表达。

工程上，LLM 洞察算法必须集中在 `DemandReconstructionInsightProtocol`，不得把协议词、反套话清单、质量门判断继续散落到 `DemandReconstructionService`、路由或前端。服务层只负责调用协议、处理失败回退和渲染结果。

LLM 洞察层会吸收旧需求洞察系统中仍有价值的方法，但只作为内部协议，不作为前台栏目：

```text
1. 字面事实：用户明确说了什么。
2. 隐含意图：用户真正想解决什么。
3. 核心张力：最尖锐、最能改变后续判断的对立面。
4. 第一性剥离：去掉风格、惯例、参考案例、社交表演后，剩下什么不可约需求。
5. 空间被雇佣：这个空间被拿来完成什么人生、商业、关系或行为任务。
6. 未知边界：哪些是事实、哪些是合理推测、哪些会改变方向。
7. 锐度自检：这条判断是否只适用于此项目，是否说出了用户没说清的事。
```

前台不得出现 `L1/L2/L3`、`JTBD`、`第一性原理`、`锐度测试` 等内部术语。它们只用于让输出更准、更锋利、更少套话。

运行时可用 `DEMAND_RECONSTRUCTION_USE_LLM=0` 临时关闭该层；当 `DEMAND_RECONSTRUCTION_USE_LLM=1` 时，入口采用 LLM-first 强契约，理解或综合不可用必须返回 typed unavailability（`UNDERSTANDING_UNAVAILABLE` / `SYNTHESIS_UNAVAILABLE`）并由路由映射为 HTTP 503，不得静默退回旧规则蓝图。

需求重构 LLM 使用独立短超时配置，不复用正式对话态的长等待策略：

```text
DEMAND_RECONSTRUCTION_LLM_TIMEOUT=8
DEMAND_RECONSTRUCTION_LLM_MAX_RETRIES=0
```

这两个默认值体现一个产品原则：第一屏可以增强洞察，但不能因为 LLM 网络失败拖垮入口。

## 4. 数据与接口字段

后端会话字段：

```text
dialogue_layer: demand_reconstruction | brief_intake | project
handoff_available: boolean
demand_reconstruction_context: object | null
```

需求重构上下文：

```yaml
demand_reconstruction_context:
  schema_version: demand_reconstruction_context.v1
  reconstruction_type: demand_reconstruction
  artifact_name: action_blueprint
  display_title: 需求重构
  display_artifact_name: 行动蓝图
  source_message: string
  adapter_context:
    project_type: string | null
    project_type_name: string | null
    space_label: string | null
    semantic_axes: object
    main_tensions: list
    archetype: object
    context_source: object
  blueprint:
    task_reframe: string
    project_viability_judgment: string
    primary_risk: string
    insight_source: llm | rule | rule_fallback
    sections: list
    key_forks: list
    unknowns: list
    routing_recommendation: string
    brief_handoff_slots: object
  brief_handoff_slots: object
```

前端卡片类型：

```text
card_type: demand_reconstruction_blueprint
title: 需求重构
artifact_name: 行动蓝图
```

## 5. 路由规则

入口路由的优先顺序：

1. 如果已有正式任务书状态，继续 `brief_intake`。
2. 如果当前 pending card 是 `demand_reconstruction_blueprint`，继续需求重构或 handoff。
3. 如果是新项目输入，无论模糊建议、零星问题、方向试探，还是明确请求完整设计建议，都进入需求重构。
4. 如果输入需要文化、历史、行为证据验证，需求重构只定义研究路径，建议进入深度研究，不伪装成结论。
5. 只有用户在需求重构后确认整理为设计任务书，才进入正式一二轮追问。

## 6. 输出边界

需求重构允许：

- 重新说明用户真正的问题；
- 给出最关键变量；
- 指出头号风险；
- 给动态行动蓝图；
- 暴露未知边界；
- 提示进入任务书后会承接哪些字段。

需求重构禁止：

- 输出完整任务书；
- 输出完整空间方案；
- 固定套用所有栏目；
- 把研究计划写成已完成研究报告；
- 重复正式一二轮追问；
- 要求用户一开始就提交 CAD、预算表或完整工程资料。

核心边界：

```text
需求重构让用户看见真实问题；
设计任务书才告诉用户这个问题怎么完整处置。
```

## 7. 测试基线

必须覆盖：

- 模糊输入进入 `demand_reconstruction`；
- 正式任务书意向的新项目输入仍先进入 `demand_reconstruction`；
- `demand_reconstruction_context.blueprint` 可被 session 保存；
- 有 LLM 时需求重构使用受控洞察层，`insight_source=llm`；
- LLM 不可用、低质或越界时降级为规则蓝图，`insight_source=rule_fallback`；
- handoff 后正式一轮卡片继承 `brief_handoff_slots`；
- 前端需求重构卡片不出现正式问诊按钮文案；
- 已进入 `scheme_round_1` 后不再被需求重构抢占。

```powershell
.\.conda\python.exe -m pytest tests/services/test_demand_reconstruction_service.py tests/api/test_scheme_advisor_entry_route.py -q
```

## 8. 开发红线

1. 前台不出现 `L1/L2/L3`、`State Gate`、`Design Freeze` 等内部术语。
2. 不再使用旧入口概念作为阶段名、文件名、字段名或测试名。
3. 需求重构不是茶饮专项能力，茶饮只是压力样例之一。
4. 需求重构输出结构必须动态选择，不能所有问题固定七段式。
5. 新增能力必须先接入既有语义理解和知识治理，不得绕过现有系统另起炉灶。
