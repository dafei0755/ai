# 方案高参知识资产三链路机制

版本：v1.1

更新时间：2026-06-12

## 文档层级声明

本文是方案高参知识资产系统的机制口径文件，用于细化“知识如何生产、如何消费、如何结算”。它不另立新的全局 schema，不覆盖既有主架构定义。

本文的定位是：

- 作为知识库引擎和知识资产治理的链路细化层。
- 具体字段命名、卡片 schema、lens 正典列表，应以正式 schema 和既有主架构版本为准。
- 本文只定义边界、职责、状态关系和落地原则，避免与运行调度、本体论、任务书编译等上层机制重复定义。

本文回答三个问题：

1. 研究资料如何变成系统可用的知识资产。
2. 用户提问时，系统如何正确调用这些知识资产。
3. 知识被调用后，如何通过真实项目反馈持续修正。

结论先行：

方案高参不能只做“文档检索”，也不能只做“卡片仓库”。合理结构应是：

```text
生产链：把知识变成资产
消费链：把资产变成答案
结算链：判断答案是否经得起真实项目验证
```

三条链共同构成知识系统闭环。生产链负责写入，消费链负责读取，结算链负责校正。三者边界必须清楚，否则系统会逐渐混乱：研究包被当成运行时知识、候选卡绕过审核、用户项目反馈无法反哺知识库，最终导致知识越积越多但越用越不可信。

---

## 1. 为什么不能只用一条链

早期容易把系统画成一条长链：

```text
空间分类 -> 本体论 -> 激活包 -> 知识包 -> approved cards
-> context_packet -> 方案高参输出
-> ResearchDossier -> candidate cards -> review
-> approved cards -> package registry -> runtime recall
```

这个表达方向上有启发，但结构上不够清晰。它把三类动作混在了一起：

| 动作 | 本质 | 是否同步发生 |
|---|---|---|
| 用户问题调用知识 | 运行时消费 | 同步，要求快 |
| 研究资料拆解入库 | 知识生产 | 异步，要求可审核 |
| 真实项目反馈修正知识 | 知识结算 | 异步，要求可追踪 |

因此，正确做法不是把它们串成一条超长链，而是拆成三条职责清晰的链。

三条链的唯一合法交汇点是已经审核通过、可以运行时读取的知识资产。生产链不能直接调用消费链，消费链不能直接写知识库，结算链不能绕过人工裁决直接改写正式知识。

## 2. 三链路总览

```text
一、生产链：写入系统
ResearchDossier / 专家笔记 / 案例材料 / SourceGap / PromotionCandidate
-> 来源登记
-> 解剖清点
-> 多物种分拣
-> 分级审核
-> approved assets / 规则库 / 题库 / 指标库 / SourceGap 入位
-> package registry 记账

二、消费链：读取系统
用户输入
-> 空间分类
-> 参数提取
-> missing_slots
-> 冲突检测 / P1 熔断
-> 本体论 lens 激活分档
-> approved assets / 规则 / 追问题召回
-> context_packet
-> AdvisorAgent 姿态装配
-> 能力链执行
-> 封顶输出
-> 消费台账登记

三、结算链：反馈修正
消费台账
-> 回访 / 用户反馈 / 项目实际数据
-> SettlementEvent
-> 证据强度判断
-> 归因分流
-> maturity / 边界 / 召回规则调整建议
-> PromotionCandidate
-> 人工裁决
-> 回到生产链
```

### 2.1 两类候选来源与统一审核闸口

方案高参的知识资产候选来源可以分成两类：

| 来源 | 发生位置 | 进入审核系统的对象 | 权限边界 |
|---|---|---|---|
| 外部生成链 | 另一台电脑本地，通过 API 接入 | ResearchDossier、candidate assets、SourceGap、规则、slot、追问题、指标 | 只能提交候选，不能批准 |
| 内部自学习链 | 方案高参系统内循环，通过内部接口接入 | ConsumptionLedger、SettlementEvent、PromotionCandidate、maturity 调整建议、召回修正建议 | 只能提交提案，不能直接改正式知识 |

两类来源都必须进入同一个知识资产审核系统，并通过管理后台完成复核、批准、拒绝、退回修改。正式知识库只能接收审核通过的 approved assets。

标准边界是：

```text
外部生成链：只能 submit candidate
内部自学习链：只能 submit proposal
知识资产审核系统：负责 review / approve / reject / needs_revision
正式知识库：只接收 approved
运行时消费链：只读取 approved
```

这意味着：

```text
生成权 ≠ 审核权
学习权 ≠ 修改权
审核权 ≠ 运行权
```

外部生成链可以高效生产研究包和候选资产；内部自学习链可以发现真实项目中的反馈和修正机会。但二者都不能绕过管理后台直接修改 approved assets、空间分类、本体论、schema 或运行规则。

### 2.2 专题复盘系统的需求重构入口

专题复盘系统里的“需求重构”，本质上是复盘主题的前置理解层，不是新的知识生产链，也不是正式审核结论。

它处理的对象通常是：

- 一次专题复盘的模糊主题、问题陈述或方向判断。
- 来自消费台账、回访记录、项目观察、用户反馈的零散信号。
- 需要被整理成可讨论、可追问、可审核的复盘提案。

它的输出不是 approved assets，而是可进入后续流程的重构结果，例如：

- 复盘主题的真实问题定义。
- 需要补齐的关键变量与缺口。
- 值得进入知识资产审核系统的 candidate assets / PromotionCandidate。
- 是否需要转入 SettlementEvent、补证据，或退回修改。

专题复盘系统当前的需求重构机制，应遵守下面这条路径：

```text
专题复盘主题
-> 需求重构
-> 复盘提案 / 行动蓝图
-> 需要沉淀的候选资产或结算线索
-> 知识资产审核系统
-> approved 后再进入正式知识库
```

这意味着：

```text
需求重构 ≠ 自动入库
需求重构 ≠ 直接改写成熟度
需求重构 ≠ 绕过审核生成正式知识
```

如果复盘问题只是“这次项目哪里不顺”，系统应先把它重构成可验证的问题陈述；如果复盘问题已经明确指向知识修正，则应把结果送入内部自学习链，作为提案而不是结论。专题复盘系统只负责把模糊复盘语义整理成清晰入口，不负责替代审核、结算或正式知识更新。

## 3. 生产链：把知识变成资产

生产链解决的问题是：一份研究包、案例、专家笔记或经过结算链沉淀的项目观察，如何变成系统可审核、可追溯、可调用的知识资产。

### 3.1 输入来源

生产链可以接收多种来源，但来源入口必须有闸。

| 来源 | 示例 | 说明 |
|---|---|---|
| 外部生成链 ResearchDossier | 另一台电脑生成的茶饮水吧台尺度研究包 | 通过 API 提交，进入审核系统 |
| 专家笔记 | 设计师对湿区边界的经验判断 | 可进入生产链，但证据上限较低，需要补证据 |
| 案例材料 | 品牌门店拆解、现场照片、运营数据 | 需要区分可迁移与不可迁移 |
| SourceGap | 标准全文不可得、品牌手册缺失 | 只能进入缺口治理，不能直接形成强结论 |
| PromotionCandidate | 系统内循环聚合后的候选知识 | 内部自学习链进入生产链的合法入口 |

单次项目观察不能绕过结算链直接进入生产链。它应先进入消费台账、回访记录或 observation log，经重复观察聚合后形成 `PromotionCandidate`，再进入人工裁决。

专家笔记可以进入生产链，但应默认设置较低证据上限，例如：

```text
source_evidence_level = expert_inference
maturity = observed
```

### 3.2 生产链不是“全文入库”

研究包原文必须保留，但不能直接作为运行时主知识。

正确方式是：

```text
原文保真
-> 拆出可判断、可调用、可审核的知识单元
-> 复核后进入运行时
```

原文的作用是追溯证据和复核脉络，不是每次回答都让系统翻长文。

### 3.3 多物种分拣

一份研究包的产出不只是卡片。以茶饮水吧台尺度研究包为例，它可能产生：

| 物种 | 进入位置 | 示例 |
|---|---|---|
| 判断卡 | approved cards | 水吧台不是单一高度，应分制作、洗区、交接层 |
| 校验规则 | 规则库 / 校验器 | 未确认设备开门包络时，不能锁死后场通道 |
| slot 词表 | missing_slots / 问询器 | 设备清单、给排水点、电量、峰值单量、员工数 |
| 追问题 | 追问题库 | 是否做外卖？是否需要明档？是否有堂食？ |
| 任务书条款 | 任务书模板 | 水吧台尺度需按设备、湿区、交接层分项确认 |
| 观测指标 | 治理台账 / 结算链 | 高峰出杯时间、员工绕行动作、交接口拥堵 |
| SourceGap | 缺口库 | 品牌手册、真实设备、现场水电点位未确认 |
| 失败模式 | 风险库 / 熔断规则 | 台下冰箱门打开阻断主通道 |

如果只拆成卡片，会丢掉大量更关键的运行能力。真正提升系统质量的，往往是规则、slot、追问、指标和失败模式。

卡片粒度应以“决策点”为边界。一张卡应对应一个可复用、可召回、可结算的专业判断。卡片太粗，无法精准召回；卡片太细，审核和维护会爆炸。

### 3.4 三个正交状态维度

知识资产不应该只有一个混合状态。至少要拆成三个正交维度：

| 维度 | 回答的问题 | 谁改变它 |
|---|---|---|
| lifecycle_status | 这条资产当前能不能被运行时读取 | 生产链审核 |
| maturity | 这条资产被真实项目验证到什么程度 | 结算链 |
| source_evidence_level | 这条资产出生时证据基础有多强 | 入库时确定，原则上不改 |

一张卡可以同时是：

```text
lifecycle_status = approved
maturity = observed
source_evidence_level = E2_research
```

含义是：审核通过，可以运行时读取；但真实项目验证还少；出生证据来自研究材料。

#### lifecycle_status

`lifecycle_status` 是生产状态机。它决定资产能不能进入运行时。

建议最小状态：

| 状态 | 含义 |
|---|---|
| draft | 草稿 |
| candidate | 候选资产 |
| needs_review | 等待审核 |
| approved | 已批准，可被运行时读取 |
| rejected | 已拒绝 |
| needs_revision | 需修改后再审 |
| retired | 主动下线 |

`stale` 和 `superseded` 不建议混入基础生产状态。它们更适合作为生命周期标记或替代关系字段：

```text
stale_flag = true / false
superseded_by = card_id
```

#### maturity

`maturity` 表示真实项目验证成熟度。结算链主要改变这个维度。

建议最小等级：

| 等级 | 含义 |
|---|---|
| observed | 有观察或研究判断，但项目验证少 |
| supported | 有案例、研究或多源材料支持 |
| validated | 已被多个真实项目验证 |
| bounded | 已验证，同时适用边界明确 |
| disputed | 存在冲突记录，需要审查 |

`disputed` 更准确地说是冲突标记，不应被当成线性成熟度升级路径。工程实现上可拆为：

```text
maturity = supported
conflict_status = disputed
```

#### source_evidence_level

`source_evidence_level` 表示资产出生时的证据基础，原则上不随结算事件直接改变。若证据基础发生根本变化，应生成新版本或新卡。

建议等级：

| 等级 | 来源 |
|---|---|
| E1_standard | 法规、标准、官方强约束 |
| E2_research | 学术研究、系统研究包 |
| E3_spec | 设备规格书、产品手册、厂商技术文件 |
| E4_guideline | 机构指南、行业指南、操作手册 |
| E5_inference | 专家推导、案例归纳、模型辅助判断 |

### 3.5 分级审核

生产链必须经过审核。候选卡、候选规则、候选追问题都不能直接进入正式运行时。

但所有资产都走同一深度人工审核，会造成审核疲劳和专家瓶颈。因此建议分级：

| 审核等级 | 适用对象 | 审核方式 |
|---|---|---|
| L1 自动校验 + 抽查 | 低风险、来源清楚、无冲突的 slot、追问题、低风险提示 | schema 校验、重复校验、冲突校验、抽查 |
| L2 快速人工审核 | 一般经验卡、一般规则、任务书条款 | 看摘要、证据、适用边界、冲突提示 |
| L3 深度专家审核 | 法规、安全、施工、设备硬尺寸、投资测算、高争议判断 | 专家逐条审核 |

L1 不等于无审核。合规、安全、消防、食安、设备硬尺寸、收益预测等高风险内容不得走 L1 自动通过。

审核界面应主动提示：

- 与哪些已有资产可能冲突。
- 证据来源是什么。
- 适用边界是什么。
- 是否涉及硬规则。
- 是否需要领域专家和知识架构师双重审核。

### 3.6 package registry 的真实作用

`package registry` 是生产管理账本，不是运行时长文知识源。

它负责记录：

- 这个研究包是否登记。
- 拆出了哪些卡、规则、slot、问题、指标。
- 哪些已经审核。
- 哪些还缺证据。
- 关联哪些空间类型、子域和 lens。
- 当前生产进度和版本关系。

运行时不应该直接读 package registry 回答用户。运行时应该读 approved assets、规则库、追问题库和 context_packet。

### 3.7 API 提交与审核系统接入

外部生成链和内部自学习链接入知识资产审核系统时，应使用统一提交协议，但必须标明来源类型。

建议最小字段：

| 字段 | 说明 |
|---|---|
| source_type | `external_generation` / `internal_settlement` / `expert_note` / `case_material` |
| source_machine_id | 外部生成机器或内部服务标识 |
| batch_id | 批次 ID |
| asset_type | ResearchDossier / KnowledgeCard / ValidationRule / SlotDefinition / FollowupQuestion / ObservationMetric / SourceGap / PromotionCandidate |
| provenance | 来源路径、原文、URL、项目 ID、对话 ID 等 |
| checksum | 原文或资产内容校验值 |
| source_evidence_level | 出生证据等级 |
| lifecycle_status | 初始应为 candidate 或 needs_review |
| related_consumption_id | 内部自学习链来源时，关联消费台账 |
| related_settlement_event_id | 内部自学习链来源时，关联结算事件 |
| supersedes | 如为修订提案，指向被替代资产 |

管理后台应区分两类待审核队列：

| 队列 | 审核重点 |
|---|---|
| 外部生成链候选 | 来源可信度、拆分质量、证据链、适用边界、是否重复 |
| 内部自学习链提案 | 反馈证据强度、归因是否正确、是否个案噪声、是否应改 maturity 或召回边界 |

这两个队列可以共用审核组件，但不能混成一个普通“待审核列表”。审核人必须能一眼看出：这是新研究资料入库，还是系统根据真实项目反馈提出的修正建议。

## 4. 消费链：把资产变成答案

消费链解决的问题是：用户一句话进来，系统如何判断该用哪些知识，并以合适深度输出。

消费链必须快、稳定、只读。它不能直接修改知识库。

### 4.1 标准对话消费链

```text
用户输入
-> 空间分类
-> 参数提取
-> missing_slots
-> 冲突检测 / P1 熔断
-> 本体论 lens 激活分档
-> grid / facet 匹配
-> 召回 approved assets / 规则 / 追问题
-> context_packet
-> AdvisorAgent 姿态装配
-> 能力链执行
-> 封顶输出
-> 消费台账登记
```

### 4.2 入口处必须先做参数处理

用户首轮输入通常不完整。系统不能直接进入“生成完整方案”。

入口处必须完成：

| 环节 | 作用 |
|---|---|
| 空间分类 | 判断这是茶饮、咖啡、餐饮、住宅还是其他空间 |
| 参数提取 | 抓取面积、位置、预算、回本目标、场景、约束 |
| 参数补全 | 对缺失变量进行克制追问 |
| 冲突检测 | 判断是否存在明显不成立的目标组合 |
| P1 熔断 | 对安全、合规、硬物理条件不明的情况设置上限 |

例如用户说：

```text
深圳南山区来福士广场，负一楼，30 平米商铺，地铁通道与商场连接处，想做奶茶店，希望半年回本。
```

系统可以识别出：

- 茶饮空间。
- 小面积。
- 商场 / 地铁连接口。
- 高客流但高租金风险。
- 强回本目标。

但仍然缺少：

- 租金。
- 装修预算。
- 设备清单。
- 外卖占比。
- 给排水点位。
- 电量。
- 消防与排烟条件。
- 峰值单量预期。

因此输出必须封顶：可以给策略框架和风险判断，不能直接锁定施工尺度和收益结论。

### 4.3 本体论 lens 激活分档

运行时不建议继续混用“激活包”这个词。更准确的表达是：

```text
Lens Activation Profile / lens 激活分档
```

它表示在当前问题中，哪些正典专业视角被激活。注意，lens 不是主题、对象或空间类型。

错误示例：

| 错误说法 | 问题 |
|---|---|
| 水吧台 lens | 水吧台是空间对象，不是 lens |
| 高端会所 lens | 高端会所是空间类型或场景，不是 lens |

正确示例：

| lens | 状态 | 触发原因 |
|---|---|---|
| OperationFlow | active | 小面积、高客流、出杯效率是关键 |
| FunctionProgram | active | 水吧台、前场、后场、交接口需要组织 |
| MaterialMEP | active | 设备、水电、排水、散热强相关 |
| BusinessModel / CostRecovery | active | 用户提出半年回本 |
| BrandCommunication | active_light | 首轮可考虑品牌识别，但不是最急 |

正典 lens 名称以正式本体论和主架构为准。本文示例只说明“水吧台应激活哪些 lens”，不是另立 lens 列表。

### 4.4 Lens 激活条件应规则化

Lens 激活不能完全依赖模型临场判断，否则同一类问题每次激活结果可能不一致。

建议把激活条件沉淀为规则资产。例如：

```text
对象：水吧台相关问题
触发条件：
  - 空间类型属于茶饮、咖啡、调饮、小餐饮
  - 用户输入包含吧台、出杯、制作区、设备、给排水等信号
激活：
  - FunctionProgram = active
  - OperationFlow = active
  - MaterialMEP = active
  - BrandCommunication = active_light
```

这类规则属于生产链的“校验规则 / 激活规则”产物，应经过审核后进入运行时。

### 4.5 approved assets 的召回

运行时召回的不是 ResearchDossier 原文，也不是未审核候选卡，而是已批准资产。

召回依据可以包括：

- 空间类型。
- 子域。
- lens。
- grid 坐标。
- facet 标签。
- 当前缺失参数。
- 风险等级。
- 用户目标。
- 阶段深度。
- 资产成熟度。
- 适用边界。

召回结果进入 context_packet，而不是直接原样展示给用户。

### 4.6 context_packet 的作用

`context_packet` 是运行时推理包。它把当前项目相关信息组织起来：

- 用户输入。
- 已提取参数。
- 缺失参数。
- 已触发风险。
- 已激活 lens。
- 已召回 approved assets。
- 适用规则。
- 追问计划。
- 输出封顶。
- 可引用依据。

它不是一个给用户看的报告，而是给方案高参生成回答用的上下文。

### 4.7 三类封顶

方案高参必须真实、诚实。封顶不是一句口号，也不是单一等级。至少要区分三类封顶。

| 封顶类型 | 触发原因 | 作用对象 |
|---|---|---|
| 信息封顶 | 用户参数不足、missing_slots 过多 | 整体输出深度 |
| 覆盖封顶 | 当前空间或问题缺少 approved assets | 整体专业置信度 |
| 卡级权重 | 某张卡 maturity 低或 evidence 弱 | 单条判断表达强度 |

#### 信息封顶建议等级

| 等级 | 触发条件 | 允许输出 | 禁止输出 |
|---|---|---|---|
| L0 完整方案 | 参数完整度高，关键合规条件已确认 | 布局建议、设备范围、预算区间、阶段任务 | 不应超出证据承诺 |
| L1 条件方案 | 参数较完整，关键约束基本明确 | 功能分区比例、动线原则、风险清单 | 精确施工尺寸、设备型号锁定 |
| L2 策略框架 | 参数不足，但核心业态明确 | 业态判断、坪效逻辑、下一步建议 | 具体布局、精确预算数字 |
| L3 风险提示 | 参数严重不足或检测到硬冲突 | 核心风险、前置条件、不建议推进理由 | 任何方案性承诺 |

如果资料不够，应明确说：

- 现在只能做条件级判断。
- 不能锁施工尺寸。
- 不能保证半年回本。
- 不能替代消防、食安、施工图、设备深化。
- 哪些条件补齐后可以进入下一层判断。

### 4.8 消费台账

每次回答后，应登记消费台账。

| 字段 | 说明 |
|---|---|
| conversation_id | 对话 ID |
| project_id | 项目 ID，可为空 |
| user_query | 用户问题摘要 |
| classified_type | 空间分类结果 |
| activated_lenses | 激活的 lens |
| recalled_asset_ids | 被召回的 approved assets |
| consumed_asset_ids | 实际进入输出判断的 approved assets |
| recalled_not_used_ids | 被召回但未使用的资产 |
| rule_ids | 使用的规则 |
| missing_slots | 缺失变量 |
| ceiling_type | 信息封顶 / 覆盖封顶 / 卡级权重 |
| ceiling_level | 输出封顶等级 |
| answer_trace | 输出依据摘要 |
| review_time | 后续建议复盘时间 |

结算链只应优先处理 `consumed_asset_ids`。`recalled_not_used_ids` 不直接进入结算，但可用于优化召回质量。如果一张卡长期被召回却不被使用，说明 facet 可能过宽，或资产质量不足。

### 4.9 任务书编译消费链

消费链不只有对话问答。任务书条款类资产的消费者是项目态的任务书编译链。

任务书编译消费链可以简化表示为：

```text
项目档案 / 已确认参数
-> 阶段目标
-> 版本档位
-> taskbook clauses 召回
-> approved assets / 规则补强
-> 任务书结构编译
-> 阶段成果输出
-> 消费台账登记
```

这条链与对话消费链共享 approved assets、规则和消费台账，但输出对象不同：对话链输出回答，任务书链输出正式任务书或阶段成果。

## 5. 结算链：让知识持续变准

结算链解决的问题是：系统给出的判断，是否在真实项目中成立。

没有结算链，知识库就是静态仓库。120 个研究包建完后，知识开始过期、失效、互相冲突，系统却不知道。

有结算链，每个真实项目都会反过来提高知识质量。

### 5.1 标准结算链

```text
消费台账
-> 到期回访 / 用户主动反馈 / 项目实际观察
-> SettlementEvent
-> settlement_evidence_strength 判断
-> attribution 归因分流
-> maturity / 边界 / 召回规则调整建议
-> 重复观察聚合
-> PromotionCandidate
-> 人工裁决
-> 回到生产链
```

### 5.2 SettlementEvent

`SettlementEvent` 是知识结算事件。

建议记录字段：

| 字段 | 说明 |
|---|---|
| event_id | 结算事件 ID |
| source_consumption_id | 对应消费台账 |
| asset_id | 被验证的资产 |
| project_context | 项目条件摘要 |
| expected_effect | 当时系统的判断 |
| observed_result | 实际观察结果 |
| settlement_result | confirm / refute / inapplicable / needs_more_evidence |
| settlement_evidence_strength | 本次反馈证据强度 |
| attribution | 归因判断 |
| suggested_action | 升级、降级、失效、替代、补证据、修召回 |
| reviewer | 人工复核人 |

### 5.3 反馈证据强度

`settlement_evidence_strength` 表示本次反馈本身有多可信。它不同于资产出生时的 `source_evidence_level`。

| 等级 | 来源 | 能驱动什么 |
|---|---|---|
| S1 强证据 | 实际运营数据、出杯速度、坪效、翻台率、施工记录等可量化材料 | 可直接触发成熟度升降建议 |
| S2 中等证据 | 用户具体反馈，有场景但缺少数值 | 触发补充观察，谨慎调整 |
| S3 弱证据 | 用户主观感受，缺少具体场景 | 仅做标记 |
| S0 无效 | 模型自行推测、无法验证的假设 | 不进入结算链 |

### 5.4 归因闸

`refute` 不能直接导致卡片降级。反馈进入结算链后，必须先做归因。

| 归因 | 含义 | 处理方式 |
|---|---|---|
| card_wrong | 卡本身判断错误 | 可进入降级、修订或替代通道 |
| recall_wrong | 卡没错，是召回场景不对 | 修 facet、适用边界或召回规则 |
| execution_deviation | 用户没有按建议执行 | 不降卡，记录执行偏差 |
| weak_observation | 观察本身不可靠 | 挂起，等待更多证据 |
| inapplicable | 当前场景不适用 | 补边界，不否定整张卡 |

只有 `card_wrong` 且证据强度足够时，才允许进入成熟度降级通道。

### 5.5 回访时间

不同卡片适合不同验证窗口。消费台账登记时，应根据资产类型建议回访时间。

| 验证窗口 | 适合结算的资产类型 |
|---|---|
| 开业 1 周 | 动线拥堵、出杯卡点、交接口拥堵 |
| 1 个月 | 设备布局、后场效率、初步坪效 |
| 3 个月 | 复购相关空间体验、传播成图率 |
| 6 个月以上 | 回本模型、装修耐久性、长期运营适配 |

### 5.6 成熟度治理

成熟度影响运行时使用方式。低成熟度只能作为提醒，高成熟度才可作为强约束。

结算链主要改变 `maturity`，不直接改变 `source_evidence_level`。

若多次结算发现原卡适用边界过宽，应优先补边界或生成新版本，不应粗暴删除。

### 5.7 自我进化、自我迭代、自我学习

方案高参需要具备自我进化、自我迭代、自我学习能力，但这不是“模型自动改知识库”，而是受治理的学习闭环。

三者可以这样区分：

| 能力 | 含义 | 所属链路 |
|---|---|---|
| 自我学习 | 从用户对话、项目反馈、真实观察中发现新信号 | 消费链产生信号，结算链沉淀证据 |
| 自我迭代 | 根据证据调整卡片边界、成熟度、召回规则、追问策略 | 结算链提出建议，生产链审核落位 |
| 自我进化 | 形成新卡、新规则、新 slot、新指标，甚至推动空间分类或本体论升级 | 生产链正式沉淀，重大变化进入人工治理 |

自我学习的入口在消费链。系统可以从对话中记录：

- 哪些问题反复出现。
- 哪些 missing_slots 经常导致封顶。
- 哪些追问用户愿意回答。
- 哪些知识被频繁召回但没有被使用。
- 哪些项目条件反复触发风险。

自我学习的证据沉淀在结算链。系统必须通过 SettlementEvent 判断：

- 反馈证据强度是否足够。
- 归因是卡错、召回错、执行偏差，还是场景不适用。
- 该反馈是否能影响 maturity。
- 是否需要生成 PromotionCandidate。

正式进化发生在生产链。只有经过审核后，系统才可以：

- 新增 approved asset。
- 修订卡片适用边界。
- 调整召回规则。
- 提升或降低 maturity。
- 标记 stale 或 superseded。
- 生成新的 slot、追问题、任务书条款或观测指标。

系统内循环接入知识资产审核系统时，只能提交提案，不拥有批准权：

```text
ConsumptionLedger / SettlementEvent
-> internal proposal
-> 知识资产审核系统
-> 管理后台人工复核
-> approved 后才进入正式知识库
```

系统禁止以下行为：

- AI 因一次回答直接生成 approved asset。
- AI 因一次用户吐槽直接降级高价值卡。
- AI 自动修改空间分类、本体论或 schema。
- AI 自动把临场推断写入正式知识库。
- AI 对用户宣称“已经学会了”但没有可追溯证据。

因此，方案高参的自我学习应遵守：

```text
消费链产生学习信号
-> 结算链形成证据和归因
-> 生产链审核沉淀
-> 消费链下次读取新版本
```

这套机制的目标不是让系统“自动相信自己”，而是让系统在真实项目反馈中逐步变准，同时保留人工治理、证据链和可回滚路径。

## 6. 关键对象边界

### 6.1 ResearchDossier

ResearchDossier 是知识生产源材料，不是每次方案输出后的推理记录。

它用于：

- 保存完整研究脉络。
- 提供证据来源。
- 生成候选卡、规则、slot、追问题、指标。
- 支撑人工复核。

它不应该：

- 被运行时直接整篇读取回答用户。
- 绕过审核进入正式知识库。
- 代替 approved assets。

### 6.2 Candidate Assets

Candidate Assets 是候选资产，可以是卡、规则、slot、追问题、指标、任务书条款等。

它们还不能被运行时使用。

### 6.3 Approved Assets

Approved Assets 是已审核、可运行时调用的知识资产。

它们是生产链和消费链的合法交汇点。

```text
生产链写入 approved assets
消费链读取 approved assets
结算链修正 approved assets 的成熟度和边界
```

### 6.4 Knowledge Package

Knowledge Package 不应成为第二真相源。

它更准确的定位是：

```text
某个 SpaceType / Subdomain 下 approved assets 的派生查询视图
```

它可以用于管理和召回组织，但不独立裁决：

- 哪些卡一定可用。
- 哪些卡一定不可用。
- 哪些卡只能弱提醒。
- 哪些卡需要满足条件。

这些判断应来自：

- lifecycle_status。
- maturity。
- source_evidence_level。
- grid / facet。
- unlock_condition。
- 规则优先级。

如果工程上保留 Knowledge Package 实体，也必须明确它只是视图或索引，不保存与卡库冲突的第二套事实。

### 6.5 Package Registry

Package Registry 是包级生产账本。

它不直接参与运行时回答，只记录生产状态、审核状态、覆盖缺口和版本关系。

### 6.6 Lens Activation Profile

Lens Activation Profile 是运行时专业视角激活状态。

它激活的是正典 lens，而不是主题、对象、空间类型。

### 6.7 ConsumptionLedger

ConsumptionLedger 是消费台账。

它记录每次回答召回了什么、真正使用了什么、触发了什么规则、缺了什么参数、输出被封顶到哪一级。

### 6.8 ProjectDossier

ProjectDossier 是项目档案。

它记录某个具体项目的上下文、关键判断、用户选择、版本演进和后续反馈。

不要把 ProjectDossier 与 ResearchDossier 混用。

### 6.9 Knowledge Asset Review System

Knowledge Asset Review System 是知识资产审核系统，管理后台是它的主要人工操作界面。

它的职责是：

- 接收外部生成链提交的候选资产。
- 接收内部自学习链提交的修正提案。
- 展示证据链、来源、diff、冲突、适用边界和风险等级。
- 支持 approve / reject / needs_revision / supersede。
- 将 approved assets 写入正式知识库。
- 保留审核记录、审核人、审核时间和回滚依据。

它不应该：

- 直接参与普通用户对话生成。
- 把未审核候选资产暴露给运行时消费链。
- 让外部生成链或内部自学习链绕过审核写入正式知识库。

## 7. 冲突优先级

当规则、卡片、模型推断发生冲突时，必须有稳定优先级。

建议原则：

```text
硬规则 > 校验规则 > approved assets > 模型临场推断
```

其中硬规则包括：

- 法规。
- 安全。
- 消防。
- 食安。
- 设备硬尺寸。
- 物理不可行条件。
- 明确施工前置条件。

经验卡不能覆盖硬规则。模型临场推断不能覆盖 approved assets。

## 8. 术语纠偏

| 容易混淆的说法 | 问题 | 建议口径 |
|---|---|---|
| 运行时读取知识包正文 | 会取消拆卡意义 | 运行时读取 approved assets 和规则 |
| ResearchDossier 由每次回答生成 | 混淆研究源和项目记录 | 回答后生成 ConsumptionLedger / ProjectDossier |
| 激活包负责唤醒卡片 | 混淆建设期和运行期 | 运行期叫 Lens Activation Profile |
| package registry 参与 runtime recall | 把生产账本当知识源 | registry 只记账，runtime recall 读卡库 |
| Knowledge Package 自行裁决可用性 | 形成第二真相源 | Knowledge Package 只能是派生视图 |
| 卡片就是全部知识资产 | 漏掉规则、slot、问题、指标 | 使用多物种分拣 |
| 只要 RAG 就能解决知识库 | 缺审核、边界、成熟度、结算 | RAG 只是召回手段之一 |
| 召回等于消费 | 会污染结算链 | 区分 recalled、consumed、recalled_not_used |

## 9. 以水吧台尺度研究包为例

以 `I01_BarCounterDimension_水吧台尺度` 为例，正确处理方式如下。

### 9.1 生产链处理

```text
I01 原文
-> 登记为 ResearchDossier
-> 解剖清点
-> 多物种分拣
-> 分级审核
-> approved assets / 规则 / slot / 追问题 / 指标 / SourceGap 入位
```

可能产出：

| 产物 | 示例 |
|---|---|
| 判断卡 | 水吧台不是单一高度，应分制作、洗区、交接层 |
| 尺度卡 | 制作台、湿区、交接台、高位展示、低位服务段的推荐范围 |
| 规则 | 设备开门包络未确认时，不能锁死后场通道 |
| slot | 设备清单、给排水点、电量、峰值单量、员工数 |
| 追问题 | 是否做外卖？是否有堂食？是否需要明档？ |
| 失败模式 | 台面过深导致高频动作越界，台下设备开门堵住主通道 |
| 观测指标 | 出杯时间、员工绕行动作、顾客交接口拥堵 |
| SourceGap | 品牌手册、真实设备、施工节点未确认 |

### 9.2 消费链处理

用户问：

```text
30 平米商铺，地铁通道与商场连接处，想做奶茶店，半年回本，需要完整设计建议。
```

系统不应直接给施工尺度，而应：

1. 分类为茶饮空间。
2. 激活 OperationFlow、FunctionProgram、MaterialMEP、BusinessModel / CostRecovery 等 lens。
3. 召回水吧台尺度相关 approved assets。
4. 识别缺失参数：设备、租金、电量、给排水、峰值单量。
5. 输出条件级建议：
   - 水吧台要按制作、洗区、出杯交接分层。
   - 台下设备开门和散热必须预留。
   - 30 平小店不能用超长单线牺牲后场效率。
   - 半年回本不能只靠装修判断，必须结合租金、客单、单量和设备投入。
6. 记录消费台账，区分 recalled 和 consumed。

### 9.3 结算链处理

项目后续反馈：

```text
高峰期台下冰箱开门挡住后场，员工需要绕行，出杯速度下降。
```

系统应生成 SettlementEvent：

- 对应资产：台下设备包络卡。
- 结果：confirm。
- 证据强度：若有出杯时间、绕行动线记录，可为 S1；若只有口头描述，可为 S2。
- 归因：card_validated。
- 建议：提升该卡成熟度，增强“设备门开启包络必须纳入后场通道校验”的规则权重。

如果反馈是：

```text
某类极小店采用不同设备后没有发生拥堵。
```

则可能生成：

- 结果：inapplicable。
- 归因：当前卡适用边界过宽或当前场景不同。
- 建议：补充适用边界，而不是否定整张卡。

## 10. 当前系统完善度判断

按三链路标准，当前系统不能视为完整成熟。

| 链路 | 当前判断 | 主要缺口 |
|---|---|---|
| 消费链 | 有前半骨架 | 缺消费台账、三类封顶、approved assets 稳定召回 |
| 生产链 | 有文档规范和方向 | 缺多物种分拣、分级审核、入位、registry 闭环 |
| 结算链 | 基本未建立 | 缺 ConsumptionLedger、SettlementEvent、归因闸、maturity 治理 |

因此，后续不应继续只扩展概念，而应补工程闭环。

## 11. 推荐实施优先级

### P0：建立最小三链闭环

以一个研究包先跑通最小闭环：

```text
I01 水吧台尺度
-> 手工拆分多物种
-> 分级审核
-> approved assets 入位
-> 奶茶店测试题召回
-> 手工最小消费台账
-> 模拟 SettlementEvent
```

P0 阶段不要求先完成结构化台账系统。可以先用手工表格或最小 JSON 记录消费台账，证明链路成立。

但 P0 不能宣称“三链全部验证完成”。I01 可以验证尺度、设备、slot、追问、消费台账雏形，但不能完整验证 P1 熔断词表和硬否决通道。后续需要用 H04 或类似强约束研究包补验。

### P1：建立多物种 schema

需要定义：

- KnowledgeCard
- ValidationRule
- SlotDefinition
- FollowupQuestion
- TaskbookClause
- ObservationMetric
- SourceGap
- FailureMode

同时明确 lifecycle_status、maturity、source_evidence_level 三个正交维度。

### P2：建立结构化消费台账

记录每次回答：

- 召回了哪些资产。
- 实际使用了哪些资产。
- 哪些召回后未使用。
- 触发哪些规则。
- 缺哪些参数。
- 为什么封顶。
- 什么时候建议复盘。

### P3：建立结算事件

支持真实项目反馈：

- confirm
- refute
- inapplicable
- needs_more_evidence

并增加：

- settlement_evidence_strength。
- attribution 归因闸。
- maturity 调整建议。
- 召回规则修正建议。
- 边界修正建议。

### P4：批量处理 120 个研究包

只有在 I01 跑通后，才适合批量吸收 120 个研究包。否则批量入库只会制造大量未经治理的资料。

批量前必须具备：

- 分级审核。
- 冲突检测。
- 多物种分拣。
- 手工或结构化台账。
- 最小结算事件样例。

## 12. 最终原则

方案高参知识资产系统的基本原则如下：

1. 原文必须保留，但不能直接代替知识卡。
2. 候选知识必须审核，不能直接进入运行时。
3. 运行时只读 approved assets。
4. Knowledge Package 是派生视图，不是第二真相源。
5. Package Registry 是生产账本，不是答案来源。
6. 用户输出必须用人话，不暴露内部术语。
7. 缺参数时必须封顶，不能不懂装懂。
8. 封顶要区分信息封顶、覆盖封顶、卡级权重。
9. 真实项目反馈必须先做证据强度和归因判断，再影响知识成熟度。
10. 规则优先于经验卡，approved assets 优先于模型临场推断。
11. 自我学习必须可追溯、可审核、可回滚，不能绕过人工治理直接改正式知识。
12. 外部生成链和内部自学习链都只能进入知识资产审核系统，不能直接写入正式知识库。
13. 120 个研究包的价值，不在“存进去”，而在“拆得准、审得住、用得出、能结算”。

一句话总结：

```text
生产链让知识进得来。
消费链让知识用得出。
结算链让知识变得准。
治理闸口让学习可信、可控、可追溯。
```
