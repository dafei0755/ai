## 零、本文在全流程中的位置

设计任务书（原"需求分析"）是项目态 4 大节点主链的第三节点，连接门禁与方案高参：

```text
用户输入 → 门禁 → 【设计任务书（S1→S5）】 → 方案高参
                       ↑
                    本文覆盖范围
```

**关键说明**：设计任务书阶段的产出本身就可作为阶段性独立交付物，其中 DesignTaskBook 冻结即为系统的主价值输出里程碑。S1-S5 的内部步骤继续按五步推进。

需求分析的核心使命：

> **把模糊需求编译成冻结的设计任务书（DesignTaskBook），为实施执行提供稳定输入。**

$$
DesignTaskBook = 空间命题 + 驱动力排序 + 边界压缩结果 + 战略取舍 + 专题任务结构
$$

## 一、为什么是五步

### 1.1 旧四步的问题

旧四步（S1 理解输入、S2 看清重点、S3 定下取舍、S4 确认任务书）把"看清重点"和"定下取舍"混在同一大步，导致：

- 战略级判断（"这个项目到底站哪边"）和专题级判断（"动线如何组织"）混在 S2 一锅炖
- 系统开始讨论"动线怎么组织"时，设计师可能还没想清楚战略方向

### 1.2 五步的核心改动

把旧 S2"看清重点"拆分为三个不同维度的讨论层：

| 旧四步 | 新五步 | 关系 |
|---|---|---|
| S1 理解输入 | S1 拆 | 对应，更克制 |
| S2 看清重点（目标动机段） | S2 目标锁定 | 独立化 |
| S2 看清重点（战略级） | S3 战略框架 | 分层独立，含内嵌冻结 |
| S2 看清重点（专题级）+ S3 定下取舍 | S4 战术分解 | 分层独立，含内嵌冻结 |
| S4 确认任务书 | S5 形成成果 | 对应，补质量保障 |

### 1.3 核心设计决策

1. **战略与战术是两个不同的讨论场**，不是同一条线从粗到细的展开。
2. **取舍冻结不独立成步**，分别内嵌在 S3（冻结方向取舍）和 S4（冻结任务结构）的闭环中。
3. **S3→S4 有维度跨越门禁**：战略不定，绝不进入战术。
4. **S4→S3 有回退机制**：战术发现战略方向物理不可行，必须正式回退。

## 二、流程总览

> S1 与 S2 在实际执行中存在交叉——用户第一次输入缺乏完整的目标动机，S1 v1 天然不足以支撑 S3+。
> 解法：S1 产出显式拆为三个版本，S1→S2 之间插入 Echo Card 对齐，S2 完成后通过两步回填形成 S1 v3，S3 入口增加 `S1_v3_complete` 门禁。

```text
S1 拆·v1（零推断，字面原料化）
  ↓
[Echo Card] 回声确认卡（非独立步骤）
  ├─ context_basis：   从原始表达提取的基础信息
  ├─ open_items：      仍待确认的关键字段
  ├─ objective_frame： 项目目的初步整理
  ├─ deliverable_scope：本轮交付物范围与边界
  ├─ success_criteria：完成标准
  └─ decision_priority：S2 将优先处理的判断顺序
  ↓（用户可纠偏 Echo Card）
S2 目标锁定（多轮追问 → 动机确认）
  ↓
[Step A] S1 v2 补全（内部动作，用户不感知）
  ├─ S2 确认事实 → explicit
  ├─ 推导但用户接受 → inferred（保留标注）
  └─ 仍悬空 → pending_validation
  ↓
[Step B] 缺口补全轮（按需触发，0..n 次；无缺口时跳过）
  └─ 基于 S2 揭露缺口，定向追问 → 用户针对性输入；可多轮直至缺口收敛
  ↓
S1 v3 = S1 v1 + S2 目标动机回填 + 缺口补全轮累计输入（无缺口时 v3 = v2）
  ↓
[S3 入口门禁] S1_v3_complete == true
  ↓
S3 战略框架（董事会级讨论场）
  ├─ 内部：激发盲区 → 识别决定性矛盾 → 冻结方向取舍
  └─ 退出：方向已定，战略取舍已冻结
  ↓
[feasibility_analyst] 外部可行性复核（技术/成本/工期/风险）
  ↓
S4 战术分解（总设计师级讨论场）
  ├─ 内部：基于已冻结方向按专题展开 → 识别专题矛盾 → 冻结任务结构
  ├─ 回退：若发现战略方向不可行 → 回退 S3
  └─ 退出：任务结构可被执行阶段消费
  ↓
S5 形成成果（编译交付）
  └─ 退出：任务书冻结，用户确认
```

### S1 的三个版本

| 版本 | 来源 | 性质 | 可进入 |
|---|---|---|---|
| **v1** | 用户第一次自由表达后的零推断整理 | 字面原料，动机层空白 | 仅作 Echo Card / S2 参考 |
| **v2** | v1 + S2 确认的目标动机回填（内部动作） | 有方向、细节仍不足 | 支撑缺口定位，不可进 S3 |
| **v3** | v2 + 缺口补全轮（**按需，0..n 次**；无缺口时 v3 = v2） | 完整可执行基线 | **S3 的唯一合法入口** |

## 三、一主两辅推进方法

### 3.1 为什么需要中层方法

流程（五步）回答"什么时候做什么"；武器（25 件）回答"由哪个工具来做"。
但还需要一层稳定的推进骨架，回答"这一阶段沿着什么主线往前走"。

这套中层方法是：

- **一主**：空间命题主线
- **两辅**：人的驱动力修正轴、实施边界压缩轴

> 方法论升级注记：
> 从 2026-03-22 起，“一主两辅”不再仅作为本章节中的推进经验，而是与多学科协同形成统一执行协议。
> 参见：`../../2026.3.22/S-方法论/一主两辅与多学科协同方法论.md`（含角色责任、冲突仲裁、门禁与冻结签署规则）。

它的推进逻辑不是三条线并排展开，而是：主线推进 → 辅轴介入 → 三者交叉处冻结取舍。

### 3.2 一主：空间命题主线

需求分析最终要交付的不是抽象人性分析，而是**一个可被设计、拆解、验证、执行的空间任务对象**。因此主线只能落在空间上，且不是"空间类型主线"，而是"空间命题主线"：

$$
空间类型 \rightarrow 空间任务 \rightarrow 空间命题
$$

- **空间类型**：负责进入正确分析框架
- **空间任务**：负责展开活动与关系
- **空间命题**：负责形成需求分析真正要冻结的对象

一个完整的空间命题至少回答：
- 这个空间服务哪些核心活动
- 活动之间如何组织
- 谁是核心用户，谁是次级用户
- 当前最重要的矛盾是什么
- 空间最终要达成什么结果

> ⚠️ 后续步骤不是只给入口框架"补细节"，而是对它持续**补充、修正、压缩，必要时重构**。最终冻结的是经过主线推进、驱动力修正、边界压缩后形成的稳定任务基线，而不是初始空间类型判断本身。

### 3.3 第一辅轴：人的驱动力修正轴

空间被要求变成某种样子，背后有人在驱动：甲方、使用者、家庭成员、品牌方、运营方、投资方……

这条轴主要修正三件事：
1. **识别真正的动因**：为什么现在必须做？谁最在意？不做会怎样？
2. **识别多方驱动力的冲突**：品牌要表达、运营要效率、用户要舒适、投资要回报，往往不一致。
3. **识别谁的权重更高**：需求分析不是平铺诉求，而是形成排序。

> 一句话：**空间为什么会被这样要求，而不是那样要求。**

### 3.4 第二辅轴：实施边界压缩轴

实施边界必须在分析过程中持续压缩空间命题的可行区间，而不是最后才出现。边界包括：造价、工期、法规、消防、结构、地理位置、现状条件、气候/环境、产权与法律、运营方式、施工条件等。

> 一句话：**把空间命题从愿望压缩成可实现版本。**

### 3.5 推进顺序

推进不是三条线并排平推，而是：

```text
1. 从空间类型进入 → 建立初始入口框架（可工作的第一版瞄准面）
2. 围绕空间命题推进 → 把"空间对象"推进成"空间任务"再到"空间命题"
3. 用驱动力修正方向 → 确认是谁、为什么、以什么优先级推动这个空间变化
4. 用实施边界压缩范围 → 持续用现实条件压缩可行区间
5. 在三者交叉处冻结取舍 → 最终冻结的是稳定任务基线，不是原始信息
```

### 3.6 在五个步骤中的嵌合

| 步骤 | 一主两辅的承载 |
|---|---|
| **S1** | 识别初始空间对象、初始驱动力线索、初始边界线索；产出 S1 v1，输出 Echo Card |
| **S2** | 锁定核心目标动机；完成后 v2 内部回填，缺口补全轮收敛形成 v3 |
| **S3** | 空间命题展开可能性方向 + 驱动力排序 + 边界初步压缩 → 冻结方向取舍（宪法级） |
| **S4** | 在空间命题 + 驱动力排序 + 边界压缩的交叉处，形成专题级冻结结果 |
| **S5** | 把冻结结果编译为统一交接对象（`compile_handoff` 意图） |

> 执行口径补充：
> S3/S4/S5 的冻结与回退除沿用本文规则外，新增遵循“无主线不协同、无证据不冻结、无仲裁不推进”的协同门禁。

## 四、三层关系：流程 / 武器 / 知识底盘

### 4.1 流程负责节奏

流程回答：什么时候只整理输入、什么时候把问题看清、什么时候做选择、什么时候把结果定稿。

如果没有流程，武器会乱开火，知识底盘也会被胡乱消费。

### 4.2 武器负责认知动作

武器回答：怎么拆、怎么辨、怎么比、怎么挑、怎么压、怎么定、怎么交接。

武器不是答案库，而是**认知动作库**。

### 4.3 知识底盘负责证据供给

知识底盘回答：为什么这样分类、为什么这样问、为什么这样判断、为什么这条红线不能碰、为什么这个案例值得参考。

知识底盘不是分析器，而是**规则、矩阵、案例、项目记忆的供弹系统**。

> **底层三层为根，五步流程为壳，一主两辅为法。**

## 五、各步骤定义

### S1 拆

| 项目 | 内容 |
|---|---|
| **功能** | 把原始表达整理成可分析原料（产出 S1 v1；经 S2 两步回填后升至 v3） |
| **讨论维度** | 纯事实层 |
| **认知模式** | 严谨、克制、零推断 |
| **动作** | 字面拆解原始表达；分离事实 / 推断 / 偏好；识别初始边界与缺口；区分 explicit / inferred / pending_validation |
| **边界红线** | 不做深层挖掘，不做价值判断，不启动大规模追问，不展示分析结论 |
| **退出条件（v1）** | 原料已干净到可以输出 Echo Card 并进入 S2 |
| **退出条件（v3）** | S2 完成 + 缺口补全轮收敛，`S1_v3_complete == true` |
| **一主两辅** | 识别初始空间对象、初始驱动力线索、初始边界线索 |
| **主骨架武器** | A1 需求信号解析器、F1 事实推断分离器、F2 根本需求追溯器、F3 关键洞见提炼器、A2 信息充足度评估器、A3 交付边界锁定器 |

**Echo Card（高规格信息对齐卡）**—— S1 v1 完成后、S2 启动前输出给用户：

| 字段 | 内容 | 规则 |
|---|---|---|
| `context_basis` | 从原始表达提取的基础信息（项目类型/场地/品牌参照/目标人群） | 先展示，作为依据层 |
| `open_items` | 尚未明确但影响后续判断的待确认项（面积/预算/房量/运营方式等） | 允许为空，后续继续回收 |
| `objective_frame` | 系统对“这次项目到底要什么”的初步整理 | 必须可编辑，不得强行定稿 |
| `deliverable_scope` | 本轮交付物范围 | 必须明确 In / Out |
| `success_criteria` | 判断本轮是否完成的标准 | 至少覆盖品牌/场地/成本三个维度 |
| `decision_priority` | 后续裁决的优先级顺序 | 用于 T2 议题排序 |

**ExpertTeamPack（专家团队包）**—— S1 v1 完成后、与 Echo Card **同步生成** 的 S1 副产物，驱动 T1.5 梦幻团队组建：

> S1 在整理原材料过程中运行现有武器（B4 使用者身份识别器 / C1 跨领域视角激活器 / C2 多方利益梳理器），将匹配结果汇总为 `ExpertTeamPack`，在 T1 信息对齐卡用户确认之后、S2 目标追问之前出示给用户（即 T1.5 梦幻团队组建卡）。

| 字段 | 内容 | 规则 |
|---|---|---|
| `core_members` | 固定 3 人核心层（空间设计总统筹 / 用户研究专家 / 实施边界顾问）| 每个项目必有，不随信号变化 |
| `project_matched` | 基于项目信号匹配的动态扩展层专家列表，每人标注触发来源 | 由信号匹配算法生成，见 `../H-1 用户/05-专家角色库与动态匹配规则-Copilot-2026-03-19.md` §三 |
| `optional_layer` | 深度感知层专家候选（T4 后激活）| 系统推荐，用户可预选 |
| `tension_pairs` | 匹配结果中识别到的跨链张力对（自动标注）| 生成 T2-a 的张力议题卡来源 |

**Research Brief Pack（基础研究呈现包）**—— T1.5 团队确认后、S2 议程裁决前的前置子阶段（即 T2-a 角色事实亮相）：

| 字段 | 内容 | 规则 |
|---|---|---|
| `market_brief` | 区域市场与竞品事实底图 | 只给事实与启发，不做裁决 |
| `site_supply_brief` | 场地/气候/供应链与耐候性底图 | 必含执行风险提示 |
| `benchmark_breakthrough_brief` | 标杆对照与突破机会底图 | 标明可借鉴与不建议照搬 |

> T2-a 定位是“先研究呈现（非裁决）”，用户读完事实底图后再进入 S2-b 议程裁决，避免在信息不足时做价值取舍。

用户在 T1.5 确认 `ExpertTeamPack` 后，该包即冻结进入会话记录，后续议程提案（S2-a）将基于此生成 `proposed_by_roles` 字段。

### S2 目标锁定

| 项目 | 内容 |
|---|---|
| **功能** | 澄清贯穿项目的核心要素：目的、动机、要解决的问题、视角、输出物；完成后触发 S1 v2/v3 补全 |
| **讨论维度** | 动机与目的层 |
| **认知模式** | 主动追问、假设验证、下潜挖掘 |
| **动作** | 多轮追问，启发用户说出真正的需求；允许推导、假设、挖掘；识别"要什么"和"为什么"，但不进入"怎么做" |
| **边界红线** | 不进入解法设计，不启动策略框架搭建 |
| **退出条件** | 核心目标已锁定且用户确认，`S1_v3_complete == true`，足以支撑 S3 |
| **一主两辅** | 把空间对象推进成空间任务，锁定驱动力修正轴的核心功能 |
| **主骨架武器** | B1 任务目标提炼器、B2 目标冲突诊断器、B3 全局影响扫描器、B4 使用者身份识别器（后台）；按需：C1/C2/C3 |

**S2 内部三阶段子流程**（v1.4 同步，对应 H-1/01 的 T2-a/T2-b/T2-c 结构）：

S2 由三个连续子阶段组成：

```text
T2-a 角色事实亮相（Research Brief Pack，非裁决）
  ├─ 系统展示区域/场地/标杆三类事实底图
  ├─ 用户可追问事实，但不在此步做方向取舍
  └─ 用户点击"已读并继续" → 进入 S2-b
S2-b 议程提案与确认（与 T2 Step 1 对应）
  ├─ 系统展示议程提案卡：三类来源的讨论切口（六字段结构，详见下）
  │    用户明示型  → "你明确提到的"
  │    张力推导型  → "你描述里推导出的张力"
  │    行业补位型  → "你没提、但从这类项目来看值得看一眼"
  ├─ 用户操作：保留 / 删减 / 排序 / 添加自定义切口
  └─ 用户点击"确认本轮切口" → 进入 S2-c
S2-c 逐切口假设卡深挖（与 T2 Step 2 对应）
  ├─ 每个确认的切口对应一张假设卡（系统预填推断 + 候选选项）
  ├─ 对应专家在假设卡前第一人称开场（T1.5 后专家发言从 T2-b 开始）
  ├─ 用户执行 Confirm / Edit / Add / Defer
  └─ 所有切口假设卡完成 → S2 目标锁定完成
```

**S2-a 议程切口六字段结构**（v1.3 口径，同步 H-1/05 v1.8）：

每条议程切口由六个字段组成。前两字段为来源结构，后四字段为“全员发声 + 责任可追溯”机制新增：

| 字段 | 含义 | 示例 |
|---|---|---|
| ① 议题名称 | 切口标题 | HAY 气质在山地语境的落地方式 |
| ② `agenda_source` | 来源分类（`user_explicit` / `tension_derived` / `industry_supplement`）| `tension_derived` |
| ③ `sole_proposer` | 独立主提人（唯一） | HAY 品牌研究专家 |
| ④ `co_proposers` | 联提人（0..n） | 丹麦北欧生活研究员、室内设计总统筹 |
| ⑤ `nomination_reason` | 提案理由——不谈这条会影响哪里的判断 | 不先定"移植"还是"转译"，色彩和家具选型都会跑偏 |
| ⑥ `impact_scope` | 影响范围——色彩/动线/运营/品牌/客群/边界哪一层 | 风格主线、材料温度、公共区气场设定 |

`sole_proposer`/`co_proposers` 字段来源于已冻结的 `ExpertTeamPack`（结合专家视角扫描输出）。T1.5 用户确认团队后，S2-a 生成议程时自动关联对应专家。张力推导型切口（`tension_derived`）同时生成「⚡张力议题卡」置顶，需用户先裁决才可进入该切口的假设卡深挖。

此外，S2-a 必须同步输出 `Agenda Voice Ledger`：
- 主提：至少 1 条 `sole_proposer`；
- 联提：仅作为补充，不替代主提覆盖；
- 暂缓：必须显示“暂缓原因 + 激活条件”。

并将过程治理层信号并行落盘，供后续节点持续消费：
- T4：风险快照（进入 `risk_register`）；
- T5：跨专题一致性检查与仲裁记录（进入 `consistency_check_records` / `arbitration_notes`）；
- T6：风险三分法签署（进入 `risk_disposition_records`）。

> **设计原则**：先确认"接下来从哪些角度看这个项目"（S2-a），再确认"每个角度的判断是什么"（S2-b）。议程不透明时，用户对后续假设卡的配合度和准确率均会下降。

**S2 完成后的两步回填**：

```text
S2 目标锁定完成
  ↓
[Step A] S1 v2 补全（内部动作）
  ├─ S2 追问中用户明确确认的事实 → explicit
  ├─ 系统推导但用户接受 → inferred（保留标注）
  └─ 仍悬空 → pending_validation
  ↓
[Step B] 缺口补全轮（按需，0..n 次；无缺口时跳过）
  └─ 基于 S2 揭露缺口定向追问 → 用户输入 → 缺口收敛
  ↓
S1 v3 完成（无缺口时 v3 = v2）→ S3 入口放行
```

### S3 战略框架

| 项目 | 内容 |
|---|---|
| **功能** | 基于已锁定目标，分解解题大思路与策略方向，提供高质量的可选路径；冻结方向取舍 |
| **讨论维度** | 方向、定位、命题、取舍原则（董事会 / 宪法级） |
| **认知模式** | 宏观激发 + 受控发散 + 内嵌冻结 |
| **心智类比** | 董事会视角：讨论"这个项目到底站哪边" |

**S3 内部小循环**：
1. **激发盲区**：主动提出设计师没想到的命题方向、跨界参考、非常规可能性；提供 2-3 个高质量宏观策略候选。
2. **识别决定性矛盾**：把候选方向之间的核心冲突和代价差异显性化，使设计师能在"可比较的选择"中做判断。
3. **冻结战略取舍**：由设计师选定或融合方向后，冻结：主优先级、让位项、红线、取舍理由。

**S3 边界红线**：
- 不讨论具体空间方案、材质、尺寸等落地细节
- 不突破现实边界（法规、造价、结构等硬约束）
- 不偏离项目本质（核心功能定位和用户根本诉求）
- 候选之间必须是真差异，不允许只是措辞变化

**S3 退出条件**：战略方向已定、战略取舍已冻结、可以进入专题展开

**S3 核心产出**：冻结的方向定位 + 取舍原则 + 红线清单 + 延后项

**S3 必说武器**：D1 设计前提校验器、D2 约束条件识别器

### S4 战术分解

| 项目 | 内容 |
|---|---|
| **功能** | 基于已冻结的战略方向，按专题展开并细化为可交接的任务结构 |
| **讨论维度** | 各专题如何响应已定的战略（总设计师 / 专题策略级） |
| **认知模式** | 专业深度 + 降维翻译 + 内嵌冻结 |
| **心智类比** | 总设计师视角：讨论"各专题如何服从宪法" |

**S4 内部小循环**：
1. **按专题展开**：将已冻结战略方向翻译到各具体维度（色彩策略、材质策略、动线策略、社交组织、灯光与氛围、运营兼容、品牌表达等），专题清单随项目类型动态调整。
2. **识别专题级矛盾**：具体展开中发现的落地冲突——是局部可调，还是必须回退战略层？
3. **冻结任务结构**：每个专题形成"优先级 + 让位项 + 红线 + 原则化规则"。

**S4 边界红线**：
- 所有展开必须溯源到 S3 的战略条文，不允许"违宪"细节
- 不讨论精确尺寸、材料品牌、节点做法、预算表、排期表、采购和施工组织
- 止步于专题级策略规则，不进入执行调度
- 不允许在战术层静默篡改战略层已冻结结论

**S4 回退规则**：
- 若 S4 发现 S3 冻结的方向因边界条件物理不可行 → 必须正式回退到 S3 发起修订
- 回退时须明确：哪条边界导致方向不可行、建议修订哪个战略取舍
- 不允许 S4 内部自行消化战略级矛盾

**S4 退出条件**：任务结构已形成；各专题有明确优先级、让位项、红线与原则化规则；任务结构可被下游消费

### 正向交接


## 七、S1–S2 用户视角路径（关键设计原则）

```text
用户第一次自由表达（"我想做一个山地民宿"）
  ↓
系统后台完成 S1 v1 整理（用户不感知，沉默）
  ↓
系统输出 Echo Card（主动呈现）
  ├─ "收到了什么"         → 事实摘要，只陈述不评价
  ├─ "打算帮您做什么"     → 初步意图猜测，标注是否为推测
  └─ "需要先明确的"       → 2-3 个目标/动机核心问题
  ↓（用户可直接纠偏）
S2：系统多轮追问目标动机（直至核心目标锁定，用户确认）
  ↓
系统后台完成 S1 v2 补全（沉默）
  ↓
缺口补全轮（按需，0..n 次；无缺口时跳过）
  ↓
S1 v3 完成 → 系统进入 S3 战略框架讨论
```

| 阶段 | 用户感知 |
|---|---|
| S1 v1 完成 | 沉默（后台整理，不打扰） |
| Echo Card | 系统主动呈现"三段对齐"，邀请确认或纠偏 |
| S2 追问 | S2 包含两个子流程：**①议程确认轮**（系统展示三类来源的讨论切口，用户确认/调整本轮切口清单）→ **②逐切口假设卡**（每个切口对应假设卡，用户执行 Confirm/Edit/Add/Defer） |
| S1 v2 补全 | 沉默（内部动作） |
| 缺口补全轮 | 系统提出少量具体问题 |
| S3 启动 | 系统表示"基础已经清晰，我们来讨论方向" |

**关键设计原则**：
- **不强制走完**：缺口补全轮 0 次也可进 S3（简单项目直接通过）
- **不重复说**：S2 确认的内容自动回填，不让用户第二次陈述同一件事
- **透明但不技术化**：Echo Card 让用户知道系统的理解，不暴露 v1/v2/v3 概念
- **可随时纠偏**：Echo Card 阶段修正成本最低
- **卡片节奏用户掌控**：所有卡片（T1–T6）响应后系统默认进入等待态，不自动弹出下一张；用户主动触发「继续下一步」才推进（详见 H-1/01 §1.4 等待态+气口区）

## 八、步骤与 T 时刻的对应关系

本文的 S 步骤是**系统内部视角**；用户感知视角对应 H-1/01 的 T 时刻，关系如下：

| 系统步骤 | 用户感知时刻 | 核心交互 |
|---|---|---|
| S1 v1（后台） + Echo Card | T1 信息对齐卡 | 依据确认 / 基线编辑 |
