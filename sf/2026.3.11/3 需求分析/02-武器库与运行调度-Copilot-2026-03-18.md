## 一、武器设计原则

### 1.1 核心约束

1. **武器不是答案，是认知动作** —— 每件武器对应一个具体的"怎么看"，而不是"得到了什么答案"。
2. **不同步骤的武器功能不可交换** —— A 组在 S1 整理，B 组在 S2 发声；不得跨阶段借用。
3. **武器的激活由 TriggerIntent 来定义** —— 调度器根据当前意图决定派哪件武器，不是把全部武器轮流过一遍。
4. **发声顺序受到保护** —— B 组必须按 B4→B1→B2→B3 顺序，D 组按 D1→D2 顺序；乱序发声会导致认知错配。
5. **条件武器有资格门槛** —— C 组武器触发需满足相关性分（relevance\_score）≥ 0.6 且不超过 2 件同时触发。

### 1.2 双轴理解

| 维度 | 含义 | 代表武器 |
|---|---|---|
| **驱动力修正轴** | 识别并校正"谁在驱动、为什么这样驱动"的力场 | B4, C2, C3, D1, F6 |
| **实施边界压缩轴** | 用现实约束（规范/造价/工期/结构）压缩可行区间 | D2, A3, B3, F9 |

两轴不是先后二选一，而是**围绕空间命题主线同时运作**：主线推进，两辅介入，三者交叉处形成冻结。

## 三、A 组：底座预处理武器（S1·全部后台运行）

> **阶段目标**：把原始输入整理成干净、分层、可分析的原料。全部对用户不可见。

---

### A1 — 需求信号解析器

| 属性 | 说明 |
|---|---|
| **功能** | 将原始需求拆解为三类信号：空间对象信号（What）、使用者信号（Who）、约束信号（Constraint） |
| **输入** | 用户原始表达（后验、非结构化的自然语言） |
| **输出** | 三类信号的初步分类结果，标注每类信号的置信度 |
| **执行时机** | S1 阶段第一步，所有其他武器排在其后 |
| **方法角色** | 主标签：底座预处理；副标签：— |
| **常见 TriggerIntent** | `advance_mainline` |
| **关键约束** | 禁止推断，只整理原始表达；若信号不足，标注为"信号不足"而不是强行分类 |

---

### A2 — 信息充足度评估器

| 属性 | 说明 |
|---|---|
| **功能** | 扫描 A1 初步分类结果，识别哪些关键槽位存在缺口，产出缺口清单，决定是否需要追问或后续 E1 补全 |
| **输入** | A1 分类结果 + 需求 Schema 必填字段定义 |
| **输出** | 缺口清单：`{ field, severity: critical/moderate/low, suggested_probe }` |
| **执行时机** | S1 阶段，A1 之后，输出供 E1 缺口补全轮使用 |
| **方法角色** | 主标签：横切校验；副标签：底座预处理 |
| **常见 TriggerIntent** | `cross_validate` |
| **关键约束** | critical 级缺口必须追问；low 级缺口可由 G3 推断兜底 |

---

### A3 — 交付边界锁定器

| 属性 | 说明 |
|---|---|
| **功能** | 从 A1 的约束信号中识别确定的边界条件（造价上限、工期、法规、结构等），写入边界状态，供后续武器参考 |
| **输入** | A1 分类中的约束信号 |
| **输出** | 边界条件清单：`{ boundary_type, value, source, certainty }` |
| **执行时机** | S1 阶段；S3 时由 D2 补充确认 |
| **方法角色** | 主标签：边界压缩；副标签：底座预处理 |
| **常见 TriggerIntent** | `compress_boundary` |
| **关键约束** | 此阶段只整理显式表达的边界，不做推断；推断性边界留给 D2 在 S3 时由用户确认 |

## 四、B 组：S2 必说武器（固定顺序，ALWAYS\_SPEAK\_S2）

> **发声顺序**：B4 → B1 → B2 → B3（受保护，不可乱序）
>
> **阶段目标**：锁定核心目标动机，识别结构性冲突，压缩影响范围。

---

### B4 — 使用者身份识别器（B 组首位）

| 属性 | 说明 |
|---|---|
| **功能** | 识别使用者身份（谁在用），推断身份背后的行为模式与诉求，为 B1–B3 的问题生成校准语气与视角 |
| **输入** | A1 的使用者信号 + F6 深层动机后台推断结果 |
| **输出** | 使用者身份画像（角色类型、主诉求、可能的隐性诉求） |
| **向用户展示** | 「在我们讨论目标之前——您的核心使用者是谁？他们最在意什么？」 |
| **执行时机** | S2 第一个发声，在 B1 之前；为 B1–B3 的追问口径服务 |
| **方法角色** | 主标签：驱动力修正；副标签：— |
| **常见 TriggerIntent** | `correct_driver` |
| **意图切换条件** | 用户确认使用者画像 → 切换到 B1 `advance_mainline`；若使用者存在多方冲突 → 在 B2 后自动触发 C2 |
| **reframe 入口** | 若中途发现使用者画像被根本推翻（如"不是自住，是出租"），应暂停 B1–B3 队列，重跑 B4 并重排 VoiceSlot |

---

### B1 — 任务目标提炼器

| 属性 | 说明 |
|---|---|
| **功能** | 从已校准视角（B4）出发，把用户的原始诉求提炼成"可执行的核心空间任务"表述 |
| **输入** | A1 空间对象信号 + B4 使用者画像 + F2 根本需求后台追溯 + F3 关键洞见 |
| **输出** | 核心空间任务表述：`{ task_statement, underlying_motivation, priority_tier }` |
| **向用户展示** | 「基于您的描述，我理解的核心任务是——[任务表述]。动机是——[根本动机]。这个理解准确吗？」 |
| **执行时机** | S2，B4 之后第一个发声 |
| **方法角色** | 主标签：空间命题推进；副标签：— |
| **常见 TriggerIntent** | `advance_mainline` |
| **意图切换条件** | 用户确认任务表述 → 推进 B2；用户否定任务表述 → 回到 B4 或上游缺口补全；用户补充大量新信息 → 触发 S1 v2 重补并暂停队列 |
| **reframe 入口** | 若用户否定根本动机层（不是"说法不准"，而是"整件事为什么做"发生根本转变），必须回退 B4 并重排队列 |

---

### B2 — 目标冲突诊断器

| 属性 | 说明 |
|---|---|
| **功能** | 识别多个目标之间的结构性冲突，区分"真冲突"与"可兼容但需排序的目标"，形成可供设计师做取舍的冲突诊断书 |
| **输入** | B1 核心空间任务 + B4 使用者画像 + 用户追问过程中补充的多目标陈述 |
| **输出** | 冲突清单：`{ conflict_pair, nature: structural/prioritization, implication, suggested_tradeoff }` |
| **向用户展示** | 「我注意到以下几个目标之间存在结构性张力——[冲突对 1]、[冲突对 2]。这些是真冲突还是您有明确的优先级？」 |
| **执行时机** | S2，B1 之后；若无冲突，简短发声并标注"目标一致性已确认"后推进 B3 |
| **方法角色** | 主标签：驱动力修正；副标签：横切校验 |
| **常见 TriggerIntent** | `correct_driver` |
| **意图切换条件** | 用户澄清冲突 → 推进 B3；若冲突解决过程中揭露多方利益主体 → 触发 C2；若揭露边界严格限制 → 触发 C3 或 D2 |
| **reframe 入口** | 若用户推翻某个目标优先级（不是"澄清"，而是"这个方向根本不对"），应回退 B1 并重排 B2 |

---

### B3 — 全局影响扫描器

| 属性 | 说明 |
|---|---|
| **功能** | 扫描当前空间决策可能带来的全局附带影响，包括：规范合规、运营可行、其他空间关系、使用者未来适应性 |
| **输入** | B1 空间任务 + B2 冲突冻结结果 + A3 边界清单 |
| **输出** | 全局影响风险清单：`{ risk_type, trigger_condition, mitigation_hint }` |
| **向用户展示** | 「如果按这个方向推进，有几个全局影响需要提前评估——[影响 1]、[影响 2]。这些在您的考虑范围内吗？」 |
| **执行时机** | S2，B2 之后；是 B 组最后一件发声武器 |
| **方法角色** | 主标签：边界压缩；副标签：横切校验 |
| **常见 TriggerIntent** | `compress_boundary` |
| **意图切换条件** | 用户确认全局影响清单 → S2 进入收口，转 S1 v3 补全流程；若全局影响暴露出未讨论的主体（如主管部门/投资方）→ 先触发 C2 |
| **reframe 入口** | 若影响扫描发现"这件事从根本上不可行"，不应继续 B3 自行兜底，应回退 B1 重构或向 feasibility_analyst 提前注入 blocker 信号 |

## 五、C 组：S2 条件触发武器（相关性驱动）

> **触发条件**：relevance\_score ≥ 0.6；每轮最多同时触发 2 件；插入 ALWAYS\_SPEAK\_S2 队列相应位置。
>
> **阶段目标**：在主骨架槽位触发特定条件时，补充专项分析视角。

---

### C1 — 跨领域视角激活器

| 属性 | 说明 |
|---|---|
| **功能** | 引入跨领域类比和非常规参考框架，突破设计师单一专业视角的盲区，提供 2–3 个颠覆性候选类比 |
| **触发条件** | 项目存在高不确定性 / 进入跨界场景（如共居、文旅、康养混合态）/ 设计师已表达"没什么思路" |
| **relevance\_score 计算** | 基础分 = 0；项目类型创新度高 +0.4；使用者需求模糊 +0.3；用户主动提到"参考别的行业" +0.3 |
| **向用户展示** | 「这个项目让我联想到——[跨界案例]。如果引入这类框架，可能解决的是——[问题]。值得参考吗？」 |
| **方法角色** | 主标签：空间命题推进；副标签：— |
| **常见 TriggerIntent** | `advance_mainline` |
| **意图切换条件** | 类比被接受 → 推进主线讨论；若类比引发驱动力重构 → 先回 B4/B1 吸收新框架再继续 |
| **reframe 入口** | 若跨领域视角让当前空间类型判断失效，触发 A1 重新分类，当前 VoiceSlot 重排 |

---

### C2 — 多方利益梳理器

| 属性 | 说明 |
|---|---|
| **功能** | 系统化梳理项目涉及的多方利益主体（委托方/使用者/运营方/品牌方/社区/主管部门），识别其诉求差异与权重关系 |
| **触发条件** | 识别到多方主体（如甲方和运营方立场不同）/ B4 画像有多个身份标签 / 用户提及机构、品牌、投资方 |
| **relevance\_score 计算** | 基础分 = 0；已识别 ≥ 2 个利益主体 +0.5；主体间有可见利益冲突 +0.4 |
| **向用户展示** | 「我注意到这个项目有多个利益主体——[主体清单]。他们的诉求分别是什么？谁的权重更高？」 |
| **方法角色** | 主标签：驱动力修正；副标签：横切校验 |
| **常见 TriggerIntent** | `correct_driver` |
| **意图切换条件** | 利益主体权重确认 → 更新 B4 身份画像后继续推进；若主体间冲突不可调和 → 回退 B2 重做冲突诊断 |
| **reframe 入口** | 若新增利益主体根本改变了"谁在驱动"的判断（如发现隐藏决策者），回退 B4 并重排整个队列 |

---

### C3 — 使用者行为模式引擎

| 属性 | 说明 |
|---|---|
| **功能** | 推断目标使用者群体的典型行为模式（活动序列、空间偏好、时间节律、社交结构），校准空间活动组织设计 |
| **触发条件** | 使用者行为模式高度特殊 / 用户提及特定生活方式 / 项目类型依赖特定使用模式（如老龄、儿童、青创） |
| **relevance\_score 计算** | 基础分 = 0；使用者群体特殊性强 +0.4；项目类型行为模式关键 +0.4；用户已提出行为相关诉求 +0.3 |
| **向用户展示** | 「基于您描述的使用者，我推断他们的典型行为模式是——[行为序列]。这些行为对空间组织有哪些特殊要求？」 |
| **方法角色** | 主标签：驱动力修正；副标签：— |
| **常见 TriggerIntent** | `correct_driver` |
| **意图切换条件** | 行为模式确认 → 更新 B1 任务表述的活动组织维度后继续；若行为模式与空间限制存在冲突 → 联动 B3 全局影响扫描 |
| **reframe 入口** | 若用户否定行为模式推断（"使用者其实不是这样的"），应重跑 B4 而不是只修正 C3 |

## 六、D 组：S3 战略框架·必说武器（ALWAYS\_SPEAK\_S3）

> **发声顺序**：D1 → D2（受保护）
>
> **阶段目标**：在 S3 内部，挑战 S2 结论的战略前提，并确认约束红线，为冻结取舍建立基础。

---

### D1 — 设计前提校验器

| 属性 | 说明 |
|---|---|
| **功能** | 站在 S3 战略框架立场，挑战 S2 目标锁定结论的隐含前提；识别哪些前提是"想当然"，而不是"真的被验证了" |
| **输入** | S2 目标锁定的核心结论（B1/B2/B3 输出的融合） |
| **输出** | 前提挑战清单：`{ assumed_premise, challenge_question, implication_if_false }` |
| **向用户展示** | 「在我们进入方向选择之前——有几个前提需要检验：[前提 1]、[前提 2]。这些是真的成立的吗？」 |
| **执行时机** | S3 战略框架第一个发声，在 D2 之前 |
| **关键约束** | 不能问"解法怎么做"，只能挑战"目标和前提本身" |
| **方法角色** | 主标签：横切校验；副标签：边界压缩 |
| **常见 TriggerIntent** | `cross_validate` |
| **意图切换条件** | 前提均成立 → 推进 D2；若某个前提被推翻 → 视影响范围：仅影响边界 → D2 处理；影响目标层 → 回退 B1/B2 |
| **reframe 入口** | 若前提挑战揭露 S2 目标本身已作废（如"项目的核心用途发生了根本变化"），必须回退至 S2 目标锁定，不得在 S3 内静默吸收 |

### D2 — 约束条件识别器

| 属性 | 说明 |
|---|---|
| **功能** | 在 S3 战略层，正式确认三类硬约束：造价类约束（最高预算/单方造价上限）、时间类约束（工期/上线节点/客观时间窗口）、规范类约束（消防/结构/环评/产权/法规） |

| **reframe 入口** | 若用户推翻已确认红线/硬限分类，重置 D2 当前结论，并回查受其约束的 S3 冻结项与 S4 编译候选 |

## 八、insight\_distiller 调度机制

### 8.1 定位

`insight_distiller` 是 S2 / S3 阶段的武器调度中枢，不直接生成最终任务书，职责如下：

1. 构建当前阶段应发声的武器队列（主骨架槽位 + 条件增强槽位）
2. 管理每件武器的 `VoiceSlot` 状态
3. 计算条件武器的相关性分（`relevance_score`）
4. 当主线重构时，精准失效依赖槽位并重排队列
5. 判断当前分析是否已达到"足以冻结"的阈值

### 8.2 TriggerIntent 五类

| TriggerIntent | 含义 | 典型激活场景 |
|---|---|---|
| `advance_mainline` | 推进空间命题主线 | 空间对象尚未锁定、任务表述尚在模糊阶段 |
| `correct_driver` | 修正驱动力 | 识别到多方主体、动机层冲突、使用者身份异常 |
| `compress_boundary` | 压缩实施边界 | 出现强边界信号（预算/规范/工期/结构） |
| `cross_validate` | 横切校验（跨轴） | 结论存疑、前提待验证、字段完整性需确认 |
| `compile_handoff` | 编译交接 | 冻结完成，准备生成任务书并向下游传递 |

### 8.3 VoiceSlot 五态

| 状态 | 含义 |
|---|---|
| `pending` | 尚未发声，待调度 |
| `delivered` | 已向用户展示结论，等待响应 |
| `responded` | 用户已回应（确认/修改/追问） |
| `skipped_by_user` | 用户明确跳过 |
| `invalidated` | 因主线重构/取舍变化/前提翻转作废，需重排入队 |

### 8.4 固定发声队列

**ALWAYS\_SPEAK\_S2**（S2 所有项目必过）：

```text
B4（使用者身份识别器）
→ B1（任务目标提炼器）
→ B2（目标冲突诊断器）
→ B3（全局影响扫描器）
```

**ALWAYS\_SPEAK\_S3**（S3 战略框架必过）：

```text
D1（设计前提校验器）
→ D2（约束条件识别器）
```

**CONDITIONAL\_SPEAK\_S2**（按 relevance\_score 插入）：

```python
if relevance_score(C1) >= 0.6:
    insert(C1, after=B1)   # 跨领域视角，在任务提炼后插入
if relevance_score(C2) >= 0.6:
    insert(C2, after=B2)   # 多方利益，在冲突诊断后插入
if relevance_score(C3) >= 0.6:
    insert(C3, after=B4)   # 行为模式，在身份识别后插入
# 每轮最多激活 2 件 C 组武器
```

### 8.5 AnalyticalCoverageTracker

```python
class AnalyticalCoverageTracker:
    """
    追踪分析覆盖率，判断是否可以进入下一步。
    使用新五步（S1-S5）的完成条件。
    """

    def s2_ready_to_close(self) -> bool:
        """S2 是否可以收口，进入缺口补全轮 / S3 前置流程"""
        return (
            self.b4_responded      # 使用者身份已确认
            and self.b1_responded  # 任务目标已提炼并用户确认
            and self.b2_responded  # 冲突诊断已完成（含无冲突确认）
            and self.b3_responded  # 全局影响已扫描
            and not self.has_open_critical_gaps()  # 无关键缺口
        )

    def s3_ready_to_close(self) -> bool:
        """S3 是否可以冻结，进入 feasibility_analyst"""
        return (
            self.d1_responded      # 前提挑战已完成
            and self.d2_responded  # 约束条件已用户确认
            and self.strategic_tradeoff_frozen  # 战略取舍已冻结
            and not self.has_s3_blocking_items()  # 无阻塞项
        )

    def invalidate_due_to_reframe(self, reframe_scope: str):
        """主线重构时，精准失效依赖此范围的所有 VoiceSlot"""
        if reframe_scope == "driver":
            # 驱动力重构：失效 B1-B3 和 C 组
            self.invalidate_slots(["B1", "B2", "B3", "C1", "C2", "C3"])
        elif reframe_scope == "space_object":
            # 空间对象重构：失效所有 S2 武器
            self.invalidate_slots(["B1", "B2", "B3", "B4", "C1", "C2", "C3"])
        elif reframe_scope == "strategic_premise":
            # 前提根本翻转：失效 D1/D2
            self.invalidate_slots(["D1", "D2"])
```

## 九、动态路由决策机制

### 9.1 为什么需要动态路由

需求分析不是固定问卷流水线，系统需要根据以下状态动态决定：
- 当前项目处于什么空间对象
- 空间主线推进到了哪里
- 人的驱动力是否出现冲突
- 实施边界是否已经把可行域压缩清楚

### 9.2 分层调度逻辑

| 槽位类型 | 机制 | 代表武器 |
|---|---|---|
| **主线槽位** | 优先完成，确认空间对象/任务/矛盾 | A1, F1–F3, B1, B2 |
| **修正槽位** | 检测到多方主体/角色冲突时自动插入 | C2, C3, B4（重新激活） |
| **压缩槽位** | 检测到规范/工程/边界信号时优先插入 | D2, A3, B3 |

### 9.3 典型路由情景

| 情景 | 系统行为 |
|---|---|
| 用户表达很散，但空间对象清楚 | 优先完成 S1 整理，再进入空间主线槽位 |
| 空间类型明确，但任务不清 | 提高 B1 优先级，先把空间对象推进成空间任务 |
| 项目出现多方利益主体冲突 | 自动插入 C2；若并发身份冲突，补充 C3 |
| 预算/规范/工期信号很强 | 提前提高 D2/A3 权重，用边界轴压缩可行区 |
| 用户否定关键冲突判断 | 相关依赖槽位 `invalidated`，回到 S2 主线重构 |
| S3 形成冻结候选后遇到 feasibility blocker | 回退 S2 或重做 S3 取舍（不能被任务书编译阶段硬吞）|
| 用户跳过个别条件武器 | 标记 `skipped_by_user`，若不影响关键冻结条件则推进 |

### 9.4 路由与门禁的关系

- **路由**：决定 S2/S3 中哪些武器发声、何时推进
- **门禁**：决定主链能否继续（参见 `03-交付合约与质量收口`）

即使路由判断"可以继续"，也不能跳过硬边界校验、feasibility blocker 检查、任务书确认与签署。

> **一句话总结**："路由负责选方向，调度负责给方向分配带有 TriggerIntent 的具体武器。"
