## 一、需求分析师 Agent 对外合约

### 1.1 合约定位

回答四个问题：**何时调用、必须产出什么、产出不足如何兜底、下游如何消费与验证。**

### 1.2 触发与输入

| 项目 | 内容 |
|---|---|
| **主触发节点** | `requirements_analyst` |
| **前置条件** | 通过初始输入门禁（`unified_input_validator_initial`） |
| **最小输入** | `user_input`（必需）+ `session_id`（建议） |

### 1.3 核心输出字段（S1 阶段产出）

| 字段 | 含义 |
|---|---|
| `structured_requirements` | 结构化需求（A1 信号分类结果） |
| `project_type` / 分类字段 | 空间类型标签 |
| `space_object_hint` | 初始空间对象识别结果 |
| `intent_baseline` | 任务定义原材料（已废弃 `task_framework`，以此替代）|
| `project_motivation` | 项目动机与驱动力线索 |
| `initial_gap_map` | 初始缺口图，供 S2 内部缺口补全轮使用 |
| `delivery_boundary` | A3 交付边界，供 S4 任务书边界核验 |
| `review_intent_hints` | 供 requirements\_analyst\_review 初始化 TriggerIntent 优先级 |

> **废弃字段（不得再引用）**：`designer_behavioral_motivation`、`task_framework`（→ `intent_baseline`）、`motivation_routing_profile`、`radar_routing_decision`

### 1.4 过程字段（可审计，非交付字段）

- `motivation_trace`：动机推导轨迹
- `detected_design_modes`：识别到的设计模式
- `identity_mode`：B4 后台识别的使用者身份模式
- `initial_boundaries`：A3 初步边界清单（S3 时由 D2 正式确认）

### 1.5 review\_intent\_hints 语义

该字段不是最终结论，而是 S2/S3 调度与交互层的**方法意图供料包**：

| 子字段 | 作用 |
|---|---|
| `mainline_pressure` | 当前是否优先需要推进空间任务/空间命题 |
| `driver_conflict_signals` | 是否存在主体/角色/利益/动机冲突线索 |
| `boundary_pressure` | 是否已有预算/规范/工期/工程/政策等边界压力 |
| `validation_risk` | 是否存在明显证据不足、字段缺失、推断过重 |

`requirements_analyst` 不决定 S2/S3 最终怎么问，但要给出**下一阶段大概率该先推进哪类意图的起始信号**。

### 1.6 Phase1 / Phase2 分工

| 阶段 | 任务 | 质量要求 |
|---|---|---|
| **Phase1** | 问题识别、题型判断、空间对象初识别、边界草案生成 | 不空、可继续、可解释 |
| **Phase2** | S1 A/F 组深化执行、字段合约对齐、质量闸门预检 | 字段完整、推断可标注、轨迹可追踪 |

### 1.7 兜底策略

1. 核心层不返回空对象/空列表
2. 不确定结论用 `[推断]` 显式标注
3. 关键字段（A/F 组相关）最小可用保障

### 1.8 下游消费关系

| 消费方 | 依赖字段 |
|---|---|
| `requirements_analyst_review`（S2/S3） | 结构化输出 + S1 武器执行轨迹 + `review_intent_hints` |
| `feasibility_analyst` | 空间命题候选、边界与冲突信号 |
| `unified_input_validator*` | 快路径与门禁判断 |
| `questionnaire_summary`（S4/S5） | 冻结结果、边界包、推断标注来源 |

### 1.9 `requirements_analyst` 只负责提供 S2 入口原料

它**不**直接生成最终任务书，**不**替 requirements\_analyst\_review 做最终调度，但应使后者清楚：
- 哪一类 TriggerIntent 可能优先启动
- 哪些信号足以触发驱动力修正或边界压缩
- 哪些缺口迫使系统优先做横切校验

它的输出最终支撑形成：`space_proposition`、`driver_priorities`、`confirmed_constraints`、`tradeoff_baseline`，只有这些结果在 S2/S3 中稳定后，才允许进入 `questionnaire_summary` 的正式定版。

## 二、requirements\_analyst\_review 交互状态机

### 2.1 节点定位

主链核心交互节点（非展示页）：

```text
承接 S1 输出
  → 驱动 S2 / S3 武器链互动（ALWAYS_SPEAK + CONDITIONAL_SPEAK）
  → 执行覆盖率门禁（AnalyticalCoverageTracker）
  → 接收用户动作（confirm / edit / rerun / skip）
  → 产出 S1 v3 基线 + S3 战略冻结包
```

### 2.2 状态机流程

```text
进入节点（S1 完成后）
  │
   ├─ 展示 S1 结构化结论（高规格 Echo Card：依据层 + 基线层）+ 武器执行轨迹
  │
  ├─ 启动 S2 目标锁定（ALWAYS_SPEAK_S2: B4→B1→B2→B3）
  │     ↑ C 组按相关性分插入
  │
  ├─ S2 收口：AnalyticalCoverageTracker.s2_ready_to_close()
  │
  ├─ [Step A] S1 v2 内部补全 + [Step B] 缺口补全轮（按需 0..n）
  │
  ├─ S1_v3_complete == true → 进入 S3 战略框架
  │
  ├─ S3 战略框架（ALWAYS_SPEAK_S3: D1→D2 + 战略取舍冻结）
  │
  ├─ S3 收口：AnalyticalCoverageTracker.s3_ready_to_close()
  │
  └─ 满足"足以冻结"条件 → questionnaire_summary（S4/S5 编译交接）
        │
        └─ 重跑（rerun）→ 回到 requirements_analyst
```

### 2.3 交互对象最小合约

每次进入 `requirements_analyst_review` 的互动对象，除武器结论外，至少携带：

| 字段 | 含义 |
|---|---|
| `weapon_id` | 当前发声武器 |
| `slot_status` | 当前槽位状态（VoiceSlot 五态之一） |
| `trigger_intent` | 当前发声的主要方法意图 |
| `intent_label` | 前端/日志可读标签，如"推进主线""修正驱动力" |
| `can_reframe` | 当前响应是否可能触发依赖重排 |
| `blocking_reason` | 若不可确认，阻塞原因是什么 |

`trigger_intent` 取值与调度文档（`02-武器库与运行调度`）保持一致：`advance_mainline` / `correct_driver` / `compress_boundary` / `cross_validate`（`compile_handoff` 属于 `questionnaire_summary` 阶段）

## 三、用户动作语义

### 3.1 四种动作

| 动作 | 语义 | 对 TriggerIntent 的影响 | 处理方式 |
|---|---|---|---|
| **confirm（确认）** | 认可当前武器结论，推进至下一件 | 当前意图视为已交付完成 | 槽位标记 `responded`，insight\_distiller 推进队列 |
| **edit（修改）** | 在当前结论上补充/矫正 | 可能保持原意图，也可能触发意图重排 | 记录注释；可触发 reframe（精准重置依赖槽位）|
| **rerun（重跑）** | 需要重新生成 S1 分析 | 当前意图整体失效，回到上游重建 | 路由至 `requirements_analyst` |
| **skip（跳过）** | 不需要当前武器的结论 | 当前意图在该槽位上被用户放弃 | 槽位标记 `skipped_by_user`，退出条件照常满足 |

### 3.2 否定层级对应的回退优先级

| 用户否定内容 | 优先回流意图 | 说明 |
|---|---|---|
| 任务定义/核心冲突 | `advance_mainline` | 空间命题层的主线需要重建 |
| 主体关系/权重判断 | `correct_driver` | 驱动力层的识别需要修正 |
| 约束/红线/可行域 | `compress_boundary` | 边界层的压缩结论需要重做 |
| 字段完整性/证据 | `cross_validate` | 横切校验层需要重新核查 |

### 3.3 防止交互死循环

**反死锁设计原则**：

1. **审阅节点的 warn/blocker 门禁**不可以导致 `confirm→rerun→confirm` 的无限循环
2. 每个 `rerun` 操作必须明确回退到哪个步骤，且必须更新当前 session 状态中的阻塞原因
3. 用户连续 `skip` 超过 N 件必说武器时，系统应主动提示"关键问题被跳过，任务书质量有风险"，而不是静默继续
4. `edit` 操作触发 reframe 时，必须向用户说明"这个修改影响了这些已完成的问题，是否重新讨论"

### 3.4 可观测审计日志字段

系统需记录以下字段，供后续质量审计使用：

| 日志字段 | 含义 |
|---|---|
| `weapon_execution_trace` | 各武器的轨迹（槽位状态历史） |
| `trigger_intent_sequence` | 本轮 TriggerIntent 切换顺序 |
| `reframe_events` | 重排事件记录（触发原因、影响范围） |
| `user_action_log` | 用户每次 confirm/edit/rerun/skip 的时间和对象 |
| `coverage_checkpoint` | s2\_ready\_to\_close / s3\_ready\_to\_close 的判断时刻与结果 |

## 四、可行性分析决策框架

### 4.1 节点位置

```text
S3 战略框架冻结后 → feasibility_analyst → unified_input_validator_secondary → S4 战术分解
```

### 4.2 与 S3 前提挑战（D1/D2）的分工

| 维度 | S3 前提挑战（D1/D2） | 可行性分析（feasibility\_analyst） |
|---|---|---|
| **关注层** | 认知层 — 挑战"分析前提是否成立" | 资源层 — 评估"执行是否可行" |
| **工期** | 不涉及 | ✅ 里程碑合理性评估 |
| **预算** | D2 识别为 hard\_limits（用户确认） | 验证技术路径与预算的实际匹配 |
| **输出形式** | 用户确认的前提修正 + 约束清单 | pass / warn / blocker 决策 |

**结论**：两者互补，不重叠。执行顺序：S3（认知挑战）→ 可行性（资源验证）→ S4（任务书编译）。

### 4.3 四个决策维度

| 维度 | 关键检查点 |
|---|---|
| **技术可行性** | 技术路径是否存在、关键依赖是否可得、是否与既有约束冲突 |
| **成本可行性** | 预算与目标是否匹配、是否有明显超预算结构、是否有替代路径 |
| **工期可行性** | 里程碑是否现实、工期与复杂度是否匹配、高概率延期风险识别 |
| **风险可控性** | 高影响高概率风险、是否有缓释策略、是否触发合规红线 |

### 4.4 输出语义

| 输出值 | 含义 | 后续处理 |
|---|---|---|
| **pass** | 可进入 unified\_input\_validator\_secondary | 正常推进 |
| **warn** | 可继续，但强制携带风险注释 | 注释必须写入 DesignTaskBook 的风险字段 |
| **blocker** | 不可继续，回退至补全/重审路径 | 必须提供：①阻断原因（按维度分类）②可修复动作 ③重评触发条件 |

### 4.5 常见误判

1. 把"未知"当"可行"
2. 把"可行"当"可立即执行"
3. 只看技术，不看成本与工期
4. 只给结论，不给回退动作
5. 与 S3 D1/D2 的职责混淆（S3 挑战认知假设，本节点验证执行资源）

> **一句话**：可行性分析的价值不是"说能不能做"，而是**给出可继续或可回退的可执行决策**。

## 五、结束条件与任务书定版标准

### 5.1 为什么必须把结束条件写死

若无明确结束条件，需求分析会出现两个问题：
1. **阶段永远结束不了**：总还能再补一点、再问一点、再发散一点。
2. **下游没有稳定起点**：角色编组、任务分发、成果验收都会建立在漂浮地基上。

> **核心原则**：未形成稳定需求基线，不得进入 `questionnaire_summary` 任务书阶段。

### 5.2 设计任务书到底是什么

设计任务书**不是**：
- 原话汇总
- 需求备忘录
- 可能性清单
- 最后一轮大型选择题

设计任务书**是**：
> 前面多轮共同推理、局部裁决、边界压缩、取舍冻结之后形成的**统一决策对象**。

它至少包含四类核心结构：
1. **空间命题结构**：这次项目真正要完成的空间任务是什么
2. **驱动力结构**：谁在推动、为什么推动、权重如何排序
3. **边界结构**：哪些硬约束不可突破，哪些软约束需要尊重
4. **取舍结构**：哪些必须保，哪些可以让，哪些延后处理

在调度语义上，`questionnaire_summary` 承接的主要意图是 **`compile_handoff`**：将已冻结的判断编译成可交接、可签署、可供下游消费的统一对象，**不是**重新发起分析。

### 5.3 允许进入任务书定版的四个前提

**四个前提必须同时满足**：

| 前提 | 判断标准 |
|---|---|
| **3.1 主问题明确** | 已回答"这次项目真正要解决什么问题"；主命题不在多个方向之间漂移 |
| **3.2 主目标与主约束稳定** | 主目标、主约束、哪些是硬红线、哪些是软偏好均已明确；不处于大幅摇摆状态 |
| **3.3 关键冲突已裁决** | 当前最关键的冲突对已识别；已倾向哪一边且有取舍理由；不存在"大量核心选项待决" |
| **3.4 剩余未决项不阻碍交接** | 允许少量未决项，但不改变主问题、不推翻主目标、不重写主约束、不影响下游任务阶段启动 |

### 5.4 什么情况下不得称为"设计任务书"

出现以下任意一种情况，不得称为任务书定版：

1. 主问题仍在多个方向之间漂移
2. 主目标与主约束仍未稳定
3. 核心冲突尚未被裁决
4. 关键缺口仍会影响冻结结果
5. 还需要大规模重新选择
6. **feasibility blocker 尚未处理**

一旦出现这些情况，必须回退至 S2（requirements\_analyst\_review）或 S3（战略框架重开），**不得在 S4/S5 内部强行定版**。

### 5.5 任务书阶段只允许的三类动作

任务书阶段（`questionnaire_summary`）不是再次大规模分析，只允许：

| 动作类型 | 允许 | 不允许 |
|---|---|---|
| **表述微调** | 改写措辞、消除歧义、提高清晰度 | 通过改写表述偷偷更换决策 |
| **轻量排序** | 在已确定主次关系内微调顺序；不改变主判断的前提下调整展示层级 | 把次要目标翻成主目标；把已冻结红线重新放松 |
| **未决项标注** | 标记哪些问题留到后续阶段；标记 `[推断]` 字段；标记外部条件待确认项 | 用"未决项"掩盖尚未完成的核心决策 |

这三类动作本质上都服务于同一个 TriggerIntent：`compile_handoff`。

### 5.6 任务书结构模板

建议 `confirmed_design_brief` 至少包含以下结构：

```text
1. 项目定义
   - 项目名称/标识
   - 空间对象与类型
   - 项目状态（新建/改造/更新/扩容/重定位）
   - 本轮需求分析范围

2. 空间命题
   - 核心空间任务
   - 主要服务对象
   - 关键活动与关系
   - 当前决定性矛盾

3. 驱动力排序
   - 主驱动方与主诉求
   - 次驱动方与次诉求
   - 权重说明与裁决原因

4. 边界结构
   - 硬约束清单（confirmed_constraints，来自 D2）[绝对不可突破]
   - 软约束清单（尊重，但可协商）
   - 延后处理项

5. 取舍结构
   - 主优先级（必须保）
   - 让位项（可以让）
   - 红线（不可穿越）
   - 延后处理项（后续阶段展开）

6. 推断标注摘要
   - [推断] 字段清单 + 推断来源
   - 信息充足度声明

7. 可行性复核摘要
   - feasibility_analyst 结论（pass/warn）
   - 风险注释（warn 时提供）
```

## 六、质量门禁四类

### 6.1 门禁总表

| 门禁类型 | 位置/节点 | 职责 |
|---|---|---|
| **输入门禁** | `unified_input_validator_initial` | 阻断不合规、不完整输入，确保 S1 有可处理原料 |
| **S3 入口门禁** | `requirements_analyst_review` 内（S2 完成后） | `S1_v3_complete == true`：S2 目标已锁定 + 缺口补全轮收敛，方可进入战略框架 |
| **二次门禁** | `unified_input_validator_secondary` | 可行性复核后，确认 S1 v3 完整、冻结包非空、无 feasibility blocker |
| **审阅一致性门禁** | `requirements_analyst_review` 内部 | 武器执行轨迹覆盖率与关键字段状态是否冲突（A/B/D 组 + G1）|
| **质量收口门禁** | G1 / G2 / G3（质量门控组） | 结论锐度 / 字段完整性 / 空字段回填 |

### 6.2 各门禁检查项

| 门禁 | 检查项 | 不通过处理 |
|---|---|---|
| **输入门禁** | 输入合法（无注入风险）+ 有最低可处理信息量 | 阻断并提示补充，不进入 S1 |
| **S3 入口门禁** | S2 核心目标已锁定且用户确认；缺口补全轮已收敛（无缺口时直接通过）| 不得进入战略讨论，回到缺口补全轮 |
| **二次门禁** | S1 v3 不为空；S3 冻结包不为空；feasibility 无 blocker | 按阻塞原因分别回退：S1 不完整→requirements\_analyst\_review 补；冻结包缺项→S3 重做 |
| **一致性门禁** | 武器覆盖率与字段一致性（ALWAYS\_SPEAK 武器是否都已 responded 或 skipped\_by\_user）| blocker（关键武器未完成）/ warn（条件武器不完整）|
| **G1 质量收口** | 结论锐度（无模糊词）+ 可执行性（有具体动作指向）+ 与已确认信息不矛盾 | 退回武器重新生成，不展示给用户 |
| **G2 结构完整性** | 关键字段完整性 | 触发 E1 追问，或触发 G3 推断兜底 |
| **G3 空字段兜底** | 无空对象直出 | 推断填充并标注 `[推断]`；若字段一旦推断即改写决策基线，则撤销推断，回退 E1/S2/S3 |

### 6.3 输出语义（三级标准）

| 输出语义 | 执行含义 | 注意 |
|---|---|---|
| **pass** | 可继续 | — |
| **warn** | 可继续但必须记录风险 | 不能等同于 pass；风险必须写入下游可见字段 |
| **blocker** | 必须修正后才能继续 | 不能当"建议"处理；必须提供回退动作 |

### 6.4 武器与门禁的关系

```text
25 件武器（A/B/C/D/E/F/G）= 做了什么（执行轨迹）
门禁框架                    = 做得是否可信、是否可继续（轨迹可信度判定）
```

两者协作形成闭环：武器执行轨迹 → 覆盖率 tracker → 门禁判定 → 放行或回退。
