## 二、缺口产生的原因分析

### 2.1 为什么武器参与显性化不足？

**原因 1：模拟输出优先展示"用户可见内容"**
- 当前模拟输出更像"给用户看的任务书"
- 而不是"给系统开发者看的武器协作日志"
- 因此省略了大量"后台运行细节"

**原因 2：武器输入输出链的文档分散**
- 武器输入输出定义在 41 个独立武器文件中
- 武器协作关系定义在"武器激活与调度机制"文档中
- 模拟输出没有把这些信息整合到一起

**原因 3：VoiceSlot + TriggerIntent 机制未在模拟中体现**
- 当前模拟是"理想路径"（所有武器都 responded）
- 没有展示 VoiceSlot 状态变化（pending → delivered → responded）
- 没有展示 TriggerIntent 如何驱动调度（advance_mainline / correct_driver / compress_boundary）

---

### 2.2 为什么知识底盘空间类型示范缺失？

**原因 1：知识底盘内容在代码库中，未在文档中展示**
- ontology.yaml 定义了 `commercial_hospitality` 框架（宾客旅程 / 地域身份 / 服务模式）
- few_shot_examples 中有福州雅诗阁 16 任务框架、狮岭村 17 任务框架
- 但这些内容没有被"拉出来"展示在模拟输出中

**原因 2：L1-L4 知识层的调用过程是"黑盒"**
- 当前只标注"知识底盘消耗：L1/L2"
- 但没有展示：
  - L1 规则层返回了什么规则（`query_rules(space_type="commercial_hospitality", constraint_type="material_durability")`）
  - L2 矩阵层返回了什么框架（`get_project_type_context(project_type="commercial_hospitality")`）
  - L3 案例层检索到了什么案例（`retrieve_cases(query="山地民宿 HAY气质", filters={'project_type': 'commercial_hospitality'})`）

**原因 3：模拟输出没有"知识底盘调用日志"章节**
- 当前模拟输出的结构是：S1 → S2 → S3 → S4 → 任务书
- 没有单独的"知识底盘调用记录"章节
- 导致用户无法看到知识底盘如何被消费

---

### 2.3 为什么一主两辅方法显性化不足？

**原因 1：一主两辅方法是"推进逻辑"，不是"输出章节"**
- 一主两辅方法回答的是"怎么推进"
- 而不是"推进后的结果是什么"
- 当前模拟输出只展示了"结果"（任务定义、冲突对、约束清单）
- 没有展示"推进过程"（空间主线如何从类型推进到命题）

**原因 2：三条轴的推进过程被"折叠"到武器输出中**
- B1 输出的 JTBD 其实是"空间主线推进"的结果
- C3 输出的行为模式其实是"驱动力修正"的结果
- D2 输出的约束清单其实是"边界压缩"的结果
- 但这些关系没有被显性标注

**原因 3：缺少"一主两辅推进轨迹图"**
- 当前只有 S1 的"锚定表格"
- 没有 S2 的"推进表格"（三条轴如何从初始状态推进到冻结状态）
- 没有 S3 的"交叉表格"（三条轴如何在交叉点形成取舍）

## 三、补充方案设计

### 3.1 补充方案 1：武器输入输出链显性化

**补充位置**：在每个武器输出后，增加"武器协作链"注释框

**补充格式**：
```
#### B1 任务目标提炼（JTBD 格式）

[当前输出内容...]

---

**武器协作链**：

| 项目 | 内容 |
|------|------|
| **输入来源** | ① A1 信号包（structured_requirements）<br>② F2 根本需求（root_needs）<br>③ F3 关键洞见（key_insights）<br>④ L2 矩阵（commercial_hospitality 框架）<br>⑤ L4 项目记忆（user_history） |
| **输出对象** | `jtbd_statement: {situation, job, motivation, full_text}` |
| **下游消费** | → B2 目标冲突诊断器（B2 消费 B1 输出 + F3 洞见）<br>→ S4 任务书（JTBD 进入"空间命题"章节）<br>→ F7 优先级反事实验证器（验证 B1 优先级稳健性） |
| **VoiceSlot 状态** | pending → delivered → responded（用户确认） |
| **TriggerIntent** | `advance_mainline`（推进空间命题主线） |
```

### 3.2 补充方案 2：知识底盘空间类型示范

#### L2 矩阵层调用

**调用接口**：`get_project_type_context(project_type="commercial_hospitality")`

**返回内容**：

**Commercial_Hospitality 框架**（来自 ontology.yaml）：

1. **宾客旅程（Guest Journey）**
   - 到达与第一印象：从预订确认到大堂入口——品牌调性传递
   - 客房作为"第二个家"：超越功能满足的情感共鸣
   - 公共空间的社交动态：大堂、餐厅、泳池氛围设计影响停留时长与复购

2. **地域身份（Place Identity）**
   - 在地性表达（Sense of Place）：本地文化、自然景观、历史记忆转译——核心差异化
   - 文旅融合深度：从"住宿+观光"到"住宿即体验"

3. **服务模式（Service Model）**
   - 服务可见度：从"隐形服务"到"表演式服务"光谱
   - 标准化-个性化平衡：连锁一致性 vs 精品定制化
   - 技术赋能：从传统人工到 AI 礼宾——效率 vs 体验权衡

**激活配置**：
- 提升话题：E3（光）、E4（材料物性）、E5（时间与时序动态）
- 典型深度：L2-L4（体验层到辩证层）
- 关键张力：品牌标准化 vs 在地独特性（E4×E5）

- 关键洞见：
  - "价值感知"空间表达：奢侈精神 + 中档价格
  - 艺术策展融合：从地面画廊到客房艺术品
  - 智能系统 + 标准化模块 + 成本精度

- 17 任务框架：文化研究 + 场地分析 + 设计策略 + 运营

  - "第三条路"：完全城市化 vs 博物馆化之间
  - 在地材料策略：竹/木/石/夯土——传统技艺 + 现代耐久性

### 3.3 补充方案 3：一主两辅方法显性化推进

**补充位置**：在 S2 结尾，增加"一主两辅推进轨迹"表格

**补充格式**：
```
### 一主两辅推进轨迹（S1 → S2）

| 轴线 | S1 初始锚定 | S2 推进过程 | S2 推进结果 |
|------|------------|------------|------------|
| **空间主线** | 空间对象 = 山地民宿集群 | **B1** 推进：山地民宿集群 → 承载轻度度假活动（住宿/景观消费/低密度社交）<br>**B2** 推进：识别核心矛盾（克制 vs 丰盛）<br>**空间命题形成**：用克制让山成为主角 | 空间命题 = 「不与自然竞争的当代空间气质」 |
| **驱动力轴** | 初始驱动力 = 业主（市场辨识度）+ 客群（城市年轻中产） | **B4** 识别：使用者身份 = 探索者型（需要引导而非结论）<br>**C3** 修正：轻度度假行为模式（慢醒来/散步/低密度社交/景观消费/拍照传播/夜间收缩）<br>**权重确认**：业主（主导）> 客群（核心）> 环境（约束） | 驱动力排序 = P0 景观 > P1 品牌辨识度 > P2 行为支撑 |
| **边界轴** | 硬边界 = 山地地形 + 高湿气候；软边界 = HAY 气质方向 | **D2** 压缩：红线（不做展厅复刻/不做木石堆砌/不遮挡景观）<br>**X2** 压缩：工程约束（湿度 75%+ 材料限制/山地运输限制）<br>**X6** 校验：气候修正（金属防潮/色彩稍暖/尺度放松 10-15%） | 边界压缩结果 = 3 条红线 + 3 条硬限制 + 3 条软偏好 |

**三条轴的交叉点**（S3 冻结取舍）：
- 空间主线（用克制让山成为主角）× 驱动力轴（P0 景观优先）× 边界轴（不遮挡景观红线）→ **冻结公式**：`克制是方法，山是主角，HAY 是语法不是内容`
```
