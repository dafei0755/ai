## 为什么需要单独定义“交付后追问”

在很多系统里，交付完成常常被误解成流程终点。

但对真实用户而言，交付完成之后经常才会出现第二层动作：

- 继续追问为什么这么判断
- 希望把某个方向再展开一点
- 对某一部分不满意，希望局部改写
- 发现自己其实想换一个方向
- 保留原方案，但希望再长出一个新的分支版本
- 希望把结果改写成另一种受众能使用的版本

如果系统不对这些动作做结构化区分，就会出现两个典型问题：

1. **过轻**：把所有追问都当成闲聊补充，结果真正的新任务被低估
2. **过重**：把所有追问都当成重新开题，结果小问题也要重启完整流程

因此，本篇的核心判断是：

**交付后的追问环节，不是单纯补充问答，而是后续动作的分流入口。**

---

## 总判断：对外三层、对内六类

结合主架构与补充参考意见后，最稳的做法不是只保留“几类追问”的单层分类，而是采用：

## 第一层：对外三层

这一层面向：

- 用户理解
- API 入口
- 项目级路由
- 会话 / 项目状态管理

建议固定为三类：

1. `small_followup`
2. `delta_action`
3. `major_action`

### small_followup

- 以解释、延展、启发为主
- 不新建项目
- 不触发增量执行
- 不改变原交付状态

### delta_action

- 在原任务书主轴仍成立的前提下补内容、补维度、补交付、局部修订
- 不新建项目
- 在原项目下产生局部增量执行
- 允许新增局部交付、分支交付或局部回流

### major_action

- 改变主命题、概念源、核心驱动力或主交付目标
- 不再适合继续挂在原任务下补做
- 应派生新项目或新任务书

## 第二层：对内六类

这一层面向：

- Follow-up Router 内部判断
- 执行调度与回流
- 版本树与交付挂接关系
- 后续对象模型

建议保留更细的六类语义：

1. 小追问 / 延展追问
2. 局部修订
3. 分支派生
4. 大动作 / 新指令
5. 纠错 / 挑战型追问
6. 结果消费 / 再包装

一句话压缩：

**对外三层，用于稳定路由；对内六类，用于保留语义分辨率。**

---

## 三层与六类的映射关系

为了避免“顶层三层太粗、底层六类太散”，建议把二者关系写死：

| 内部语义类型 | 顶层动作类型 | 说明 |
|---|---|---|
| 小追问 / 延展追问 | `small_followup` | 继续解释、补充启发，不改原交付状态 |
| 局部修订 | `delta_action` | 同题内修，触发局部回流或局部重生成 |
| 分支派生 | `delta_action` 或 `major_action` | 若原主轴保留且新版本并列存在，多数属于 `delta_action`；若实质改轴，则升级为 `major_action` |
| 大动作 / 新指令 | `major_action` | 改主命题、主轴、主交付目标，需派生新项目 |
| 纠错 / 挑战型追问 | 先判层级，再映射 | 若只是修正事实或局部偏差，多数落 `delta_action`；若修正后主轴失效，升级为 `major_action` |
| 结果消费 / 再包装 | `small_followup` 或 `delta_action` | 轻量改写多属 `small_followup`；若形成新增局部交付，则归 `delta_action` |

这意味着：

- 三层不是替代六类
- 六类也不应直接暴露成第一层 API 类型
- 系统应先做顶层路由，再保留底层语义标签

---

## 最稳的判断标准：不要先看大小，要先看是否改同一性

如果只从直觉看，交付后动作往往会被粗分成两类：

1. 小追问
2. 大动作

这个划分方向对，但不够细。

更稳的制度划分，至少应有四类：

1. 小追问 / 延展追问
2. 局部修订
3. 大动作 / 新指令
4. 纠错 / 挑战型追问

而如果要真正支持系统落地，建议扩展成六类：

1. 小追问 / 延展追问
2. 局部修订
3. 分支派生
4. 大动作 / 新指令
5. 纠错 / 挑战型追问
6. 结果消费 / 再包装

这六类能覆盖绝大多数交付后场景，而且每一类的处理机制都明显不同。

但在真正路由时，系统不应先问“动作看起来大不大”，而应先判断：

1. 是否改变一主两辅冻结结果
2. 是否改变主交付骨架
3. 是否需要重新选择核心专家主阵容
4. 是否能在原任务书边界内完成
5. 是否只是改变结果表达形式，而不改变结果判断

更准确地说：

**判断追问后续处理方式的核心，不是动作大小，而是它是否改变原任务同一性。**

---

## 第一类：小追问 / 延展追问

这是最轻的一类动作。

它的特点是：

- 不改变原任务主问题
- 不改变原任务主轴
- 不改变原交付物主框架
- 不要求重做原论证链
- 更像围绕既有结果继续延展理解

### 典型例子

例如原任务已经完成：

- 以“李白的诗意”为概念的空间设计方案

用户继续问：

- 你再展开一下“月下独酌”的空间情绪表达
- 如果材质更轻、更空灵，会有哪些处理方法
- 请从灯光角度再解释一下诗意来源
- 再给我 3 个更偏现代感的表达提示

这些都还在同一主轴内，只是在做说明、延展或启发。

### 处理机制

这类应被识别为：

- `follow_up_expand`
- `explanation_addendum`
- `inspiration_extension`

建议处理方式：

- 不重开需求冻结
- 不重启执行主流程
- 不覆盖原交付物
- 在原交付物下新增附属说明、补充回答、启发提示

### 制度结论

**小追问 = 在原结果上继续长解释与启发，不进入回流，也不进入新任务。**

---

## 第二类：局部修订

这一类最容易被忽略，但它在真实场景里非常常见。

它的特点是：

- 原主问题不变
- 原主轴不变
- 原交付目标不变
- 但用户希望局部内容被重做、改写或加强

换句话说，它不是“继续聊”，也不是“换题”，而是：

**同题内修。**

### 典型例子

仍然以“李白诗意空间设计”为例，用户提出：

- 整体方向保留，但希望减少一点“仙气感”，增加现实栖居感
- 保留诗意主轴，但色调不要这么冷，材质偏温暖一些
- 不改概念方向，但希望把入口空间做得更收，主厅更开
- 保留整体方案，只重做动线叙事这一部分

这些动作没有改成“杜甫”，也没有改题，只是在原同一性内做修订。

### 处理机制

这类应被识别为：

- `localized_revision`
- `partial_rework`
- `localized_regeneration`

建议处理方式：

- 锁定原主问题与原主轴
- 明确修订范围
- 触发局部回流 / 局部重生成
- 保留旧版本
- 生成修订版交付物（如 `v1.1` / `v2`）

### 制度结论

**局部修订 = 原问题同一性仍成立，但需要对局部结果进行回流和重做。**

---

## 第三类：分支派生

这类动作经常会被误判成“重开一轮”，但其实它更适合被当作：

**在保留原结果的前提下，再派生一个平行版本。**

### 它和“大动作”的区别

- 大动作通常意味着替换原任务或改写原方向
- 分支派生则意味着：原结果保留，同时长出旁支

### 典型例子

- 原来的李白方向保留，再额外给我一版更偏杜甫现实感的方案
- 原方案作为 A 版，再生成一版更商业化表达的 B 版
- 保留当前方向，再给一版更适合年轻客群的派生版本

### 处理机制

这类应被识别为：

- `branch_derivation`
- `parallel_variant`
- `sibling_solution_request`

建议处理方式：

- 不覆盖原结果
- 明确从哪一个原交付物派生
- 新建一个分支任务或平行交付物
- 在结果树中并列展示

### 制度结论

**分支派生 = 原方案继续保留，但基于它派生出新的兄弟分支。**

---

## 第四类：大动作 / 新指令

这就是最典型的“不是续问，而是新要求”。

### 它的关键特征

它通常改变了以下至少一项：

- 主问题表达方式
- 核心概念源
- 主轴或核心命题
- 交付目标
- 评价标准或审美重心

### 典型例子

- 原来是“以李白诗意为概念”，现在希望改成“杜甫的诗意”
- 原来是概念型空间设计，现在改成更偏商业运营导向
- 原来是做叙事空间体验，现在改成强调施工落地优先

这类变化已经不是“小修小补”，而是触碰了原任务同一性。

### 处理机制

这类应被识别为：

- `reframed_new_task`
- `new_dimension_request`
- `supersedes_original_direction`

建议处理方式：

- 不覆盖原交付物
- 不伪装成原任务“修订版”
- 新建一轮需求冻结或新任务书
- 作为 `derived_project` 处理
- 自动继承原项目的摘要上下文、任务书与核心输入
- 自动生成与原项目的 `change_summary`
- 明确它与原任务的关系（替换、继承、分叉）

### 制度结论

**大动作 = 改变原任务同一性，应进入新一轮任务或新分支，而不是继续沿原流程续写。**

这里要特别固定两条：

1. 大动作输出必须是**完整新结果**，而不是只有差异片段
2. 原项目历史结果不得被覆盖，而应与新项目保持可追溯关系

---

## 第五类：纠错 / 挑战型追问

这类动作不是在补充，也不是在换方向，而是在说：

- 你理解错了
- 你抓错重点了
- 你误解了我的边界
- 你虽然做得完整，但已经偏题了

这类情况非常关键，因为它不是普通追问，而是：

**对原交付的正确性提出挑战。**

### 典型例子

- 我不是要“唐诗气质”，我是明确要“李白的浪漫主义”，你现在做得太泛了
- 你理解成了酒店空间，我其实要的是书院式复合空间
- 我说的“轻”是精神气质，不是材质轻薄
- 你这个方案很完整，但已经不在我原来的边界里了

### 处理机制

这类应被识别为：

- `challenge_and_reflow`
- `delivery_correction`
- `misalignment_claim`

建议处理方式：

- 不是直接继续追问回答
- 也不是直接新建任务
- 而是先判断被挑战的是哪一层：
  - 表达层
  - 局部逻辑层
  - 主方向层
  - 需求冻结层
- 再决定：
  - 局部修订
  - 阶段性交付物回流
  - 方向级回流
  - 需求冻结重判

### 制度结论

**纠错 / 挑战型追问 = 回流入口，而不是普通追问入口。**

---

## 第六类：结果消费 / 再包装

还有一类动作常被忽略：

用户不是要你继续生成新内容，而是希望你把已有内容换一种“可使用形式”输出。

### 典型例子

- 把刚才方案整理成汇报提纲
- 把这个结果改成给甲方看的语言
- 提炼成 5 个 PPT 标题
- 把这个设计概念转成施工沟通摘要
- 帮我生成一个对外汇报版本和一个内部讨论版本

### 它的本质

这类通常不改变原判断，只改变：

- 受众
- 表达形式
- 交付格式
- 使用场景

### 处理机制

这类应被识别为：

- `delivery_repack`
- `presentation_transform`
- `audience_adaptation`

建议处理方式：

- 不重新冻结任务书
- 不重做原分析
- 在既有交付物基础上做再包装 / 再表达 / 再投递

### 制度结论

**结果消费 / 再包装 = 不改变原结果同一性，只改变它的使用形式。**

---

## 六类内部语义的详细定义仍然必要

虽然顶层路由建议收敛成三层，但这并不意味着内部不再需要更细的语义分类。

原因是：

- `delta_action` 内部同时包含局部修订、维度新增、分支派生、再包装型增量交付
- `major_action` 内部既可能是直接改题，也可能是由挑战型输入升级而来
- `small_followup` 内部也区分解释、启发、轻量压缩与轻量再表达

因此，本篇保留六类细分，并不是为了把接口做复杂，而是为了让执行层知道：

- 是做局部回流
- 还是做增量交付
- 还是开平行分支
- 还是派生新项目

---

## 最稳的判断标准：不要按“动作大小”，要按“是否改变原任务同一性”

交付后动作最容易被误分，是因为人习惯凭感觉判断“这个动作大不大”。

但真正稳的制度标准，不是大小，而是：

**它有没有改变原任务的同一性。**

建议用四个问题来判断：

### 1. 是否改变主问题

如果改变，通常就不是小追问。

### 2. 是否改变主轴 / 核心命题

如果改变，通常是大动作或新分支。

### 3. 是否要求重做原论证链

如果要求，通常是局部修订或回流，而不是简单附加说明。

### 4. 是要替换原结果，还是在原结果旁边再长一个

- 替换原结果：偏向大动作 / 重构
- 保留原结果并行生长：偏向分支派生

因此，最稳的路由原则不是：

- 看上去像不像大动作

而是：

- **它是否还在回答原来的同一个问题。**

## 建议增加一个显式结构：Post-Delivery Follow-up Router

如果后续要把这套机制落进系统，不建议把所有交付后输入直接丢给模型“继续回答”，而建议单独增加一个结构层：

## Post-Delivery Follow-up Router

它的职责不是生成最终内容，而是：

- 先判断用户的新动作属于哪一类
- 再决定应走哪一种后续处理机制

更准确地说，它应分两步完成判断：

### 第一步：先输出顶层动作类型

- `small_followup`
- `delta_action`
- `major_action`

### 第二步：再打内部语义标签

- `explanation_extension`
- `localized_revision`
- `branch_derivation`
- `reframed_new_task`
- `challenge_and_reflow`
- `delivery_repack`

### 推荐输出类型

建议至少支持以下几种路由输出：

- 顶层动作类型：
  - `small_followup`
  - `delta_action`
  - `major_action`
- 内部语义标签：
  - `follow_up_expand`
  - `localized_revision`
  - `branch_derivation`
  - `reframed_new_task`
  - `challenge_and_reflow`
  - `delivery_repack`

这样，系统就不会把：

- “再解释一下入口叙事”
- 和
- “把李白改成杜甫”

都误当成一句“继续生成”。

---

## 建议的对象模型与接口方向

如果后续要把这套机制接到系统接口层，建议至少考虑以下对象：

- `PostDeliveryAction`
- `DeltaTask`
- `DerivedProject`
- `ChangeSummary`
- `FollowupHistory`
- `DeliveryArtifactLink`

它们大致承担以下职责：

### PostDeliveryAction

- 记录用户在交付后的新输入
- 记录顶层动作类型与内部语义标签
- 作为路由决策的统一入口对象

### DeltaTask

- 承载 `delta_action` 下的局部增量执行
- 可用于局部修订、维度新增、再包装型增量交付

### DerivedProject

- 承载 `major_action` 产生的新项目
- 与原项目建立 `derived_from` 关系

### ChangeSummary

- 描述新项目与原项目之间的主要差异
- 用于帮助用户快速理解“改了什么、为什么要开新项目”

### FollowupHistory

- 记录小追问历史
- 避免把轻量补充污染成主交付版本树

### DeliveryArtifactLink

- 记录增量交付与原交付之间的挂接关系
- 支持分支派生、局部追加、对比展示

在接口层，建议保留一个统一入口，例如：

`POST /api/v1/projects/{project_id}/post-delivery-actions`

请求先做分类，再决定：

- `small_followup` → 直接返回补充回答与建议
- `delta_action` → 新建 `delta_task`
- `major_action` → 新建 `derived_project`

## 推荐的处理矩阵

为了方便后续系统设计与前端交互，也可以把这套机制压成表格：

| 类型 | 顶层动作 | 是否改变原主轴 | 是否重启原流程 | 建议处理 |
|---|---|---:|---|
| 小追问 / 延展 | `small_followup` | 否 | 否 | 直接追问回答，挂附加说明 |
| 局部修订 | `delta_action` | 否 | 局部 | 局部回流 / 局部重生成 |
| 分支派生 | `delta_action` / `major_action` | 不一定 | 新分支 | 新建派生任务，保留原结果 |
| 大动作 / 新指令 | `major_action` | 是 | 是 | 新一轮需求冻结 / 新任务书 / 派生新项目 |
| 纠错 / 挑战 | 先判层级，再映射 | 可能 | 视层级而定 | 触发回流判断 |
| 结果消费 / 再包装 | `small_followup` / `delta_action` | 否 | 否 | 对既有结果做格式转换或受众适配 |

## 与前面文档的关系

本篇与前面文档的关系如下：

- `专家执行与交付/07` 已经明确：
  - 人机交互主要分布在需求冻结与交付后追问两个阶段
  - 执行实施阶段默认自动推进，仅异常升级人工
- 本篇进一步解决：
  - 交付后追问到底不是一种动作，而是多种动作
  - 这些动作应该如何被识别和分流
  - 什么情况下继续补充、什么情况下局部回流、什么情况下新建分支或重开任务

也就是说：

- `07` 解决“追问阶段要不要存在”
- `追问/01` 解决“追问阶段内部如何分流”

## 推荐写入制度边界的几句话

如果只保留几句最适合写进系统总说明或制度边界的话，建议固定如下：

1. 交付后的追问环节不是普通补充问答，而是后续动作的分流入口
2. 对外建议采用：小追问 / 中动作 / 大动作三层路由；对内保留更细的语义分类
3. 系统至少应区分：延展追问、局部修订、分支派生、新任务重构、纠错回流、结果再包装
4. 判断分流的核心标准不是动作大小，而是是否改变原任务同一性
5. 不改变同一性的动作原则上不重启原流程；改变同一性的动作应进入新分支或新任务
6. 纠错 / 挑战型追问应优先进入回流判断，而不是直接继续生成

## 最终结论

本篇想固定的最核心一句话是：

**交付后的追问环节不是“继续聊”，而是决定“继续补、局部改、分支长、还是重开一轮”的分流入口。**

如果展开成更完整的一句，则推荐固定为：

**系统应对外把交付后用户的新动作先路由为小追问 / 中动作 / 大动作三层，再在内部细分为延展追问、局部修订、分支派生、大动作重构、纠错回流与结果再包装，并根据它是否改变原任务同一性，决定是直接附加、局部增量执行、生成平行分支，还是派生新项目并输出差异摘要。**

只要这条被固定下来，交付后的追问阶段就不会再退化成：

- 所有事都只能继续聊天
- 或者所有事都只能重开完整流程
