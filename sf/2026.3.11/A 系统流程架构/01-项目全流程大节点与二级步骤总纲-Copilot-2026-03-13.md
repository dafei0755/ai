## 零、系统主结构坐标系（术语对齐）

为杜绝后续的沟通折叠与边界错位，本系统全面采用 **Mode > Node > Step** 的绝对结构坐标系：

1. **Mode（两态）**：系统的顶层运行模式（对话态、项目态）。
2. **Node（四大节点）**：仅属于"项目态"的主干骨架，即本文的四大节点：输入、门禁、设计任务书、方案高参。绝不可将内部细节称为"大节点"。
3. **Step（步骤）**：挂载在 Node 下方的内部微执行结构。例如设计任务书节点的内部 T1-T5、方案高参节点的内部 R0-R5（按需回合制）都必须严格叫"步骤"，不可叫"阶段"或"节点"。
4. **Status（对象状态）**：描述产物生命周期，如 Draft（草稿）、Frozen（冻结）、Archived（归档）。

## 系统双态：对话态与项目态

> 2026-03-14 新增

### 为什么需要双态

用户与高参兄的交互不总是"启动一个完整项目"。现实中，设计师可能：

- 随口问一个行业问题（"山地民宿的消防规范一般怎么处理？"）
- 试探性地聊一个方向（"HAY 的那种年轻感，放在山里会不会太轻浮？"）
- 借案例找灵感（"有没有类似的山地民宿案例？"）
- 认真推进一个完整项目（"帮我做一个 200 平山地民宿的完整方案"）

前三种场景不需要走完整的 T1→T5 管线。如果只有项目态，轻量需求被迫走全流程，体验笨重；如果只有对话态，就退化成普通问答，丢掉核心定位。

### 双态定义

系统采用**一个前台入口、两种后台工作状态**的架构：

| 维度 | 对话态 | 项目态 |
|---|---|---|
| 定位 | 日常陪伴、组织判断、沉淀草稿 | 深度共创、逼出判断、冻结任务书 |
| 触发条件 | 零星提问、灵感试探、局部求助、概念校准 | 用户有明确项目，需要系统性推进 |
| 流程深度 | 不走项目态主链，由对话引擎驱动 | 完整 4 节点主链（设计任务书 T1→T5 + 方案高参 R0→R5 按需回合） |
| 默认产物 | 草稿对象（意图原点、共识包等），不冻结正式任务书 | `DesignTaskBook`（冻结任务书） |
| 人格表达 | 专业但松弛，有问必答，不逼冻结 | 严谨、深度、逼判断、逼冻结 |
| 知识底盘调用 | 按话题片段调用 L1-L3 | L1-L4 全层按步激活 |

> ⚠️ **L 标注消歧义**：本文表格「知识底盘调用」行中的「L1-L3」「L1-L4」指**知识底盘层级**，与交互范式分层无关。  
> `../H-1 用户/02-系统级高参协作协议` 中的 L1/L2/L3 是**全系统交互范式**（L1 流动层 / L2 协作层 / L3 冻结层），适用于系统任何阶段，**两套命名是不同维度，不要混用**。  
> 对话态并非单一均质态这一判断本身正确，相关机制详见 H-1/02。

### 硬规则

不经用户明确选择：

- **绝不**冻结正式任务书
- **绝不**启动下游专家执行
- 默认产物始终是"草稿对象"而非"正式结论"

### 两态共享

两种状态共享同一个底盘，不是两个系统：

- 知识底盘（L1-L4）
- 用户记忆档案
- 专家角色知识（对话态按需片段激活，项目态全链路）
- 统一人格：同一个高参兄

### 态切换

**对话态 → 项目态（升级）：**

系统持续观察对话信号，不再单纯依赖“连续几轮”等表象数据，须基于以下**三大认知指标**跨越阈值后，方可发出**软提示**（不强切）：

- **冻结准备度**：核心任务基本探明，主要冲突已显性化，且开始触及面积/预算等硬红线，继续闲聊不会改变物理结构。
- **认知债务**：对话中积累了大量悬而未决的“需做取舍”的前提条件，如果不即刻进入项目态收束，这些债务将导致后续系统逻辑断裂。
- **发散疲劳度**：用户表述已高度收敛，虽然轮次增加，但均在同词复读，未提出新的结构性需求。

软提示示例：*"我发现当前的几个核心问题都已经浮露（如：选址的高差、木材预算的瓶颈），如果不收拢，继续聊容易打空转。建议我先按项目方式帮你收一下基线，确立一个正式框架？"*

升级时，已有草稿对象自动编译为项目态起始输入（`RawBriefPacket` + 预填充），不需要重新说一遍。

**项目态 → 对话态（回落）：**

项目交付完成后，系统自然回归对话态。此时对话态的上下文自动注入：

- 完整交付物档案（`DeliveryBundle`）
- 版本树与版本关系
- 决策记录与风险摘要
- 方案高参过程中的审阅意见与过程痕迹
- 已冻结的 `DesignTaskBook` 与方案高参会话编排记录（如有）

注入后，对话态即具备对该项目的完整**解释、修订和派生**能力：

| 用户交付后动作 | 对话态响应与边界断定规则 | 说明 |
|---|---|---|
| 解释（"为什么选这个材料？"） | 直接在对话态中回答，引用项目档案 | 天然能力，零阻力调用记录即可回答 |
| 局部修订（"墙面材质换木质"） | 检测到意图为 Delta → **局部重入方案高参** | 增量执行，不回流需求定义主链（T1-T5）。前提：不推翻已冻结的方向/专题结论。 |
| 平行/重大派生（"改风格","加两层"） | 检测到意图触碰红线或底层战略 → **启动DerivedProject** | 强制挂载原项目档案，开辟全新的项目态节点，**重新进门禁并走完整 T1→T5**。 |
| 方向全换（"推翻，从零来"） | 软继承上下文 → 升级至新门禁 | 相当于从 0 启动新工作线程 |

此外：

- 用户在项目态进行中穿插零星问题时，系统临时以对话态响应，不打断项目主线

**保持对话态的反向判据：**

满足以下条件时不应升级：

- 只是试探一个方向
- 只是问局部问题
- 只是借案例找灵感
- 用户明显不想被流程化

### 与项目态主链的关系

4 大节点主链是**项目态的骨架**。对话态不走这条主链，而是由独立的对话引擎驱动，但可以随时升级进入项目态主链。项目交付完成后回归对话态，对话态带着项目全部上下文继续工作。

## 4 大节点

> 2026-03-14 精简：原"追问"不再作为独立节点——项目交付后自然回归对话态，由对话态在项目上下文中完成解释、修订与派生。

本项目的主链（项目态骨架）统一定义为：

1. 用户输入
2. 门禁
3. 设计任务书
4. 方案高参

它们分别承担如下职责：

| 大节点 | 作用 | 说明 |
|---|---|---|
| 1. 用户输入 | 接住原始 brief | 负责接收、记录、建立入口上下文，并粗识别一主两辅入口信号、多学科线索及工作地图初始信号（A类交付物主线 / B类洞察补位线） |
| 2. 门禁 | 做运行前判断 | 负责安全、边界、可行性、状态判定与是否放行 |
| 3. 设计任务书 | 收口为冻结对象 | 负责基于项目基线推进 T1-T5（信息对齐、团队组建、任务安排、任务实施、审阅确认），按一主两辅组织问题并吸收转译后的多学科认知，最终编译成可独立交付的 `DesignTaskBook`（协同规则详见 `../../2026.3.22/S-方法论/一主两辅与多学科协同方法论.md`） |
| 4. 方案高参 | 按需重发起高参动作 | 以 `DesignTaskBook` 为上下文输入，基于用户当下意图动态重组动作（深化、追问、修订、派生），不默认继承大节点3的固定步骤指令；内部二级步骤采用 R0-R5 按需回合制 |

一句话概括：

**先接住输入，再判断能否进入主链；进入主链后把需求冻结为可独立交付的任务书；若用户继续深化，再进入方案高参按需发起动作；交付完成后回归对话态。**

## 大节点与二级步骤的关系

整个系统可以拆成两层理解：

### 第一层：大节点（Macro Node）

大节点解决的是：

- 全流程现在走到哪里
- 这一段承担什么职责
- 上下游交接的对象是什么

它定义的是流程骨架。

### 第二层：二级步骤（SubStep）

二级步骤解决的是：

- 这个大节点内部如何完成
- 哪些动作必经，哪些按条件触发
- 异常、回流与局部分流如何处理

它定义的是节点内部做法。

更准确地说：

**大节点定义阶段，二级步骤定义做法。**

### 二级步骤最新口径（2026-03-21）

| 大节点 | 二级步骤形态 | 当前口径 |
|---|---|---|
| 用户输入 | 线性收纳 | I1 输入接收 → I2 原话保真 → I3 初始要素抽取 → I4 会话建立 |
| 门禁 | 线性判定 | G1 安全校验 → G2 边界校验 → G3 可行性初判 → G4 轻量预采集 → G5 系统可用性检查 → G6 状态判定 |
| 设计任务书 | 线性收敛 | T1 信息对齐 → T2 梦幻团队组建 → T3 任务安排 → T4 任务实施（T4-1/4-2） → T5 任务书审阅与确认 |
| 方案高参 | 回合制（按需重发起） | R0 触发判定 → R1 意图归类 → R2 上下文装载 → R3 动作编排 → R4 执行协同与审阅 → R5 回写收束与下一回合判定 |

> 关键约束：T1-T5 是一次性冻结链；R0-R5 是可重复回合链。用户每次新意图进入方案高参，都会从 R0 重新判定，而不是沿用上一轮固定步骤。

## 突破行业惯性：主链推进的“异步化与柔性化”

建筑与空间设计极度惧怕“填表式”的高压审讯。对流程编排层而言，`T1→T5` 的推进是强时序的，但面向用户的展现必须是彻底的“异步化（Asynchronous）”。

**在体验层必须贯彻以下特征：**
1. **多线索与断点续传**：用户在 T4（任务实施）聊到一半，突然跳去其他项目查询资料，再切回来时，流程编排层必须无缝提示：“上次我们已经锁定方向基线，还有两个专题待确认，继续吗？” 
2. **“无错回退”的温和处理**：如果在 T4-2（专题确认）用户反悔：“我还是觉得方向不对。” 系统不需要报错，更不应该弹出“警告：跨节点回流”。系统直接用对话语境说：“没问题，我们回到 T4-1 把方向再校准一下”，而底层执行复杂的版本溯源与连带状态擦除。


压成产品化表达：

> **用户和高参兄在对话态中开始交流；门禁判定走项目态还是留对话态。项目态先冻结设计任务书（可独立交付）；若用户继续，再进入方案高参按需深化执行；交付完成后回归对话态，带着项目全部上下文继续陪伴。两态共享同一个底盘、同一份记忆、同一个人格。**

## 4 大节点 + 对话态之间交接什么

系统能串起来，不只是因为有顺序，还因为有明确的交付物交接。

从这个角度看，4 大节点 + 对话态之间传递的是一条交付链：

```text
原始 brief
  → 放行结论 + 状态判定
  → DesignTaskBook（独立交付里程碑）
    ├─ [用户选择 A] 停止，自行执行设计
    └─ [用户选择 B] 继续进入方案高参
       → 本轮按需执行编排（可生成会话级执行计划）+ 执行交付物 + 版本树
       → 最终交付结果 + 阶段性交付物
       → 项目档案注入对话态上下文
```

建议把全流程交付物明确为下表：

| 阶段 | 核心交付物 | 交付物性质 | 主要下游消费者 |
|---|---|---|---|
| 用户输入 | `RawBriefPacket` | 原始输入对象 | 门禁 |
| 门禁 | `GateDecision` | 入口治理对象 | 设计任务书 / 对话态 |
| 设计任务书 | `DesignTaskBook`（完整设计任务书） | 独立交付对象 | 用户 / 设计师 / （可选）方案高参 |
| 方案高参 | 会话级执行编排、执行交付物、版本树、风险说明 | 动态执行对象 / 成果对象 | 用户、报告层 |
| 对话态 | 草稿对象 / 升级编译产物 | 非正式产物 / 升级输入 | 门禁（升级时）/ 方案高参（局部修订时） |

这里最重要的不是对象命名本身，而是下面这条关系：

**每个阶段都要留下可挂接、可追溯、可被下游消费的交付物；否则流程就只是状态变化，不是可运营系统。**

## 阶段交付物与最终交付物

全流程里的交付物可以分成两类：

### 阶段交付物

它们的作用是让下一个大节点能够继续工作，例如：

- `RawBriefPacket`
- `GateDecision`
- **`DesignTaskBook`**（完整设计任务书，设计任务书阶段T5冻结产出）
- 方案高参阶段的阶段性交付物与版本树（需根据用户选择是否进入方案高参来生成）

这类对象的核心意义是：

- 让流程能交接
- 让系统能回看
- 让异常能定位到具体产物层

> **重要说明**（2026-03-20 升级，2026-03-21补充）：**设计任务书是真正独立的、完整的里程碑**，用户可以在T5阶段拿到它并停止。设计师可基于这份完整的设计任务书自行执行后续设计工作。如果用户选择继续与系统互动进行设计深化、执行迭代、追问回应，系统会在方案高参阶段按当前意图动态发起动作，必要时生成会话级执行编排（而非继承大节点3固定步骤）。

### 最终交付物

它们的作用是让结果能够被用户验收并继续被消费，例如：

- 最终方案结果（基于冻结任务书的完整成果）
- 最终简报 / PDF
- 交付说明与风险摘要
- 可展示的图像、策略、分析结论包

这类对象的核心意义是：

- 能被用户验收  
- 能在对话态中（带项目上下文）继续被解释、补充、修订或派生

> **关于方案高参的完成条件**：方案高参阶段的交付物完成与否取决于用户是否提出深化需求、追问、修订指令。如用户在任务书阶段已满足需求然后停止，则方案高参交付物为可选；如用户继续与系统互动进行设计深化、执行迭代、追问回应，方案高参会依据这些指令逐步形成最终交付物。

一句话压缩：

**设计任务书是独立交付的完整里程碑，用户可在此停止自行执行；方案高参仅把任务书作为上下文输入，动作按当下需求重发起。**

### 对话态草稿对象

> 2026-03-14 新增

除了项目态的正式交付物链，系统还有一类**对话态专属产物——草稿对象**。

对话态不产出正式任务书，但每次有价值的对话都会沉淀为结构化草稿：

| 草稿对象 | 作用 |
|---|---|
| `IntentSeed` | 意图原点：捕捉最初的想法和方向 |
| `ProblemFrameDraft` | 问题框架草稿：初步组织问题结构 |
| `DirectionCandidatePack` | 方向候选包：可能的策略方向集合 |
| `ConflictPack` | 关键冲突包：已识别的矛盾与张力 |
| `BoundaryDraft` | 边界与红线草稿：初步约束条件 |
| `ConsensusPack` | 阶段性共识包：对话中已达成的共识 |

每个草稿对象必须携带元数据：

- `source`：来源（哪轮对话产生的）
- `user_confirmed`：用户是否已确认
- `inferred`：是否包含推断内容
- `open_questions`：可继续追问的点
- `upgrade_ready`：是否可升级为正式输入

草稿对象与正式对象的关系：

- 草稿对象**默认不等于**正式产物
- 当用户选择升级为项目态时，草稿对象由**升级编译器**映射为 `RawBriefPacket` + 预填充信号
- 升级后，对话中已确认的共识直接进入项目态，不需要重新从零说起

## 一、用户输入

### 这个大节点的功能

用户输入阶段负责：

- 接收用户原始表达
- 保留原话与原意
- 建立会话 / 项目入口
- 提取初始对象、目标、约束与场景线索
- 粗识别一主两辅入口信号（空间主线 / 驱动力轴 / 边界轴）与可继续转译的多学科线索

它的定位是：

**先接住，不急着下判断，但要为后续组织问题留下足够的入口信号。**

### 典型二级步骤

| 二级步骤 | 功能 |
|---|---|
| 输入接收 | 接住用户原始 brief、问题、附件、上下文 |
| 原话保真 | 记录用户原始表达，不让系统一上来就替用户改写 |
| 初始要素抽取 | 粗提项目对象、目标、场景、限制、偏好 |
| 会话建立 | 创建当前项目 / 任务的上下文容器 |

### 核心交付物

本节点至少产出：

- 原始 brief
- 初始结构化输入
- 进入门禁所需的基础上下文

如果用交付物语言来写，可定义为：

- `RawBriefPacket`
  - `raw_user_prompt`
  - `attachments`
  - `initial_context`
  - `session_or_project_stub`

### 与下一个节点的关系

它把“用户说了什么”交给门禁，但不替门禁决定“能不能继续”。

## 二、门禁

### 这个大节点的功能

**传统IT认知：** 负责数据校验、合法性安全检查、不符合结构则拦截请求（拦截器）。
**高参系统再定义（行业映射）：** 门禁是一个**“项目首诊医生”与“风险测试盘”**。

它不再做纯粹死板的拦截（如因为“模糊”就报错弹回），而是负责业务护航：
- **项目首诊：** 调用轻量逻辑敏锐诊断出最关键的硬缺口（如：到底哪座山、什么地形）。
- **极端条件发生器（逼出判断）：** 如果需求呈现极端矛盾（最低预算+顶级效果），抛出两条极端路径（A极省/B极好），逼迫用户取舍。
- **状态判定与路由：** 判断当前输入应进入对话态（持续交流）还是项目态（开始启动引擎计费并推演）。

它做的是：

**继续 / 限制 / 极端二选一 / 补条件 / 路由到对话态** 的判断。

### 典型二级步骤

| 二级步骤 | 功能 |
|---|---|
| 安全校验 | 过滤不允许内容与高风险输入 |
| 合法性与边界校验 | 检查是否越过系统职责或现实边界 |
| 可行性初判 | 判断是否具备继续分析和执行的基本条件 |
| 轻量预采集 | 在不打断主链的情况下补最小必要信息 |
| 系统可用性检查 | 确认关键依赖、调用能力、运行条件可用 |
| **状态判定** | **判断当前输入属于对话态（零星对话）还是项目态（完整项目分析）**（2026-03-14 新增） |

> 2026-03-14 补充：状态判定不是强制阻塞。系统自动判定，用户可随时手动切换。对话态中系统持续观察升级信号，项目态中允许临时对话态响应。

### 核心交付物

本节点产出的是结构化放行结论：

- 可继续（进入项目态）
- 进入对话态（2026-03-14 新增）
- 有条件继续
- 应拒绝
- 需要补前提再继续

如果用交付物语言来写，可定义为：

- `GateDecision`
  - `status`：continue / **conversation** / conditional_continue / reject / need_more_prerequisite
  - `reason`
  - `boundary_notes`
  - `required_preconditions`
  - `interaction_state`：conversation / project（2026-03-14 新增）

### 与上下游的关系

- 它消费用户输入阶段产出的原始材料
- `status = continue` → 进入项目态，为设计任务书阶段提供被允许进入主链的输入
- `status = conversation` → 进入对话态，由对话引擎接管（2026-03-14 新增）

一句话：

**门禁决定能不能往下走、以什么状态往下走，但不替设计任务书决定应该怎么走。**

## 三、设计任务书

### 这个大节点的功能

设计任务书阶段是整个主链的认知收敛中心，也是系统的**主价值输出里程碑**。

它负责把：

- 原始表达
- 门禁后放行的输入
- 项目背景与边界

收口为：

- `DesignTaskBook`

也就是：

**把"想做什么"变成"可以被系统执行的冻结对象"——一份真正覆盖洞察分析、差异化命题、战略定向的设计任务书。**

### 二级步骤（统一采用 T1-T5 口径）

> 2026-03-21 对齐：大节点 3（设计任务书）的二级步骤，以 `H-1 用户/01-用户视角交互流程` 为中心文档，统一采用 **T1-T5**。本文不再使用旧五步命名作为对外二级步骤口径。

| 步骤 | 核心目标 | 用户看到的关键卡片 | 输出 |
|---|---|---|---|
| **T1 信息对齐** | 站稳项目基线（目的/交付物/成功标准/边界/优先级） | 信息对齐卡 | 对齐基线 |
| **T2 梦幻团队组建** | 基于工作地图确认“谁来干” | 解题思路 + 团队清单卡 | 团队清单 |
| **T3 任务安排** | 基于工作地图明确“怎么干”（任务依赖/并行关系/成员落位） | 任务清单卡（任务1-10） | 任务清单锁定 |
| **T4 任务实施** | 完成方向锁定与专题确认（T4-1 / T4-2） | 方向基线卡 + 专题策略面板 | 方向与专题结论冻结 |
| **T5 任务书审阅与确认** | 审阅、内联编辑并冻结完整任务书 | 任务书审阅卡 | `DesignTaskBook` 冻结 |

**从 T0 到 T5 的用户链路（总纲级表达）**：

```text
T0 初始表达
  → T1 信息对齐
  → T2 梦幻团队组建
  → T3 任务安排
  → T4-1 方向锁定
  → T4-2 专题确认
  → T5 任务书审阅与确认（冻结）
  → T5.1 等待用户明确指令（继续 / 自行执行 / 需要修改 / 其他需求）
```

### T5 后对象导向分流判据（2026-03-21）

> 目的：防止把所有“追问”一概归入方案高参，确保 Node3 与 Node4 边界稳定。

| 用户追问对象 | 判定 | 系统流向 |
|---|---|---|
| 质疑任务书是否漏项/偏题/方向是否成立 | 仍属“定义题”问题 | 留在设计任务书闭环（按需回退 T4/T5） |
| 认可任务书，仅要求深化/变体/执行推进 | 属“基于已定义之题推进” | 进入方案高参 R0-R5 回合 |
| 目标整体更换或新增独立项目 | 不再是同一题目 | 升级至门禁，开启新项目线程 |

一句话：**追问“题有没有定对”在 Node3；追问“题定完后怎么做”在 Node4。**

> 注：涉及字段级回填与版本管理等内部实现细节，统一沉到实现文档维护；A/01 仅保留总纲层的 T1-T5 流程口径与节点边界。

### 核心交付物

这一节点最重要的产出是：

- `DesignTaskBook`

它作为可独立交付的冻结里程碑，供用户直接执行，或在后续作为方案高参的上下文输入。

如果写得更完整，可表达为：

- `DesignTaskBook`
  - 项目意图
  - 核心命题
  - 一主两辅冻结结果（战略层冻结 + 专题层冻结）
  - 边界与红线
  - 风险与判断依据

### 与下一个节点的关系

设计任务书交给方案高参的不是固定执行步骤，而是：

- 明确目标
- 明确边界
- 明确交付结构
- 明确约束边界（红线/风险/回退锚点）

**特别说明**：设计任务书本身已是可独立交付的完整里程碑——设计师可在此停止，基于任务书自行执行后续设计工作；或选择继续进入方案高参，由系统基于当下意图动态重组动作进行深化。

### T5 完成后的用户选择提示机制（2026-03-20 新增）

设计任务书冻结完成后，系统**不自动推进任何下一步**，而是向用户明确呈现选择菜单：

| 用户发起的指令 | 系统的响应 | 流向 |
|---|---|---|
| **「继续」** — 我需要系统帮我深化方案、生成视觉稿、反复迭代 | 系统以 `DesignTaskBook` 为上下文按当前意图重发起动作（必要时生成会话级执行编排），进入方案高参 | 进入→方案高参 |
| **「自行执行」** — 感谢，我已经有了任务书，我自己来做设计 | 系统确认存档，项目进入「暂停态」，冻结的任务书可随时查阅 | 项目进入等待态 |
| **「需要修改」** — 任务书里有几个地方我想改一下 | 用户指定修改范围 → 系统判断改动范围（表述修改 vs 实质改动）→ 对应的对齐处理 | 留在 T5 调整或回退 |
| **「新问题」** — 我想追问一个新的设计问题 / 衍生项目 | 用户新增指令 → 系统判决：启动新项目态还是在对话态中聊 | 回到对话态或新建项目 |
| **「我不确定」** — 我还需要思考一下接下来怎么办 | 系统保持无状态等待，用户可随时回来 | 项目进入「思考态」 |

**系统的关键行为约束**：
- ❌ 不自动推进到方案高参——必须等用户明确说「继续」
- ❌ 不反复提醒用户「要不要继续？」——等待用户主动发起指令
- ✅ 清晰展示任务书已交付完成——用户明确知道可以拿去自行执行
- ✅ 明确列举可选路径——降低用户的选择成本与心理负担
- ✅ 保持长期可用性——用户随时可回来发起新指令，无需重新开始

一句话：

**任务书阶段产出设计师最缺的——一份经过深度共同推理、洞察分析、战略定向的设计任务书。交付完成后，系统等待用户的明确指令；若继续，方案高参会按当前需求重新发起动作。**

## 四、方案高参

> 2026-03-20 升级，2026-03-21补充：方案高参阶段基于已冻结的设计任务书进行深化执行、设计迭代、用户追问回应。它合并了原「实施执行」与「追问」两个节点的全部职能，是系统与用户交付后的统一入口。**重要：方案高参不是自动激活的，只有用户在 T5 后发起「继续」指令时，系统才以任务书为上下文动态重发起动作（必要时生成会话级执行编排）并进入执行协调模式。**

### 0. 二级步骤（R0-R5，按需回合制）

| 步骤 | 名称 | 作用 |
|---|---|---|
| R0 | 触发判定 | 判断是否由用户明确触发（继续 / 修改 / 派生），未触发则保持等待态 |
| R1 | 意图归类 | 将本轮请求归类为解释、局部修订、深化执行、重大派生等 |
| R2 | 上下文装载 | 读取 `DesignTaskBook` + 项目档案 + 本轮增量输入，形成本轮工作上下文 |
| R3 | 动作编排 | 根据本轮意图动态生成执行序列与协作角色，不继承上一轮固定步骤 |
| R4 | 执行协同与审阅 | 执行动作、进行质量审阅与一致性检查，必要时触发轻量协调 |
| R5 | 回写收束与下一回合判定 | 将结果与风险回写项目档案，给出下一步选项并回到等待态 |

> 说明：R1-R5 不是“一次走完即结束”的单次流水，而是可按用户连续意图反复循环的回合机制。

### 1. 这个大节点的功能（设计任务书随后的执行与交付后互动统一入口）

**激活条件**：用户在 T5 任务书冻结完成后，发起「继续」指令

**激活时的系统动作**：读取 `DesignTaskBook` 与当前用户意图，动态重组本轮动作并进入执行深化与协调模式（必要时生成会话级执行编排）

**职能说明**：

方案高参阶段是系统的**执行深化与交付后对话中枢**。

它基于已冻结的 DesignTaskBook，负责：
- 任务展开与批次协同
- 调度专家角色并挂载核心技能
- 执行并产出各项物理交付物
- 质量预检并聚合回流给用户
- **交付后处理**：解释、局部修订、新项目派生等一切后续分流

一句话：
**它不是沿用固定步骤的执行器，而是基于冻结任务书上下文按需发起动作的调度执行总线，同时承担交付后的全部用户互动职责。**

### 1.1 依赖读取与一致性检查（2026-03-19 补强 / 2026-03-20 升级）

方案高参执行阶段中，专家协作遵循"**共同读取冻结对象**，而非专家之间实时互联"原则：

- 默认读取源：`DesignTaskBook`（来自设计任务书阶段冻结） + 当前节点增量上下文（必要时附会话级执行编排）
- 不允许把其他专家的原始长文本作为硬前置依赖直接互传
- 跨专题协调重点放在“结果汇总检查”，不放在“过程实时互读”

**一致性检查机制（汇总里程碑触发）**：

```
专题产出汇总
  ↓
跨专题一致性检查（如视觉×嗅觉×声景）
  ├─ 无冲突 → 进入下一节点
  └─ 有冲突 → 轻量召回协调
       ↓
     由总整合角色裁决（必要时联动实施边界顾问）
       ↓
    裁决结果版本化回写 DesignTaskBook / 会话级执行编排
```

该机制保持主架构不变：方案高参仍以冻结任务书为约束输入并按当前意图动态编排生产成果，只在汇总点增加收敛检查与责任归口。

### 1.2 洞察亮相信号与风险总控（2026-03-19 补强）

方案高参阶段除消费显性专家结论外，还需消费设计任务书阶段沉淀的“洞察亮相信号”（Insight Reveal Signals）：

- 经营与市场信号（竞品/差异化/ROI）
- 区域与场地信号（气候耐候/游客画像/供应链）
- 标杆与突破信号（同类对照/跨界方法）
- 风险总控信号（失败条件、避坑项、回退触发条件）

**消费原则**：
- 关键洞察先以摘要级前台亮相（不展开长论证）；
- 亮相后分流：先完成 T2/T3 的事实与任务基线，再在 T4/T5 完成取舍与冻结；
- 仅在高影响/高风险/冲突命中时升级为条件触发席位；
- 与梦幻团队四层分工对齐：资料层进入 T2/T3，议题层进入 T4，过程治理层贯穿 T4/T5 与后续方案高参回合，启发层默认可折叠并可转议题；
- 仍通过单一中介读取（`DesignTaskBook + 当前节点上下文（必要时附会话级执行编排）`），不引入专家间实时互联。

**风险总控闭环**：
- 方向层（T4）产出风险快照；
- 专题层（T5）产出避坑条目；
- 审阅冻结层（T5）产出风险三分法（已覆盖 / 知情接受 / 悬空待定）；
- 对悬空高风险项触发回退或后续验证任务。

### 2. 稳定技能池层 (Skills Level)

节点之下，系统为执行代理（Agents / 专家角色）提供以下 6 类稳态能力（Skills）。技能是长期稳定的业务抽象，不关心底层具体挂载了哪个外接 API：

- **Evidence Skills (取证能力)**：互联网宽域检索、私有知识底盘穿透检索、项目过往档案召回。
- **Reasoning Skills (推理判断)**：方案级对比评估、硬约束规则校验（如消退红线核对）、方案逻辑推敲、风险预判。
- **Generation Skills (生成能力)**：多模态图像/渲染图生成、项目文本与排版语料组装、结构化图表生成。
- **Transformation Skills (转换能力)**：文本大纲改写与汇总、多版本设定参数映射、格式解析转换。
- **Review Skills (审阅能力)**：阶段性质量预检、上下游内容一致性核对、破坏冻结区的红线检测。
- **Execution Control Skills (执行控制)**：并发批次调度、局部重跑路由（入 DeltaRouter）、增量组装。

### 3. 运行时动作层 (Actions Level)

当技能被调用时，将交由第 5 层（原子动作与外挂接口层）真实的无状态插件执行。这些动作是纯函数式的，也是**可被系统精确调度、记录成本和审计的物理调用单元**。
例如：
- search_web (执行外网查找)
- query_knowledge_base (调取 RAG 检索)
- generate_image (调取 MJ/SD 生图引擎)
- generate_text_package (组合排版文案)
- validate_constraints (与数据库绝对值比对)
- regenerate_delta (启动局部重绘制图)

### 4. 风险门禁分级层 (Gates Level)

为了确保能力调用不越界（防范模型幻觉、预算超支、越权），所有动作实施前必须穿透执行门禁。系统将物理动作分四级（A/B/C/D）：

- **A类：安全认知动作（默认自动）**
  - **涵盖**：检索私有底盘、基线对比、编撰草稿。
  - **策略**：无副作用，系统自动快速完成，不阻塞主流程。
- **B类：外部取证动作（自动但强审计）**
  - **涵盖**：广域网搜索、抓取外部案例和研报。
  - **策略**：自动调用，但必须留痕（进入系统 Audit 审计流），记录抓取链接，备查溯源。
- **C类：高成本生成动作（预设配额与熔断）**
  - **涵盖**：大批量的图像生成、重资源的外部代码引擎调用。
  - **策略**：前置拦截。必须依赖**本轮会话级执行编排**中的 Budget Guard（如：生图上限 15次）。超配额则拦截挂起，靠软提示向用户申请追加预算。
- **D类：不可逆或现实操作（阻断级中继确认）**
  - **涵盖**：触碰核心区的物理修改、外发现实世界的指令（调 API 发邮件、自动下单等）。
  - **策略**：执行拦截，强制抛出高危 Confirm 门禁卡片，必须由人类用户明确确认才可放行流转。

### 核心交付物

本节点产出：

- 最终交付结果
- 阶段性交付物
- 风险说明
- 版本树（如 `v1 → v1.1 → v1.2`）
- 一致性检查记录（跨专题冲突与协同结果）
- 仲裁说明（冲突裁决者、裁决依据、回写位置）
- 洞察亮相记录（系统自动补位的关键信号与触发依据）
- 风险台账与处置结果（覆盖/接受/悬空）
- 交付完成后注入对话态上下文的项目档案
- **交付后追问处理记录**（用户后续提问、修订、派生的完整轨迹）

如果用交付物语言来写，可定义为：

- `DeliveryBundle`
  - `final_deliverables`
  - `stage_deliverables`
  - `insight_records`
  - `risk_summary`
  - `version_lineage`
  - `consistency_check_records`
  - `arbitration_notes`
  - `insight_reveal_records`（兼容旧键：`hidden_insight_records`）
  - `risk_register`
  - `risk_disposition_records`
  - `explanation_materials`

### 交付后的流向

方案高参不是流程终点，但也不交给下一个"节点"。

交付完成后，系统自然回归对话态。方案高参产出的全部结果（交付物、过程痕迹、版本关系、审阅记录）自动注入对话态上下文，让用户可以继续在对话态中完成解释、修订或派生——这些后续动作实际上仍由方案高参的内部路由机制处理（small_followup / delta_action / major_action）。

## 交付后回归对话态

> 2026-03-14 重构：原"追问"不再作为独立第 5 节点。项目交付完成后，系统自然回归对话态；对话态带着完整项目上下文，承担原追问的全部职责。

### 为什么追问不是独立节点

原设计中"追问"作为第 5 大节点，负责解释、修订和派生。但经分析发现：

- 对话态本身已具备完整的意图识别、分流和知识调用能力
- 追问与对话态的唯一差别是**上下文里有项目档案**
- 维护两套分流逻辑（对话态一套、追问又一套）增加了不必要的复杂度

因此：**追问 = 带项目上下文的对话态**，不需要独立节点。

### 项目上下文注入

项目态交付完成后，系统自然回归对话态，同时将以下内容注入对话态上下文：

- 完整交付物档案（`DeliveryBundle`）
- 版本树与版本关系
- 决策记录与风险摘要
- 方案高参过程中的审阅意见与过程痕迹
- 跨专题一致性检查记录与仲裁说明
- 洞察亮相记录与风险处置轨迹
- 已冻结的 `DesignTaskBook` 与方案高参会话编排记录（如有）

注入后的对话态，与项目无关的对话态共享同一个引擎，只是上下文更丰富。

### 对话态如何承担原追问职责

| 用户交付后动作 | 对话态响应 | 等价原追问分流 |
|---|---|---|
| 解释（"为什么选这个材料？"） | 直接在对话态中回答，引用项目档案 | `small_followup` |
| 延展讨论（"那如果换成木结构呢？"） | 对话态陪伴思考，沉淀为草稿对象 | `small_followup` |
| 局部修订（"大堂层高改成 5 米"） | 检测到修改意图 → 局部重入方案高参（增量执行） | `delta_action` |
| 平行派生（"基于这个做个大胆版本"） | 检测到新项目信号 → 升级至门禁 → 新一轮项目态 | `major_action` |
| 方向全换（"推翻，从零来"） | 同上，但与原项目继承关系更弱 | `major_action` |

一句话：

**项目交付后，系统不是停在项目态等下一条指令，而是回到对话态继续陪伴。用户需要解释就解释，需要改就改，需要新项目就升级——全由同一个对话引擎完成。**

## 节点之间的关系：谁消费谁的产出

| 上游 | 下游 | 交接对象 | 关系说明 |
|---|---|---|---|
| 用户输入 | 门禁 | 原始 brief / 初始结构化输入 | 门禁基于原始材料做放行判断 |
| 门禁 | 设计任务书 / 对话态 | 放行结论 + 状态判定 | status=continue 进项目态；status=conversation 留对话态 |
| 设计任务书 | 方案高参 | `DesignTaskBook`（独立交付） | 设计任务书是完整的交付里程碑；如果用户发起方案高参请求，系统才基于当前意图动态发起本轮动作 |
| 方案高参 | 对话态（回归） | 交付结果 / 版本树 / 项目档案 | 交付完成后注入对话态上下文 |
| 对话态 | 门禁（升级时） | 草稿对象 / 升级信号 | 升级编译器将草稿映射为 `RawBriefPacket` |
| 对话态 | 方案高参（局部修订时） | 执行层修改指令 + 原交付物引用 | 增量执行，不重走 T1→T5（不改写 `DesignTaskBook`） |

### 节点契约（三元模型：输入 / 输出 / 禁止项）

| 节点 | 输入 | 输出 | 禁止项 |
|---|---|---|---|
| 设计任务书（Node3） | `GateDecision(status=continue)` + 已确认上下文 | `DesignTaskBook`（独立交付里程碑） | 预生成 Node4 的执行批次、执行指令、自动推进信号 |
| 方案高参（Node4） | `DesignTaskBook` + 用户本轮意图 | 本轮会话级执行编排 + 执行交付物 + 回写记录 | 将 Node3 冻结结论静默改写（必须走正式回退机制） |

这里最关键的几条是：

1. **设计任务书是独立交付的完整里程碑**——交接对象是 `DesignTaskBook`，用户可以在此停止。
2. **会话级执行编排仅在方案高参中按需生成**——不是设计任务书阶段预制下发。
3. **方案高参阶段按“当前意图 + 任务书上下文”动态发起动作**——需求定义与执行深化界限清晰。

## 附：系统分步验证路径（MVP 规划）

避免“架构过全”导致落地延期，系统遵循**三阶段 MVP 剥树皮式交付**：

### Phase 1：发散前厅（证明高频交互闭环）
- 聚焦：完善“纯对话态”。验证用户是否愿意持续在此闲聊找灵感。
- 核心产出：跑通对话编排引擎与轻量级草稿提取。

### Phase 2：单轨贯通（证明长链条生产闭环）
- 聚焦：在单一垂直场景（如“四川山地民宿”）跑通完整骨架。
- 核心产出：跑通“收集草稿 → 触发软提示升级 → 过门禁 → T1至T5 冻结任务书 → 执行端生图与文字包装包”的主链。此时暂不接驳复杂的 Delta 局部重入。

### Phase 3：能力绽放（证明生态派生极高价值）
- 聚焦：跑通交付后回流对话态的高阶应用。
- 核心产出：实现增量重跑（DeltaRouter）与重大版本派生（DerivedProject），全面放开多子专家调用和记忆的长效存储。

进一步说，全流程不是步骤堆叠，而是：

**交付物接交付物，节点是这些交付物的生产场。**

## 推荐作为系统总说明保留的几句话

1. 系统采用双态架构：对话态是常驻底态，项目态是结构化生产管线。
2. 项目态主链为 4 大节点：用户输入、门禁、设计任务书、方案高参。
3. 大节点定义阶段，二级步骤定义做法。
4. **设计任务书阶段的终点是独立交付的完整里程碑：用户可拿着 `DesignTaskBook` 停止并自行执行设计；或发起方案高参请求，由系统基于当前意图动态发起动作**。
5. 方案高参阶段负责在冻结任务书上下文中进行深化、迭代与追问分流，二级步骤采用 R0-R5 按需回合制，而不是按大节点3固定步骤执行。
6. 项目交付完成后回归对话态；对话态在项目上下文中完成解释、修订与派生（实际由方案高参内部机制支撑）。
7. 不经用户明确选择，绝不冻结正式任务书，绝不启动下游执行。
8. **设计任务书冻结后，系统不自动推进方案高参——必须等待用户发起明确指令**（「继续深化」、「自行执行」、「返回成果页修改」、「新问题」等），才决定下一步流向。系统清晰展示选择菜单，但不主动催促。
9. 两态共享同一个底盘、同一份记忆、同一个人格——同一个高参兄。
10. **设计任务书本身已可独立停止** — 用户可基于冻结的任务书自行执行后续设计，或选择进入方案高参进行深化。

## 最终结论

**这个项目应被理解为一个"对话态常驻 + 项目态 4 节点主链"的双态系统。**

对话态是用户与高参兄交互的常驻底态——日常陪伴、沉淀草稿、组织判断。当对话信号积累到项目级别时，系统软提示升级进入项目态：用户输入接住原始 brief，门禁判断是否放行并路由状态，设计任务书阶段把问题冻结为 `DesignTaskBook`（可独立交付）；用户若继续进入方案高参，系统再基于任务书上下文与当前意图动态发起动作完成交付。

交付完成后，系统不停在项目态等待下一条指令，而是自然回归对话态——此时对话态已注入完整项目档案，具备解释、修订与派生的全部能力。

一句话：

**对话态陪你想清楚，项目态帮你做出来，做完了回到对话态继续陪你。**
