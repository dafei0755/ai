## 一、为什么流程之外还需要架构文档

流程文档回答“按什么顺序推进”，架构文档回答“由谁承接、对象如何稳定流转”。

如果只有流程没有架构，通常会出现三类问题：

1. 流程一改，对象结构跟着漂移；
2. 新增能力时，边界不清导致互相越权；
3. 结果可运行但不可追溯，难以治理和审计。

因此本文固定两件事：

- **纵向分层职责**（谁负责什么）
- **横向对象链契约**（对象何时创建、冻结、消费、回写）

## 二、七层架构（纵向分层）

```text
入口交互层
  ↓
流程编排层
  ↓
领域对象层
  ↓
能力执行层
  ↓
基础能力接口层

（横向贯穿）知识与记忆层 + 运行时与治理层
```

| 分层 | 核心职责 | 不负责什么 |
|---|---|---|
| 入口交互层 | 承接用户输入、卡片交互、等待态与气口区体验 | 不定义对象真相源 |
| 流程编排层 | 对话态编排 + 项目态 4 节点推进（用户输入、门禁、设计任务书、方案高参）+ S1–S5 步骤调度 | 不直接存放对象本体 |
| 领域对象层 | 定义核心对象、字段契约、冻结/版本/回写规则 | 不做流程判定 |
| 能力执行层 | 分析、生成、审阅、聚合等业务能力编排 | 不改流程剧本 |
| 基础能力接口层 | 无状态工具调用（检索、生成、转换、校验） | 不承载业务语义 |
| 知识与记忆层（横向） | 提供规则、案例、模板、长期记忆供弹 | 不直接驱动节点流转 |
| 运行时与治理层（横向） | 运行、审计、回放、断点续传、风险门禁与人工接管 | 不定义业务内容 |

## 三、证据优先机制在架构层如何落地（2026-03-19）

### 3.1 四层分工与对象分流

梦幻团队不再是“统一黑盒输出”，而是四层并行产出、分路消费：

| 梦幻团队分层 | 产出对象 | 首要消费节点 |
|---|---|---|
| 基础研究资料层 | `ResearchBriefPack`（事实底图） | T1.6（先呈现） |
| 议题交互层 | `AgendaProposals`（需用户裁决议题） | T2（再裁决） |
| 过程治理层 | `RiskRegister` / `ConsistencyChecks` / `ArbitrationNotes` | T4/T5/T6 全程门禁 |
| 启发层 | `InspirationHints`（可折叠启发） | 可选查看，可转议题 |

核心顺序固定为：

```text
T1.5 ExpertTeamPack 确认
  ↓
T1.6 ResearchBriefPack 呈现（非裁决）
  ↓
T2 AgendaProposals 裁决（需确认/讨论/交互）
```

### 3.2 洞察命名统一

- 前台与对象统一使用“**洞察亮相（Insight Reveal）**”语义；
- 对象键统一为 `insight_reveal_records`；
- 兼容历史数据时可读旧键 `hidden_insight_records`，但新写入不再使用旧键名。

## 四、领域对象层（真相源）

### 4.1 核心对象清单

| 对象 | 阶段 | 作用 |
|---|---|---|
| `RawBriefPacket` | 用户输入 | 原始 brief 与初始上下文 |
| `GateDecision` | 门禁 | 放行/补条件/拒绝/路由对话态 |
| `ExpertTeamPack` | S1→T1.5 | 专家团队构成与来源依据 |
| `ResearchBriefPack` | T1.6 | 事实底图（市场/场地/标杆） |
| `AgendaProposals` | S2-a | 议程切口与来源、提案责任链 |
| `AgendaVoiceLedger` | S2-a | 主提/联提/暂缓+原因可见化 |
| `DesignTaskBook` | S5 | 冻结任务书 |
| 会话级执行编排（按需） | 方案高参回合内 | 本轮执行编排对象 |
| `DeliveryBundle` | 实施执行 | 最终交付与阶段性交付集合 |
| `DeltaDelivery` | 交付后对话态 | 局部增量重入执行 |
| `DerivedProject` | 交付后对话态 | 重大派生项目 |

### 4.2 真相源生命周期契约

1. **草稿是提议，不是定论**：对话态草稿对象默认不可替代冻结对象。  
2. **冻结即当前真相**：`DesignTaskBook` 冻结后成为当前线程真相源；方案高参仅在回合内按需生成会话级执行编排。  
3. **禁止静默覆写**：所有修订必须版本化（如 `v1.0 -> v1.1`）或派生为 `DerivedProject`。  
4. **治理记录随对象走**：风险快照、一致性检查、仲裁说明必须回挂到对应版本。

## 五、流程编排层与对象层的边界

编排层只做三件事：

- 何时创建对象
- 何时消费对象
- 何时触发回退/升级

对象层只做两件事：

- 定义对象结构与字段契约
- 定义冻结、版本、派生与回写规则

这条边界用于避免“流程改动 = 数据结构重写”的耦合风险。

## 六、治理闭环（风险与一致性）

### 6.1 风险闭环对象

- `risk_register`：风险台账
- `consistency_check_records`：跨专题一致性检查记录
- `arbitration_notes`：冲突仲裁记录
- `risk_disposition_records`：风险三分法（已覆盖 / 知情接受 / 悬空待定）

### 6.2 闭环触发路径

```text
T4 方向锁定 → 生成风险快照
  ↓
T5 专题展开 → 一致性检查 / 冲突仲裁
  ↓
T6 签署确认 → 风险三分法归档
  ↓
高风险悬空项 → 触发回退或后续验证任务
```

治理闭环是“过程中持续生效”的，不是仅在末端补一个总结。

## 八、最终结论

本系统必须同时满足两条主线：

1. **流程主线**：对话态常驻 + 项目态 4 大节点；
2. **架构主线**：七层承接 + 对象真相源 + 治理闭环。

在 2026-03-19 口径下，关键新增是：

- T1.6 `ResearchBriefPack` 成为证据优先的正式架构对象；
- 梦幻团队四层分工被映射为可消费的对象分流；
- “洞察亮相”与风险闭环在对象层与治理层双落地。

一句话：

**流程让系统走得动，架构让系统走得稳；证据优先与治理闭环让系统走得久。**
