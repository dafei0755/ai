## 一句话定义

> 专业底盘不是"知识大池"，而是**可调用、可判断、可进化、可治理**的行业认知基础设施。  
> 它不是另建一个系统，而是给现有 5 个知识仓库加一个**智能配送中心** — 知道每个节点需要什么，按需组装，精准投递。

## 一、为什么现在需要底盘

### 1.1 当前系统的本质特征

现有 6 大节点 + 武器库机制解决的是**"过程逻辑"**问题：执行顺序、职责边界、中断审批、质量门禁。这是必要条件，但不是充分条件。

没有底盘的系统在每个项目上都是**"空手上阵、现场发挥"**：
- 知识分散在各节点的 prompt 字符串里
- 同类问题重复推理，无法复用历史判断
- 规范与经验靠"缘分触发"，不是"系统检索"
- 成功策略难沉淀，失败教训更难反哺
- 不同专家角色对同一概念各说各话

> A 类比：就像让 7 个没有共同病历系统的医生会诊 — 每人都很专业，但没有共享的检查结果和历史记录，最终诊断质量取决于他们碰巧记住了什么。

### 1.2 题型跨度揭示的底盘需求

`q.txt` 里的题型跨越：
- 单体住宅 → 城市更新
- 概念叙事 → 工程技术 → 运营策略
- 高寒供暖供氧 → 高盐雾木构防腐 → 杜比声学 → 行为经济学
- 200 米地标 → 乡村振兴 → 不停业快装 → 零碳样板房

**这个跨度意味着**：如果没有统一底盘，每个环节都在"现场回忆、现场拼装"。短期看像灵活，长期看就是知识无法积累的天然上限。

### 1.3 没有底盘 vs 有底盘的差距

| 维度 | 没有底盘 | 有底盘 |
|------|---------|--------|
| 知识存储 | 散落在 prompt 字符串里 | 结构化，可查询，可版本化 |
| 知识调用 | 每个节点各找各的 loader | 统一接口，按场景组装 |
| 错误传播 | 某个 prompt 里的过时知识会影响所有输出 | 知识变更一处生效，全局同步 |
| 经验积累 | 好案例做完就消失了 | 沉淀为可检索的经验卡 |
| 专业标准 | 靠 LLM 的隐式记忆 | 显式规则，LLM 的盲区被结构补位 |
| 系统进化 | 只能靠改 prompt，手工维护 | 学习飞轮，使用中自动改善 |

## 二、现状盘点：5 个独立知识仓库

系统已沉淀大量行业知识，但分布在 5 个独立仓库中，各有各的 loader，无统一接入层：

| 仓库 | 内容 | 规模 | 加载方式 | 问题 |
|------|------|------|---------|------|
| `sf/` 知识文件 | 12 模式引擎、12 能力核心、评估矩阵、输出标准、CASE | 55 md 文件，~7K 行 | `sf_knowledge_loader.py` | 只供执行节点读取，需求分析阶段不可见 |
| `config/` YAML | 107 配置：prompt 模板、维度库、角色基因池、模式任务库、本体论 | 49K 行 YAML | `PromptManager` + 各专用 loader | 知识混在配置里，难以独立查询 |
| `ontology.yaml` | 10+ 项目类型框架、元框架、专家扩展维度 | 67K 单文件 | `OntologyLoader` | 单文件过大，维护困难 |
| 硬编码 dict | 身份模式、投射类型、场景维度映射、角色 LLM 参数 | 散落在 4-5 个 py 文件 | 直接 import | 最不透明，新增类型需要改代码 |
| `learning/` | 概念发现、标签晋升、维度反馈 | SQLite + 4 个服务 | `taxonomy_learning_collector` | 调度器注册的关键方法缺失（见§六.1） |

### 碎片化的三种具体表现

**表现 1：同一概念，4 处口径不一致**

"项目类型"在 4 个地方有不同命名和分类粒度：
- `_type_registry.py`：30+ 类型（关键词匹配）
- `ontology.yaml`：10+ 框架（按项目类型组织）
- `radar_dimensions.yaml`：按项目类型的维度映射
- `MODE_TASK_LIBRARY.yaml`：按模式的任务库

新增一个项目类型（如"宠物医院"）需要同时改 **4 个文件**，漏改任意一处就会导致行为不一致。

**表现 2：知识消费点对点，不是池化的**

```
当前：各节点直接找各自的 loader
  requirements_analyst → PromptManager + ModeDetector
  execution_nodes → OntologyLoader + sf_knowledge_loader
  progressive_questionnaire → DimensionSelector

理想：统一入口，按场景组装
  所有节点 → KnowledgeRegistry → 按需组装知识包
```

**表现 3：学习系统是"观察型"而非"适应型"**

`learning/` 有概念发现、标签晋升、反馈收集，但：
- 收集的数据不会自动更新核心知识（prompt、维度、模式定义）
- 没有 A/B 测试机制
- 没有知识版本化
- **关键调度任务方法缺失**（见§六.1）

## 三、底盘架构设计

### 3.1 整体架构：不是图谱，是"分层配送中心"

**为什么不直接上知识图谱？**

| 维度 | 知识图谱（KG） | 知识合同层（推荐） |
|------|-------------|-----------------|
| 建设成本 | 极高（本体建模 + 关系标注） | 低（~150 行接口层） |
| 维护成本 | 高（关系会随时间过时） | 低（矩阵式，改一处全局生效） |
| 查询能力 | 强（任意关系遍历、多跳推理） | 中（按场景组装） |
| 与 LLM 协同 | 冗余（LLM 自带隐式图谱） | 互补（显式知识补充 LLM 盲区） |
| 学习能力 | 需额外建设 | 可复用现有 `learning/` 基础设施 |
| 适合阶段 | 产品成熟期，有专职知识工程师 | **现在**，个体开发者 |

> **图谱的时机**：当矩阵关系节点 > 50 且出现**多跳推理**需求时（如"某材料 → 适用气候 → 可推荐专家 → 评估标准"），再升级。当前原材料不足，过早建图谱会建出"很好看但摸不到门把手"的蜘蛛网。

**整体层次图**

```
┌──────────────────────────────────────────────────────────────┐
│                      工作流节点层                              │
│  requirements_analyst / feasibility / gap_filling / executor  │
│                       ↓ 统一调用                               │
│                 KnowledgeRegistry（合同层）                    │
│   query_rules() | get_mode_context() | get_execution_context() │
└───────────────────────┬──────────────────────────────────────┘
                        │ 路由分发（按知识类型）
         ┌──────────────┼──────────────┬──────────────┐
         ▼              ▼              ▼              ▼
   ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
   │ L1 规则层 │  │ L2 矩阵层 │  │ L3 经验层 │  │ L4 项目  │
   │ 硬约束   │  │ 类型×模式 │  │ 案例向量 │  │ 记忆层   │
   └──────────┘  └──────────┘  └──────────┘  └──────────┘
                                                  ↑
                              [严格隔离：行业知识 ≠ 项目记忆]
```

### 3.2 四层知识设计

#### L1：规则层（强约束，只读）

**存放**：行业标准、法规指标、面积基准、典型造价区间、冲突规则、配额审查清单  
**形态**：`industry_standards.yaml`（现有）升级为全节点可查的服务  
**特性**：只读，版本号追踪，人工审核才能更新  
**接口**：`query_rules(space_type, constraint_type)` → `[RuleCard]`

> L1 的核心原则：**规则优先级高于 LLM 推理，不可被 prompt 覆盖。**  
> 类比：消防距离不因设计方案精彩而失效。

#### L2：矩阵层（单一事实源，中频演进）

**存放**：项目类型 × 设计模式的映射关系、维度推荐、任务库、角色推荐  
**形态**：新增 `type_mode_matrix.yaml`（取代 4 处口径不一致的分散定义）  
**特性**：变更一处，全局生效；支持 `tier: core | reference | deprecated` 分级  
**接口**：`get_mode_context(mode_id)` / `get_project_type_context(project_type)`

矩阵结构示例：

```yaml
# knowledge_base/type_mode_matrix.yaml
project_types:
  rural_construction:
    display_name: "乡村建设"
    tier: core
    primary_modes: [M5_rural_context]
    secondary_modes: [M3_emotional_experience, M12_ecology_regeneration]
    ontology_framework: "rural_regeneration_urban_renewal"
    radar_dimensions: ["文化真实性", "在地材料", "社区参与", "运营可持续"]
    mandatory_tasks: ["文化保护策略", "社区参与方案"]
    case_examples: ["狮岭村"]
    motivation_types: [M18_cultural_preservation, M19_community_economy]

  healthcare_facility:
    display_name: "医疗康养设施"
    tier: core
    primary_modes: [M11_healthcare_healing]
    secondary_modes: [M6_commercialbrand, M7_tech_smart]
    radar_dimensions: ["声学隔音", "空气质量", "动线分离", "情绪管理"]
    ...
```

#### L3：经验层（向量，软知识，可增量摄入）

**存放**：历史任务书（`confirmed_design_brief`）、成功方案片段、失败复盘摘要、典型追问模式  
**形态**：现有 Milvus 向量库（已有）  
**特性**：自动摄入，无需人工标注  
**学习入口**：用户确认任务书后 → 自动摄入 L3（E-001 实现后生效）  
**接口**：`retrieve_cases(query, filters={'project_type', 'mode', 'phase'})`

**核心池准入原则**（防止"什么都吃"）：
> 只有满足以下**三条**的内容才进核心池：  
> ①能被流程**复用** ②能形成**判断** ③能**跨项目迁移**  
> 
> 招标全文、案例详述 → 进**外围向量库**（可检索但不绑定核心流程）  
> 失败模式摘要、决策规则推断 → 进**核心池**  
> 在 `type_mode_matrix.yaml` 用 `tier: reference` 区分外围内容。

#### L4：项目记忆层（严格隔离，per-session）

**存放**：当前项目的用户动机、偏好倾向、否决历史、已确认项、冲突轴、迭代记录  
**形态**：`state` 字段 + `ProjectMemoryStore`（跨会话持久化）  
**关键边界**：**行业知识要稳，项目记忆要活，两者绝对不混用**

> A 的警告：把个别客户偏好当行业真理，是知识底盘最常见的污染路径。  
> 某个用户偏好"不要用原木"，不应影响其他项目的原木推荐逻辑。

## 四、检索策略：四路并行

单一向量检索不够用。设计问题往往同时需要：

| 检索路 | 适合什么内容 | 当前工具 | 状态 |
|--------|------------|---------|------|
| **向量检索** | 语义相近案例、经验片段、风格描述 | Milvus（已有） | ✅ 已有 |
| **关键词/混合检索** | 规范词、品牌词、材料名、精确术语 | BM25（可在 Milvus 叠加） | ⚠️ 未启用 |
| **规则过滤** | 约束硬边界、禁忌类型、面积基准 | `query_rules()` | ⬜ 待建 |
| **矩阵查询** | 项目类型→模式→维度→角色 | `get_mode_context()` | ⬜ 待建 |

`KnowledgeRegistry` 在合同层做**融合排序**，按优先级：规则 > 矩阵 > 混合检索 > 向量。

> 核心逻辑：不是"先搜一堆文本再让模型悟"，而是"**先把候选世界收窄成一个对的问题宇宙，再让模型表达**"。

## 五、与工作流节点的集成坐标

底盘不是独立系统，它服务于 6 大节点中的具体调用点：

| 工作流节点 | 调用类型 | 方法 | 对应主架构演进项 |
|----------|---------|------|----------------|
| Node 2 检查门禁 | 规则过滤初筛 | `query_rules(space_type)` | E-002 问题定型前置化的底盘支撑 |
| Node 3 RA（gap_filling） | 模式特定追问模板 | `get_mode_context(mode_id)` | H-001（模式感知追问） |
| Node 3 RA（radar） | 按项目类型组装维度 | `get_project_type_context()` | 武器库 Step 2 的底盘支撑 |
| Node 3 需求洞察 | 写入 confirmed_design_brief | `ingest_brief(brief)` | E-001 任务书实体化 |
| Node 5 执行循环 | 专家知识包 | `get_execution_context(mode, role)` | 武器库 Step 3（M23 交接） |
| END 节点 | 学习摄入 | `trigger_learning(session_data)` | Phase 3 学习飞轮 |

这 6 个调用点是 `KnowledgeRegistry` 接口设计时的**优先场景**，其他接口等需求出现再扩展。

## 七、自动学习机制：半自动 + 受控治理

### 7.1 学习闭环设计

```
触发：用户确认任务书（confirmed_design_brief）
  ↓
L3 向量库自动摄入（无需人工，立即生效）
  ↓
项目执行完成 → DimensionExtractor 从 final_report 提取候选维度（已有模块）
  ↓
QualityAssessor 评分（已有模块）
  ↓
分数 > 阈值 → 进入"待审队列"（新增，不直接写入核心）
  ↓
人工确认 → 写入 L2 矩阵层（受控学习）
```

### 7.2 三条核心原则

**原则 1：L3 可自动摄入，L1/L2 必须经过人工确认队列**

L3（向量库）是软知识，摄入错误影响范围有限；L1（规则）和 L2（矩阵）的错误会影响所有后续项目。

**原则 2：先"候选提议"，再"审核发布"**

```
新内容 → 自动抽取实体/标签/关系 → 置信度评估 → 分级入库
  ↓ 按三级分流
  ├─ 高置信、通用性强 → 待审队列（人工快速审核）
  ├─ 中置信、项目特例 → 临时层（记录但不推广）
  └─ 低置信、涉及规范硬知识 → 丢弃或人工处理
```

**原则 3：核心池克制原则**

> 系统最怕"胃口太好" — 吃到最后连塑料袋也当营养。  
> 核心池必须克制：只存能复用、能判断、能跨项目迁移的知识。  
> 有些内容只适合做外围参考，不适合进核心池。

### 7.3 数据飞轮路径

```
用户在 radar 阶段手动添加了"声学隔音"维度（系统没推荐）
  ↓
learning_collector 记录：project_type=healthcare, user_added=声学隔音
  ↓
累积 8 次（阈值可配置）
  ↓
taxonomy_promotion_service 触发晋升提议
  ↓
待审队列 → 人工确认
  ↓
自动更新 type_mode_matrix.yaml：healthcare.radar_dimensions += "声学隔音"
  ↓
下次 healthcare 项目自动推荐该维度
```

### Phase 1：统一接入层（中期，K-001 + K-002 + 基础治理 + 可观测性基线）

> **Phase 1 前置**：先产出《KnowledgeRegistry Schema Contract v1.0》（约 1 页，即 K-000），冻结每个接口的输入规格、输出字段（含 `source / tier / confidence / version / empty_reason`）、空返回策略。Schema Contract 冻结后才开始 K-001 编码。

**K-001：新增 `KnowledgeRegistry` 统一索引层（~150 行）**

```python
# intelligent_project_analyzer/knowledge_base/knowledge_registry.py
class KnowledgeRegistry:
    def get_mode_context(self, mode_id: str) -> ModeContext:
        """模式的完整知识上下文：定义+能力+评估+标准+维度+任务库+CASE"""

    def get_project_type_context(self, project_type: str) -> ProjectTypeContext:
        """项目类型的完整知识上下文：本体论+空间分类+维度+角色推荐"""

    def get_execution_context(self, mode_id: str, role_id: str) -> ExecutionContext:
        """专家执行所需的完整知识包：本体论+评估标准+角色指导+输出格式"""

    def query_rules(self, space_type: str, constraint_type: str | None = None) -> list[RuleCard]:
        """规则过滤：返回适用的约束卡片"""

    def retrieve_cases(self, query: str, filters: dict) -> list[CaseCard]:
        """向量检索：返回相关案例片段（含混合检索路）"""
```

所有返回值按 Schema Contract 携带 `source / tier / confidence / version / empty_reason` 字段。增加**近义词语义映射**：用户输入"养老院"自动关联 `healthcare_facility`，避免术语不统一导致检索失败。

**K-002：新增 `type_mode_matrix` 单一事实源（逻辑单源 + 物理 3 文件）**

## 八.6 可观测性设计

> 来源：建议 B 风险 4 的"解法提前"（原本 Phase 5，按建议前移到 Phase 1 基线）

**告警阈值（Phase 2 起生效）**：

| 指标 | 告警条件 | 观察窗口 | 处置建议 |
|------|---------|---------|---------|
| Registry 错误率 | > 1% | 5 分钟 | 立即检查 YAML 文件完整性；触发 fallback 降级 |

### 13.5 三处独立风险

**风险 1：K-002-a 三张兼容表原子迁移**  
`LEGACY_TYPE_ALIASES / PARENT_TYPE_MAP / SPECIALTY_TAG_MAP` 必须整体一次迁移，残留任何一张都会造成新旧两套解析路径并存。**策略**：迁移前先跑行为快照测试，固化当前 40+ 类型的解析结果，迁移后回归对比。

**风险 2：mode_signatures.yaml 热更新决策**  
`lru_cache` 缓存 YAML 结果。若运维需要不重启新增模式，需要 cache invalidation 接口。**策略**：K-002-b 阶段明确写 ADR：是否支持热加载；若不支持，文档注明需重启，不留隐性假设。

**风险 3：`query_rules()` 空值 fallback 合同**  
YAML 缺失或查询 miss 时，若调用方无 fallback 会用空值走逻辑造成静默错误。**策略**：K-000 Schema Contract 中明确 `empty_reason` 的全部合法值；K-001 实现规定空值返回必附 `empty_reason`；所有调用方基于 `empty_reason` 退化到当前硬编码行为（而非报错）。

### 14.2 管理后台模块设计

> 实现入口：挂载到现有 FastAPI（`api/admin_` 路由族），不另起服务。Phase 3 后具备完整后台能力。

**五个模块职责：**

| 模块 | 功能 | 最低可用版本 |
|------|------|------------|
| **知识总览** | 当前版本号、发布状态、命中率、空返回率趋势、候选积压数 | Phase 2 |
| **候选审核台** | 候选列表/详情/比对/审批/驳回/批量操作；展示 `tier / confidence / source` | Phase 3 |
| **发布中心** | 预检校验、灰度发布（按节点子集测试）、全量发布、一键回滚 | Phase 3 |
| **监控中心** | 各接口 P95/错误率/空返回率实时图；告警事件列表 | Phase 2 |
| **审计中心** | 谁在何时改了什么；关联版本与操作工单；可检索 | Phase 3 |

### 14.3 RBAC 角色权限

| 角色 | 描述 | 允许操作 | 禁止操作 |
|------|------|---------|---------|
| **Admin** | 架构负责人 | 发布/回滚/权限管理/全部查看 | — |
| **Reviewer** | 知识评审员 | 查看候选、审批/驳回候选 | 直接发布到生产 |
| **Operator** | 运维人员 | 查看监控、确认告警、查看审计 | 修改知识内容 |
| **Reader** | 只读观察者 | 查看总览和监控 | 任何写操作 |

> 当前单人开发阶段：Admin 身份执行所有操作；RBAC 框架在 Phase 3 搭好，权限控制代码预留，不强制执行，待多人协作时开启。

### 14.4 发布 SOP

```
① 候选通过 Reviewer 审核 → 进入待发布集
② 执行契约校验（所有接口签名符合 K-000 Schema Contract）
③ 执行 YAML 语法校验（ruamel.yaml 严格模式）
④ 预发环境回归（5 个关键节点：RA/radar/feasibility/questionnaire_summary/execution）
⑤ 生产发布 + 统一 reload（lru_cache 清除 + registry 实例重建）
⑥ 发布后 30 分钟重点观测（错误率 / 空返回率 / P95）
⑦ 如任一告警触发 → 一键回滚（git revert YAML + reload）
```

### 14.5 运营 SOP 框架

| 周期 | 关键检查项 |
|------|----------|
| **每日** | 处理候选队列新增条目；检查告警事件；确认空返回异常是否有已知原因 |
| **每周** | 校验类型口径一致性（`type_mode_matrix` vs `_type_registry`）；清理标记为 `deprecated` 的条目；抽检 L3 向量命中质量（随机 5 条） |
| **每月** | 版本发布 + 回归验证；知识变更复盘（晋升了哪些、驳回了哪些，原因是否记录）；告警阈值是否需要调整 |

### 14.6 维护边界（正式不变量，与 CLAUDE.md 冻结并列）

以下约束在底盘运行期间**不得破坏**，违反须在 CLAUDE.md 记录变更原因：

```
INV-B1: 禁止在工作流运行时直接写入生产 YAML（L1/L2）
INV-B2: L3 自动摄入（ingest_brief）允许直通；L1/L2 变更必须经"审核→发布"流程
INV-B3: L4 项目记忆与行业知识（L1/L2/L3）物理存储隔离，禁止跨层写入
INV-B4: KnowledgeRegistry 返回值必须包含 source/tier/confidence/version/empty_reason 五字段
INV-B5: empty_reason 非空时，调用方退化到硬编码 fallback，不得使用空值走业务逻辑
INV-B6: 发布回滚必须在 30 分钟内可完成（YAML git revert + reload < 5 分钟操作）
```
