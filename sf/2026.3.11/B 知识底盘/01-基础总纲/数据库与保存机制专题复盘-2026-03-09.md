# 数据库与保存机制专题复盘（2026-03-09）

> **导航提示：** 建议先读 [README](README.md) 与 [01-专业知识底盘总纲与实施路线](01-专业知识底盘总纲与实施路线-2026-03-11.md)；本文对应本目录的 [02-数据库与保存机制与长期记忆](02-数据库与保存机制与长期记忆-2026-03-11.md) 实现层入口。

> **一句话结论：** 当前系统采用“Redis 热数据 + LangGraph checkpoint + SQL 归档（PostgreSQL 优先，SQLite 兼容回退）”三层持久化架构，并通过归档前 checkpoint→Redis 同步保障数据完整性。本文以**代码事实为第一证据源**，并对外部参考建议做交叉验证后形成执行路径。

## 一、当前架构总览

### 1) 热数据层：在线会话（Redis）

- 组件：`RedisSessionManager`
- 文件：`intelligent_project_analyzer/services/redis_session_manager.py`
- 角色：
  - 承载运行中会话状态（主读写）
  - 分布式锁保护并发更新
  - 会话 TTL 管理（默认 7 天）
  - 状态缓存与用户索引维护
- 降级：Redis 不可用时可回退内存模式（开发兜底）

### 2) 过程状态层：工作流 checkpoint（LangGraph）

- 组件：`checkpointer`
- 文件：`intelligent_project_analyzer/workflow/main_workflow.py`
- 角色：
  - 持久化工作流节点推进状态
  - 支持中断恢复/重启续跑
- 后端策略：
  - 优先 Postgres（可配置严格模式）
  - SQLite 为兼容回退路径（可通过开关禁止）
  - 回退时默认文件：`data/checkpoints/workflow.db`

### 3) 长期归档层：历史会话（SQL）

- 组件：`SessionArchiveManager`
- 文件：`intelligent_project_analyzer/services/session_archive_manager.py`
- 角色：
  - 永久保存归档会话（`archived_sessions`）
  - 永久保存搜索归档（`archived_search_sessions`）
  - 提供分页、过滤、统计、元数据管理、冷存储导出
- 后端支持：SQLite / PostgreSQL
 - 后端支持：PostgreSQL 优先；SQLite 兼容（可禁用）

### 4) 旁路与辅助层（不并入主会话真源）

- 文件系统：报告、上传、冷存储 JSON、日志等
- 专项数据系统：外部爬虫库、向量检索库（如 Milvus / pgvector）
- 说明：以上属于扩展能力或专项链路，不应与“主会话存储真源”混淆

## 二、关键数据流（当前生效版本）

```text
用户请求
  → RedisSessionManager（在线会话）
  → Workflow 执行 + checkpoint 落盘（LangGraph）
  → 归档触发时先做 sync_checkpoint_to_redis(session_id)
  → SessionArchiveManager.archive_session(...)
  → 写入 archived_sessions / archived_search_sessions（长期保存）
```

### 归档完整性保障（关键）

- 同步函数：`sync_checkpoint_to_redis()`
- 文件：`intelligent_project_analyzer/api/deps.py`
- 目的：将 checkpoint 中关键字段回填到 Redis，防止“只归档到基础元数据、丢失过程字段”。

## 三、配置与开关（影响持久化语义）

### 核心配置

- `REDIS_URL`
- `DATABASE_URL`
- `ARCHIVE_DATABASE_URL`
- `CHECKPOINT_BACKEND`
- `CHECKPOINT_DATABASE_URL`

### 扩展/旁路配置（按需）

- `EXTERNAL_DB_URL`（外部数据系统）
- `MILVUS_HOST` / `MILVUS_PORT`（向量检索）

### 风险闸门开关

- `CHECKPOINT_STRICT_POSTGRES`
  - 开启后，checkpoint 必须成功使用 Postgres，否则启动失败。
- `DISABLE_SQLITE_CHECKPOINT_FALLBACK`
  - 开启后，禁止 checkpoint 回退 SQLite。
- `DISABLE_SQLITE_ARCHIVE_BACKEND`
  - 开启后，禁止归档层使用 SQLite（要求 PG）。

### 当前环境口径（本仓库 `.env`）

- `DATABASE_URL` 当前配置为 PostgreSQL
- `CHECKPOINT_BACKEND=postgres`
- `CHECKPOINT_STRICT_POSTGRES=false`（表示 PG 失败时仍允许回退）
- `.env` 中未显式设置 `DISABLE_SQLITE_CHECKPOINT_FALLBACK` / `DISABLE_SQLITE_ARCHIVE_BACKEND`

> 结论：**当前环境主用 PostgreSQL，但代码层仍保留 SQLite 回退能力**，因此“SQLite 已废除”这一说法不成立。

## 四、与“专业底盘 L4 记忆层”的关系

L4 当前表述为：`LangGraph state + archived_sessions.db`。

复盘后的精确口径建议：

- **运行记忆（短期）**：Redis 会话态 + checkpoint
- **历史记忆（长期）**：`archived_sessions`（SQL）
- **检索/学习用途**：历史会话可作为后续学习与回放的数据来源

即：L4 不是单点数据库，而是“会话态 + 过程态 + 历史态”的组合体系。

## 八、验证矩阵（盘点验收，不是功能改造）

1. 活跃会话创建后，Redis 可见核心字段且存在 TTL

7. 回退策略行为符合开关语义：
  - Redis 不可用 → 内存兜底
  - Checkpoint PG 不可用 → SQLite 回退（若未禁）
  - Archive 禁 SQLite 时应快速失败并给出可诊断错误
