# 空间类型知识底盘系统框架总览

> 日期：2026-03-12  
> 适用范围：`intelligent_project_analyzer` 中与 **项目类型 / 空间类型 / 空间分类 / 类型化本体注入 / 激活图谱 / 专家扩展** 相关的当前实现。  
> 文档目的：把“空间类型知识底盘”从零散引用中单独立出来，说明它到底有哪些层、覆盖哪些类型、如何参与推理，以及它为什么是需求分析系统的关键入口之一。

---

## 1. 先给结论

空间类型知识底盘，**不是一个类型表**，而是一套多层知识组织系统。

它至少同时承担六件事：

1. 定义系统里到底有哪些项目/空间类型；
2. 把细粒度类型归并成更宽的推理桶；
3. 进一步识别专项细分标签；
4. 按类型注入不同的本体分析框架；
5. 按类型调整本体议题的激活重心与分析深度；
6. 给不同专家角色挂接不同的强化视角。

因此，空间类型底盘真正做的不是：

- “给项目打个标签”

而是：

- “决定系统接下来该用哪一套知识看这个项目”

这也是它在整个专业知识底盘中的特殊地位：

> **它是 KnowledgeRegistry 进入类型化知识的总入口之一。**

## 2. 为什么要单独立这份文档

此前在 `04-空间分类系统与类型清单-2026-03-11.md` 与 `SPACE_CLASSIFICATION_SYSTEM_INVENTORY-空间分类系统清单.md` 中，已经能看到“空间分类是一条链”。但对读者来说，仍然容易出现两个误解：

1. 误以为空间类型层只有几类简单分类；
2. 误以为空间类型的作用只是影响路由，而不是影响后续分析世界观。

本总览文档的目的，就是把这层从“链路说明”升级成“库级说明书”。

## 3. 当前实现中的真实落点

### 3.1 当前单一权威注册源

当前项目里，空间类型/项目类型的单一权威注册，已经主要收敛在：

- `intelligent_project_analyzer/services/project_type_detector.py`

其核心对象包括：

- `PROJECT_TYPE_REGISTRY`
- `LEGACY_TYPE_ALIASES`
- `PARENT_TYPE_MAP`
- `SPECIALTY_TAG_MAP`
- `ProjectTypeDetector`

这意味着：

- 类型定义不是散落在多个文件里；
- 类型标签、优先级、关键词、父类桶和专项标签，已经有统一入口；
- 下游模块原则上应从这里读取，而不是自行维护一份新的类型字典。

### 3.2 与底盘文档的关系

底盘文档 `04-空间分类系统与类型清单-2026-03-11.md` 仍然是重要入口，但更偏“数据盘点与调用链说明”；
而当前代码实现，已经进一步把类型注册源收束到了 `project_type_detector.py`。

因此，理解这层时应同时持有两个视角：

- **文档视角**：空间分类是一条链；
- **代码视角**：链的起点与真实权威注册表在 `project_type_detector.py`。

## 4. 空间类型知识底盘的六层结构

### 4.1 第一层：类型注册层（Type Registry）

作用：定义系统里“到底有哪些空间/项目类型”。

当前核心载体：

- `PROJECT_TYPE_REGISTRY`

注册表中每个类型条目通常至少包含：

- `name`：中文名
- `name_en`：英文检索上下文
- `keywords`：主关键词
- `secondary_keywords`：次要关键词
- `priority`：优先级
- `min_secondary_hits`：无主关键词命中时的次关键词阈值
- `include_in_prompt`：是否进入提示词可选类型列表

这说明注册表不是一个静态标签表，而是一个兼具：

- 分类定义
- 检测支持
- Prompt 注入控制
- 优先级调度支持

的多用途数据源。

### 4.2 第二层：父类归桶层（Parent Bucket）

作用：把细粒度类型收束成更宽的推理桶。

当前核心载体：

- `PARENT_TYPE_MAP`

典型父类桶包括：

- `residential`
- `hospitality`
- `office`
- `retail`
- `leisure`
- `education`
- `healthcare`
- `public`
- `industrial`
- `urban_renewal`
- `outdoor`
- `special`

这层的意义是：

- 当系统需要粗粒度理解时，不必每次都在几十个细分类之间直接比较；
- 它为后续的维度选择、任务完备度分析、问卷追问和路由压缩提供了中间抽象层。

### 4.3 第三层：专项标签层（Specialty Tag）

作用：在细分类型命中后，再进一步给出专项标签。

当前核心载体：

- `SPECIALTY_TAG_MAP`

示例：

- 餐饮：`buffet` `bbq` `hotpot` `cafe`
- 住宅：`villa` `apartment` `duplex` `loft`
- 酒店：`boutique_hotel` `b_and_b` `treehouse`
- 办公：`co_working` `incubator` `makerspace`
- 娱乐：`ktv` `escape_room` `mahjong_room`
- 医疗：`dental` `tcm` `elderly_care` `age_friendly`

这层的意义是：

- 父类桶解决“看问题的大镜头”；
- 专项标签解决“这个类型内部到底是哪一支”。

### 4.4 第四层：类型化本体框架层（Ontology Frameworks）

作用：决定不同类型项目该从哪些维度分析。

当前核心载体：

- `intelligent_project_analyzer/knowledge_base/ontology.yaml`
- `ontology_frameworks`

典型框架包括：

- `personal_residential`
- `hybrid_residential_commercial`
- `commercial_enterprise`
- `public_cultural`
- `healthcare_wellness`
- `commercial_office`
- `commercial_hospitality`
- `industrial_conversion`
- `educational_facility`
- `transportation_civic`
- `rural_regeneration_urban_renewal`
- `religious_spiritual`
- `landscape_outdoor`
- `commercial_retail`

这层回答的问题不再是“它是什么”，而是：

- “这一类项目通常应该分析哪些核心维度？”

### 4.5 第五层：激活图谱层（Activation Profiles）

作用：决定某一类项目应优先激活哪些本体议题、分析到多深、最典型的张力是什么。

当前核心载体：

- `ontology.yaml::activation_profiles`

每个类型通常包含：

- `elevated_topics`
- `typical_depth`
- `guidance`
- `key_tensions`

例如：

- `commercial_hospitality` 偏重 `E3 / E4 / E5`
- `commercial_office` 偏重 `E1 / E2 / E8`
- `healthcare_wellness` 偏重 `E2 / E3 / E8`
- `commercial_retail` 偏重 `E1 / E3 / E9`

这层的意义在于：

- 同样都是空间，不同类型的“核心问题”其实完全不同；
- 激活图谱在提示系统：**不要用同一套眼镜看所有项目**。

### 4.6 第六层：专家扩展层（Expert Extensions）

作用：在通用类型框架之上，再按专家角色注入专门视角。

当前核心载体：

- `ontology.yaml::expert_extensions`

典型角色包括：

- `design_director`
- `narrative_expert`
- `design_researcher`
- `technology_consultant`
- `scenario_expert`
- `chief_engineer`
- `functional_optimization`
- `capital_strategy_expert`
- `technology_integration_expert`
- `operational_analyst`
- `lighting_engineer`
- `sustainability_expert`
- `emotional_insight_expert`
- `organizational_psychologist`

这意味着底盘真正输出的不是单纯“类型信息”，而是：

> **类型上下文 × 专家上下文 的组合知识包**

## 6. 空间类型底盘与本体论基础的关系

`ontology.yaml` 中不仅有类型化框架，还有更底层的本体论议题：

- `E1 空间体量与比例`
- `E2 身体体验与动觉`
- `E3 光作为设计材料`
- `E4 材料物性与时间性`
- `E5 时间与时序动态`
- `E8 技术系统作为设计驱动`
- `E9 经济伦理与价值分配`

空间类型底盘的关键作用，不是替代这些本体议题，而是：

- 决定**哪一类项目应该优先看哪些议题**；
- 决定这些议题应该分析到什么深度；
- 决定系统在什么地方必须直面张力，而不是泛泛展开。

也就是说：

- 本体论基础提供“可讨论的普遍问题”；
- 空间类型底盘提供“哪些问题在这个项目里最关键”。

## 7. 认知脚手架如何与空间类型层联动

`ontology.yaml` 中的 `cognitive_scaffolding` 定义了：

- `L0_factual`
- `L1_functional`
- `L2_experiential`
- `L3_interpretive`
- `L4_dialectical`

空间类型底盘会与这套脚手架联动，决定：

- 住宅是否需要深入到生活方式张力；
- 医疗是否必须覆盖从硬指标到伦理张力的全深度；
- 酒店是否应从体验层推进到意义层与张力层；
- 商业零售是否需在效率与品牌叙事之间建立桥梁。

因此，空间类型层不仅决定“看什么”，还在决定“看到多深”。

## 8. 当前运行中的典型数据流

空间类型底盘在运行时大致遵循如下链路：

```text
用户输入
  → ProjectTypeDetector
  → project_type / parent_type / specialty_tag
  → requirements_analyst / requirements_nodes 写入状态
  → ontology_loader.get_layered_ontology(project_type, expert_role)
  → activation_profiles / expert_extensions 注入
  → questionnaire / review / execution / deliverable 层消费
```

如果展开理解，就是：

1. 先检测它是什么类型；
2. 再决定它属于哪个更宽的业态桶；
3. 再判断是否命中了专项细分；
4. 再注入对应的本体框架；
5. 再按专家角色补充特殊分析视角；
6. 最终影响需求分析、问卷、执行层和交付命名。

## 9. 案例映射示范：七里坪山地民宿 × HAY

为了让这套库不只停在抽象层，以下用一个案例演示它如何工作。

### 9.1 命中链

| 层级 | 案例命中 |
|---|---|
| `project_type` | `commercial_hospitality` |
| 中文标签 | `酒店民宿/度假` |
| `parent_type` | `hospitality` |
| `specialty_tag` 候选 | `b_and_b` / `boutique_hotel` |
| 本体框架 | `commercial_hospitality` |
| 激活重心 | `E3 / E4 / E5` |

### 9.2 它会如何改变判断重点

命中 `commercial_hospitality` 后，系统更容易优先关注：

- 宾客旅程
- 公共空间社交动力学
- 在地性表达
- 季节性与时间性
- 标准化与个性化平衡

因此案例里的下列判断就不是偶然：

- 强调山地光感与材料温度；
- 强调“低压社交 + 可退出停留”；
- 强调品牌识别不能靠强陈列；
- 强调旺季 / 淡季、公区 / 私区、品牌 / 场地之间的张力。

### 9.3 如果判错类型会怎样

若误判为其他类型，则结果会明显偏移：

| 若误判类型 | 典型偏差 |
|---|---|
| `personal_residential` | 过度转向家庭生活和户型收纳 |
| `brand_experience` | 过度转向品牌展示与视觉识别 |
| `commercial_retail` | 过度转向浏览动线与转化率 |
| `landscape_outdoor` | 过度转向生态路径与室外微气候 |

这反过来也说明：

> 空间类型底盘不是后验标签，而是前置方向系统。

## 10. 这个底盘已经很丰满，但还不算“最终形态”

从当前状态看，这套空间类型底盘已经具有相当强的系统性：

- 有权威注册表；
- 有别名兼容；
- 有父类桶；
- 有专项标签；
- 有类型化本体框架；
- 有激活图谱；
- 有认知脚手架；
- 有专家扩展。

但如果从“超强知识底盘”的标准看，仍然有几个可以继续补的方向：

### 10.1 类型样例库

当前库更强于“结构定义”，还可以继续补：

- 每类项目的正反例样本
- 典型失败模式
- 类型边界模糊时的判别规则样例

### 10.2 类型 × 任务 × 交付矩阵

当前已有类型到维度的映射，但还可以更进一步：

- 某类型最常见的任务集合
- 某类型最常见的交付对象
- 某类型最典型的冻结对象模板

### 10.3 类型 × 武器激活建议

现在武器系统和类型系统是可联动但未完全显性绑定的，后续可以加强为：

- 什么类型优先用哪些武器
- 哪些武器只在某些类型下高频触发
- 哪些武器在某些类型下应谨慎触发

### 10.4 类型边界冲突处理手册

例如：

- 品牌民宿 vs 精品酒店
- 社区公共 vs 文化展陈
- 医疗康养 vs 度假疗愈
- 乡建民宿 vs 文旅综合体

这些边界案例若沉淀成专门手册，会让类型底盘更强。

## 12. 最后的判断

可以明确说：

- 空间类型知识底盘**已经不是几句话的背景层**；

> **空间类型底盘是需求分析系统最核心的知识组织入口之一，它决定系统该用哪套世界观理解项目，而不只是决定项目被叫什么名字。**
