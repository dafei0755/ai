# 反向模拟：民宿空间类型知识底盘示范（宽口径增强版 · 2026-03-12）

> 目的：不是描述“当前系统已经实现到哪里”，而是从需求分析视角**反向模拟**——如果系统真的要把“民宿”做成一个成熟、立体、可扩展、可经营、可回写的知识底盘，它应该长成什么样。  
> 适用：需求分析阶段的 `S1-S4` 主流程、武器调用、TriggerIntent 判断、任务书冻结与后评估回写。  
> 结论先行：民宿知识底盘不能只停留在“山地 / 滨海 / 森林”这类场景标签，也不能只停留在“风格 / 人群 / 材料”这类软描述，而必须升级为：**主类型 + 多轴变量 + 组合规则 + 经营验证 + 用户反馈 + 冻结模板 + 协议映射**。

---

## 1. 为什么说“以前的太窄了”

如果一份民宿知识底盘只回答：

- 这是民宿；
- 它是山地民宿 / 滨海民宿；
- 它适合某种风格；

那它依然是“偏窄”的。

因为真正参与需求分析的知识底盘，还必须继续回答：

- 这是**哪一种经营模型**下的民宿？
- 这是**哪一种客群结构**下的民宿？
- 这是**哪一种价格带与品牌模式**下的民宿？
- 这是**哪一种卖点兑现逻辑**下的民宿？
- 这是**哪一种投入/维护/回本压力**下的民宿？
- 这是**哪一种口碑风险与评价结构**下的民宿？
- 它最终应该冻结哪些对象，而不是泛泛聊概念？

所以，真正成熟的民宿底盘，不能只是“空间类型底盘”，而应该是：

> **空间类型底盘 + 产品定义底盘 + 经营约束底盘 + 证据反馈底盘**

一句话说透：

> **系统不是要识别“像不像民宿”，而是要识别“到底是哪一种民宿的人、地、产品、材料、品牌、盈利与口碑组合”。**

---

## 2. 宽口径版本的整体结构

如果从系统设计角度反推，一个成熟的民宿知识底盘，建议至少由八层构成。

### 2.1 主类型层（Core Type Layer）

回答：

- 这是 `commercial_hospitality` 里的哪一支？
- 是 `homestay / boutique_stay / retreat_lodge / resort_stay / glamping_stay` 的哪种基本盘？

这一层负责：

- 与住宅、办公、零售、展馆、教育等主类型严格区分；
- 稳定进入正确的需求分析主通道；
- 保持类型树简洁，不在这里过度碎片化。

### 2.2 场地语境层（Site Context Layer）

回答：

- 民宿长在什么自然环境里？
- 它面对什么地貌、气候、到达方式和维护压力？

建议最少包含：

- `landscape_archetype`：山地 / 滨海 / 湖畔 / 森林 / 田园 / 高原 / 寒地 / 峡谷
- `cultural_geography`：江南 / 岭南 / 西南山地民族 / 塞北 / 中原 / 滨海渔业 / 高原藏地
- `climate_maintenance_profile`：防潮、防霉、耐盐雾、防风、防晒、保温、融雪、排湿等
- `site_constraints`：停车受限、坡地到达、季节封路、落差大、转运远等

这一层决定：

- 借景方式；
- 室内外过渡方式；
- 材料耐候逻辑；
- 夜间策略；
- 基础运维成本。

### 2.3 文化-生活方式层（Cultural Lifestyle Layer）

回答：

- 它不是抽象地处于某个地理点，而是处于哪一种生活世界里？
- 是什么地方秩序、什么手工传统、什么日常节奏在支撑它？

建议包含：

- `vernacular_reference`
- `craft_reference`
- `local_lifestyle_reference`
- `hospitality_ritual_reference`

这层的价值是防止系统犯两个常见错误：

- 把所有民宿做成统一的“文艺白盒子”；
- 把“在地性”误解成表皮符号堆砌。

### 2.4 产品体验层（Product Experience Layer）

回答：

- 这家民宿卖的到底是什么？
- 用户为什么愿意从“普通住一晚”升级为“愿意多花钱、愿意分享、愿意复购”？

建议包含：

- `experience_core`：观景、静养、疗愈、温泉、在地生活、社交、手作、饮食、亲子、工作旅居
- `stay_mode`：周末短逃离、慢旅行、家庭假期、朋友聚会、疗愈静修、workation
- `social_intensity_profile`：私密安静、低压共享、社区友好、活动型
- `signature_selling_points`：看星星、负氧离子、山雾、海景日出、茶冥想、温泉恢复、农食体验
- `personalization_depth`：标准化、轻个性化、主理人策展式、深定制、共创型

这一层决定：

- 公区到底应该热闹还是克制；
- 客房是“住”还是“停留”；
- 卖点是否会变成真正可感知的体验；
- 是否值得为某种差异化投入额外成本。

### 2.5 客群与社交层（Guest and Social Layer）

回答：

- 谁在为它付钱？
- 谁会喜欢它？
- 谁之间会产生冲突？

建议包含：

- `guest_segment_profile`
- `guest_conflict_profile`
- `social_pressure_threshold`
- `family_friendliness`
- `pet_friendliness`
- `accessibility_expectation`

这层非常关键，因为同样叫民宿，可能分别对应：

- 年轻情侣的静谧周末；
- 亲子家庭的高频活动；
- 朋友微聚会；
- 疗愈与独处人群；
- 中老年慢旅行；
- 内容创作者 / workation 用户。

只要客群画像错了，后面的空间策略、服务策略和价格策略都会跟着跑偏。

### 2.6 运营与服务层（Operation and Service Layer）

回答：

- 这家民宿是怎么活的？
- 它能否被持续经营，而不是“开业即高光，半年后塌房”？

建议包含：

- `operation_model`：主理人驻场、家族经营、专业团队、精品连锁、本地共营
- `service_visibility`：隐形服务、轻介入、主理人互动、仪式化服务
- `seasonality_profile`：周末峰值、夏季峰值、冬季峰值、全年均衡、强淡季
- `maintenance_capacity`：维护承接能力
- `staffing_intensity`
- `cleaning_turnover_pressure`
- `night_operation_pressure`
- `guest_journey_profile`：到达 / 入住 / 客房 / 公区 / 夜间 / 离店

这一层是很多项目最容易被忽视的一层，因为很多方案不是美学问题，而是：

- 高峰接不住；
- 淡季养不起；
- 主理人不在就崩；
- 房型太异质，保洁与维护成本爆炸；
- 卖点强，但服务兑现跟不上。

### 2.7 品牌与商业层（Brand and Business Layer）

回答：

- 这家民宿为什么存在？
- 它是为了赚钱、做品牌、带动景区，还是承载主理人的生活方式表达？

建议包含：

- `price_tier_profile`
- `brand_mode_profile`
- `brand_expression_level`
- `strategic_business_intent`
- `revenue_structure`
- `capex_profile`
- `opex_profile`
- `profitability_model`
- `payback_expectation`

这层的作用是把“浪漫叙事”拉回“经营现实”。

因为系统不仅要问：

- 好不好看；

还要问：

- 值不值得投；
- 撑不撑得住；
- 卖点能不能转成真实溢价；
- 价格带和设计强度是否匹配。

### 2.8 证据反馈层（Evidence and Feedback Layer）

回答：

- 现实世界里，这种民宿是怎么成功、怎么失败、怎么被评价的？

建议包含：

- `failure_case_patterns`
- `success_experience_patterns`
- `review_signal_clusters`
- `experience_pain_points`
- `experience_delight_points`
- `selling_point_validation`

这一层会把底盘从“专家想象”推进到“真实市场知识”。

没有这一层，系统就容易停留在：

- 讲得很懂；
- 看起来很美；
- 但不知道为什么用户会给差评。

## 3. 不是“五种民宿”，而是一组“原型簇”

以前窄，很大一个原因是容易把“山地 / 滨海 / 江南 / 塞北 / 森林”当成全部。  
实际上它们更适合作为**原型簇入口**，而不是最终分类终点。

建议把民宿知识底盘拆成以下九组原型簇：

### 3.1 自然景观原型簇

- 山地民宿
- 滨海民宿
- 湖畔民宿
- 森林民宿
- 田园民宿
- 高原民宿
- 雪地/寒地民宿
- 峡谷/荒野民宿

### 3.2 聚落与文化原型簇

- 江南水乡民宿
- 岭南湿热民宿
- 西南山地民族民宿
- 塞北边地民宿
- 中原乡村民宿
- 渔村更新型民宿
- 古镇更新型民宿

### 3.3 产品体验原型簇

- 观景型民宿
- 疗愈静修型民宿
- 温泉康养型民宿
- 在地生活沉浸型民宿
- 亲子假期型民宿
- 社交活动型民宿
- 手作课程型民宿
- workation 型民宿

### 3.4 建筑载体原型簇

- 老宅改造型
- 村落组团型
- 新建度假组团型
- 石屋更新型
- 树屋/架空式型
- 院落复合型
- 模块化 / glamping 型

### 3.5 品牌模式原型簇

- 主理人独立品牌
- 精品独立品牌
- 软品牌集合
- 区域精品连锁
- 文旅目的地子品牌
- 弱品牌在地住留

### 3.6 价格与交付原型簇

- 经济型
- 中端型
- 中高端型
- 精品高端型
- 奢享目的地型

### 3.7 社交关系原型簇

- 强私密避世型
- 低压共享型
- 社区友好型
- 活动聚会型

### 3.8 经营目标原型簇

- 盈利优先型
- 情怀表达型
- 品牌展示型
- 目的地配套型
- 资产盘活型
- 社区振兴型

### 3.9 反馈风控原型簇

- 高维护风险型
- 高季节波动型
- 高口碑脆弱型
- 高卖点兑现压力型
- 高社交冲突型

这九组原型簇叠加后，系统才真正具备“宽口径识别能力”。

- 同时支撑识别、推理、冻结与回写；
- 同时支持“山地疗愈民宿”和“滨海亲子民宿”这类复合对象。

## 5. 组合规则：系统不是贴标签，而是要会判断

光有变量还不够，必须有组合规则。  
否则系统只是“知道很多名词”，并不真的“懂民宿”。

### 5.1 增强型组合规则示例

#### 规则 A：疗愈 × 活动冲突
- 条件：
  - `experience_core` 包含 `healing_retreat`
  - `social_intensity_profile = community_friendly` 或 `event_active`
- 判断：
  - 疗愈叙事与高社交噪声可能冲突
- 输出：
  - 强制进入“分区 / 分时 / 夜间静音策略”核查

#### 规则 B：高个性化 × 中低价格冲突
- 条件：
  - `personalization_depth = deep_customized`
  - `price_tier_profile` 低于 `premium_boutique`
- 判断：
  - 个性化维护与培训成本可能无法覆盖
- 输出：
  - S3 要求补充“成本可承接性说明”

#### 规则 C：滨海 × 高反光材料风险
- 条件：
  - `landscape_archetype = coastal`
  - `material_palette_profile` 偏 `metal_glass_refined`
- 判断：
  - 眩光、腐蚀、清洁成本上升
- 输出：
  - 抬高 `anti_corrosion / solar_protection / cleaning_frequency` 权重

#### 规则 D：山地 × 雨雾 × 弱到达体验风险
- 条件：
  - `landscape_archetype = mountain`
  - `climate_maintenance_profile` 包含 `humid_mildew_risk` 或 `heavy_rainfall`
  - `site_constraints` 包含 `steep_arrival_path`
- 判断：
  - 到达体验和维护体验都容易成为差评核心
- 输出：
  - 强制检查“到达减压设计 + 防潮维护边界 + 夜间回房安全”

#### 规则 E：亲子 × 疗愈双客群冲突
- 条件：
  - `guest_segment_profile` 同时包含 `parent_child_family` 与 `healing_retreat_guest`
- 判断：
  - 客群节奏冲突高
- 输出：
  - 要么做分栋分区，要么做时段运营，不可直接混住

#### 规则 F：品牌连锁 × 在地匿名冲突
- 条件：
  - `brand_mode_profile = chain_boutique_brand`
  - `brand_expression_level = anonymous_local`
- 判断：
  - 品牌一致性与地方弱表达存在张力
- 输出：
  - 需要定义“哪些标准统一、哪些表达在地化”

## 6. 五类常见民宿，只是入口示范，不是全部世界

下面仍以五类原型为例，但每类都从“空间 + 产品 + 经营 + 反馈”四个维度来写，避免只剩类型标签。

### 6.1 山地民宿

#### 典型变量组合
- `landscape_archetype = mountain`
- `climate_maintenance_profile = humid_mildew_risk + heavy_rainfall`
- `experience_core = viewing_landscape + silence_rest + healing_retreat`
- `guest_segment_profile = urban_couple + healing_retreat_guest`
- `social_intensity_profile = low_pressure_shared`

#### 设计重点
- 坡地进入与情绪切换
- 借景层级与停留节点
- 雨雾环境下的室内外过渡
- 夜间照明克制与安全平衡
- 防潮、防霉、木石维护边界

#### 经营重点
- 强淡季波动管理
- 山路到达的服务预案
- 房晚溢价是否足以覆盖维护成本

#### 高频口碑信号
- 好评：安静、景观真实、空气好、适合放空
- 差评：潮、冷、路难走、餐食弱、隔音差

### 6.2 滨海民宿

#### 典型变量组合
- `landscape_archetype = coastal`
- `climate_maintenance_profile = salt_fog_corrosion_risk + strong_solar_exposure`
- `experience_core = viewing_landscape + community_social`
- `guest_segment_profile = young_social_group + parent_child_family`
- `social_intensity_profile = community_friendly`

#### 设计重点
- 观海界面与日照控制
- 防风、防晒、防腐蚀
- 湿区、沙地、户外回收动线
- 高峰时段公区与客房干扰控制

#### 经营重点
- 暑期与节假日峰值承压
- 清洁频率与材料寿命管理
- 景观承诺和真实体验一致性

#### 高频口碑信号
- 好评：看海、日落、拍照、孩子放电
- 差评：晒、脏、旧、吵、旺季拥挤

### 6.3 江南民宿

#### 典型变量组合
- `cultural_geography = jiangnan`
- `landscape_archetype = riverside / lakeside`
- `experience_core = immersive_local_life + food_culture + silence_rest`
- `brand_expression_level = anonymous_local / soft_branded`

#### 设计重点
- 灰空间与细密日常尺度
- 湿润漫反射光感
- 材料与手工感控制
- 在地生活线索而非符号仿古

#### 经营重点
- 日常体验而不是一次性打卡
- 低刺激高复购的内容组织
- 冬季体感与潮湿舒适度维护

#### 高频口碑信号
- 好评：细腻、安静、在地感、茶食体验
- 差评：潮、冷、隔音弱、假古董感强

### 6.4 塞北民宿

#### 典型变量组合
- `cultural_geography = northern_frontier`
- `climate_maintenance_profile = dry_cold_heat_loss + snow_load_winterized`
- `experience_core = silence_rest + hot_spring_wellness`
- `seasonality_profile = winter_peak`

#### 设计重点
- 围合与防风
- 热源与入口缓冲组织
- 冬季动线、保暖、雪后维护
- 室内温暖反差体验营造

#### 经营重点
- 冬季高能耗与回本测算
- 淡旺季人力配置差异
- 自驾到达服务与安全说明

#### 高频口碑信号
- 好评：暖、静、冬景强记忆点
- 差评：冷风冲击、干燥、交通不便、能耗痕迹明显

### 6.5 森林民宿

#### 典型变量组合
- `landscape_archetype = forest`
- `experience_core = healing_retreat + immersive_local_life + silence_rest`
- `social_intensity_profile = silent_private`
- `carrier_archetype = treehouse / dispersed_cluster`

#### 设计重点
- 林下视线过滤与隐匿感
- 分散式客房组织
- 夜间低干预照明
- 防潮、防火、防虫与静音机电

#### 经营重点
- 强疗愈承诺下的体验兑现
- 夜间运营边界
- 维护频率与自然环境保护平衡

#### 高频口碑信号
- 好评：安静、治愈、离自然近、睡得好
- 差评：霉味、虫、照明不足、夜间不安全感

## 7. 更进一步：从“类型”走向“经营结果”

以前偏窄，另一个原因是很多民宿底盘只讨论“长什么样”，却不讨论“活得怎么样”。  
真正能进入需求分析系统的底盘，必须回答四个经营结果问题。

### 7.1 投入结构

系统至少应知道：

- 重投入在哪里；
- 哪些投入是必要投入；
- 哪些投入是表达型投入；
- 哪些投入会形成维护负债。

例如：

- 山地高个性化木石体系 → 可能形成长期防潮维护成本；
- 滨海大面积玻璃与金属 → 可能形成清洁与腐蚀成本；
- 森林分散式树屋 → 可能形成运维与安全巡查成本。

### 7.2 盈利路径

系统至少应知道：

- 靠房晚溢价赚钱，还是靠复合内容赚钱？
- 靠高入住率，还是靠低入住率高客单？
- 卖点是拉新噱头，还是能构成稳定收入？

例如：

- `room_revenue + food_beverage` 是基础盘；
- `activity_workshop + membership` 更像品牌/社区型拓展；
- `hot_spring` 属于高投入但可拉高复购的内容。

### 7.3 体验兑现率

系统至少应知道：

- 用户是“真的感受到卖点”，还是“宣传比现场强”；
- 哪些体验节点是决胜点；
- 哪些体验节点一旦失败就会直接拉低评价。

例如：

- 卖“看星星”，结果夜间灯光太亮；
- 卖“疗愈静修”，结果机电噪声明显；
- 卖“在地生活”，结果动线像标准连锁酒店；
- 卖“海边放松”，结果暴晒、风大、清洁差。

### 7.4 口碑脆弱点

系统至少应知道：

- 这类民宿最容易被用户抱怨什么；
- 哪些差评是偶发，哪些差评代表底层定位问题；
- 哪些差评信号一出现，就应该触发 review 收紧。

例如：

- “景好但不想再来” 往往意味着体验承接失败；
- “拍照好看但住得不舒服” 往往意味着表达压倒使用；
- “服务很热情但还是累” 往往意味着动线与到达体验有问题。

## 8. 这套底盘如何进入需求分析主流程

这部分非常重要，因为底盘不是写给人看的百科，而是要参与 `S1-S4` 的。

### 8.1 在 S1：用于初判方向

底盘要帮助系统快速判断：

- 主类型是否明确；
- 场地语境是否已足够明确；
- 体验核心是否明确；
- 客群与价格带是否出现明显冲突；
- 是否已经可以进入一主两辅主线。

S1 输出应至少包含：

- `type_stack`
- `site_context_profile`
- `experience_core`
- `guest_segment_profile`
- `price_tier_profile`
- `strategic_business_intent`

### 8.2 在 S2：用于补问与重排

底盘要帮助系统知道：

- 还缺什么关键变量；
- 哪些冲突必须补问；
- 哪些 TriggerIntent 应该被点亮。

例如：

- 疗愈 + 亲子并存 → 触发分区/时段补问；
- 高端价格带 + 轻服务团队 → 触发服务兑现补问；
- 山地 + 雨雾 + 坡地到达 → 触发到达与夜间安全补问。

### 8.3 在 S3：用于武器选择与收敛

底盘要帮助系统决定：

- 哪些武器先上；
- 哪些风险必须先压住；
- 哪些矛盾要先冻结而不是继续发散。

典型输出：

- `key_tensions`
- `recommended_focus`
- `risk_flags`
- `preferred_weapons`
- `feasibility_gate_hints`

### 8.4 在 S4：用于冻结与回写

底盘要帮助系统明确：

- 任务书必须冻结哪些对象；
- 哪些条目要写进后评估回写字段；
- 哪些经验要回流到 L3。

典型冻结对象：

- 公区社交压力等级
- 卖点兑现路径
- 借景与停留层级
- 到达体验与夜间安全
- 材料与维护边界
- 价格带与服务承诺关系
- 口碑高风险项预防方案

## 9. 一个真正“宽”的示范，不只是列标签，而是给出判断模板

下面给一个增强版判断模板，展示系统如何用这套底盘做真正的需求分析。

### 示例：山地疗愈型精品民宿

#### 已识别变量
- `hospitality_subtype = retreat_lodge`
- `landscape_archetype = mountain`
- `cultural_geography = southwest_ethnic_highland`
- `experience_core = healing_retreat + viewing_landscape + silence_rest`
- `guest_segment_profile = urban_couple + healing_retreat_guest`
- `social_intensity_profile = low_pressure_shared`
- `price_tier_profile = premium_boutique`
- `strategic_business_intent = lifestyle_expression`

#### 系统自动判断的关键张力
- 观景开敞 vs 私密疗愈
- 个性化体验 vs 运营稳定性
- 弱社交氛围 vs 周末峰值承压
- 木石自然感 vs 防潮维护成本

#### 系统自动抬高的分析优先级
- 借景与停留层级
- 夜间照明与噪声控制
- 客房静音与睡眠体验
- 到达减压设计
- 防潮维护边界
- 餐食与疗愈叙事的一致性

#### 系统自动预警的风险
- 强淡季波动
- 雨雾季差评聚集
- 疗愈叙事过强但服务承接不足
- 卖点停留在文案层，现场缺乏真实感知路径

#### 系统建议冻结的对象
- 公区社交压力等级
- 夜间光环境上限
- 卖点兑现路径（观景 / 呼吸 / 静音 / 茶冥想）
- 维护可承接材料边界
- 客房停留层级与景观关系

这才是“知识底盘参与需求分析”的完整样子。  
不是只说一句“这是山地民宿”，而是要把判断、冲突、风险、冻结都带出来。

## 10. 最后的判断

如果要把 `民宿空间类型知识底盘示范` 做得足够宽，它的目标不应该只是：

- 给民宿多加几个标签；

而应该是：

> **把民宿从“单一类型”升级为“多轴组合对象”，再把这个对象压进需求分析的判断、补问、收敛、冻结与回写流程里。**

所以，一个成熟版本至少应同时覆盖：

- 空间类型
- 场地语境
- 文化地域
- 产品体验
- 客群社交
- 运营服务
- 品牌商业
- 投入盈利
- 用户体验
- 用户评价
- 冲突规则
- 冻结模板

一句话收尾：

> **民宿知识底盘真正的“宽”，不是知道更多民宿名字，而是能把“人、地、体验、材料、品牌、经营、口碑”一起纳入系统判断。**

## 11. 附录 A：变量矩阵与冻结对象对照表

### 11.1 场地语境 × 设计重点 × 高频风险矩阵

|---|---|---|---|
| 山地 | 坡地进入、借景层级、停留节点、雨雾过渡 | 潮湿、路难走、夜间回房风险、淡季波动 | 到达体验、借景层级、夜间照明、防潮边界 |
| 滨海 | 观海界面、防晒防风、防腐蚀、沙地回收 | 眩光、腐蚀、清洁压力、旺季拥挤 | 观海界面、材料耐候、清洁频率、高峰容量 |
| 江南 | 灰空间、细密尺度、漫反射光、在地生活感 | 潮冷、隔音弱、符号化仿古 | 灰空间层级、舒适度边界、在地表达方式 |

### 11.2 客群结构 × 社交压力 × 空间组织矩阵

| 客群结构 | 社交压力建议 | 空间组织倾向 | 风险提醒 |
|---|---|---|---|
| 年轻情侣 | `silent_private` / `low_pressure_shared` | 客房停留感强，公区弱社交 | 过度活动化会破坏私密氛围 |
| 亲子家庭 | `community_friendly` | 回收动线清晰，活动区与安静区分离 | 亲子噪声与其他客群冲突 |
| 朋友结伴 | `low_pressure_shared` / `community_friendly` | 公区节点丰富，可支持轻聚会 | 夜间扰民、房内外界线模糊 |
| 疗愈客群 | `silent_private` | 强化安静、疗愈、分时分区 | 与亲子/活动客群强冲突 |
| 中老年慢旅行 | `low_pressure_shared` | 强化舒适、易达、保暖、服务稳定 | 台阶、夜间照明、冬季体感问题 |
| workation 用户 | `low_pressure_shared` | 需要兼顾专注与轻交流 | 噪声、网络、办公舒适度不达标 |

### 11.3 价格带 × 服务承诺 × 维护压力矩阵

| 价格带 | 用户预期 | 服务承诺强度 | 维护要求 | 风险点 |
|---|---|---|---|---|
| `budget` | 干净、顺畅、性价比 | 基础稳定 | 中 | 表达过度、维护跟不上 |
| `midscale` | 舒适、清爽、有记忆点 | 轻服务 | 中 | 价格不上不下，定位模糊 |
| `upper_midscale` | 有体验差异、卖点可感知 | 轻至中服务 | 中高 | 卖点承诺与现场体验不一致 |
| `premium_boutique` | 整体感、细节感、稳定感 | 中至强服务 | 高 | 个性化成本与维护负债 |
| `luxury_destination` | 稀缺性、完整体验、稳定高品质 | 强服务 | 很高 | 一处短板即形成差评放大 |

### 11.4 品牌模式 × 个性化深度 × 运营可承接矩阵

| 品牌模式 | 个性化深度建议 | 运营承接逻辑 | 风险提示 |
|---|---|---|---|
| 主理人独立品牌 | `host_curated` / `deep_customized` | 依赖主理人叙事与现场控制 | 主理人离场即失真 |
| 精品独立品牌 | `light_personalized` / `host_curated` | 强调一致体验与差异记忆点平衡 | 过度艺术化导致维护压力 |
| 软品牌集合 | `light_personalized` | 标准与在地表达折中 | 品牌模糊、卖点不清晰 |
| 区域精品连锁 | `standardized` / `light_personalized` | 以稳定交付为主 | 在地感不足 |
| 目的地子品牌 | `light_personalized` | 与景区/文旅系统协同 | 容易沦为配套宿舍化 |

### 11.5 卖点类型 × 空间兑现方式 × 差评风险矩阵

| 卖点类型 | 需要的空间兑现方式 | 常见翻车点 |
|---|---|---|
| 看星星 | 控光、静音、夜间观景节点、保暖 | 光污染、风太大、回房不安全 |
| 森林疗愈 | 安静、呼吸感、分散停留、低机噪 | 霉味、虫、夜间噪声 |
| 海景日出 | 面海界面、日照控制、清晨动线 | 暴晒、眩光、清洁失控 |
| 茶冥想 | 低刺激灰空间、材料触感、安静 | 流于摆拍、实际过度商业化 |
| 温泉恢复 | 湿区卫生、动线分离、隐私 | 潮湿异味、噪声、排队拥挤 |
| 农食体验 | 餐食真实度、厨房/采摘/就餐组织 | 体验弱、仅剩宣传文本 |

### 11.6 风险类型 × review 收紧动作对照表

| 风险类型 | 信号表现 | review 收紧动作 |
|---|---|---|
| 到达体验风险 | 山路难走、找不到、夜间不安 | 强制补充到达流程与夜间回房方案 |

| 价格带错配风险 | 价格高但体验感薄 | 要求补服务承诺与体验完整性说明 |

## 12. 附录 B：需求分析接口版示意

如果说正文回答的是“底盘应该包含什么”，那这一附录回答的是：

> **需求分析系统在每个阶段，到底该从这套底盘里拿什么、问什么、冻什么。**

### 12.1 S1 输入 / 输出接口建议

#### S1 最小输入字段
- `core_type`
- `hospitality_subtype`
- `landscape_archetype`
- `cultural_geography`
- `experience_core`
- `guest_segment_profile`
- `price_tier_profile`
- `strategic_business_intent`

#### S1 核心判断任务
- 是否真的是民宿而非其他住宿类型？
- 场地语境是否足够明确？
- 产品体验是否已经出现主导方向？
- 客群、价格、卖点之间是否有第一轮冲突？

#### S1 输出建议
- `type_stack_summary`
- `site_context_summary`
- `primary_experience_hypothesis`
- `primary_conflict_hints`
- `trigger_intent_candidates`

### 12.2 S2 补问触发器建议

#### 补问触发器 A：客群冲突未解
- 条件：同时出现亲子 / 疗愈 / workation 等高冲突客群
- 补问方向：
  - 是否分栋、分层或分时？
  - 哪类客群是主力客群，哪类只是兼容客群？

#### 补问触发器 B：价格带与服务承诺不匹配
- 条件：高价格带但服务模型偏弱
- 补问方向：
  - 服务可见度与用户预期是否匹配？
  - 是否存在“卖高端，但服务接不住”的风险？

#### 补问触发器 C：场地高风险未展开
- 条件：山地/滨海/森林等高维护场景已识别，但维护策略未说明
- 补问方向：
  - 防潮/防腐/防风/防虫的边界是什么？
  - 夜间与恶劣天气策略是什么？

#### 补问触发器 D：卖点强但兑现路径弱
- 条件：出现强记忆点卖点，但空间承接方式不清楚
- 补问方向：
  - 卖点通过哪些空间节点兑现？
  - 用户在什么时候、以什么方式感知到它？

### 12.3 S3 武器优先级建议

| 识别到的主问题 | 优先武器方向 | 目标 |
|---|---|---|
| 客群冲突高 | 分区/分时/动线组织类武器 | 压低混住冲突 |
| 场地风险高 | 场地约束 / 材料维护 / 夜间策略类武器 | 提前压住差评源 |
| 卖点强但兑现弱 | 卖点兑现链 / 体验路径类武器 | 防止营销先飞 |
| 价格带高 | 服务稳定性 / 细节一致性类武器 | 保证高价不翻车 |
| 淡旺季波动强 | 经营可承接性 / 公区规模控制类武器 | 避免淡季空耗 |

### 12.4 S4 任务书冻结模板建议

#### 必冻对象（民宿通用）
- 主类型与住宿子类型

## 13. 附录 C：从“知识底盘示范”到“系统实现”的最短路径

如果后续要继续推进，不需要一步到位把全部民宿世界都建完。  
更现实的路径是先做一个最小闭环：

### 第一步：先固化最小识别集
- 主类型
- 场地语境
- 客群结构
- 体验核心
- 价格带
- 商业意图

### 第二步：补齐最小规则集
- 至少 5 类强冲突规则
- 至少 5 类优先级提升规则
- 至少 5 类 review 收紧规则

### 第三步：补齐最小经验集
- 每类原型至少 `3 个正例 + 3 个反例`
- 每类原型至少 `5 个高频好评 / 5 个高频差评`

### 第四步：挂进 S1-S4
- S1 用于初判
- S2 用于补问
- S3 用于收敛与武器排序
- S4 用于冻结与回写

### 第五步：回收真实项目反馈
- 从真实项目的审阅记录、修改记录、上线后评价中回写 L3
- 逐步把“纸面知识”变成“运营过的知识”

这条路径的关键是：

> **先让系统对几类典型民宿“判断得准”，再慢慢扩展到更多原型簇，而不是一开始就把所有变量塞满。**
