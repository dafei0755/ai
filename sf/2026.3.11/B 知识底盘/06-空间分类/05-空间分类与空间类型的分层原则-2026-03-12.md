# 空间分类与空间类型的分层原则（2026-03-12）

> 目的：把“空间分类”“空间类型”“类型变量”“混合项目”这几个最容易混淆的层次彻底分开，作为后续类型知识包、问卷路由、一主两辅挂接和任务书编译的共同基础。  
> 核心结论：**空间分类不是风格树，也不是材料树，更不是体验词树；它首先是一套“项目成立逻辑”的分层系统。一级分类决定系统用哪套眼镜看项目，二级类型决定调用哪包类型知识，变量层才负责承接场地、人群、经营、体验和跨学科拔高。**
> Codex备注：本文件由 Codex 于 2026-03-12 生成，用于固化空间分类与空间类型的分层原则。

---

## 1. 先把三个对象说清

如果不先区分对象，后面所有讨论都会混。

### 1.1 空间分类（Classification）

回答：

- 这是什么性质的项目？
- 它属于哪种成立逻辑？
- 系统后续应该启用哪套分析框架？

它的作用是：

- 路由
- 归桶
- 决定分析世界观

### 1.2 空间类型（Type）

回答：

- 在这个分类桶里，它更具体是哪一种典型项目？
- 这一类项目通常有哪些稳定变量、典型张力、经营方式和输出重点？

它的作用是：

- 调用类型知识包
- 提供稳定经验
- 给问卷、分析维度和任务书模板做细化

### 1.3 类型变量（Type Variables）

回答：

- 这个具体项目在场地、气候、人群、经营、体验、文化、品牌上有哪些差异？

它的作用是：

- 不改变主类型
- 但改变同一类型内部的判断重心

一句话说透：

> **分类决定“看什么逻辑”，类型决定“调用什么知识”，变量决定“这一次有什么不同”。**

## 2. 一级分类到底按什么分

一级分类不能按风格分，也不能按表面空间名字分。  
它应该按“项目如何成立”来分。

也就是：这个项目最核心的判断逻辑、风险结构和成功标准是什么。

### 2.1 一级分类建议口径

建议一级分类控制在有限的 8-12 个大桶，不要无限扩张。

可采用以下口径：

- `residential`
  - 以居住、长期停留、家庭生活与个体日常为主

- `hospitality`
  - 以短住、接待、度假、旅居、恢复性停留为主

- `office_workplace`
  - 以工作效率、协作结构、组织关系与专注/社交平衡为主

- `retail_dining`
  - 以消费转化、停留效率、展示与服务体验为主

- `culture_education`
  - 以学习、认知、传播、文化体验与内容承载为主

- `healthcare_wellness`
  - 以身体舒适、安全、恢复、照护与秩序边界为主

- `public_civic`
  - 以公共性、可达性、制度服务与多人群共存为主

- `industrial_production`
  - 以生产流程、安全、效率、物流和技术约束为主

- `renewal_mixed_use`
  - 以复合功能、存量改造、旧有结构再组织为主

- `religious_contemplative`
  - 以精神性、仪式、禁忌、静修与秩序边界为主

- `landscape_outdoor`
  - 以自然环境、外部行为、路径体验与气候条件为主

### 2.2 一级分类的判断标准

一个项目进入哪个一级分类，主要看四件事：

1. 主要使用逻辑
2. 主要成功标准
3. 主要风险来源
4. 主要分析框架

不是看：

- 它长得像什么
- 它用了什么材料
- 甲方说了什么风格词

## 3. 二级类型到底按什么细分

二级类型不是随便继续拆名字。  
它应该在一级分类内部，按“典型使用场景 + 经营方式 + 体验结构”细分。

### 3.1 二级类型的三条细分轴

#### 第一条：典型使用场景

例如在 `hospitality` 下：

- 民宿
- 精品酒店
- 度假酒店
- 长住公寓
- 疗愈型旅居

#### 第二条：经营与运营方式

例如：

- 独立经营
- 连锁标准化
- 小型精品
- 目的地型
- 高周转型

#### 第三条：核心体验结构

例如：

- 恢复性停留
- 景观消费
- 家庭共处
- 强社交
- 品牌展示

### 3.2 二级类型的作用

二级类型不是只为了名字更细，而是为了回答：

- 这类项目最典型的变量有哪些？
- 什么冲突最容易出现？
- 哪类输出模板最适合？

所以二级类型要服务知识调用，而不是服务分类表好看。

## 4. 什么不能混进分类树

空间分类系统最容易失控的原因，是把本不属于分类的信息塞进了分类层。

以下内容不应直接进入分类树：

### 4.1 风格词

例如：

- 侘寂
- 新中式
- 极简
- 复古

这些属于审美和表达变量，不是项目成立逻辑。

### 4.2 材料词

例如：

- 木质
- 石材
- 金属
- 微水泥

这些属于材料策略，不是类型。

### 4.3 跨学科气质词

例如：

- 诗意
- 哲学感
- 戏剧感
- 高级感

这些属于体验命题或拔高层，不是分类层。

### 4.4 单次项目概念

例如：

- 山谷疗愈乌托邦
- 都市精神洞穴
- 可呼吸的第二客厅

这些是项目级概念，不是可长期治理的分类对象。

### 4.5 过细运营细节

例如：

- 自助早餐型
- 周末活动型
- 短视频友好型

这些可进入变量层或运营标签层，不宜污染分类树。

一句话说透：

> **分类树只收“长期稳定、能决定分析框架”的信息，不收“这次项目很特别”的信息。**

## 5. 主类型与变量层怎么分工

一旦项目主类型确定，后续大量差异不应继续靠“加类型名”解决，而应进入变量层。

### 5.1 主类型负责稳定骨架

例如：

- `homestay`
- `boutique_hotel`
- `tea_space`
- `clinic`
- `co_working_office`

主类型负责定义：

- 基本产品性质
- 典型问题结构
- 常见输出模板

### 5.2 变量层负责具体差异

例如民宿项目的差异，不应再扩成几十个“新类型”，而应由变量表示：

- 地理语境：山地 / 滨海 / 江南 / 森林
- 气候维护：潮湿 / 强紫外 / 高风 / 低温
- 客群：情侣 / 家庭 / 朋友小团 / 康养
- 经营目标：复购 / 品牌传播 / 景观溢价 / 地方共建
- 体验重心：恢复性 / 打卡性 / 社交性 / 仪式性

因此更合理的结构不是：

> 无止境新增类型名

而是：

> **稳定主类型 + 多轴变量层**

## 6. 混合型项目怎么处理

真正困难的不是纯项目，而是复合项目。

例如：

- 民宿 + 茶空间
- 办公 + 展示 + 社交
- 康养 + 疗愈 + 度假
- 社区 + 商业 + 文化

这类项目不能只选一个类型，也不能把所有类型并列平铺。

### 6.1 推荐结构：主类型 + 副类型 + 混合权重

建议每个混合项目至少有：

- `primary_type`
- `secondary_types`
- `hybrid_weights`

示例：

```yaml
project_classification:
  primary_bucket: hospitality
  primary_type: homestay
  secondary_types:
    - tea_space
    - community_culture
  hybrid_weights:
    homestay: 0.60
    tea_space: 0.25
    community_culture: 0.15
```

### 6.2 主类型的判断原则

谁决定下面这些，谁就是主类型：

- 主要经营模型
- 主要使用时长
- 主要成功指标
- 主要一主矛盾

### 6.3 副类型的作用

副类型不取代主类型，而是：

- 补充功能
- 改变体验重心
- 改变空间组织
- 改变边界与禁忌

### 6.4 不能怎么做

不能：

- 把三个类型并列平权
- 遇到复合项目就新建一个超级长的类型名
- 用风格词去缝补混合关系

## 7. 分类结果如何进入后续系统

分类不是终点，它必须驱动下游。

### 7.1 驱动本体框架选择

一级分类决定：

- 启用哪套核心分析框架
- 哪些议题优先级更高

### 7.2 驱动类型知识包调用

二级类型决定：

- 调用哪包类型知识
- 用哪套变量矩阵
- 用哪类典型张力库

### 7.3 驱动问卷与补问

变量层决定：

- 哪些问题需要继续追问
- 哪些矛盾需要暴露

### 7.4 驱动一主两辅组织

分类结构会影响：

- 主命题如何表述
- 驱动力如何排序
- 边界优先级如何收紧

所以分类系统不是标签系统，而是：

> **后续认知调用的总入口。**

## 8. 一个最简判断流程

为了让空间分类不再发散，建议以后统一走下面这条流程：

### Step 1：先判一级分类

问：

- 这个项目最主要的成立逻辑是什么？

### Step 2：再判主类型

问：

- 在这个一级分类内，它最像哪类稳定项目？

### Step 3：再挂变量层

问：

- 这一次和同类项目相比，有哪些关键差异？

### Step 4：如果是复合项目，再补副类型和权重

问：

- 哪些副类型影响它，但并不主导它？

### Step 5：最后才进入体验命题与跨学科拔高

问：

- 这个项目除了成立，还想成为什么样的存在？

这个顺序很重要。  
如果体验命题先于类型判断，系统会飘；  
如果类型判断之后没有体验命题，系统会粗。

---

## 9. 示例：民宿 + 茶空间

假设一个项目是：

- 山地民宿
- 带茶空间
- 带小型文化活动

更合理的分类不是：

- 茶民宿文化空间

而是：

```yaml
project_classification:
  primary_bucket: hospitality
  primary_type: homestay
  secondary_types:
    - tea_space
    - culture_saloon
  type_variables:
    geo_scene: mountain
    target_audience:
      - urban_white_collar
      - weekend_family
    experience_focus:
      - restoration
      - low_pressure_companionship
    operation_mode:
      - independent
      - small_scale_event
```

这时：

- 分类系统保持清晰
- 类型知识仍可稳定调用
- 茶空间和文化属性也不会丢

## 10. 最后的判断

空间分类与空间类型真正需要解决的，不是“名字列得够不够多”，而是“系统是否因此更清楚地知道该怎么看项目”。

所以最重要的原则是：

### 10.1 一级分类按成立逻辑分

不是按风格，不是按材料，不是按感觉。

### 10.2 二级类型按典型使用场景、经营方式与体验结构细分

不是无止境堆名称。

### 10.3 变量层承接差异，不让分类树失控

不要把每次项目特殊性都变成新类型。

### 10.4 混合项目用“主类型 + 副类型 + 权重”处理

不要发明怪异复合名称。

### 10.5 体验命题和跨学科拔高必须后置

它们是建立在分类和类型已经清楚之后的高级层。

一句话总结：

> **空间分类负责确定项目属于哪种成立逻辑，空间类型负责调用哪包知识，变量层负责说明这次项目为何不同，体验命题负责让它从成立走向深刻。**
