## 一、先把总判断说清：知识底盘后台不是一个产品，而是两个相关但不同的后台

如果只从表面看，知识底盘似乎都在做同一件事：

- 上传知识
- 解析结构
- 审核发布
- 提供给需求分析调用

但进一步拆开就会发现，这里面至少有两类根本不同的对象：

### 1. 多学科/桥接/命题类知识资产

例如：

- 文学入库包
- feeling core
- bridge terms
- IR packet
- proposition
- case projection bundle

这一类本质上是：

- 内容资产
- 转译资产
- 命题资产
- 被结构化之后可拆条调用的知识对象

### 2. 空间分类 / 空间类型 / 路由类协议对象

例如：

- `project_type`
- `bucket / parent_type`
- `specialty_tag`
- `runtime_modifier`
- 类型边界与混淆规则
- ontology framework 绑定
- activation profile 绑定

这一类本质上是：

- 系统级注册表
- 路由协议
- 下游大量引用的稳定字典
- 被需求分析、问卷、类型检测、本体注入等模块反复依赖的核心骨架

所以第一条必须定死的结论是：

> **知识底盘后台不能只有一种操作形态，必须采用双轨并行。**

也就是说：

- 知识资产走“模板选型 → 人工 + LLM 清洗转译 → 结构化入库包提交 → 解析拆条 → 审核发布”
- 空间分类/类型走“注册表管理 → 变更审核 → 发布生效”

## 二、为什么不能做成纯 RAGFlow 式文件知识库

从 UI 形态上看，RAGFlow 类产品给了很好的启发：

- 可以上传文件
- 可以看到解析状态
- 可以做启停
- 可以做检索测试

但如果照着做，会产生根本偏差。

### 1. 因为我们的核心对象不是“文档块”，而是“知识对象”

RAG 类系统的核心对象通常是：

- document
- chunk
- embedding
- retrieval

而知识底盘的核心对象是：

- bundle
- source_record
- bridge_terms
- feeling_core
- experience_structure
- ir_packet
- space_state_proposition
- lifecycle state
- registry entry

也就是说：

> **我们管理的不是“文档被切成什么块”，而是“知识被解析成什么对象”。**

### 2. 因为我们的目标不是问答，而是需求分析调用

通用 RAG 的目标常常是：

- 上传文档
- 向量召回
- 问答引用

而知识底盘后台最终服务的是：

- 需求分析阶段调用
- 一主两辅投影
- 风险门禁
- 冻结分流
- 回评升级

因此，系统更关心的是：

- 哪条 proposition 已发布
- 它适用于哪些空间类型
- 它的 freeze ceiling 是什么
- 是否存在高风险误读
- 它会挂到一主、驱动力还是边界

所以不能把后台误做成普通文档仓库。

## 三、为什么也不能做成纯数据库表单后台

反过来，如果完全不保留 YAML / 包级概念，只做数据库表单管理，也会走偏。

因为知识底盘还有很强的：

- 人工可读性
- 审阅性
- 方法论资产属性
- Git diff 价值
- 导入导出价值
- 迁移与分享价值

像《清平乐·村居》那份完整 YAML 样板，它本身就是一种高质量的“知识条目包表达”。

如果完全取消这种表达方式，会导致：

- 人工创建成本过高
- 评审过程困难
- AI 自动生成不顺畅
- 包级语义关系丢失
- 迁移与批量导入困难

所以第二条必须定死的结论是：

> **数据库必须是真源，但 YAML 不能消失。YAML 应作为条目包格式和变更介质被保留。**

## 四、最终真源放哪里：数据库做运行真源，YAML 做交换真源

这一点必须制度化，不然以后一定出现双真源问题。

## 1. 数据库：运行真源

数据库负责回答：

- 系统当前认哪一版？
- 哪些条目已经 published？
- 哪些 proposition 当前 enabled？
- 哪些类型已经生效？
- 哪些变更审核通过？
- 哪些历史引用仍需兼容？

也就是说：

> **运行时永远只认数据库中的最新已发布状态。**

## 2. YAML：交换真源

YAML 负责：

- 条目包录入
- 批量导入导出
- 人工审阅
- Git 管理
- 快照备份
- 变更提案

它回答的是：

- 这份知识/这组变更如何被表达
- 人如何看、如何审、如何迁移

但不负责直接作为运行时最终真源。

## 3. 这句话必须写成制度

建议固定为：

> **数据库负责“系统当前认什么”，YAML 负责“人如何看、如何导、如何审、如何迁”。**

## 五、主产品形态：双轨并行，而不是一轨通吃

## 轨道 A：知识资产后台

这条线管理的是“可上传、可解析、可拆条”的结构化知识对象。

### 适用对象

- 多学科知识包
- bridge / feeling / IR / proposition bundle
- case projection bundle
- 经验模板包

### 主入口

- 选择入口模板
- 按模板进行人工 + LLM 清洗转译
- 提交结构化 YAML / JSON 入库包
- 预校验
- 解析预览
- 拆条
- 审核
- 发布

### 运行时调用对象

不是整包，而是拆出的正式资产：

- proposition
- IR
- bridge terms
- rules
- case records

### 一个关键修正：正式后台不建议直接上传原始素材

这里必须把“上传优先”再说精确一点。

所谓上传优先，不是指：

- 把 PDF、截图、网页全文、原始评论直接扔进正式后台

而是指：

- 后台以“结构化提交”为主入口
- 每个入口先提供不同模板
- 人工根据模板组织材料
- 借助 LLM 做清洗、去噪、归纳、转译
- 最终提交的是结构化入库包，而不是原始材料本身

也就是说：

> **正式后台接收的对象应该是“已被转译过的结构化知识包”，不是未经整理的原始素材。**

原始素材可以：

- 保留在外部素材仓
- 作为 `source_ref` 被引用
- 只截取必要证据片段进入系统

但不建议直接以“原始全文直传”的方式进入正式知识底盘。

### 知识资产入口分类原则：入口按“系统角色”分，而不是按学科、好坏或文件格式分

到这一步，知识资产后台的“入口模板”不宜继续按素材来源无限细分，也不宜直接按一主两辅对用户暴露。更稳定的做法是：

> **一级入口按材料进入系统后扮演什么角色来分；一主两辅作为内部吸收与路由逻辑，而不是直接作为用户上传入口。**

因此，一级入口不应主要按以下方式成立：

- 不按学科成立（文学 / 哲学 / 电影 / 艺术……）
- 不按好坏成立（优秀 / 失败）
- 不按文件格式成立（PDF / PPT / DOCX / YAML）

而应按以下问题成立：

- 这份材料首先是在回答“用户要什么”吗？
- 它是在复盘一个具体项目吗？
- 它是在提供规则与边界吗？
- 它是在表达某种可复用的方法或手法吗？
- 它与项目没有直接关系，必须先经过一次转译吗？

### 建议的一级入口：6 类

在当前阶段，知识资产后台建议收敛为 5 个一级入口：

1. `用户与需求`
2. `案例复盘`
3. `方法与手法`
4. `多学科 / 跨域转译`
5. `规范规则`
6. `落地实施`

这 5 类入口既符合用户上传时的自然习惯，也能被系统稳定吸收到一主两辅与风险门禁逻辑中。

其中排序建议也有含义：

- 前半段优先放“认知与判断形成类”入口
- 后半段集中放“实现与边界约束类”入口

因此将 `规范规则` 后移，并与 `落地实施` 放在一起，更有利于形成“制度边界 + 现实边界”的连续认知。

### 1. 用户与需求

适用于：

- 用户评价
- 用户访谈
- 客群研究
- 区域商业调查
- 行业报告
- 行为与动机研究

这一类入口的成立依据是：

> **材料首先回答“用户真正要什么、为什么要、真实痛点和驱动力是什么”。**

它通常优先供给：

- 一主候选
- 驱动轴
- 少量边界提醒

### 2. 案例复盘

适用于：

- 具体项目案例
- 标杆案例拆解
- 项目成败复盘
- 竞品项目复盘

这一类入口的成立依据是：

> **材料主对象是一个具体项目，且核心价值仍依附于该项目的成立点、失误点、条件成立点与不可复制前提。**

这里必须明确：

- 优秀案例与失败案例不宜再做一级入口拆分
- 更合理的做法是统一进入 `案例复盘`
- 再在审核中拆出正向成立点、反向失误点、条件成立点与不可复制点

也就是说：

> **案例是载体，正反是提取维度。**

### 3. 方法与手法

适用于：

- 大师方法论
- 设计组织方法
- 审阅透镜
- 工法 / 技法
- 流派 / 风格机制
- 趋势 / 潮流中已形成共性的规律对象

这一类入口的成立依据不是“它是不是来自某个大师”，也不是“它是不是某种风格标签”，而是：

> **材料的核心价值已经不局限于单个具体项目，而是形成了跨项目可复用的共性规律。**

因此，这一类可以容纳：

- 某个流派
- 某种风格机制
- 某个趋势 / 潮流的共性判断
- 某种工法逻辑
- 某位大师的方法论

但必须注意：

> **风格、趋势、潮流并不自动等于高质量方法；只有当它们被提炼成稳定规律、组织逻辑或可复用判断时，才应进入正式“方法与手法”资产。**

### 4. 多学科 / 跨域转译

适用于：

- 文学
- 哲学
- 电影
- 艺术
- 人类学
- 生活方式观察
- 审美分析

这一类保留为一级入口的原因，不是因为它们都来自“外部学科”，而是因为：

> **它们往往与项目没有直接关系，必须先经过一次从非项目语境到项目语境的转译，才能进入正式知识系统。**

也就是说，多学科入口的成立依据是“需要先转译”，而不是“学科很多”。

### 5. 规范规则

适用于：

- 品牌规范
- 空间标准
- 法规约束
- 服务标准
- 不得越界项

这一类入口的成立依据是：

> **材料主对象是约束、标准、护栏与一致性要求，而不是启发本身。**

它通常优先供给：

- 边界轴
- 实施边界
- 审核门禁

### 6. 落地实施

适用于：

- 材料物料
- 工艺工法
- 价格造价
- 品牌 / 供应商 / 产品线
- 替代关系
- 实施风险

这一类入口的成立依据是：

> **材料主对象是项目实现层的现实条件：能不能做、怎么做、做得起吗、供应链撑得住吗、风险是否可控。**

它与 `规范规则` 同属第二辅轴，但两者并不相同：

- `规范规则` 更偏制度边界
- `落地实施` 更偏现实边界

因此，`落地实施` 应与 `规范规则` 并列，而不是并入其下。


### 案例复盘与方法与手法的边界

这两个入口最容易交叉，因此必须明确一条判断规则：

> **案例讲“这个项目发生了什么”，方法讲“跨项目都可能成立什么”。**

更具体地说：

- 如果材料的主对象仍然是具体项目及其成败条件 → `案例复盘`
- 如果材料的核心价值已经从项目中抽离出来，成为可跨项目迁移的规律 → `方法与手法`

因此：

> **案例复盘是项目层对象，方法与手法是规律层对象。**

### 默认处理规则：材料同时包含案例描述和方法总结时

现实中大量材料同时具有案例描述与方法总结，因此建议固定默认规则：

- 若主对象仍是具体项目 → 默认先走 `案例复盘`
- 审核过程中可再从中提炼出 `方法与手法` 资产

也就是说：

> **默认先落具体，再升抽象；先作为案例复盘入库，再按需要提炼出方法资产。**

这样既能承认案例与方法的交叉，又能避免入口判定时的混乱。

## 轨道 B：空间分类 / 类型后台

是注册表中最新已发布的：

## 六、知识资产如何对应到空间分类与空间类型

这是双轨体系里最关键的挂接关系之一。

前面说“用户评价、行业报告、品牌规范、大师方法等不直接进入空间分类注册表”，并不等于它们和空间分类无关。恰恰相反：

> **知识资产不负责定义空间类型；它与空间分类的关系，应在审核入库页面由人工勾选绑定，而不是在文档正文里预先声明。**

也就是说：

- 空间分类后台负责定义“系统有哪些正式类型”
- 知识资产后台负责承载内容本身
- 审核入库页面负责把内容与 bucket / type / tag / modifier 绑定起来

### 1. 四层挂接关系应作为审核绑定结果写入数据库

这组信息不建议由文档作者手写进正文，也不建议在上传前硬编码在 YAML 主体里。

更稳定的方式是：

1. 文档先完成清洗、摘要、转译
2. 进入审核入库页面
3. 在页面里勾选分类层级
4. 审核通过后，再把绑定结果写入数据库关系层

其中 `bucket` 的绑定规则建议明确为：

- 必须选择 **1 个主 bucket**
- 允许附加 **多个附属 bucket**

这样既能保证每条知识资产有稳定的主空间语境，又能承认一部分知识确实具有跨 bucket 的辅助适用性。

与之对应，`type` 的选择规则建议明确为：

- **主 type 只能从主 bucket 下选择**
- **附属 type 只能从对应附属 bucket 下选择**
- **主 bucket 已确认时，主 type 允许暂空，但必须标记为 `type_pending` / 待补主 type**

关于 `pending` 的使用边界，建议进一步明确为：

- **只有主 type 允许使用 `type_pending`**
- `specialty_tag` 不单独设 `pending`
- `runtime_modifier` 不单独设 `pending`

也就是说：

- tag 未选 = 当前无需细化到该层
- modifier 未选 = 当前暂无明确运行修正条件

这样可以把 `pending` 严格限制在骨架层，避免细化层出现过多“待补状态”而削弱治理稳定性。

这样可以保证审核绑定时的树状约束关系稳定，避免 bucket 与 type 跨层乱挂。

建议入库后的关系字段包括：

- `applicable_bucket_codes`
- `applicable_type_codes`
- `applicable_specialty_tags`
- `applicable_runtime_modifiers`

同时补一个强弱字段：

- `binding_strength`

用于区分：

- `strong_default`（强适用）
- `conditional`（条件适用）
- `weak_signal`（弱线索）
- `not_recommended`（不建议适用）

建议在 V1 中就把这 4 档与系统行为直接绑定，而不是只做文字标签：

### 强适用（`strong_default`）

- 对该 bucket / type / tag / modifier 稳定成立
- 可高优先级进入正式调用
- 可参与默认召回

### 条件适用（`conditional`）

- 对该对象成立，但依赖客群、预算、定位、运营模式等条件
- 可进入正式调用，但优先级次于强适用
- 调用时应附带条件检查

### 弱线索（`weak_signal`）

- 更偏启发、透镜、观察或辅助判断
- 可低优先级参与召回
- 更适合作为审阅补充，而不应主导调用

### 不建议适用（`not_recommended`）

- 明确容易误挂、误用或误译
- 不进入正式调用
- 只保留为后台警示或风险记录

建议将 `binding_strength` 理解为**对每个已绑定对象单独设置**，而不是整条知识资产只设置一个全局强度。

也就是说：

- 对主 bucket 可以是强适用
- 对某个附属 bucket 可以只是弱线索
- 对某个 modifier 甚至可以是不建议适用

这些字段的归属应理解为：

- **不是文档正文属性**
- **而是审核入库后的系统绑定属性**

### 2. 六类材料与空间类型的挂接强度不同

#### 用户评价 / 调查报告 / 行业报告

更适合挂到：

- `type`
- `specialty_tag`
- `runtime_modifier`

因为它们常常对某些细分业态、客群条件、经营场景更敏感。

#### 品牌设计规范

更适合挂到：

- `type`
- `brand_scope`
- `mandatory_when`

因为它往往不是启发，而是某些空间类型下的硬约束。

#### 大师设计思路 / 观察分析

更适合挂到：

- `bucket`
- `possible_type_hints`
- `not_applicable_types`

因为它们更像方法透镜与观察线索，适用范围通常更宽，但约束力更弱。

### 3. 知识资产只能挂接类型，不能偷偷生长新类型

如果某条知识资产上传后发现：

- 现有空间类型无法容纳它
- 需要新增一个正式 type 才能合理挂接

正确流程不是在知识资产线里硬塞一个新类型，而是：

1. 先把该知识资产标记为 `type_gap_detected`
2. 自动生成空间分类后台候选变更任务
3. 由注册表流程决定是否新增 / 调整 type

这样能避免知识资产线偷偷长出“野生空间类型”。

### 4. 后台应增加“类型挂接视图”

在知识资产详情页中，应增加：

- 当前挂接的 bucket / type / tag / modifier
- 绑定强度
- 不适用类型
- 受影响的类型变更记录

这样后台编辑者就能看见：

- 这条知识到底服务哪些空间类型
- 如果空间类型变了，它会受什么影响

## 九、两条后台各自的主界面形态

## A. 知识资产后台：以“导入台 + 包列表 + 条目库 + 审核台 + 调用测试”为核心

### 页面 1：导入台

支持：

- 选择入口模板
- 查看模板字段说明
- 人工填写清洗后的结构化内容
- 调用 LLM 辅助清洗、摘要、转译
- 上传结构化 YAML / JSON 入库包
- 预校验
- 解析预览
- 显示将生成哪些资产
- 提交入库

这里要明确：

> **导入台不是“原始素材投喂口”，而是“模板化结构化提交台”。**

如果需要保留原始材料，建议只保留：

- 来源链接
- 来源文件标识
- 摘要片段
- 关键证据摘录

### 页面 2：导入包列表

展示：

- package 名称
- package 类型
- 解析状态
- 审核状态
- 资产数量
- 发布时间
- 操作

### 页面 3：条目库

展示：

- 资产类型
- 来源包
- 启用状态
- 风险等级
- 审核状态
- 版本

并建议额外展示：

- 适用空间类型
- 绑定强度
- 是否受类型变更影响

### 页面 4：审核台

重点审：

- 字段完整性
- 挂接合理性
- 风险标记
- 冻结级别
- 是否可调用

并增加：

- LLM 推荐的 bucket / type / tag / modifier 是否合理
- 审核人是否已完成人工勾选确认
- 是否误挂到不适用的空间类型
- 是否应触发类型缺口任务

这里建议把审核台拆成左右两区：

- 左侧看内容：来源摘要、证据摘录、结构化结果、proposition 候选、风险提示
- 右侧做绑定：主 bucket、附属 bucket、type、specialty tag、runtime modifier、绑定强度、不适用类型

其中右侧绑定区的交互顺序建议固定为：

1. 先选主 bucket
2. 再从主 bucket 下选择主 type（如暂无法确认，可先置为 `type_pending`）
3. 如有附属 bucket，再展开各自 bucket 下的附属 type
4. 最后再补 specialty tag、runtime modifier、绑定强度与限制项

在这一步中，建议采用：

> **LLM 推荐 + 人工确认**

也就是说：

- 系统可先根据内容给出 bucket / type / tag / modifier / binding_strength 的候选推荐
- 审核人可以接受、修改、删除或补充这些推荐
- 未经人工确认的推荐，不能直接写入正式绑定关系

这条规则的目的，是在降低审核操作负担的同时，避免模型自动拍板带来的错误挂接。

也就是说：

> **空间分类层级不是文档属性，而是审核入库时的人机协同绑定结果。**

### 页面 5：调用测试页

这页必须尽早进入 V1，因为它决定后台不是“看起来整齐”，而是真的服务需求分析调用。

测试内容包括：

- 给定一个项目输入，会召回哪些 proposition
- 哪些 assets 会命中
- 哪些被门禁拦下
- 哪些挂到一主 / 驱动力 / 边界

### 页面 6：详情页与修订页

这页很关键，因为后台不仅要能上传，还必须能看见已经发布的内容，并支持安全修订。

这页建议展示：

- 当前已发布版本
- 来源摘要与证据摘录
- 结构化字段详情
- 类型挂接详情
- 历史版本
- 变更原因
- “发起修订”按钮

## B. 空间分类 / 类型后台：以“注册表树 + 详情页 + 变更包导入 + 影响/版本”为核心

### 页面 1：注册表树管理

建议分 tab 展示：

- bucket
- type
- specialty tag
- runtime modifier

支持：

- 新增
- 编辑

- 停用
- 移动
- 合并

- 典型张力
- 最易混淆对象
- ontology / activation 绑定
- alias
- impact 范围
- 历史变更

### 页面 3：变更包导入

- 某次移动/合并/重命名的历史链
- 回滚能力

## 十、YAML 在两条线中的角色必须区分清楚

这是全套方案非常关键的一点。

## 1. 在知识资产线中，YAML 是“入库包”

它表达的是：

- 一整包知识如何被结构化表达
- 它将被拆成哪些资产
- 它如何被审、被发、被导出

这类 YAML 是：

- `Knowledge Bundle YAML`

## 2. 在空间分类线中，YAML 不是“知识包”，而是“注册表快照 / 变更补丁”

建议分成两类：

### `Registry Snapshot YAML`
用于：

- 当前已发布注册表导出
- 备份
- 审阅
- Git diff
- 离线查看

### `ChangeSet YAML`
用于：

- add
- rename
- deprecate
- merge
- move
- restore

所以必须明确：

> **空间分类与空间类型也可以用 YAML，但它们不应复用普通知识条目包的 schema。**

## 十一、修改规则：哪些可以改，哪些必须高门槛

## A. 知识资产线

### 允许

- 以模板为基础提交结构化包
- 重命名包标题
- 编辑字段
- 停用条目
- 归档条目
- 重新解析
- 导出包

### 必须补充的一条制度：不能直接修改已发布数据库记录

知识资产一旦 published，后台所有修改都不应直接落到当前运行态记录上，而应走：

1. 发起修订
2. 生成 `draft_revision`
3. 在草稿副本中编辑
4. 重新审核
5. 发布新版本
6. 由数据库切换“当前已发布版本”指针

也就是说：

> **可以在后台看见已发布内容，但修改必须走“草稿副本 → 审核 → 新版本发布”，而不是直接改数据库现值。**

建议状态机至少包括：

- `draft`
- `review_pending`
- `published`
- `archived`
- `deprecated`

建议增加两个实现对象：

- `DraftRevision`
- `PublishedPointer`

其中：

- `DraftRevision` 负责承接编辑行为
- `PublishedPointer` 负责指向当前生效版本

### 默认不建议

- 直接硬删除已发布条目

更合理的默认动作应是：

- archive
- disable
- deprecated

## B. 空间分类线

### 允许

- 新增 bucket / type / tag / modifier
- 重命名 label
- 停用
- 移动
- 合并
- 恢复

### 必须附带的制度

#### 1. 重命名不改 canonical_id

- `type_code` 不变
- `label` 可变
- 历史名自动进入 alias

#### 2. 删除默认解释为“停用 / 迁移 / 归档”

只有满足“无引用或完成迁移”时，才允许硬删。

#### 3. 一级分类变更比二级类型更严格

因为 bucket 是路由骨架，不只是显示字段。

#### 4. 高风险字段变更必须重新审核

例如：

- `bucket_code`
- `ontology_framework_ref`
- `activation_profile_ref`
- `misclassification_risks`
- `freeze_priority_hint`

## 十二、冲突裁决：后台表单与 YAML 变更包如何共存

这里最容易混淆。

不应简单说“后台优先”，而应更精确地写成：

> **已发布注册表优先。后台表单与 YAML 变更包，都是变更提案入口。**

这意味着：

- 表单改动 ≠ 立即生效
- YAML 导入 ≠ 立即生效
- 两者都必须进入审核与发布流程
- 运行时永远只认最新已发布版本

当两者冲突时，正确做法应是：

- 以当前已发布注册表为基线
- 做差异比对
- 形成合并审核
- 发布后统一生效

## 十三、与需求分析阶段的关系：后台不是为了好看，而是为了调用

无论是知识资产后台，还是空间分类后台，最后都必须回到一个问题：

> **它是否真正服务需求分析阶段的调用？**

### 1. 知识资产后台服务什么

它服务：

- proposition 召回
- 体验命题增强
- IR 支撑
- 风险门禁
- 一主两辅投影

### 2. 空间分类后台服务什么

它服务：

- project type 检测
- question 路由
- ontology framework 注入
- activation profile 选择
- specialty tag 识别
- modifier 修正

### 3. 两条线如何联动

建议固定两条自动联动规则：

#### 规则一：类型变更后自动生成挂接校验任务

检查：

- 哪些知识包的 `applicable_space_types` 受影响
- 哪些 proposition 的挂接失效
- 哪些问卷或模板需要复核

#### 规则二：新类型发布后自动生成知识补齐任务

提醒：

- 该类型缺少哪些 proposition
- 缺少哪些案例
- 缺少哪些边界样例
- 缺少哪些多学科增强资源

#### 规则三：知识资产修订后自动触发类型重校验

检查：

- 新版本是否仍适用于原 type
- 绑定强度是否发生变化
- 是否新增了 `not_applicable_types`
- 是否需要重新进入调用测试

## 十五、最重要的产品定义

如果把这整套方案压成一句产品定义，建议定成：

> **知识底盘后台不是通用文档知识库，而是一个以模板化结构化条目包为入口、以数据库为真源、以拆条发布与注册表发布为核心、以审核和调用测试为门禁的结构化知识运营台。**

如果再进一步分成两句：

> **知识资产走“模板清洗后提交结构化包”，空间类型走“注册表”；二者都可用 YAML，但不是同一种 YAML，也不是同一种后台操作对象。**

## 十六、最后的结论

这轮讨论后，我认为最应该固定下来的不是某个局部 UI，而是以下五条总原则：

### 1. 知识底盘后台必须双轨并行

- 知识资产后台
- 空间分类/类型后台

### 2. 数据库是真源，YAML 是交换与变更介质

运行时只认数据库中的已发布状态。

### 3. 知识资产以“整包导入、拆条调用”为核心

运行时不直接吃原始包。

更准确地说，正式后台不直接吃原始素材，而只接收经过模板清洗与转译的结构化包。

### 4. 空间分类/类型以“注册表管理、变更审核、引用保护”为核心

不能当成普通知识条目处理。

知识资产只能挂接空间类型，不能绕过注册表流程私自生成新类型。

### 5. 后台的价值不在于管理文件，而在于服务需求分析阶段调用

不能被调用、不能被审核、不能被回评的对象，不应进入正式底盘。

### 6. 已发布内容可见，但修改必须版本化

后台必须支持查看已发布内容，但所有修订都应通过草稿副本、审核与重新发布完成，而不是直接改数据库现值。

一句总收尾：

> **知识底盘后台的正确形态，不是做一个更漂亮的文件柜，而是做一个能把知识、类型、路由、审核与调用真正接起来的结构化运营台。**
