# 安全验证双阶段与拒绝路由契约（2026-03-09）

> **导航提示：** 建议先读 [README](README.md) 与 [04-安全验证与拒绝路由](04-安全验证与拒绝路由-2026-03-11.md)；若你要先理解运行时中控和实时链路，可回看 [01](01-运行时实时链路与断线恢复-2026-03-11.md) / [02](02-工作流运行器与状态广播契约-2026-03-11.md)。

> 范围：`unified_input_validator_initial`、`unified_input_validator_secondary`、`input_rejected`。  
> 原则：以当前代码为准，不采信历史链路中的已废弃路径。

---

## 1. 节点职责与主链位置

主链中的安全门禁分为两段：

```
START
  → unified_input_validator_initial
  → requirements_analyst
  → requirements_analyst_review
  → output_intent_detection
  → feasibility_analyst
  → unified_input_validator_secondary
  → progressive_step3_gap_filling
```

- `unified_input_validator_initial`：输入初筛（安全/领域/复杂度）
- `unified_input_validator_secondary`：需求分析后复检（领域一致性、漂移风险）
- `input_rejected`：拒绝终止节点，提供可解释拒绝原因

---

## 2. 路由契约（代码语义）

### 2.1 初始验证

- 通过：`goto="requirements_analyst"`
- 拒绝：`goto="input_rejected"`

关键约束：
1. 初始验证不直接进入问卷步骤。
2. 它只决定“是否允许进入需求分析”。

### 2.2 二次验证

- 正常通过：进入 `progressive_step3_gap_filling`
- 拒绝：`goto="input_rejected"`
- 领域漂移重判：可回流 `requirements_analyst`

关键约束：
1. 二次验证发生在可行性分析后。
2. 其目标是“收口前的领域一致性兜底”。

---

## 3. state 字段读写契约

典型读取：
- `user_input`
- `structured_requirements` / `agent_results`（用于二次验证摘要）

典型写入：
- `domain_classification`
- `content_safety_status`
- `rejection_reason`
- `rejection_message`
- `final_status`（拒绝场景）

建议：
- 前端统一消费 `rejection_reason + rejection_message`，避免“只提示失败、不解释原因”。

---

## 4. 前端交互契约（interrupt）

安全验证可能触发澄清型交互（如领域不明确）：
- 交互动作应映射到“继续 / 澄清 / 拒绝”三类决策
- 用户确认后必须恢复到原节点语义，不能跳过后续必要门禁

实践建议：
- 将澄清响应结构化（action + optional_text），便于后端复判。

---

## 5. 风险与防回归清单

1. **历史文档漂移**：把 `progressive_step1_core_task` 当作主链节点（错误）。
2. **拒绝路由弱语义**：只返回失败标记，不返回可解释原因。
3. **前后端动作不一致**：前端“确认”被后端解释成“重跑”。

最小回归点：
- 非法输入应稳定进入 `input_rejected`。
- 合法输入必须进入 `requirements_analyst`。
- 二次验证失败不会误放行到后续问卷节点。
