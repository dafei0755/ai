> **一句话结论：** 当前系统已具备“WebSocket 实时推送 + EventStore 事件落盘 + HTTP 回放补偿”的闭环，断线重连可基于 `after_seq` 拉取遗漏事件。

---

## 一、代码事实锚点

| 能力 | 代码位置 | 事实 |
|---|---|---|
| WebSocket 入口 | `intelligent_project_analyzer/api/ws_routes.py` | `@router.websocket("/ws/{session_id}")`；连接池管理；初始状态补发；心跳 ping/pong |
| 广播入口 | `intelligent_project_analyzer/api/workflow_runner.py` | `broadcast_to_websockets(session_id, message)` 在广播前写入 EventStore |
| 事件存储 | `intelligent_project_analyzer/services/event_store.py` | `append()` 生成会话内自增 `seq`；`get_after()` 按 `seq > after_seq` 返回；支持 Memory/Redis 后端 |
| 回放接口 | `intelligent_project_analyzer/api/_report_routes.py` | `GET /api/analysis/events/{session_id}?after_seq=` 返回遗漏事件列表 |
| 前端统一入口 | `frontend-nextjs/lib/workflow-realtime-client.ts` | 继承 `WebSocketClient`，预留 seq 去重与 HTTP 回放接入位 |

---

## 二、闭环时序（当前生效）

```text
工作流节点产出消息
  → workflow_runner.broadcast_to_websockets()
  → EventStore.append(session_id, payload)  [写入 seq]
  → WebSocket 推送给在线客户端

客户端断线
  → 重连后发送最后已处理序号 after_seq
  → GET /api/analysis/events/{session_id}?after_seq=N
  → EventStore.get_after() 返回 seq>N 的遗漏事件
  → 客户端按 seq 顺序补播
```

## 三、关键契约

### 3.1 事件结构契约

```json
{
  "seq": 12,
  "session_id": "...",
  "timestamp": 1700000000.0,
  "payload": { "type": "status_update", "progress": 0.4 }
}
```

### 3.2 语义契约

1. `seq` 在**同一会话内严格递增**（从 1 开始）
2. 回放接口返回 `seq > after_seq` 的全部事件
3. 事件有 TTL（默认 3600 秒）；超出 TTL 不保证可回放
4. EventStore 写入失败不阻断主流程（降级为仅实时推送）

---

## 四、实现边界与风险

| 风险 | 说明 | 对策 |
|---|---|---|
| TTL 导致长断线缺口 | 超过保留窗口后无法补齐完整事件流 | 前端重连时先拉 `initial_status`，再回放；必要时提示“部分历史不可用” |
| 客户端重复消费 | 重连+回放可能与实时推送重叠 | 前端按 `seq` 去重（在 `workflow-realtime-client.ts` 实现） |
| 多实例一致性 | 单内存后端仅单实例可见 | 生产使用 Redis 后端，确保跨实例回放一致 |

## 五、落地建议（P0/P1）

- **P1**：补一条集成测试：断线后 `after_seq` 回放事件数量与顺序正确
