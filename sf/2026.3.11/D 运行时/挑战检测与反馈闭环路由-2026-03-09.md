# 挑战检测与反馈闭环路由（2026-03-09）

> **导航提示：** 建议先读 [README](README.md) 与 [05-统一审核预检与挑战闭环](05-统一审核预检与挑战闭环-2026-03-11.md)；本文负责其中“挑战识别 → 分级 → 回流/继续”的后半闭环。

> 范围：`detect_challenges` 节点及其后续分流。  
> 目标：把“挑战识别 → 分级 → 路由”的闭环规则固化为可回归协议。

---

## 1. 节点位置

执行阶段尾部：

```
batch_router
  → detect_challenges
  → result_aggregator（默认）
```

根据挑战情况可能分流到：
- `manual_review`
- 回访/重判链路（通常回流需求分析或审核链）

---

## 2. 输入来源与输出语义

输入来源（常见）：
- `agent_results[*].challenge_flags`
- 批次执行元数据中的问题集合

核心输出：
- `challenge_detection`（检测结果总览）
- `challenge_handling`（处理建议）
- `has_active_challenges`
- `requires_manual_review`
- `requires_client_review`
- `requires_feedback_loop`

---

## 3. 分级与路由优先级

建议固定优先级：
1. `manual_review`（高严重度密集）
2. `client_review`（需外部裁决）
3. `feedback_loop`（信息不足/冲突需回补）
4. `continue`（可继续聚合）

原因：优先处理“高风险、不可自动决策”的问题，降低误放行。

---

## 4. 与主链冻结约束的关系

本项目当前主链事实是 `detect_challenges`。  
文档中出现 `detect_and_handle_challenges` 时，应标为“兼容实现名/历史名”，避免与工作流节点名混淆。

---

## 5. 前端与可观测性建议

前端建议：
- 展示 challenge 数量与严重度分布（high/medium/low）
- 区分“自动可继续”与“需要人工处理”状态

可观测性建议：
- 对每次挑战分流写入统一事件（session_id + route + reason）
- 在回放接口中可重建“为什么被分流”

---

## 6. 最小回归断言

1. 无挑战时必须进入 `result_aggregator`。
2. 严重挑战满足阈值时必须进入 `manual_review`。
3. 反馈闭环触发后不得丢失 `feedback_loop_reason`。
4. 分流后 state 中 challenge 字段保持可解释、可追踪。
