# 统一审核到质量预检的确认协议（2026-03-09）

> **导航提示：** 建议先读 [README](README.md) 与 [05-统一审核预检与挑战闭环](05-统一审核预检与挑战闭环-2026-03-11.md)；本文负责其中“审批确认 → 质量预检”的前半闭环。

> 范围：`role_task_unified_review` → `quality_preflight`。  
> 目标：固化“用户确认后先预检，再执行”的协议，避免历史文档误导为直接执行。

---

## 1. 主链位置与关键语义

```
project_director
  → role_task_unified_review
  → quality_preflight
  → batch_executor
```

关键语义：
- `role_task_unified_review`：用户审批点（可修改角色/任务）
- `quality_preflight`：静默预检，不再弹同级审核中断
- `batch_executor`：仅在审批+预检完成后进入

---

## 2. 审批动作与路由映射

典型动作：
- `approve/confirm`：进入 `quality_preflight`
- `modify_roles`：回流 `project_director`
- `modify_tasks`：回流 `project_director`
- `change_strategy`：回流 `project_director`
- `reject`：回流 `project_director`（附拒绝原因）

协议要点：
1. “确认”不是“直达执行”。
2. 所有用户修改必须入 state（可审计）。

---

## 3. 负载与 state 契约

统一审核中断负载至少应包含：
- 角色选择结果（selected_roles）
- 任务分配结构（task list / work packages）
- 可执行选项（approve / modify / reject）

审批写入建议字段：
- `role_selection_approved`
- `task_assignment_approved`
- `unified_review_result`
- `quality_preflight_completed`

修改回流字段：
- `role_modification_request`
- `task_modification_request`
- `requested_strategy`
- `retry_reason`

---

## 4. 为什么必须保留 quality_preflight

`quality_preflight` 价值：
1. 对高风险任务做最后静默兜底。
2. 将“用户确认”与“系统可执行性”分层处理。
3. 避免批量执行阶段才暴露结构性问题。

因此协议上应明确：
- `role_task_unified_review` 是人机决策层；
- `quality_preflight` 是自动质量层；
- 两层不能合并为单跳。

---

## 5. 前端对齐建议

1. 审批弹窗按钮文案明确为“确认并进入预检”。
2. 前端回传 action 必须结构化。
3. 回显“已进入预检”状态，避免用户误判系统卡住。

---

## 6. 防回归清单

- 禁止把 `approve` 路由改回 `batch_executor` 直连。
- 禁止把已废弃节点（`role_selection_quality_review` / `task_assignment_review`）重新挂回主链。
- 禁止未记录用户修改就进入执行。
