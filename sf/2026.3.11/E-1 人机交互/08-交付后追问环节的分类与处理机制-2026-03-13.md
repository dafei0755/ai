# 08-交付后追问环节的分类与处理机制-2026-03-20

> ⚠️ **2026-03-20 更新**：此文档中的"追问"机制已完全归并到大节点4"方案高参"中作为内部分流。本文保留作为历史参考和设计原理说明，实发现调度见 `../4 实施执行/01-专家角色体系与成果化主线-2026-03-11.md`。

> 本文解决一个核心问题：交付物完成后，用户的后续动作如何分类、如何处理、如何与已有系统衔接。

---

## 这篇文档要解决什么问题

交付物完成并不代表完全结束。

用户在看到成果后，几乎一定会产生新的动作需求。这些动作的性质差异极大：有的只是"再展开说说"，有的可能是"整个方向换掉"。

如果系统不区分这些动作的性质，就会出现两种极端：

- 所有追问都走轻量路径 → 大动作被当成小修补，结果质量崩塌
- 所有追问都走重启路径 → 小问题也要重跑全流程，用户体验极差

因此必须先把追问分类，再定义每类的处理机制。

---

## 四种追问类型

交付后用户的动作，按影响范围从小到大，分为四种：

### 第一种：局部深化

用户想在已有产出的基础上做延展、补充、启发。

不改变任何已有产出的结构，不触及任务书，不重做任何交付物。

典型场景：

- "叙事方案里的情绪锚点能不能再展开说说？"
- "工程可行性报告里的替代材料，能不能多给几个选项？"
- "这个概念方向很好，能不能帮我生成一张概念图？"
- "V4 的案例对标分析里提到了三个案例，能不能再补两个？"

本质：**在已有产出上做局部深化或补充。**

### 第二种：局部重做

用户对某个交付物或某些任务的结果不满意，需要重新做一版。

任务书的核心命题和边界不变，但某个交付物或某些任务需要局部重做。

典型场景：

- "叙事方案的整体方向没问题，但情绪节奏设计不太对，能不能重新做一版？"
- "工程可行性报告的结论我接受，但成本估算太粗了，能不能细化到分项？"
- "总体策略里的优先级排序我想调整一下，把体验优先改成成本优先"

本质：**不改方向，重做某个交付物或某些任务。**

### 第三种：方向变更

用户改变了任务书的核心前提，导致大部分产出需要重做。

典型场景：

- "之前说的是以李白的诗意为概念，现在想改成杜甫的诗意"
- "不做民宿了，改成联合办公"
- "预算从500万降到200万"（如果这导致整个方案需要推翻重来）
- "目标客群从年轻人改成老年人"

本质：**任务书的核心命题、取舍、甚至项目类型发生了变化。**

### 第四种：维度新增

用户不改变已有产出，但想新增一个任务书没有覆盖的交付物。

典型场景：

- "之前的方案都很好，但我现在还想加一个投资回报分析"
- "能不能再加一个政策合规性评估？"
- "帮我做一个品牌视觉方向的初步建议"

本质：**不改已有，新增一个交付物。**

## 每种追问的处理机制

### 第一种：局部深化

**处理方式**：直接在当前会话中完成，不需要回到任何流程节点。

**具体做法**：

- 识别用户追问指向的是哪个交付物、哪个任务、哪段产出
- 加载对应专家角色的配置
- 注入原始任务书上下文 + 该任务的已有产出
- 让专家在已有产出的基础上做延展
- 产出追加到对应交付物下

**不需要做的事**：

- 不需要重新跑需求分析
- 不需要重新调度批次
- 不需要重新做质量预检
- 不需要修改任务书

**对系统的要求**：

- 系统必须能定位"用户追问指向的是哪段产出"
- 系统必须能在不重启流程的情况下，单独调用某个专家角色
- 追加产出必须能被版本化管理（区分原始产出和追问产出）

### 第二种：局部重做

**处理方式**：回到执行阶段，重新执行受影响的任务，但不回到需求分析阶段。

**具体做法**：

- 识别用户要求重做的是哪个交付物或哪些任务
- 判断重做范围：只重做该任务，还是该任务的下游也需要重做
- 如果用户给了新的约束或偏好（比如"把体验优先改成成本优先"），更新执行蓝图中对应任务的输入
- 重新调度受影响的任务
- 产出替换原有版本，但保留历史版本

**不需要做的事**：

- 不需要重新跑需求分析（S1-S4）
- 不需要重新生成交付物清单
- 不需要重新做角色指派
- 不影响的交付物和任务不需要重做

**需要判断的关键问题**：

- 重做的任务是否有下游依赖？如果有，下游是否也需要重做？
- 用户给的新约束是否改变了任务书的核心取舍？如果是，应该升级为"方向变更"

**对系统的要求**：

- 系统必须能识别任务之间的依赖关系
- 系统必须能局部重新调度（只重做受影响的任务链）
- 系统必须支持产出的版本管理（新版本替换旧版本，但旧版本可追溯）

### 第三种：方向变更

**处理方式**：回到需求分析阶段，从变更点开始重新走流程。

**具体做法**：

- 识别变更的性质：是核心命题变了，还是关键取舍变了，还是项目类型变了
- 判断变更影响的范围：
  - 如果只是核心命题变了（比如从李白改成杜甫），可能从 S3（定下取舍）开始重新走
  - 如果项目类型变了（比如从民宿改成联合办公），可能需要从 S1（理解输入）开始重新走
  - 如果是边界约束变了（比如预算大幅缩减），可能从 S2（看清重点）开始重新走
- 重新走需求分析流程，产出新的任务书
- 基于新任务书重新执行

**关键原则**：

- 不是所有方向变更都需要从头开始
- 应该从"变更影响到的最早步骤"开始重新走
- 已有的、不受影响的分析结果应该被保留和复用

**需要判断的关键问题**：

- 变更影响到了需求分析的哪一步？
- 已有的哪些分析结果仍然有效？
- 已有的哪些交付物可以部分复用？

**对系统的要求**：

- 系统必须能判断"变更影响到了哪一步"
- 系统必须能从中间步骤重新启动需求分析流程
- 系统必须能保留和复用不受影响的分析结果
- 系统必须能标记"哪些产出是基于旧任务书的，哪些是基于新任务书的"

### 第四种：维度新增

**处理方式**：在已有任务书的基础上，新增一个交付物和对应的任务，然后执行。

**具体做法**：

- 识别用户要新增的维度是什么
- 判断这个维度是否在当前任务书的边界内：
  - 如果在边界内（比如任务书本来就涉及商业维度，只是没有单独做投资回报分析）→ 直接新增交付物和任务
  - 如果超出边界（比如任务书是纯设计项目，用户突然要求做法律合规评估）→ 需要先扩展任务书的边界
- 为新交付物生成任务分解和角色指派
- 执行新增的任务
- 新增产出追加到成果包中

**不需要做的事**：

- 不需要重做已有的交付物
- 不需要重新跑完整的需求分析流程

**需要判断的关键问题**：

- 新维度是否需要参考已有产出？如果需要，哪些产出是它的输入？
- 新维度是否与已有交付物存在冲突或依赖？
- 新维度是否需要新的专家角色（比如 V8 政策顾问、V9 产业链分析师）？

**对系统的要求**：

- 系统必须能在已有任务书的基础上增量新增交付物
- 系统必须能为新交付物独立调度任务执行
- 系统必须能把新增产出与已有产出整合到同一个成果包中

## 追问分类的判断机制

系统如何判断用户的追问属于哪一种？

### 判断流程

```
用户发起追问
  ↓
是否改变了任务书的核心命题、取舍或项目类型？
  → 是 → 第三种：方向变更
  → 否 ↓
是否要求新增一个任务书没有覆盖的交付物？
  → 是 → 第四种：维度新增
  → 否 ↓
是否要求重做某个交付物或某些任务？
  → 是 → 第二种：局部重做
  → 否 ↓
第一种：局部深化
```

### 判断的关键信号

**方向变更的信号**：

- 用户明确说"换一个方向"、"改成..."、"不要...了"
- 用户给出的新约束与任务书的核心取舍矛盾
- 用户提到的新目标与任务书的核心命题不兼容

**维度新增的信号**：

- 用户说"还想加一个..."、"能不能再做一个..."
- 用户提到的维度在当前交付物清单中不存在
- 用户提到的维度需要当前没有参与的专家角色

**局部重做的信号**：

- 用户说"这个不太对"、"能不能重新做一版"、"我想调整..."
- 用户指向的是某个具体的交付物或任务
- 用户给出了新的约束或偏好，但不改变核心方向

**局部深化的信号**：

- 用户说"能不能展开说说"、"再多给几个"、"这个很好，能不能深入一下"
- 用户指向的是某段具体的产出内容
- 用户没有表达不满，而是表达兴趣

### 模糊情况的处理

当系统无法确定追问属于哪一种时：

- 默认按较轻的类型处理（宁可先按局部深化处理，发现不够再升级）
- 如果处理过程中发现影响范围比预期大，自动升级到更重的类型
- 必要时向用户确认："你是想在现有方向上深化，还是想调整方向？"

## 四种追问与系统各层的关系

| 追问类型 | 是否回到需求分析 | 是否重新调度执行 | 是否修改任务书 | 是否需要人机交互 |
|---------|----------------|----------------|--------------|----------------|
| 局部深化 | 否 | 否 | 否 | 有（追问本身） |
| 局部重做 | 否 | 是（局部） | 否（或微调执行蓝图） | 有（确认重做范围） |
| 方向变更 | 是（从变更点开始） | 是（全部或大部分） | 是 | 有（重新走需求分析） |
| 维度新增 | 否（或轻量扩展） | 是（新增部分） | 是（新增交付物） | 有（确认新维度） |

## 版本管理与可追溯性

无论哪种追问，都必须保证可追溯性。

### 原则

1. 每次追问产生的变更都必须被记录
2. 原始产出不被覆盖，而是被新版本替代
3. 用户可以回看任何历史版本
4. 系统可以追溯"这段产出是基于哪个版本的任务书产生的"

### 版本标记建议

- `v1`：原始交付
- `v1.1`：局部深化（追加内容）
- `v2`：局部重做（替换某个交付物）
- `v3`：方向变更后的全新交付
- `v1 + D_new`：维度新增（原有不变，新增交付物）

## 最终结论

1. 交付后追问分四种：局部深化、局部重做、方向变更、维度新增
2. 每种追问的处理路径不同，不能一刀切
3. 系统必须能判断追问属于哪一种，模糊时默认按较轻类型处理
4. 所有追问产生的变更都必须可追溯
5. 方向变更是唯一需要回到需求分析阶段的追问类型
