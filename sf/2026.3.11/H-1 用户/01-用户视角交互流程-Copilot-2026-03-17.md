## 一、阅读说明

### 1.0 本文在全流程中的位置

本文是 `../../2026.3.22/A 步骤/1 项目步骤及流程.md` 所定义的项目态 4 大节点全流程，在**用户感知层**的对应展开。

```text
对话态（常驻底态）
  ↕  升级 / 回归

【大节点 1】用户输入          ←  T0 初始表达              ✓ 本文覆盖
  ↓
【大节点 2】门禁              ←  系统首诊（通常自动）       — 用户感知说明见下
  ↓
【大节点 3】设计任务书（S1-S5） ←  T1–T5                  ✓ 本文核心
  ↓
【大节点 4】方案高参          ←  作战室实况直播             ✎ 待补充
  ↓
  回归对话态                  ←  交付后解释 / 修订 / 派生   ✎ 待补充
```

**关于大节点 2（门禁）的用户感知**：用户提交 T0 后，系统在进入 T1 前完成首诊判断，正常情况自动放行，用户无需等待。仅当项目信息严重缺失或存在硬约束冲突时，系统会在 T0→T1 之间主动提示补充关键信息。无论哪种情况，用户感知到的都是"系统在处理"，而不是"进入了一个叫门禁的步骤"。

### 1.1 本文回答的问题

- 用户在整个协作过程中，会经历哪些"交互时刻"？
- 每个时刻：用户看到什么 → 需要做什么 → 可以不做吗 → 做了之后发生什么？
- 用户在什么时候可以叫停、纠偏、要求回退？
- 常见误区：用户容易在哪些节点产生困惑？

### 1.2 核心交互原则：系统先出牌

本系统不采用纯问答模式（系统问空白问题 → 用户从零构造答案）。原因：
- 开放问题认知负担高，用户容易发散或跑偏
- 用户不知道系统期望什么粒度的答案
- 错误修正需要重新叙述，而不是只改错的部分

**取而代之的模式：选择 → 编辑 → 补充**

| 步骤 | 含义 | 用户体验 |
|---|---|---|
| **选择** | 系统先给出预填的假设/候选项，用户从中选择最接近的 | 在已有选项里打勾 |
| **编辑** | 对不准确的字段/描述原地修改，不需要重写整段 | 改错别字，不是重写文章 |
| **补充** | 没有合适选项时，才打开自由输入框 | 在"其他"里填写 |
| **组合构造** | 对于融合型候选卡，从多个候选项中摘取属性，系统实时生成摘要句，用户确认摘要而非原始选项 | 调蘸料，不是选套餐 |

用户绝大多数情况下只需要**选择 + 微调**，极少情况才需要从头开始输入。

### 1.3 系统有两种工作状态

在进入完整项目协作之前，系统有两种工作状态，用户需要了解自己在哪种状态下：

| 状态 | 触发场景 | 系统人格 | 产出性质 |
|---|---|---|---|
| **日常陪伴模式** | 随口提问、灵感试探、案例参考、局部求助 | 专业但松弛，有问必答 | 草稿/建议，不冻结任何结论 |
| **项目深度模式** | 用户有明确项目需要系统性推进 | 严谨、深度、逼出判断 | 正式任务书，可供后续执行消费 |

**用户不需要手动切换**。系统会持续观察对话信号——当核心讨论基本清晰、主要矛盾已浮出、继续聊不会改变基本结构时，系统会主动提出软提示：

> *"我发现当前几个核心问题都已经浮露（例如选址高差、材料预算瓶颈等），建议我帮你先把框架钉在黑板上，确立一个正式基线，再往下推——这样后面不容易打空转。"*

> *（Prompt 正式版本以 `../../2026.3.22/A 步骤/1 项目步骤及流程.md` 为准；3.11 A/01 仅作历史参考。）*

用户可以同意、可以拒绝、也可以继续聊。系统不会强切。

### 1.4 卡片衔接原则：三段式气口

> **核心问题**：如果每张卡片只是"凭空冒出的题目"，哪怕每张单独都设计精良，整体体验仍然是被审讯——用户始终不知道自己在哪、为什么到这里、要去哪里。

每张卡片的生命周期不是「出现 → 操作 → 消失」，而是**三段式**：

```
[来由旁白]  →  [卡片本体]  →  [落点确认 + 等待态 + 气口区]
```

#### 第一段：来由旁白（卡片出现前）

**作用**：让卡片有"来处"，成为对话的自然延伸，而不是凭空冒出的表单。

**格式**：系统在卡片出现前先说一句话，逻辑结构固定为：

> 「我注意到 [你说了什么 / 出现了什么情况]，所以我需要确认一下 [这张卡的主题]。」

**各时刻示例**：

| 卡片 | 来由旁白 |
|---|---|
| T1 信息对齐卡 | "我先把你刚才表达里的基础信息站稳，再和你确认这次到底要什么、交付什么、按什么标准算完成。" |
| T2 梦幻团队组建卡 | "信息确认完了。在展开议题之前，我先把这轮解题思路推导出来；系统会据此生成工作地图，但不会额外弹出一个新步骤让你审批。你先看懂为什么这样拆题、为什么需要这些能力，再确认团队。" |
| T2 议程提案卡 | "团队确认后，我先把本轮议程摊出来。你先决定要讨论什么、先后顺序怎么排。" |
| T2 角色事实亮相卡 | "议程确定后，我让各角色围绕这些议题依次亮相事实卡。你先逐条确认依据，再进入裁决。" |
| T2 假设选择卡（首轮） | "项目方向不同，后续策略差别很大——我先猜一下你最核心的出发点，你来纠正。" |
| 缺口回收（嵌入式） | "若某条信息不明确，我会在当前议题当场补问并写回，不额外跳独立步骤。" |
| T2 假设选择卡（后续轮次） | "上一个维度确认了。还有一个问题我没把握，但对我后面的判断影响挺大——" |

**原则**：旁白不超过两句；不重述用户说过的原话；不卖关子，直接说"因为什么所以要问这个"。

#### 第二段：卡片本体（当前设计已有，补充操控感细节）

- 卡片右上角显示 **「第 X 个 / 共 Y 个」**（当前批次内的位置感）
- 多轮流程（如 T2 多维度）每张卡底部加一条**轻进度条**，不必知道总数，知道"快了还是远着呢"即可
- **「先跳过」和「返回改上一张」按钮始终可见**，不需要找；选择跳过不触发警告

#### 第三段：落点确认 + 等待态 + 气口区（卡片响应后）

**作用**：用户刚提交判断，系统首先回声，然后默认进入**等待态**——不自动弹出下一张卡。用户主动选择下一步去哪，而不是被流程推着走。

系统做两件事：

1. **回声（echo）**：一句话复述用户刚确认的判断——让用户感觉"被听见了"
2. **等待态 + 气口区**：呈现三个驻留/换向入口，用户自主选择

**等待态下的气口区**（与主动作区分开，常驻显示）：

| 气口 | 触发行为 | 系统响应 | 状态机 |
|---|---|---|---|
| 💬 **展开聊聊这个** | 想深入了解当前选择的含义、代价、案例 | 系统进入 L1，围绕当前卡片主题展开；卡片状态暂停 | 不变 |
| 🔄 **换个角度重新出牌** | 觉得这张卡的提问框架本身不合适 | 系统重新生成候选卡（换维度/换粒度），原卡作废 | 原卡退出，新卡入 |
| ❓ **你为什么这么判断** | 质疑系统的预填假设 | 系统展示推理来源，进入 L1 解释模式 | 不变 |

**气口对话结束后**，系统根据对话内容更新候选卡预填内容并重新出示，用户再执行标准动作。**只有用户主动点「继续下一步」，流程才向前推进。**

**回声格式参考**：

> 「记下了——[一句话复述判断]。」（之后系统进入等待态，气口区可见，不预设去向）

**各时刻回声示例**：

| 刚完成的卡 | 回声（之后进入等待态） |
|---|---|
| T1 信息对齐卡 | "好，基础信息已经站稳；在这个依据上，目的、交付物和成功标准也对齐了。" |
| T2 梦幻团队确认 | "好，已按解题思路推导确认团队。接下来我会基于同一张工作地图，把任务清单和顺序一次性排清。" |
| T2 议程确认后 | "好，就这几个切口。我们一个个来，你随时可以叫停或调整节奏。" |
| T2 第一切口深挖后 | "明白了，自住+体验是第一位的。" |
| 缺口回收（嵌入式） | "好，这条缺口已在当前议题补齐/标注，继续推进即可。" |
| T4 方向锁定 | "方向基线锁定了。" |

> **气口 vs 预告**：气口由用户主动触发；如果用户直接点「继续下一步」，系统再给出下一张卡的来由旁白；预告时机前移到"推进触发"时，而不是每次默认播出。

#### 行为层操控感保障

认知层面的控制感（三段旁白）之外，还需要**行为层**的控制感：

| 用户需求 | 设计响应 |
|---|---|
| 想暂停，不想被流程推着走 | 每张卡响应后系统进入**等待态**（默认态），气口区常驻显示；用户主动点「继续下一步」才推进，不存在自动弹出 |
| 想看全局、回看历史 | 右侧常驻**折叠式进度轨**，显示所有既往卡片的摘要，可展开回看；气口对话期间进度轨显示 `⏸ 探讨中` |
| 想改之前的判断 | 进度轨里每张历史卡都有「重新编辑」入口；触发时系统从该节点重新衔接，不需要重头开始 |
| 不知道"共几张卡" | 点「继续下一步」时系统随之给出预告，说明"还有 N 个"或"这是最后一个" |

> **一句话总结**：每张卡 = **「为什么问（来由）」+「问你什么（卡片本体）」+「你说了我听见了+你决定去哪（落点+等待态+气口区）」**。
> 用户的操控感来自始终知道自己在哪、为什么在这、以及**自己决定接下来去哪**——而不只是"有选项可以选"、也不是"被流程推着走"。

| 编号 | 时刻名称 | 用户动作类型 | 可否跳过 | 接下来发生什么 |

## 三、各时刻详述

### T0 · 初始表达

**这是什么**：用户用自己的语言描述项目，可以是一句话、一段文字，也可以上传附件或草图。

**用户看到什么**：一个空白对话框，没有模板、没有必填字段，系统不要求格式。

**用户需要做什么**：
- 用自然语言说出"我想做什么"
- 不需要写完整需求书，不需要提前整理思路
- 越真实、越直接越好，哪怕只有一句话

**示例**：
> "帮我做一个山地民宿，大概 200 平，预算 80 万以内，想做一个有山野感的轻奢风格。"

#### T0.1 任务洞察示例（防超纲/防漏项）

> 用户原话：
> 以丹麦家居品牌 HAY 的年轻、克制、功能主义气质为核心，为四川峨眉山七里坪山地民宿提供室内设计概念。项目需要兼顾山地自然景观、轻度度假人群需求与品牌辨识度。请提出完整设计框架，说明色彩系统、家具策略、空间尺度控制与公共社交空间的组织方式。可以不牵涉到工期/法规/施工维护限制。

**系统应提取的任务主旨（不可遗漏）**：
- 设计目标：形成“山地民宿室内概念方案”，不是施工图深化
- 品牌核心：HAY（年轻 / 克制 / 功能主义）
- 场景约束：山地自然景观 + 轻度度假人群 + 品牌辨识度三者并重
- 必须交付的四个模块：
  1. 色彩系统
  2. 家具策略
  3. 空间尺度控制
  4. 公共社交空间组织方式

**任务边界（防超纲）**：
- 本轮不展开：工期编排
- 本轮不展开：法规合规性论证
- 本轮不展开：施工维护与运维细则

**用户可见任务写法（推荐）**：
- 先一句话复述任务主旨（确保“你说的我听懂了”）
- 再按四个必交付模块逐项展开（避免遗漏）
- 最后用“本轮不涉及项”收口（避免超纲）

**完成后发生什么**：系统在后台默默理解、整理您说的内容，不打扰用户，准备输出对齐确认。

---

### T1 · 信息对齐卡

**这是什么**：系统完成初步理解后，先把**从用户原始表达里提取出的基础信息**站稳，再在此依据上与用户对齐这次项目的目的、交付物、成功判定、边界和优先级。T1 不再只是低成本改字段，而是建立后续全流程的共同基线。

**用户看到什么**：一张高规格信息对齐卡，按“已确定信息在前、待确认项在后”的顺序展开：

```
┌──────────────────────────────────────────────────────────────┐
│ 基础信息（从原始表达提取）                                    │
│ 项目类型   山地民宿室内概念                              ✏️  │
│ 场地位置   四川峨眉山七里坪                              ✏️  │
│ 品牌参照   HAY（年轻/克制/功能主义）                     ✏️  │
│ 目标人群   轻度度假 + 周末短住                            ✏️  │
│                                                              │
│ 高规格基线                                                    │
│ 项目目的   在山地自然感、HAY辨识度、经营可行性间建立平衡    ✏️ │
│ 交付物     色彩/家具/尺度/公区组织/风险清单                 ✏️ │
│ 成功判定   品牌可识别 / 场地不冲突 / 成本可落地             ✏️ │
│ 项目边界   本轮只做概念与策略，不做施工图与材料下单         ✏️ │
│ 优先级     先裁品牌纯粹度 vs 经营可行性                     ✏️ │
│                                                              │
│ 待确认项                                                      │
│ 建筑面积   ⚠️ 待确认                                     ✏️  │
│ 概算预算   ⚠️ 待确认                                     ✏️  │
│ 房量规模   ⚠️ 待确认                                     ✏️  │
│ 运营方式   ⚠️ 待确认                                     ✏️  │
│                                                              │
│  + 补充其他信息                               [确认全部并作为后续判断基线] │
└──────────────────────────────────────────────────────────────┘
```

- `✏️` — 点击可原地编辑该字段，不需要重写整段内容
- `⚠️ 待确认` — 用户尚未明确给出的重要信息，允许保留为空并后续补齐
- 先展示**基础信息**与**高规格基线**，把事实和已确定判断放前面；**待确认项**单列后置，作为收口与后续跟踪入口

**用户需要做什么**：
- 先看基础信息提取是否准确
- 再确认项目目的、交付物、成功标准、边界和优先级是否成立
- 对 `⚠️ 待确认` 项选择填写或保留为空
- 全部满意后点击「确认全部并作为后续判断基线」

**可以跳过吗**：可以直接确认，但系统仍会保留待确认项标记，并在后续 T2/T3 中继续回收这些信息。

**完成后发生什么**：这张卡被视为后续判断基线。后续梦幻团队组建、角色事实亮相、议题裁决和任务书编译都要围绕这张基线卡推进。

---

### T2 · 梦幻团队组建

**这是什么**：T1 之后，系统会先基于项目基线形成**解题思路**，再据此生成**工作地图**。这两层都在逻辑上独立存在，但不会被拆成新的对外主步骤。这里需要明确：**解题思路只与工作地图发生关系**，它不直接归属于 T2；T2 本身是**基于工作地图**来确认本轮团队如何编组。

> **原则前置**：没有调研就没有发言权。团队亮相不等于直接裁决，先给事实底图，再进入议题取舍。

> **为什么有这一步**：先把“为什么这样拆题”讲清楚，再确认“谁来承接这些工作”，避免“先有团队后找依据”。

**解题思路与工作地图的关系**：

- **解题思路**：T1 基线后的前置推导，回答“为什么这样拆题、为什么需要这些工作主线”；
- **工作地图**：由解题思路推导出的工作结构，是 T2 与 T3 的共同底盘；
- **T2 的职责**：基于工作地图确认团队如何编组；
- **T3 的职责**：基于同一张工作地图，将其展开为任务清单、依赖关系与执行门禁。

**由解题思路推导出的工作地图，必须覆盖的系统内置工作逻辑**：

| 工作主线 | 这轮要完成什么 | 在 T2 的落点 |
|---|---|---|
| A类：交付物驱动工作 | 围绕 T1 已确认交付物（色彩/家具/尺度/公区/风险）完成必要研究与判断 | 在 T2 中先定议程，再补事实，最后进入逐题裁决 |
| B类：洞察补位工作 | 补齐“项目类型必然涉及但用户未必点名”的关键洞察（经营/区域/标杆/风险） | 在 T2 中明确讨论边界，形成共同底图，再将需取舍项送入裁决 |

> **边界约束**：T2 只说明解题思路、工作结构与编组依据，不展开洞察细节；细节在后续研究与议题卡中逐条呈现。

**用户看到什么**：一张“解题思路推导 + 梦幻团队清单”组合卡：

```
┌──────────────────────────────────────────────────────────────────┐
│  T1.5 解题思路推导                                                │
│  这轮判断先覆盖四个维度：品牌转译 / 在地约束 / 用户行为 / 经营可行性 │
│  据此生成工作地图：                                               │
│  A类：交付物驱动工作（色彩/家具/尺度/公区/风险）                  │
│  B类：洞察补位工作（经营/区域/标杆/风险）                         │
│  编组原则：每个角色必须绑定明确工作责任                            │
│                                                                  │
│  梦幻团队清单（按角色展示工作内容与使命）                          │
│  [确认这支团队，进入基础研究]   [调整成员]                       │
└──────────────────────────────────────────────────────────────────┘
```

> **与总纲口径一致**：前台用“解题思路 → 工作地图 → 团队清单”做用户交互；后台仍是“一主两辅组织问题，多学科提供认知，知识底盘负责转译”。

**三区说明**：

| 区域 | 组成方式 | 用户操作 |
|---|---|---|
| **核心层**（3 人固定）| 每个项目必有，不依赖信号 | 不可移除，可展开查看详情 |
| **项目召集层**（5-10 人）| 基于项目信号自动匹配，每人标注触发来源 | 可调整/替换/移除，移除时系统提示影响 |
| **可选加入层**（深度感知）| 方向锁定后激活，感官/氛围类专家 | 现在可预选，T4 后自动激活 |

**专家卡展开详情**（点击每位专家可查看）：

- **「我对这个项目最在意的问题是：」**（第一人称，有立场，不是介绍词）
- 来源溯源：从项目信息的哪条被召集
- 不可替代性：能提出什么别人提不出的问题
- `scope_boundary`：不越界说的内容
- 贯穿责任：后面接住哪段工作
- 可能的张力对：与哪位专家有跨链分歧，从哪里开始

**用户需要做什么**：
- 先理解系统已经给出的解题思路推导与工作地图依据（无需逐条审批）
- 再查看梦幻团队清单，确认角色编组
- 点「确认这支团队，进入 T3 任务安排」

**可以跳过吗**：可以"快速通过"。即直接阅读解题思路后确认默认团队；系统会保留"已阅读/已确认"状态留痕。

**完成后发生什么**：`ExpertTeamPack` 冻结，团队成员列表写入会话记录；系统据同一张工作地图进入 **T3 · 任务安排**，并吸收 T2 已形成的关键判断与边界信息；经用户筛选保留的成员作用会在任务中落位体现；同时不根据团队反向制造任务。

---

### T3 · 任务安排

**这是什么**：T3 不是根据 T2 的团队名单来派活，而是以 **T1 项目基线 + 解题思路推导出的工作地图** 为主底盘，按**优先级、依赖关系、讨论边界**进行任务编排；同时吸收 T2 已形成的关键判断与边界信息，并把经用户筛选保留的 T2 成员作用转译为任务中的主责/联提/审校/门禁落位。T3 展示任务1-5（基线与方向锁定）+ 任务6-9（四专题独立定义）+ 任务10（方案高参入口准备）的完整任务清单，帮助你清楚知道"接下来要完成哪些工作、它们之间的关系是什么"。

**落实规则**：
- 经用户在 T2 筛选后保留的成员，在 T3 中必须有至少一处任务落位，避免“有人无任务”；
- 同一成员可跨任务承担不同责任，确保作用被充分发挥；
- 若任务编排出现 T2 名单外的新增能力需求，允许在 T3 补充能力位，不受 T2 名单限制；
- 成员是否保留、是否待激活、责任级别由用户判断并确认。

**机制说明**：T3 是"先合后分"节奏中的第一个**合点**——在进入 T4 分层推进前，先把工作地图翻译成任务清单，把所有工作框架梳理清楚。

**用户看到什么**：一张**任务清单卡**，展示十个任务的层级与逻辑关系：

```
┌─────────────────────────────────────────────────────────────┐
│ T3 任务安排（任务清单卡）                                     │
│                                                             │
│ ▼ 基线与方向锁定（任务1-5）                                  │
│   任务1 | 项目基础信息确认与议程预告                          │
│          前置依赖：无                                        │
│          入口：T1 信息对齐完成                               │

#### T4-2 · 专题策略确认

**这是什么**：基于已锁定的方向，系统将各个专题逐一整理为**可确认/编辑的策略面板**。每一张面板都明确**溯源到方向基线**，确保专题层逻辑不漂移。

**系统来由旁白**：
> 我按专题展开，每条都溯源到你刚锁定的方向。若某专题与方向产生矛盾，我会标红提醒，你可以选择改方向或改策略——但这个选择权在你手里，不会让我背后默默改。

> **这一步的作用**：不是让每个专题独立精妙，而是「确保所有专题一致地指向同一个战略方向」。倘若发现战术层逻辑与战略不符，立即回溯到 T4-1，不允许静默调和。这就是"**溯源**"与"**回退门禁**"机制的含义。

**用户看到什么**：一组专题面板，每个面板结构相同：

## §三 常见提问与设计说明

### Q2：可以直接跳过 T2，进入 T3 吗？为什么要讨论那么多前置议题？

**不可以**。直接跳过 T2 意味着系统只掌握了你初次描述的 30-40% 信息，后续方向卡片会建立在大量假设之上，质量和稳定性都会大幅下降，后期返工成本更高。T2 的意义是让方向选择建立在真实动机上，而非依赖设计师的想象。

### Q3：假设选择卡里的选项我都不满意，怎么办？

每张假设卡都有"以上都不准确 → 自己描述"选项，直接选它进入自由输入框即可。假设卡的选项是**降低你构造答案的心智负担**用的，不是强制选项。不满意就选"以上都不准确"——这是设计好的路径，不是失败状态。

### Q4：T3 分层后，为什么 T4 还要再选一次方向？分层不就是方向吗？

不一样。T3 分层是**确认哪些因素重要、优先级如何**；T4 方向选择是**对这些重要因素的价值判断**。分层是"这些都得考虑"，方向是"这些中间我选谁宗旨、谁是收益"。两者是不同维度的决策。

### Q5：方向明明定下来了，为什么后来 T4-2 还要回退？不是推翻之前的决定吗？

这是**正常且健康的信号**。方向讨论在某些信息缺失的情况下，有时无法预见到专题层面的物理限制。一旦专题展开发现方向层面有**根本矛盾**（而不只是细节问题），系统会主动触发正式回退，而不是在底下偷偷调整。这是保护你的基线不被静默篡改的机制。

### Q6：任务书中有几个"待确认项"，这是不是流程出问题了？

没有。待确认项是**刻意保留的透明化标记**，不是错误。有些项目本来就在当前阶段无法确认（比如场地勘测结果、甲方内部审批结论等），**强行填写反而会导致后续执行基于错误前提**。待确认项会被明确标出，供执行阶段跟进，比藏在任务书里更安全。

### Q7：任务书冻结之后还可以改吗？改了会怎样？

可以改，但入口唯一：**只能回到 T5 固化后的任务书成果页面修改**，不能在方案高参或追问对话里直接改题。改动代价如下：

| 改动层级 | 影响范围 | 需要回退 |
|---|---|---|
| 文字表述（不含实质意义） | 仅该表述处 | 无 |
| 某专题的具体参数 | 该专题内部 | 回到 T4-2 重走该专题 |
| 战略方向或核心取舍 | 所有专题 | 回到 T4-1 重选方向 |

系统不允许在不回退讨论的情况下偷偷修改底层结论。

## §四 设计原则与约束

### 卡片设计原则（§1.4 详述）

**每张卡片三段式设计**：

1. **来由旁白**（为什么系统要出这张卡）
   - 透明地说明判断逻辑，而不是直接给答案
   - 让用户理解"系统为什么这样问"

2. **本体交互**（卡片本身的输入/选择）
   - 提供多入口（单选 / 融合 / 自由描述）
   - 系统预填假设，用户只做 Confirm/Edit/Add

3. **落点确认+等待态**（交互完成后什么发生）
   - 系统给出回声（让用户知道自己的选择被记录了）
   - 进入等待态，不自动推进
   - 用户主动触发「继续下一步」

### 信息呈现分层（§1.2 详述）

T2 流程中，信息被分为**四个层级**：

- **A 层 - 事实依据层**（直接呈现，不要求判断）
  - 基础数据、竞品分析、技术约束等纯资料内容
  - 用户可快速浏览或深入查看来源

- **B 层 - 议题交互层**（需用户确认/讨论）
  - 从事实推导出的关键切口与张力
  - 用户需参与定义本轮讨论边界

- **C 层 - 过程作用层**（全程门禁）
  - 风险控制官、时间管理、版本治理等过程类角色
  - 这些角色全程参与但不在议程中单列

- **D 层 - 启发层**（可选）
  - 超出当前议程边界但有价值的跨界思想
  - 默认折叠，用户可自主转化为议题或保留

### 缺口回收机制（§1.1 详述）

缺口信息**不再作为独立步骤出现**。处理方式随场景而异：

- **T2 中发现的缺口** → 当场澄清或标记"待确认"
- **T3 中发现的缺口** → 填写状态标签并持续跟踪
- **T4(1/2) 中发现的缺口** → 当前上下文就地回收，不强制回跳上一阶段
- **T5 中发现的缺口** → 标记"待执行验证"，并在用户发起「继续」后进入方案高参阶段跟踪

使用道德：缺口是正常的，透明标注化比隐瞒更安全。
