## 一、协议定位

### 1.1 这是什么

本协议是**系统级交互范式的定义文档**，规定：

- 对话与卡片各自负责什么（功能分工，不是主辅关系）
- 系统在任何阶段向用户出示内容时必须遵循的结构
- 用户可以对系统出示内容执行的标准动作集合
- 卡片从生成到冻结的完整生命周期
- 何时必须保留自然对话，何时必须切入卡片

### 1.2 这不是什么

| 容易混淆的概念 | 说明 |
|---|---|
| **不是 UI 规范** | 本文定义机制，不规定视觉样式（颜色、圆角、动效）|
| **不是交互流程文档** | 具体 T0-T5 的流程见 01 文档 |
| **不是 LLM Prompt 模板** | 本文约束行为，具体 Prompt 见 `../3 需求分析/` |
| **不是某阶段专属协议** | 本协议对全部阶段（需求分析/专题研究/任务书编制）生效 |
| **不是聊天机器人设计规范** | 系统有明确的"对象编译"目标，不是会话纪念馆 |

### 1.3 一句话核心定性

> **对话负责流动，卡片负责定锚；系统先组织局面，用户后校准判断；每次推进都必须产生可确认对象。**

## 二、核心定性：对话流动，卡片定锚

### 2.1 为什么不是"卡片为主，对话为辅"

"主辅关系"的提法会导致工程上的误判：

- 容易把所有环节都强制卡片化，破坏对话的流动感和松弛感
- 用户在探索期（尚未明确目标时）需要自由叙述，卡片会形成压迫感
- 对话本身有不可替代的功能（见第六节）

正确理解是**功能分工**：

| 层 | 负责什么 | 评判标准 |
|---|---|---|
| **对话** | 流动——让信息和认知自然涌现 | 是否打开了新的可能性？|
| **卡片** | 定锚——把已经基本清晰的内容从对话流中"钉住" | 是否消除了模糊性？|

对话的结果**不会自动产生效力**；只有通过卡片或动作将对话内容"编译"为可确认对象，才能被后续系统消费。

### 2.2 角色反转：系统先出牌

传统问答模式：系统出空白提示 → 用户从零构造答案。
本协议的模式：系统出预填假设 → 用户校准（确认/修改/补充/推迟）。

**为什么这个方向是对的：**

- 认知负担从用户侧转移至系统侧（用户评价比用户创作容易 10 倍）
- 错误修正从"重新叙述"变为"改错的那一格"
- 系统预填强迫系统自己先完成推理，而不是把推理甩给用户
- 用户的跳过（无动作）等价于默认接受，加速推进

### 2.3 "每次推进都必须产生可确认对象"的含义

- 系统不能只输出一段文字分析然后继续聊
- 每次对话推进（特别是在协作层 L2 激活时），必须产生至少一个**卡片/草稿对象**
- 用户必须对该对象做出明确动作（Confirm / Edit / Add / Defer），才能进入下一步
- 这是保证后续系统可以消费人机协作结论的根本约束

## 三、三层结构

系统的交互行为由三个层次组成，**自下而上逐层收紧**：

```
┌─────────────────────────────────────────────────────────────┐
│                  L3 冻结层（对象编译层）                    │
│  冻结对象（任务书字段、方向基线、策略条目）                  │
│  只读，有来源标签，可申请回退                               │
├─────────────────────────────────────────────────────────────┤
│                  L2 协作层（卡片引导层）                    │
│  卡片（草稿卡→候选卡→确认卡→冻结）                         │
│  系统先出牌，用户执行4个标准动作                            │
├─────────────────────────────────────────────────────────────┤
│                  L1 流动层（自然对话层）                    │
│  自然语言流动，系统监听语义信号                              │
│  当检测到"可定锚内容"时，切入 L2                           │
└─────────────────────────────────────────────────────────────┘
```

### 3.1 L1 流动层（自然对话层）

**作用**：信息自然涌现、认知探索、情感共鸣、建立信任。

**特征**：
- 系统以陪伴者姿态回应，不要求输出格式
- 任何话题均可，不设门禁
- 系统在后台持续监听**可定锚信号**（见 3.1.1）

**触发退出条件**：检测到下列可定锚信号时，系统提出切入 L2 的轻软提示：

> *"刚才你说的 XXX 我觉得挺具体了，我帮你先把这一条钉住，可以吗？"*

用户可接受（进入 L2），也可拒绝或无视（继续在 L1）。

#### 3.1.1 可定锚信号示例

| 信号类型 | 典型话语 | 检测关键词 |
|---|---|---|
| 项目基本事实陈述完毕 | "这是南京的一个住宅项目，300㎡左右" | 地点+类型+规模同时出现 |
| 目标已从模糊变为具体 | "我希望让老年人也能独立用这个系统" | 明确服务对象+明确功能目标 |
| 矛盾点已被用户承认 | "预算确实卡得很死，但我还是想用好材料" | 限制条件+但是+期望 |
| 用户主动要求定案 | "你觉得这个思路可以吗？帮我整理一下" | 确认/整理/总结等动词 |

### 3.2 L2 协作层（卡片引导层）

**作用**：将模糊信息逐步收敛为明确的可确认对象。

**特征**：
- 系统出示卡片（预填假设 + 候选选项）
- 用户执行4个标准动作（见第五节）
- 卡片在状态机中流转（见第四节）
- 整组卡片的进度状态对用户可见（✅/❓/⚠️）

**层内规则**：
1. 系统不发出空白问题（不问"你的目标是什么？"而是出示"目标假设卡：[系统推断的目标选项]"）
2. 每张卡片对应一个**具体命题**，不会是宽泛主题
3. 用户对卡片的无动作（如直接点击"继续"）等价于默认接受当前内容

**T2 目标动机澄清阶段的 L2 内部两子层**：

在 T2 阶段，L2 协作层内部分为两个连续子层，不可跳跃：

| 子层 | 出示对象 | 用户动作 | 退出条件 |
|---|---|---|---|
| **L2-a 议程提案层** | 议程提案卡（三类来源：用户明示型 / 张力推导型 / 行业补位型）| 确认保留 / 删减 / 排序 / 添加自定义切口 | 用户点击"确认本轮切口" |
| **L2-b 逐切口深挖层** | 每个切口对应的假设卡（可选项 / 预填推断）| Confirm / Edit / Add / Defer | 本轮所有切口的假设卡全部完成（确认或推迟） |

> L2-a 是对"接下来讨论哪些切口"的议程共识，L2-b 才是对每个切口判断方向的假设验证。两者不可合并——议程不透明时，用户会带着"为什么要讨论这个"的疑惑进入卡片，阻力加大。

**T1.5 梦幻团队组建的 L2 专属子机制**：

T1.5 是一个独立 L2 卡片单元，发生在 T1（信息对齐）完成后、T2-a（议程提案）之前。它不是新的推理管道，而是将现有武器（B4 使用者身份识别器 / C1 跨领域视角激活器 / C2 多方利益梳理器）的隐性运算结果，以“解题思路 + 专家团队”的用户可见结构前置出示。

在协议上，**工作地图为系统内置对象**（由 S1 维护），不再作为独立审批卡对用户逐条出示；但解题思路必须显式覆盖：
- A类交付物驱动工作
- B类洞察补位工作
- 团队编组与工作责任绑定依据

| 子机制 | 出示对象 | 用户动作 | 退出条件 |
|---|---|---|---|
| **T1.5 解题与编组卡** | 解题思路卡（含系统内置工作地图摘要）+ 团队亮相卡（核心层 3 人必有 + 项目召集层动态匹配 + 可选加入层深度感知） | 阅读解题思路 / 浏览专家详情 / 调整成员 / 确认 | 用户确认团队，`ExpertTeamPack` 冻结 |

专家在 T1.5 阶段的职责是**明确工作责任并提名议题**（后续 T2-a 每条议程标注 `proposed_by_roles`），不在此阶段直接输出内容答案。专家以人格开口（第一人称有立场发言）从 T2-b 开始。

> **架构说明**：T1.5 不新增业务推理节点——它是 S1 副产物（系统内置工作地图 + `ExpertTeamPack`）的显性化呈现。工作地图在后台维护并在解题思路中摘要展示；团队清单是该内置工作地图的编组结果。

**触发退出条件**：
- 当一组卡片全部进入"确认"或"推迟"状态，触发进入 L3 编译

### 3.3 L3 冻结层（对象编译层）

**作用**：将已确认的卡片内容编译为可供后续系统消费的正式结构体。

**特征**：
- 内容只读（不可在 L3 内直接编辑）
- 每个字段带来源标签（来自哪张卡片 / 哪轮对话）
- 用户可以申请回退到 L2 重新讨论某个字段
- 回退代价需明确告知（下游哪些依赖此字段的内容会重新评估）

**三层转换汇总**：

| 转换 | 触发条件 | 谁决定 |
|---|---|---|
| L1 → L2 | 可定锚信号 + 用户接受 | 系统提议，用户确认 |
| L2 → L3 | 一组卡片全部完成 | 系统自动或用户主动编译 |
| L3 → L2（回退）| 用户申请回退某字段 | 用户申请，系统评估代价告知 |

### 3.4 专家人格发言约束规范

梦幻团队成员在 T1.5 之后随流程持续在场，但在不同节点的出场方式受以下约束：

**阶段性职责边界**：

| 节点 | 专家职责 | 出场形式 |
|---|---|---|
| T1.5 | 绑定工作责任并提名议题（不直接输出内容答案）| 解题与编组卡中的自我定位说明 |
| T2-b | 第一人称人格开口，引导本切口假设卡 | 「【专家称谓 · 角度说明】」旁白 + 开场白（≤4句） |
| T4 | 为方向候选背书（主导专家签名）| 卡片标注 `[主导：X，背书：Y]` |
| T5 | 主导对应专题策略卡，以其语气呈现 | 策略卡标注提出者，可展开专家协作意见 |
| T5 | 联署任务书（≤2句，有异议则明确表达）| 签署区独立栏，异议附注不阻断冻结 |

**人格发言三要素约束**（每位专家发言必须符合）：

1. **关注维度**：只从本专家的视角切口发言，不越 `scope_boundary` 说其他领域的话
2. **语气特征**：与其他专家有明显差异，可辨识——不同专家在同一节点的发言不能听起来是同一个系统在说话
3. **惯用质疑方式**：与其关注维度强相关——品牌专家质疑「借了形没借逻辑」，经营代理人质疑「回收周期拉长多久」，用户研究专家质疑「这个词在实际行为里意味着什么」

**scope_boundary 执行规则**：
- 专家发言一旦越出 `scope_boundary`，系统标注 `⚠️ 越界建议` 并提示用户是否采纳
- 用户可强制接受越界建议，但系统不默认支持
- 越界不影响专家其他发言内容的有效性

**专家全流程记忆传承**：
- 每位专家从 T1.5 开始到 T5 有连续记忆——T2 阶段的判断对 T5 可见，无需重新介绍项目背景
- 当同一专家在不同节点出场，语气和关注维度保持一致（不因节点切换而人格漂移）

> **参考文档**：专家角色完整定义（人格三要素 + 四方向问题 + scope_boundary）见 `05-专家角色库与动态匹配规则-Copilot-2026-03-19.md`。

### 3.5 四层分工协作与过程作用层触发规范（v1.4）

## 四、卡片状态机

每张卡片从生成到冻结，经历以下状态：

```
[生成] → 草稿卡 → 候选卡 → 确认卡 → 冻结对象
                                    ↖ 回退卡（从冻结申请重开）
```

### 4.1 各状态定义

| 状态 | 触发条件 | 用户可执行动作 | 显示样式提示 |
|---|---|---|---|
| **草稿卡** | 系统内部生成，尚未出示给用户 | — | 不出示 |
| **候选卡** | 系统出示给用户，等待响应 | Confirm / Edit / Add / Defer | 卡片高亮，等待态 |
| **确认卡** | 用户执行 Confirm 或 Edit 后保存 | 申请回退 | 卡片收起，✅标记 |
| **冻结对象** | 整组卡片完成后进入 L3 编译 | 申请回退 | 任务书字段，来源标签 |
| **回退卡** | 用户从冻结对象申请重开讨论 | Edit / Add / Confirm | ⚠️标记，带历史版本对比 |

### 4.2 状态转换规则

1. **草稿卡不会直接到确认卡**：系统不允许在用户没有参与的情况下完成一张卡片
2. **Defer（推迟）不改变状态**：卡片仍为候选卡，标注"暂无结论"，但不阻塞其他卡片推进
3. **Edit 触发局部重校验**：编辑某字段后，系统检查是否产生新的依赖矛盾，如有则生成子卡片
4. **回退传播评估**：任何冻结对象的回退，系统必须列出"受影响的下游对象"，经用户确认后才开始回退

### 4.3 Defer（推迟）字段的处理

被推迟的字段：
- 不阻塞一组卡片的整体"完成"判断（推迟也算完成某张卡片的处理）
- 在 L3 冻结对象中标注为 `[待定]`
- 系统在合适时机（通常是下一个相关阶段入口）重新提出候选卡

## 四（附）、候选卡三种判决模型

LLM 节点生成候选卡时，必须在卡片结构体中标注 `card_type` 字段，前端组件按类型渲染不同交互形态。

| 判决模型 | 本质 | 适用场景 | Confirm 的对象 |
|---|---|---|---|
| **排他型** | 互斥选择，只能锚定一个 | 红线 / 禁区 / 非此即彼边界 / "最想避免"类维度 | 单一选项或用户自填内容 |
| **融合型** | 从多个候选中摘取属性，嫁接为新组合 | 方向 / 风格 / 价值取向 / 策略 / 客群画像 | 系统生成的融合摘要句（Composite Candidate），不是原始选项 |
| **自由描述型** | 现有候选框架不适用，用户从零描述 | 系统候选项完全不覆盖用户真实情况时的兜底路径 | 用户输入经系统整理后的摘要句 |

### 4a.1 融合型候选卡的工作流

融合是 Confirm 之前的**构造过程**，不破坏状态机：

```
用户勾选来源属性  →  系统实时生成融合摘要  →  用户编辑/确认摘要
      ↑（调整/追加）                                    ↓
                                        Confirm（冻结摘要句，进入确认态）
```

**关键规则**：
- Confirm 的对象是**融合摘要句**（自然语言），不是原始权重或选项组合
- 融合摘要在 L3 冻结对象中保留多来源标签，如 `source_ref: ["A.核心取向", "B.运营逻辑"]`
- 融合过程的中间状态（勾选/调整）不写入状态机，只有 Confirm 后的摘要句才进入确认态
- **T2 议程阶段的额外要求**：融合摘要的 `source_ref` 中须同时记录该切口的来源分类（`agenda_source: "user_explicit" | "tension_derived" | "industry_supplement"`），供下游 S2 冻结对象溯源使用

### 4a.2 排他型候选卡的约束

排他型卡不提供融合工作台。如果用户需要同时设立多条排他型边界（如两条红线并存），系统自动生成多张独立的排他型候选卡，而不是合并为一张融合型卡。

### 4a.3 卡片类型的预设与切换

- 系统按语义推断卡片类型（"你最想避免什么"→ 排他型；"核心价值取向"→ 融合型）
- 用户可在卡片出示时切换类型（如把融合型改为"我就选一个"的排他型）
- 类型切换记录保存在卡片结构体中，供回退时参考

## 五、4个标准用户动作

在整个 L2 协作层，用户对每张候选卡只能执行以下4个动作：

| 动作 | 含义 | 后续 | 快捷
|---|---|---|---|
| ✅ **Confirm** | 系统预填的内容基本准确，接受；融合型卡中，Confirm 的对象是**融合摘要句**（Composite Candidate），而非原始选项 | 卡片进入确认态 | 点击"确认" |
| ✏️ **Edit** | 内容有偏差，原地修改某字段 | 修改后保存 → 确认态 | 直接点击字段 |
| ➕ **Add** | 系统遗漏了某条内容，追加补充 | 追加后保存 → 确认态（含补充项）| 点击"补充" |
| ⏸ **Defer** | 暂时没有把握，先跳过这张卡 | 卡片标注"暂无结论" | 点击"先跳过" |

### 5.1 为什么只允许这4个动作

- **清晰的信号边界**：系统接收到用户信号后，有明确的下一步处理路径
- **防止动作歧义**：自由聊天可以继续在 L1，L2 内部必须产生一个判决动作
- **Defer 比"不回答"更安全**：明确的推迟比用户沉默或绕开回答更诚实，下游可感知

### 5.2 用户可以在任何时候"打断"进入 L1

上述4个动作是 L2 协作层的规范，但用户**随时可以打断**，回到自由对话：

> 用户说"等等，我先聊一下背景" → 系统暂停卡片，回到 L1 对话模式

打断后，系统保留已完成卡片的状态，等待用户重新进入 L2。

### 5.3 候选卡气口规则

候选卡执行标准动作（Confirm / Edit / Add / Defer）后，系统默认进入**等待态**——不自动弹出下一张候选卡。每张候选卡的气口区（与主动作区分开显示）必须提供以下入口：

| 气口 | 触发行为 | 系统响应 | 状态机影响 |
|---|---|---|---|
| 💬 **展开聊聊这个** | 用户想深入了解当前选择的含义、代价、案例 | 系统进入 L1，围绕当前卡片主题展开；卡片状态暂停 | 无（保持当前状态） |
| 🔄 **换个角度重新出牌** | 用户认为这张卡的提问框架本身不合适 | 系统重新生成候选卡（换维度/换粒度），原卡作废 | 原卡退出，新候选卡进入草稿→候选流程 |
| ❓ **你为什么这么判断** | 用户质疑系统的预填假设 | 系统展示 `source_ref` 推理来源，进入 L1 解释模式（对应 P1 原则） | 无（保持当前状态） |

**规则**：
- 气口触发后系统进入 L1；L1 对话结束后，系统根据对话内容**更新候选卡预填内容并重新出示**，用户再执行标准动作
- 气口区与主动作区（Confirm / Edit / Add / Defer）**分区显示**，不混用
- 进度轨在气口对话期间显示 **`⏸ 探讨中`**，以区别于 `❓ 待处理`
- **只有用户主动点「继续下一步」，流程才向前推进**；「继续下一步」在主动作区，而非气口区

## 六、自然对话的精确定位

以下5种场景**必须**保留自然对话（不可强制切入卡片）：

| 场景 | 说明 | 强制卡片的错误示例 |
|---|---|---|
| **1. 认知探索期** | 用户尚未确定方向，需要在叙述中发现自己要什么 | 用户刚说"我想做个项目"，立刻出现"项目名称"填写框 |
| **2. 情感/价值陈述** | 用户表达期望、担忧、审美偏好的深层原因 | 用户说"我爸妈等了二十年才住上这套房子"，系统立刻出"关键词提取卡" |
| **3. 矛盾澄清期** | 用户表述中存在自相矛盾，需要进一步探讨再定型 | 在矛盾未解决前出示选择卡，相当于掩盖了矛盾 |
| **4. 意外信息出现** | 用户在流程中揭示了改变全局的新信息 | 新信息出现时不重新对话，直接更新字段，可能导致用户未意识到已产生结构性变化 |
| **5. 系统需要解释推理** | 系统提出某假设时，用户问"你为什么这么认为" | 出示一个推理结果卡而不是用语言说明推理过程 |

## 七、6条协作原则

以下6条原则由以下5个基础问题推导而来：
> Q1: 用户凭什么相信系统的预填假设？
> Q2: 用户跳过后悔了怎么办？
> Q3: 系统如何知道何时该出卡片？
> Q4: 卡片内容冲突时谁仲裁？
> Q5: 如何保证"卡片收紧"而不是"卡片越来越多"？

---

**P1：系统的预填假设必须可见推理依据**

每张候选卡出示时，必须附带推理依据（来自哪句话、哪项信息）。不允许无来源的假设。

> ✅ 正确："基于你刚才说的'预算卡死'，我推断约束等级为'高'，请确认"
> ❌ 错误：直接出示"约束等级：高"字段，不说明来源

---

**P2：回退通道必须始终可达**

用户在任何 L2 或 L3 状态，都可以回退到已确认的内容重新讨论。回退后系统必须：
① 明确告知影响范围（什么会重新评估）
② 保留历史版本供对比
③ 不允许系统单方面拒绝回退请求

---

**P3：推迟的代价必须被合理估计**

某字段被 Defer 后，下游依赖此字段的卡片可以**按默认假设先行推进**；但系统必须标注"此处基于推迟字段 X 的默认假设，若后续变更将触发重新评估"。

---

**P4：卡片数量有明确上限约束**

每轮 L2 协作最多产生 N 张候选卡（建议 N ≤ 7）。超出范围时，系统必须做**优先级筛选**，只出示本轮最关键的卡片，其余进入"下一轮候选池"。不允许用户在一次 L2 中面对超过 7 张开放卡片。

---

**P5：用户的整体进度始终可见**

在任何 L2 协作过程中，用户能看到本阶段所有卡片的完成状态（✅ 已确认 / ❓ 待处理 / ⚠️ 已推迟 / 🔒 已冻结）。不允许系统悄悄新增卡片而不告知全局进度变化。

---

**P6：卡片冻结的时机必须告知**

进入 L3 编译（冻结）之前，系统必须出示一个**整体确认提示**，明确告知"以下内容将被冻结，后续修改需要回退流程"，用户主动确认后才执行冻结。不允许静默冻结。

---

## 八、2个风险边界

### 8.1 过度卡片化（Too Card-Heavy）

**症状**：
- 任何对话都立刻触发卡片，用户无法自然叙述
- 卡片数量爆炸（一次 L2 出现 15+ 张卡片）
- 用户感觉被审讯而不是被协助

**防线**：
- 严格遵守 L1 流动层的不可替代场景（见第六节）
- 每轮 L2 卡片数量上限 ≤ 7（P4）
- 卡片触发必须基于"可定锚信号"而不是"收到任何输入"

**测试信号**：如果用户开始用"好的好的我知道了能不能先不管这个"来回应卡片，说明已过度卡片化。

### 8.2 过度自由对话化（Too Chat-Heavy）

**症状**：
- 大量讨论但什么都没有被"钉住"
- 用户以为讨论过的内容已经定案，但系统没有冻结任何对象
- 下游节点消费需求信息时发现"一切皆模糊"

**防线**：
- L1 层的"可定锚信号"监听必须始终激活
- 每次对话轮次超过阈值（如 6 轮）而未产生任何候选卡，系统主动提出切换
- 任务书编制阶段强制要求 L3 冻结对象数量达标才能进入下一阶段

**测试信号**：如果用户在后期说"我们之前聊的时候不是说好了…但现在怎么又变了"，说明缺少有效的卡片定锚。

## 九、对T1-T5的统一语法约束

以下约束对所有阶段（T1信息对齐 / T2梦幻团队组建 / T3任务安排 / T4任务实施 / T5任务书审阅与确认）生效：

| 约束项 | 规定 | 违规示例 |
|---|---|---|
| **卡片触发方式** | 系统主动出示候选卡，不发空白问题 | "请描述你的项目目标：________" |
| **假设来源标注** | 每个预填字段必须有来源指向（"基于你说的…"）| 无来源的字段值 |
| **卡片判决类型** | LLM 输出候选卡时必须携带 `card_type`（排他/融合/自由描述），前端按类型渲染对应交互形态 | 候选卡无类型标注，或前端将融合型卡按单选渲染 |
| **进度可见性** | 本轮所有卡片状态实时可见 | 用户不知道还有几张卡待处理 |
| **动作集合** | 仅 Confirm / Edit / Add / Defer；融合型卡中 Confirm 的对象是 Composite Candidate 摘要句，不是原始选项 | 出现"同意吗Y/N"等不在集合内的动作；强制用户在融合型卡中选原始选项 |
| **冻结前确认** | 进入 L3 前必须出示整体确认提示 | 静默写入任务书字段 |
| **回退代价告知** | 回退前必须列出受影响的下游对象 | 直接跳回上一步不说明影响 |
| **Defer 可见标注** | 推迟字段在冻结对象中标注 `[待定]` | 推迟字段被静默填充默认值 |

## 十、与系统其他层的关系

### 10.1 与 LLM 节点层的关系

本协议**约束** LLM 节点的**输出行为**，不约束其内部推理方式。

| 约束来源 | 对 LLM 的要求 |
|---|---|
| P1（假设来源） | LLM 每次生成预填字段时，必须在 Prompt 输出中携带 `source_ref` 字段 |
| L2（候选卡出示） | LLM 推理完成后不直接输出结论，而是输出"候选卡结构体"交由前端渲染 |
| P4（卡片数量） | LLM 节点的输出 schema 限制单次最多生成 7 张候选卡 |

### 10.2 与状态机层的关系

卡片状态机（草稿→候选→确认→冻结→回退）在应用层维护，不依赖 LLM 判断。

- 状态只能被**用户动作**或**系统自动触发条件**推进
- LLM 不能直接将卡片推入"确认"状态
- 冻结操作由应用层状态机执行，触发 L3 编译流程

### 10.3 与前端组件层的关系

本协议定义**组件行为约束**，不定义视觉设计：

| 组件类型 | 对应协议要求 |
|---|---|
| 候选卡片组件 | 必须渲染4个动作按钮（Confirm/Edit/Add/Defer）|
| 进度状态条 | 必须实时反映本轮所有卡片的 ✅/❓/⚠️/🔒 状态 |
| 冻结对象展示组件 | 每个字段必须渲染来源标签，回退按钮始终可见 |
| 回退确认弹窗 | 必须展示受影响的下游依赖对象列表，用户确认后才回退 |

### 10.4 与人格表达层的关系

系统的"人格"（如松弛感、幽默、专业度）在 L1 流动层自由表达；进入 L2 协作层后，人格仍可在对话引导语中体现，但**不能以人格为由跳过或软化协议约束**。

例如：系统可以用友好的语气说"这一条我帮你先猜了，你看准不准？"，但仍然必须出示候选卡 + 来源标注，不能只说一段话就当作"达成共识"。
