## 零、机制定位与命名

正式命名为：

**对话态实时引导机制（Real-time Guidance Loop）**

它在整个系统中的层级定位：

- 属于 **对话态** 的前台编排层，不属于项目态
- 是对话引擎（`conversation_engine.py`）的内置能力模块，而非独立节点
- 在项目态 S1-S5 执行期间不以高频卡片形式出现，仅在用户穿插闲聊时轻量响应

一句话：

**它负责把"发散聊天"变成"被温和组织的方案讨论"，并将用户的每次选择沉淀为结构化草稿对象。**

## 一、关键冲突排查：`interrupt()` vs REST 附 card

参考1 主张用 LangGraph 的 `interrupt()` 实现引导卡片暂停。本文明确不采纳此技术路径，原因如下：

| 维度 | `interrupt()` 方案 | REST response 附 `guidance_card` 方案 |
|---|---|---|
| 设计意图 | 为项目态长链路执行中途暂停而设计（图已运行到某节点，等待用户输入后 resume） | 对话态"一消息一响应"本身已是暂停，REST 返回前端即意味着等待 |
| 对话态适配性 | 场景错配：对话态不存在"图已运行到一半"的状态 | 天然匹配：对话引擎处理完一条消息即结束，前端渲染卡片等待下一条消息 |
| 基础设施代价 | 需要 checkpointer 持久化挂起状态，与项目态复杂机制耦合 | 无额外基础设施，在现有 REST response 中加字段 |
| 语义清晰度 | resume payload 携带 card_id + 选项，语义清晰 | 前端下一条消息携带 `in_response_to_card_id + selected_option_id`，语义等同 |

**结论**：参考1 的**目标**（结构化选择、精确消费用户回答，沉淀草稿对象）完全采纳；**技术路径**不采纳。对话态使用 REST 附 `guidance_card` 实现相同语义，代价最小。

## 二、核心设计原则

### 草稿对象的两条写入路径

| 路径 | 触发方式 | 写入结果 | `user_confirmed` |
|---|---|---|---|
| **路径 A（主路径）** | 用户在引导卡上做出选择/确认 | 对应草稿对象（见映射表）| `True` |
| **路径 B（被动兜底）** | LLM 从自由对话中识别到冲突或意图 | `ConflictPack`（冲突包）| `False`（待确认） |

路径 A 产出的草稿对象是可直接升级编译的信任数据。路径 B 产出的是推断数据，只有通过后续卡片被用户确认后，才能升格为 `user_confirmed=True`。

**这条分层是保证升级编译质量的根基。**

### 最小干预原则

- 每次只推一张卡，不连发
- 用户有未响应的卡片时，不推新卡
- 用户可跳过任何卡片，跳过行为记入 `GuidanceTrace`（`user_action=skip`）
- 纯知识问答场景不推卡（无草稿沉淀价值）

## 三、4 种引导卡类型

### 3.1 归纳卡（Mirror Card）

**用途**：镜像系统当前理解，让用户快速校正"你是不是理解偏了"。

**触发时机**：
- 用户单轮表达密度过高，系统若不归纳易产生理解偏差
- 升级前夜（接近升级阈值，做最后一次收束）

**结构**：
- 标题：`我先归纳一下当前理解`
- 内容：当前 3-5 个核心判断
- 操作：`基本对` / `补充一点` / `不对，我重说`

**写入草稿对象**：用户选"基本对"→ `ConsensusPack`（`user_confirmed=True`）

---

### 3.2 选择卡（Fork Card）

**用途**：将已出现的方向分叉显性化，避免用户在未看见选择成本的情况下盲试。

**触发时机**：
- 对话中已出现 ≥2 个互斥方向
- 继续泛聊不会自动收敛

**结构**：
- 标题：`这里其实有几个方向，你更想先压哪一个？`
- 选项：2-4 个，**每个选项必须附后果说明**（`consequence_hint`）
- 包含"其他，我来说"兜底入口

**示例后果说明**：
- `高端隐居路线` → 「客单价高，但客群窄，营销链路更长」
- `年轻社交路线` → 「引流快，但对运营持续投入要求高」

**写入草稿对象**：用户选中后 → `DirectionCandidatePack`（选中项，`user_confirmed=True`）；原有 `ConflictPack` 中对应分叉条目标记为已解决

---

### 3.3 补充卡（Gap Card）

**用途**：系统发现缺一个关键前提才有资格继续判断时，精准补缺。

**触发时机**：
- 预算、面积、地形、客群、工期等硬字段缺失
- 继续推演会导致后续所有结论失真

**结构**：
- 标题：`还差一个关键前提，我补齐后判断会稳很多`
- 明确说明缺哪一项及"为什么这里卡住"
- 给出 2-3 个常见参考值 + 自由输入入口
- 底部强制显示自由输入框

**制度约束**：一次只补最关键的一口，不允许连发多张补充卡。

**写入草稿对象**：用户输入后 → `BoundaryDraft`

---

### 3.4 设想卡（Hypothesis Card）

**用途**：用户处于探索期、不适合强行收束时，系统主动抛出值得讨论的高价值设想。

**触发时机**：
- 用户只给了模糊审美偏好，尚无结构性需求
- 系统判断此时更适合启发，而非逼确认

**结构**：
- 标题：`我先给你抛几个值得试探的设想`
- 内容：每个设想附简短逻辑
- 操作：`展开这个` / `都不像，我补一个新的`

**写入草稿对象**：用户确认某设想 → `IntentSeed` 或 `ProblemFrameDraft`（含 `inferred=False` 标记）

## 四、卡片类型与草稿对象映射表

| 卡片类型 | 触发信号 | 用户行为 | 写入草稿对象 | `user_confirmed` |
|---|---|---|---|---|
| 归纳卡（Mirror） | 信息密度过高 / 升级前夜 | 确认理解 | `ConsensusPack` | `True` |
| 归纳卡（Mirror） | 同上 | 补充/修正 | `ConsensusPack`（修正版） | `True` |
| 选择卡（Fork） | 方向分叉 ≥2 | 选择方向 | `DirectionCandidatePack`（选中项） | `True` |
| 选择卡（Fork） | 同上 | 选择方向 | `ConflictPack`（对应分叉标记已解决） | — |
| 补充卡（Gap） | 关键前提缺失 | 填入数值/描述 | `BoundaryDraft` | `True` |
| 设想卡（Hypothesis） | 探索期有启发空间 | 确认设想 | `IntentSeed` / `ProblemFrameDraft` | `True` |
| 任意类型 | — | 跳过 | 无写入，`GuidanceTrace.user_action=skip` | — |

**LLM 自由识别（无卡片）**：仅写入 `ConflictPack`（`user_confirmed=False`，待后续卡片确认）

---

## 五、触发优先级

当多个触发信号同时满足时，按以下优先级只发一张卡：

```
gap（关键前提缺失）
  ↓
fork（方向分叉显性化）
  ↓
mirror（信息密度过高 / 升级前夜）
  ↓
hypothesis（探索期有启发空间）
```

逻辑依据：缺少硬前提时，连选方向都是无效的；方向未定时，做归纳也是不稳定的。

## 六、新增领域对象定义

以下对象建议在 `intelligent_project_analyzer/core/domain_objects.py` 中新增。

### `GuidanceCardType`（枚举）

```python
class GuidanceCardType(str, Enum):
    MIRROR = "mirror"        # 归纳卡
    FORK = "fork"            # 选择卡
    GAP = "gap"              # 补充卡
    HYPOTHESIS = "hypothesis"  # 设想卡
```

### `GuidanceCardOption`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `str` | 选项唯一 ID |
| `label` | `str` | 选项标签（前台显示文字） |
| `description` | `str` | 选项说明 |
| `consequence_hint` | `Optional[str]` | 后果提示（Fork 卡必填） |
| `recommended` | `bool` | 是否为推荐项 |

### `GuidanceCard`

| 字段 | 类型 | 说明 |
|---|---|---|
| `card_id` | `str` | 卡片唯一 ID（UUID） |
| `card_type` | `GuidanceCardType` | 卡片类型 |
| `prompt_text` | `str` | 展示给用户的标题/提示语 |
| `options` | `List[GuidanceCardOption]` | 选项列表（2-4个） |
| `allow_freetext` | `bool` | 是否显示自由输入框（Gap 卡默认 True） |
| `source_turns` | `List[str]` | 来源轮次 ID（用于溯源） |
| `rationale` | `str` | 系统生成此卡的内部原因（不展示给用户） |

### `GuidanceTrace`

| 字段 | 类型 | 说明 |
|---|---|---|
| `trace_id` | `str` | 留痕记录 ID |
| `card_id` | `str` | 关联的卡片 ID |
| `user_action` | `Literal["select", "skip", "rewrite", "supplement"]` | 用户行为 |
| `captured_signal` | `str` | 用户选择的具体内容 |
| `promoted_to_draft_object` | `Optional[str]` | 写入了哪类草稿对象（`user_action=select` 时填写） |

## 九、对话引擎执行流程

```text
接收用户消息
  ↓
检查 in_response_to_card_id
  ├─ 存在 → 执行 _process_card_response()
  │           按 card_type 写入对应草稿对象
  │           创建 GuidanceTrace 留痕
  │           清空 pending_guidance_card
  │           不发新卡（本轮响应已处理卡片，直接走正常对话流）
  └─ 不存在 → 走正常对话流
                ↓
              生成 LLM 回复
                ↓
              执行 _maybe_generate_guidance_card()
                检查是否已有 pending_guidance_card（有则不发新卡）
                按触发优先级检查信号
                若触发 → 生成 GuidanceCard，写入 pending_guidance_card
                若不触发 → guidance_card=null
                ↓
              返回 response（含 guidance_card 字段）
```

## 十、前台交互规格

### 卡片渲染位置

内嵌于助手消息气泡正下方，不弹 Modal，不打断输入焦点。

### 卡片状态

| 状态 | 视觉表现 |
|---|---|
| 待响应 | 完整卡片，选项可点击 |
| 已选 | 折叠为"已选：xxx"灰色摘要行，不可二次点击 |
| 已跳过（用户发新消息） | 折叠为"已跳过"灰色摘要行 |

### 用户交互流

1. 用户点击选项 → 前端构造下一条消息文本（`label` + `context_hint`），附 `in_response_to_card_id` + `selected_option_id`，调用 `handleSendMessage`
2. 用户点击"跳过，直接说" → 卡片标记 skipped，`handleSendMessage` 发送用户自由输入（不携带 card_id）
3. 用户直接在输入框输入并发送 → 等同于跳过当前卡片（前端自动将卡片折叠为 skipped 状态）

### 禁止的交互模式

- 同时显示多张卡片
- 强制用户必须响应卡片才能继续发消息
- 在 Fork 卡选项中不提供后果说明

## 十一、制度边界

以下规则不可破坏：

1. **不强制**：用户可跳过任何卡片，直接继续自由输入
2. **不代替正式冻结**：卡片选择只写入草稿对象，未升级项目态前不视为正式任务书结论
3. **不滥问**：一次只解决一个最关键问题，优先级见第五节
4. **不做无后果的选择题**：Fork 卡每个选项必须有 `consequence_hint`
5. **不假装全懂**：LLM 推断的信息（路径 B）写入 `ConflictPack` 并标记 `user_confirmed=False`，不直接进入升级编译

---

## 十二、验证标准

| 验证项 | 预期行为 |
|---|---|
| 发含方向分叉的消息 | response 含 `fork` 卡，选项有后果说明 |
| 发缺预算信息的消息 | response 含 `gap` 卡（优先级高于 fork） |
| 点击 fork 卡选项 | `DirectionCandidatePack` 中出现新条目，`user_confirmed=True` |
| 发纯知识问答 | `guidance_card=null`，前端不渲染卡片 |
| 跳过卡片后发新消息 | `GuidanceTrace` 记录 `user_action=skip`，草稿对象无写入 |
| 检查升级编译产物 | 只有卡片确认的草稿对象进入 `RawBriefPacket`，LLM 推断项保持 `user_confirmed=False` |

## 十三、与现有草稿对象的完整关系

```text
用户自然表达
  ↓
对话引擎抽取线索
  │
  ├─ LLM 识别到冲突/意图
  │     → 写入 ConflictPack（user_confirmed=False）
  │
  └─ 触发引导卡
        GuidanceCard 展示给用户
          ↓
        用户选择（GuidanceTrace 留痕）
          ↓
        按卡片类型写入对应草稿对象（user_confirmed=True）
          └─ Mirror → ConsensusPack
          └─ Fork   → DirectionCandidatePack + ConflictPack（标记已解）
          └─ Gap    → BoundaryDraft
          └─ Hypothesis → IntentSeed / ProblemFrameDraft
          ↓
        升级编译（_compile_upgrade_packet）
          ↓
        RawBriefPacket（只含 user_confirmed=True 的字段）
```
