## 一、机制定位

### 1.1 梦幻团队的本质

梦幻团队**不是人物扮演集合**，而是**项目化认知视角矩阵**：

- 每位专家代表一种**真实的专业知识边界**，在边界内发言，不越界
- 在知识边界约束下，以**有辨识度的人格和立场**开口——品牌专家和运营研究员听起来应该截然不同
- 专家不是"来回答问题的"，而是先"决定哪些问题值得上桌"

> **设计原则**：角色 = 真实专业视角边界 + 有辨识度的表达人格。人格是视角的表达形式，不是脱离视角的角色扮演。

### 1.2 梦幻团队解决什么问题

| 原有问题 | 梦幻团队如何解决 |
|---|---|
| 议程由"匿名系统"提出，用户不知道是谁在说话 | 每条议程有具名提出者，知识责任透明 |
| 单一设计师视角覆盖所有维度，存在系统性盲区 | 多视角链式组织，盲区显性化为张力议题 |
| 建议没有来源，难以质疑和追溯 | 每条建议标注提出者和提案理由，可追溯 |
| 执行阶段角色重新发明，与分析阶段断裂 | 专家全程持续，按责任链接棒执行 |

### 1.3 与现有武器体系的关系

T1.5 不新增业务推理逻辑，而是将原有武器的隐性运算结果显性化为一个用户可见的前置对象：

| 原有武器 | 在梦幻团队中的对应 |
|---|---|
| B4 使用者身份识别器 | 识别"谁在使用这个空间" → 触发用户研究专家 |
| C1 跨领域视角激活器 | 识别"还有哪些视角必须进来" → 触发专题圈角色 |
| C2 多方利益梳理器 | 识别"谁在驱动这个项目" → 触发运营/投资视角 |

`ExpertTeamPack` = B4 + C1 + C2 的隐性运算结果，以用户可见的团队形式前置出示。

### 1.4 系统内置工作地图原则（v1.11）

T1.5 的正确顺序不是“先出团队，再解释为什么”，而是：

```text
T1 交付物与目标确认
  ↓
工作地图（两类基础工作）
  ├─ A类：交付物驱动工作（用户明确提出）
  └─ B类：洞察亮相工作（项目类型必然涉及，用户未必点名）
  ↓
能力维度/方法/学科映射
  ↓
梦幻团队编组（团队作为结果出现）
```

**A类（交付物驱动工作）**用于回答“为了交付这次承诺的结果，需要做哪些研究与判断”；
**B类（洞察亮相工作）**用于回答“即使用户没提，这类项目也必须先补齐哪些底层洞察”。

> 结论：团队不是起点，而是工作地图编译结果。T1.5 前台统一口径为“**解题思路（含系统内置工作地图）→团队清单**”。

## 二、角色库三层结构

### 2.1 核心层（每个项目必有，3 个固定角色）

核心层是不依赖项目信号、每个室内/空间设计项目都必须存在的视角：

| 角色称谓（必须项目化命名）| 知识边界 | 不越界说的内容 |
|---|---|---|
| 空间设计总统筹（专注度假/民宿/山地类型，能整合跨学科团队） | 空间命题组织、功能动线、所有专题的最终编译 | 不做用户心理判断、不做品牌策略判断 |
| 用户研究专家（行为模式/使用旅程/个体与群体） | 使用者的行为、情绪、动机、群体关系 | 不做设计执行判断、不做运营经济判断 |
| 实施边界顾问（造价/工期/结构/法规/材料耐候） | 物理可行性的边界压缩 | 不做风格判断、不做用户研究 |

> **核心层职责**：这 3 个角色从 T1.5 开始到 T6 全程在场，任何专题策略卡都需要其中至少 1 位参与把关。

### 2.2 动态扩展层（基于项目信号匹配，5-10 个角色）

系统根据 T1 确认后的项目基础信息包，按信号自动匹配，见 §三匹配算法。

动态扩展层是 T2-b/T2-c 议题裁决阶段的**核心提名者**——大多数议程切口来自这层专家的视角碰撞。

动态扩展层角色举例：

| 角色类别 | 触发信号 | 角色称谓（项目化命名） |
|---|---|---|
| 品牌研究 | 有知名品牌参照 | HAY 品牌语义与产品策略研究员 |
| 文化背景 | 品牌研究专家触发（链式） | 丹麦及北欧功能主义生活方式研究员 |
| 在地场地 | 有具体地域场地 | [地域] 山地生活方式研究员 |
| 建筑景观 | 改造项目或山地/水边场地 | 建筑-景观室内接口设计顾问 |
| 民宿运营 | 建筑类型为民宿 | [地域] 民宿经营与投资视角代理人 |
| 度假产品 | 目标人群为度假者 | 轻度假旅程与情绪体验研究员 |
| 社交心理 | 有公共社交空间议题 | 空间社交心理与群体行为研究员 |
| 材料工艺 | 有本地材料/在地工艺议题 | [地域] 本地工艺与材料顾问 |

### 2.3 深度感知层（用户选择加入，最多 6 个角色）

深度感知层不主导第一轮议程，在方向锁定后（T4）激活，聚焦感官/氛围/体验细化：

| 角色称谓 | 激活条件 | 接手工作 |
|---|---|---|
| 山地民宿声景编辑 | 公共区氛围已被确认为核心议题 | 声音环境策划、公共区时间轴音景 |
| 山地民宿香氛专家 | 品牌辨识度需通过感官链路表达 | 嗅觉锚点设计、场景记忆建立 |
| 自然光感顾问 | 山地光线/开窗策略为关键变量 | 光线情绪研究、开窗-遮阳策略 |
| 服务剧本与前场体验策划 | 用户旅程「抵达-停留-离开」需精细设计 | 服务触点剧本、前场体验序列 |

### 2.4 洞察亮相层（系统自动补位，关键洞察先前台表态）

> **v1.7 调整**
> 由“默认后台隐藏”升级为“关键洞察先亮相、先表态”。用于补齐“用户未提及但项目类型必然涉及”的关键视角，并在 T1.5 后先给出前台共识底图。

**定位**：
- 显性席位解决“用户能直接感知和讨论的问题”；
- 洞察亮相层解决“项目必然存在但用户未显式提出的问题”。
- 在工作地图中，洞察亮相层属于 **B类基础工作（主动补位型）**：不是替代交付物工作，而是为交付物建立成立条件与风险底图。

**触发源（非用户点名）**：
- 项目类型（经营性空间 / 民宿 / 改造）
- 商业模式（盈利目标 / 回收周期约束）
- 品牌参照（如 HAY）
- 区域语境（如七里坪山地）
- 执行与合规风险

**默认洞察群（示例）**：

| 洞察群 | 典型隐藏席位 | 主要输出 |
|---|---|---|
| 经营与市场 | 竞品研究、区域市场、差异化定位、ROI结构分析 | 市场成立性与商业成立性雷达 |
| 区域与场地 | 区域风土、游客画像、气候耐候、供应链可达性 | 场地特异性与落地约束雷达 |
| 标杆与突破 | 同类标杆对照、传统方法论对照、跨界方法引入 | 方案突破度与同质化风险雷达 |
| 风险总控 | 风险分析员（总控）+ 分维接口专家 | 失败路径预警与避坑清单 |

**输出形态（强约束）**：
- 先输出「一句话立场」+ 结构化洞察卡，不输出长篇专家发言：
  `risk_or_opportunity / impact_scope / confidence / need_to_escalate / recommended_owner`
- 仍通过单一中介读取：`DesignTaskBook + 当前节点上下文（必要时附会话级执行编排）`

**运行分流（先亮相，再分工）**：
1. **T1.5 后先亮相**：关键洞察以“先表态”方式进入前台，形成共同底图；
2. **T2-a 角色事实亮相**：把洞察编译为 `Research Brief Pack`（非裁决任务，逐条轻量确认）；
3. **T2-b/T2-c 议题裁决**：仅将“需要取舍”的问题送入议程讨论。

**与交付物驱动工作的边界**：
- 交付物驱动工作（A类）回答“这次要交什么、怎么交”；
- 洞察亮相工作（B类）回答“这次即使不问也必须先知道什么”；
- 两类工作在 T2-a 汇合为事实底图，在 T2-b/T2-c 汇合为可裁决议题。

**升前台阈值**：
1. 高影响（影响方向冻结或核心商业变量）
2. 高风险（合规/预算/工期/品牌边界）
3. 与已冻结方向存在冲突
4. 用户追问命中该洞察域

## 三、信号匹配算法

### 3.1 匹配规则（T1 确认后后台运行，用户不感知）

```
项目信号（来自 T1 基础信息包）→ 触发角色

[品牌参照]
  有知名品牌参照（如 HAY、Muji、Aesop）
    → 品牌语义研究专家（对应品牌）
    → [链式触发] 品牌所属文化背景研究员

[场地类型]
  山地 / 坡地         → 山地生活方式研究员 + 建筑-景观接口顾问
  城市历史街区改造     → 城市文脉与历史建筑改造顾问
  水边 / 湖边         → 滨水场地与微气候顾问
  农村 / 乡村田野      → 乡土材料与乡村生活方式研究员

[建筑类型]
  民宿               → 轻度假旅程研究员 + 民宿经营代理人
  社区商业            → 社区运营与城市微公共空间顾问
  办公               → 工作行为模式与组织心理顾问

[目标人群]
  度假/旅游人群       → 轻度假旅程研究员（与民宿信号去重）
  亲子家庭            → 儿童行为发展与安全空间顾问
  老年人              → 无障碍设计与老龄化行为顾问

[核心议题]
  公共社交空间        → 空间社交心理与群体行为研究员
  色彩系统            → 色彩情绪与光环境系统专家
  家具策略            → 家具软装系统统筹专家（FF&E）
  本地材料/在地性      → [地域] 本地工艺与材料顾问
```

### 3.2 去重规则

多条信号触发同一角色时：
- 该角色**只出现一次**，不重复
- 在角色卡片的「[来源：...]」标签中，**列出所有触发该角色的信号**
- 例：`轻度假旅程研究员` 被「建筑类型: 民宿」和「人群: 度假者」同时触发 → 出现一次，标注两个来源

### 3.3 链式触发规则

某些角色在被触发后，自动触发链条上的下一位专家：

```
HAY 品牌语义研究专家
  └→ [链式] 丹麦及北欧功能主义生活方式研究员
       └→ [链式] 功能主义跨语境转译顾问（可选，按项目复杂度决定是否激活）

山地生活方式研究员
  └→ [链式] 本地工艺与材料顾问（如有改造保留当地建材）

用户研究专家（核心层，必有）
  └→ [按需] 空间社交心理与群体行为研究员（当有明确社交空间议题时激活）
```

链式触发的角色在 T1.5 卡片上标注 `[来源：链式触发，上游：XXX专家]`。

## 四、专家链结构（知识对话关系）

专家不以平行列表组织，而以「链」组织——每条链有方向，链间有跨链张力。

### 4.1 链结构示例（HAY × 峨眉山七里坪民宿）

```
链 A · 品牌文化链
  HAY 品牌语义与产品策略研究员
    └→ 丹麦及北欧功能主义生活方式研究员
         └→ 功能主义跨语境转译顾问

链 B · 在地知识链
  建筑-景观室内接口设计顾问
    └→ 七里坪山地民宿经营与投资视角代理人
         └→ 峨眉山山地生活方式研究员
              └→ 本地竹石材料与工艺顾问

链 C · 设计执行链
  山地度假民宿改造室内设计总统筹（主导，核心层）
    ├→ 色彩情绪与光环境系统专家
    └→ 家具软装系统统筹专家

链 D · 用户体验链
  轻度假旅程与情绪体验研究员
    └→ 用户研究专家（行为/社交/独处，核心层）
         └→ 空间社交心理与群体行为研究员

链 E · 感官策展链（深度感知层，T4 后激活）
  山地民宿声景编辑
  山地民宿香氛专家
  自然光感顾问
  服务剧本与前场体验策划
```

### 4.2 跨链张力对（必须显性化为张力议题）

| 张力对 | 张力内容 | 对后续判断的阻断影响 |
|---|---|---|
| 链A品牌专家 × 链B经营代理人 | 品牌纯粹度 vs 商业可行性 | 不先裁决：家具策略、材料选型无法定锚 |
| 链A功能主义顾问 × 链D用户研究专家 | 去除"冗余" vs 度假情绪价值 | 不先裁决：公共区留白与织物配置方向相反 |
| 链C室内设计师 × 链B材料顾问 | 进口品形式精度 vs 本地工艺边界 | 不先裁决：家具分层策略无法建立 |

## 五、T1.5 解题与团队清单卡——前台交互规范

### 5.1 组合卡片结构

T1.5 呈现给用户的是一张“解题思路 + 团队清单”组合卡：

```
┌──────────────────────────────────────────────────────────────────┐
│  梦幻团队组建                                                     │
│  解题思路（含系统内置工作地图）：                                 │
│  - A类：交付物驱动工作（围绕本轮交付物）                          │
│  - B类：洞察补位工作（项目类型必然涉及）                          │
│  - 编组原则：每个角色必须绑定明确工作责任                          │
│                                                                  │
│  这个项目不是一个视角能完整回答的                                 │
│  我已为这次项目召集了以下专家——你来决定谁留下，有没有漏掉的       │
│                                                                  │
│ ── 核心成员（每个项目必有，不可移除）──────────────────────────  │
│  ✓  空间设计总统筹                                                │
│     专注度假/民宿/山地场景，整合所有专题，最终编译空间命题        │
│  ✓  用户研究专家                                                  │
│     洞察使用者的行为、情绪、群体关系与空间期待                    │
│  ✓  实施边界顾问                                                  │
│     从造价/工期/结构/法规/材料耐候角度压缩可行区间                │
```

### 5.4 入席资格核验（1+1+1 规则）

> **v1.3 新增**

| 要素 | 要求 | 验证方式 |
|---|---|---|
| **1 议程** | 至少能提出 1 条独立主提的议程切口（sole_proposer） | §7.0 视角扫描预运行验证 |
| **1 判断** | 至少在 1 个后续判断节点（T2-b/T4/T5）有明确可见意见 | 按参与档位（§8.5）分档承诺 |
| **1 责任** | 至少绑定 1 个执行责任位（主责/协作/审阅）或追问责任位 | `scope_boundary` 与任务骨架的交叉覆盖 |

**三档处理策略**：

| 核验结果 | 处理方式 | T1.5 卡片呈现 |
|---|---|---|
| ✅ 三项均满足 | 进入前台 ExpertTeamPack | 第一区（核心）或第二区（特别召集） |
| ⚠️ 条件满足后可履行 | 进入「可选加入」区 | 第三区，标注激活条件 |
| ❌ 当前项目阶段无法履行 | 降格为后台候补知识源（D 档） | 不出现在 T1.5 卡片 |

> **典型判断示例**：声景编辑在项目尚未进入氛围深化阶段时，视角扫描难以产出实质切口 → 第三区，标注「方向锁定后激活」。建筑-景观接口顾问在既有建筑改造项目中，接口问题必然产生 → 三项均满足，进第二区。

## 六、专家人格设计规范

### 6.1 人格三要素

每位专家的发言必须建立在三要素约束下：

| 要素 | 定义 | 约束 |
|---|---|---|
| **关注维度** | 这个专家只从什么角度看问题 | 发言不越出 `scope_boundary` |
| **语气特征** | 如何开口——句式、节奏、倾向 | 与其他专家有明显差异，可辨识 |
| **惯用质疑方式** | 遇到假设时从哪个方向打问号 | 与「关注维度」强相关 |

### 6.2 四方向问题（专家卡内在逻辑必须能回答）

1. **为什么他必须在场**（不可替代性）
2. **从用户 brief 的哪条信息被召集**（来源溯源）
3. **他能提出什么别人提不出来的问题**（独占视角）
4. **他后面接住哪段工作**（贯穿责任）

### 6.3 人格示例（HAY 案例，3 位专家）

---

**HAY 品牌语义与产品策略研究员**

> 「我需要提醒的是——HAY 的美学不是'北欧简约'的同义词，它有非常清晰的功能优先原则。任何把 HAY 当风格板来用的提案，我都会提出异议。这个项目最大的危险是：用 HAY 的样子，丢掉 HAY 的逻辑。」

- 关注维度：HAY 的产品语法与品牌识别机制
- 语气特征：直接、有专业边界感、对"风格化"高度警惕
- 惯用质疑：「这个设计借的是 HAY 的哪个逻辑，还是只借了外形？」
- scope_boundary：不评价山地运营的商业可行性

---

**七里坪山地民宿经营与投资视角代理人**

> 「设计漂不漂亮不是我关心的。我关心的是：这套设计能不能支撑一个有复购率的产品，让运营方有理由继续投。七里坪的竞争格局今天已经很成熟，差异化必须能被算进商业模型里。」

- 关注维度：入住率、坪效、运维摩擦、回本周期
- 语气特征：务实、直接追问代价和回报、不回避商业约束
- 惯用质疑：「这个决策会让回收周期拉长多久？」
- scope_boundary：不做色彩或材质的美学判断

---

**用户研究专家**

> 「"轻度度假"这个词被严重欠定义。到底是身体上的轻、社交上的轻，还是决策上的轻？三种"轻"对应完全不同的空间行为。如果不先澄清，后面所有关于动线和社交区的假设都是在赌。」

- 关注维度：使用者的行为模式、情绪边界、群体与个体关系
- 语气特征：从现象打问号、拒绝接受模糊词汇、要求操作性定义
- 惯用质疑：「这个词在实际空间行为里意味着什么？」
- scope_boundary：不做设计执行判断，不做运营经济判断

## 七、议程项五字段结构（T2-b/T2-c 使用）

T1.5 团队确认后，系统先进入 T2-a 角色事实亮相（Research Brief Pack）；随后在 T2-b/T2-c 议题裁决中，每条切口由团队中的对应专家提名，切口结构升级为**六字段**（v1.2 新增 `sole_proposer` / `co_proposers` 拆分）：

```
① 议题名称
② agenda_source：内容来源（用户明示型 / 张力推导型 / 行业补位型）
③ sole_proposer：独立主提人（唯一一位；每位入场专家必须是至少 1 条议题的独立主提人）← 新增
④ co_proposers：联合参与者（0..n 位；额外背书或共同观察，不替代独立主提的覆盖要求）← 新增
⑤ nomination_reason：提案理由（不谈这条会影响哪里的判断；必须来自 sole_proposer 的专属视角）
⑥ impact_scope：影响范围（色彩/动线/运营/品牌/客群/边界哪一层）
```

### 7.0 议程生成：专家视角扫描模型（v1.3 重构）

> **原机制**：系统推导议程 → 标注专家为提出者 → 零沉默检查兜底
> **升级机制**：专家视角扫描 → 专家主动提案（expert-first）→ 系统汇总去重排序 → 零沉默兜底

**专家视角扫描（Expert Perspective Scan）**：T1.5 确认后、T2-b/T2-c 正式展示前（在 T2-a 事实亮相之后），系统为每位入场专家运行一次扫描：

```
每位专家回答同一个问题：
「基于目前的项目信息，我最担心被忽略的问题是什么？」
```

扫描约束：
- 答案必须来自该专家的 `scope_boundary` 内
- 必须是"若不上桌讨论，会导致具体判断错位"的维度（不接受泛描述）
- 答案自动编译为一条议程切口，该专家自动成为 `sole_proposer`

**汇总规则（系统自动）**：

```
汇总所有专家视角扫描输出
  ↓
去重：core_intent 重合度 > 80% 的议题合并
  ├─ 合并时：原 sole_proposer 保留，另一位转为 co_proposer
  └─ 实现层差异不合并（角度不同即使结论相近也保留）
  ↓
排序：张力议题（⚡ conflict-flagged）置顶；其余按 impact_scope 广度排序
  ↓
输出：T2-b 议程列表（每条议题有明确 sole_proposer，来自专家自身视角）
```

**示例（HAY 案例，部分专家扫描输出）**：

```
HAY 品牌语义与产品策略研究员扫描结果：
  「HAY 的落地方式是精准移植还是转译——不先定，
   后面所有材料和家具决策都会跑偏。」
  → 议题：「HAY 气质在山地语境的落地方式」
    sole_proposer: HAY 品牌研究专家

七里坪山地民宿经营与投资视角代理人扫描结果：
  「进口品比例和本地工艺的边界——这直接影响回收周期，
   但设计师通常不会主动提这个。」
  → 议题：「品牌纯粹度 vs 经营可行性」（⚡ 张力议题）
    sole_proposer: 经营代理人

用户研究专家扫描结果：
  「"轻度度假"这个词没有被定义——社交上的轻、
   身体上的轻、决策上的轻，三种轻对应完全不同的空间行为。」
  → 议题：「轻度度假的行为定义」
    sole_proposer: 用户研究专家
```

### 7.1 零沉默原则（Silence-Zero Rule）——兜底验证层

> **v1.3 调整定位**：§7.0 专家视角扫描为主机制，本规则降格为兜底验证层。正常情况下视角扫描天然满足 `sole_proposer` 覆盖；仅当某专家的扫描输出在去重合并中被完全消失时，才触发补生成流程。

**规则**：每位确认入场的专家，必须作为 `sole_proposer` 出现在至少 1 条议程切口中。

**执行机制**：
```
系统生成初版议程
  ↓
零沉默检查：遍历 ExpertTeamPack，检查每位专家是否有 sole_proposer 记录
  ├─ 已覆盖 → 通过
  └─ 未覆盖 → 强制补生成
       ├─ 触发条件：该专家的 scope_boundary 内存在"若不讨论会导致判断错位"的维度
       ├─ 生成方式：系统从该专家的 scope_boundary + 项目信号推导独占视角切口
       ├─ 标注：agenda_source = 「补位型（零沉默保障）」
       └─ 原则：补生成的切口必须是真实专业盲区，不是凑数的泛描述
```

**禁止绕过规则**：
- `co_proposers` 的联合参与**不能**替代 `sole_proposer` 的独立覆盖要求
- 联合提出另算，不计入零沉默检查的覆盖

### 7.2 议程示例（HAY 案例，含拆分结构）

```
议题：HAY 气质在山地语境的落地方式
  agenda_source：张力推导型
  sole_proposer：HAY 品牌语义与产品策略研究员
  co_proposers：丹麦及北欧功能主义生活方式研究员、空间设计总统筹
  nomination_reason：从品牌语法视角——HAY 的产品逻辑是功能优先；
                    山地厚重、湿润、安静感与之形成张力。
                    不先定"精准移植"还是"转译保留张力"，
                    色彩锚点和家具选型方向将相互矛盾，无法定锚。
  impact_scope：风格主线、材料温度、公共区气场设定

议题：公共空间是社交发生器还是安静停泊器
  agenda_source：行业补位型
  sole_proposer：七里坪山地民宿经营与投资视角代理人
  co_proposers：轻度假旅程与情绪体验研究员、空间设计总统筹
  nomination_reason：从经营模型视角——入住率与回头客结构在两种公区逻辑下的
                    运营摩擦完全不同。不先定性，公区尺度和家具密度都是错的。
  impact_scope：客厅尺度、餐区关系、停留时长预测、运营模型
```

### 7.3 全员发声台账（Agenda Voice Ledger）

> **v1.6 新增**
> 零沉默原则（§7.1）是机制约束；本节定义前台可见的对照层，避免用户体感为“只有系统在发言”。

**适用范围（本轮议程）**：
- 核心层 + 项目召集层 + 被用户勾选为当轮参与的可选加入层。

**台账目标**：
- 让用户在 T2-b 一眼看到每位入场成员的发声状态，而不是只看到最终议题列表。

**每位成员的状态必须三选一**：

| 状态 | 判定条件 | 前台展示要求 |
|---|---|---|
| 主提 | 至少 1 条议题担任 `sole_proposer` | 显示议题名 + 影响范围 |
| 联提 | 无独立主提，但至少 1 条担任 `co_proposers` | 显示联提议题 + 联提理由 |
| 暂缓 | 本轮不适合发言（条件未命中/阶段未到） | 必须显示「暂缓原因 + 激活条件」 |

> 注：机制层的硬约束仍以 §7.1 为准——已确认入场的核心与项目召集成员，原则上必须满足 `sole_proposer` 覆盖；若因合并去重导致前台只剩联提展示，仍需在台账中回链到其原始扫描发声记录。

**输出结构建议**：

```yaml
voice_ledger:
  - expert: "用户研究专家"
    status: "主提"
    linked_agenda: ["轻度度假的行为定义"]
    note: "行为定义不清会导致动线和社交区尺度误判"
  - expert: "山地民宿香氛专家"
    status: "暂缓"
    activation_condition: "T4方向锁定后且感官链路被激活"
    note: "当前阶段不主导议程，但已注册后续责任"
```

**用户动作支持**：
- 用户可在 T2-b 点击任一「暂缓」成员，要求当轮补位提案；
- 系统需返回：补位议题名称、`agenda_source`、`sole_proposer` 与 `impact_scope`。

**张力议题卡**（conflict-flagged 类型，置顶）：

当同一议题有跨链专家持相反判断时，自动生成张力议题卡，用户必须先裁决才能进入其他议程项：

## 八、全流程贯穿方式

### 8.1 各节点专家出场方式

| 节点 | 出场方式 | 专家职责 |
|---|---|---|
| **T1.5** | 解题思路（含系统内置工作地图）+ 团队清单卡 | 先说明“这次需要完成哪些基础工作（A类+B类）”，再确认“谁来做” |
| **T2-a** | 角色事实亮相（`Research Brief Pack`） | 先铺事实底图，轻量确认，暂不裁决 |
| **T2-b/T2-c** | 议题提案与逐切口裁决（含 `proposed_by_roles`） | 以专家人格立场开口并推动取舍 |
| **T4** | 方向候选标注 `[主导：A，背书：B]` | 每个方向有专家签名背书 |
| **T5** | 专题策略卡标注 `[主导：A，参照：B 提供 XX 依据]` + 协作意见可展开 | 专题由对应链主导专家以其语气呈现 |
| **T4 战略冻结** | 团队联署设计宪章（≤10 条原则） | 宪章作为后续所有执行的宪法级约束 |
| **T6** | 任务书签署区（每位专家 ≤2 句） | 「我的关注点是否被满足」，异议记录附注不阻断冻结 |

### 8.2 T2-b 专家开场白规范

对应专家在假设卡出现前第一人称开场（取代中性系统来由旁白）：

- 内容：当前关注的角度 + 从其视角看到的项目特殊性 + 引出假设卡的理由
- 长度：≤4 句话，不做长篇铺垫
- 语气：与人格三要素一致，跨卡可辨识
- 格式：`【专家称谓 · 角度说明】\n"...开场白..."`

### 8.3 执行阶段召回规则（大节点 4，规则层）

- 每个执行专题对应专家「把关人」，负责审阅执行结论
- 专题出现决策争议时，召回对应链专家重新介入
- 专家记忆继承：需求分析阶段的判断记录对其可见，不需要重新介绍项目背景

### 8.4 追问环节专家直连规则（交付后对话态）

> **v1.2 新增**
> 交付后系统回归对话态，用户的追问不全由高参兄统筹回答。凡命中专家责任领域的追问，由该专家以第一人称人格直接开口。

**双通道触发机制**：

| 触发通道 | 触发方式 | 识别逻辑 | 示例 |
|---|---|---|---|
| **通道一：明确点名** | 用户在追问中直接提及专家称谓或所属视角 | 字符串匹配专家称谓关键词；或提及该专家在 T2-a 独立主提的具名议题 | "运营顾问当时是怎么算这个回收周期的？" |
| **通道二：自动识别** | 系统根据追问内容判断归属领域，主动切换对应专家开口 | 语义匹配 `scope_boundary` + `impact_scope` 字段；置信度 ≥ 0.75 才触发 | 用户问"这个木材替代方案会不会影响品牌感"→ 系统识别属于 HAY 品牌专家范畴，由该专家开口 |

**发言格式**：
```
【专家称谓 · 触发来源：点名 / 自动识别】
"...以第一人称、该专家人格语气回答..."
```

**范围约束**：
- 专家仅在自己的 `scope_boundary` 内发言，越界内容切回高参兄
- 自动识别置信度 < 0.75 时，由高参兄统筹回答，可选引用专家视角（"从运营代理人的角度看……"）
- 综合性追问（同时命中多位专家领域）由高参兄统筹，按需引用各专家立场

**专家记忆延续**：
- 专家在追问环节可见：自己在 T2-a 独立主提的议题、T5 专题策略卡中自己主导或参照的内容、T6 签署区的发言与异议
- 不需要重新介绍背景，基于既有记录直接接续

### 8.5 参与度分档制度（A/B/C/D 档）

> **v1.3 新增**
> 梦幻团队成员按全程参与深度分为四档，影响各节点的出场方式与频率，防止"全员每轮刷存在感"的噪音状态。

| 档位 | 名称 | 参与范围 | 典型角色 | 与三层角色库的对应 |
|---|---|---|---|---|
| **A 档** | 核心贯穿 | 议程→战略→专题→执行→追问 全程持续 | 空间设计总统筹、用户研究专家、实施边界顾问 | 核心层（§二.2.1） |
| **B 档** | 阶段主导 | 在特定关键阶段担任主导发言人 | HAY 品牌专家、经营代理人、北欧生活研究员 | 动态扩展层（§二.2.2）主力 |
| **C 档** | 条件触发 | 仅当特定议题激活或追问触及时出场 | 声景编辑、香氛专家、自然光感顾问 | 深度感知层（§二.2.3） |
| **D 档** | 后台候补 | 不前台发声，仅作系统内部知识源 | 深度技术顾问（非设计师可感知） | 不进 ExpertTeamPack |

> D 档不出现在 T1.5 亮相卡中，不进入 ExpertTeamPack。当 1+1+1 核验（§5.4）无法满足时，专家降格为 D 档。

**分档与 8.1 出场方式的联动**：

| 节点 | A 档 | B 档 | C 档 |
|---|---|---|---|
| T1.5 | 第一区亮相 | 第二区亮相 | 第三区（可选加入）|
| T2-a 事实亮相 | 参与事实底图校准 | 参与事实底图校准 | 按条件补充 |
| T2-b/T2-c 视角扫描与开场白 | 必须产出并主导 sole_proposer 切口 | 必须产出并主导 sole_proposer 切口 | 条件触发时开场 |
| T4 方向讨论 | 持续参与，主动触发（A 类） | 持相关立场时介入 | 通常不出场 |
| T5 专题策略 | 参与所有专题的编译审阅 | 主导对应专题 | 对应专题激活时出场 |
| T6 签署 | 必须签署 | 必须签署 | 已激活者签署 |
| 追问 | 全范围可召回 | 责任域内可召回 | 责任域触发时可召回 |

### 8.6 全流程三类触发机制

> **v1.3 新增**
> 专家在 T2-b 至追问全流程中的出场，按三类机制触发。§8.4 的追问直连是类型 C 在追问阶段的具体实现；本节将三类机制扩展至 T2-b/T3/T4/T5 全程。

**类型 A：主动触发（专家主动介入）**

当节点内容进入专家的 `scope_boundary` 且沉默会导致该节点产出质量明显下降时，专家主动发声，不等用户触发。

触发条件：
- T3 缺口补全时：某条缺口项直接影响该专家在后续节点的判断质量
- T4 方向讨论时：某个方向候选与该专家核心立场有明确冲突（张力显性化）
- T5 专题策略时：某条策略规则超出该专家知识边界，需补充或纠正

示例：
```
T3 缺口补全，用户跳过「室内净高范围」
→ 建筑-景观接口顾问主动介入：
  【建筑-景观室内接口设计顾问 · 主动触发 · T3】
  「净高数据是我在 T5 给出层高分级策略的必要输入。
   如果跳过，我只能给范围建议，无法给精确数值。
   建议至少确认一个大概区间，否则尺度策略会留缺口。」
```

**类型 B：被动触发（用户点击气口时专家响应）**

用户点击任意内容块的气口（「💬 展开说说」「为什么这么判断」），不由匿名系统回答，而由对应专家以第一人称立场响应。

触发条件：用户触发气口 → 系统识别该内容属于哪位专家的 `scope_boundary` → 由该专家开口

示例：
```
用户点击：💬 展开说说苔藓绿 vs 竹黄的选择依据
→ 峨眉山山地生活方式研究员响应：
  【峨眉山山地生活方式研究员 · 气口触发 · T5】
  「苔藓绿是峨眉山湿润气候的视觉结果，不是因为好看。
   竹黄属于干燥季节的颜色——七里坪常年云雾，竹黄会显'不对时'。
   如果旺季集中在秋冬干燥期，竹黄才值得考虑。」
```

**类型 C：召回触发（追问阶段专家重新介入）**

见 §8.4 追问直连规则。适用于交付后对话态。本节三类触发框架中，§8.4 是类型 C 在追问阶段的完整规范。

**三类触发发言格式统一**：
```
【专家称谓 · 触发类型：主动触发 / 气口触发 / 点名召回 / 自动识别召回 · 所在节点】
"...第一人称，该专家人格语气..."
```

### 8.7 克制原则（Restraint Protocol）

> **v1.3 新增**
> 专家的存在感应是"持续在场但不打扰"——用户知道他们在，需要时能找到，但不会被淹没。

**四条硬约束**：

1. **每节点最多 2-3 位专家主动发声**
   - 超过时按档位序（A > B > C）和议题相关度自动筛选
   - 其余专家意见折叠为「还有 X 位专家的补充意见 ▶」，用户可展开

2. **发言长度上限**
   - 主流程中每次发声 ≤4 句话
   - 气口展开（B 类触发）可适当扩展，但不超过 150 字

3. **A 类主动触发有内部阈值**
   - 仅当"沉默会导致该节点产出质量明显下降"才触发
   - 一般性观察意见折叠为「待确认补充」，节点结束后展示，不打断主流程

4. **发言优先级序**
   - 主导专家（A 档主发）> 协作专家（B 档参与）> 背书专家（co_proposer 补充）
   - sole_proposer 发言优先级高于 co_proposer

### 8.8 专家依赖收敛原则（单一中介，不做网状互读）

> **v1.4 新增**
> 梦幻团队内部允许依赖，但不允许专家之间形成“全文互读、实时互联”的网状结构。依赖必须收敛为有限类型，并通过统一中介对象读取。

**统一中介对象**：
- `DesignTaskBook`（已冻结主线、专题结论、红线）
- 会话级执行编排（任务骨架、责任映射、审阅门，按需生成）
- 当前节点上下文（仅本节点必要的增量信息）

专家在执行或追问中默认读取以上三类对象，不直接读取其他专家的原始长文本输出。

**三类依赖（仅保留这三种）**：

| 依赖类型 | 定义 | 触发时机 | 示例（香氛专家） |
|---|---|---|---|
| 前置依赖 | 没有该信息不能开工 | 专题开始前 | 需先读取空间命题、客房/公区气质、刺激阈值 |
| 参考依赖 | 有更好，无也可先出初版 | 专题执行中 | 读取色彩系统摘要，微调嗅觉锚点 |
| 审阅依赖 | 产出后需指定角色做冲突审阅 | 专题完成后 | 由空间设计总统筹审阅是否与整体气质冲突 |

**结构化接口摘要（允许传递）**：
- 允许传递“约束过的结构化信号”，不传递散文式长文本。
- 推荐字段：`space_zone`、`time_band`、`emotion_target`、`stimulus_threshold`、`do_not_use`、`brand_visibility`。

**禁止项**：
1. 专家之间全文互读并循环引用；
2. 未经中介对象冻结就把临时草稿作为他人硬前置输入；
3. 以“多人实时互聊”替代明确责任和仲裁。

### 8.9 跨专题一致性检查与仲裁路径

> **v1.4 新增**
> 专家协作的重点是“结果一致性”，不是“过程互联”。跨专题冲突在汇总里程碑统一检查，按需召回，集中仲裁。

**检查时机**：
- T5 专题策略汇总后；
- T6 任务书签署前；
- 交付后重大追问触发局部重入实施执行前。

**检查对象（示例）**：
- 视觉 × 嗅觉（色彩系统 × 香氛方案）
- 视觉 × 声景（空间节奏 × 声景密度）
- 品牌显隐 × 运营可行（品牌表达强度 × 运维摩擦）

**冲突处理流程**：
```
产出汇总
  ↓
一致性检查（生成 conflict records）
  ├─ 无冲突 → 直接进入下一节点
  └─ 有冲突 → 触发轻量召回协调
       ↓
     A 档总整合角色（空间设计总统筹）裁决
       ↓
     必要时联动实施边界顾问做硬约束复核
       ↓
    裁决结果回写 DesignTaskBook / 会话级执行编排（版本化留痕）
```

**归口原则**：
- 专家可提出异议，但不做无限互辩；
- 冲突最终由单一责任角色裁决，确保责任闭环。

### 8.10 洞察运行机制（显性席位 / 洞察亮相席 / 条件触发席）

> **v1.7 调整**

为防止“洞察先亮相”演变为前台专家膨胀，统一采用三种运行身份：

| 身份 | 默认可见性 | 何时出场 | 主要职责 |
|---|---|---|---|
| 显性席位 | 用户可见 | T1.5 起即在场 | 前台共创、议程提名、专题主导 |
| 洞察亮相席 | 用户可见（摘要级） | T1.5 后先亮相 | 先表态建立底图，后续分流为研究呈现或议题裁决 |
| 条件触发席 | 默认不可见 | 命中阈值或用户追问时 | 聚焦解释/纠偏/补充判断 |

**展示原则**：
- 洞察亮相席以“摘要立场”展示，不与显性席位抢主流程；
- 细粒度计算过程仍可折叠展示：
  「展开查看该洞察的证据与计算依据」。

### 8.11 风险分析员机制（总控席位 + 分维接口）

> **v1.5 新增**
> 风险分析员是高优先级隐藏席位。其职责不是否定方案，而是提前暴露“何种条件下会失败”。

**风险五维**：
1. 方向风险（战略层命题错配）
2. 市场/经营风险（客群、溢价、回收模型）
3. 执行风险（施工、采购、维护、供应链）
4. 时间风险（季节波动、老化、生命周期）
5. 边界风险（品牌参照边界、合规与伦理）

**四个必经节点**：
- T1.5：建立“避坑合伙人”角色存在感
- T4：对方向候选输出风险快照
- T5：对每个专题输出 ≤2 条避坑项
- T6：风险三分法签署

**风险三分法签署**：
- 已覆盖风险（已有策略处理）
- 知情接受风险（用户明确接受）
- 悬空风险（需回退或后续验证）

**处理三态**：
1. 接受并记录（不阻断）
2. 触发讨论（召回对应专家）
3. 触发回退（回 S3/S4 对应层）

### 8.12 梦幻团队工作分层的实施模板（v1.8）

> **v1.8 新增**
> 将“没有调研就没有发言权”落成可执行结构：先资料、再议题、过程门禁持续作用、启发可转议题。

> **v1.10 补强**
> 工作分层由“工作地图双主线”驱动：
> - A类：交付物驱动工作（围绕用户已确认目标与交付物）；
> - B类：洞察亮相工作（2.4 主动补位，补齐成立条件与风险底图）。
> 两类工作先在 T1.5 明确，再在 T2-a/T2-b 汇合执行。

**四层分工（实施口径）**：

| 层级 | 产出类型 | 是否需用户裁决 | 典型责任人 |
|---|---|---|---|
| 基础研究资料层 | `Research Brief Pack`（事实底图） | 否（可追问来源） | 区域/场地/标杆洞察席 |
| 议题交互层 | `Agenda Pack`（需取舍议题） | 是（保留/删减/排序/确认） | `sole_proposer` + `co_proposers` |
| 过程作用层 | `Process Guard Records`（门禁/风险/一致性记录） | 条件触发 | 风险分析员、实施边界顾问、A档总整合角色 |
| 启发层 | `Inspiration Pack`（可选启发） | 否（可转议题） | 深度感知层/跨界席位 |

**工作地图两类输入到四层分工的映射**：

| 工作地图来源 | 在四层分工中的落点 | 说明 |
|---|---|---|
| A类：交付物驱动工作 | 基础研究资料层 + 议题交互层 | 围绕“要交什么”形成事实与议题主线 |
| B类：洞察亮相工作（2.4） | 基础研究资料层 + 过程作用层 | 围绕“必须先知道什么”补齐底图与门禁 |

> 约束：T1.5 只展示“工作类型与必要性”，不展开长篇洞察内容；洞察内容在 T2-a 以 `Research Brief Pack` 逐条呈现，避免前台重复。

**过程作用层触发点（强约束）**：

| 节点 | 必做动作 | 产出字段 |
|---|---|---|
| T4 | 风险快照（五维） | `risk_register[]` |
| T5 | 跨专题一致性检查 + 仲裁 | `consistency_check_records[]` / `arbitration_notes[]` |

## 九、验证方式

用 HAY 民宿案例跑完整模拟，验证以下 13 个检查点：

1. **T1.5 团队准确性**：生成的团队中每位专家的「我最在意的问题」高度项目专属，无通用泛描述
2. **专家语气可辨识性**：抽取 HAY 品牌专家 / 经营代理人 / 用户研究专家的 T2-b 开场白——三者语气差异必须可辨识，不能听起来是同一个系统在说话
3. **张力对浮现**：链 A×链 B、链 A×链 D、链 C×链 B 的三组张力是否自动生成「⚡张力议题卡」
4. **T6 异议表达**：让经营代理人保留一条异议——验证异议精准表达，≤2 句，不阻断任务书冻结
5. **零沉默原则覆盖**：检查所有入场专家（含核心层 3 位 + 动态扩展层全部）是否各有至少 1 条 `sole_proposer` 独立主提议题；若有遗漏，验证系统是否自动触发补生成流程，且补生成的切口有实质专业内容而非泛描述
6. **追问直连双通道**：交付后向经营代理人追问（通道一：明确点名），再就"品牌感"提问（通道二：期待自动识别为 HAY 品牌专家）——验证两次是否正确触发对应专家人格，且不越出各自 `scope_boundary`
7. **A/B/C/D 档位分配合理性**：检查 T1.5 生成的团队中各专家档位是否符合项目阶段——深度感知层专家是否正确归入 C 档（可选加入）而非默认进 A 档；1+1+1 核验是否过滤掉无戏份的候选专家
8. **三类触发完整性**：模拟 T3 缺口补全（A 类主动）、T4 方向讨论气口（B 类被动）、追问环节（C 类召回）三种场景——验证对应专家是否正确出场，发言在 `scope_boundary` 内，且符合克制原则（≤4 句、每节点 ≤3 人发声）
9. **依赖收敛合规性**：抽样香氛/色彩/山地生活方式三位专家，验证是否通过 `DesignTaskBook + 当前节点上下文（必要时附会话级执行编排）` 读取所需信息；不得出现专家间全文互读链条
10. **冲突仲裁闭环**：制造“色彩偏高刺激 vs 香氛低刺激阈值”的冲突样例，验证系统是否在汇总节点触发一致性检查、召回协调、A 档裁决并完成版本化回写
11. **隐藏洞察自动补位**：在“经营性山地民宿+品牌参照”输入下，验证系统是否自动触发经营/区域/标杆/风险四类隐藏席位，不依赖用户点名
12. **升前台阈值有效性**：验证隐藏席位仅在高影响/高风险/冲突/用户追问命中时升前台；未命中时保持后台运行，不造成前台噪音
13. **风险总控闭环**：验证风险分析员在 T4/T5/T6 均产出可追溯结果（风险快照、专题避坑项、风险三分法签署），并形成版本化留痕

## 十、三层对照全景表：前台席位 ↔ 中台责任包 ↔ 后台 V 角色

> **Copilot 新增（v1.1，2026-03-19）**
> 本节基于两份参考意见交叉校验后整合。核心判断：梦幻团队前台席位与 V2-V9 执行角色是**分层关系而非竞争关系**，两者之间需要一个可编译的中台责任层做桥接。

### 10.1 三层结构定义

| 层级 | 名称 | 可见性 | 生命周期 | 语言风格 |
|---|---|---|---|---|
| **前台** | 项目专家编组层（Project Expert Board） | 用户可见 | 动态，与项目绑定，一次性 | 项目语言（"HAY品牌研究专家"） |
| **中台** | 责任编译层（Expert Responsibility Skeleton） | 系统内部，不暴露给用户 | 随任务书冻结并在方案高参按需编排时装载 | 职责包语言（"品牌叙事转译"） |
| **后台** | 执行代理层（V2-V9 Execution Agents） | 系统内部，不暴露给用户 | 稳定复用，跨项目存在 | 系统语言（"V3 A3 Narrative L5"） |

> ⚠️ **前端绝不暴露 V 编号**：T1.5 团队亮相卡展示的是前台席位名（项目语言）。把"V2、V5、V7"直接暴露给用户，违反 A/01 的「内源严谨，外延柔化」原则。

### 10.2 三层对照全景表

基于本文 §二 三层角色库 + `intelligent_project_analyzer/config/roles/` YAML 角色定义，对照关系如下（roles/*.yaml 是权威底盘，examples/ 仅作参考）：

| 前台项目席位（T1.5 用户可见） | 中台责任包（S5 冻结后在方案高参按需装载） | 后台 V 角色（大节点4执行） | 承接类型 |
|---|---|---|---|
| 山地民宿室内总统筹 | 空间命题编制 + 全局方案整合 | **V2** 设计总监（A1 Concept L5） | 直接对应 |
| HAY 品牌研究专家 | 品牌基因提取 + 文化符号转译 | **V3**（A3 Narrative L5） | 动态扩展→判断注入 |
| 丹麦 / 北欧生活研究员 | 案例对标 + 生活方式趋势依据 | **V4** 设计研究员 | 动态扩展→判断注入 |
| 山地民宿主理人视角 | 运营约束红线 + 经营可行性判断 | **V5** 场景与行业专家 | 直接对应 |
| 山地生活方式研究员 | 场景文化叙事 + 在地知识输入 | **V4** + **V5** | 拆分承接 |
| 轻度假产品研究员 | 体验触点清单 + 旅程弧线设计 | **V3**（A3-2感官体验）+ **V5** | 拆分承接 |
| 用户体验与行为研究专家 | 用户行为模型 + 心理需求分析 | **V7** 社会关系与心理洞察（A9 L4） | 直接对应 |
| 实施边界顾问 | 结构可行性 + 技术红线 + 造价约束 | **V6** 首席总工程师（A2/A8 L5） | 直接对应 |
| 政策与在地语境顾问 | 审批路径 + 法规合规 + 地方语境翻译 | **V8** 政策顾问（A9/A12） | 直接对应 |
| 色彩 / 香氛 / 音乐感官专家 | 感官策展方案 + 氛围叙事 | **⚠️ 当前底盘缺口**（V3+V7 临时代打） | 待沉淀角色 |
| 家具与软装设计顾问 | 家具选型系统 + 软装搭配逻辑 | **⚠️ 当前底盘缺口**（V2+V6 临时代打） | 待沉淀角色 |

### 10.3 动态扩展角色的注入机制

**"动态扩展→判断注入"** 的含义（区别于"直接对应"）：

项目特有前台席位（如"HAY品牌研究专家"）在需求分析阶段作为独立认知视角存在，产出判断记录、议程切口、张力裁决。进入实施执行阶段时：

1. **不另开独立执行节点**——后台执行层保持 V2-V9 稳定结构不膨胀
2. 该席位的全部判断记录作为 **上下文前缀** 注入到最近 V 角色的任务包中
3. 注入格式：`source_expert_context: {seat_name, key_judgments[], agenda_cuts[]}`
4. 对应 V 角色在执行时看到的是：任务书 + 该席位在 S2-S4 阶段的认知积累

这确保了"前面谁提出问题，后面就有人真正把这条线做下去"——系统结构不因项目不同而改变执行角色数量。

### 10.4 待沉淀角色缺口登记

当下列席位在项目中高频出现、且临时代打质量不足时，启动正式 V 角色扩容：

| 待沉淀席位 | 高频场景 | 建议新角色定位 | 优先级 |
|---|---|---|---|
| 色彩 / 材质专家 | 高端精品民宿、品牌化空间项目 | V10 色彩与材质策展师 | 高 |
| 感官策展（香氛 / 声景 / 触感） | 深度体验场景，T4 后激活 | V11 感官叙事专家 | 中 |
| 家具与软装顾问 | 所有精装场景 | 并入 V6 子角色或独立 V12 | 中 |

## 十一、前后台双向约束规则

> **Copilot 新增（v1.1，2026-03-19）**
> 本节处理一个结构诚信问题：如果前台可以随意召唤任何酷炫席位，而后台无对应承接者，系统会对用户做出无法兑现的承诺。这是质量隐患，不是风格问题。

### 11.1 约束方向定义

联动不是单向的"前台→后台映射"，而是 **双向约束**：

```
※ 正向约束（前台决定后台怎么接）
T1.5 ExpertTeamPack 生成
  → S5 编译为 ExecutionRoleMapping
  → 大节点4入口：V-角色接收任务包 + source_expert 上下文

※ 反向约束（后台能力边界约束前台能稳定承诺的席位）
V2-V9 能力边界（roles/*.yaml 定义）
  → 前台信号匹配时检查是否有承接底盘
  → 若有缺口 → 按 11.2 三级策略处理
```

### 11.2 后台缺口的三级处理策略

当 T1.5 信号匹配生成的某个席位，在 V2-V9 中找不到稳定承接者时：

| 缺口等级 | 判定标准 | 处理策略 |
|---|---|---|
| **A 级：可临时代打** | 最近 V 角色能力覆盖 ≥ 60% | 自动分配代打角色，T1.5 亮相卡标注：「⚡ 此席位由 [V角色] 兼任，能力边界：[说明]」 |
| **B 级：部分拼凑** | 需 2 个以上 V 角色拼凑，覆盖率 30%-60% | 向用户说明："当前系统对此专业的执行深度有限，将由 X+Y 合力承接，建议在后续阶段追加专家输入"，标注为「低保真席位」 |
| **C 级：底盘空白** | 覆盖率 < 30%，无合理代打 | 该席位不进入本次 ExpertTeamPack，向用户说明："此方向目前系统暂无执行能力，已记录为角色库扩容需求"，不做虚假承诺 |

### 11.3 会话级执行编排角色映射字段规范

打通前后台的关键数据结构（S5 编译时生成，大节点4入口消费）：

**`ExecutionRoleMapping`** 挂在“会话级执行编排.expert_responsibility_skeleton”下：

```yaml
execution_role_mapping:
  - expert_board_seat: "HAY品牌研究专家"         # 前台席位名（T1.5 确认）
    responsibility_bucket: "品牌基因提取与文化符号转译"  # 中台责任包
    lead_v_role: "V3"                            # 后台主承接 V 角色
    support_v_roles: ["V4"]                      # 后台协作角色
    承接类型: "动态扩展注入"                      # 直接对应 / 拆分承接 / 动态扩展注入 / 临时代打
    source_expert_context:                        # 注入到 V3 任务包的认知前缀
      key_judgments:
        - "HAY 品牌在山地语境中最大的张力是：斯堪的纳维亚克制感 vs 山地粗粝感，不应融合，应保持张力共存"
      agenda_cuts:
        - "色彩系统应以 HAY 2024 粉灰色板为锚点，向山地土石色系延伸，而非直接本土化"
```

**S4 专题结构新增三字段**（专题条目升级版，在现有字段基础上追加）：

```yaml
专题条目:
  topic: "色彩与材质系统"
  priority: high
  红线: ["不使用红色/金色传统符号"]
  原则化规则: "HAY 色板锚点不可替换"
  # --- v1.1 新增：前后台联动字段 ---
  lead_role: "V3"                         # 后台主导执行角色
  support_roles: ["V6-色彩材质"]          # 后台协作角色
  source_expert: "HAY品牌研究专家"         # 此专题在 S2-S4 由哪个前台席位提出
```

### 11.4 双向约束完整运行时序

```
[T1.5] 信号匹配 → 候选席位列表生成
         ↓
     ← 反向约束检查：每个席位是否有 V 角色承接底盘？
         ├─ 有底盘 → 正常加入 ExpertTeamPack
         ├─ A级代打 → 加入，标注兼任说明
         ├─ B级拼凑 → 加入，标注「低保真席位」
         └─ C级空白 → 不加入，记录扩容需求
         ↓
[S2-S4] 各席位标注议程来源（source_expert 字段逐步累积）
         ↓
[S5] 编译 ExecutionRoleMapping
     + 各专题 lead_role / support_roles / source_expert
         ↓
[大节点4入口] V-角色同时接收：
  ① 自己负责的专题任务结构（来自本轮会话级执行编排）
   ② source_expert 的判断记录前缀（认知继承，不从零读任务书）
   ③ 跨角色协作关系（谁是 lead，谁是 support）
         ↓
[V-角色执行] 携带需求分析阶段认知积累，不产生认知断层
```
