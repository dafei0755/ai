# ucppt.com 会员打通主架构执行方案（2026-03-09）

> **一句话结论：** 采用“WordPress/ucppt.com 作为会员唯一事实源，AI 应用作为消费与执行控制方”的主架构，不重建会员主表；优先补齐服务端权限闭环与状态同步闭环，再推进 webhook 与性能治理。

---

## 一、文档目标与边界

### 1) 目标

在不破坏现有主架构（Redis 热数据 + LangGraph checkpoint + SQL 归档）的前提下，明确会员打通机制的：

- 实现原理
- 事实口径
- 风险与冲突点
- 可落地执行路径

### 2) 边界

- **本次聚焦：** 认证、会员状态、权限、配额、同步、配置收敛。
- **本次不做：** 支付网关重构、订单域主导权迁移。

---

## 二、主架构定位（与现有系统一致）

### 1) 角色分工

- **WordPress / ucppt.com：** 会员与订单事实源（Source of Truth）
- **FastAPI：** 身份验证、权限裁决、配额执行、同步编排
- **Next.js：** 登录与状态展示、交互门禁提示（非安全边界）

### 2) 与“数据库与保存机制”关系

会员打通属于**业务权限域**，不替代主会话存储链路：

- 运行态：Redis
- 过程态：checkpoint
- 历史态：archive（PostgreSQL 优先，SQLite 兼容回退）

因此，会员体系不应被设计为新的“主会话真源”。

## 三、当前代码事实（F1）

> 结论基于仓库代码核验，不依赖主观假设。

### F1-1 已有能力

1. 已有会员查询接口：`GET /api/member/my-membership`  
   文件：`intelligent_project_analyzer/api/member_routes.py`
2. 分析入口已强制登录（JWT）：`POST /api/analysis/start`  
   文件：`intelligent_project_analyzer/api/_start_routes.py`
3. 前端有 VIP→Tier 映射与会员 hook  
   文件：`frontend-nextjs/lib/tier-mapping.ts`、`frontend-nextjs/hooks/useMembership.ts`

### F1-2 已识别缺口

1. **服务端 tier 门禁未形成统一依赖闭环**（登录 ≠ 会员授权）。
2. **配额接口存在 `user_tier` 入参模式**，理论上有被伪造风险面。  
   文件：`intelligent_project_analyzer/api/quota_routes.py`
3. `wpcom_member_api.py` 主要为同步调用（httpx 同步 API），有阻塞风险。  
   文件：`intelligent_project_analyzer/api/wpcom_member_api.py`
4. CORS 当前为 `allow_origins=["*"]`（需按环境收敛）。  
   文件：`intelligent_project_analyzer/api/server.py`
5. `JWT_SECRET_KEY` 缺省时使用随机生成密钥，重启可能导致旧 token 失效。  
   文件：`intelligent_project_analyzer/services/wordpress_jwt_service.py`

## 四、参考建议交叉评估（A/B）

## 4.1 建议A评估

### 可采纳（主线）

- WordPress 作为唯一会员事实源（正确）
- AI 端只做消费与执行控制（正确）
- 服务端权限闭环优先（正确）
- webhook + 拉取同步双策略（正确）
- 配置收敛与签名安全（正确）

### 需约束

- webhook 事件全集需结合 WP 侧插件能力分阶段落地，不能一次性假定全可用。

## 4.2 建议B评估

### 可采纳（盘点价值）

- 认证、会员、配额、钱包、设备等模块盘点较完整。
- 对风险项（secret、CORS、明文配置）提示有效。

### 需修正

- “核心链路完整可用”应调整为“**认证与查询可用，授权闭环未完成**”。

## 4.3 冲突裁决

1. **A强调闭环缺口，B偏向可用完成度**：以代码事实为准，判定“部分可用，闭环待补”。
2. **是否信任前端 tier**：不信任，必须后端按 `current_user` 解析。
3. **是否引入本地会员主表**：不引入，仅缓存同步快照（非事实源）。

## 五、实现原理（目标态）

### 1) 认证原理

`ucppt.com 登录 -> SSO token/get-token -> /api/auth/verify -> 本地会话`

- Token 负责“你是谁”
- 会员等级负责“你能做什么”

二者必须分层，不可混用。

### 2) 授权原理

所有受限能力统一经过服务端依赖：

- `require_membership(min_level)` 或 `require_tier(min_tier)`
- 前端只用于 UX 提示，不作为安全控制点

### 3) 配额原理

统一执行顺序：

1. 解析当前用户
2. 计算/读取服务端 tier
3. 校验配额
4. 执行业务
5. 原子扣减 + 审计

### 4) 同步原理

双通道保证一致性：

- **主通道**：webhook 主动推送（实时）
- **兜底通道**：登录时拉取 + 关键接口懒刷新 + 定时对账

### 5) 存储原理

- 会员事实仍在 WordPress
- AI 侧仅保存“同步快照/缓存”（如 `vip_level`、`expire_date`、`synced_at`）
- 会话持久化继续沿用 Redis/checkpoint/archive 主链

## 六、执行路线（合理化分期）

### Phase P0（1~1.5周，阻塞上线）

1. 建立服务端权限依赖并接入受限 API（至少 analysis start 系列）
2. 配额接口去客户端 `user_tier` 信任路径，改为服务端推导
3. 新增 `GET /api/member/access-summary`（统一下发门禁与配额视图）

### Phase P1（1周）

1. 新增 `POST /api/member/webhooks/wordpress`
2. 实现签名校验、防重放、幂等处理
3. 若 webhook 不可用，补定时对账任务

### Phase P1（并行）

1. 配置收敛：`WP_MAIN_URL`、`WP_SSO_API_BASE`、`WP_MEMBER_CENTER_URL`
2. CORS 收敛到白名单（分环境）
3. 生产强制 `JWT_SECRET_KEY`（禁随机回退）

### Phase P2（后续优化）

1. `wpcom_member_api.py` async 化
2. 会员接口短 TTL 缓存 + webhook 主动失效
3. 监控看板：会员同步延迟、403/429 比例、webhook 成功率

---

## 七、验收矩阵（必须通过）

1. 未登录用户不能访问受限接口。
2. 免费/普通/超级/钻石用户在受限 API 的行为一致可复现。
3. 前端伪造 tier、篡改 localStorage、直调高级接口都被后端拒绝。
4. 会员升级/过期后，在 webhook 或懒刷新触发后权限正确收敛。
5. WP API 超时场景下可降级，不导致主链路雪崩。
6. 回退开关与主架构语义一致（不破坏 Redis/checkpoint/archive）。

---

## 八、风险与治理建议

### 高优先级风险

1. 权限闭环缺口导致越权风险
2. CORS 过宽导致跨域面扩大
3. JWT 密钥随机回退导致 token 稳定性问题

### 治理建议

- 先做 P0，再推进 webhook
- 采用 F1/F2/F3 事实分级做评审材料
- 发布采用灰度：5% -> 20% -> 50% -> 100%

---

## 九、最终结论

当前系统已经具备“认证 + 会员查询 + 映射展示”的基础能力，但距离“生产级会员权限闭环”仍差关键一步：**服务端强制授权与同步一致性机制**。

最优策略不是重建会员系统，而是在现有主架构上完成闭环补强：

- 会员事实不迁移
- 权限裁决后端化
- 同步机制双通道
- 配置与安全收敛

这条路径改动最小、风险可控、与当前代码和存储架构兼容性最高。
