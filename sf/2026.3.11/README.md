## 零、快速开始（按当前仓库可用入口）

### 1) 基础准备

- Python（建议 3.10+，Windows 可用 Conda base）
- Node.js（用于 `frontend-nextjs`）

### 2) 安装依赖

```bash
pip install -r requirements.txt
cd frontend-nextjs && npm install
```

### 3) 启动服务（当前可用）

后端（二选一）：

```bash
python -B scripts/run_server_production.py
```

或：

```bash
start_backend_main.bat
```

前端：

```bash
start_frontend_main.bat
```

默认访问：

- 前端：`http://localhost:3001`
- API 文档：`http://localhost:8000/docs`

### 4) 端口占用处理

```bash
python scripts/utils/port_manager.py release 8000
python scripts/utils/port_manager.py release 3001
```

> 注：历史文档中的 `start_services.bat` 在当前仓库不可用，已不作为推荐入口。

## 一、过程：主线 + 二级步骤

### 主线：6 大节点

| 大节点 | 核心职责 | 关键约束 |
|---|---|---|
| 1. 用户输入 | 接收原始 brief | 不做任何分析 |
| 2. 检查门禁 | 安全/合法/可行性验证 | E-008：可同步轻量预采集 |
| 3. 设计任务书 | 理解"要什么/为什么"，收口为设计任务书 | 前置路由决定策略；questionnaire_summary 必选收口 |
| 4. 方案高参 | 设计任务书落实为工作包 + 用户审批 | 从 confirmed_design_brief 读取；未审批不得进入执行 |
| 5. 生成交付结果 | 专家并行执行，产出 成果 + 洞察 | 支持批次间方向校准（v1 → v1.1 → v1.2） |
| 6. 追问 | 基于交付结果深化/调整 | R-001 待打通 |

```
START
  → unified_input_validator_initial
  → requirements_analyst
  → requirements_analyst_review        ← interrupt（用户审阅）
  → output_intent_detection
  → feasibility_analyst
  → unified_input_validator_secondary
  → progressive_step3_gap_filling      ← 按需
  → progressive_step2_radar            ← 按需
  → questionnaire_summary              ← 必选收口
  → project_director                   ← interrupt（用户审批）
  → ...执行循环...
  → END
```

### 术语映射（概念层 → 代码节点）

| 业务大节点 | 当前主要代码节点 |
|---|---|
| 用户输入 | `START → unified_input_validator_initial` |
| 检查门禁 | `unified_input_validator_initial`、`feasibility_analyst`、`unified_input_validator_secondary` |
| 设计任务书（大节点3） | `requirements_analyst → requirements_analyst_review → output_intent_detection → gap_filling(按需) → radar(按需) → questionnaire_summary(必选)` |
| 方案高参（大节点4） | `project_director` |
| 生成交付结果 | 执行循环与聚合节点 |
| 追问（已归并方案高参） | `END` 后追问入口（R-001 未完全打通） |

| 层级 | 步骤 | 特征 |

## 六、重构交付包（给程序员）

> 本节是“可直接执行”的重构交付说明，默认以代码为准，文档为辅。

### 1) 重构范围（In / Out）

**In Scope（本轮必须覆盖）**
- 工作流主链与节点契约：`workflow_contract.py`、`main_workflow.py`
- 状态模型与字段收敛：`core/state.py`
- 运行时广播与回放链路：`workflow_runner`、事件回放 API、WS 客户端
- 审批/预检/挑战检测闭环：`role_task_unified_review`、`quality_preflight`、`detect_challenges`

**Out Scope（本轮不纳入）**
- 搜索子系统（已废弃）
- 非关键 UI 美化与低优先级重排版

### 2) 冻结约束（不可回退）

执行前先阅读：`../../CLAUDE.md`。  
以下为本轮必须遵守的不变量（若需变更，先改冻结记录再改代码）：

1. `progressive_step1_core_task` 为废弃节点，不得恢复为活跃主链节点。
2. `main_workflow.py` 不注册 `progressive_step1_core_task`。
3. `unified_input_validator_secondary` 后续节点保持 `progressive_step3_gap_filling`。
4. `core/state.py` 中 `active_steps` 默认值不得含 `step1_core_task`。

### 3) 目标产物（程序员需交付）

- 代码改动：最小必要变更，避免无关重构
- 设计说明：每个关键改动点“为何改 / 改了什么 / 如何验证”
- 回归证据：测试输出与结论（通过/失败原因）
- 风险清单：已知风险、未覆盖风险、后续计划

### 4) 分阶段执行顺序（建议）

1. **阶段A：契约收敛**
  - 校正主链节点注册与路由
  - 清理与废弃节点相关的误导入口
2. **阶段B：状态与事件一致性**
  - 统一关键 state 字段来源
  - 校验 WS 广播与事件回放语义一致
3. **阶段C：质量闭环**
  - 审批 → 预检 → 执行链路稳定
  - 挑战检测分流（继续/回流/人工）可解释
4. **阶段D：文档与验收**
  - 更新本目录专题文档
  - 输出测试矩阵与验收结论

### 5) 验收标准（Definition of Done）

满足以下条件才可合并：

- 主链路由与冻结约束完全一致
- 关键回归测试通过（见下方测试矩阵）
- 无新增高优先级 lint/type/运行时错误
- 文档已同步（本 README + 对应专题）
- 变更可回滚（有明确回退点）

### 6) 最小测试矩阵（仓库已存在）

```bash
python scripts/verify/_verify_v8.py

python -m pytest tests/unit/services/test_project_specific_dimension_generator.py -v --tb=short --no-header -q
python -m pytest tests/integration/test_v8_radar_integration.py -v --tb=short --no-header
python -m pytest tests/regression/test_v8_radar_regression.py -v --tb=short --no-header
python -m pytest tests/e2e/test_v8_questionnaire_e2e.py -v --tb=short --no-header -q

python -m pytest tests/unit/test_requirements_method_contracts.py -v --tb=short --no-header -q
python -m pytest tests/regression/test_requirements_review_trace_regression.py -v --tb=short --no-header -q
```

### 7) 回滚与风险控制

- 每个阶段独立提交，禁止“超大一把梭”提交
- 任何主链节点名/阶段映射改动必须先过契约审查
- 发现链路漂移时优先回滚到上一稳定提交

### 8) 程序员开工前 5 分钟检查单

1. 读完 `../../CLAUDE.md` 冻结条款
2. 确认本轮 In/Out Scope
3. 确认要改的目标文件与测试用例
4. 准备分阶段提交计划
5. 约定最终验收输出格式（测试结论 + 风险说明）
