## 一分钟定义

把「模糊的项目描述」转成**一句可执行的任务定义**，让用户和 AI 在「这个项目到底要做什么」上达成明确共识。这是 S2 的第一步发声，也是后续所有分析的起点。

---

## 功能详述

B1 使用 JTBD（Jobs-To-Be-Done）格式输出任务定义：

```
当 [用户情境]，用户想要 [完成的事]，因为 [深层动因]
```

**为什么用 JTBD 格式**：
- 「用户情境」锁定使用场景，防止空洞描述
- 「完成的事」明确可验证的任务成果，防止目标漂移
- 「深层动因」揭示真实驱动力，防止只满足表层诉求

**B1 的核心价值**：不是「告诉用户他的项目是什么」，而是「把他们以为自己知道的事情用可验证的格式说出来」，让隐性目标显性化。

## 输入

```
intent_baseline        # F3 关键洞见提炼的原材料
identity_mode          # B4 使用者身份识别结果（影响表达语气）
structured_requirements  # A1 信号包
```

---

## 输出

```python
jtbd_statement: {
    "situation":    "当 ...",          # 用户情境
    "job":          "用户想要 ...",     # 核心任务
    "motivation":   "因为 ...",         # 深层动因
    "full_text":    "当...，用户想要...，因为..."
}
# 写入 state.problem_framework.jtbd
```

## 激活条件

- B4（使用者身份识别器）完成之后
- S2 强制执行，不可跳过

---

## 执行方式

- **执行器**：LLM 调用
- **语气校准**：B4 识别的身份模式在此生效——探索者用疑问句引导、决策者用结论句确认
- **G1 前置检查**：展示前先过 G1（输出锐度门控），确保任务定义具体可执行
- **F5 前置检查**：展示前先过 F5（套话替换），去掉「以人为本」「注重体验」等空洞表述

## 用户交互

**有**。展示格式：

```
这个项目的核心任务是：

当 [情境]，你想要 [完成的事]，因为 [动因]。

这个描述准确吗？还有什么关键的遗漏？
```

**用户响应类型及处理**：

| 响应类型 | 处理方式 |
|---------|---------|
| 确认 | 槽位状态 → responded，进入 B2 |
| 修改细节 | 更新 jtbd_statement，再次确认 |
| 否定核心 | 触发 reframe，B1 槽位重置 → pending，重新生成 |
| 追问 | 补充解释，不重置槽位 |

```

  ← F3 关键洞见提炼器（洞见原材料）
  ← F2 根本需求追溯器（裸需求提炼）

  → B2 目标冲突诊断器（B1 给出的任务定义是 B2 找冲突的素材）

  → F7 优先级反事实验证器（验证 B1 输出的优先级稳健性）
```

## Reframe 依赖关系

B1 被否定（reframe）时，以下槽位重置为 `invalidated`：
- B2（依赖 B1 的任务定义来诊断冲突）
- B3（依赖 B1 的任务定义来扫描影响）
- C1/C2/C3（也依赖 B1 结论）
- D1（S3 挑战的前提来自 B1）

## 常见误用

1. **把 JTBD 写成通用模板套话**
   纠偏：「当用户需要装修时，想要一个美观实用的家」是失败的 JTBD——「情境」必须具体（三口之家、老公上班主要在家的年轻妈妈），「动因」必须有深度（不是「实用」，而是「想在孩子玩耍时还能有自己的喘息空间」）

2. **直接输出给用户不经 G1 / F5 过滤**
   纠偏：B1 输出必须先经 G1 检查锐度、F5 替换套话，再展示

3. **把 B1 当做确认需求的节点（让用户填表）**
   纠偏：B1 是「提出 AI 的解读版本请用户确认」，是展示结论，不是收集输入

## 扩展优化方向

- **JTBD 质量评分器**：内置评分逻辑，检测「情境」「任务」「动因」的具体程度，低分自动重生成
- **历史 JTBD 库**：积累高质量 JTBD 案例，支持 few-shot 生成
- **多 JTBD 并行输出**：复杂项目可输出 2~3 个备选任务定义，让用户选择或混合
