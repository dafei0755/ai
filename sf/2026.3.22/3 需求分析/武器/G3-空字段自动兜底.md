# G3 — 空字段自动兜底

> **组别**：G 组（质量门控）| **阶段**：全流程·收口 | **类型**：后台·自动填充引擎
> **原始编号**：Q3 空字段回填策略（后台部分）| **消费方**：RequirementsSchema

---

## 一分钟定义

**对所有经过 E1 / G2 后仍然为空的非核心字段，用推断值自动填充，并强制标记 `[推断]`**。确保 RequirementsSchema 中零空对象下游。

---

## 功能详述

G3 是「最后一道防线」：在 E1 没有问、或用户跳过了 E1 的情况下，让字段不带空值进入下游。

G3 的每次填充遵循三步：

```
1. 定位空字段
2. 用已有上下文推断最可能的值
3. 标记：[推断: 基于 X（信息来源）]
```

| 字段类型 | 推断策略 |
|---------|---------|
| `behavior_mode_profile` | 从 B1 JTBD + A1 信号推断最可能的行为模式 |
| `stakeholder_map` | 从项目规模 + 使用者描述推断决策链 |
| `complexity_score` | 从约束数量 + 目标冲突数计算 |
| `timeline_estimate` | 从项目类型 + 规模匹配历史基准 |

---

## 输入

```
requirements_schema     # 当前完整状态（含空字段）
g2_completeness_report  # G2 的缺口清单
full_context            # 全量对话 + 武器输出（用于推断）
```

---

## 输出

```python
# 直接写入 requirements_schema，不返回新对象
# 每个被填充字段附带来源标记：
behavior_mode_profile: {
    "primary_mode": "流动者",
    "confidence": 0.65,
    "source": "[推断: 基于 B1 JTBD 中『家庭活动区切换频繁』]"
}
```

---

## 激活条件

由 G2 触发，在 G2 判定某字段「辅助级」或「用户已 skip」时调用。

---

## 铁律

**核心字段（G2 标记为 critical）不得由 G3 填充。** 核心字段为空 → 必须等待 E1 / 用户响应 → 才能继续。G3 只处理 G2 报告中 `missing_important` 和 `missing_auxiliary` 两类。

---

## 标记规范

G3 填充的每个字段，必须包含：
1. `[推断]` 前缀
2. 推断来源（「基于 [信息源]」）
3. 置信度分（0.0~1.0）

S4 确认任务书界面**必须**展示所有 `[推断]` 标记的字段，让用户知道哪些信息是推断而非确认。

---

## 用户交互

**无**（G3 是静默填充）。但 S4 确认任务书时，用户可见所有 `[推断]` 字段，可选择修正或接受。

---

## 协作关系

```
上游（依赖）：← G2 completeness_report（告知哪些字段需要填充）
             ← E1 已问完的字段（避免重复填充 E1 已处理的字段）
下游（供给）：→ RequirementsSchema（直接写入）
             → S4 确认任务书界面（[推断] 字段展示）
             → F8/F9（以完整 schema 为输入）
```

---

## 常见误用

1. 用 G3 填充核心字段然后让用户「签署确认」（用户无法识别这是推断，误以为是确认值，导致后续专家工作方向偏差）
2. 不添加 `[推断]` 标记直接填充（下游完全无法区分「用户确认」和「系统推断」）

---

## 扩展优化方向

- **推断置信度阈值**：置信度低于 0.4 时，降级为「询问用户」而不是直接填充，即使是辅助字段
