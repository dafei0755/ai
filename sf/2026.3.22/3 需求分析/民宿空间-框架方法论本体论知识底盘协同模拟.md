## 1. 目的与问题

你当前的核心问题是：

- “民宿”在空间分类、方法论、知识底盘中都出现了，边界不清；
- 不确定“通常框架体系、案例、方法论、本体论”各自该放哪里；

## 2. 五类内容的边界定义（先分工，再协同）

### 2.1 空间分类（Project Type）

**回答问题**：这是什么项目？

- 输出：标准类型ID（如 `hospitality_homestay`）
- 用途：路由、统计、策略选择入口
- 约束：只做“识别与命名”，不承载完整方法步骤

### 2.2 通常框架体系（Domain Framework）

**回答问题**：这类项目通常由哪些维度组成？

- 输出：维度框架（客群、运营、空间、成本、法规等）
- 用途：Node3 信息对齐时的维度覆盖检查
- 约束：不做具体专家任务排程

### 2.3 方法论（Methodology）

**回答问题**：流程上怎么做？按什么顺序做？

- 输出：追问顺序、门禁规则、验证闭环（HEVA等）
- 用途：驱动 Node3/Node4 的推进策略
- 约束：不重复定义“民宿是什么”

### 2.4 本体论（Ontology）

**回答问题**：系统如何结构化理解“民宿世界”？

- 输出：概念、关系、属性、约束（机读）
- 用途：语义标准化、冲突检测、检索增强
- 约束：不替代流程方法论

### 2.5 案例（Case）

**回答问题**：历史上别人怎么做，结果如何？

- 输出：背景-决策-结果-复盘
- 用途：提示、类比、反例提醒
- 约束：不作为唯一规则源

### 2.6 知识底盘（Knowledge Backbone）

**回答问题**：系统的稳定复用能力是什么？

- 输出：可复用能力原子（约束识别、冲突诊断、验证器等）
- 用途：在所有类型项目中稳定复用
- 约束：尽量去业务化，不写“民宿专属定义”

### 2.7 民宿项目全概念清单（详细）

> 目的：把“你到底在管理哪些概念”一次讲清，避免后续讨论时跨层混用。

#### A. 项目识别与分流概念（分类层）

1. **`project_type`（项目类型）**
   - 定义：系统用于路由的标准类型键。
   - 民宿示例：`hospitality_homestay`。
   - 边界：只负责识别与路由，不负责流程策略。

2. **`canonical_id`（规范主ID）**
   - 定义：同义词统一后的唯一业务标识。
   - 民宿示例：民宿/客栈/旅居/度假民宿 → `hospitality_homestay`。
   - 边界：一个概念只能有一个 canonical_id。

3. **`synonyms`（同义词字典）**
   - 定义：输入归一化词表，用于提高识别召回。
   - 民宿示例：`["民宿","客栈","旅居","度假民宿"]`。

4. **`mode_router`（模式路由）**
   - 定义：基于 `project_type + intent + risk` 的运行模式选择器。
   - 输出：对话态 / 项目态、是否触发 Node3/Node4 主链。

#### B. 项目定义与推进概念（主方法论层）

5. **Node1（输入接入）**
   - 作用：接收用户输入，提取初始意图与约束信号。

6. **Node2（门禁与分流）**
   - 作用：做 accept/clarify/reject 判定，控制是否进入项目态主链。

7. **Node3（信息对齐）**
   - 作用：定义问题、锁定目标与边界，形成冻结基线 `AlignedBrief`。

8. **Node4（初步设计）**
   - 作用：基于 Node3 冻结基线产出 `InitialDesignPack`。
   - 规则：Node4 不直接改题，改题需回退 Node3。

9. **`HEVA` / `HEVA-A`（验证闭环）**
   - 定义：假设-证据-验证-动作闭环；A 版本用于冻结前门禁（PASS/PASS-WARN/FAIL）。

#### C. 通常框架体系概念（Domain Framework 层）

10. **框架维度（Domain Dimensions）**
  - 民宿常见：客群结构、运营模型、空间分区、实施约束、风险与验证。
  - 用途：做“覆盖检查”，避免遗漏关键面向。

11. **`framework_coverage`（框架覆盖率）**
  - 定义：当前需求与方案对框架维度的覆盖程度。
  - 用途：Node3 检查是否缺口过大。

12. **`activation_policy`（框架激活策略）**
  - 定义：在何节点、何条件下激活哪些模块（追问、层级、HEVA）。

#### D. 本体论概念（Ontology 层）

13. **实体（Entity）**
  - 民宿示例：客房、公区、后勤区、运营方、住客类型。

14. **关系（Relation）**
  - 民宿示例：包含、服务、约束、冲突。

15. **属性（Attribute）**
  - 民宿示例：容量、噪声敏感度、运营季节性、预算区间。

16. **约束（Constraint）**
  - 民宿示例：消防前置、客流与后勤动线分离。

17. **本体作用边界**
  - 作用：定义语义、校验一致性、支持检索。
  - 非作用：不替代流程决策。

#### E. 辅助方法论概念（增强层）

18. **终极追问引擎（Ultimate Questioning）**
  - 作用：识别假设盲区、做反事实压力测试。
  - 成熟项目定位：低频风险校验器，不是高频主流程驱动器。

19. **用户需求层级框架（Need Hierarchy）**
  - 作用：把需求分层（刚需/享受/精神 × 实用/情绪价值）。
  - 成熟项目定位：价值覆盖审计器，避免“只做显性需求”。

20. **辅助方法论触发条件**
  - 高风险变更、冲突新增、外部约束变化。
  - 默认静默，不满足条件不触发。

#### F. 知识底盘与案例概念（物理隔离、运行关联）

21. **知识底盘能力原子（Capability Atoms）**
  - 例：约束识别器、冲突诊断器、质量门控器、解释器。
  - 特征：跨类型复用、尽量去业务化。

22. **案例层（Evidence Layer）**
  - 例：成功样例、失败样例、复盘结论。
  - 角色：证据与类比，不是规则主源。

23. **案例与底盘关系**
  - 推荐：**物理隔离存放**（不同目录、不同文件、不同维护责任人）。
  - 运行时关系：底盘提供“检索与评估能力”，案例提供“经验内容”；二者仅通过 `case_for` / 本体标签进行关联，不合并定义。

#### G. 治理与防混淆概念（元规则层）

24. **单一真相源（Single Source of Truth）**
  - 类型主定义：分类层 + 本体层。
  - 方法层与案例层只引用不重复定义。

25. **回退规则（Reflow Rule）**
  - Node4 改题越界 → 回退 Node3。

26. **冻结对象（Frozen Objects）**
  - `AlignedBrief`（Node3）
  - `InitialDesignPack`（Node4）

27. **突破层（L5 元认知层）**
  - 目的：检查、打破、突破，防止路径依赖。
  - 节奏：里程碑触发，不高频常开。

## 3. 民宿空间模拟：各自放哪里

## 3.1 建议放置（目录/配置）

- 空间分类：`config/project_type_registry.yaml`
  - `hospitality_homestay` 类型主定义（canonical）
- 通常框架体系：`config/domain_frameworks.yaml`
  - `hospitality_homestay.framework`
- 方法论：`sf/2026.3.22/S-方法论/*.md`
  - 用 `applies_to: hospitality_homestay` 关联
- 本体论：`intelligent_project_analyzer/knowledge_base/ontology.yaml`
  - 实体：客房/公区/后勤区/运营方/住客/季节性等
  - 关系：包含/依赖/冲突/约束
- 案例：`sf/2026.3.22/CASE_*.md`
  - 增加 `case_for: hospitality_homestay`
- 知识底盘能力：`intelligent_project_analyzer/services/*`
  - 如：约束加载器、验证器、规则解释器

## 3.2 去重主原则（防“民宿三处重复定义”）

- 唯一主定义：`project_type_registry` + `ontology`。
- 方法论文档不再定义“民宿是什么”，只引用 `hospitality_homestay`。
- 案例不定义规则，只给证据与经验。
- 知识底盘不定义业务类型，只提供能力。

## 3.3 三者隔离硬规则（防“写到一起”）

- 本体论、案例、知识底盘：**三处独立存放，禁止合并成一个文件或同一配置块**。
- 允许的只有“引用关系”，不允许“内容拷贝粘贴式重复定义”。
- 任何涉及民宿语义定义的新增字段，优先落 `ontology.yaml`；
  案例仅保留事实证据；
  底盘仅保留可复用能力。

## 4. 运行方式 A：没有知识底盘时（可跑，但弱）

### 4.1 运行链路

1. 输入文本命中“民宿”关键词 → 分类器识别为 `hospitality_homestay`（规则/关键词）。
2. Node3 按民宿方法论模板追问与对齐。
3. Node4 依据通用任务模板生成初步设计包。
4. 用少量案例做提示（非强约束）。

### 4.2 特征与风险

- 优点：快速可用，实施成本低。
- 风险：
  - 同义词不统一（民宿/客栈/旅居）
  - 约束遗漏（消防、运营旺淡季、噪声邻里冲突）
  - 跨项目复用一致性弱

---

## 5. 运行方式 B：有知识底盘时（稳定增强）

### 5.1 运行链路

1. 输入 → 分类器确定 `hospitality_homestay`。
2. 读取本体论与框架：加载“民宿相关概念图 + 必检约束”。
3. Node3：
   - 框架覆盖检查（客群/动线/运营/法规/预算/时间）
   - 方法论追问器按优先级补齐缺口
4. Node4：
   - 任务编排器依据本体关系生成更稳的任务图
   - HEVA/质量门按本体约束做一致性校验
5. 案例检索：按本体标签召回相似项目，给决策支持。

### 5.2 增强效果

- 概念统一：同词异义下降
- 缺口减少：关键约束更不容易漏
- 可解释性更好：每条建议可追溯到“框架/方法/本体/案例”来源

## 6. 民宿项目“单次模拟”示例（简版）

### 6.1 输入

“我要做一个山地度假民宿，预算中等，希望四季可运营，兼顾年轻客群和家庭客群，工期8个月。”

### 6.2 系统分层处理

- 空间分类：`hospitality_homestay`
- 框架体系命中维度：
  - 客群结构、淡旺季运营、客房产品层级、公区社交、后勤效率、消防与审批
- 方法论动作（Node3）：
  - 先锁终局（全年运营模型）
  - 再锁约束（预算/工期/审批）
  - 再锁验证（入住率、复购、运营成本）
- 本体论约束：
  - 客房数量与服务动线关系
  - 公区噪声与家庭客群冲突关系
  - 山地条件与设备维护关系
- 案例召回：
  - 山地民宿A（成功）：四季产品切换机制
  - 山地民宿B（失败）：动线冲突导致运维成本失控

### 6.3 输出产物（示意）

- `AlignedBrief`：明确“全年运营能力”为核心命题
- `InitialDesignPack`：
  - 三类客房策略
  - 公区-后勤动线分离
  - 预算分层投放与里程碑验收

## 7. 最终落地规则（团队执行口径）

1. 同一业务概念只允许一个 canonical ID。  
2. 类型定义在分类/本体层，方法层只引用。  
3. 案例是证据，不是规则主源。  
4. 无底盘可跑通；有底盘后优先走“本体约束 + 方法编排 + 案例验证”。  
5. 若 Node4 出现改题行为，必须回退 Node3 重对齐。

---

## 8. 给当前仓库的最小实施顺序（建议）

1. 先统一 `hospitality_homestay` canonical ID（分类层）。  
2. 在 `domain_frameworks` 写民宿通常框架。  
3. 在方法论文档改为 `applies_to` 引用，不再重复定义。  
4. 在 `ontology.yaml` 增补民宿核心实体与关系。  
5. 案例补 `case_for` 标签并接入检索。  
6. 最后再做“门禁与S1-S5节点”规则联动。

## 10. 民宿项目全过程（全概念挂接版）

> 目标：把 `2.7` 中 1~27 个概念，按系统真实执行顺序逐段挂接，做到“看流程就能知道每个概念何时触发、做什么、产出什么”。

### 10.1 流程图（文字版）

`用户输入`  
→ `Node1 输入接入`（抽取意图/约束信号）  
→ `Node2 门禁分流`（accept/clarify/reject）  
→ `项目态进入 Node3 信息对齐`（框架覆盖 + 本体一致性 + 条件触发辅助方法）  
→ `冻结 AlignedBrief`  
→ `Node4 初步设计`（任务编排 + 质量门）  
→ `冻结 InitialDesignPack`  
→ `若 Node4 改题越界 => 回退 Node3`  
→ `通过后进入后续深化执行`。

### 10.2 分阶段挂接矩阵（人话版）

| 阶段 | 主动作 | 必触发概念（编号） | 条件触发概念（编号） | 阶段产物 |
|---|---|---|---|---|
| S0 输入解析 | 识别民宿意图与关键约束 | 1,2,3,4,5 | - | 输入结构化草稿 |
| S1 门禁分流 | 判定 accept/clarify/reject | 6,9 | 20 | 进入项目态或补充问题 |
| S2 信息对齐 | 锁目标、边界、验证口径 | 7,10,11,12 | 18,19 | `AlignedBrief` |
| S3 语义校验 | 校验实体/关系/约束一致性 | 13,14,15,16,17 | 21 | 语义一致的问题定义 |

### 10.4 四个高频场景（把概念串起来）

#### 场景 A：年轻客群夜间社交 vs 家庭客群安静休息

- S0/S2：由 10/11 发现“客群与空间分区”覆盖不足。
- S3：13~16 判定“公区噪声与客房静区”存在冲突关系。
- S5：21 启动冲突诊断器，给出高风险告警。
- S4：22 召回失败案例；23 用底盘对案例进行相似度解释。
- S6：若方案未解决冲突，9 门禁不通过或 25 回退 Node3。

#### 场景 B：四季运营目标与山地维护成本冲突

- S2：7 锁定“全年运营”为核心命题；10/11 检查运营维度。
- S3：15/16 校验季节性属性与维护约束。
- S4：22 召回“四季产品切换”成功案例。
- S5：8 产出分季策略设计；19 评估价值层级是否均衡。

#### 场景 C：预算 1200 万 + 工期 8 个月 + 高配置公区

- S2：7 锁定预算/工期边界；11 识别覆盖缺口。
- S3：16 识别约束冲突。
- S5：21 触发约束识别器，给“分期建设/优先级”建议。
- S6：26 冻结可执行版本，防止后续反复改题。

#### 场景 D：新增外部审批要求（政策变化）

- S1/S2：20 触发辅助方法论。
- S2：18 发起风险追问；12 激活补充流程。
- S3：16 更新约束校验。
- S6：24 确保定义仍以分类层+本体层为主，不把规则写进案例或底盘。

**结论**：
“民宿”可以出现在多个层，但必须遵循“**一个主定义源 + 多层引用协同**”。
没有知识底盘时系统可运行但一致性弱；有知识底盘后，系统从“能跑”升级到“稳定、可解释、可复用”。
