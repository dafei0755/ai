## 一、交叉校验结论（六份参考意见独立评估）

本模块在落地前，对六份参考意见进行了系统性交叉校验，以下为关键裁决：

### 1.1 采纳项

| 来源 | 核心贡献 | 采纳决策 |
|------|---------|---------|
| 参考1 | 独有"到达层"（到达疲劳/首感机制）填补主架构盲点 | 升层至七层，将到达层作为第二层 |
| 参考1 | 四类派生产出物（约束卡/机会卡/旅程卡/经营影响卡） | 作为 3.S.0 编译的标准交付结构 |
| 参考1 | 双模接入（项目态硬输入 vs 对话态软推断） | 完整采纳，防止对话流程被强制中断 |
| 参考1 | 增强版本元数据（poi_snapshot_at / climate_snapshot_at 等） | 纳入字段契约元数据层 |
| 参考4 | `emotional_tone` 字段（心境/情绪关键词） | 纳入 `urban_semantic` 子字段 |
| 参考5 | 法规地理约束（风貌管控/退界限高/历史保护） | 纳入 `constraints_and_opportunities.regulatory_constraints` |

### 1.2 冲突裁决

**冲突一：对象命名**
- 参考3/4/5 主张 `GeoContextBaseline`；参考1 主张 `SiteContextBaseline`；参考2 称 `Site Context Matrix`
- **裁决：保留主架构命名 `GeoCoordinateBaseline`**。"Coordinate"强调它是物理坐标锚定的产物，而非抽象上下文汇总；命名携带"这必须先点图"的强制语义，这正是本模块的架构原则。别名兼容：文档中提到 `GeoContextBaseline` 时指同一对象。

**冲突二：节点落位**
- 参考3 建议新增 Node0（地理为第一大节点）
- **裁决：拒绝 Node0，保留两段式**。主链结构（Node1→Node2→Node3→Node4）不能被单一专项改写。两段式（Node1强制采集 + Node3.S.0深度编译）在不改主链编号的前提下实现了相同效果。

**冲突三：四校验器**
- 参考3 建议新增 PlaceFitValidator / ClimateFitValidator / MarketFitValidator / CulturalLegitimacyValidator 作为独立对象
- **裁决：降级为门禁检查项**。现有五门制（Contract/Geometry/System/Perception/Delivery）中，`PlaceFit` 和 `CulturalLegitimacy` 对应 Perception 门，`ClimateFit` 和 `MarketFit` 对应 System 门的地理合规校验。将其分列为新对象会引入额外治理开销，且与现有门禁体系重叠。

### 1.3 降级为远期愿景（不进当前对象契约）

- GIS 实时数据注入、3D Gaussian Splatting 带地理真实感渲染 → 列入扩展路线图
- 气候数据库自动爬取、规划一张图接入 → Phase 2-3 实现选项，非 Phase 1 硬依赖

## 二、架构判断

**一句系统原则：**

> 项目地理坐标不是普通背景字段，而是世界模型的入口锚点；项目态必须强制完成地图点选或地点确认，并将其编译为 `GeoCoordinateBaseline`，先于 `AlignedBrief + SPG` 进入对象链，用于约束问题定义、工作地图、梦幻团队与任务清单。

**为什么"地理坐标"不是信息，而是约束发生器：**

离开具体位置谈空间，不只是"不够严谨"，而是导致后续所有判断系统性失真：
- **风格失真**：强场地语境下，很多风格不是"可选项"，而是天然被排除的
- **功能失真**：同样是民宿，山地度假、城市塔尖、景区商业街，空间组织逻辑完全不同
- **商业失真**：周边竞品密度、交通可达、旅程节奏，直接重写盈利模型
- **情绪失真**：山地、海景、城市天际线，带来的不是景观差异，而是用户心境与期待差异
- **落地失真**：海拔、湿度、风压、日照，改变材料、设备、成本与寿命判断

## 三、两段式架构（不新增大节点）

```
Node1（强制采集）
  → geo_pin 地图点选 + 基础字段录入
  → 阻断规则：geo_pin 未完成 → 门禁不放行
  ↓
Node2 门禁（检查 geo_pin 完整性）
  ↓
Node3 内部步骤 3.S.0（地理坐标编译）
  → GeoCoordinateBaseline 深度解读与冻结
  → 七层地理智能提取
  → 生成四类派生产出物
  ↓
3.S.1 解题思路（消费 GeoCoordinateBaseline）
  ↓
3.S.2 工作地图（消费 GeoCoordinateBaseline）
  ↓
AlignedBrief + SPG + WorkMap + GeoCoordinateBaseline 同步冻结
```

**关键设计意图：**
- `3.S.0` 编号刻意先于 `3.S.1`；`GeoCoordinateBaseline` 冻结是 `3.S.1` 解题思路的硬前提
- Node3 消费的不是裸坐标，而是已编译的 `GeoCoordinateBaseline`
- Node4 消费的是被场地约束过的 `SPG / WorkMap`，而不是再次自行理解场地

## 四、双模接入机制

### 4.1 项目态：硬输入机制（强制点选）

适用于正式项目模式。用户须完成以下至少一项：

1. **地图点选**（优先）：在系统地图上直接点选项目位置
2. **精确地址**：精确到街道/楼盘/景区名称
3. **地块/物业确认**：上传用地红线图或建筑编号

> 没有完成此步骤，系统可以进入对话讨论，但不能进入高置信项目态冻结。`geo_pin` 未确认 → 门禁阻断。

### 4.2 对话态：软推断机制（先识别后确认）

适用于对话探索阶段或前期试探。

用户说出地点名称后，系统先做地点归一与置信度判断：

```
用户说："峨眉山七里坪"
→ 系统识别：四川省乐山市峨眉山市，高海拔山地度假区
→ 返回确认询问：「这里是高海拔康养山地度假区，项目为山地民宿/度假酒店场景，是否准确？」
→ 用户确认后，生成初步 GeoCoordinateBaseline（标记 confidence_level: provisional）
```

> 对话态的基线标记为 `provisional`，不得冻结为正式版本，须在项目态下完成点选后升级为 `v1.0 frozen`。

## 五、核心对象：GeoCoordinateBaseline

**独立对象，不嵌入 AlignedBrief**，被 `AlignedBrief`、`SPG`、`WorkMap` 三者同时消费。

### 5.1 字段分层概览

| 层级 | 字段组 | 采集阶段 |
|------|-------|---------|
| 锚点层 | `geo_pin` | Node1 强制 |
| 自然物理层 | `physical_context` | Node3.S.0 编译 |
| 到达与可达层 | `accessibility_context` | Node3.S.0 编译 |
| 城市语义层 | `urban_semantic` | Node3.S.0 编译 |
| 文化基因层 | `cultural_dna` | Node3.S.0 编译 |
| 市场环境层 | `market_context` | Node3.S.0 编译 |
| 约束与机会层 | `constraints_and_opportunities` | Node3.S.0 编译 |
| 世界模型锚点层 | `world_model_anchor` | Node3.S.0 编译 |
| 元数据层 | `metadata` | 全程维护 |

> 完整字段定义见 `03-GeoCoordinateBaseline字段契约.md`

### 5.2 与 AlignedBrief / SPG / WorkMap 的消费关系

```
GeoCoordinateBaseline
  │
  ├── → AlignedBrief
  │       target_audience ← urban_semantic.demographic_signal
  │       constraints     ← constraints_and_opportunities
  │       success_criteria ← market_context.competitive_gap
  │
  ├── → SPG
  │       strategy_scopes ← world_model_anchor + cultural_dna
  │       style_boundary  ← cultural_dna.taboo_styles（硬约束，不可被覆盖）
  │       zone_constraints ← physical_context + accessibility_context
  │
  └── → WorkMap
          specialist_roles ← 地理特殊性触发的专业席位
          task_priority    ← constraints_and_opportunities.risk_flags
          geo_driven_tasks ← unique_opportunities（每个机会对应至少一项专题任务）
```

## 六、四类派生产出物（3.S.0 标准交付结构）

`GeoCoordinateBaseline` 冻结后，必须同时输出以下四类卡片，作为 3.S.1 / 3.S.2 / Node4 的直接消费材料：

### A. 场地约束卡（什么不能做）
- 气候/材料禁区（不宜高维护材料、不宜特定工艺）
- 风格禁区（`taboo_styles` 强制传播至 SPG，不得被静默覆盖）
- 商业禁区（不宜做某类业态，例如周边餐饮竞争过强时不宜重兵押注餐饮）
- 法规禁区（风貌管控/限高/退界）

### B. 场地机会卡（什么值得放大）
- 地形/景观独特性（山景/海景/城市天际线/森林）
- 气候稀缺性（高海拔清凉/南方光照充足/北方四季明显）
- 人群心境契合点（逃离都市/仪式感/疗愈/身份表达）
- 差异化竞争缺口（周边未被填满的体验空白）

### C. 用户旅程卡（人以什么状态进入这个空间）
- 到达方式与疲劳值（高速3小时自驾 vs 地铁5分钟）
- 情绪入场状态（期待感/疲惫感/仪式感）
- 行为模式预测（家庭亲子周末/商务社交/情侣度假）
- 离开时情绪目标（恢复感/满足感/"还想再来"）

### D. 经营影响卡（商业模型会被场地怎样改写）
- 淡旺季波动与空间兼容性要求
- 周边餐饮竞争与本地餐饮定位策略
- 单客停留时长与空间配比权重
- 物流可达性与运营成本影响

## 七、治理规则

### 7.1 硬规则（阻断级）

1. **`geo_pin` 未完成 → 门禁不放行，Node3 不启动**。可进入对话态讨论，但不能进入项目态冻结。
2. **`GeoCoordinateBaseline` 未冻结 → `3.S.1` 不得启动**。解题思路必须基于已冻结的地理基线。
3. **`taboo_styles`（风格禁区）→ 作为硬约束传播至 SPG 和 InitialDesignPack**。不得被后续节点静默覆盖，违反时触发 `CulturalLegitimacy` 校验阻断。
4. **项目地点变更 → 触发 `GeoCoordinateBaseline v1.x` 版本化**。必须评估对 `AlignedBrief / SPG / WorkMap` 的影响范围，不得静默继承旧场地理解。

### 7.2 版本化规则

| 场景 | 版本操作 |
|------|---------|
| 初次点选并编译完成 | `GeoCoordinateBaseline v1.0`（frozen） |
| 局部字段更新（如发现竞品新数据） | `v1.x`（局部更新，标注字段级 diff） |
| 地点根本性变更（选址迁移）| 触发 `DerivedProject`，重新生成 `v1.0` |
| 对话态初步识别 | `provisional`（不冻结，仅供讨论） |

### 7.3 下游校验规则（对应门禁体系）

| 原参考意见校验器 | 映射至现有门禁 | 触发条件 |
|----------------|--------------|---------|
| PlaceFitValidator | Perception 门 | 方案风格是否符合地点身份与语境 |
| CulturalLegitimacyValidator | Perception 门 | 风格叙事是否"长在这里"，不强行空降 |
| ClimateFitValidator | System 门 | 材料/开口/光照是否适配气候条件 |
| MarketFitValidator | System 门 | 定位/业态/价格带是否被市场环境支持 |
