## 两大功能与四大节点（总览）

### 运行总原则（2026-03-26 补充）

1. **片段任务优先，完整项目可升级**：默认先接住真实片段需求，再判断是否升级主链；
2. **入口可断点，签收不可断链**：允许从中间阶段接入，但正式交付必须满足对象链与门禁；
3. **外部输入先归一化再执行**：CAD/SU/PDF/图片/文本都可进门，但必须先转为内部 `draft` 对象；
4. **系统定位是决策与编译中枢**：承接判型、编译、校验、回退，不替代外部工具全流程生产。

### Node 命名来源与严格定义（2026-03-22）

为避免“Node3 / Node4”被不同文档语境混用，统一口径如下：

1. **命名来源**
	- `Node1~Node4` 来自本文件定义的“项目态主链四大节点编号”，不是临时别名。
	- 编号与下列文件一一对应：
	  - `2 大节点1-用户输入.md` → Node1
	  - `3 大节点2-门禁.md` → Node2
	  - `4 大节点3-信息对齐.md` → Node3
	  - `5 大节点4-初步设计.md` → Node4

2. **Node3 是什么（严格定义）**
	- Node3 = **信息对齐节点（项目定义层）**。
	- 职责：把原始输入编译为可执行问题定义，并形成冻结基线 `AlignedBrief` 与空间程序图谱 `SpatialProgramGraph`（`SPG`）。
	- 边界：Node3 负责“定义清楚问题”，不负责输出最终实施成果包。

3. **Node4 是什么（严格定义）**
	- Node4 = **初步设计节点（项目决策层）**。
	- 职责：基于 Node3 冻结基线（`AlignedBrief + SPG`），形成可推进、可校验、可回溯的 `InitialDesignPack`。
	- 边界：Node4 负责“做成首轮决策包”，仅允许按 `SPG` 派生策略，不回写改题；改题应回到 Node3 对齐链。

4. **与历史标签的关系（防混淆）**
	- 历史资料中的 `S1/S2/S3/S4`（常见于武器文档）是**武器运行阶段标签**。
	- 现行主链以 `Node1~Node4` 为准；`S*` 仅作执行层历史标签，不替代 Node 定义。

5. **判定规则（执行时）**
	- 若讨论“问题定义、约束显性化、对齐冻结” → 归 Node3。
	- 若讨论“团队组建、任务编排、实施与成果冻结” → 归 Node4。
	- 若出现“在 Node4 直接改题” → 视为越界，回退 Node3。

### 功能层（对业务价值）

**功能 A：信息对齐（项目定义层）**

- 目标：把原始输入反推为“可执行的项目定义”（目标 / 约束 / 风险 / 验证）
- 产物：`AlignedBrief`（项目对齐简报）
- 结构化承接产物：`SpatialProgramGraph`（`SPG`，空间程序图谱）
- 关键步骤：终局目标澄清、关键变量识别、约束显性化、缺口补齐
- 设计行业适配：在 3.3 冻结前允许草图、参考图、粗模与候选方案进入探索比选；信息对齐的任务不是压制修改，而是把探索结果编译成当前阶段主版本
- 最小执法子步骤：`3.S.0` 地理约束编译 → `3.S.0.5` 功能用途交叉编译 → `3.S.0.6` 时间约束编译 → `3.S.0d` 人因编译与仲裁 → `3.S.1` 解题思路 → `3.S.2` 工作地图
- 内部承接：3.S.1 解题思路、3.S.2 工作地图
- 冻结治理：Node3 完成后同步冻结 `AlignedBrief v1.0 + SPG v1.0`，并显式绑定 `GeoCoordinateBaseline + UseIntentBaseline` 版本；任一基线升版，另一基线自动进入“需评估”状态；冻结代表“当前阶段主版本快照”，不等于后续不得继续修改

**功能 B：初步设计（项目决策层）**

- 目标：把已对齐的问题转成首轮“可执行决策包”（可推进、可校验、可回溯），并确保策略按 `SPG` 的模块/分区/流线映射输出
- 产物：`InitialDesignPack`（阶段性成果包 / 初步设计包）
- 关键步骤：跨专业协作编组、任务反推编排、执行与校验、成果审阅与冻结
- 分流治理：轻量级项目可在 Node4 结束；复杂项目以该成果包为基线进入“深化设计”后续分支
- 边界治理：Node4 仅做策略派生与执行收束，不静默改写 Node3 冻结的 `SPG` 上位结构

一句话：**信息对齐负责“把项目问题定义清楚”，初步设计负责“把首轮项目决策做成立”。**

### 流程层（对系统编排）

**大节点 1：用户输入（输入接入）**

- 作用：接收用户原始请求，形成项目态判断前的初始输入。
- 输入类型（并列合法入口）：
	- 文本入口（需求描述/目标/约束）
	- 结构图入口（CAD、平面图、建筑框架图、PDF底图）
	- 感知图入口（效果图、参考图、草图）
	- 系统对象入口（已有 `SPG/FloorPlanIR/VizSpec` 等）
- 执行要求：外部输入不得直接视为真相源，先进入归一化步骤生成 `draft` 对象。
- 输出去向：进入 **大节点 2：门禁与任务判型**。

**大节点 2：门禁与任务判型（前置治理与路由）**

- 作用：判断请求是否属于项目态处理范围，并决定后续路由。
- 第一步（领域门禁）结果：
	- `accept`：进入项目态主链
	- `clarify`：先做最小澄清，再重新判定
	- `reject`：结束或拒绝
- 前置条件：仅对“空间设计相关且在项目态主链处理范围内”的请求启动双态分流；不相关输入由门禁外拦截（out-of-scope），不进入双态判断。
- 第二步（任务判型）结果：
	- `dialog_fragment`（对话型片段任务）
	- `stage_fragment`（阶段性片段任务）
	- `incremental_revision`（增量修订任务）
	- `derived_rebuild`（派生重构任务）
	- `full_project`（完整项目任务）
- 第三步（工作区路由）：
	- 正式项目工作区（强治理）
	- 片段任务工作区（中治理）
	- 临时探索工作区（轻治理）
- 下一步：`full_project` 进入 **大节点 3：信息对齐**；其余类型按片段/临时流程执行，必要时触发转正进入 Node3。

**大节点 3：信息对齐（承载功能 A）**

- 作用：把原始输入反推为“可执行的问题定义”，并形成冻结基线 `AlignedBrief + SPG`。
- 对应二级步骤：
	- **3.1 信息梳理与追问**：把显性需求、隐性缺口、关键问题先拉出来。
	- **3.2 动机与目的锁定**：确认项目真正要达成什么终局目标。
	- **3.3 补充采集与确认**：把仍然缺失但会影响后续推进的关键信息补齐。
- 对应系统内部步骤：
	- **3.S.0 地理约束编译**：形成 `GeoCoordinateBaseline` 冻结候选版本；
	- **3.S.0.5 功能用途交叉编译**：形成 `FunctionalUseStatement / UseIntentBaseline`；
	- **3.S.0.6 时间约束编译**：形成 `TemporalBaseline`；
	- **3.S.0d 人因编译与仲裁**：形成 `HumanContextLayer`（非 Node1 并列输入基线）；
	- **探索比选回路（合法前置活动）**：允许草图/参考图/粗模形成候选版本，通过 `ComparisonBoard` 提炼约束、偏好与冲突，再进入 3.3 冻结；
	- **3.S.1 解题思路**：对齐过程中的内部推导，用于生成问题结构与求解方向。
		- 调用模块：终极追问引擎 + 用户需求层级框架（形成“追问结论卡 + 层级覆盖结论”）
		- 协同组织：用“一主两辅与多学科协同方法论”识别主线问题、驱动力修正轴与边界压缩轴，避免问题拆解失焦
	- **3.S.2 工作地图**：承接解题思路，作为大节点 4 中团队组建与任务安排的共同底盘。
		- 调用模块：HEVA（建立关键假设池与验证计划）
		- 组织产物：把主辅关系与多学科参与位编译为 `WorkMap`，为后续 `ExpertTeamPack` 与 `TaskArrangementPack` 提供依据
- 冻结产物：`AlignedBrief`、`SpatialProgramGraph (SPG)`
- 冻结规则：3.S.1/3.S.2 可形成 `SPG draft`；在 3.3 确认后同步冻结 `SPG v1.0`，且 `AlignedBrief` 必须记录双基线版本引用（`Geo + UseIntent`）
- 下一步：进入 **大节点 4：初步设计**。

**大节点 4：初步设计（承载功能 B）**

- 作用：基于 `AlignedBrief + SPG` 形成首轮“可执行、可校验、可回溯”的项目决策包 `InitialDesignPack`。
- 对外二级步骤（完整项目叙事，保留）：
	- **4.1 梦幻团队组建**：基于工作地图，形成跨专业协作清单，并明确主提 / 联提 / 审阅 / 否决等责任位。
	- **4.2 任务安排**：基于工作地图 + 团队清单，形成执行蓝图，并显式确定任务优先级、依赖关系与冲突仲裁路径。
	- **4.3 任务实施**：进入方向锁定与专题推进。
	- **4.4 成果审阅与冻结**：对阶段性成果做审阅、校验与冻结。
		- 调用模块：HEVA-A（PASS / PASS-WARN / FAIL），作为冻结前门禁。
- 运行时执行结构（多元任务口径，新增）：
	- **4.0 任务归类与输入归一化**：先判定本轮任务类型，并将外部输入编译为可治理 `draft` 对象。
	- **4.1 协同编组**：按任务类型自动编译本轮所需角色与责任位（可显式、可自动）。
	- **4.2 执行蓝图编排**：将依赖、顺序、冲突仲裁与冻结条件写入 `ExecutionPlan`。
	- **4.3 任务执行与专题推进**：执行专题动作，兼容完整项目推进与片段任务处理（含工件输入后的局部优化/诊断）。
	- **4.4 审阅、回退判定、转正与冻结**：先比较候选与风险，再决定回退 Node3、留在候选态，或转正冻结进 `InitialDesignPack`。
- 冻结产物：`InitialDesignPack`
- 派生规则：Node4 的专题策略必须绑定 `zone_id/module_id`，按 `SPG` 输出；若需改题或改上位空间结构，回退 Node3
- 分流治理：
	- 轻量级项目可在 Node4 结束
	- 复杂项目可据此进入后续深化设计分支

**后续分支：深化设计（按需触发，不强制）**

- 触发条件：只有当用户明确要求继续、当前成果不足以落地、复杂度超出轻量阈值，或关键风险仍未消解时，才进入此分支。
- 设计行业口径：持续改图、多方案比较、局部推翻重做都属于正常现象；本分支用于承接这种持续修改，而不是把修改视为异常情况。
- 防歧义规则（2026-03-26 补充）：片段任务中可在 Node2 / Node4.0 预执行部分深化前置能力（意图归类、上下文装载、动作草编），但这不等于深化分支本体前置；深化分支正式回合仍以 Node4 后触发为准。
- 对应回合步骤：
	- **R0 触发判定**
	- **R1 意图归类**
	- **R2 上下文装载**
	- **R3 动作编排**
	- **R4 执行协同与审阅**
	- **R5 回写收束与下一回合判定**

## 多入口归一化与转正（执行补充）

为保证“片段优先”不破坏主链治理，新增以下统一执行规范：

### 1) 外部工件归一化（Artifact Ingress）

统一链路：`外部输入 → ArtifactImportRequest → draft对象 → 路由执行`。

最小字段（必须落审计）：

1. `source_type`
2. `source_ref`
3. `parsed_confidence`
4. `missing_constraints`
5. `suggested_target_mode`
6. `writeback_policy`

### 2) 片段执行门禁（中治理）

片段任务可在约束不完整时启动，但必须：

1. 显式记录 `missing_constraints`；
2. 输出附带 `risk_notes` 与置信度；
3. 不得直接改写 `SPG/AlignedBrief` 冻结对象；
4. 触及结构变更时，提交 `Impact Matrix` 或升级回退。

### 3) 转正流程（片段/临时 → 正式）

满足以下条件才允许进入正式主链：

1. 补齐最小上游约束（至少 `GeoCoordinateBaseline + UseIntentBaseline`）；
2. 完成对象绑定与作用域绑定校验；
3. 通过 Gate；
4. 生成正式冻结引用（含 `source_frozen_id`）。

未通过转正校验时，结果仅可留在片段/临时工作区，不得作为正式交付签收。

### 4) 深化预执行与正式回合边界

1. Node2 / Node4.0 可预执行：任务判型、上下文装载、动作草编（对应 R0~R3 的前置能力）；
2. Node4 后才可进入深化正式回合：执行协同与审阅、回写收束与下一回合判定（R4~R5）；
3. 任何涉及正式签收的结果，必须经过 R4/R5 或等价治理，不得以前置预执行结果直接冒充深化结论。

- 本文聚焦**双态架构中的项目态主链**；对话态仍然保留，用于轻量问答、试探方向、局部判断与项目后的解释 / 修订 / 派生。
- 本版采用双层表达：**功能层（价值能力）+ 流程层（系统编排）**。
- 本版同时保留四种结构元素：**大节点 / 二级步骤 / 系统内部步骤 / 后续分支**。
- 主链由 4 个大节点构成：**用户输入 → 门禁 → 信息对齐 → 初步设计**。
- `AlignedBrief` 与 `SPG` 是大节点 3 的同步冻结产物：前者承接“问题基线”，后者承接“空间结构化真相源”。
- `InitialDesignPack` 是大节点 4 的冻结产物，用于承接“首轮可交付成果”；轻量级项目可在此结束，复杂项目可据此进入深化设计。
- 双态详细定义（对话态 / 项目态、门禁 `clarify`、升级/回落接口）见：`../C 双态/01-系统双态专题.md`。
- 双态分流的前提是领域相关性：请求需与空间设计相关且在项目态主链处理范围内；不相关输入由门禁外拦截处理。
- “解题思路、工作地图”不单列为大节点，而是大节点 3 内部的系统承接步骤，服务项目问题定义与后续项目决策推进。
- “深化设计”不是并列主链大节点，而是大节点 4 之后的按需后续分支；其内部正式步骤保留 `R0-R5` 回合制。
- 后续追问与深化设计不直接改写上游冻结对象；若用户提出改题 / 重定义 / 补充核心条目，应回到对应冻结成果页处理，避免跨阶段改题导致链路混乱。
- 对空间结构的修改遵循版本化：局部增量形成 `SPG v1.x`，范式变化触发 `DerivedProject`。
- 运行时执法机制：阶段推进前由 `Gate Guardian` 校验前置冻结；对象写回前由 `ContractValidator` 校验 `source_frozen_id` 与作用域越权；结构变更未提交 `Impact Matrix` 时由 `Impact Enforcer` 阻断。
- 版本优先治理：项目全程允许候选版本并行，但每个阶段只能有一个主版本；冻结是主版本快照，不是“从此不许再改”。
- 探索/候选分支治理：允许在沙盒或候选链中持续比较与反复改图（需责任人、变更原因、审计留痕），但不得构成平行真相源；转正写回必须经 Gate、`ComparisonBoard` 与影响分析。

## 扩展接入流程（插件化执行）

为支持架构稳定后的插拔式进化，新增项统一按以下流程接入：

1. 先分类：`Role Plugin / Knowledge Plugin / Capability Plugin / Topic Plugin`；
2. 再定层：角色进 `ExpertTeamPack`，能力进“能力执行层+基础接口层”，知识进“知识与记忆层”；
3. 再过门禁：冻结引用、作用域绑定、影响分析、阶段顺序、审计留痕五项全通过；
4. 再上线：通过后纳入 `ExecutionPlan` 执行编排。

硬规则：新增项默认不得改主链，不得新增平行真相源；仅当满足独立目标、稳定输入输出、独立校验与 `SPG` 绑定时，才评估升格为新专题系统。

## 如何区分：大节点、二级步骤、系统内部步骤、后续分支

### 大节点

大节点是项目主链上的**骨架层**，回答的是：

- 现在流程走到哪一段；
- 这一段承担什么职责；
- 要向下一个环节交接什么。

在当前口径里，大节点是：

- 大节点 1：用户输入
- 大节点 2：门禁
- 大节点 3：信息对齐
- 大节点 4：初步设计

一句话：**大节点是整条主链的分段。**

### 二级步骤

二级步骤是挂在某个大节点下面的**内部推进步骤**，回答的是：

- 这个大节点内部具体怎么完成；
- 先做什么，后做什么；
- 哪些步骤构成冻结链或回合链。

在当前口径里：

- 大节点 3（信息对齐）下的二级步骤是 `3.1 → 3.3`，即信息梳理与追问、动机与目的锁定、补充采集与确认
- 大节点 4（初步设计）下的**对外二级步骤**是 `4.1 → 4.4`，即梦幻团队组建、任务安排、任务实施、成果审阅与冻结
- 大节点 4（初步设计）下的**运行时执行结构**是 `4.0 → 4.4`，即任务归类与输入归一化、协同编组、执行蓝图编排、任务执行与专题推进、审阅/回退判定/转正与冻结

一句话：**二级步骤不是新的大节点，而是某个大节点内部的走法。**

### 面向系统的内部步骤

系统内部步骤指的是：**存在于系统编排与认知组织层，但不单独升格为大节点的内部推导/内部对象/内部底盘。**

在这条链里，典型代表是：

- 系统内部步骤 3.S.1：解题思路
- 系统内部步骤 3.S.2：工作地图

它们的作用分别是：

- **解题思路**：位于信息对齐过程中，是大节点 3 内部的系统承接步骤，用于生成后续工作结构；
- **工作地图**：承接解题思路，作为初步设计中团队组建与任务安排的共同底盘。

在新的口径里，它们更准确地承担：

- **解题思路**：位于信息对齐过程中，是大节点 3 内部的系统承接步骤，用于生成问题结构与求解方向；
- **工作地图**：承接解题思路，作为大节点 4 中梦幻团队组建与任务安排的共同底盘。

因此它们更适合被理解为：

- 不是大节点；
- 也不是对外独立主链步骤；
- 而是服务于大节点 3 内部、并向大节点 4 提供底盘支撑的**系统内部步骤/内部对象**。

一句话：**系统内部步骤负责支撑步骤，不单独成为主链节点。**

### 后续分支

后续分支指的是：**主链完成后，只有在用户明确要求继续、当前成果不足以落地、复杂度超出轻量阈值，或关键风险尚未消解时，才按需触发的后继工作域。**

在当前口径里，典型代表是：

- 深化设计（`R0 → R5` 回合制）

它回答的是：

- 当前阶段性成果之后是否还需要继续；
- 如果继续，本轮想深化、修订、派生什么；
- 如何在不改写上游冻结对象的前提下完成下一轮推进。

一句话：**后续分支不是主链必经段，而是主链之后的按需延展。**

## 最简单判断法

- 如果它在项目主链上承担一整段职责，就是**大节点**。
- 如果它是某个大节点内部的正式推进序列，就是**二级步骤**。
- 如果它主要服务于系统内部推导、编排、承接与组织，但不单独对外成段展示，就是**系统内部步骤**。
- 如果它只在主链完成后按条件触发、并以回合方式持续推进，就是**后续分支**。

- **大节点**：1 用户输入、2 门禁、3 信息对齐、4 初步设计
