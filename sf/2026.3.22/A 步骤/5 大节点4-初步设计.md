# 5 大节点4-初步设计

> 备注（2026-03-22）：
> 本文用于展开大节点 4「初步设计」的正式二级步骤，以及其后“深化设计”分支的衔接关系。
>
> 说明：当前文件名仍沿用旧命名，仅作为过渡；本文现行口径以“初步设计”为准。

## 节点定位

**大节点 4：初步设计**

它负责把已完成信息对齐的问题基线，转化为首轮可交付成果，并在必要时冻结为后续深化设计的稳定输入。

它对用户呈现为一个统一的大阶段，但对系统内部仍保留清晰分层：

- 谁来做：梦幻团队组建
- 怎么做：任务安排 / 执行蓝图（`TaskArrangementPack`）
- 做出了什么：任务实施
- 如何收口：成果审阅与冻结

补充口径（2026-03-26）：Node4 采用“双视图”表达——

1. 对外仍保留 `4.1~4.4`（完整项目叙事）；
2. 运行时采用 `4.0~4.4`（多元任务执行结构）。

## 边界治理（硬规则）

- 大节点 4 完成后，必须显式形成一个阶段性成果页（`InitialDesignPack`）。
- 设计行业默认存在持续改图与多轮方案比较；Node4 必须以“版本优先治理”承接修改，而不是假设本节点只会做极少数修订。
- `InitialDesignPack` 的修改、补充或继续深化，必须在该成果页完成版本化改版（如 `v1.0→v1.1`），不得在其他节点或回合中隐式改写。
- `AlignedBrief + SPG + WorkMap` 仍是上游定义对象；若用户提出改题 / 重定义 / 补充目标边界 / 更改成功标准 / 改上位空间结构等诉求，必须先回信息对齐成果页处理。
- 深化设计与项目后追问阶段，不直接改写上游冻结对象；若要改上游定义，按冻结对象逐级回退。
- 完整项目口径下，深化设计分支仅可消费 `InitialDesignPack` 并产出增量交付/比较结论，不得直接改写 `InitialDesignPack` 本体；如需调整初步设计，必须回到 `InitialDesignPack` 结果页改版后再进入后续回合。
- Node4 仅允许在 `SPG` 约束下做策略派生：空间作用域产物需绑定 `zone_id/module_id`；跨域产物需绑定对象版本与作用范围。
- Node4 所有策略写回需声明 `source_frozen_id`（至少绑定 `AlignedBrief/SPG` 版本）；缺失时不得进入冻结。
- Node4 可存在“阶段主版本 + 多个候选版本”并行，但正式冻结时只能选择一个主版本写入 `InitialDesignPack`。

## 核心作用

- 基于 `AlignedBrief + SPG + WorkMap` 组织首轮设计推进
- 将工作地图编译为团队与执行蓝图（`ExpertTeamPack + TaskArrangementPack`）
- 推进方向锁定与专题判断
- 显式审阅并冻结阶段性成果
- 为轻量项目提供完成点，为复杂项目提供深化基线

其中：

- `ExpertTeamPack` 负责把 `WorkMap` 中的多学科参与位编译为真实协作席位；
- `TaskArrangementPack` 负责把主线问题、两辅约束与冲突仲裁路径编译为可执行顺序；
- 两者共同保证 Node4 不是“先凑团队再找理由”，而是“按 Node3 已定义的问题结构继续推进”。

## 对外二级步骤（完整项目叙事，保留）

- **4.1 梦幻团队组建**
- **4.2 任务安排**
- **4.3 任务实施**
- **4.4 成果审阅与冻结**

## 运行时执行结构（多元任务口径）

- **4.0 任务归类与输入归一化**：先判定本轮任务类型，并将外部输入编译为可治理 `draft` 对象。
- **4.1 协同编组**：按任务类型自动编译本轮所需角色与责任位（可显式、可自动）。
- **4.2 执行蓝图编排**：将依赖、顺序、冲突仲裁与冻结条件写入 `ExecutionPlan`。
- **4.3 任务执行与专题推进**：执行专题动作，兼容完整项目推进与片段任务处理（含工件输入后的局部优化/诊断）。
- **4.4 审阅、回退判定、转正与冻结**：先比较候选与风险，再决定回退 Node3、留在候选态，或转正冻结进 `InitialDesignPack`。

## 输入

- `AlignedBrief`
- `SpatialProgramGraph (SPG)`
- `WorkMap`
- 已确认的项目上下文
- 必要素材、案例与补充条件

补充口径（2026-03-26）：Node4 的正式冻结输入应来自正式主链对象；片段任务工作区的结果默认作为建议态/候选态输入，需经转正后才可作为正式签收依据。

## 输出

- `InitialDesignPack`（阶段性成果包 / 初步设计包）
- `ComparisonBoard`（候选方案比较与转正结论）
- 团队清单（`ExpertTeamPack`）
- 执行蓝图 / 任务清单（`TaskArrangementPack`）
- 方向锁定与专题结论
- 审阅冻结结果

补充规则：

1. 片段任务可在 Node4 能力域内生成建议与候选版本，但不直接构成正式 `InitialDesignPack`；
2. 若要签收为正式阶段成果，必须绑定正式 `source_frozen_id` 并通过 Gate；
3. 未转正候选只能留在 `ComparisonBoard` 候选区，不得冒充主版本。

其中建议补充：

- `ExpertTeamPack` 至少显式声明各角色责任位（主提 / 联提 / 审阅 / 否决 / 观察）；
- `TaskArrangementPack` 至少显式声明任务优先级、依赖关系、冲突仲裁路径与冻结签署条件。

## `InitialDesignPack` 建议内容

建议至少包含以下内容：

- 项目目的与关键边界（引用 `AlignedBrief`）
- `SPG` 作用域引用（模块/分区/流线）
- 工作地图摘要（引用 `WorkMap`）
- 团队清单（引用 `ExpertTeamPack`）
- 任务清单 / 执行蓝图（引用 `TaskArrangementPack`）
- 方向锁定结论
- 专题推进结论
- 待验证风险
- 后续建议（停止 / 继续深化 / 返回修改）

## Node4 内部对象链（决策层）

```text
SPG
	→ WorkMap
	→ ExpertTeamPack
	→ TaskArrangementPack
	→ ComparisonBoard
	→ InitialDesignPack
```

说明：

- `4.1` 产出 `ExpertTeamPack`；
- `4.2` 产出 `TaskArrangementPack`；
- `4.3/4.4` 在上述对象基础上收束为 `InitialDesignPack`；
- 任何触及上位空间结构的变更都不在 Node4 内闭环，必须回退 Node3。

补充：

- `4.1` 不只是“找人”，而是把 `WorkMap` 里的多学科参与位落成责任矩阵；
- `4.2` 不只是“排活”，而是把主线问题、两辅约束、专题冲突与冻结顺序排成可执行链；
- `4.4` 冻结前必须确认：有责任人、有审阅人、有必要时的否决位，否则只能停留在草案态。

## Node4 版本治理（设计行业常态）

1. Node4 默认承接持续修改，不以“一轮出完就不动”为前提；
2. 每次调整都应尽量先在对应专题或对应 Pack 局部吸收，避免动辄整链推翻；
3. 若同一问题存在多个候选方向，应进入 `ComparisonBoard` 明确差异、适用条件与保留理由；
4. 冻结 `InitialDesignPack` 时，选择的是“当前阶段主版本”，而不是项目最终唯一版本；
5. 若修改触及 `SPG` 上位结构或 `AlignedBrief` 核心命题，立即停止 Node4 内部兜底，回退 Node3。

## 深化设计分支接口

“深化设计”不是并列主链大节点，而是大节点 4 完成后的按需后续分支。

深化设计流程展开见：[`6 后续分支-深化设计.md`](./6%20后续分支-深化设计.md)。

建议仅在以下情况触发：

- 用户明确要求继续
- 当前成果不足以落地
- 项目复杂度超出轻量级阈值
- 关键风险尚未消解
- 需要更高精度交付物

其内部正式步骤继续保留回合制：

- **R0 触发判定**
- **R1 意图归类**
- **R2 上下文装载**
- **R3 动作编排**
- **R4 执行协同与审阅**
- **R5 回写收束与下一回合判定**

补充执法口径（2026-03-26）：

1. 深化分支中的“回写”默认指向 `DeltaDelivery/ComparisonBoard/回合记录`，不指向 `InitialDesignPack` 本体；
2. 任何对完整项目初步设计内容的改动，都必须先回到 `InitialDesignPack` 结果页完成版本更新；
3. 未经结果页版本更新的深化改动，不得作为初步设计签收依据。

## 建议后续展开的小节

- 对外二级步骤：4.1 梦幻团队组建、4.2 任务安排、4.3 任务实施、4.4 成果审阅与冻结
- 运行时执行结构：4.0 任务归类与输入归一化、4.1 协同编组、4.2 执行蓝图编排、4.3 任务执行与专题推进、4.4 审阅/回退判定/转正与冻结
- 深化设计分支：R0-R5 回合制

## 与上下游关系

- 上游：消费大节点 3 交付的 `AlignedBrief + SPG + WorkMap`
- 边界：不在本节点改写 `AlignedBrief/SPG/WorkMap`；若需改题或改上位空间结构，回到信息对齐成果页触发
- 下游：轻量级项目可在本节点结束；复杂项目以 `InitialDesignPack` 为基线进入“深化设计”分支；若进入正式交付，按 `ConceptPack → FloorPlanPack → VisualizationPack → ConstructionPack` 依次推进，不可跨越；项目交付完成后回归对话态，继续解释、修订与派生

## 运行时执法提示（执行侧）

- `Gate Guardian`：阶段推进前校验前置冻结是否齐全，缺失则阻断并返回补条件；
- `ContractValidator`：对象写回前校验 `source_frozen_id` 与作用域越权，未通过不得冻结；
- `Impact Enforcer`：触及结构变更但未提交 `Impact Matrix` 时，阻断并要求先走影响分析流程。

## 协同组织补充规则

1. 若 `ExpertTeamPack` 只有专家名称、没有责任位，则视为未编译完成。
2. 若 `TaskArrangementPack` 只有任务列表、没有依赖与仲裁路径，则视为未编译完成。
3. 若专题结论之间存在冲突但未标出审阅位或否决位，不得进入 `4.4` 冻结。
4. 若冻结时发现问题定义本身不成立，应回退 Node3，而不是在 Node4 局部补丁式掩盖。
