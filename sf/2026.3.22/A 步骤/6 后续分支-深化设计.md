# 6 后续分支-深化设计

> 备注（2026-03-24）：
> 本文用于展开项目态主链在 Node4（初步设计）之后的后续分支“深化设计”，强调其**流程推进用途**（何时触发、如何执行、如何收束）。
>
> 口径区分：
> - 本文（`A 步骤`）= 流程执行专题（面向“怎么推进”）
> - `../B 架构/07-深化设计专题.md` = 架构解释专题（面向“为什么这样设计”）

## 分支定位

“深化设计”不是并列主链大节点，而是 Node4 完成后的按需后续分支。

它回答的是：

- 要不要继续推进；
- 继续的话本轮做什么；
- 如何在不破坏上游冻结对象的前提下持续推进。

设计行业补充口径：持续改图、持续改方案、多轮比较与局部推翻重做，是本分支要默认承接的正常工作方式，不是异常情况。

## 与 Node2 / Node4.0 的关系（防“前置误读”）

片段任务模式下，Node2 / Node4.0 可预执行部分深化前置能力（如意图归类、上下文装载、动作草编），用于快速响应。

但执法边界不变：

1. 这些预执行能力不等同于深化分支本体启动；
2. 深化分支正式回合仍以 Node4 后触发为准；
3. 涉及正式签收的结论必须经过 R4/R5（或等价审阅与回写治理）。

## 进入条件（触发门槛）

仅在满足以下任一条件时进入：

- 用户明确要求继续深化；
- `InitialDesignPack` 仍不足以落地执行；
- 项目复杂度超过轻量级收口阈值；
- 关键风险未消解，需追加验证与修订。

不满足时，项目可在 Node4 收束。

补充口径（2026-03-26）：当用户仅提出局部问题（如仅动线、仅色彩、仅材料）时，可由片段任务工作区直接触发本分支回合，不强制重跑完整主链。

## 输入与边界

### 输入

- Node4 冻结产物：`InitialDesignPack`
- Node3 冻结基线：`AlignedBrief + SpatialProgramGraph (SPG) + WorkMap`
- 本轮用户新增意图与约束
- 当前回合历史记录（审阅结论、遗留风险）

片段触发最小输入（可替代完整输入集）：

1. 本轮作用域（专题/分区/对象）；
2. 来源引用（`draft_ref` 或 `source_frozen_id`）；
3. 目标类型（建议态/派生态/转正候选）；
4. 缺失约束清单（若存在）。

### 边界（硬规则）

- 深化设计不直接改写 `AlignedBrief / SPG / WorkMap` 与上游冻结内容。
- 深化设计不直接改写 `InitialDesignPack` 本体；完整项目下若需修改初步设计，必须回到 `InitialDesignPack` 结果页完成版本更新。
- 若用户提出改题 / 重定义 / 成功标准重设，必须回退 Node3 处理。
- 若仅对既有成果做局部修订，可走 `DeltaDelivery`；
- 若触及上位空间结构、核心命题或项目范式变化，应触发 `DerivedProject`，而不是在本分支内硬改。
- 每一回合都要显式产出可回溯记录，不能只留口头结论。
- 每一回合允许存在多个候选版本并行，但必须在收束前通过 `ComparisonBoard` 选定当前主版本。
- 片段回合允许约束不完整启动，但必须显式输出 `missing_constraints` 与 `risk_notes`；若结果拟进入正式签收，必须先走转正流程。

### 对象级分流规则

- **局部深化 / 局部修订**：保持 `SPG` 上位结构不变，在 `DeltaDelivery/DeliveryBundle/ComparisonBoard` 上形成增量回写；若需改初步设计内容，回到 `InitialDesignPack` 结果页改版；
- **结构级调整**：涉及分区、流线、上位策略作用域变化时，回退 Node3，生成 `SPG v1.x`；
- **范式级变化**：涉及业态、核心目标、成功标准、主命题变化时，触发 `DerivedProject`。

## 回合流程（R0-R5）

### R0 触发判定

- 判断是否进入深化分支；
- 明确本轮目标与停止条件。
- 片段任务中的“预判型动作”可作为输入，但不替代本步骤的正式触发判定。

### R1 意图归类

- 归类为：深化 / 修订 / 比较 / 派生 / 风险补偿；
- 锁定本轮只处理的范围，避免目标漂移。

### R2 上下文装载

- 装载相关冻结对象、关键约束、历史审阅结论；
- 默认装载对象：`AlignedBrief + SPG + WorkMap + InitialDesignPack`；
- 若为局部修订回合，同时装载最近一次 `DeltaDelivery` 与影响范围；
- 标记本轮必须遵守的硬边界、`zone_id/module_id` 作用域与验收口径。

### R3 动作编排

- 生成本轮动作清单（谁做、做什么、何时交付）；
- 绑定验证动作与完成定义（DoD）；
- 若本轮产物属于空间作用域，必须声明对应 `zone_id/module_id`；跨域产物必须声明版本与作用范围。

### R4 执行协同与审阅

- 执行动作并协同产出；
- 进行审阅并输出结论：PASS / PASS-WARN / FAIL。

### R5 回写收束与下一回合判定

- 回写本轮成果、风险状态、未决问题；
- 判定“继续下一回合”或“本分支收束”；
- 若本轮需要调整初步设计内容，先回 `InitialDesignPack` 结果页改版，再进入下一回合；
- 若本轮触及 Node3 上位结构，应停止本分支并回退主链，不在深化分支内静默升级。

## 每回合最小交付清单（建议）

至少包含：

- 本轮目标与边界
- 动作清单与责任分配
- 候选版本与比较结论（若存在多方案并行）
- 关键决策与依据
- 审阅结论与风险状态
- 下一步判定（继续 / 收束 / 回退上游）

如为结构化产物，建议同时包含：

- 作用域声明（`spatial` / `cross_cutting`）
- `zone_id/module_id` 或对象版本引用
- 与 `SPG` / `InitialDesignPack` 的关联关系

## 深化设计与主链对象关系

```text
AlignedBrief + SPG + WorkMap
	+ InitialDesignPack
		→ R0/R1 确定回合边界
		→ R2 装载上下文
		→ R3/R4 形成增量成果
		→ R5 回写 DeltaDelivery 或触发 DerivedProject
```

说明：深化设计的本质不是“重新做一遍主链”，而是在不破坏上游冻结对象的前提下，围绕既有冻结成果做定向深化、修订、收束或派生。
