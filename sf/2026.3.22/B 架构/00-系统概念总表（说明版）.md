## 1. 顶层总览

解释：这一节像“地图封面”，先告诉大家这套系统由哪两大块组成，以及为什么要这样拆。你只要先记住“先定义、后承接”，后面的细节就不会看乱。

| 概念 | 定义说明 | 关键价值 |
|---|---|---|
| 总架构 | 先把项目定义清楚，再让系统承接执行 | 防止“边做边改题” |
| 项目定义层 | 回答“这项目是什么、为何成立、风险在哪” | 给下游稳定输入 |
| 系统承接层 | 把定义编译为对象、流程、交付、治理 | 让执行可追溯、可回退 |

**总公式（主文档口径）**：

> **总架构 = 项目定义层 + 系统承接层**  
> **系统承接层 = 分层 + 对象链 + 公共底盘 + 专题系统 + 交付链 + 协同治理**

### 1.1 设计行业适配原则（持续修改常态）

1. 设计行业默认存在**持续改图、持续改方案、持续比较版本**，系统不得以“一次定稿”作为隐含前提；
2. 冻结的含义是“**当前阶段主版本快照**”，用于追溯、协同与回退，不等于后续不得继续修改；
3. 任一阶段允许存在多个候选版本并行探索，但正式主版本始终只能有一个；
4. 系统治理的对象不是“尽量不改”，而是“在持续修改下仍保持真相源、版本链与交付秩序”。

### 1.2 任务多元化承接原则（全链路 + 片段辅助）

1. 系统默认同时承接两类任务形态：
	- **全链路模式**：按 `Node1 → Node4 → 交付链` 连续推进；
	- **片段辅助模式**：仅承接某一阶段或某一专题问题（如平面优化、动线复核、色彩校准）。
2. 片段辅助模式不等于跨阶段豁免：凡进入正式交付的结果，仍需满足对应门禁与版本追溯要求；
3. 平台定位是“能力承接平台”，不是“全流程代工平台”：系统负责关键编译与治理能力，不替代用户承担全项目过程责任；
4. 用户习惯中的外部工具数据（如 CAD 平面图）允许接入，但必须先编译为内部对象再进入主链，不得绕过对象契约直接写入真相源。

## 2. 项目定义层（5个核心要素）

解释：这一层不做图、不做执行，专门负责把题目说清楚。它解决的是“我们到底在做什么项目、按什么逻辑推进、遇到风险怎么识别”，相当于把方向盘先扶正。

| 概念 | 定义说明 | 主要产出 | 不负责什么 |
|---|---|---|---|
| 空间分类 | 先认清“这到底是哪类项目” | 主流程路由、模板选择 | 不出具体方案 |
| 本体论 | 定义对象、关系、约束 | 统一语义与对象边界 | 不决定推进顺序 |
| 商业方法论 | 决定“先做啥后做啥” | 阶段优先级、回退点 | 不定义对象字段 |
| 通用方法论 | 持续追问、查漏、仲裁 | 风险显性化、协同组织 | 不是单纯经验口号 |
| 知识底盘 | 经验/案例/规则统一复用入口 | 检索与复用能力 | 不是项目完成前置条件 |

---

## 3. 四层上游约束（Node3 冻结）

解释：四层约束就是项目的“硬边界+软仲裁”。一旦在 Node3 冻结，就像合同生效，后续所有对象和交付都必须引用它们的版本，不能口头改、不能偷改。

| 概念 | 定义说明 | 主要消费者 | 变更影响 |
|---|---|---|---|
| `GeoCoordinateBaseline` | “在哪里”的客观边界（地理/气候/市场） | `AlignedBrief` / `SPG` / Gate | 通常触发全链重评 |
| `UseIntentBaseline` | “要干什么、为谁、为何成立” | `AlignedBrief` / `ExecutionPlan` / Gate | 触发对象链影响分析 |
| `TemporalBaseline` | 时间节律约束（日夜/淡旺季/生命周期） | `SPG` / `FloorPlanPack` / `VisualizationPack` | 触发时段策略重算 |
| `HumanContextLayer` | 人因编译与冲突仲裁层（非并列硬基线） | `ExecutionPlan` / Gate / Impact Matrix | 触发仲裁重审 |

来源链补充（执法口径）：

1. `UseIntentBaseline` 由 `FunctionalUseStatement` 在 Node3.S.0.5 编译升级得到；
2. `HumanContextLayer` 为 Node3.S.0d 编译产物（消费已编译基线，不作为 Node1 并列输入基线）；
3. 四层约束冻结后，所有下游对象必须引用冻结版本，不得静默替换来源对象。

双基线联动冻结（最小执法规则）：

1. `GeoCoordinateBaseline` 与 `UseIntentBaseline` 在 Node3 冻结时必须完成版本绑定（禁止单独冻结其一）；
2. 任一基线升版，另一基线自动进入“需评估”状态；
3. `AlignedBrief` 冻结时必须显式记录双基线版本引用。

## 4. 架构分层（五纵两横，共七层）

解释：分层的目的不是把系统写复杂，而是防止“谁都能改一切”。每层只做自己的事，出了问题能快速定位责任，避免前端改后端语义、执行层改对象真相这类事故。

| 分层 | 定义说明 | 核心职责 | 不负责 |
|---|---|---|---|
| 入口交互层 | 用户交互门面 | 收输入、回状态、提示门禁 | 不定义真相源对象 |
| 流程编排层 | 项目推进导演 | Node推进、回退编排 | 不持有对象本体 |
| 领域对象层 | 对象宪法层 | 契约、冻结、版本、`SPG`真相源 | 不裁流程 |
| 能力执行层 | 干活引擎层 | 分析/生成/审阅/影响分析 | 不改流程剧本 |
| 基础能力接口层 | 工具连接层 | 检索/转换/校验接口 | 不定义业务语义 |
| 知识与记忆层（横向） | 经验复用层 | 案例/规则/模板召回 | 不驱动流程状态 |
| 运行时与治理层（横向） | 纪律审计层 | 审计、门禁、回退、越权拦截 | 不写业务内容 |

## 5. 主对象链（项目态）

解释：对象链就是项目数据的“接力棒顺序”。每一棒都要冻结、留痕、可回溯，保证从用户原始需求到设计成果之间，逻辑不断链、责任不丢失。

| 对象 | 定义说明 | 生成节点 | 关键规则 |
|---|---|---|---|
| `RawBriefPacket` | 原始需求包 | Node1 | Node2后不允许静默改写 |
| `GateDecision` | 门禁判定结果 | Node2 | 决定放行/补条件/拒绝 |
| `AlignedBrief` | 对齐冻结简报 | Node3 | 禁止直接改，需回溯Node3 |
| `SpatialProgramGraph (SPG)` | 空间程序图谱真相源 | Node3 | 禁止直接改，需回溯Node3 |
| `ExecutionPlan` | 执行编排容器 | Node3 | 受控修订（微/中/大） |
| `InitialDesignPack` | Node4阶段成果容器 | Node4 | 增量版本制 |

补充：`ExecutionPlan = WorkMap + ExpertTeamPack + TaskArrangementPack`（统一容器口径）。

容器边界补充（执法口径）：`ExecutionPlan` 仅为门面容器（facade），不替代 `WorkMap / ExpertTeamPack / TaskArrangementPack` 的独立对象契约与版本追踪。

---

## 6. 交付链（不可跨越）

解释：交付链强调“先后次序不可跳步”。先讲清楚为什么，再落空间，再做感知，最后落建造；这样可以把高成本返工压在前面低成本阶段解决。

| 交付对象 | 回答问题 | 主要输入 | 常见禁止行为 |
|---|---|---|---|
| `ConceptPack` | 为什么这样做 | 四基线 + `AlignedBrief` + `SPG` | 直接跳施工图 |
| `FloorPlanPack` (+`FloorPlanIR`) | 空间怎么成立 | `ConceptPack`冻结ID + `SPG` | 跳过平面直接效果图 |
| `VisualizationPack` (+`VizSpec`) | 如何被感知 | `FloorPlanPack`冻结ID | 静默改结构真相 |
| `ConstructionPack` (+接口编码) | 如何被建造 | `FloorPlanPack` + 技术约束 | 把施工阶段当重开概念 |

### 6.1 对象链与交付链衔接（执法口径）

1. `InitialDesignPack` 为 Node4 阶段成果容器，不构成平行真相源；
2. `ConceptPack` 从 `AlignedBrief + SPG + ExecutionPlan` 派生，并可引用 `InitialDesignPack` 内已冻结专题结论；
3. 交付链各 Pack 必须保留上游对象引用（至少含 `source_frozen_id` / `spg_version`）；
4. 下游 Pack 仅可反馈问题，不得直接改写 `SPG/AlignedBrief`，结构变更必须回到治理流程。

---

## 7. 公共底盘（共享前提）

解释：公共底盘是全系统都要踩的“统一地基”。它不创造新语义，只负责把上游已定义好的约束稳定地绑定给所有消费者，确保大家用的是同一套版本真相。

| 底盘 | 定义说明 | 作用 |
|---|---|---|
| 前置约束绑定底盘 | 绑定四层约束的冻结版本与消费权限 | 统一“谁消费哪个版本” |
| 载体技术底盘 | 结构/机电/景观/施工边界 | 统一技术落地边界 |
| 空间真相底盘 | 以 `SPG` 承载分区/流线/作用域 | 保证结构真相不漂移 |

接口最小规则：
1. 只引用冻结ID，不重写上游语义；
2. 任一前置约束升版，必须触发影响分析；
3. 未绑定完成，不得签收进入交付链。

---

## 8. 专题系统（MECE分组）

解释：专题系统是执行阶段的“专业分工包”，解决的是“谁负责把哪类问题做深做实”。它是执行组织方式，不是方法论替代，更不是对象定义层。

| 专题系统 | 定义说明 | 典型下游 |
|---|---|---|
| 空间组织系统 | 管空间组织、流线、尺度 | 硬装/灯光/FFE/施工 |
| 硬装界面系统 | 管墙地顶与界面构成 | 施工细化 |
| 色彩系统 | 管视觉主色与配色逻辑 | 灯光/材料/FFE/表现 |
| 材料系统 | 管材质选型与构造适配 | 硬装/施工 |
| 灯光系统 | 管照明策略与场景体验 | 表现/施工 |
| FFE/软装系统 | 管可采购件、陈设触点、软装氛围 | 表现/落地采购 |

边界提醒：
- 专题系统是“执行分组”，不是“定义层替代品”；
- 不重写本体论，不改商业门禁，不自建知识主语义。

### 8.1 专题系统实施边界（防重复、可检查）

判定原则：专题系统是**执行编排单元**，不替代项目定义层。

| 对象 | 专题系统可做 | 专题系统不可做 |
|---|---|---|
| 本体论 | 消费既有对象语义并映射到 `SPG/module/zone` | 重写对象定义、关系语义、约束词典 |
| 商业方法论 | 执行既定阶段优先级与回退路径 | 自行改写阶段顺序、Gate口径 |
| 通用方法论 | 承接追问结果并落地冲突消解动作 | 越权定义仲裁规则与决策权重 |
| 知识底盘 | 调用模板/案例/规则并标注来源版本 | 自建平行知识真相源 |

实施检查（最小）：

1. 每个专题输出必须绑定 `SPG.zone_id/module_id`；
2. 每个专题输出必须声明上游引用（`baseline_refs` / `source_frozen_id`）；
3. 触及结构层变更时，必须走 `Impact Matrix`，不得在专题内静默改写；
4. 任一专题若修改 Gate 条件或仲裁权重，视为越权并回退到定义层重审。

## 9. 协同治理术语

解释：治理术语就是项目里的“交通规则”。没有这套规则，团队很快会出现多头拍板、越权修改、问题无人兜底；有了它，协同就从“靠感觉”变成“按机制”。

| 概念 | 定义说明 | 作用 |
|---|---|---|
| `Gate Checklist` | 每阶段放行清单 | 防止低质量推进 |
| `RASVO` | 角色矩阵：R主提/A签收/S联提/V否决/O观察 | 明确决策权责 |
| `Impact Matrix` | 变更影响模板 | 说明“改了谁、影响谁、是否回退” |
| `ComparisonBoard` | 方案比较看板 | 汇总候选版本差异、取舍依据与转正结论 |
| 受控修订分级 | 微调/中调/大调 | 控制变更成本与风险 |

## 10. 节点与阶段（运行视角）

解释：这一节把系统流程按时间顺序摊开，帮助你快速判断“当前卡在哪一站”。当你知道自己在 Node2 还是 Node4，就知道该补条件、回退，还是推进交付。

| 概念 | 定义说明 |
|---|---|
| Node1 | 收题：把需求进入系统 |
| Node2 | 门禁：判定能否推进 |
| Node3 | 对齐与冻结：形成稳定真相源 |
| Node4 | 初步设计：输出阶段成果 |
| 深化设计（Node4后） | 在不改写上游冻结对象前提下做定向深化 |

### 10.1 Node3 内部编译子步骤（最小执法表）

| 子步骤 | 关键动作 | 产出对象 |
|---|---|---|
| `3.S.0` | 地理约束编译 | `GeoCoordinateBaseline` |
| `3.S.0.5` | 功能用途交叉编译 | `FunctionalUseStatement` / `UseIntentBaseline` |
| `3.S.0.6` | 时间约束编译 | `TemporalBaseline` |
| `3.S.0d` | 人因编译与仲裁 | `HumanContextLayer` |
| `3.S.1` | 解题思路编排 | 解题思路草案 |
| `3.S.2` | 工作地图编排 | `WorkMap` |
| `3.3` | 用户确认与冻结 | `AlignedBrief` + `SPG` + 基线版本绑定 |

规则：Node3 冻结至少应满足“关键子步骤完成 + 版本绑定可追溯”，否则不得推进 Node4。

## 11. 兼容/历史术语（仍可能在专题中出现）

解释：这部分是“新旧口径转换表”。你在老文档里看到的术语并不等于作废，而是被纳入新架构中的某个位置，避免迁移期出现同词不同义。

| 术语 | 当前关系 |
|---|---|
| `WorkMap` | `ExecutionPlan` 组成对象（桥接Node3→Node4） |
| `ExpertTeamPack` | 团队编排中间对象，纳入 `ExecutionPlan` |
| `TaskArrangementPack` | 任务编排中间对象，纳入 `ExecutionPlan` |
| `DesignTaskBook`（历史） | 兼容期存在，逐步由 `AlignedBrief/SPG` 承接语义 |
| `ExecutionBlueprint` / `deliverable_work_packages`（历史） | 执行层可兼容，逐步补齐与 `SPG` 显式绑定 |

## 12. 快速防混淆卡（会议现场可直接读）

解释：这是一页“防跑偏速查卡”。当讨论开始发散、角色开始越权时，直接回到这5条，能在几分钟内把会议拉回同一口径。

1. **定义层**回答“是什么/为什么”；**承接层**回答“怎么编译与执行”。  
2. `SPG` 是结构真相，不是展示草图。  
3. 交付链必须按 `Concept → FloorPlan → Visualization → Construction` 走，不可跨越。  
4. 专题系统是执行分组，不是方法论、本体论、知识底盘的替代。  
5. 触及四层上游约束升版，必须做影响分析与回退判定。

## 13. 一句话总纲

解释：如果只允许记一句话，就记这一句。它把整套架构压缩成“定义→承接→交付→治理”的闭环，能用于新人入门、管理汇报、以及项目对齐开场。

> 前置层（5要素+4约束）把题目定义清楚；承接层（分层+对象链+底盘+专题+交付+治理）把定义稳定编译为可执行、可审计、可回退的交付链。

## 14. 分期实现与可验证完成标准（DoD）

解释：分期不是时间表装饰，而是能力验收合同。每一阶段必须产出可检查结果，否则不得宣告“已完成”。

| Phase | 范围 | 对应层 | 完成标准（DoD） |
|---|---|---|---|
| Phase 1（MVP） | Node1~Node4 主链 | 流程编排+对象层 | 能冻结 `AlignedBrief/SPG`，并阻断跨阶段签收 |
| Phase 2（约束深化） | 四基线编译 + 冲突检测 | 对象层+能力层+治理层 | `Geo/UseIntent/Temporal/Human` 可编译且可追溯 |
| Phase 3（决策成熟） | `ExecutionPlan` + Gate自动化 | 流程+治理 | Gate Checklist 自动判定，可输出拒收原因 |
| Phase 4（几何编译） | `SPG → FloorPlanIR` + 可视化 | 能力层+接口层 | 平面对象可编译，视觉层不反写结构层 |
| Phase 5（知识复利） | 模板库/案例库/跨项目复用 | 知识层+治理层 | 可量化提升复用率与返工率 |

## 15. 治理执行规则（唯一口径）

解释：治理规则是系统稳定运行的底线协议。所有执行动作必须满足“可追溯、可回退、可审计”。

### 15.1 基础规则

1. 禁止跨阶段签收；
2. 禁止平行真相源（仅允许符合 15.5 的探索分支）；
3. 禁止静默改题；
4. 允许受控增量（仅版本化）；
5. 全变更可审计。
6. 冻结是阶段主版本快照，不等于禁止后续继续修改。

### 15.2 受控修订分级

| 修订级别 | 触发条件 | 处理方式 |
|---|---|---|
| 微调 | 不触及四基线、不改 `SPG` 结构、不改 `zone/module` 绑定，仅局部表达或参数优化 | 记录 `delta`，保留主版本，不回退主链 |
| 中调 | 影响单个专题、局部分区、局部流线或单个 Pack，但未触及四基线与 `SPG` 主结构 | 回退到对应 Pack / 专题链重跑，并更新 `ComparisonBoard` |
| 大调 | 触及 `Geo/UseIntent/Temporal/Human`、`AlignedBrief` 核心命题或 `SPG` 主结构 | 回退 Node3，重做影响分析并形成新主版本候选 |

判定原则（设计行业口径）：

1. 修订分级优先依据**被修改对象、影响范围、是否触及冻结约束**判定，而不是靠主观感觉拍板；
2. 系统应先给出建议级别，人工只处理争议项复核；
3. 持续修改是常态，分级的目的在于降低返工成本，不是压制修改行为。

### 15.3 Impact Matrix（强制模板）

| 变更对象 | 变更类型 | 影响下游对象 | 是否回退 | 是否重算专题 | 审批人 |
|---|---|---|---|---|---|
| 示例：`SPG.zone_A` | 中调 | `FloorPlanPack`, `VisualizationPack` | 是 | 流线/尺度/灯光 | 项目总控（A） |

### 15.4 运行时治理执行主体（谁来执法）

| 机制 | 检测点 | 违规动作 | 系统处置 |
|---|---|---|---|
| Gate Guardian | 阶段推进前 | 跨阶段签收 / 缺前置冻结ID | 阻断推进并返回补条件清单 |
| ContractValidator | 对象写回前 | 无冻结引用 / 无 `source_frozen_id` / 越权写入 | 阻断写回并生成仲裁建议 |
| Impact Enforcer | 变更提交时 | 未提交 `Impact Matrix` 直接改结构对象 | 阻断变更并强制进入影响分析流程 |

执行原则：治理规则以“运行时拦截 + 审计留痕”为准，不以口头约定替代系统执法。

### 15.5 探索 / 候选分支治理（设计行业常态，防滥用）

在设计行业中，多方案并行、反复改图、边比边改属于正常工作方式。探索/候选分支不是对主链的破坏，而是正式版本治理的一部分；但它们**不得自动升格为真相源**。

创建规则：

1. **主版本唯一**：同一阶段允许多个候选版本并行，但正式主版本始终只能有一个；
2. **来源绑定**：每个候选版本都必须绑定来源对象版本（`source_frozen_id`）与本轮变更原因；
3. **责任明确**：必须声明责任人、目标问题与有效期（TTL），避免候选版本无限漂浮；
4. **比较留痕**：候选版本之间必须可进入 `ComparisonBoard` 比较，显式记录保留/放弃原因；
5. **边界不变**：候选版本可持续修改，但在转正前不得替代主链真相源，也不得绕过 Gate 直接签收正式交付。

转正规则（候选 → 主链）：

1. 必须通过 `Gate Guardian` 审核并提交 `Impact Matrix`；
2. 必须在 `ComparisonBoard` 中显式选择单一主版本写回，其他候选版本归档为备选证据；
3. 一旦转正写回，后续变更全部回到受控修订分级与版本化治理，不再以“探索中”为由绕开审计。

### 15.6 持续修改场景下的版本优先治理

1. 系统默认项目全程都可能发生修改，不以“冻结后基本不动”为设计前提；
2. 每次改动都应至少记录：`change_reason`、`change_source`、`impact_scope`、`requires_recompile`；
3. 系统优先追求“局部修改局部吸收”，只有触及上游真相或主结构时才整链回退；
4. 版本治理优先于口头治理：先形成版本、再比较版本、再选择阶段主版本；
5. 方案比较能力是正式治理能力，不是额外附加功能。

## 17. 插件扩展合同（Extension Contract）

解释：本节用于把“可扩展”从口号变成可执法机制。新增项必须先判定插件类型，再按契约接入；禁止绕过主链、禁止新增平行真相源。

### 17.1 扩展分类器（先分类，后接入）

新增项仅允许归入以下四类：

1. `Role Plugin`（角色插件）：新增专业席位，例如唐诗宋词专家、空调专家；
2. `Knowledge Plugin`（知识插件）：新增规则/案例/模板/语义包；
3. `Capability Plugin`（能力插件）：新增工具能力，例如 CAD 绘制、SU 模型生成；
4. `Topic Plugin`（专题插件）：仅在满足独立目标与完整契约时新增一级专题系统。

默认规则：新增项优先按 `Role/Knowledge/Capability` 接入；仅在无法被三类容纳时，才评估升格为 `Topic Plugin`。

### 17.2 四类插件最小契约

| 插件类型 | 最小契约字段 | 默认落层 | 严禁行为 |
|---|---|---|---|
| `Role Plugin` | `role_name`, `stage_scope`, `pack_scope`, `rasvo_default`, `allowed_outputs` | `ExecutionPlan` / `ExpertTeamPack` | 直接改写 `SPG/AlignedBrief` |
| `Knowledge Plugin` | `plugin_name`, `knowledge_type`, `index_tags`, `source_version`, `callable_stage` | 知识与记忆层 | 生成平行真相源 |
| `Capability Plugin` | `capability_name`, `input_objects`, `output_artifacts`, `validation_rules`, `writeback_policy` | 能力执行层 + 基础接口层 | 绕过对象链直接成图/成包 |
| `Topic Plugin` | `objective`, `upstream_inputs`, `downstream_outputs`, `validation_rule`, `zone_binding_rule` | 专题系统层 | 无 `SPG` 绑定即入主链 |

### 17.3 接入门禁（统一执法）

所有插件接入必须通过以下门禁：

1. **对象门禁**：输入对象必须来自冻结版本（至少含 `source_frozen_id`）；
2. **作用域门禁**：空间作用域产物必须绑定 `SPG.zone_id/module_id`；
3. **治理门禁**：触及结构变更时必须提交 `Impact Matrix`；
4. **阶段门禁**：不得破坏 `Concept → FloorPlan → Visualization → Construction` 顺序；
5. **审计门禁**：接入、执行、回写全程可追溯。

### 17.4 升格规则（何时允许 Topic Plugin）

仅当新增项同时满足以下条件，才允许升格为新专题系统：

1. 有独立目标（非单一角色意见）；
2. 有稳定输入输出契约；
3. 有独立校验规则；
4. 可稳定绑定 `SPG` 作用域；
5. 可纳入 `Gate/RASVO/Impact Matrix` 治理闭环。

否则一律按 `Role/Knowledge/Capability` 处理，不得借扩展之名改主架构。

### 17.5 典型接入示例（口径）

- 唐诗宋词专家：`Role Plugin + Knowledge Plugin`（文化语义输入），不升格为一级系统；
- 空调专家：`Role Plugin + Knowledge Plugin`（技术约束输入），必要时提升 RASVO 权重；
- CAD 绘制：`Capability Plugin`（消费冻结对象，输出派生工件）；
- SU 模型生成：`Capability Plugin`（消费几何/表现对象，不反写结构真相）。

执行原则：**主链不变、真相源不变、门禁不变；新增项按插件契约接入。**

## 18. 项目能力（当前架构可承接的能力清单）

解释：本节用于说明“这套架构现在能承接什么能力、按什么边界承接”。口径上只列**可被主架构合法承接**的能力，不把高风险逆向推理包装成正式真相生成能力。

### 18.1 原生强支持能力（顺主交付链）

| 能力 | 核心产物 | 口径说明 |
|---|---|---|
| 项目定义与对齐 | `AlignedBrief` / 四层约束 | 可完成项目收题、对齐、冻结与版本绑定 |
| 设计概念生成 | `ConceptPack` | 可输出概念方向、专题策略、风险提示与各专业概念协同 |
| 参数化平面生成 | `FloorPlanPack` + `FloorPlanIR` | 可基于冻结语义与约束编译平面真相 |
| 平面到视觉生成 | `VisualizationPack` + `VizSpec` | 可将平面真相投影为受约束的视觉成果 |
| 平面到施工承接 | `ConstructionPack` | 可将平面与技术约束衔接到施工接口与编码 |
| 方案反馈与回退治理 | `Impact Matrix` / Gate流程 | 可对设计变更做影响判定、回退与重编译 |
| 多方案比较与持续版本迭代 | `ComparisonBoard` / `DeltaDelivery` | 可承接全程反复改图、比较候选版本并选择阶段主版本 |

### 18.2 通过适配器可承接能力（需插件/接口层补桥）

| 能力 | 典型桥接对象/方式 | 当前边界 |
|---|---|---|
| 上传平面图后做优化建议 | `PlanImportAdapter` → `FloorPlanIR draft` | 可承接，但必须先编译进对象层，不能只停留在图片点评 |
| 上传建筑框架图生成平面 | `BuildingFrameImportAdapter` → `BuildingCarrierBaseline draft` | 可承接，但必须先形成载体约束对象 |
| 平面导出 CAD / PDF / SVG / PNG | `OutputProjectionPack` / 导出适配器 | 可承接为交付投影能力，不改变主对象链 |
| 平面生成 SU / 3D 模型 | `Capability Plugin`（如 `SKPExportAdapter`） | 可承接为派生工件输出，不反写结构真相 |
| 效果图拆解材料/软装候选清单 | 识别/拆解能力插件 + 清单对象 | 可承接为候选清单能力，正式清单仍需校验与绑定 |

### 18.3 仅允许以提议态承接的能力（不得直接升格为真相）

| 能力 | 合法产物 | 严格限制 |
|---|---|---|
| 效果图反推平面 | `FloorPlanIR draft` / `SPG draft proposal` | 只能作为草案或提议，必须经过 Gate 与影响分析 |
| 参考图启发生成平面 | `ReferencePatternProposal` / 布局草案 | 只能提供启发式布局，不得直接成为正式平面真相 |
| 外部图片反推材料/系统信息 | 候选清单 / `confidence` 标注结果 | 必须标注不确定性，不得跳过对象绑定直接签收 |

### 18.4 能力声明的统一边界

1. 所有正式能力都必须服从 `Concept → FloorPlan → Visualization → Construction` 主交付链；
2. 外部输入类能力必须先编译为内部对象，再进入治理链；
3. 逆向推理类能力默认只产生 `draft/proposal/candidate`，不得直接形成冻结真相；
4. 任一能力若触及结构变更，必须提交 `Impact Matrix` 并接受运行时治理拦截；
5. 任一新增能力若无法说明输入对象、输出对象、校验规则与回写策略，则不得宣称为项目正式能力。
6. 冻结只代表“当前阶段主版本已明确”，不代表项目后续不得继续修改或比较其他候选版本。

一句话口径：**本架构强于“正向设计编译”，可扩展承接“导入/导出与工具桥接”，但对“图像逆向生成真相”实行提议态治理，不直接承诺为正式真相能力。**

## 19. 多入口任务路由与转正规范（流程级）

解释：本节把“片段任务优先、完整项目可升级”从原则落为可执行流程。目的不是替代主链，而是让用户可从任意真实入口接入，并在需要时受控升级到正式主链。

### 19.1 三类工作区（运行态）

| 工作区 | 定义 | 典型输入 | 治理强度 |
|---|---|---|---|
| 正式项目工作区 | 按主对象链与交付链推进 | Node1 输入 / 已冻结对象 | 强治理（完整 Gate + 版本冻结） |
| 片段任务工作区 | 聚焦某一阶段/专题任务 | CAD平面图、效果图、局部问题 | 中治理（作用域门禁 + 风险标注） |
| 临时探索工作区 | 快速试探与比较，不直接入主链 | 参考图、草图、临时提问 | 轻治理（最小审计，不冻结真相） |

规则：可从片段/临时起步，但进入正式交付前必须通过转正规则。

### 19.2 外部工件入口协议（Artifact Ingress Contract）

外部输入（CAD/SU/PDF/图片/文本）进入系统时，必须先归一化为 `draft` 对象，不得直写真相源。

最小入口字段：

1. `source_type`（cad/su/pdf/image/text）；
2. `source_ref`（原始文件引用）；
3. `parsed_confidence`（解析置信度）；
4. `missing_constraints`（缺失约束清单）；
5. `suggested_target_mode`（建议目标模式：片段/临时/正式）；
6. `writeback_policy`（仅建议/可派生/需转正）。

### 19.3 任务判型与路由（先判型，后执行）

入口交互层必须先完成任务判型，再决定路由：

1. 对话型片段任务（建议/诊断为主）；
2. 阶段性片段任务（在某阶段内优化）；
3. 增量修订任务（局部变更）；
4. 派生重构任务（形成新线程）；
5. 完整项目任务（全链治理）。

路由原则：入口可断点，签收不可断链。

### 19.4 片段任务门禁与约束降级

片段任务允许“约束不完整”启动，但必须同时满足：

1. 显式输出 `missing_constraints`；
2. 输出结果附带 `risk_notes`；
3. 若触及结构真相（`SPG` 主结构/四基线），自动升级为回退或转正流程；
4. 未完成对象绑定（`source_frozen_id` 或合法 `draft_ref`）不得进入正式交付签收。

### 19.5 转正规则（片段/临时 → 正式主链）

转正最小流程：

1. 补齐最小上游约束（至少 `GeoCoordinateBaseline` 与 `UseIntentBaseline`）；
2. 完成一致性校验（对象绑定、作用域绑定、冲突检查）；
3. 提交 `Impact Matrix`（如触及结构变更）；
4. 通过 Gate 后生成正式冻结引用（含 `source_frozen_id`）；
5. 未通过则留在片段/临时工作区，禁止冒充正式交付。

### 19.6 边界声明（防平台膨胀）

1. 系统承接“判型、编译、校验、回退决策”，不承接外部工具的全流程生产控制；
2. 导入导出是桥接能力，不改变“主链唯一真相源”原则；
3. 任何入口都必须先归一化，再挂接主链或专题链，不允许以外部文件直接成为平行真相源。
