# 知识底盘专题

> 主文档入口：`./00-系统概念总表（说明版）.md`
>
> 口径说明：本专题为专项解释页，不承载执法口径；若与主文档冲突，以主文档为准。

> 日期：2026-03-22  
> 文档说明：本文件用于从用户视角解释“知识底盘”在民宿项目中的作用、输入方式、价值与可暂缓性。

---

## 1. 知识底盘是什么

知识底盘回答的是：

> **项目用到的经验、规则、案例、模板，统一往哪里输入。**

对用户来说，它可以直接理解为：

> **知识底盘 = 你往里面输入知识的地方。**

这里不再单独展开案例库、知识库、检索层、调用层这些实现细节。

---

## 2. 在民宿项目里，会往里面输入什么

以民宿项目为例，可以输入到知识底盘里的内容包括：

- 民宿成功案例
- 民宿失败案例
- 审批要求
- 消防要求
- 四季运营经验
- 客群冲突经验
- 动线优化模板
- 预算分配模板

---

## 3. 它的核心作用

知识底盘最重要的作用是：

- 把经验沉淀下来
- 让下一个民宿项目可以复用
- 提高一致性
- 提高可解释性
- 降低对单个人经验的依赖

简单说，它不是项目骨架，但它能让同类项目越做越稳。

---

## 4. 它是不是必须项

**不是。**

---

## 5. 没有知识底盘，民宿项目能不能做完

**能。**

因为只靠下面这些，项目照样可以做下去：

- 空间分类
- 本体论
- 商业方法论
- 通用方法论

再加上人的经验，也能把民宿项目做完。

---

## 6. 那为什么还要有知识底盘

因为有了它以后，项目会：

- 做得更稳
- 经验更可复用
- 知识不容易丢
- 新人更容易接手
- 同类项目越来越快

所以它的定位最准确的是：

> **增强项，不是前置项。**

---

## 7. 它不负责什么

知识底盘不负责：

- 判断这是什么项目
- 定义民宿里有哪些核心对象
- 决定项目推进顺序
- 做项目主流程的风险审计

这些分别属于：

- 空间分类
- 本体论
- 商业方法论
- 通用方法论

---

## 8. 一句话总结

> **知识底盘的作用，是把民宿项目的案例、规则、经验、模板沉淀下来，方便后续复用；没有它项目也能做完，但有了它项目会更稳。**

## 升级：知识底盘的多维组合索引系统（2026-03-25）

### 背景

随着 `GeoCoordinateBaseline` 和 `UseIntentBaseline` 的引入，知识底盘不再是"单维过滤的案例库"，而应该成为"基于功能/地理/用途的多维组合检索系统"。

### 升级定义

从前：
> 知识底盘 = "案例库 + 规则库 + 模板库"（单维索引：按项目类型或地理类型检索）

升级为：
> 知识底盘 = "按 (project_archetype, geo_type, brand_positioning, use_context) 多维组合建立的检索系统"（多维笛卡尔积索引）

### 多维索引结构

所有知识条目（案例、模板、规则）都应该包含四个维度的标记：

| 维度 | 示例值 | 作用 |
|---|---|---|
| **project_archetype** | 民宿、酒店、精品酒店、度假村 | 项目业态分类 |
| **geo_type** | 山地、平地城市、水滨、沙漠、高海拔 | 地理环境分类 |
| **brand_positioning** | 疗愈、社交、商务、奢侈、经济 | 品牌定位分类 |
| **use_context** | 轻度假、周末度假、长期居留、团队建设 | 使用场景分类 |

### 峨眉山案例：多维索引标记

**案例**："HAY品牌山地疗愈民宿运营经验"

老做法（单维索引）：
```
标签：民宿、山地、疗愈
检索：用户搜"山地民宿" → 可能混入平地冒险民宿、高端度假村等不相关案例
```

新做法（多维笛卡尔积索引）：
```
多维标记：
	project_archetype = 民宿
	geo_type = 山地
	brand_positioning = 疗愈
	use_context = 轻度假

检索：用户输入"山地疗愈+轻度假"
	→ 系统精准匹配 (民宿, 山地, 疗愈, 轻度假) 的案例组合
	→ 不混入其他组合的案例
```

### 知识条目库组织方案

建议的目录结构（基于多维笛卡尔积）：

```
knowledge_base/
├── cases/                              # 案例库
│   ├── (minsu, mountain, healing, light_vacation)/
│   │   ├── emei_mountain_case.md       # 峨眉山案例
│   │   ├── luguhu_case.md              # 泸沽湖案例
│   └── (minsu, urban, business, weekend)/
│       ├── beijing_boutique_case.md
│
├── templates/                          # 模板库
│   ├── (minsu, mountain, healing, *)/
│   │   ├── room_layout_template.yaml
│   │   ├── brand_material_template.md
│   └── (minsu, urban, *, *)/
│       ├── lobby_layout_template.yaml
│
├── rules/                              # 规则库
│   ├── geo_rules/
│   │   ├── mountain_safety_rules.md    # 山地安全规则
│   │   ├── mountain_climate_rules.md   # 山地气候规则
│   └── brand_rules/
│       ├── hay_brand_guidelines.md     # HAY品牌指南

└── standards/                          # 标准库
		├── fire_code_rules.yaml            # 消防规范
		├── accessibility_standards.yaml    # 无障碍标准
```

### 检索与调用机制

当系统处理"山地疗愈民宿"项目时，知识底盘检索流程：

1. **维度匹配**：系统识别项目的四个维度 {民宿, 山地, 疗愈, 轻度假}
2. **多维查询**：查询知识库中所有满足这四个维度的条目（不要求全部维度都匹配，但匹配度越高优先级越高）
3. **分级返回**：
	 - 优先返回**精准匹配** (民宿, 山地, 疗愈, 轻度假) 的条目
	 - 次返回**部分匹配** (民宿, 山地, *, *) 的条目（通用山地民宿经验）
	 - 再次返回**单维匹配** (民宿, *, *, *) 的条目（通用民宿经验）
4. **冲突避免**：不返回维度冲突的条目（例如"平地商务酒店"不应该返回给"山地疗愈民宿"）

### 知识条目的版本与演化

每个知识条目应该记录：

- **四维标签**：(archetype, geo, brand, use_context)
- **有效性标记**：(已验证 / 待验证 / 已过期)
- **来源**：某个生成的项目版本 (如 InitialDesignPack v1.0)
- **反馈记录**：这个模板/规则在后续项目中的应用效果

### 一句话升级总结

> **从"按单一维度的案例库"升级为"(业态×地理×品牌×用途)多维笛卡尔积的检索系统"——让后续项目找到真正相关的经验，而不是淹没在相关性低的海量案例中。**
