## 1. 为什么流程之外还需要架构文档

流程文档回答"按什么顺序推进"，架构文档回答"由谁承接、对象如何稳定流转"。

只有流程没有架构，通常会出现三类问题：

1. **流程一改，对象结构跟着漂移**——没有稳定的对象契约作锚点；
2. **新增能力时边界不清**——无法判断该加在哪一层、由谁负责；
3. **结果可运行但不可追溯**——治理和审计无从落脚。

因此本文固定两件事：

- **纵向分层职责**：谁负责什么；
- **横向对象链契约**：对象何时创建、冻结、消费、回写。

一句话：**流程让系统走得动，架构让系统走得稳。**

## 2. 七层架构（纵向分层）

```text
入口交互层
  ↓
流程编排层
  ↓
领域对象层
  ↓
能力执行层
  ↓
基础能力接口层

（横向贯穿）知识与记忆层 + 运行时与治理层
```

| 分层 | 核心职责 | 不负责什么 |
|---|---|---|
| 入口交互层 | 承接用户输入、卡片交互、等待态与气口区体验 | 不定义对象真相源 |
| 流程编排层 | 对话态编排 + 项目态四节点推进（用户输入/门禁/信息对齐/初步设计）+ 子步骤调度 | 不直接存放对象本体 |
| 领域对象层 | 定义核心对象、字段契约、冻结/版本/回写规则；维护空间程序图谱真相源（`SpatialProgramGraph`） | 不做流程判定 |
| 能力执行层 | 分析、生成、审阅、聚合等业务能力编排；执行模板实例化、分区映射、流线冲突检查与影响分析 | 不改流程剧本 |
| 基础能力接口层 | 无状态工具调用（检索、生成、转换、校验） | 不承载业务语义 |
| 知识与记忆层（横向） | 提供规则、案例、模板、长期记忆供调用；沉淀业态模板库（民宿/私宅/酒店等） | 不直接驱动节点流转 |
| 运行时与治理层（横向） | 运行、审计、回放、断点续传、风险门禁与人工接管；提供一致性红绿灯与越权拦截 | 不定义业务内容 |

七层分工的核心原则：**每层只做自己该做的事，不越权也不缺位。**

## 3. 核心域对象清单

域对象是系统内各层共享的"真相源"，不是临时变量。

为避免同物多名，本文采用统一命名：

- **系统真相源对象**：`SpatialProgramGraph`（简称 `SPG`）
- **展示/交互视图名**：`SpaceTree`
- **任务与清单投影视图名**：`SpaceModuleList` / `SpaceModulePack`

其中，`SpaceTree` 与 `SpaceModuleList` 仅是 `SPG` 的派生视图，不是独立真相源。

| 对象 | 创建节点 | 作用 |
|---|---|---|
| `RawBriefPacket` | 大节点1 用户输入 | 原始 brief 与初始上下文（`GA`） |
| `GateDecision` | 大节点2 门禁 | 放行 / 补条件 / 拒绝 / 路由对话态（`GA`） |
| `ResearchBriefPack` | 大节点3 信息对齐内部 | 事实底图（市场/场地/标杆）；先呈现，后由议题裁决（`Planned`） |
| `AgendaProposals` | 大节点3 信息对齐内部 | 议程切口与来源、提案责任链（`Planned`） |
| `AgendaVoiceLedger` | 大节点3 信息对齐内部 | 主提/联提/暂缓 + 原因可见化（`Planned`） |
| `ExplorationDraft` | 大节点3 冻结前 / Node4 / 深化设计回合 | 草图、参考图、粗模等形成的探索草案（`Planned`） |
| `OptionSet` | 大节点3 冻结前 / Node4 / 深化设计回合 | 同一问题的多个候选方向集合（`Planned`） |
| `ComparisonBoard` | Node4 / 深化设计回合 | 候选版本差异、取舍理由与主版本选择记录（`Planned`） |
| `AlignedBrief` | 大节点3 冻结产物 | 信息对齐冻结基线，成为后续一切判断的真相源（`Planned`） |
| `SpatialProgramGraph` (`SPG`) | 大节点3 内部生成，3.3 同步冻结 | 空间程序图谱真相源：承接“空间类型→功能模块→分区→子分区→流线→策略作用域”（`Planned`） |
| `WorkMap` | 大节点3 系统内部步骤 3.S.2 | 承接解题思路并向 Node4 输出团队组建与任务安排底盘（`Planned`） |
| `ExpertTeamPack` | 大节点4 步骤4.1 | 专家团队构成与来源依据（可按 `SPG` 的模块/分区落位）（`Planned`） |
| `TaskArrangementPack` | 大节点4 步骤4.2 | 基于 `WorkMap + ExpertTeamPack` 的任务编排蓝图（`Planned`） |
| `InitialDesignPack` | 大节点4 冻结产物 | 初步设计阶段成果包，含所有专题策略与待确认项（`Planned`） |
| `DeliveryBundle` | 实施执行节点（主链/后续分支均可产出） | 最终交付与阶段性交付集合（`GA`） |
| `DeltaDelivery` | 交付后对话态 | 局部增量重入执行（`GA`） |
| `DerivedProject` | 交付后对话态 | 重大派生项目（`GA`） |

### 3.0.1 总则与专项的维护分工（2026-03-25）

为避免“总则文档”和“专项文档”双份维护，统一口径如下：

1. 本文（`B 架构/08`）负责分层职责、对象链总关系、冻结与版本治理总原则；
2. 世界模型专项（如 `../4-3 世界模型/4-3-1 地理坐标/03-GeoCoordinateBaseline字段契约.md`）负责对象字段契约、编译细节与下游消费映射；
3. 若二者存在表述差异，以“总则在 08、实现在专项”的双层解释法处理，不做跨文档重复粘贴。

### 3.1 对象链（主链视角）

```text
RawBriefPacket
  → ExplorationDraft / OptionSet
  → GateDecision
  → AlignedBrief
  → SpatialProgramGraph (SPG)
  → WorkMap
  → ExpertTeamPack
  → TaskArrangementPack
  → ComparisonBoard
  → InitialDesignPack
  → DeliveryBundle
```

关键解释：

- `SPG` 是 `AlignedBrief` 与 `InitialDesignPack` 之间的结构化承接层，避免“靠大段文本临时推理过桥”；
- `InitialDesignPack` 的色彩/家具/尺度/公区策略必须按 `SPG` 分区与节点映射，禁止整体一刀切。

### 3.2 Node4 内部对象链（决策层视角）

```text
SPG
  → WorkMap
  → ExpertTeamPack
  → TaskArrangementPack
  → InitialDesignPack
```

说明：

- `WorkMap` 是 Node3 与 Node4 的桥对象，不单独成为主链大节点；
- `ExpertTeamPack` 与 `TaskArrangementPack` 是 Node4 决策编译链中间层，避免“有步骤、少对象”。

### 3.3 对象生命周期的五条契约

1. **草稿是提议，不是定论**：对话态草稿对象不能替代冻结对象；
2. **冻结即当前真相**：Node3 结束时应同步冻结 `AlignedBrief v1.0` 与 `SPG v1.0`；`InitialDesignPack` 冻结后成为初步设计真相源；
3. **禁止静默覆写**：所有修订必须版本化（如 `v1.0 → v1.1`）或派生为 `DerivedProject`；
4. **治理记录随对象走**：风险快照、一致性检查、仲裁说明必须回挂到对应版本。
5. **分区即宪法**：`SPG` 一旦冻结，后续专题策略必须按模块/分区映射输出，禁止跨区越权或跳过 `zone_id/module_id` 绑定。
6. **主版本唯一、候选版本并行**：设计行业允许多个候选版本并行，但每个阶段只能有一个正式主版本；候选版本必须通过 `ComparisonBoard` 选定后方可转正。

### 3.4 SPG 最小字段契约（工程落地）

`SPG` 至少包含以下字段：

- `space_type`
- `user_roles`
- `functional_modules`
- `zones`
- `subzones`
- `flows`
- `adjacency_rules`
- `privacy_gradient`
- `strategy_scopes`
- `version` / `source_refs`

字段约束补充（最小执行口径）：

- `zones[].zone_id`：必填，唯一；
- `subzones[].parent_zone_id`：必填，必须引用已存在 `zone_id`；
- `flows[].from_zone_id / to_zone_id`：必填，必须可解析到 `zones` 或 `subzones`；
- `strategy_scopes[]`：必须声明作用域类型（`spatial` / `cross_cutting`）；
- `version`：必填，采用语义版本（`major.minor.patch`）；
- `source_refs[]`：必填，记录来源阶段与责任角色。

### 3.5 现状对象 ↔ 目标对象映射（兼容期）

| 现状实现对象 | 目标态对象 | 关系类型 | 迁移说明 |
|---|---|---|---|
| `DesignTaskBook` (`GA`) | `AlignedBrief` + `SPG` (`Planned`) | 编译拆分 | 兼容期允许并存；中长期由 `AlignedBrief/SPG` 替代“单体任务书承载全部语义” |
| `ExecutionBlueprint` (`GA`) | `TaskArrangementPack` (`Planned`) | 近似映射 | 当前执行骨架继续可用；补齐 `zone/module` 绑定后向目标对象收敛 |
| `deliverable_work_packages` (`GA`) | `TaskArrangementPack` 子集 (`Planned`) | 子集映射 | 保留 DWP 作为执行层一等实体，逐步补全与 `SPG` 的显式引用 |
| `DeliveryBundle` (`GA`) | `DeliveryBundle` (`GA`) | 一致 | 生命周期保持一致，主链与后续分支均可产出 |

兼容原则：

1. 兼容期先建立映射，不强行一次性替换；
2. 任一映射缺失时，不得宣称该目标对象为现行唯一真相源；
3. 迁移顺序优先“冻结对象可追溯”，其次“执行对象可扩展”。

### 3.6 冻结触发决策树（Node3）

```text
3.S.1 完成 && 3.S.2 完成 && 3.3 用户确认
  → 冻结 AlignedBrief v1.0 + SPG v1.0 + WorkMap v1.0

若存在关键 open items（阻断级）
  → 标记 BLOCKED，不冻结，回到 3.1/3.3 补齐

若 Node4 提出改上位空间结构
  → 回退 Node3，创建 SPG v1.x 或 DerivedProject
```

## 4. 流程编排层与对象层的边界

这条边界用于避免"流程改动 = 数据结构重写"的耦合风险。

**编排层只做三件事**：

- 何时创建对象；
- 何时消费对象；
- 何时触发回退或升级。

**对象层只做两件事**：

- 定义对象结构与字段契约；
- 定义冻结、版本、派生与回写规则。

实际效果：主链节点可以迭代调整，只要不改动对象的冻结/回写契约，对象层就不需要跟着重写。

编排层在 `SPG/WorkMap` 相关的职责边界如下：

- **可做**：决定何时生成 `SPG draft`、何时冻结 `SPG v1.x`、何时触发派生项目；
- **不可做**：定义 `SPG` 字段语义、私自改写冻结后的分区结构。

能力层在 `SPG/WorkMap` 相关的职责边界如下：

- **可做**：模板召回、实例化补全、冲突检查、影响范围分析；
- **不可做**：绕过对象契约直接写入“无分区绑定”的策略结论。

## 5. 治理闭环（风险与一致性）

### 5.1 治理对象

- `risk_register`：风险台账
- `consistency_check_records`：跨专题一致性检查记录
- `arbitration_notes`：冲突仲裁记录
- `risk_disposition_records`：风险三分法（已覆盖 / 知情接受 / 悬空待定）
- `contract_validation_records`：对象契约校验记录（字段完整性、版本引用、分区绑定）
- `governance_signal_records`：治理红绿灯记录（一致性分/冲突分/越权分）

### 5.2 契约校验器（ContractValidator）

在能力执行层与对象层之间设置 `ContractValidator`，每次写回前强制校验：

1. 是否绑定有效 `zone_id/module_id`（仅对 `spatial` 作用域产物强制）；
2. 是否引用冻结对象版本（如 `SPG v1.0`）；
3. 是否发生跨区越权（例如客房策略覆盖公共区）；
4. 是否存在无来源写入（缺 `source_refs`）。

任一项不通过：阻断写回并生成仲裁/回退建议。

作用域规则：

- **Spatial Artifact**（空间作用域产物）：必须绑定 `zone_id/module_id`；
- **Cross-cutting Artifact**（跨域产物，如命名方案/研究总述）：可不绑定 `zone_id`，但必须绑定对象版本与作用范围声明。

### 5.3 闭环触发路径（对应主链节点）

```text
大节点3 信息对齐（步骤3.S.1/3.S.2/3.3）→ 生成 SPG draft 并冻结 SPG v1.0 + 风险快照
  ↓
大节点4 初步设计（步骤4.1/4.2/4.3）→ 按 SPG + WorkMap 映射策略 + 一致性检查 / 冲突仲裁
  ↓
大节点4 步骤4.4 成果审阅与冻结 → 风险三分法归档 + 治理红绿灯签署
  ↓
高风险悬空项 → 触发回退或后续深化设计任务
```

治理闭环的核心原则：**过程中持续生效，不是末端补一个总结。**

## 6. 与主链文档的关系

- `A 步骤/1 项目步骤及流程.md` 解决"**怎么走**"（时序与节点职责）；
- 本文 `B 架构/08` 解决"**谁承接**"（结构与对象契约）。

两者合并后形成完整系统基线：

1. **时序可推进**——主链节点与子步骤有明确口径；
2. **对象可稳定**——`AlignedBrief + SPG + InitialDesignPack` 三段冻结产物有契约，不随流程漂移；
3. **能力可扩展**——七层分工清晰，新能力知道落在哪一层；
4. **治理可追责**——每条判断有来源、有版本、有风险归档。

### 6.1 双态桥接规则（防静默覆写）

为避免“对话态草稿”与“项目态冻结对象”混写，补充桥接规则：

1. 对话态草稿对象不构成真相源；
2. 草稿仅在编译进入 `RawBriefPacket` 或 `SPG draft` 后，才进入项目态对象链；
3. 项目态冻结对象回落到对话态时，只能作为上下文注入，不能被自然对话静默覆写；
4. 若触及上位结构改写，必须回退 Node3 并走版本化（`SPG v1.x`）或派生项目（`DerivedProject`）。

## 升级：双基线版本治理（2026-03-25）

### 背景

随着 `UseIntentBaseline` 的引入，系统架构不再是"单基线（GeoCoordinateBaseline）治理"，而应该成为"双基线同步版本治理"的框架。

### 升级定义

从前：
> 系统架构 = "GeoCoordinateBaseline 版本治理"（单基线冻结）

升级为：
> 系统架构 = "GeoCoordinateBaseline + UseIntentBaseline 双基线同步治理"（双基线绑定与版本同步）

### 2.1 双基线对象的定义

**GeoCoordinateBaseline（地理基线）**
- 职责：承载项目地理、气候、文化、市场等位置感知
- 版本管理：一旦冻结为 v1.0 则不改写，升级时产生 v1.1 / v2.0
- 被消费者：`UseIntentBaseline` / `AlignedBrief` / `SPG`

**UseIntentBaseline（用途基线）**
- 职责：承载项目功能、商业模型、品牌定位、运营逻辑
- 版本管理：与 GeoCoordinateBaseline 同步冻结；任一升级时，另一个自动标记"需评估"
- 被消费者：`AlignedBrief` / `SPG` / `WorkMap` / `InitialDesignPack`

### 2.2 双基线绑定规则（CRITICAL）

| 规则 | 示例 |
|---|---|
| **绑定明确性** | `AlignedBrief.version = "v1.0"` 必须显式记录 `GeoCoordinateBaseline_version = "v1.0"` 和 `UseIntentBaseline_version = "v1.0"` |
| **同步冻结** | Node3 冻结时，必须同时冻结 `GeoCoordinateBaseline v1.0` 和 `UseIntentBaseline v1.0`；不可单独冻结一个 |
| **版本升级链** | 若 GeoCoordinateBaseline 升到 v1.1（如发现气候数据有误），则下游所有消费者（UseIntentBaseline / AlignedBrief）自动标记为"需评估版本兼容性" |
| **冲突检测** | 若 UseIntentBaseline 升级后与 GeoCoordinateBaseline 产生新冲突（如新增用途与地理环保相悖），该冲突记录在 `UseIntentBaseline.conflicts` 并触发 Node3 回退选项 |

### 2.3 冻结决策树升级（Node3 冻结时）

```text
（原来的决策树）
3.S.1 完成 && 3.S.2 完成 && 3.3 用户确认
  → 冻结 AlignedBrief v1.0 + SPG v1.0 + WorkMap v1.0

（升级后的决策树）
3.S.1 完成 && 3.S.2 完成 && 3.3 用户确认
  → 检查 GeoCoordinateBaseline 与 UseIntentBaseline 的绑定状态
    → 两个基线都在 "v1.x 冻结" 或 "Provisional" 状态？
      → YES: 同步冻结 AlignedBrief v1.0 + SPG v1.0 + WorkMap v1.0
      → NO（某个基线在草稿态）: 阻断冻结，返还用户"请先冻结基线再锁定项目定义"

若存在关键 open items（阻断级）
  → 标记 BLOCKED，不冻结，回到 3.1/3.3 补齐

若冲突来自"GeoCoordinateBaseline vs UseIntentBaseline 的根本矛盾"
  → 评估：这个矛盾是可调和的张力（录入 unresolved_tensions）还是越界矛盾？
    → 可调和 → 标记为 unresolved_tension，继续冻结但加 WARN 标记
    → 越界 → 回退 Node3，选择修改 UseIntentBaseline 的某个维度

若 Node4 提出"使用需求与地理现实不相容"的改题
  → 回退 Node3，决定是升级 GeoCoordinateBaseline 的认知还是修改 UseIntentBaseline 的承诺
```

### 2.4 双基线的协同示例（峨眉山）

### 2.5 运行中的版本影响分析

若在 InitialDesignPack 生成后发生基线升级：

**场景**：Node4 执行中，突然发现 GeoCoordinateBaseline 数据有误（如实际降水量远高于 v1.0 的估计）

**处理流程**：
1. 创建 `GeoCoordinateBaseline.v1.1`（patch版本）
2. 触发"版本影响分析"：检查 UseIntentBaseline 是否需要调整
3. 若 UseIntentBaseline 不变，则 AlignedBrief 标记为"关键信息变化，需二次对齐"
4. 若 UseIntentBaseline 需改（如"防潮要求升为顶级"），则：
   - 创建 `UseIntentBaseline.v1.1`（同时升级）
   - 所有下游产物（SPG / InitialDesignPack）标记为"需重新评估"
   - 回溯 Node3 或启动增量深化流程处理

### 2.6 一句话升级总结

> **从"单基线冻结治理"升级为"双基线同步治理"——让 GeoCoordinateBaseline 和 UseIntentBaseline 不再各自独立，而是形成紧耦合的版本链，确保项目定义始终建立在双重真相源的稳定基础之上。**
