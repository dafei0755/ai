## 1. 为什么专题探讨功能与用途

在空间设计项目中，有一个最容易被跳过的前置步骤：

> **这个空间，要让人做什么？谁来做？为了什么目的？**

通常的做法是直接进入"这是民宿项目，那就按民宿来"——让空间分类承担了这个判断。但这里有一个隐藏错误：**空间分类是功能与用途确定之后的归类结论，而非前置判断框架。**

如果跳过功能与用途，直接用"空间类型"来驱动后续所有决策，就会产生系统性偏差：

- **空间分类失准**：同样叫"民宿"，山地疗愈型 vs 城市社交型的功能组合完全不同
- **本体论失焦**：对象关系的建立缺乏功能锚点，"客房""公区"只是标签，而不是活的功能系统
- **商业方法论失根**：推进顺序和决策框架悬空，因为"这个空间要达成什么"没有被真正打开

**一句结论：**

> 地理坐标确定了"在哪里"，功能与用途确定了"为什么在这里、要发生什么、谁来发生"。这是空间设计的第一性问题框架。

### 1.1 用途驱动的任务双模式（原则级）

功能与用途不仅决定“做什么”，也决定“这一轮需要承接多大范围”：

1. **全链路模式**：当用途尚未稳定、冲突较多时，按主链完整推进；
2. **片段辅助模式**：当用途已稳定，仅存在局部决策缺口时，允许只承接专题片段任务；
3. 双模式共享同一治理底线：片段可以局部承接，但不得绕过版本追溯、门禁与对象绑定；
4. 用户习惯中的外部数据流（如 CAD 平面图输入）可作为用途校验与空间修订的触发源，但必须先编译为系统对象，不得直接替代 `UseIntentBaseline/SPG`。

### 1.2 片段模式下的最小必要约束提示（流程级）

当用户仅做片段任务（如仅色彩、仅流线）时，系统应执行“最小必要约束提示”，而不是强制补齐全量项。

最小提示规则：

1. 色彩相关任务优先提示：地理语境 + 目标客群；
2. 平面/流线相关任务优先提示：用途目标 + 关键运营约束；
3. 若用户跳过提示项，允许继续，但必须在输出中附 `risk_notes` 与 `confidence`；
4. 当片段结果拟转正为正式交付时，必须回补并校验缺失约束。

## 2. 两个核心维度的定义

### 2.1 功能（Function）

**功能 = 这个空间让哪些活动发生。**

功能是空间的使能清单——哪些人类行为在这里可以成立，哪些不能。

它不是"你想做什么"，而是"这个空间结构上能承载什么"。

功能有层级：

| 层级 | 描述 | 民宿示范 |
|------|------|---------|
| 主功能 | 空间存在的核心活动使命 | 住宿与休息 |
| 辅助功能 | 支撑主功能运作的活动 | 餐饮、卫浴、存储 |
| 激活功能 | 提升体验质量、创造留存理由 | 公共社交、景观阅读、健身 |
| 运营功能 | 维持空间正常运转的后台活动 | 客房整理、物资配送、安防 |

**功能清单决定了：**
- 哪些房间必须有（必须有的空间模块）
- 哪些动线必须打通（流线拓扑）
- 哪些功能之间存在干扰（冲突识别）

### 2.2 用途（Use / Purpose）

**用途 = 这个空间被谁使用、以什么方式使用、为了达到什么效果。**

用途是功能的意图层——同样是"住宿"功能，不同的用途定义会产生完全不同的空间逻辑。

用途的三要素：

| 要素 | 问题 | 民宿示范 |
|------|------|---------|
| 使用者（Who） | 谁在这个空间里活动 | 家庭/情侣/商旅/短住康养人群 |
| 使用模式（How） | 以什么行为方式使用 | 自助式/服务式/浸入式/仪式感体验 |
| 使用目的（Why） | 使用结束时希望达到什么状态 | 疗愈/社交/拍照打卡/身份表达/逃离城市 |

**用途定义决定了：**
- 空间的情绪基调（安静疗愈 vs 社交活跃 vs 身份展示）
- 功能的权重分配（哪些功能是核心，哪些是点缀）
- 体验的峰谷设计（什么时刻是关键情绪节点）

### 2.3 功能 vs 用途：不是同一回事

| 维度 | 功能 | 用途 |
|------|------|------|
| 回答的问题 | 做什么 | 为谁做 / 为何做 |
| 视角 | 空间能力视角 | 人的目的视角 |
| 层次 | 操作层（What） | 意图层（Why + Who） |
| 主导者 | 建筑/室内逻辑 | 运营/人群/商业逻辑 |
| 产出物 | 空间模块清单 | 体验目标与使用场景 |

**两者必须同时确定，缺一则另一个失真：**
- 只有功能无用途：空间"能住"，但不知道谁来住、为什么来、要什么感受
- 只有用途无功能：知道"要让人感到疗愈"，但不知道靠哪些空间活动来承载这种感受

## 3. 功能与用途和地理坐标的联动

**地理坐标不只是背景，它直接约束和塑造功能与用途的可能性边界。**

### 3.1 地理坐标对功能的约束

| 地理条件 | 对功能的直接影响 |
|---------|----------------|
| 高海拔 / 高湿 | 餐饮后厨的通风功能不可省略；防潮功能必须前置 |
| 山地坡地 | 货运动线功能变复杂；无障碍化功能成本高 |
| 周边餐饮强势 | 本地餐饮供给功能可以弱化，差异化激活功能权重提升 |
| 景观稀缺资源 | 取景功能（景观朝向/窗口框景）优先级上升为主功能级 |
| 偏远 / 可达性差 | 自足性功能权重提升（洗衣/储物/食材备货） |

### 3.2 地理坐标对用途的约束

| 地理条件 | 对用途的直接影响 |
|---------|----------------|
| 高海拔度假区 | 使用者以康养/疗愈为主导目的，"打卡"目的被压制 |
| 城市封面地标 | 使用者使用目的叠加身份表达层，不能只做"住得舒适" |
| 老城历史街区 | 文化沉浸式用途合法，纯现代高效商务用途会"失地" |
| 旅游景区周边 | 过夜是工具性用途，目的是景区体验；民宿本身不是目的地 |

### 3.3 联动公式

```
GeoCoordinateBaseline（WHERE）
    +
FunctionalUseStatement（WHAT FOR + WHO）
    ↓
SPG 空间程序图谱（HOW TO DESIGN）
```

**关键原则：**

> 离开地理坐标谈功能，功能清单会是通用模板而非项目专属；
> 离开功能用途谈空间分类，分类变成贴标签而非真正理解项目。

## 4. 功能与用途是三大核心要素的共同基础层

### 4.1 它如何构成空间分类的底层

空间分类回答"这是什么项目"，但"是什么"的判断依据，正是功能与用途：

```
功能清单（住宿+餐饮+社交+激活功能）
    + 用途定义（康养人群 / 短住 / 自助式）
    ↓
空间分类判断：这是"山地度假民宿"，不是"精品酒店"，不是"青年旅社"
```

如果功能与用途不事先界定，空间分类就只是靠用户说的词来贴标签，无法校验该标签是否正确。

**反例：** 用户说"我做民宿"，但功能分析发现餐饮接待 > 住宿比例为 3:1，且用途分析显示主要服务本地聚会客群——这其实更接近"餐厅+包房"而非"民宿"。功能用途先行，才能识别这个漂移。

### 4.2 它如何构成本体论的底层

本体论定义"系统里有哪些对象、对象之间什么关系"。但对象的边界、属性和关系，来自功能与用途的结构性要求：

| 功能/用途需求 | 本体论对象结论 |
|-------------|--------------|
| 住宿功能 | 必须有 Room 对象，包含 capacity / orientation / privacy_level |
| 亲子用途 | Room 对象新增 child_safe / noise_isolation 属性 |
| 社交激活功能 | 必须有 CommonArea 对象，含 social_density / noise_zone 属性 |
| 后勤运营功能 | 必须有 StaffRoute 对象，与 GuestRoute 无交叉约束 |
| 疗愈用途 | CommonArea 的 social_density 阈值需要被约束在低密度 |

本体论如果不从功能用途推导，就变成一个僵硬的通用对象清单，无法反映这个项目的特殊结构逻辑。

### 4.3 它如何构成商业方法论的底层

商业方法论规定"按什么顺序推进、每阶段产出什么"。但推进顺序的排布依据，正是功能与用途的复杂度和优先级：

| 功能用途特征 | 商业方法论决策 |
|------------|--------------|
| 主功能简单（只住宿） | 可以较快进入方案阶段 |
| 多功能组合（住+餐+康+社） | 必须先完成功能权重确认，再进入SPG |
| 用途中含高不确定性（目标客群未明） | 必须在 Node3 内完成用途锁定，否则 SPG 漂移 |
| 用途和地理坐标有明显张力（用途 vs 地理约束冲突）| 必须在解题思路中前置处理冲突 |

## 5. 功能用途矩阵：结构化表达工具

将功能与用途综合表达为矩阵，作为进入 SPG 的前置输入：

| 功能类别 | 功能描述 | 主要使用者 | 使用模式 | 使用目的 | 地理约束影响 | 优先级 |
|---------|---------|----------|---------|---------|------------|-------|
| 主功能 | 住宿与休息 | 家庭/情侣/自驾客 | 自助式 | 疗愈/逃离 | 山地景观取景优先 | P0 |
| 辅助功能 | 早餐/轻餐 | 所有住客 | 半服务式 | 日常补给 | 周边餐饮强竞争，弱化正餐 | P1 |
| 激活功能 | 户外公区/共享客厅 | 家庭为主 | 自发性社交 | 增加留存感 | 景观朝向公区优先 | P1 |
| 运营功能 | 客房整理/物资配送 | 员工 | 隐性流线 | 维持运营 | 山地货运特殊设计 | P0（但不可见） |
| 可选功能 | 温泉/会客室/艺术空间 | 特定客群 | 仪式性 | 差异化记忆点 | 受预算和地质约束 | P2 |

这张矩阵完成后，再进SPG的分区、流线、策略规划，每一项都有溯源依据。

## 6. 域对象：FunctionalUseStatement

将"功能与用途"结构化为可被主链消费的域对象：

```python
class FunctionItem(BaseModel):
    function_id: str
    category: str           # primary / supporting / activation / operational / optional
    description: str        # 功能描述
    space_modules: list[str]  # 承载这个功能的空间模块
    priority: str           # P0 / P1 / P2

class UseContext(BaseModel):
    primary_users: list[str]   # 主要使用者画像
    usage_mode: str            # self_service / serviced / immersive / ritual
    experience_goal: str       # 使用结束时希望达到的状态
    emotional_tone: list[str]  # 与 GeoCoordinateBaseline.urban_semantic.emotional_tone 对齐

class FunctionalUseStatement(BaseModel):
    """
    功能与用途声明对象
    
    采集节点：Node3.S.1 解题思路前（与 GeoCoordinateBaseline 交叉编译产出）
    消费者：SPG / AlignedBrief
    冻结规则：与 GeoCoordinateBaseline 同步评估后，在 AlignedBrief 冻结前完成
    """
    project_id: str
    function_matrix: list[FunctionItem]     # 功能矩阵
    use_context: UseContext                  # 用途上下文
    function_conflicts: list[str]            # 已识别的功能冲突点
    geo_constraints_applied: list[str]       # 已从 GeoCoordinateBaseline 施加的约束
    unresolved_tensions: list[str]           # 功能与用途之间尚未解决的张力
    version: str
    freeze_status: str                       # draft / frozen
```

## 7. 在主链中的落位

功能与用途不新增独立大节点，而是作为 **Node3.S.0（地理坐标编译）之后、Node3.S.1（解题思路）之前** 的内置编译步骤：

```
Node1 用户输入
  → geo_pin 采集
  ↓
Node3.S.0 地理坐标编译
  → GeoCoordinateBaseline 冻结
  ↓
Node3.S.0.5 功能用途编译（新增）
  → 接收用户表述的功能期望
  → 交叉 GeoCoordinateBaseline 约束
  → 产出 FunctionalUseStatement
  → 识别功能冲突与用途张力
  ↓
Node3.S.1 解题思路
  → 消费 GeoCoordinateBaseline + FunctionalUseStatement
  → 主线问题从这两个基线共同推导
  ↓
AlignedBrief + SPG（空间程序图谱）
  → SPG 是 FunctionalUseStatement 的空间化实现
```

**SPG 与 FunctionalUseStatement 的关系：**

> SPG 不是凭空生成的空间结构，而是 `FunctionalUseStatement` 的空间编译版本——把"哪些功能用什么方式服务哪些人以达到什么目的"翻译为"哪些空间模块、怎样的流线拓扑、什么样的分区逻辑"。

## 8. 治理规则

### 硬规则

1. **`FunctionalUseStatement` 未完成 → SPG 不得生成**。SPG 必须从功能用途声明中派生，不得直接从空间类型模板填充。
2. **识别到的功能冲突必须显性处理**。不得把冲突偷偷甩给 Node4；若无法在 Node3 内解决，必须标记 `unresolved_tensions`，显性写入 AlignedBrief。
3. **用途定义与 GeoCoordinateBaseline 发生张力时，必须在 3.S.0.5 内进行仲裁**。不得两者都保留假装没问题。

### 版本规则

- 初次产出：`FunctionalUseStatement v1.0`（随 AlignedBrief 同步冻结）
- 用途重定义（例如：客群目标发生根本调整）→ 回 Node3 重编译，AlignedBrief + SPG 连带升版

## 9. 民宿示范案例

**场景：** 用户说"我要做一个山地民宿，预算1200万，8个月开业，兼顾亲子和年轻社交客群"

### 第一步：功能矩阵初步产出

| 功能 | 描述 | 优先级 |
|------|------|-------|
| 主功能 | 住宿（亲子房+双人间） | P0 |
| 支撑功能 | 早餐、卫浴、储物 | P0 |
| 激活功能-亲子 | 户外儿童活动区、亲子公区 | P1 |
| 激活功能-社交 | 青年公共客厅、露营台地 | P1 |
| 运营功能 | 客房清洁、厨房后勤、货运通道 | P0（隐性） |

### 第二步：用途上下文

- **使用者**：亲子家庭（主）+ 年轻情侣/朋友组（副）
- **使用模式**：自助为主，有少量服务节点（早餐/接待）
- **使用目的**：家庭疗愈 + 年轻人"反城市"情绪释放

### 第三步：交叉 GeoCoordinateBaseline 约束

- 山地坡地 → 货运通道需要独立规划，不能假设与客人共享
- 高湿环境 → 儿童户外活动区需要防滑/排水功能前置
- 周边农家乐竞品强 → 正餐功能弱化，差异化早餐体验提权
- 景观资源强 → 公区朝向景观面功能优先级 > 私密性

### 第四步：识别功能冲突

**冲突1：亲子静谧需求 vs 年轻社交噪音**
- 亲子客群需要安静环境（孩子休息时间早）
- 年轻社交客群需要活跃公区（夜间聚集）
- **仲裁：** 社交公区与亲子住宿区做噪音隔离分区；夜间10点后社交区静音规则进设计

**冲突2：激活功能（户外台地）vs 预算/工期约束**
- 1200万预算 + 8个月工期，双激活功能存在超预算风险
- **仲裁：** 先保学儿童活动区（P1a），露营台地作为P2选项待Phase 2

### 产出 FunctionalUseStatement 核心结论

```
主功能：住宿（亲子优先配比）
激活功能：以亲子户外活动区为P1a；年轻社交公区为P1b（噪音隔离设计）
用途：疗愈型亲子家庭度假 + 反城市情绪释放的年轻客群
已处理冲突：噪音分区方案
待观察张力：双激活功能预算压力（建议分期）
```

这个结论才能输入 SPG，生成真正有溯源依据的空间程序图谱。

## 11. 一句话总结

> **地理坐标确定"在哪里"，功能与用途确定"这里要发生什么、为谁而发生、达到什么效果"。**
> 这两个问题共同构成空间设计的第一性基础：空间分类从中归类，本体论从中推导对象，商业方法论从中确定推进优先级。跳过功能用途直接进方案，会让所有后续判断都漂浮在空中。

## 12. 系统级升级：FunctionalUseStatement → UseIntentBaseline

### 12.1 对象地位升级

从 **Phase 2026-03-25** 开始，将 `FunctionalUseStatement` 升级为 **`UseIntentBaseline`**，使其获得与 `GeoCoordinateBaseline` 并列的"强制基线"地位。

**为什么升级**：
- 功能与用途不仅是一个信息字段，而是决定整个项目定义和系统解题方向的核心锚点
- 必须与地理坐标同步冻结、版本化管理、消费方通知
- 是空间分类、本体论、商业方法论三大核心要素的共同底层依据

### 12.2 对象规范（融合参考意见的深化）

`UseIntentBaseline` 对象结构，融合参考意见1的三层功能分解框架：

```python
class UseIntentBaseline(BaseModel):
    """
    项目用途与功能基线对象 — 与GeoCoordinateBaseline并列的强制基线
    
    采集节点：Node1 → Node2 → Node3.S.0.5
    冻结节点：Node3.S.0.5
    消费者：AlignedBrief / SPG / WorkMap / Node3.S.1解题思路
    治理规则：冻结后不得静默修改，版本升级需通知所有消费者
    """
    
    # === 治理字段（与GeoCoordinateBaseline平行） ===
    project_id: str
    version: str                          # v1.0 / v1.1 / v2.0
    baseline_status: str                  # draft / frozen / v1.0_locked / invalidated
    frozen_at: datetime                   # 冻结时间戳
    geo_binding_version: str              # "GeoCoordinateBaseline.v1.0"（显式绑定）
    confidence_level: float               # 0.0-1.0，用途定义的确定度
    data_completeness: float              # 字段填充完整度
    
    # === 第一层：项目用途（Project Use） ===
    # 回答：这个项目在社会/商业/家庭中的根本角色是什么
    project_archetype: str                # 民宿 / 私宅 / 酒店 / 零售 / 展示 / 复合体
    project_use_primary: str              # 度假康养 / 家庭仪式 / 商务接待 / 品牌展示等
    project_use_secondary: list[str]      # 季节性/可选用途
    target_users: list[str]               # 主要客群画像
    success_end_state: str                # 使用完成时期望达到的状态
    core_value_proposition: str           # 项目为用户创造的核心价值
    
    # === 第二层：运营用途（Operational Use）— 新增维度 ===
    # 回答：它如何成立、按什么逻辑运营、依靠什么收入模式
    business_model: str                   # 自住 / 短租 / 长租 / 混合 / 品牌运营
    operational_model: str                # 自助式 / 服务式 / 管家型 / 混合
    payer_roles: list[str]                # 谁来支付
    operator_roles: list[str]             # 谁来运营
    revenue_logic: str                    # 入住率 / 客单价 / 复购率 / 品牌溢价等
    operational_cycle: str                # 日常/周/季/年的运行节奏
    peak_valley_pattern: str              # 业务的季节波动模式
    temporal_logic: list[str]             # 工作日→周末、淡季→旺季等时间变量
    
    # === 第三层：空间功能（Spatial Function） ===
    # 回答：空间要承载哪些活动、谁来使用、怎样使用
    function_matrix: list[FunctionItem]   # [见§5定义]
    use_context: UseContext               # [见§6定义]
    
    # === 交叉编译结果 ===
    geo_constraints_applied: list[str]    # 从GeoCoordinateBaseline施加的约束列表
    geo_derived_opportunities: list[str]  # 从GeoCoordinateBaseline推导的机会
    geo_function_mismatches: list[str]    # 地理-功能不匹配点（参考意见2启发）
    
    # === 冲突与张力（保留主架构方式） ===
    function_conflicts: list[str]         # 已识别的功能冲突点
    unresolved_tensions: list[str]        # 未能在Node3内完全解决的张力
    conflict_arbitration_log: list[str]   # 已解决冲突的仲裁记录（追溯性）
    
    # === 元数据 ===
    created_at: datetime
    last_modified_at: datetime
    modified_reason: str                  # 为何修改，链接到版本升级理由
```

### 12.3 Node2-Node3 工作流升级

#### Node2 新增"功能初步交互"门禁

在现有的"地理点选 → 空间分类确认"之后，新增第三步：

```
Node2 强制门禁流程（改进后）：
  ① 地理点选
     → 获得 GeoCoordinateBaseline.GeoPin
     → 触发空间分类推荐
     
  ② 空间分类确认
     → 用户确认或修正分类
     → 为功能/用途采集提供语境
     
  ③ 功能/用途初步交互（新增）
     → 系统基于"空间分类"推荐常见的用途模板
     → 用户选择 + 自由描述
     → 记录为 UseIntentBaseline.draft（未冻结）
     
  进入Node3的前置条件：地理✓ && 空间分类✓ && 用途初步表述✓
```

#### Node3.S.0.5 强化为"双基线交叉编译"专门步骤

```
Node3.S.0.5 执行逻辑：

【输入源】
  - GeoCoordinateBaseline.frozen v1.0（来自Node3.S.0）
  - UseIntentBaseline.draft（来自Node2 + 用户补充）
  - 空间分类确认结果

【执行方式】
  Step A：功能矩阵精化（参考意见1的三层拆解）
    用户初步表述 → 精化为具体功能清单、优先级、用途层级
    
  Step B：地理约束施加（参考意见2的反向校验思路）
    从 GeoCoordinateBaseline 推导约束：
    · 物理约束（防潮/排气/坡地动线）
    · 市场约束（周边竞品/可达性）
    · 文化约束（taboo_styles）
    输出："约束下可行的功能清单"
    
  Step C：冲突仲裁（参考主架构的做法）
    识别并处理：
    · 功能-功能冲突 → 通过分区/优先级排序仲裁
    · 地理-功能不匹配 → 仲裁或标记unresolved_tensions
    输出："已处理冲突的记录" + "待观察张力列表"

【校验规则】（参考意见2，但采用显性标记而非硬退出）
  - 地理-功能接近度 < 70%？ → 显示风险标记✓（允许继续）
  - 识别到的冲突全部输出到 unresolved_tensions

【输出】
  UseIntentBaseline.frozen v1.0
  绑定到 geo_binding_version="GeoCoordinateBaseline.v1.0"
  包含所有编译结果与冲突仲裁记录
```

### 12.5 治理规则升级

#### 硬规则

1. **UseIntentBaseline 未冻结 → SPG 不得生成**
   - 理由：SPG必须从使用意图的功能矩阵派生，不得凭想象

2. **一旦冻结 → Node4 不得静默修改运营模型**
   - 理由：商业方法论已依此制定，修改需版本升级与AlignedBrief同步

3. **交叉编译中的冲突必须显性处理**
   - 一律标记到 unresolved_tensions，显性写入ALignedBrief.risks

4. **GeoCoordinateBaseline升版 → UseIntentBaseline自动标记"需评估"**
   - 不立即失效，但通知所有消费者地理约束已变更

#### 版本规则

- **初版**：UseIntentBaseline v1.0（与AlignedBrief同步冻结）
- **修订**：用途重定义（客群转向/商业模型调整）→ 升到v1.1/v2.0，通知消费者
- **撤销**：地理根本变更（地点转移）→ 标记invalidated，重新编译

### 12.6 三大核心要素与 UseIntentBaseline 的推导关系

| 核心要素 | 推导规则 |
|---------|---------|
| **空间分类** | UseIntentBaseline.project_archetype → 分类不是标签，而是从三层用途结构推导出的 |
| **本体论** | UseIntentBaseline.function_matrix → 每个FunctionItem激活对应的本体对象与属性约束 |
| **商业方法论** | UseIntentBaseline.(business_model + temporal_logic) → 推进顺序与优先级 |

**关键洞察**：现在"空间分类是什么"不再是用户凭直觉说的"民宿"，而是有原因可追溯的"基于功能/用途定义的民宿"。
