## 0. 本专题的目的

在「地理坐标基线」「功能与用途基线」「建筑载体基线」三输入的基础上，正式确立「人」的系统级地位。

**核心判断**：人必须上升到系统级高度，但**不是**作为第四个并列 Baseline，而是作为**编译层/仲裁层**，在 Node3.S.0d 处正式对象化，向下游施加一致的人因约束。

**一句话定性**：

> 离开人，空间没有成立的意义。没有被对象化的人，最终会被设计师的想象代替。

---

## 1. 人的四个系统级问题

设计系统在处理「人」时，本质上要回答四个问题：

### 1.1 这个空间最终是为哪些人服务？

**答案来源**：`UseIntentBaseline.user_archetype + user_profile`（功能用途基线中的人群定义）

- 个体维度：年龄段、身体条件、审美倾向、生活方式、认知习惯
- 群体维度：家庭结构、团队关系、同住/分住关系、社交频率
- 社会维度：阶层/圈层、职业身份、地域文化、审美语境

### 1.2 这些人会怎样使用它？

**答案来源**：`HumanContextLayer.behavior_layer + body_layer`（人因编译层的行为与身体维度）

- 身体模式：进入/停留/转身/坐卧/洗漱/收纳的尺度与路径
- 行为模式：典型活动序列、高频行为节点、行为冲突点、隐私梯度
- 时间模式：谁在什么时候出现、停留多久、峰值场景是什么

### 1.3 冲突时谁优先、为什么？

**答案来源**：`HumanContextLayer.social_layer + 加权仲裁规则`（人因编译层的社会关系与冲突仲裁）

- 多用户权重矩阵（谁的需求优先满足）
- 角色优先级（父母vs孩子、主人vs客人、使用者vs服务方）
- 保护的人性底线（不可牺牲的基础需求）

### 1.4 设计是否真的让人感到安全、顺畅、认同、被表达、被疗愈？

**答案来源**：`HumanContextLayer.psychology_layer + 需求层级验证`（人因编译层的心理维度与五层需求检查）

- 五层需求覆盖（安全层→舒适层→审美层→身份层→超越层）
- 触发器与禁区（哪些行为会让人恐惧/烦躁/疏离）
- 情绪峰谷变化（空间是否支持人的情绪节奏）
- 记忆锚点（什么会成为这个空间在人心中的永久记忆）

## 2. 为什么「人」不能是第四个并列 Baseline

### 争议背景

在六份参考意见中，有三份（参考1、3、4）强烈主张新建 `HumanBaseline / HumanContextBaseline / HumanFactorsBaseline`，与 `GeoCoordinateBaseline / FunctionUseBaseline / BuildingCarrierBaseline` 完全并列。

这个主张的表面逻辑很强：既然地理、功能、建筑都是 Baseline，人也应该是。

**但这个逻辑有三个致命问题**：

### 2.1 「人」不是客观事实，是解释视角

| 对象 | 性质 | Node1 采集方式 | 冻结后可否改 |
|------|------|--------------|-----------|
| GeoCoordinateBaseline | 客观地点 | 点选地图/输入坐标 | 几乎不改（改地点=新项目） |
| FunctionUseBaseline | 用途声明 | "民宿"/"办公"单选 | 改则变项目 |
| BuildingCarrierBaseline | 建筑物理现实 | CAD/底图/数据 | 改则变项目 |
| HumanContextBaseline（如果平级） | 人的描述/假设 | ??? 什么算"采集"完成 | 人可能变，假设会错 |

地理、功能、建筑都是**外部约束**——项目方说了「在峨眉山，做民宿，改造老木屋」，系统就有了约束边界。

但「人」不同：
- 项目方说「目标客群是中产家庭」，但什么是"中产"？预期停留时长多久？私密需求有多强？
- 这些需要编译、需要跨学科补充（B4 身份识别 + C3 行为引擎 + X5 加权器）
- 这些也会在项目进行中被修正（比如:"哦，这个客群其实更需要社交，不是独处"）

所以「人」是**不稳定的、需要编译、需要持续确认**的。把它当成与地理/建筑平行的"基线"，会要求 Node1 采集不了的东西。

### 2.2 引入对象重复维护的陷阱

如果新建 `HumanContextBaseline`：

```
UseIntentBaseline:
  ├─ target_users: "亲子家庭"
  ├─ primary_users: ["成年人", "儿童"]
  ├─ payer_roles: ["父母"]
  └─ user_profile: {...}

HumanContextBaseline:  ← 新建，与上面重复
  ├─ primary_user_profile: "亲子家庭"
  ├─ user_roles: ["成年人", "儿童"]
  └─ segment_profiles: {...}
```

到时候问题来了：
- 两个地方身份信息不同步怎么办？
- 哪个是真的"真相源"？
- 系统怎么自动一致性校验？

这不是"两个角度看同一个数据"的好设计，而是**同一信息在系统里出现两次，造成维护噩梦**。

### 2.3 人体工程学应与 FloorPlanIR 的门禁结合，不是 Baseline 的字段

参考3/4 倾向于把"人体工程学约束"放进新 Baseline 的字段里，比如：

```
HumanContextBaseline:
  ergonomic_constraints:
    - clearance_standards: "通道宽度900mm"
    - reach_zone_limits: "台面高度800-850mm"
```

**问题**：字段本身无法执行。真正的门禁校验应该在 `FloorPlanIR.BodyFitValidator` 里，自动对比平面的实际尺寸。

如果只是在 Baseline 里写了"通道宽度900mm"，但平面编译器没有校验逻辑，那这个字段只是文档，无法真正约束系统。

### 2.4 架构的一致性原则

当前系统的原则是：**Baseline 承接外部约束，对象链承接求解过程**。

```
GeoCoordinateBaseline ┐
FunctionUseBaseline  ├─→ [编译] → SpaceOntologyBaseline / SPG
BuildingCarrierBaseline ┘
                                    ↓
                                    [SPG决定] → AlignedBrief / WorkMap
                                    ↓
                                 [编译] → FloorPlanIR
                                    ↓
                                [验证与投影] → VizDeliveryPack
```

如果在这个链的"编译"环节塞进一个新的"能和前三者平行的 Baseline"，就破坏了这个清晰的分层。

更合理的做法：在 Node3.S.0d 新增一个**编译步骤**，它消费 `UseIntentBaseline + 已有的武器库工具`，生成一个**解释层对象** `HumanContextLayer`——不是新 Baseline，而是"对上游约束如何在人因维度被理解和应用"的交付物。

## 3. 采纳方案：HumanContextLayer（编译层/仲裁层）

### 3.1 定位

`HumanContextLayer` 不是 Node1 的第四个输入 pin，不是与前三个 Baseline 平行的独立冻结对象。

它是：

- **Node3.S.0d 的编译输出**（在 3.S.0 / 3.S.0.5 / 3.S.0.7 三个 Baseline 编译完成后）
- **统一的人因解释与仲裁接口**（向下游 SPG、WorkMap、AlignedBrief 施加一致的人因约束）
- **参考意见1的四层结构的正式对象化**（身体层/行为层/心理层/社会关系层）
- **武器库工具的统一出口**（B4 身份识别 + C3 行为引擎 + X5 加权器 + 需求层级框架的结果汇总）

## 4. 对 UseIntentBaseline 的升级（不新建 Baseline，就地升级）

### 4.1 不「新建 HumanBaseline」的理由

`UseIntentBaseline` 已经有 `target_users` 字段，如果新建 `HumanContextBaseline` 平行对象，必然导致：

```
来源1: UseIntentBaseline.target_users = "亲子家庭"
来源2: HumanContextBaseline.primary_user_profile = "亲子家庭"
来源3: HumanContextLayer.social_layer.primary_users = ["成人", "儿童"]
```

三个地方都在说"这个项目的用户构成"，但来自不同对象，维护混乱噩梦。

**更合理的做法**：在 UseIntentBaseline 内部，把 `target_users` 从文本标签升级为结构化 `HumanProfile` 字段，这样：

- 保持 UseIntentBaseline 作为唯一的"功能与用户的语义源头"
- 避免同一信息两处维护
- HumanContextLayer 可以直接引用这个结构化 `HumanProfile`，而不需要新 Baseline

### 4.2 升级方案：HumanProfile 字段组

在 `B 架构/09-功能与用途专题.md` 中，把 UseIntentBaseline 的原有字段：

```python
target_users: list[str]  # 当前：只是文本标签
```

升级为：

```python
target_users: list[str]  # 保留原有的向后兼容文本标签

human_profile: HumanProfile = {  # 新增：结构化人群画像
    "user_archetype": "亲子家庭",  # 主要使用者类型
    "group_composition": {
        "primary_users": ["成人", "儿童"],
        "age_segment": {"adults": "35-50", "children": "6-12"},
        "typical_group_size": "3-4人"
    },
    "behavioral_pattern": "停留型/疗愈/轻社交",
    "cultural_reference": "都市中产，西方审美",
    "privacy_expectation": "中等私密需求（家庭内共处，但需隔离公开来客）",
    "accessibility_needs": "无特殊无障碍需求，但需儿童友好设计（防跌落、圆角等）"
}
```

这样 UseIntentBaseline 本身就承载了足够的人群信息，HumanContextLayer 则进一步对这些信息进行编译、验证、补充心理和社会维度。

## 6. 人体工程学的双层部署

### 6.1 为什么是「双层」而非「单个字段」

人体工程学不应该只停留在"新 Baseline 的一个字段"，而应该在两个层次同时发挥作用：

层次 A（语义层）：SPG 中定义尺度要求
```
SPG.scale_requirements:
  - meeting_room.size_range: "20-40㎡"
  - corridor.min_width: "900mm"（来自 HumanContextLayer.body_layer.ergonomic_constraints）
```

层次 B（几何层）：FloorPlanIR 中执行校验
```
FloorPlanIR.validation.BodyFitValidator:
  检查实际通道尺寸是否≥900mm
  检查轮椅回转空间是否≥1500mm
  检查台面高度是否在800-850mm范围内
```

### 6.2 BodyFitValidator（新校验器）

在 `4-1 平面图/01-平面图落地思路与执行路径.md` 的 Section 6「五门制在平面层的落位」中新增：

```python
class BodyFitValidator(ContractValidator):
    """人体工学硬约束校验"""
    
    def validate(self, floorplan_ir: FloorPlanIR, human_context: HumanContextLayer) -> ValidationResult:
        checks = [
            # 通道宽度
            self._check_circulation_width(floorplan_ir, human_context),
            # 轮椅回转（若无障碍）
            self._check_wheelchair_accessibility(floorplan_ir, human_context),
            # 台面高度（厨房/卫浴）
            self._check_counter_height(floorplan_ir, human_context),
            # 视线高度（儿童友好）
            self._check_child_sight_lines(floorplan_ir, human_context),
            # 无眩光要求
            self._check_glare_sensitivity(floorplan_ir, human_context)
        ]
        return self._compile_result(checks)
```

这个校验器不是"建议"，而是**门禁阻断**——人体工学硬约束不满足，FloorPlanIR 无法进入下一阶段。

### 6.3 RelationshipFitValidator（关系编排校验）

类似地，新增：

```python
class RelationshipFitValidator(ContractValidator):
    """人际关系编排校验"""
    
    def validate(self, floorplan_ir: FloorPlanIR, human_context: HumanContextLayer) -> ValidationResult:
        checks = [
            # 私密梯度
            self._check_privacy_gradient(floorplan_ir, human_context),
            # 冲突避免
            self._check_conflict_zones(floorplan_ir, human_context),
            # 权力空间
            self._check_power_dynamics_space(floorplan_ir, human_context)
        ]
        return self._compile_result(checks)
```

## 7. 为什么这不是「第七个项目要素」

当前口径为 **5个核心项目要素 + 系统承接层**：

1. 空间分类
2. 本体论
3. 商业方法论
4. 通用方法论
5. 知识底盘

配套结构：系统承接层（分层 + 对象链 + 交付链 + 治理）

「人」不新增为第七个要素，原因有三：

### 7.1 「人」已经贯穿在要素层与承接层中

升级后的关系是：

| 要素 | 与「人」的关系 |
|-----|--------------|
| 空间分类 | 由「地理 × 人群结构」共同确定（不只是"民宿"，而是"亲子康养型民宿"） |
| 本体论 | 对象属性需要同时考虑人体工学、行为模式、心理需求 |
| 商业方法论 | 由「用户需求层级」决定推进顺序（先安全层，后审美层） |
| 通用方法论 | 追问引擎增加「人-功能-建筑」三向冲突检查 |
| 知识底盘 | 案例索引增加「human_profile_tags」维度 |
| 系统承接层 | 新增 HumanContextLayer 作为人因约束的统一出口 |

「人」不是第七个平行的要素，而是贯穿在所有要素中的**价值判据**。

### 7.2 对外口径稳定，对内架构升级

对外沟通时，保持"5要素 + 系统承接层"。对内实现时，每个要素都获得了"人因维度"的升级。

这样避免项目要素层与承接层混平，不破坏现行主口径。

### 7.3 「人」的系统级地位更高，不需要降级为"第七个要素"

如果把「人」改成第七个并列要素，反而是一种降格——它会沦为"既有要素体系之外的附加项"。

实际上「人」应该是**所有设计决策的终极判据**——在上方，而不是在旁边。

## 9. 最终定性

### 核心论述

空间为人而存在，但不是"为抽象的人"。

- 如果系统里没有"人"的对象化，后面所有东西——功能、平面、视觉、商业模型——都会变成**"设计师在替用户想象"**。
- 如果人被对象化为第四个并列 Baseline，会导致**同一信息两处维护**，系统陷入混乱。
- 如果人只停留在"文本标签"（UseIntentBaseline 中的 `target_users: "亲子家庭"`），就无法真正驱动下游决策。

**正确的做法**：

1. 在 UseIntentBaseline 内部升级为结构化 `HumanProfile`（不新建对象）
2. 在 Node3.S.0d 新增编译步骤，生成 `HumanContextLayer`（编译层/仲裁层）
3. 让 SPG、FloorPlanIR、WorkMap 都显式引用 HumanContextLayer 的约束
4. 通过 `BodyFitValidator / RelationshipFitValidator` 把人因约束变成可执行的门禁

### 一句话系统级定位

**人是设计系统的终极价值判据——不做第四个并列 Baseline，而是做所有设计决策背后的仲裁者。离开人，空间没有成立的意义；没有被对象化的人，最终会被设计师的想象代替。**
