# 01 项目底盘的输入

版本：v0.2  
日期：2026-04-30  
定位：定义项目底盘由哪些多源输入构成、如何编译、如何进入平面推演与方案画布

## 1. 核心裁决

项目底盘不应被理解为一张一次性填写完成的表单。

更准确地说：

```text
项目底盘是一个由多源、异质、动态输入共同建构的项目认知模型。
```

它不是只记录：

```text
项目类型
面积
预算
客群
风格
```

而是要回答：

```text
这个项目处在什么地方？
这个地方意味着什么？
建筑真实状态是什么？
用户真正想要什么？
经营逻辑是否成立？
有哪些资源、限制、风险和沉默地带？
哪些判断来自事实，哪些只是系统假设？
```

所以项目底盘的输入应从单一表单升级为：

```text
文字输入
+ 地理坐标
+ 图纸资料
+ 现场资料
+ 视觉参考
+ 经营目标
+ 时间约束
+ 利益相关方
+ 合规约束
+ 历史案例
+ 用户语言信号
+ 设计师 / 硅基分身偏好
+ 平面推演反向回填
```

最终目标不是“填满信息”，而是形成一个足够支撑判断的 `ProjectContext`。

## 2. 与平面推演的关系

项目底盘与平面推演不是简单顺序：

```text
项目底盘 → 平面推演
```

更准确的链路是：

```text
多源项目输入
→ ProjectSeed / 项目种子
→ ProjectContext / 项目上下文
→ GeoContext / SiteContext / MarketContext / FieldEvidence
→ LightProjectBrief
→ SpatialProgramGraph
→ FloorPlanFacts
→ DesignConstraintGraph
→ LayoutVariant
→ 用户选择与系统反诘
→ BackfillEvent / ProjectBasePatch
→ 项目底盘升版
```

也就是说：

```text
项目底盘给平面推演提供判断依据；
平面推演给项目底盘提供验证结果。
```

例如：

```text
项目底盘提出：本项目应强化景观公区。
平面推演发现：景观公区强化会导致 4 间客房失去最佳山景。
系统应回填：景观公区传播价值与客房看山率存在资源争夺。
```

再例如：

```text
项目底盘提出：预算不能失控。
平面推演发现：体验价值版需要大量拆墙和后勤移位。
系统应回填：用户并非绝对低预算，而是希望“强体验节点局部投入，客房区低改造收敛”。
```

所以平面推演不只是消费项目底盘，也参与生成项目底盘。

## 3. 关键冲突的裁决：地理坐标是否必须前置

参考意见中有一个重要张力：

```text
一方认为地理坐标应成为 L0 必填项；
另一方认为用户可以从任意入口开始，不应被表单阻断。
```

综合判断如下：

```text
地理坐标是正式项目底盘的一级输入；
但不是所有探索动作的硬阻断门槛。
```

具体规则：

```text
只有图纸，没有地理坐标：
可以做空间事实识别、粗风险提示、中性平面可能性。

有项目类型 + 图纸，但没有地理坐标：
可以做轻推演，但必须标注“缺少在地语境”。

有项目类型 + 地理坐标 + 图纸：
可以做场地化平面推演。

有项目类型 + 地理坐标 + 现场资料 + 经营目标：
可以做正式多版本推演、风险反诘和底盘升版。
```

一句话：

```text
地理坐标不是启动探索的绝对门槛，
但它是进入正式项目判断和场地化推演的必要条件。
```

## 4. 项目底盘的多源输入地图

建议把项目底盘输入划分为 12 类。

```text
1. 用户文字与对话输入
2. 地理坐标与地址输入
3. 图纸资料输入
4. 现场照片与视频输入
5. 卫星图 / 航拍 / 地图输入
6. 建筑效果图 / 历史方案 / 参考图输入
7. 手绘示意与用户标注输入
8. 商业目标与经营模式输入
9. 时间约束输入
10. 利益相关方与决策结构输入
11. 法规、政策与合规输入
12. 历史案例、竞品与硅基分身输入
```

每一类输入都必须记录：

```text
来源
可信度
是否用户确认
影响哪些推演维度
是否需要回查
是否与其他输入冲突
```

## 5. 地理坐标输入：项目所处的世界

地理坐标不是“项目地址”字段，而是项目底盘的上游变量。

它会派生：

```text
自然维度：气候、海拔、湿度、日照、风向、雨雪、植被
文化维度：地方文化、民族特征、历史记忆、地方禁忌、节庆习俗
经济维度：城市等级、消费能力、收入水平、租金与造价水平
商业维度：周边业态、竞品密度、客群结构、消费习惯、价格锚点
政策维度：规划性质、文保风险、产业政策、地方管理要求
交通维度：自驾可达、公共交通、停车、落客、机场 / 高铁距离
历史维度：街区演变、建筑记忆、地方叙事素材
时间维度：淡旺季、季节性、未来规划变化
```

同样是：

```text
800㎡ 民宿，12 间客房
```

不同地理坐标会推导出完全不同的平面策略：

```text
莫干山：周末度假、复购、社交公共区、强竞品差异化。
大理：景观面、慢生活、旅拍、院落感、文化商业混合。
香格里拉：高海拔、保温、供氧、文化谨慎、深度旅居。
喀纳斯：短旺季、长冬、暖源中心、远程客流、强室内核心。
县城近郊：亲子、团建、成本控制、停车与外摆效率。
```

### 5.1 GeoContext 对象

建议项目底盘中建立 `GeoContext`：

```json
{
  "geo_context": {
    "location_name": "重庆仙女山",
    "coordinates": [107.75, 29.43],
    "location_precision": "town_or_scenic_area",
    "terrain_type": "mountain",
    "altitude_band": "mid_mountain",
    "climate_tags": ["humid", "cool_summer", "possible_fog"],
    "view_resources": ["mountain_view", "forest_view"],
    "access_pattern": "self_driving_primary",
    "seasonality": "summer_peak",
    "local_culture_tags": ["mountain_resort", "western_chongqing"],
    "market_context_status": "to_be_enriched",
    "confidence": 0.68
  }
}
```

### 5.2 地理坐标的解析层级

地理输入允许不同精度：

```text
国家 / 文化圈：决定方法论适用边界。
气候带 / 地理大区：决定自然约束和材料语言。
城市 / 行政区：决定消费能力、客群结构和政策环境。
街区 / 景区 / 村落：决定商业氛围、竞品密度和到达方式。
具体坐标 / 场地边界：决定景观、朝向、道路、噪音和入口逻辑。
```

产品应允许用户从低精度开始，但要持续提示：

```text
当前地理精度不足，系统只能做区域级判断。
补充具体地址或坐标后，可进一步判断景观面、到达路径、竞品和气候风险。
```

## 6. 现场资料输入：建筑真实处在什么世界里

图纸回答：

```text
建筑被画成什么样。
```

现场资料回答：

```text
建筑真实是什么状态。
```

现场信息应被视为“第二底盘”，因为它往往比图纸更接近真实项目。

### 6.1 现场照片

应鼓励用户上传：

```text
入口
外立面
室内现状
窗外景观
楼梯
柱梁
天花
地面
卫生间
后勤区域
设备井
周边环境
破损与老化状态
```

影响：

```text
改造成本判断
空间气质判断
结构可动性判断
入口体验
景观资源
采光真实性
拍照传播点
材料策略
维护风险
```

### 6.2 卫星图 / 航拍图

影响：

```text
建筑朝向
道路接入
停车与落客
周边密度
山体 / 水体关系
景观方向
噪音来源
邻里关系
场地边界
外部人流
```

### 6.3 建筑效果图 / 原始设计图

它们不一定是事实，但能表达：

```text
原建筑意图
外立面语言
业主预期
既有方案方向
已投入成本
哪些方向可能已经被否定
```

系统应明确：

```text
效果图是意图资料，不是现场事实。
```

### 6.4 手绘示意

手绘常常包含用户真实意图：

```text
这里想做大堂
这里要看山
这里不要动
这里做客房
这里希望动线断开
```

系统应把手绘作为 `UserIntentEvidence`，不能直接当成几何事实。

### 6.5 视频 / 走访记录

影响：

```text
到达路径
空间连续性
真实尺度感
光线变化
噪声
气味
湿度
人流动线
```

### 6.6 竞品照片 / 周边项目资料

影响：

```text
差异化定位
价格段判断
风格避让
传播策略
客群画像
商业竞争
```

## 7. 视觉资料的证据等级

不同资料不能混为一种“事实”。

建议建立证据等级：

```text
用户确认事实
> 实测数据
> 测绘图 / CAD / 施工图
> 现场照片 / 视频
> 卫星图 / 航拍
> 用户手绘与标注
> 效果图 / 参考图
> 用户口述
> 系统推测
> 默认假设
```

注意：

```text
现场照片可能比旧图纸更接近真实。
效果图表达意图，但不能证明现场能实现。
手绘表达用户目标，但不能作为尺寸依据。
卫星图适合判断外部关系，但不能替代现场踏勘。
```

系统输出任何判断时，都应能给出来源链。

例如：

```text
判断：南侧适合做景观公区。

来源链：
- 卫星图显示南侧无遮挡山景
- 现场照片显示南侧窗面连续
- 用户确认主要景观在南侧
- 民宿目标包含“景观记忆点”
```

## 8. 更多关键输入

### 8.1 时间维度

空间不是静态的。

应记录：

```text
项目启动时间
开业目标
工期范围
雨季 / 雪季 / 旺季
淡旺季变化
日夜使用差异
入住高峰
清扫时段
早餐时段
未来扩建可能
建筑历史年份
历次改造记录
```

对平面推演的影响：

```text
工期短：排除过激拆改。
雨季施工：优先保守结构与防水路径。
冬季运营：公区取暖、入口缓冲、热饮与围坐更重要。
旺季前开业：功能优先级需要收敛。
淡季明显：公共区和运营面积不宜盲目放大。
```

### 8.2 经营模式

尤其对民宿、商业、餐饮、办公项目，经营模式必须进入底盘。

字段包括：

```text
高客单价 / 中端走量
自营 / 托管 / 品牌加盟
是否重餐饮
是否重社交传播
是否依赖团建
是否需要活动空间
是否需要二次消费
人员配置
清扫标准
早餐模式
入住办理方式
前台是否常驻
```

没有经营模式，平面推演容易只做空间，不懂运营。

### 8.3 目标客群

不是所有民宿都服务同一类人。

例如：

```text
情侣度假
亲子家庭
朋友小团体
企业团建
高端疗愈
摄影打卡
长住避暑
退休旅居
研学营地
```

不同客群影响：

```text
客房面积
公区类型
私密度
亲子活动
早餐空间
社交尺度
噪音控制
户外动线
安全边界
```

### 8.4 资源与限制

很多平面问题实际是资源问题。

应记录：

```text
预算
工期
施工队能力
材料供应
山地运输难度
消防限制
排水排污
电力容量
暖通条件
运营人员
当地审批
产权边界
邻里关系
```

### 8.5 利益相关方与决策结构

“用户”不是一个抽象点，真实项目里常常是多方决策。

应记录：

```text
谁有最终决策权
谁有否决权
谁主导审美
谁控制预算
未来运营方是谁
家人 / 合伙人 / 投资人是否参与
工程顾问 / 造价顾问是否有强约束
```

对推演的影响：

```text
夫妻共同决策：可生成审美光谱两端版本用于对照。
运营方强势：服务动线、清扫效率和后勤节点权重提高。
投资人控预算：保守版和 ROI 解释要更强。
业主全权委托：系统可更主动提出策略判断。
```

### 8.6 用户语言与情绪信号

用户的表达本身也是输入。

系统应识别：

```text
专业词密度
描述精度
犹豫词
担忧词
否定词
反复出现的偏好
从未提及的沉默地带
```

例如：

```text
用户反复说“不要太贵”“能省就省”，预算严格度应提高。
用户反复说“不要像网红店”，品牌差异化和审美克制应提高。
用户从不提运营，系统应主动询问是否已有运营方。
```

### 8.7 法规与合规输入

根据：

```text
项目类型
地理坐标
建筑属性
经营模式
```

系统应自动初始化合规约束清单。

包括：

```text
消防
无障碍
卫生防疫
餐饮许可
民宿备案
特种行业许可
文保与历史建筑保护
地方性管理条例
加建限制
排污与环保
```

合规输入应作为硬约束或高风险约束进入推演。

### 8.8 历史案例、竞品与对标

输入包括：

```text
成功案例
失败案例
竞品调研
业主参考项目
设计师历史项目
平台知识底盘案例
```

作用：

```text
确定差异化方向
提取空间策略
识别用户审美锚点
建立价格与客群参照
为版本解释提供来源链
```

### 8.9 设计师偏好 / 硅基分身输入

同一个项目，不同设计师会做出不同判断。

底盘可读取：

```text
设计师更保守还是激进
更重体验还是重成本
是否擅长东方叙事
是否擅长轻改造
常用空间策略
常被客户接受的方案类型
常被客户否定的风险点
```

这部分不应替代项目判断，只能作为生成版本的个性化偏置。

## 9. 沉默地带：用户没有说什么

用户没有说的内容，也是重要输入。

例如：

```text
从不提预算：可能预算宽，也可能没想清楚。
从不提运营：可能已有运营方，也可能忽略运营。
从不提客群：可能没有用户研究。
从不提风险：可能过度乐观。
从不提现场限制：可能误以为都能改。
```

系统应把沉默地带转为温和反诘：

```text
我注意到你详细讲了空间想做什么，但还没有提运营。
这个项目是自营、托管，还是后续再定？
这会影响前台、后勤、清扫和早餐动线。
```

沉默地带不是为了质疑用户，而是防止底盘缺少关键判断。

## 10. ProjectContextCompiler：多源输入编译层

建议在项目底盘与平面推演之前建立：

```text
ProjectContextCompiler
```

它负责把多源输入编译成可推演上下文。

### 10.1 输入

```text
用户文本
地理坐标
项目地址
PDF / CAD 平面
现场照片
卫星图
手绘
建筑效果图
竞品案例
预算信息
运营目标
客群信息
时间约束
利益相关方
设计师偏好
法规清单
```

### 10.2 输出

```text
ProjectSeed
ProjectContext
GeoContext
SiteContext
FieldEvidence
MarketContext
StakeholderContext
TimeContext
ComplianceContext
LightProjectBrief
BriefGap
AssumptionRegister
SourceTrace
```

### 10.3 编译职责

```text
提取事实
识别假设
标注来源
判断置信度
发现冲突
生成缺口卡
提出轻问询
把可用信息转为 SPG / DesignConstraintGraph 的输入
```

没有这个编译层，平面推演会过度依赖图纸和用户一句话。

有了这个编译层，系统才真正像空间设计高参。

## 11. 底盘成熟度：从线性等级到维度密度

底盘不是“完成 / 未完成”，而是多维度密度逐步增加。

### 11.1 线性成熟度

```text
L0：只有单一输入
L1：轻项目底盘
L2：可推演底盘
L3：可冻结底盘
L4：项目资产底盘
```

#### L0：只有单一输入

例如：

```text
只有平面图
只有照片
只有一句话
只有地址
```

系统可以：

```text
输入识别
事实摘要
明显风险提示
缺口卡生成
```

不能：

```text
正式推荐
版本冻结
方案画布输出
```

#### L1：轻项目底盘

例如：

```text
山地民宿
800㎡
12 间客房
要景观公区
预算不能失控
后勤不要打架
```

系统可以：

```text
粗策略推演
多版本方向
关键假设提示
初步风险判断
```

#### L2：可推演底盘

具备：

```text
项目类型
地理位置
基本功能
主要用户
预算倾向

```

系统可以：

```

#### L3：可冻结底盘

### 11.2 维度密度雷达

线性等级不够表达真实情况。

这比单纯的 `L1 / L2` 更能引导用户补全薄弱维度。

## 12. 输入与平面推演的接口映射

任何输入都不能只是存档，必须明确如何影响推演。

| 输入类型 | 对平面推演的影响 |
|---|---|
| 地理坐标 | 派生气候、文化、市场、交通、竞品和在地性权重 |
| 现场照片 | 校正图纸事实、识别景观、采光、材料、破损和真实限制 |
| 卫星图 / 航拍 | 判断道路、停车、邻里、景观方向和外部动线 |
| 手绘示意 | 提取用户意图、保留点、禁止点和空间想象 |
| 效果图 / 参考图 | 提取审美锚点和业主期待，但不作为事实 |
| 经营模式 | 决定公区比例、后勤动线、清扫路径和二次消费空间 |
| 客群画像 | 决定客房尺度、公共区类型、私密度和活动空间 |
| 时间约束 | 限制拆改强度、施工策略和开业优先级 |
| 利益相关方 | 决定版本差异策略、反诘方式和决策记录 |
| 合规约束 | 作为硬约束过滤版本或标记风险 |
| 用户语言信号 | 调整预算敏感度、反诘强度和版本解释方式 |
| 历史案例 / 竞品 | 建立参照、差异化方向和解释来源链 |
| 硅基分身 | 调整默认策略池和用户偏好，但不能覆盖项目事实 |
| 平面推演回填 | 更新项目定位、优先级、风险容忍和空间策略 |

- 淡旺季明显

2. 上传现场照片
3. 确认目标客房数与客群

- 入口较弱
- 景观面潜力较强

### 14.1 必填最低集

主要目标
至少一个硬约束
```

### 14.2 正式推演建议集

用于进入场地化正式推演。

```text
地理位置
现场照片
预算倾向
目标用户 / 客群
运营模式
时间约束
```

### 14.3 增强输入集

用于提高推演质量和高参解释质量。

```text
卫星图
竞品案例

手绘动线
设计师偏好
历史案例
材料偏好
法规资料
利益相关方结构
```

产品语言：

```text
你现在的信息已经可以进入轻推演；
如果补充地理位置和现场照片，系统能更准确判断景观、到达、材料和运营风险。
```

## 15. 多源输入的冲突处理

多源输入必然产生冲突。

系统不能静默选择其中一个，必须显化。

### 15.1 图纸与地理坐标冲突

例如：

```text
底盘填“浙江莫干山”，PDF 图签写“昆明市设计院”。
```

系统应提示：

```text
我发现项目地址和图纸来源存在不一致。
这是复用旧图纸，还是上传了错误文件？
```

### 15.2 地理在地性与用户风格冲突

例如：

```text
项目在山东，用户希望做云南风格。
```

系统应提示：

```text
这个方向可以成立，但它不是在地化策略，而是异地主题策略。
是否确认要走主题化表达，而不是地方文化表达？
```

### 15.3 视觉资料质量不足

系统应说：

```text
这张照片我能看出入口较窄，但看不清窗外景观。
如果要判断景观公区位置，建议补一张朝窗外的照片。
```

### 15.4 输入过多

用户上传大量参考图时，系统不能假装全看完。

系统应说：

```text
你上传了 25 张参考图。
我先抽取 5 张代表性图片识别风格关键词，其余资料会在版本深化时继续使用。
```

### 15.5 表单与对话冲突

例如：

```text
表单预算：200 万。
对话里说：最好压到 150 万。
```

系统应提示：

```text
我注意到你之前填写预算 200 万，但刚才说希望压到 150 万。
这是弹性区间，还是预算目标已经更新？
```

## 18. 渐进式输入机制

项目底盘的信息输入不能一次性要求用户全量完成。

但也不能允许系统在没有基本判断上下文时进入正式推演。

因此建议采用：

```text
3 分钟铁底基线
→ 30 秒空间类型加分轮
→ 轻底盘摘要与缺口卡
→ 进入轻推演
→ 推演中按需追问
→ 资料上传持续补全
→ 用户选择反向回填
→ 冻结前关键字段确认
```

这不是传统问卷，而是一个渐进式项目认知建构系统。

### 18.1 核心原则

项目底盘输入机制应遵循五条原则：

```text
1. 第一轮输入不能超过 3 分钟。
2. 基础输入必须足够让系统不瞎。
3. 任何非阻断字段都允许“还不知道”。
4. 每个输入都要给用户立即可见的回报。
5. 后续问题必须由空间类型、用户目标和推演行为动态触发。
```

参考意见中有一个分歧：

```text
一种建议是 60 秒基础表单；
另一种建议是 3 分钟基线问询。
```

综合判断：

```text
60 秒适合作为极简启动体验；
3 分钟是可靠生成第一轮轻推演的上限。
```

所以产品上可以表达为：

```text
先用 60 秒完成项目种子；
如果愿意再补充 2-3 个问题，3 分钟内形成轻项目底盘。
```

### 18.2 3 分钟铁底基线

铁底基线不是完整项目底盘，而是 `ProjectSeed`。

它的目标是：

```text
让系统能启动第一轮轻推演，且推演结果不离谱。
```

建议基线只包含 5 组问题。

#### 1. 空间类型

必填。

建议选项：

```text
住宅
别墅
民宿 / 文旅
酒店
办公
餐饮
商业零售
展厅
教育
医疗 / 康养
文化公共
娱乐休闲
其他
```

空间类型是动态路由入口。

选择后，系统不应立刻展开大量分支表单，而是改变后续问题的表达方式。

#### 2. 地理位置

必填，但允许低精度。

允许：

```text
城市级
区县级
片区 / 景区级
详细地址
地图点选 / 经纬度
```

系统应明确：

```text
城市级：可做区域气质、气候和市场粗判断。
片区级：可做客群、商业氛围和旅游属性判断。
地址级：可结合周边环境、交通、竞品与噪音。
坐标级：可进入场地、朝向、卫星图和景观资源分析。
```

地理位置不是为了卡住用户，而是为了防止平面推演脱离真实世界。

#### 3. 体量描述

必填。

基础字段：

```text
面积
层数
是否已有原始平面
```

同时根据空间类型动态加入核心数量。

```text
民宿 / 酒店：目标客房数
餐饮：目标座位数 / 客单价倾向
办公：目标工位数
住宅 / 别墅：居住人数 / 卧室数
商业零售：经营品类 / 展示面积
展厅：展陈面积 / 接待人数
教育：班级数 / 学员容量
医疗康养：床位数 / 服务类型
```

这些不是装饰字段，而是各类型的业务密度核心参数。

#### 4. 项目动机与功能诉求

必填，但应支持自由描述。

建议提问：

```text
你最希望这个项目解决什么？
请用自己的话描述，也可以只写一句。
```

可选项：

```text
提高使用效率
提升空间体验
强化品牌记忆点
控制改造成本
提升商业转化
增强私密性
改善动线
增加房间 / 工位 / 座位
提高客户接待能力
强化家庭关系 / 社交关系
提升传播性
改善运营后勤
准备方案汇报
```

自由描述必须保留。

因为用户自然语言里往往包含：

```text
真实动机
焦虑点
预算敏感度
审美倾向
犹豫状态
隐性约束
```

#### 5. 时间与决策结构

建议放入基线，但允许“不确定”。

时间问题：

```text
项目预计什么时候完成？
快：6 个月内
中：6-18 个月
慢：18 个月以上
不确定
```

决策结构：

```text
业主一人主导
夫妻 / 家庭共同决策
合伙人共同决策
团队 / 委员会决策
尚不稳定
```

这两个字段会影响策略池：

```text
快项目：减少激进拆改。
慢项目：允许更多重构型方案。
多人决策：需要生成对照光谱更明显的版本。
运营方强势：后勤和效率权重提高。
```

### 18.3 预算字段的处理

预算很重要，但早期不宜强制具体金额。

建议问：

```text
改造强度倾向
```

选项：

```text
尽量低改造
允许局部重点投入
可以中高强度改造
暂不确定
```

也可以补充：

```text
预算敏感度：高 / 中 / 低 / 不确定
```

这样比直接问“预算多少钱”更适合早期推演。

如果用户愿意填写金额，再记录为增强字段。

### 18.4 当前资料状态

资料状态建议作为基线或基线后的紧邻问题。

可勾选：

```text
已有 CAD / PDF 平面图
已有现场照片
已有建筑效果图
已有手绘示意
已有卫星图 / 航拍图
已有项目任务书
已有竞品案例
暂无资料，只想先聊思路
```

这个字段决定入口路由：

```text
图纸先行
现场先行
地理先行
对话先行
完整项目先行
```

如果用户没有资料，也不应被阻断。

系统可以进入项目种子模式：

```text
先形成项目摘要、缺口卡和下一步建议。
```

### 18.5 30 秒空间类型加分轮

完成铁底基线后，不应马上弹出深问卷。

应给用户一个可跳过的加分轮：

```text
基本信息已经足够进入轻推演。
再用 30 秒回答两个问题，推演会更准。
也可以跳过，直接看第一轮方向。
```

加分轮根据空间类型动态变化。

#### 民宿 / 文旅

```text
主要客群是谁？
是否做餐饮 / 公区运营？
```

#### 餐饮

```text
正餐、咖啡、酒吧还是快餐？
翻台效率和体验氛围哪个更重要？
```

#### 办公

```text
固定办公还是灵活办公？
是否需要客户接待展示？
```

#### 住宅 / 别墅

```text
家庭结构是什么？
老人、儿童、家政或高频接待是否重要？
```

#### 商业零售

```text
主要经营品类是什么？
更重成交效率、品牌展示，还是体验停留？
```

加分轮必须是邀请，不是阻断。

### 18.6 动态路由规则

选择空间类型后，系统不能进入分支表单地狱。

正确机制是把后续问题分成三类：

```text
立刻必须：并入铁底基线。
强烈建议：进入 30 秒加分轮。
情境需要：推演过程中按需追问。
```

以民宿为例：

```text
立刻必须：面积 + 客房数。
加分轮：客群 + 餐饮配置。
推演中追问：季节性、定价、运营团队、后勤分流、淡旺季、传播平台。
```

以办公为例：

```text
立刻必须：面积 + 工位数。
加分轮：办公模式 + 接待展示需求。
推演中追问：部门结构、会议频率、未来扩张、高管区、安静专注需求。
```

每个字段都应绑定：

```text
触发情境
默认假设
置信度
对推演的影响
是否需要用户确认
追问优先级
```

### 18.7 每轮追问最多 1-3 个问题

动态追问的优先级：

```text
先问阻断项
再问高影响项
最后问增强项
```

阻断项：

```text
不知道空间类型
没有面积或边界
没有目标
没有任何空间事实
```

高影响项：

```text
预算态度
目标客群
目标房间数 / 工位数 / 座位数
地理位置
是否保留结构
是否有后勤入口
```

增强项：

```text
竞品案例
材料倾向
审美参考
运营团队规模
未来扩展计划
```

系统每次只问当前最影响判断的 1-3 个问题。

不应把缺口一次性全部抛给用户。

### 18.8 表单、对话、上传并行

项目底盘输入不应只有表单。

理想入口应支持：

```text
填基础表单
直接说一段话
上传图纸
上传现场照片
点地图
上传参考图
导入项目任务书
```

系统应自动抽取信息并回填底盘。

例如用户输入：

```text
我在重庆仙女山有一个 800㎡ 山地民宿，想做 12 间客房，预算别失控。
```

系统自动填：

```text
空间类型：民宿 / 文旅
地理位置：重庆仙女山
面积：800㎡
目标客房数：12
预算态度：成本敏感 / 中等控制
项目诉求：山地民宿改造
```

然后只追问：

```text
是否已有原始平面？
主要客群更偏亲子、情侣、团建还是高端度假？
是否需要餐饮或独立公区运营？
```

这才是 AI 产品，而不是传统表单。

### 18.9 即时回报机制

用户每输入一个高价值字段，系统必须给出可见反馈。

示例：

```text
填“民宿”：加载民宿策略池。
填“重庆仙女山”：提示山地、湿度、避暑、自驾、淡旺季。
填“12 间客房”：进入面积快检。
填“低改造”：低改造版本权重提高。
上传现场照片：提取入口、景观、破损、材料、采光线索。
```

没有即时回报的输入，会被用户感知为表单负担。

### 18.10 轻底盘摘要与缺口卡

基线完成后，系统应显示：

```text
当前底盘成熟度：L1 轻项目底盘
可以：初步判断 / 轻推演 / 多版本方向
不建议：正式冻结 / 方案画布输出
```

同时显示：

```text
已知：
- 民宿 / 文旅
- 重庆仙女山
- 约 800㎡
- 目标 12 间客房
- 预算不希望失控

缺失：
- 客群未知
- 运营模式未知
- 现场照片缺失
- 原始平面未上传
- 后勤入口未知
```

并展示维度密度：

```text
地理：中
图纸：缺
现场：缺
经营：低
客群：缺
预算：中
时间：低
决策方：低
```

### 18.11 允许“还不知道”，但必须登记假设

任何非阻断字段都允许：

```text
还不知道
稍后再说
先按常见情况推演
```

系统回应：

```text
好，我先按一个常见情况假设，并在版本卡片里标出来。
你看到推演结果后可以随时改。
```

注意：

```text
不能静默使用默认值。
不能把系统假设写成用户确认。
不能把低质量回答当成高置信字段。
```

例如用户回答：

```text
客群：看情况。
```

系统应记录为：

```text
字段：target_guest_profile
值：uncertain
置信度：低
后续触发：看到版本后再次追问
```

### 18.12 推演中的持续沉积

进入平面推演后，底盘还要继续生长。

来源包括：

```text
用户选择哪个版本
用户否定哪个版本
用户在哪个版本停留最久
用户反复强调什么风险
用户要求融合哪些优点
用户上传了哪些新资料
用户修正了哪些系统假设
```

这些都应进入：

```text
BackfillEvent
ProjectBasePatch
LayoutVersionGraph
```

冻结前，系统必须提示：

```text
本次推演形成了这些项目底盘判断，是否写入正式底盘？
```

## 19. 与当前实施路线的关系

当前平面推演已完成 Phase 0 的基础闭环：

```text
领域对象扩展
轻量平面生成服务
FastAPI 路由
Next.js 代理
PlanSandboxPanel 同步
测试覆盖
```

下一步不应只推进自然语言操作。

建议增加：

```text
P0.5：ProjectContextCompiler / 多源输入编译层
```

调整后的路线：

```text
P0：前端多版本体验闭环
P0.5：多源输入编译层，支持地理坐标、现场照片、轻底盘
P1：几何编译输出 FloorPlanFacts / Carrier Facts
P2：用户指令 → LayoutOperation → Diff
P3：知识底盘与硅基分身注入
P4：求解器升级
```

如果没有 P0.5，平面推演会太依赖前端临时 SPG。

如果有 P0.5，平面推演才会从“图纸生成器”升级为“项目语境驱动的空间高参”。

## 20. 最终规则

系统原则应固定为：

```text
没有完整项目底盘，可以开始；
没有任何判断上下文，不能正式推演。

用户可以从图纸、位置、照片、对话、商业目标任意入口进入；
系统负责把输入编译成轻底盘；
轻底盘允许初步推演；
推演过程反向升级项目底盘；
冻结版本必须回写为正式项目判断。
```

渐进式输入原则：

```text
基础表单负责让系统不瞎；
动态追问负责让系统更懂；
资料上传负责让判断接近真实；
平面推演负责让底盘被空间验证；
版本沉淀负责让项目底盘真正长成。
```

最终表达：

```text
地理坐标告诉系统项目处在什么世界；
现场资料告诉系统建筑真实是什么状态；
图纸告诉系统空间允许怎么动；
用户目标告诉系统为什么要动；
经营模式告诉系统动了以后如何成立；
平面推演告诉系统哪种动法更成立；
用户选择则把这些判断沉淀为项目底盘。
```

项目底盘不是平面推演的前置门槛。

它是平面推演不断生成、验证和修正的认知母体。
