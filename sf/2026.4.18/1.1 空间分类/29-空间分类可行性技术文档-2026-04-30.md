# 空间分类可行性技术文档

> 日期：2026-04-30  
> 主题：空间分类作为“方案高参”的基础设施落地方案  
> 依据：本目录 5 份空间分类专题文档，并对照当前 `intelligent_project_analyzer` 代码链路  
> 目标：把空间分类从概念清单推进为可治理、可路由、可解释、可验收的工程能力

---

## 0. 执行结论

空间分类具备明确落地价值，且可以在现有系统上渐进实现。它不应被做成一个孤立的“空间类型表”，而应成为方案高参的前置路由基础设施，负责决定系统后续使用哪套问题结构、知识框架、追问路径、冻结顺序和交付语言。

综合现有文档与代码现实，建议采用“兼容现状、逐步收敛”的路线：

1. 短期不重写现有 `project_type` 体系，先在其外侧增加统一分类结果对象。
2. 保留 `project_type` 作为当前主链兼容字段，新增 `space_classification` / `classification_result` 作为更完整的内部协议。
3. 把 `parent_type`、`specialty_tag`、`secondary_type`、`is_ambiguous`、`runtime_modifiers`、`spatial_zones` 统一装入一个可解释结构。
4. 将“一级桶、正式项目类型、专项标签、运行时变量、空间区域”严格分层，避免风格词、材料词、体验词污染类型树。
5. 先覆盖高频空间类型和高风险边界案例，再扩展完整知识包，不追求一次性建成全世界空间分类百科。

可行性判断：

| 维度 | 判断 |
|---|---|
| 业务必要性 | 高。空间分类决定方案高参是否先问对问题。 |
| 当前基础 | 中高。已有类型注册表、检测器、本体、问卷、交付消费链。 |
| 工程复杂度 | 中。主要难点不是新增类型，而是字段治理和下游兼容。 |
| 数据复杂度 | 中高。类型、标签、变量、空间部位容易混用。 |
| 推进建议 | 分 3 期落地，先协议化和可解释化，再做本体补齐和混合权重。 |
| 不建议做法 | 直接替换现有 `project_type`；一次性扩成庞大分类树；让 LLM 自由生成类型名。 |

## 1. 背景与问题定义

### 1.1 为什么空间分类是方案高参的基础设施

方案高参不是普通问答系统，它需要在用户一句模糊需求之后，迅速判断：

- 这个项目属于哪种成立逻辑；
- 它的成败由什么定义；
- 先追问什么，后追问什么；
- 哪些矛盾必须先冻结；
- 哪些专家视角需要优先激活；
- 最终交付物应该用什么语言组织。

这些能力的入口不是风格分析，也不是材料推荐，而是空间分类。

如果空间分类不稳，后续会出现连锁偏差：

- 把民宿当住宅，追问家庭成员和收纳，却漏掉客群旅程、运营弹性、公私分区；
- 把疗愈酒店当医疗康养，过度流程化，压缩度假体验；
- 把医疗康养当度假空间，低估安全、照护、伦理和技术流程；
- 把品牌体验店当普通零售，过度关注坪效，漏掉品牌认知沉浸；
- 把乡建项目当单体民宿，低估村民关系、公共性和产业联动。

因此，空间分类的核心价值不是“叫什么”，而是“系统接下来该怎么看”。

### 1.2 本次技术文档的定位

本文件不是再新增一份分类名录，而是将既有材料转译为工程落地方案。

它重点回答：

1. 当前文档共识是什么；
2. 当前代码现实是什么；
3. 哪些方案可落地，哪些方案现在不宜做；
4. 应该采用怎样的数据协议；
5. 现有链路如何接入；
6. 分几期推进，验收标准是什么；
7. 如何控制类型系统的长期复杂度。

## 2. 现有材料综合评估

### 2.1 五份文档的核心共识

本目录 5 份材料已经形成稳定共识：

| 文档 | 核心贡献 |
|---|---|
| `05-空间分类与空间类型的分层原则` | 明确分类、类型、变量的分层，不把风格词和材料词塞入分类树。 |
| `06-空间一级分类与二级类型初始清单` | 提供 11 个一级桶和首批二级类型清单。 |
| `27-空间分类与空间类型的成立标准` | 把“类型是否成立”定义为是否改变分析世界观、张力、追问、冻结对象。 |
| `28-空间类型边界案例与误判手册` | 给出高风险边界案例和误判后果，适合转化为裁决规则。 |
| `SPACE_CLASSIFICATION_SYSTEM_INVENTORY` | 梳理现有系统中的类型检测、本体注入、问卷、交付消费链。 |

可沉淀为一句总原则：

> 空间分类不是命名系统，而是分析路由系统；分类是否成立，取决于它是否改变系统后续的判断方式。

### 2.2 文档中的高价值原则

以下原则应进入正式工程规范：

1. 一级分类按项目成立逻辑分，不按风格、材料、体验词分。
2. 二级类型按典型使用场景、经营方式、体验结构细分。
3. 同一类型内部差异优先进入变量层，而不是不断新增类型名。
4. 混合项目采用主类型、副类型和权重，不发明超长复合类型。
5. 边界案例先看成功标准，再看表面形态。
6. 新类型只有在改变分析世界观、核心张力、本体激活、追问路径、冻结对象时，才值得升级。
7. 空间部位如大堂、客房、餐区、接待区，不应混同为项目类型。

### 2.3 文档之间需要统一的地方

当前材料存在两套层级表达，需要工程合并：

| 表达 A | 表达 B | 建议工程口径 |
|---|---|---|
| 一级分类 | 父类归桶 `parent_type` | 统一为 `primary_bucket` 或 `parent_bucket` |
| 二级类型 | 正式项目类型 `project_type` | 统一为 `project_type`，保持现有代码兼容 |
| 类型变量 | 运行时修饰项 | 统一为 `runtime_modifiers` |
| 混合项目权重 | 次候选类型/副类型 | 统一为 `secondary_types` + `hybrid_weights` |
| 空间部位 | `space_type` / `spatial_zone` | 统一从项目类型中剥离，归入 `spatial_zones` |

最关键的统一点：

> `project_type` 继续作为正式项目类型的工程主字段；`parent_type` 是上位业态桶；`specialty_tag` 和 `runtime_modifiers` 只改变细节权重，不直接替代主类型。

### 3.4 当前检测器具备可解释基础，但解释粒度不足

`detect_with_details()` 当前已经输出：

- `project_type`
- `project_type_name`
- `confidence`
- `reason`
- `parent_type`
- `specialty_tag`
- `secondary_type`
- `secondary_type_name`
- `is_ambiguous`
- `all_matches`

这对空间分类落地非常有利。

但当前不足是：

1. `secondary_type` 只是从 reason 字符串中解析，结构不够稳定。
2. `all_matches` 固定为空，没有暴露完整候选排名。
3. `is_ambiguous` 只基于 top-2 接近，不包含边界案例规则。
4. 没有输出成功标准、主张力、优先冻结对象等裁决依据。
5. 没有输出运行时变量，如山地、存量改造、亲子、高客单价、短期活动。
6. 没有输出混合权重，只给了单个主类型和弱次选。

因此，短期可在检测器外层增加一个分类聚合服务，不直接破坏现有检测器。

### 3.5 当前 `project_classification` 状态字段存在语义漂移

`core/state.py` 中仍保留：

- `project_type`
- `detected_design_modes`
- `project_classification`
- `extracted_spatial_zones`

其中 `project_classification` 的注释称它是统一项目分类结果，建议下游优先读取。但 `workflow/main_workflow.py` 中明确注释：

```text
v9.1: project_classification 已移除（死代码清理）
下游组件直接使用 detected_design_modes 和 project_type
```

同时 `interaction/nodes/output_intent_detection.py` 又为了兼容空间规则，从 `project_type` 构造了临时 `project_classification`：

```text
project_classification = {"project_type": _project_type_str}
```

这说明当前系统正处于过渡状态：

- 概念上需要统一分类出口；
- 主链实现上曾移除该出口；
- 部分下游又需要一个兼容结构。

落地建议：

> 不直接复活旧 `project_classification` 语义，而是新增更明确的 `space_classification` 或 `classification_result`，并让旧字段只做兼容镜像。

### 3.6 本体框架覆盖不完整且命名不一致

`ontology.yaml` 已有框架：

- `meta_framework`
- `personal_residential`
- `hybrid_residential_commercial`
- `commercial_enterprise`
- `public_cultural`
- `healthcare_wellness`
- `commercial_office`
- `commercial_hospitality`
- `sports_entertainment_arts`
- `industrial_conversion`
- `educational_facility`
- `transportation_civic`
- `rural_regeneration_urban_renewal`
- `religious_spiritual`
- `landscape_outdoor`
- `commercial_retail`

但注册表中的许多类型没有一对一 ontology：

- `brand_experience`
- `commercial_dining`
- `popup_temporary`
- `residential_renovation`
- `community_public`
- `urban_renewal_market`
- `urban_renewal_heritage`
- `rural_construction`
- `wedding_banquet`
- `beauty_personal_care`
- `automotive_showroom`
- 等。

这意味着：空间分类即使检测准确，也可能在本体注入阶段退化为邻近类型或通用框架。

短期策略：

1. 建立 `project_type -> ontology_framework` 映射。
2. 对没有专属 ontology 的类型，映射到父类或相邻框架。
3. 只有高频且路由差异大的类型，才新增独立 ontology。

### 3.7 `space_type` 当前混用严重

当前系统中 `space_type` 至少承担了三种角色：

1. 作为物理空间类型，例如民宿、住宅、办公。
2. 作为功能空间或空间部位，例如客房、大堂、餐区。
3. 作为交付命名词，例如 `{space_type}整体设计方案`。

这会导致：

- 项目类型和空间部位混淆；
- 下游命名不稳定；
- 问卷路由不知道该按项目业态还是局部空间追问；
- 未来多空间区域分析难以扩展。

建议将概念拆开：

| 概念 | 字段 | 示例 |
|---|---|---|
| 项目正式类型 | `project_type` | `commercial_hospitality` |
| 父类桶 | `parent_type` / `primary_bucket` | `hospitality` |
| 专项标签 | `specialty_tag` | `boutique_hotel` |
| 运行时变量 | `runtime_modifiers` | `mountain`, `high_budget`, `family_oriented` |
| 空间区域 | `spatial_zones` | `lobby`, `guest_room`, `tea_room` |
| 用户可读命名 | `display_space_label` | `山地民宿` |

## 4. 目标架构

### 4.1 总体目标

空间分类目标架构应服务 6 个下游能力：

1. 需求理解：识别项目成败逻辑和边界案例。
2. 问卷路由：决定补问维度、追问顺序和歧义澄清。
3. 本体注入：选择类型框架和专家增强层。
4. 一主两辅：影响主命题、辅助驱动力和边界收束。
5. 交付组织：影响任务书、成果命名、输出深度和角色分工。
6. 长期治理：支持类型扩展、案例库、误判反馈和资产复用。

### 4.2 推荐分层模型

建议采用 5 层模型。

#### L1：父类桶 `primary_bucket`

回答：这个项目的成立逻辑属于哪一大类？

典型值：

- `residential`
- `hospitality`
- `office`
- `retail`
- `education`
- `healthcare`
- `public`
- `industrial`
- `urban_renewal`
- `outdoor`
- `special`

作用：

- 粗路由；
- 大类问卷；
- 初始 ontology fallback；
- 统计与治理。

#### L2：正式项目类型 `project_type`

回答：系统应采用哪套稳定分析入口？

典型值：

- `commercial_hospitality`
- `personal_residential`
- `healthcare_wellness`
- `commercial_retail`
- `brand_experience`
- `commercial_office`
- `rural_construction`
- `public_cultural`

作用：

- 决定主分析世界观；
- 决定本体框架；
- 决定核心张力库；
- 决定追问路径；
- 决定优先冻结对象。

#### L3：专项标签 `specialty_tag`

回答：在正式类型内部，它更具体像哪种稳定场景？

典型值：

- `b_and_b`
- `boutique_hotel`
- `cafe`
- `hotpot`
- `co_working`
- `dental`
- `tcm`
- `kindergarten`
- `popup`

作用：

- 细化追问；
- 优化案例匹配；
- 影响局部模板；
- 改进交付语言。

不应让专项标签替代 `project_type`。

#### L4：运行时变量 `runtime_modifiers`

回答：这次项目有什么条件差异？

典型变量轴：

- 场地：山地、滨海、乡村、街区、地下、顶层、临水；
- 更新：新建、存量改造、历史建筑、旧厂房、局部翻新；
- 客群：亲子、银发、白领、游客、居民、村民、访客；
- 运营：高周转、低频高客单、活动导向、长期运营、快闪短期；
- 体验：恢复性、社交性、仪式性、展示性、学习性；
- 约束：低预算、高合规、强施工边界、高维护难度。

作用：

- 改变权重；
- 触发补问；
- 调整风险提示；
- 调整冻结顺序；
- 不新增正式类型。

#### L5：空间区域 `spatial_zones`

回答：项目内部涉及哪些空间部位或区域？

典型值：

- `overall`
- `lobby`
- `guest_room`
- `tea_room`
- `dining_area`
- `clinic_room`
- `waiting_area`
- `office_area`
- `exhibition_area`

作用：

- 支持局部约束；
- 支持图片约束识别；
- 支持分区交付；
- 支持多区域任务包。

它是空间对象，不是项目类型。

### 4.3 推荐分类结果协议

建议新增结构：

```yaml
space_classification:
  schema_version: "1.0"
  primary_bucket: hospitality
  project_type: commercial_hospitality
  project_type_name: 酒店民宿/度假
  confidence: 0.86
  confidence_level: high

  specialty_tag: b_and_b
  secondary_candidates:
    - project_type: rural_construction
      project_type_name: 乡建/新农村建设
      score: 0.72
      reason: 同时命中乡村、村落、在地运营等信号

  is_ambiguous: true
  ambiguity_type: boundary_case
  boundary_case:
    pair:
      - commercial_hospitality
      - rural_construction
    decision_question: 项目成败主要取决于住宿经营，还是乡村公共性与产业组织？
    risk_if_wrong:
      as_commercial_hospitality: 可能低估村民关系、公共性和产业联动
      as_rural_construction: 可能稀释住宿产品、客群旅程和运营回报

  hybrid:
    is_hybrid: true
    secondary_types:
      - tea_house
      - culture_saloon
    weights:
      commercial_hospitality: 0.65
      tea_house: 0.20
      culture_saloon: 0.15

  runtime_modifiers:
    geo_scene:
      - mountain
      - rural
    operation_mode:
      - independent_operation
      - small_scale_event
    audience:
      - urban_weekend_visitor
      - family_group
    experience_focus:
      - restoration
      - low_pressure_social

  spatial_zones:
    - id: overall
      label: 整体
      source: preset
    - id: guest_room
      label: 客房
      source: user_text
    - id: tea_room
      label: 茶空间
      source: user_text

  routing:
    ontology_framework: commercial_hospitality
    questionnaire_profile: hospitality
    completeness_space_type: commercial
    deliverable_label: 山地民宿

  evidence:
    matched_keywords:
      - 民宿
      - 山地
      - 茶空间
    negative_signals: []
    source: project_type_detector_v8.1
```

这个协议的关键是把“主判断”和“辅助信息”分开，不再让一个 `space_type` 承担所有语义。

## 5. 核心流程设计

### 5.1 数据流

建议目标数据流：

```text
用户输入 / 已确认任务 / 上传资料
  -> type_alias_normalizer
  -> ProjectTypeDetector.detect_with_details()
  -> SpaceClassificationService.enrich()
  -> space_classification
  -> 写入 state
  -> 问卷路由 / 本体注入 / 任务完整性 / 输出意图 / 交付命名 / 案例检索
```

其中 `ProjectTypeDetector` 保持轻量关键词检测，`SpaceClassificationService` 负责聚合和解释：

- canonical bucket 映射；
- secondary candidates 排序；
- 边界案例裁决；
- runtime modifiers 提取；
- hybrid 权重估算；
- ontology 和问卷路由映射；
- 输出可解释证据。

### 5.2 分类服务职责边界

建议新增服务：

```text
intelligent_project_analyzer/services/space_classification_service.py
```

职责：

1. 调用现有 `ProjectTypeDetector.detect_with_details()`。
2. 从检测结果中构造统一分类对象。
3. 将 `parent_type` 映射为 canonical `primary_bucket`。
4. 根据边界规则判断是否需要追问。
5. 提取运行时变量。
6. 生成下游 routing hints。
7. 对旧字段提供兼容输出。

不建议该服务做的事：

- 不直接生成设计结论；
- 不调用大模型写长分析；
- 不自由创造新类型；
- 不替代 ontology；
- 不替代问卷逻辑。

### 5.3 边界案例裁决流程

边界案例应作为规则层，而不是完全交给 LLM。

建议流程：

```text
1. 获取 top-2 候选类型
2. 判断是否命中边界案例对
3. 提取四类裁决信号
   - 主成功标准
   - 主张力结构
   - 优先冻结对象
   - 主要使用者 / 运营关系
4. 若信号足够，输出裁决理由
5. 若信号不足，生成澄清问题
6. 将误判风险写入 classification_result
```

首批边界案例对：

| 边界对 | 高风险点 |
|---|---|
| `commercial_hospitality` vs `personal_residential` | 居家感误导为住宅。 |
| `brand_experience` vs `commercial_retail` | 品牌认知和销售转化主次不清。 |
| `commercial_hospitality` vs `healthcare_wellness` | 疗愈度假和照护康复混淆。 |
| `commercial_hospitality` vs `rural_construction` | 乡村位置误导为乡建，或乡建被缩成民宿。 |
| `community_public` vs `public_cultural` | 社区日常和文化展陈混淆。 |
| `commercial_office` vs `brand_experience` | 总部办公和对外展厅混淆。 |
| `personal_residential` vs `residential_renovation` | 新建住宅和存量改造混淆。 |
| `popup_temporary` vs `brand_experience` / `commercial_retail` | 临时传播和长期运营混淆。 |

### 5.4 运行时变量提取

运行时变量不应一开始做成复杂 NER 系统。首版可采用关键词词典 + 规则归类：

```yaml
runtime_modifier_rules:
  geo_scene:
    mountain: ["山地", "山谷", "山顶", "半山"]
    waterfront: ["滨水", "河边", "湖边", "海边", "临水"]
    rural: ["乡村", "村庄", "田园", "古村"]

  lifecycle:
    renovation: ["改造", "翻新", "旧改", "存量"]
    temporary: ["快闪", "临时", "短期", "撤场"]
    long_term: ["长期运营", "常年", "持续运营"]

  audience:
    family: ["亲子", "家庭", "儿童"]
    elderly: ["银发", "老人", "适老", "养老"]
    tourist: ["游客", "旅客", "度假客"]

  operation_mode:
    high_turnover: ["翻台", "高周转", "坪效"]
    event_based: ["活动", "沙龙", "发布会", "展演"]
    independent: ["独立经营", "主理人", "小型精品"]
```

变量提取只做“影响权重”的事实记录，不改变主类型。

### 5.5 混合项目处理

混合项目不建议首版做复杂概率模型。可采用规则权重：

1. 主类型来自 `ProjectTypeDetector` 第一候选。
2. 若 `secondary_type` 存在且 `is_ambiguous = true`，进入次候选。
3. 若文本命中明确副业态，如茶空间、展厅、活动、社区服务，进入 `secondary_types`。
4. 权重首版采用启发式：
   - 主类型默认 0.60 到 0.75；
   - 强副类型 0.15 到 0.30；
   - 弱副类型 0.05 到 0.15；
   - 总和归一化。

示例：

```yaml
hybrid:
  is_hybrid: true
  primary_type: commercial_hospitality
  secondary_types:
    - tea_house
    - culture_saloon
  weights:
    commercial_hospitality: 0.65
    tea_house: 0.20
    culture_saloon: 0.15
```

## 6. 与现有模块的接入方案

### 6.1 `project_type_detector.py`

短期改造建议：

1. 保持 `PROJECT_TYPE_REGISTRY` 作为项目类型真相源。

4. 避免从 `reason` 字符串反解析 `secondary_type`。

```python
{

```

### 6.2 `core/state.py`

建议状态层新增：

```python
space_classification: Optional[Dict[str, Any]]
```

兼容策略：

- `project_type` 继续顶层保留，供旧链路读取；

- 新链路优先读取 `space_classification`；
- 若 `space_classification` 不存在，则从 `project_type` 构造轻量兼容对象。

### 6.3 `workflow/main_workflow.py`

在 requirements analyst 之后，写入：

```python
space_classification = SpaceClassificationService().classify(
    user_input=state.get("user_input", ""),

```

状态更新：

```python
update_dict = {
    "structured_requirements": result.structured_data,
```

如果暂时不改主 workflow，也可以先在 `output_intent_detection.py` 中替代当前临时 `project_classification` 构造逻辑。

### 6.4 `output_intent_detection.py`

当前节点依赖 project type 判断空间属性信号，并提取 `extracted_spatial_zones`。

改造建议：

1. 优先读取 `state["space_classification"]`。
2. 没有时兼容 `project_type`。
3. 将 `_extract_spatial_zones()` 的结果回写到 `space_classification.spatial_zones`。
4. 边界案例不应直接 interrupt 大段解释，而应生成简短澄清问题。

### 6.5 `task_completeness_analyzer.py`

当前已有 `project_type -> parent -> space_type_dimension_map` 映射。问题是映射粒度偏粗，例如 `hospitality` 和 `retail` 都进入 `commercial`。

建议：

1. 首期保留现有映射，避免影响问卷完整性。
2. 增加 `questionnaire_profile` 字段，由 `space_classification.routing.questionnaire_profile` 提供。
3. 对高风险类型单独细化：
   - `healthcare_wellness`
   - `rural_construction`
   - `brand_experience`
   - `commercial_hospitality`
   - `residential_renovation`
   - `popup_temporary`

### 6.6 `ontology.yaml`

短期不要求每个 `project_type` 都有独立 ontology。

建议新增映射表：

```yaml
project_type_to_ontology:
  commercial_hospitality: commercial_hospitality
  commercial_dining: commercial_retail
  brand_experience: commercial_retail
  popup_temporary: commercial_retail

```

之后再根据真实使用频率决定是否为 `brand_experience`、`residential_renovation`、`rural_construction` 新增专属框架。

### 6.7 `deliverable_id_generator_node.py`

当前交付命名读取 `structured_requirements.physical_context.space_type`。

建议改为：

1. 优先读取 `space_classification.routing.deliverable_label`。
2. 其次读取 `physical_context.space_type`。
3. 再次使用 `project_type_name`。
4. 严禁把 `spatial_zones[0].label` 当作项目整体命名，除非用户明确要求局部空间。

示例：

```python
display_label = (

    or physical_context.get("space_type", "")
    or space_classification.get("project_type_name", "")

```

### 6.8 问卷生成器

当前 `generators.py` 对部分旧类型做了硬编码映射：

```python
{
  "personal_residential": "住宅空间",
  "hybrid_residential_commercial": "混合型空间",

}
```

这和现有 30 多种 `project_type` 已不匹配。

建议：

1. 问卷生成器读取 `space_classification.routing.questionnaire_profile`。

3. 将办公、住宅、商业、医疗、公共、乡建、酒店、品牌体验分别做最小问题模板。

## 7. 分期落地路线

### 7.1 P0：协议化和可解释分类

目标：不改动大主链逻辑，先让分类结果变成一个稳定对象。

范围：

- 新增 `space_classification_service.py`。
- 新增 `SpaceClassificationResult` 数据结构，可先用 dict。
- 包装现有 `ProjectTypeDetector.detect_with_details()`。
- 输出 `primary_bucket`、`project_type`、`specialty_tag`、`secondary_candidates`、`is_ambiguous`。
- 增加 canonical bucket 映射。
- 增加 `routing.ontology_framework` 和 `routing.questionnaire_profile`。
- 增加首批边界案例对的规则表，但只输出提示，不强制追问。

不做：

- 不新增大量类型；
- 不改 ontology 主体；
- 不重写问卷；
- 不引入复杂机器学习。

验收：

- 20 条典型输入可稳定输出分类对象；
- 旧 `project_type` 仍可正常写入；
- 下游无破坏性回归；
- `commercial_hospitality` vs `personal_residential`、`brand_experience` vs `commercial_retail` 等边界能给出可解释提示。

复杂度：中低。

建议周期：2 到 4 个工作日。

### 7.2 P1：下游消费改造

目标：让分类结果真正驱动问卷、本体和交付命名。

范围：

- 在 state 中新增 `space_classification`。
- workflow 写入该字段。
- `output_intent_detection.py` 优先读取新字段。
- `task_completeness_analyzer.py` 支持 `questionnaire_profile`。
- `deliverable_id_generator_node.py` 支持 `deliverable_label`。
- 建立 `project_type_to_ontology` 映射。
- 补充 `all_matches`，避免 reason 字符串反解析。

验收：

- 同一项目在需求分析、问卷、交付命名中使用一致的项目类型；
- 无 `space_type` 混用导致的明显命名错误；
- 无 ontology 找不到时的异常；
- 边界模糊项目能触发澄清问题或风险提示。

复杂度：中。

建议周期：5 到 8 个工作日。

### 7.3 P2：类型治理和知识包扩展

目标：把空间分类变成长期知识底盘。

范围：

- 建立类型新增评审模板。
- 建立误判样本库。
- 为高频类型补专属 ontology：
  - `brand_experience`
  - `rural_construction`
  - `residential_renovation`
  - `commercial_dining`
  - `popup_temporary`
- 建立 runtime modifiers 词典。
- 建立 hybrid weights 规则。
- 将分类反馈写入学习采集器。

验收：

- 新类型不会只靠关键词加入，必须提供分析差异证据；
- 每个正式类型至少有边界说明、典型张力、追问重点、冻结对象；
- 误判案例可以回流到规则或样本库；
- 类型清单增长受到治理约束。

复杂度：中高。

建议周期：2 到 4 周，适合分批推进。

### 7.4 P3：智能裁决与案例学习

目标：在规则稳定后，引入更智能的二次裁决。

范围：

- 对高歧义样本调用 LLM 裁决，但输出必须落入固定 schema。
- 建立人工确认反馈闭环。
- 根据真实项目数据调整边界规则和关键词权重。
- 将 few-shot 案例与分类结果绑定。

不建议提前做 P3。原因是当前字段和协议尚未完全收敛，过早智能化会放大混乱。

## 8. 复杂度与风险评估

### 8.1 主要复杂度来源

| 来源 | 说明 | 控制策略 |
|---|---|---|
| 类型层级混用 | 项目类型、空间部位、风格词混在一起。 | 强制五层模型，拆分字段。 |
| 旧字段兼容 | `project_type`、`project_classification`、`space_type` 多处读取。 | 新增 `space_classification`，旧字段镜像兼容。 |
| 本体覆盖不足 | 注册表类型多，ontology 框架少。 | 增加映射表，优先 fallback，不急着补全全部。 |
| 边界案例模糊 | 同一项目可被多种类型解释。 | 输出主类型、次候选、裁决依据和误判风险。 |
| 分类树膨胀 | 每次遇到新词都想新增类型。 | 新类型评审模板和成立标准。 |
| LLM 幻觉类型 | 模型可能生成不存在的类型名。 | 所有类型必须枚举校验，未知类型进入候选池。 |

### 8.2 高风险点

#### 风险 1：把空间分类做成“越细越专业”的类型树

后果：

- 注册表膨胀；
- 问卷分支失控；
- ontology 维护困难；
- 相邻类型误判增多。

控制：

- 新类型必须证明会改变分析世界观；
- 优先用 `runtime_modifiers` 表达差异；
- 类型新增必须带边界案例和误判后果。

#### 风险 2：直接替换现有 `project_type`

后果：

- 本体注入、问卷、任务完整性、交付命名都可能断裂；
- 旧数据兼容复杂；
- 测试面过大。

控制：

- `project_type` 短期保持；
- 新字段旁路接入；
- 稳定后逐步迁移下游读取。

#### 风险 3：过度依赖 LLM 做分类

后果：

- 输出不稳定；
- 难以调试；
- 难以复现；
- 类型治理失控。

控制：

- 规则和注册表做第一判断；
- LLM 只做高歧义裁决和解释补充；
- LLM 输出必须通过 schema 和枚举校验。

#### 风险 4：空间部位和项目类型继续混用

后果：

- 交付命名错误；
- 局部空间覆盖整体；
- 多区域约束无法表达。

控制：

- `project_type` 表达项目；
- `spatial_zones` 表达空间部位；
- `display_space_label` 表达可读命名。

## 10. 类型治理规范

### 10.1 新类型成立标准

候选类型要升级为正式 `project_type`，至少满足以下大部分条件：

1. 改变分析世界观；
2. 改变核心张力；
3. 值得单独写 ontology 或 routing profile；
4. 改变需求追问路径；
5. 改变优先冻结对象；
6. 改变专家扩展组合；
7. 有稳定复现性；
8. 有清晰边界和误判风险；
9. 不能被现有类型加变量表达。

### 10.2 不应进入正式类型的内容

以下内容不进入 `project_type`：

- 风格词：侘寂、新中式、极简、复古；
- 材料词：木质、石材、金属、微水泥；
- 情绪词：诗意、高级感、松弛感、戏剧感；
- 单次概念：山谷疗愈乌托邦、精神洞穴；

## 12. 首批落地样例

### 12.1 山地民宿加茶空间

输入：

```text
做一个山地民宿，包含客房、茶空间、小型文化活动，希望有低压社交和疗愈感。
```

期望输出：

```yaml
space_classification:
  primary_bucket: hospitality
  project_type: commercial_hospitality
  specialty_tag: b_and_b
  runtime_modifiers:
    geo_scene: [mountain]
    experience_focus: [restoration, low_pressure_social]
    operation_mode: [small_scale_event]
  secondary_types:
    - tea_house
    - culture_saloon
  spatial_zones:
    - guest_room
    - tea_room
    - event_area
  routing:
    ontology_framework: commercial_hospitality
    questionnaire_profile: hospitality
```

关键判断：

- 主类型不是“茶民宿文化空间”；
- 茶空间是副类型或空间区域；
- 疗愈感是体验变量；
- 山地是场地变量。

### 12.2 品牌体验店

输入：

```text
做一个新消费品牌体验店，主要不是卖货，而是让用户理解品牌价值和参与互动。
```

期望输出：

```yaml
space_classification:
  primary_bucket: retail
  project_type: brand_experience
  secondary_candidates:
    - project_type: commercial_retail
  boundary_case:
    pair: [brand_experience, commercial_retail]
    decision_reason: 成功标准更偏品牌认知沉浸，而非单纯销售转化。
  routing:
    ontology_framework: commercial_retail
    questionnaire_profile: brand_experience
```

关键判断：

- 如果成功标准是品牌认知，应优先走 `brand_experience`；
- 如果成功标准是坪效和转化，应回到 `commercial_retail`。

### 12.3 疗愈度假与医疗康养

输入：

```text
做一个疗愈度假中心，有冥想、健康餐、泡汤和自然景观，不涉及专业诊疗。
```

期望输出：

```yaml
space_classification:
  primary_bucket: hospitality
  project_type: commercial_hospitality
  secondary_candidates:
    - project_type: healthcare_wellness
  boundary_case:
    pair: [commercial_hospitality, healthcare_wellness]
    decision_reason: 主世界观仍是旅居停留和情绪恢复，不是诊疗照护流程。
  runtime_modifiers:
    experience_focus: [restoration, wellness]
```

关键判断：

- “疗愈”不是自动等于医疗康养；
- 只有安全、照护、康复、适老、技术流程成为主问题时，才进入 `healthcare_wellness`。

## 13. 最终建议

空间分类的可行落地，不在于马上扩展出一个巨大、完美的分类体系，而在于先完成三件事：

1. 把分类层级拆干净：父类桶、正式项目类型、专项标签、运行时变量、空间区域各归其位。
2. 把分类结果协议化：让系统拿到的不只是 `project_type` 字符串，而是一份可解释、可路由、可追问的结构化对象。
3. 把复杂度关进治理笼子：新类型必须证明它改变分析，不允许风格词、材料词、单次概念污染分类树。

推荐首期落地目标：

```text
在不破坏现有 project_type 主链的前提下，
新增 space_classification 统一分类结果，
覆盖高频类型、边界提示、路由映射和字段兼容。
```

这样做的收益最大、风险可控，也最符合方案高参当前阶段的系统复杂度。

一句话结论：

> 空间分类应当先成为“稳定的分析路由协议”，再逐步成长为“完整的空间知识底盘”；先解决问对问题，再追求分得更细。
