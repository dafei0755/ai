**这张表是这份技术可行性文档最重要的一张表。** 它说明:

1. **没有任何一套口径是完整的**——06 提了山地景观但代码没有,代码有 `digital_media_studio` 但理论文档没提。
2. **同一个概念在四处用四个名字**——`hospitality` / `commercial_hospitality` / `hospitality_tourism` 同时存在,这不是命名风格分歧,这是**会让检测器、本体加载器、问卷生成器返回不同结果的硬 bug 源**。

### 1.4 27 号"四层"与 05 号"分类/类型/变量"的口径对齐

这是另一个理论内部的不一致,需要先处理掉。

05 号说三个对象:
- 空间分类 (Classification)
- 空间类型 (Type)
- 类型变量 (Variables)

27 号说四层:
- 一级:正式项目类型 (Primary Project Type)
- 二级:父类归桶 (Parent Bucket)
- 三级:专项标签 (Specialty Tag)
- 四级:运行时修饰项 (Runtime Modifiers)

这两套**不是冲突的,但顺序不同、粒度不同**。

合理的统一是:

| 统一层 | 对应字段 | 对应 05 概念 | 对应 27 概念 | 例 |
|---|---|---|---|---|
| L1 父桶 | `parent_type` | 空间分类 | 父类归桶 | `hospitality` |
| L2 主类型 | `primary_type` | 空间类型 | 正式项目类型 | `boutique_hotel` |
| L3 专项标签 | `specialty_tags[]` | (隐含在 05 的"二级类型细分轴") | 专项标签 | `mountain_retreat` |
| L4 修饰项 | `runtime_modifiers{}` | 类型变量 | 运行时修饰项 | `geo=mountain, audience=family` |

**关键判断**:把 05 号的"空间分类"对应到 27 号的"父桶"(L1),把 05 号的"空间类型"对应到 27 号的"主类型"(L2),把 05 号的"变量"拆成 L3 标签(影响经验调用)和 L4 修饰项(影响判断权重)。这是**两套理论文档第一次被强制对齐**,后面所有协议设计都基于此。

### 1.5 真实项目复杂度的画像

理论文档假设的"项目"是结构化的、目标清晰的、用户能描述清楚的。但落地时面对的项目长这样:

#### 复杂度类型 A:用户输入极短

实际场景:

> "帮我做个山里民宿,带点茶空间,业主想做品牌"

这一句话要求系统:
- 识别一级桶(hospitality)
- 识别主类型(homestay/boutique_hotel?)
- 识别副类型(tea_house, brand_experience)
- 识别修饰项(山地)
- 估计混合权重

但这一句话**没有任何**关于客群、运营、预算、规模、停留时长的信息。冷启动场景下检测器**必然要在低置信度下做判断**,后续靠问卷补全。

**技术含义**:检测器必须显式输出置信度分布,而不是单一标签;主链必须能在低置信度下安全降级,而不是把"我猜是 homestay"当作既成事实推给后续节点。

#### 复杂度类型 B:用户表述自相矛盾

实际场景:

> "做个民宿,想要医院级别的安静和无障碍,服务老人家庭,但又要年轻人喜欢的高级感和打卡点"

这里同时引用了 hospitality 的语汇、healthcare_wellness 的需求、brand_experience 的目标。**用 27 号"主成功标准"裁决,这个项目其实可能是 healthcare_wellness × hospitality 的混合,且 healthcare_wellness 是隐含主导**——但用户自己没意识到。

**技术含义**:边界裁决器不能只看用户用了哪些词,要能识别"用词归属类型 A,但成功标准归属类型 B"的隐性冲突,触发追问。

#### 复杂度类型 C:类型在过程中漂移

实际场景:

> S1 阶段用户说"做茶空间",分类判定 retail_dining > tea_house。
> S3 阶段追问后发现:其实没有零售逻辑,核心是品牌方的会客接待场地。
> 实际类型应是 brand_experience,且业主自己没说清楚。

**技术含义**:分类不能只在 S1 一次性冻结,必须在 S2/S3 留有重判机会;但重判会影响 ontology 注入和已生成的问卷,需要明确"哪些下游可以无损重算,哪些需要标记 invalid"。

#### 复杂度类型 D:风格词污染分类

实际场景:

> "做个侘寂感的诊所"

如果检测器没有 27 号说的"风格词不进分类树"的规则,可能被"侘寂"带偏,误判成 wellness_retreat 之类的氛围向类型,而漏掉它**根本上是 clinic**(医疗合规、流程、安全才是主问题)。

**技术含义**:检测器需要**显式的风格词/材料词过滤层**,不能只靠关键词匹配。

#### 复杂度类型 E:混合权重不稳定

实际场景:

> 民宿(60%) + 茶空间(25%) + 文化沙龙(15%)

按 06 号示例,权重应该这样写。但**这些数字从哪来?** 用户不会告诉你"我的茶空间占 25%"。如果让 LLM 估,稳定性堪忧;如果用规则,规则从哪来。

**技术含义**:混合权重应该是**派生量**而不是**输入量**——用更可观测的指标(主使用时长占比、面积占比、营收占比、首要冻结对象数)派生出权重,且明确标注派生方式,而不是凭空给一个数字。

#### 复杂度类型 F:边界类型本身就是常态

经验上看,真正纯净的"独栋民宿""标准化连锁酒店"在实际项目里反而是少数。**多数实际项目天然就在边界上**:民宿+茶空间、办公+品牌展示、零售+餐饮、康养+度假……

**技术含义**:边界裁决不是"异常处理",是**主路径的一等公民**。不能把它做成"低置信度时才走的兜底分支"。

## 2. 核心技术抉择

进入设计前,先把几个会反复扯皮的设计抉择钉死,避免后面一边改 schema 一边推翻自己。

### 2.1 选择四层而不是三层或五层

**候选方案**:

- A. 三层:父桶 + 主类型 + 变量(05 号默认结构)
- B. 四层:父桶 + 主类型 + 标签 + 修饰项(27 号结构)
- C. 五层:父桶 + 主类型 + 子类型 + 标签 + 修饰项(更细)

**抉择**:采用四层(B),理由:

- 三层把"标签"和"修饰项"合并成"变量",会丢失一个关键区别——**标签会改变经验模板调用(影响 ontology 子章节、案例库 few-shot 选择),修饰项只改变判断权重**。这两件事在系统里走的是不同的下游路径,合并会让下游不知道该按哪条路径走。
- 五层会让"主类型"和"子类型"之间的判断标准模糊化——什么时候子类型才该升格为主类型?27 号的"五问筛选"只回答了主类型 vs 标签的问题,中间再插一层会让筛选规则不够用。
- 四层和现有代码 `parent_type` / `project_type` / `specialty_tag` / (modifiers 待建) 一一对应,迁移代价最小。

### 2.2 主类型 vs 副类型 vs 修饰项的边界守则

这是 28 号边界裁决在协议层的表现,要明确:

**判定为"主类型"的最小条件**(任一不满足都不能进 L2):

1. 它能稳定改变 `ontology.yaml` 中的 framework 选择(对应不同的 framework key)。
2. 它有独立的"优先冻结对象"清单(影响 S4 冻结顺序)。
3. 它在 `_type_registry.PROJECT_TYPE_REGISTRY` 里有独立 ID,不是别的类型的 alias。

**判定为"副类型"的条件**(L2 子集,在混合项目中):

1. 它本身具备 L2 资格(满足上面三条)。
2. 但它在当前项目中**不主导主成功标准**。
3. 它仍然影响 ontology 注入(用更轻的方式,见 4.4)。

**判定为"专项标签"的条件**(L3):

1. 不改变 framework,只影响 framework 内某些 dimension 的 weight 或 expansion。
2. 改变 few-shot 案例选择。
3. 改变交付命名的修饰部分(比如 "山地民宿" 中的"山地",虽然这其实更像 L4)。

**判定为"修饰项"的条件**(L4):

1. 不改变类型识别本身。
2. 改变同类项目内的判断权重、风险词、追问优先级。
3. 多数是场地/客群/经营/品牌等可枚举的轴。

**边界守则的可操作判断**(给检测器和审阅人共用):

| 候选项 | 改 framework? | 改优先冻结? | 改追问路径? | 反复出现? | 结论 |
|---|---|---|---|---|---|
| `boutique_hotel` | 否(共用 hospitality) | 否 | 微调 | 是 | L3 标签 |
| `clinic` | 是(走 healthcare_wellness) | 是 | 是 | 是 | L2 主类型 |
| 山地 | 否 | 否 | 微调权重 | 是 | L4 修饰项 |
| 侘寂 | 否 | 否 | 否 | 是 | **不进分类树**(风格层) |
| `brand_experience` | 是(独立 framework) | 是 | 是 | 是 | L2 主类型 |
| `popup_temporary` | 是(生命周期完全不同) | 是 | 是 | 是 | L2 主类型 |
| 亲子导向 | 否 | 微调 | 是 | 是 | L4 修饰项 |
| `tea_house` | 半(可在 retail_dining 内) | 微调 | 是 | 是 | L2 主类型(在副位) |

**关键判断**:这张表应该作为以后任何"新类型 PR"的强制 review 单。

### 2.3 混合项目 vs 升级新类型的取舍

经常出现的诱惑:遇到混合项目就想造一个新名字(比如 `tea_homestay`、`brand_office_hybrid`)。

**守则**:

- **优先用 L2 主+副 + L4 修饰** 表达组合,而不是造新 L2。
- 只有当一个组合**反复出现 ≥ 5 次**,**且现有主+副表达不足以指导分析**(比如它产生了独特的张力,如 `popup_temporary` 与普通零售的区别),才考虑独立成一个 L2。
- 即使要独立,先在 L3 试点(作为某个 L2 的标签),观察 3-6 个月,再考虑升 L2。

**反例**:`popup_temporary` 之所以已经是独立 L2,是因为它的**生命周期(周/月级)完全改变了优先冻结对象**(冻结的是搭建/拆除节奏,不是运营结构)。这是它配得上 L2 的硬证据。`tea_homestay` 不配,因为它的张力可以用 `homestay` (主) + `tea_house` (副) + `restoration` (修饰) 完整表达。

### 2.4 命名空间收敛策略

三套不一致的命名空间(参见 1.3),不能一次性大改。采用**渐进收敛**:

- **不动 v1 注册表**:`_type_registry.py` 现有 ID 作为代码权威 ID,不改名。
- **建立映射文档**:在 `_type_registry.py` 同目录新建 `TYPE_NAMING_MAP.md`,记录每个 ID 在 06 文档、27 文档、ontology.yaml 中的对应名,所有跨文档引用以此表为准。
- **增量统一**:新建的代码、ontology framework key,统一以 `_type_registry` 的 ID 为准。
- **标记弃用**:`ontology.yaml` 中 `hospitality_tourism` 这种与 ID 不一致的 key,在下次更新时增加 `aliases:` 字段,并在 ontology_loader 里做软兼容(优先 ID,fallback 别名)。

**不采用的方案**:大版本一次性改名。理由:`_type_registry` 已通过 `LEGACY_TYPE_ALIASES` 兼容旧 ID,任何改名都需要走 alias 流程,改名收益不抵迁移成本。

### 2.5 与 `extracted_spatial_zones` 的关系

系统清单 7.2 节提到新主线在向对象协议聚合,`extracted_spatial_zones` 是新结构化空间语义的承载体。

需要明确:

- **`project_classification` 描述项目整体**(L1-L4)。
- **`extracted_spatial_zones` 描述项目内部空间单元**(大堂、客房、茶室、儿童区)。
- **这是两层,不能混用**——27 号文档明确说"项目类型 vs 空间部位"必须分开。
- 但二者有耦合:某些 spatial_zone 的存在与缺失,可以**反向佐证**项目类型(比如出现"诊疗室"强提示 healthcare_wellness)。这种反向佐证应该作为检测器的输入证据,但**不能让 spatial_zones 自己当主类型**。

## 3. 数据结构与协议设计

到这里所有原则已经定完,正式给出协议层 schema。

### 3.1 顶层对象:`ProjectClassification`

替代现有零散字段(`project_type`、`project_classification`、`space_classification`、部分 `physical_context`),作为分类领域的单一对象协议:

```yaml
# ProjectClassification (v1)
ProjectClassification:
  # ---- L1 父桶 ----
  parent_type: string              # 必填,11 个固定值之一
  parent_type_confidence: float    # 0.0-1.0

  # ---- L2 主类型 ----
  primary_type: string             # 必填,_type_registry 中的 ID
  primary_type_confidence: float   # 0.0-1.0
  primary_type_evidence: list      # 命中证据(关键词/句子/语义片段)

  # ---- L2 副类型(0..n) ----
  secondary_types:
    - type: string                 # _type_registry ID
      weight: float                # 0.0-1.0,所有 secondary + primary 之和不强制 = 1
      role: enum                   # complement / extension / hybrid_partner
      evidence: list

  # ---- L3 专项标签 ----
  specialty_tags:                  # 0..n
    - tag: string                  # _type_registry.SPECIALTY_TAG_MAP 中的 ID
      strength: float              # 0.0-1.0,影响 few-shot 与 ontology 子章节加权
      source: enum                 # detected / declared / inferred

  # ---- L4 运行时修饰项 ----
  runtime_modifiers:
    geo_scene: string?             # mountain/coastal/urban/rural/...
    climate_factors: list?         # humid / strong_uv / low_temp / ...
    target_audience: list?
    operation_mode: list?
    experience_focus: list?
    constraints: list?             # heritage / accessibility_required / ...
    lifecycle: enum?               # permanent / pop_up / phased
    budget_tier: enum?             # entry / mid / premium / unconstrained

  # ---- 元信息 ----
  detection_meta:
    detector_version: string
    detected_at: timestamp
    is_ambiguous: bool             # 是否触发了边界裁决
    ambiguity_pair: list?          # [type_a, type_b] 当 is_ambiguous = true
    arbitration:                   # 仅 is_ambiguous 时存在
      winning_criterion: enum      # success_standard / tension / freezing_object / user_declared
      losing_type: string
      misjudgment_risks: list      # 引用 28 号手册的误判后果
    revisable_until: enum          # S1_lock / S3_lock / S5_lock
    revision_history:              # 可空
      - from: string
        to: string
        reason: string
        stage: enum
        at: timestamp
```

**设计说明**:

1. **`primary_type` 必填且唯一**——主类型只有一个。混合通过 `secondary_types` 表达。
2. **`weight` 不强制和为 1**——理论上可以,但如果用户后续追问只补了主类型信息,副类型权重不应被迫归零;让权重保留"绝对强度"语义,后续如果需要规范化,可以临时算。
3. **`role` 字段区分副类型角色**:
   - `complement`(补充功能,如民宿 + 早餐厅)
   - `extension`(扩展体验,如民宿 + 茶空间)
   - `hybrid_partner`(真混合,如商办综合体的零售部分)
4. **`is_ambiguous` 与 `arbitration`** 是 28 号手册在协议层的落地。**不是所有项目都需要 arbitration**,只有触发边界裁决器的才填。
5. **`revisable_until`** 显式声明类型在哪个阶段之前可以重判,避免 S5 之后还在改类型导致下游全部 invalidate。

### 3.2 `_type_registry` 的扩展 schema

现有 `_type_registry` 是一组扁平 dict,要扩展为结构化条目:

```yaml
# 单个 type 条目的扩展 schema
TypeRegistryEntry:
  id: string                       # 主键, e.g. "commercial_hospitality"
  level: enum                      # L1 / L2 / L3 / L4
  parent_id: string?               # L2 指向 L1, L3 指向 L2 或 L1
  labels:
    zh: string                     # 中文显示名
    en: string                     # 英文检索上下文
  aliases:                         # 来自 LEGACY_TYPE_ALIASES + 跨文档别名
    - source: enum                 # legacy / doc_06 / ontology_yaml
      alias: string
  ontology_framework_key: string?  # 仅 L2 必填,指向 ontology.yaml 中 key
  detection_keywords:              # 用于检测器的关键词
    strong: list                   # 强信号词
    weak: list                     # 弱信号词
    style_words_excluded: list     # 必须显式排除的风格词
  success_standards:               # 来自 27/28 号
    - 中文描述
  primary_tensions:                # 主张力,来自 27/28
    - 中文描述
  freezing_priorities:             # 优先冻结对象,来自 28
    ordered_list: list
  boundary_neighbors:               # 边界邻居,来自 28
    - neighbor_id: string
      ambiguity_signals: list       # 容易混的信号
      arbitration_question: string  # 28 号"裁决建议"中的关键问句
      misjudgment_risks_self_to_neighbor: list
      misjudgment_risks_neighbor_to_self: list
  status: enum                      # active / experimental / deprecated
  introduced_at: date
  evidence_cases: int               # 复现性证据计数(支持 27 号"反复出现"标准)
```

**关键设计**:

- **`boundary_neighbors`** 直接让 28 号手册的 8 个案例**结构化进数据**——不再只是文档里的散装段落,而是检测器可以查询的字段。这是把"边界手册"转化为运行时资产的核心一步。
- **`evidence_cases`** 支撑 27 号"是否反复出现"的硬标准。每加入一个案例,这个计数 +1。当某个 experimental 类型 evidence_cases ≥ N(建议 N=5)且至少有 2 套不同任务书,才考虑升 active。
- **`ontology_framework_key`** 显式声明 ID 与 ontology framework 的映射,**修复 1.3 节的不一致**。

### 3.3 ontology framework 的对齐 schema

`ontology.yaml` 里的 framework key 与 `_type_registry` ID 的对齐,通过 ontology 自身的元数据声明:

```yaml
ontology_frameworks:
  hospitality_tourism:           # 旧 key 保留
    aliases_for: commercial_hospitality   # 新增字段:声明这是哪个 ID 的 framework
    deprecated_key: true                  # 这个 key 在下次大版本时归并
    # ... 原有内容不动
```

**`ontology_loader.get_layered_ontology()`** 加载逻辑改为:

1. 先查 `_type_registry` 拿到 `ontology_framework_key`。
2. 用这个 key 在 `ontology.yaml` 里找 framework。
3. 如果找不到,fallback 用 ID 直接当 key 找。
4. 如果还找不到,fallback 到 `meta_framework`。

这样**不需要立刻改 ontology.yaml**,但建立了一个"找不到时该往哪降级"的清晰链路。

### 3.4 与现有 `state.py` 字段的兼容映射

现有主链字段不能立刻改名。给出过渡期映射:

| 现有字段 | 新对象路径 | 过渡策略 |
|---|---|---|
| `state.project_type` | `state.project_classification.primary_type` | 双写期 6 周,旧字段保留只读 |
| `state.project_classification` (dict) | `state.project_classification` (对象) | 同名升级,需要 contract 测试 |
| `state.space_classification` | 移除,合并到 `project_classification` | 标记 deprecated,不再写入,读旧值时 fallback |
| `state.physical_context.space_type` | `state.project_classification.primary_type` | 注意:这里语义上历来混乱(有时是项目类型,有时是物理空间名),需要**先做一次清查**才能迁移 |
| `state.extracted_spatial_zones` | 不变 | 这是空间单元层,不受分类层重构影响 |

**`physical_context.space_type` 是最大的迁移风险点**。它在 `deliverable_id_generator_node.py` 里被用来拼"{space_type}整体设计方案"这种交付物名,实际写入时的语义不稳定:

- 有时是 `民宿`(主类型显示名)
- 有时是 `茶空间`(副类型或物理空间名)
- 有时是 `山地民宿`(主类型 + 修饰项的组合显示名)

**Phase 1 必做的一件事**:在迁移之前,先在生产环境采样 100+ 真实 `physical_context.space_type` 值,做一次人工分类,搞清楚现状里它到底承载了几种语义,再决定如何拆分到 `primary_type` / `display_name` / `space_unit_type`。

## 4. 分类引擎技术方案

### 4.1 检测 pipeline 总览

按职责分四阶段,每阶段是一个独立可替换组件:

```
[阶段 1] 输入清洗与归一化
  ├─ 风格词剥离(侘寂/极简/高级感 → 移到 style_hints,不进分类)
  ├─ 材料词剥离(微水泥/木作 → 移到 material_hints)
  ├─ 别名归一(type_alias_normalizer.py)
  └─ 语境标记(地点词、规模词、客群词进 modifiers)

[阶段 2] 候选类型生成
  ├─ 强信号词匹配 → top-3 候选 + 强度
  ├─ 语义相似度匹配(向量召回)→ top-5 候选 + 相似度
  └─ 合并去重 → 候选池(每个候选含来源、命中证据、初始置信度)

[阶段 3] 主类型裁决
  ├─ 单候选高置信度 → 直接落定
  ├─ 多候选竞争 → 进入边界裁决器(4.4)
  └─ 全部低置信度 → 进入冷启动追问

[阶段 4] 输出装配
  ├─ 填充 primary_type / parent_type / specialty_tags / runtime_modifiers
  ├─ 填充 detection_meta(包括 is_ambiguous / arbitration)
  └─ 写入 state.project_classification
```

### 4.2 阶段 1 的关键:风格词/材料词/体验词显式剥离

这是 27 号文档说"分类树不收风格/材料/体验词"在工程上的落点。现有 `project_type_detector.py` 没有这个剥离环节,关键词匹配会被风格词污染。

**实现要点**:

1. 在 `_type_registry.py` 或独立的 `style_word_dictionary.py` 中维护三个词典:
   - `STYLE_WORDS`:侘寂、新中式、极简、轻奢、复古、工业风、ins 风…
   - `MATERIAL_WORDS`:微水泥、木质、石材、金属、肌理、岩板…
   - `EXPERIENCE_WORDS`:诗意、哲学感、戏剧感、高级感、松弛感、烟火气…

2. 阶段 1 处理时:
   - 命中即剥离,记录到 `style_hints` / `material_hints` / `experience_hints`(供后续生成阶段消费,不影响分类)。
   - **但保留位置信息**——这些词周边的句子可能仍含分类信号,不能整句剔除。

3. 风格词剥离后,如果剩余文本不足以做分类(剥光了),进入冷启动路径(见 4.6)。

**反例**:用户输入"做个侘寂感的乡村民宿"。
- 错的处理:把"侘寂感的乡村民宿"整体当 token,匹配上 `wabi_sabi_homestay` (这个伪类型不存在,但容易被向量召回到错的近邻)。
- 对的处理:剥出"侘寂"→ `style_hints: [wabi_sabi]`,剩余"乡村民宿"→ `primary_type: homestay`, `runtime_modifiers.geo_scene: rural`。

### 4.3 阶段 2 的关键:多源候选合并

不应只用关键词匹配。建议三源召回:

| 召回源 | 适用场景 | 输出 |
|---|---|---|
| 强信号词典 | 高确定性短输入("诊所"、"民宿") | 高置信度,但召回率低 |
| 弱信号 + 共现 | 间接描述("看病的地方"、"接待客人住的") | 中置信度 |
| 向量语义召回 | 长输入、隐喻表达 | 召回率高,但可能召回近邻噪声 |

**合并规则**:

1. 每个候选 type 的最终强度 = max(强信号强度, 0.7 × 弱信号强度, 0.5 × 向量相似度)
2. 至少有一个强信号或两个弱信号,才进入候选池(避免向量召回的孤立误命中)
3. 候选池上限 5 个,按强度降序

**不采用的方案**:把所有候选都喂 LLM 让它选。理由:LLM 在分类任务上稳定性差,且会把 ontology 加载放到 LLM 调用之后,延迟和成本都会显著上升。LLM 应该只在阶段 3 的边界裁决器里用,而且要用结构化输出。

### 4.4 阶段 3:边界裁决器(BoundaryArbiter)

这是把 28 号手册转化为运行时组件的核心。

**触发条件**:候选池 top-2 强度差 < 0.15(阈值待调),或者 top-1 在 `boundary_neighbors` 里显式登记了与 top-2 的边界关系。

**输入**:

```yaml
ArbiterInput:
  candidates: [top_1, top_2]
  user_text: string
  modifiers_extracted: dict
  registry_neighbor_record:        # _type_registry.boundary_neighbors 中的对应条目
    arbitration_question: string
    misjudgment_risks: dict
```

**裁决步骤**:

1. **先尝试规则裁决**:基于已抽到的 modifiers。例:
   - 若候选是 `homestay` vs `personal_residential`,且 `runtime_modifiers.lifecycle != permanent`(明显短住),规则即可裁决为 hospitality 桶下的 homestay。
   - 若候选是 `clinic` vs `wellness_retreat`,且文本含"医师/诊疗/医保",规则即可裁决为 clinic。

2. **规则无法裁决时,启用 LLM 单问裁决**(不是开放生成,是结构化二选一):
   - Prompt 模板由 `boundary_neighbors.arbitration_question` 提供。
   - 例:"请判断这个项目最怕失败在哪——'体验割裂'(选 A)还是'照护失效'(选 B)?基于以下文本:..."
   - 输出固定为 `{winner: A|B|need_more_info, reason: string}`。
   - 输出 `need_more_info` 时,触发 4.6 的冷启动追问。

3. **裁决结果写入 `arbitration` 字段**,附带 `winning_criterion` 和 `losing_type`,**保留败选信息**。这非常重要——后续阶段如果发现误判,可以快速回退到败选作为新候选,而不是从头跑检测器。

**为什么要"保留败选"**:复杂度类型 C(类型在过程中漂移)出现时,如果 S3 阶段发现 S1 判错了,有 `losing_type` 的话可以**直接试败选**作为新主类型,而不必重新检测。这是用 5% 的存储换 30% 的回退效率。

### 4.5 阶段 3 的备选:多类型并存输出

某些场景规则和 LLM 都判不出,因为项目本身就**还没决定**自己是什么。

例:用户说"我有块地,想做个能接待客人也能办活动的地方,具体形态再讨论"。

这种情况不应硬选,应输出 `primary_type_confidence < 0.5`,并把候选池前 3 个一并存入 `secondary_types`(都标 `role: hybrid_partner`),让后续问卷阶段去做"先收敛业态再细化"。

**关键**:检测器要能**正确地表达不确定性**,而不是被迫给一个错的肯定答案。

### 4.6 冷启动与低置信度处理

当所有候选强度都低于阈值(建议 0.5),启动冷启动追问:

1. **不进入 ontology 注入**(否则会用错的 framework 污染分析)。
2. 不写 `primary_type`,但写 `parent_type`(父桶通常较容易判)。
3. 触发问卷的"分类前置追问模板",问 5 个最能区分父桶下属类型的关键问题:
   - 主要使用者是谁?(住客 / 业主 / 公众 / 员工 / 患者 / 学习者)
   - 使用时长?(几小时 / 当晚 / 几天 / 长期)
   - 主要成功标准?(28 号问句的简化版)
   - 主要营收逻辑?(按次 / 按时长 / 不直接营收)
   - 是否新建?(新建 / 改造 / 临时)

这五个问题的答案能把 11 个父桶下的所有 L2 主类型基本区分开。

### 4.7 检测器的可观测点

不可观测的检测器最容易在生产里出问题。建议落:

| 指标 | 维度 | 用途 |
|---|---|---|
| `detection_count_total` | by primary_type | 每天每个类型被分到多少次 |
| `detection_confidence_distribution` | by primary_type | 置信度直方图,识别"总在低置信"的类型 |
| `arbitration_rate` | by neighbor_pair | 哪对边界最常触发裁决 |
| `arbitration_winner_distribution` | by neighbor_pair | 裁决结果是否过于偏向某一边(可能规则有偏) |
| `revision_rate` | by stage | S2/S3/S4 分别有多少类型被重判 |
| `cold_start_rate` | overall | 冷启动追问触发率 |
| `style_word_pollution_count` | by style_word | 哪些风格词最常被剥离 |

这些指标 Phase 2 必须接入,否则系统是黑盒。

## 5. 现实复杂度的应对策略

把 1.5 节列出的 6 类复杂度,逐一对应到技术处理。

### 5.1 应对 A 类:用户输入极短

**策略**:

- 检测器输出**阶段化置信度**(stage_confidence),而不是单一置信度。
- `stage_confidence: { stage_S1: 0.6, stage_S3_min_required: 0.8 }`——意思是 S1 阶段有 0.6 已经足够推下游,但 S3 之前必须涨到 0.8 才能 lock。
- 主链节点根据当前阶段读对应阈值,不够则触发问卷补强。

### 5.2 应对 B 类:表述自相矛盾

**策略**:

- 在阶段 1 输出 `signal_dissonance_flag`:当文本同时强命中两个父桶(且不是已知的合理混合,如 hospitality + retail_dining 是合理的,但 hospitality + healthcare_wellness 是 28 号明确说的高风险边界)。
- 命中即触发**强裁决**:不允许检测器自己拍板,必须走 LLM 单问 + 用户确认。
- 实现上,在 `_type_registry.boundary_neighbors` 里给每对高风险边界标 `force_arbitration: true`。

### 5.3 应对 C 类:类型在过程中漂移

**策略**:

- `revisable_until` 字段是核心,定义三档:
  - `S1_lock`:锁定前可任意改(默认)
  - `S3_lock`:S2 问卷阶段还能改,S3 后冻结
  - `S5_lock`:几乎不能改(只有 user 强制覆盖)
- 漂移触发点:
  - S2 问卷答完后,关键问句答案与当前 primary_type 的 success_standards 冲突 → 触发**软重判**(再跑一次裁决器,不重跑检测器)。
  - S3 中途若 user 显式说"其实不是 X 是 Y" → 触发**硬重判**(整个检测重跑)。
- 漂移代价管理:
  - **能无损重算的**:ontology 注入、问卷下一步生成、few-shot 选择(只要还没被消费)。
  - **必须 invalidate 的**:已经生成的问卷答案如果与新类型不相干、已经写出的交付物名(如果用了旧 space_type)。
- 在 `revision_history` 里完整记录,审计用。

### 5.4 应对 D 类:风格词污染

**策略**:见 4.2 阶段 1 的剥离机制。**关键**:剥离层要被监控(指标 `style_word_pollution_count`),如果某个风格词反复出现且每次都被剥离,可以考虑加进强词典;如果某些风格词在 ontology 里其实有合法用途(比如"侘寂"对于某些 hospitality 子类型可能是有效的体验线索),要在 ontology framework 里显式声明该风格词的可接受范围,而不是全局剥离。

### 5.5 应对 E 类:混合权重不稳定

**策略**:权重是派生量,不是输入量。明确派生口径:

```python
# weight_derivation_v1
def derive_weight(secondary_type, project_data):
    signals = {
        "area_ratio": project_data.area_breakdown.get(secondary_type, 0),
        "operation_revenue_ratio": project_data.revenue_breakdown.get(secondary_type, 0),
        "freezing_priority_overlap": count_overlap(
            secondary_type.freezing_priorities,
            project_data.declared_priorities
        ),
        "primary_use_time_ratio": project_data.use_time_breakdown.get(secondary_type, 0),
    }
    # 加权平均,且要求至少有 2 个非零信号
    return weighted_average(signals, weights=DEFAULT_WEIGHT_DERIVATION_PROFILE)
```

如果 4 个信号全都缺,**不要凭空给一个数**——给 `weight_unknown: true`,让下游知道这个权重是占位符,不要用它做关键决策。

### 5.6 应对 F 类:边界类型是常态

**策略**:

- 边界裁决器**不是兜底分支**,是主路径。`detect_with_details()` 返回的每个结果都要标记 `is_ambiguous`,即使是 false。
- 监控 `arbitration_rate`,如果发现某对父桶之间裁决率长期 > 30%,意味着这对父桶的边界本身是模糊的——这是真实信号,可能需要调整 `_type_registry` 中的边界定义,或者新增一个标签来吸收这部分边界。

## 6. 系统接入与数据流

### 6.1 主数据流(改造后)

```
用户输入
  ↓
[新] InputCleaner (阶段 1):风格/材料/体验词剥离 → style_hints
  ↓
[改造] ProjectTypeDetector:
  - 阶段 2 多源候选生成
  - 阶段 3 边界裁决(可调用 LLM)
  - 阶段 4 装配 ProjectClassification 对象
  ↓
[改造] requirements_analyst_agent:
  - 接收 ProjectClassification 对象,而非散字段
  - 写入 state.project_classification
  - 同时在过渡期回填 state.project_type 等旧字段
  ↓
[改造] requirements_nodes:
  - 读 ProjectClassification.primary_type / secondary_types
  - 检查 stage_confidence 是否足以进入下一阶段
  - 不够则触发冷启动追问(由问卷节点接管)
  ↓
[改造] ontology_loader.get_layered_ontology:
  - 输入 ProjectClassification (而不只是 project_type)
  - 主类型走主 framework,副类型用减半权重叠加(见 6.2)
  - specialty_tags 用于 framework 内子章节加权
  - runtime_modifiers 不影响 framework,但传给下游 prompt 作为上下文
  ↓
问卷生成(改造):
  - 根据 primary_type 选模板
  - 根据 secondary_types 增加跨业态追问
  - 根据 modifiers 加追问
  - 低置信度时优先走"分类前置追问"模板(4.6)
  ↓
执行节点 / 交付节点:
  - deliverable_id_generator_node 改读 ProjectClassification.primary_type 和 display_name
  - 不再依赖 physical_context.space_type 的混乱语义
```

### 6.2 副类型在 ontology 注入中的处理

主+副类型并存时,**ontology 不能简单"全部并集"**——那会让分析维度爆炸。

建议规则:

1. 主类型 framework 全量加载。
2. 副类型 framework 只加载它**与主类型不同**的 dimension(diff 加载)。
3. diff 加载的 dimension,weight 按 `secondary_type.weight × 0.6` 折减(0.6 是经验系数,Phase 2 调)。
4. 如果某个 dimension 在主和副里都存在但表述不同,**保留主的表述**,把副的表述放到 `dimension_alternative_views`,作为分析时可选的视角。
5. expert_extensions 按主类型的专家组合启用,副类型的特有 expert(如 brand_experience 的"叙事专家")用 `auxiliary_experts: true` 标记,只在涉及副类型的具体追问时才激活。

### 6.3 不破坏现有交付层的过渡

`deliverable_id_generator_node.py` 现在直接读 `physical_context.space_type` 拼名。过渡期:

- **保留现有读法**作为 fallback。
- 优先读 `state.project_classification.display_name`(见 3.1,新增字段)。
- `display_name` 由 ProjectClassification 的装配函数生成:
  - 默认 = `primary_type.labels.zh`
  - 若有强相关 modifier(如 geo_scene=mountain),= `{modifier_zh}{primary_type.labels.zh}`(山地民宿)
  - 若有副类型且 weight ≥ 0.3,= `{primary}+{secondary}`(民宿+茶空间)
- `display_name` 是分类系统对外的"名牌",不参与任何分析逻辑,只用于交付命名、问卷文案、UI 显示。

## 7. 治理机制

### 7.1 类型新增评审流程

任何"新增类型"PR 必须包含:

```yaml
# new_type_proposal.yaml
proposal:
  candidate_id: string
  candidate_zh_label: string
  proposed_level: enum             # L1/L2/L3/L4
  parent_id: string?

  # 来自 27 号"五问筛选"
  five_question_check:
    Q1_changes_main_view: yes/no/partially      # 是否改变分析世界观
    Q2_changes_primary_tension: yes/no/partially
    Q3_needs_independent_ontology: yes/no
    Q4_changes_questioning_path: yes/no
    Q5_will_recur: yes/no
    evidence_for_each: list

  # 来自 27 号"边界与误判"
  boundary_analysis:
    nearest_neighbors:
      - neighbor_id: string
        why_not_alias: string
        misjudgment_risks: list

  # 落地资产
  required_assets:
    ontology_framework: required_if_L2
    detection_keywords:
      strong: list (≥ 5)
      weak: list (≥ 10)
    style_words_excluded: list
    boundary_neighbor_records: list (必须 ≥ 1)

  # 复现性
  evidence_cases:
    cases_collected: int (≥ 3 才能进 experimental, ≥ 5 才能升 active)
    case_links: list

  # 风险
  system_complexity_delta:
    new_questionnaire_branches: int
    new_few_shot_buckets: int
    estimated_review_burden: low/medium/high
  proposed_status: experimental
```

**评审委员会**:至少 1 名理论文档维护者 + 1 名代码维护者 + 1 名实际项目使用者(产品/设计 lead)。

**通过标准**:

- 五问中至少 4 问为 yes(Q1/Q3 任一为 no 直接驳回)。
- 必备资产齐全。
- evidence_cases ≥ 3。
- 系统复杂度 delta 评级为 low/medium 时直接通过;high 时需额外提交"复杂度收益对比"。

### 7.2 类型质量监控

每月一次类型健康巡检,重点指标:

| 指标 | 健康阈值 | 异常处理 |
|---|---|---|
| 月触发次数 | ≥ 3 | 连续 3 月低于阈值 → 标 `dormant`,候选合并到父桶 |
| 平均置信度 | ≥ 0.6 | 低于阈值 → review 关键词词典 |
| 边界裁决率 | ≤ 30% | 高于阈值 → review 与最近邻的边界定义 |
| 重判率(漂移) | ≤ 15% | 高于阈值 → 该类型的 success_standards 可能太宽松 |
| 用户覆盖纠错率 | ≤ 10% | 高于阈值 → 检测器在该类型上有偏 |

`dormant` 类型在 6 个月内未被重新激活,进入 `deprecated`,从注册表移除(保留在 LEGACY_TYPE_ALIASES 中)。

### 7.3 类型生命周期

明确状态机:

```
proposed → experimental → active → dormant → deprecated → archived

         ↑                ↑
       evidence_cases≥3  evidence_cases≥5 且通过评审
```

**experimental** 状态下:
- 仅参与检测(命中后写入 ProjectClassification)
- 不强制要求完整 ontology framework(可以临时复用最近邻)
- UI 上标注"实验类型",收集反馈

**active** 状态下:
- 全功能可用
- 必须有完整 ontology framework
- 必须出现在 `boundary_neighbors` 网络中

**dormant** 状态下:
- 检测器仍可识别(避免老项目无法复现)
- 不出现在新项目的候选池里

### 7.4 命名空间治理

承接 1.3 节的现状,Phase 1 必须建立单一权威:

- `_type_registry.py` 中的 ID 是**唯一权威 ID**。
- 所有文档(05/06/27/28 + 本文档 + 后续)在引用类型时,**必须用 ID,不再用中文显示名**作为主标识。
- 中文标签变更时,只改 `labels.zh`,ID 永不变更(除非走 deprecation 流程)。
- ontology framework key 的命名,新增时一律与 ID 一致;存量不一致的(如 `hospitality_tourism`),通过 alias 字段软兼容,不强制改名。

## 8. 落地路径(分阶段)

不要试图一次性大重构。分四阶段,每阶段独立可验证、可回滚。

### Phase 0:基线对齐(2-3 周)

**目标**:解决理论与代码的 gap,产出一份"权威清单 v1"。

**产出**:

1. `TYPE_NAMING_MAP.md`——三套口径的对齐表,作为后续讨论的唯一参考。
2. `_type_registry.py` 的小规模扩展:为每个现有类型补充 `boundary_neighbors`(从 28 号手册拷过来)和 `success_standards`(从 27 号拷过来),作为静态字段。
3. `physical_context.space_type` 的语义清查报告:采样 100+ 真实值,人工标注其实际语义,产出迁移决策(分别对应 primary_type / display_name / spatial_zone)。
4. **不做**协议升级,**不做**检测器改造。

**验证**:

- `TYPE_NAMING_MAP.md` 通过 1 名理论维护者 + 1 名代码维护者 review。

**回滚**:Phase 0 是纯文档和数据,不涉及代码逻辑改动,无需回滚。

### Phase 1:协议固化(4-6 周)

**目标**:`ProjectClassification` 对象协议落地,主链双写,旧字段保留只读。

**产出**:

1. `ProjectClassification` 数据类(Python dataclass / Pydantic),带版本字段。
2. `requirements_analyst_agent` 改造:输出 `ProjectClassification` 对象,同时双写旧字段。
3. `state.py` 增加 `project_classification: ProjectClassification`,标记旧 `project_type` / `space_classification` 为 deprecated_for_read。
4. `ontology_loader` 改造:接受 `ProjectClassification` 输入,内部仍主要用 `primary_type`,副类型 diff 加载先简化处理(可以先全加载,Phase 2 再精细化)。
5. `deliverable_id_generator_node` 改造:优先读 `display_name`,fallback 旧 `space_type`。

**验证**:

- 双写测试:旧链路与新链路输出对齐率 ≥ 95%。
- 现有问卷不应受影响(回归测试)。

### Phase 2:检测引擎升级(6-8 周)

**目标**:新检测 pipeline 落地,边界裁决器上线,可观测性接入。

**产出**:

1. `InputCleaner` 模块:风格/材料/体验词剥离。

### Phase 3:治理闭环与生态(6-8 周)

**目标**:把治理机制(类型新增评审、月度健康巡检、漂移监控)正式落地,开始处理低优先级的存量类型不一致(如 `digital_media_studio`、`special_function`、`hybrid_residential_commercial` 这些理论文档没明确处理的类型该归入哪里)。

2. 月度类型健康报告自动生成。

## 9. 风险评估与降级

每个技术系统都会出问题,关键是出问题时**降级到什么状态**。

### 9.1 风险清单

按"发生概率 × 影响范围"排列:

| 风险 | 概率 | 影响 | 分类 |
|---|---|---|---|
| `physical_context.space_type` 语义清查发现存量数据混乱程度超预期 | 高 | 高 | 阻塞性 |
| LLM 边界裁决在某些案例上稳定性不足 | 中 | 中 | 可迭代 |
| 命名空间收敛过程中漏改某处,导致 ontology 加载失败 | 中 | 高 | 工程性 |
| 新增类型评审流程过重,实际很少有人走 | 中 | 中 | 流程性 |
| Phase 2 上线后,某些类型的检测准确率不升反降 | 中 | 高 | 可回滚 |
| 副类型 ontology 叠加导致 prompt 过长、成本上升 | 中 | 中 | 可优化 |
| 治理监控数据没人看,问题不被发现 | 高 | 中 | 文化性 |
| 迁移期双写产生数据漂移(新旧字段不一致) | 中 | 高 | 工程性 |
| 风格词剥离过度,误剥真实分类信号 | 低 | 中 | 可调参 |
| 用户在 S5 之后强制要求改类型,触发大面积下游 invalidate | 低 | 高 | 流程性 |

### 9.2 关键降级策略

**降级 1:检测器整体失效**

如果新检测器在生产中出现严重问题,**Feature flag 切回旧检测器**。`ProjectClassification` 对象仍然生成,但只有 `primary_type` 字段填充,其他字段空缺。下游代码必须能容忍 `secondary_types = []`、`runtime_modifiers = {}`、`arbitration = null` 的情况——这是协议设计时就要约束的(所有非 primary_type 字段都是 Optional)。

**降级 2:边界裁决器失效**

裁决器 LLM 调用失败或超时时,fallback 顺序:
1. 用规则裁决(规则查不到就跳过)
2. 选 top-1 候选,标 `is_ambiguous: true`,`arbitration: null`
3. 在下次问卷里追问,让用户来判

**绝不**:在裁决器失效时硬选某一边却不标 `is_ambiguous`——这会让后续节点以为分类已确定,造成静默错误。

**降级 3:ontology 找不到对应 framework**

按 3.3 的 fallback 链:ID → key → meta_framework。如果连 meta_framework 都找不到(意味着 ontology.yaml 损坏),抛硬错误,**不做静默兜底**——分析完全没有 ontology 比有错的 ontology 危害小。

**降级 4:副类型权重派生失败**

按 5.5 的策略,标 `weight_unknown: true`,在 ontology 副类型叠加时,按 0.3 默认权重处理;在 display_name 生成时,不显示副类型。

**降级 5:阶段置信度不达标**

不阻塞流程,但触发追问。不要因为分类不够准就拒绝继续——用户可能不需要那么准的分类(比如非常前期的概念阶段)。让用户决定是否补充信息。

### 9.3 数据迁移风险专项

最危险的是 `physical_context.space_type` 的迁移。

**Phase 0 必须完成的清查报告应该包含**:

- 现有取值的频次分布(top 50)。
- 每个值的语义归属(项目类型 / 物理空间名 / 修饰组合 / 不明)。
- "不明"占比 → 决定迁移策略:
  - 不明 < 5%:可以直接迁移,不明值标 `legacy_unparsed: true`,后续手动处理。
  - 5% ≤ 不明 < 20%:需要先做一轮"反向标注"(用 LLM 把每个不明值映射到正确的 primary_type,再人工校验)。
  - 不明 ≥ 20%:迁移风险过高,需要先治理数据,再迁移协议。

**判断**:这个清查报告本身就是 Phase 0 的关键里程碑。**没有这份报告,Phase 1 不应启动。**

### 9.4 不可逆风险与可逆风险

明确区分:

| 操作 | 可逆性 | 处理 |
|---|---|---|
| 新增类型 ID | 可逆(标 deprecated 即可) | 走轻评审 |

## 11. 决策表与最终建议

### 11.1 关键技术决策汇总表

把全文的核心决策汇成一张表,供后续 review 与争议时直接引用:

| 决策点 | 选项 | 决策 | 依据 |
|---|---|---|---|
| 层级数 | 3/4/5 | **4 层** | 标签和修饰项必须分开,五层划分模糊(2.1) |
| 命名空间收敛 | 大版本改名 / 渐进收敛 | **渐进收敛** | 改名收益不抵迁移成本(2.4) |
| 权威 ID 来源 | 文档 ID / 代码 ID | **代码 ID** (`_type_registry.py`) | 代码是运行时真相源(7.4) |
| 混合权重 | 输入量 / 派生量 | **派生量** | 用户无法可靠地给数字(5.5) |
| 副类型 ontology 处理 | 全合并 / diff 加载 | **diff 加载 + 折减** | 避免 prompt 爆炸(6.2) |
| LLM 在裁决器中的角色 | 主裁决 / 兜底裁决 | **兜底裁决** | LLM 稳定性差,规则优先(4.4) |
| 边界裁决触发条件 | 总是触发 / 强信号差小才触发 | **后者(差 < 0.15 或显式登记)** | 平衡精度与性能(4.4) |
| 类型漂移处理 | 一次性冻结 / 多档冻结 | **多档冻结**(S1/S3/S5) | 真实项目类型确实会漂移(5.3) |
| 风格词处理 | 进分类 / 剥离 | **剥离** + 保留位置 | 27 号原则的工程化(4.2) |
| 双写过渡期 | 无 / 短(2 周)/ 长(6 周) | **6 周** | 给充分回归时间(8 节 Phase 1) |
| `physical_context.space_type` 迁移前置 | 直接迁移 / 先做语义清查 | **先做清查** | 风险最高的存量字段(3.4, 9.3) |
| 类型新增门槛 | 灵活 / 严格(五问 + 评审) | **严格** | 控制类型膨胀(7.1) |
| 类型规模目标 | 不限 / 30-50 | **30-50** | 大于此则治理失控(10.5) |
| 自定义类型 | 支持 / 不支持 | **不支持** | 破坏分析框架稳定性(8.5) |

### 11.2 最终建议:做什么、不做什么

**应该做**:

1. **先把命名空间钉死再做检测器升级**——Phase 0 不能跳。这是所有后续工作的基础。
2. **把 28 号手册的 8 个边界案例结构化进 `_type_registry`**——它们是检测器最难处理的部分,也是用户感知最强的部分,优先回报最高。
3. **建立可观测性,从 Phase 2 开始监控**——分类系统的问题不会自己暴露,必须主动看数据。
4. **把"分类"和"空间单元"两层彻底分开**——`project_classification` 描述项目,`extracted_spatial_zones` 描述内部空间,共享数据但不共用字段。
5. **把混合项目当一等公民,而不是特例**——大多数真实项目都在边界上。
6. **保留败选信息**——`arbitration.losing_type` 不要省,它是最便宜的容错保险。
7. **新增类型评审走严格流程,但允许 experimental 状态降低门槛**——给新类型一个低成本试错的入口,但不让它静默升级。

**不应该做**:

1. **不做**一次性大改名。命名收敛通过 alias 兼容渐进做。
2. **不做**让 LLM 当主分类器。LLM 在分类任务上稳定性不够,且会引入成本和延迟。
3. **不做**自动派生混合权重(在 Phase 1)。先接受 `weight_unknown`,等数据积累再上派生。
4. **不做**支持用户/项目自定义类型。这会让 ontology 框架失稳。
5. **不做**把所有边界都规则化。规则覆盖 28 号 8 个案例就够了,其他用 LLM 兜底。
6. **不做**在低置信度时硬选。宁可触发追问,也不要给一个错的肯定答案。
7. **不做**跨阶段保留过严格的类型锁。允许 S3 之前重判,这是给真实项目的灵活性。

### 11.3 一句话总结

把全文压成一句:

> **空间分类不是把世界分细的任务,而是给后续分析做正确路由的基础设施。技术上要做的,不是发明更多类型,而是把"类型不确定性、混合性、边界性、漂移性"这四件事变成可观测、可裁决、可降级、可治理的协议字段;并且在做这件事之前,先把现存四份理论文档与四套代码字段的命名不一致钉死。**
