# 空间分类交叉校验与合理化执行思路

> 日期：2026-04-30  
> 目标：以主架构为基线，交叉校验参考 1 与参考 2，形成不拼盘、不盲从、可执行的推进路线。  
> 基本立场：空间分类是方案高参的分析路由基础设施，不是空间名称表；执行上必须兼容当前代码现实，先消除字段和命名混乱，再逐步增强智能裁决。

---

## 0. 总判断

主架构的总体方向成立：

1. 不重写现有 `project_type` 主链；
2. 在现有检测器外侧增加统一分类结果对象；
3. 把父类桶、正式项目类型、专项标签、运行时变量、空间区域拆开；
4. 用边界案例和误判风险治理真实复杂项目；
5. 让分类结果驱动问卷、本体、交付命名、平面沙盘和方案画布。

但参考意见暴露出三个必须修正的点：

1. 不能一上来就做复杂服务和下游改造，必须先做“命名空间 + 旧字段语义”清查。
2. 不能把 `spatial_zones` 当作空间分类层级的一部分，它应该是相关对象，不是项目分类本体。
3. 不能把类型数量快速扩到 60-80 个正式项目类型；当前更现实的是 30-50 个 active `project_type`，更多差异进入标签、变量、知识包候选或 alias。

最终建议采用：

> **四层分类核心 + 空间区域侧车对象 + 渐进式双写迁移。**

即：

```text
L1 parent_bucket / primary_bucket
L2 project_type
L3 specialty_tags / secondary_types
L4 runtime_modifiers

+ spatial_zones 作为关联对象，不进入项目类型树
```

## 1. 事实校验

### 1.1 当前代码真相源

参考 2 多次提到 `services/_type_registry.py`，但当前代码中该文件不存在。

事实校验结果：

```text
intelligent_project_analyzer/services/_type_registry.py  不存在
intelligent_project_analyzer/services/project_type_detector.py  存在
```

当前权威注册和检测对象实际在：

```text
intelligent_project_analyzer/services/project_type_detector.py
```

包括：

- `PROJECT_TYPE_REGISTRY`
- `LEGACY_TYPE_ALIASES`
- `PARENT_TYPE_MAP`
- `SPECIALTY_TAG_MAP`
- `ProjectTypeDetector`

因此，参考 2 中所有 `_type_registry.py` 的执行建议，需要替换为：

```text
project_type_detector.py 当前承载注册表；
中长期可以抽出独立 YAML/JSON registry；
但短期不能以不存在的 _type_registry.py 作为实施入口。
```

### 1.2 当前 `project_classification` 处于语义漂移状态

`core/state.py` 里仍有：

```python
project_classification: Optional[Dict[str, Any]]
```

但 `workflow/main_workflow.py` 明确注释：

```text
v9.1: project_classification 已移除（死代码清理）
下游组件直接使用 detected_design_modes 和 project_type
```

`output_intent_detection.py` 又临时从 `project_type` 构造：

```python
project_classification = {"project_type": _project_type_str}
```

结论：

- 参考 2 提议直接把 `project_classification` 升级为 `ProjectClassification`，理论上干净，但在当前代码语境下容易复活一个已经语义漂移的字段。
- 主架构提议新增 `space_classification` 更稳，因为它明确表达“空间分类结果”，不会和设计模式、动机分类等广义 project classification 混在一起。

建议：

```text
短期新增 state.space_classification；
继续保留 top-level project_type；
project_classification 暂不作为新语义入口；
后续如果要统一为 ProjectClassification，需要单独迁移 RFC。
```

### 1.3 `physical_context.space_type` 是最大存量风险

主架构已经指出 `space_type` 混用；参考 2 进一步强调迁移前必须做语义清查，这一点应采纳。

当前 `space_type` 可能同时表示：

- 项目类型：民宿、住宅、办公；
- 空间部位：客房、大堂、餐区；
- 展示命名：`{space_type}整体设计方案`；
- 用户自然语言中的不稳定称呼。

结论：

```text
可以先设计 space_classification 协议；
但不能贸然改 deliverable_id_generator_node 的 space_type 读取逻辑；
必须先采样清查 physical_context.space_type 的真实取值。
```

## 2. 参考意见采纳与修正

### 2.1 参考 1 应采纳的部分

参考 1 的价值在于把空间分类放进方案高参的完整生产链：

- 项目底盘；
- 动态问卷；
- 类型知识包 / ontology；
- 平面沙盘；
- 方案画布；
- 最终简报与交付命名。

这些应采纳。它提醒我们：空间分类不只是需求分析前置标签，而是会贯穿后续生产。

尤其值得采纳：

1. 渐进输入机制：不要要求用户一开始填完整分类信息。
2. 用户确认 / 修正入口：空间分类不是 AI 拍板，而是可解释候选。
3. 平面沙盘语义：项目类型决定同一个空间部位如何被理解。
4. 方案画布约束：不同类型有不同视觉误区，不应只生成氛围图。
5. 类型知识包结构：每个类型应有核心逻辑、典型张力、必需变量、问卷 profile、floorplan profile、visual profile、deliverable profile。

### 2.2 参考 1 需要降级的部分

参考 1 提到：

- 固定 60-80 个二级类型；
- 规则分类 + embedding matcher + LLM 分类融合；
- TypeRegistry / TypeDetector / BoundaryResolver / Governance 全套架构。

这些方向长期合理，但 MVP 不宜一次性上。

修正为：

```text
正式 active project_type 先控制在 30-50；
60-80 可以作为“类型知识包候选 / specialty tag / alias / 二期扩展池”，不能全部升正式类型。

MVP 先用现有 ProjectTypeDetector + rule enrichment；
embedding 和 LLM classifier 暂缓；
LLM 只作为高歧义裁决兜底，不做主分类器。
```

### 2.3 参考 2 应采纳的部分

参考 2 的价值在于工程风险意识更强，尤其是：

1. 命名空间不一致必须先处理。
2. 旧字段迁移不能凭感觉，`physical_context.space_type` 要采样清查。
3. 边界案例不是异常，而是主路径能力。
4. 混合权重不应凭空生成，首版可以 `weight_unknown`。
5. LLM 不应做主裁决，规则优先，LLM 兜底。
6. 要有 feature flag、双写、回滚和可观测性。
7. 不支持用户自定义正式类型，避免 ontology 失稳。

这些建议应进入执行路线。

### 2.4 参考 2 需要修正的部分

参考 2 存在几个不符合当前代码事实或执行上过重的点：

| 参考 2 观点 | 校验结果 | 处理 |
|---|---|---|
| `_type_registry.py` 是当前权威注册表 | 当前文件不存在 | 改为 `project_type_detector.py`，中期再抽 registry |
| 直接升级 `project_classification` 为 `ProjectClassification` | 当前字段曾被主链移除，下游临时兼容 | 短期新增 `space_classification`，不复活旧语义 |
| 分类核心采用四层，不含 `spatial_zones` | 判断成立 | 采用“四层 + spatial_zones 侧车” |
| Phase 0 完全不做协议升级 | 过于保守 | Phase 0 先冻结协议草案和映射，不接主链 |
| 类型总规模 30-50 | 合理 | 采纳为 active project_type 约束 |
| 双写 6 周 | 对轻量 MVP 偏长 | 作为生产迁移建议；本地验证可缩短，正式上线保留双写窗口 |

## 3. 冲突裁决

### 3.1 四层还是五层

主架构提出 5 层：

```text
父类桶 / 项目类型 / 专项标签 / 运行时变量 / 空间区域
```

参考 2 提出 4 层：

```text
父桶 / 主类型 / 标签 / 修饰项
```

裁决：

```text
采用“四层分类核心 + spatial_zones 关联对象”。
```

理由：

- 空间区域不是项目分类层，而是项目内部对象；
- `extracted_spatial_zones` 已经在当前 state 中存在，适合继续独立；
- 分类服务可以引用 `spatial_zones` 作为证据或 routing hint，但不应把它混入类型树；
- 这能同时保留主架构的空间部位隔离原则和参考 2 的层级治理清晰度。

### 3.2 `SpaceClassificationResult` 还是 `ProjectClassification`

参考 1 偏 `SpaceClassificationResult`。
参考 2 偏 `ProjectClassification`。
主架构偏 `space_classification`。

裁决：

```text
短期采用 SpaceClassificationResult，并写入 state.space_classification。
```

理由：

- 当前任务边界是“空间分类”，不是所有项目分类。
- `project_classification` 现有语义已经被注释为移除/兼容，直接复用风险高。
- `SpaceClassificationResult` 可以作为未来 `ProjectClassification` 的子对象或组成部分。

建议命名：

```yaml
space_classification:
  schema_version: "space_classification.v1"
  parent_type:
  primary_bucket:
  project_type:
  specialty_tags:
  secondary_types:
  runtime_modifiers:
  ambiguity:
  routing:
  evidence:
  freeze_state:
```

### 3.3 类型规模：60-80 还是 30-50

参考 1 建议 60-80 个二级类型。
参考 2 建议 30-50 个 active 类型。
当前代码已有约 30 多个 `project_type`。

裁决：

```text
正式 active project_type 控制在 30-50；
60-80 只作为“扩展候选池”，不一次性升为正式类型。
```

理由：

- 当前代码已经接近 30+，继续小幅补齐即可覆盖多数高频项目；
- 正式类型过多会导致 ontology、问卷、边界规则、few-shot 全线膨胀；
- 类型差异应优先进入 `specialty_tags` 和 `runtime_modifiers`。

### 3.4 是否立即做混合权重

主架构示例给出了 0.65 / 0.20 / 0.15。
参考 2 提醒权重不应凭空估。

裁决：

```text
首版支持 secondary_types，但 hybrid_weights 可以为空或标 weight_unknown。
```

可接受的首版结构：

```yaml
secondary_types:
  - type: tea_house
    role: supporting_function
    confidence: 0.72
    weight: null
    weight_status: unknown
```

到后期再按面积占比、营收占比、使用时长、用户确认等依据派生权重。

### 3.5 是否引入 LLM / embedding

参考 1 的架构中有 embedding matcher 和 LLM classifier。
参考 2 强调 LLM 只能兜底。

裁决：

```text
MVP 不引入 embedding matcher；
LLM 不做主分类器，只做高歧义边界裁决兜底，并且输出必须 schema 校验。
```

## 4. 合理化执行路线

### Phase 0：事实对齐与协议冻结

目标：先把语言和旧字段搞清楚，不改主链。

任务：

1. 建立 `TYPE_NAMING_MAP.md`
   - 对齐 06 初始清单、27 成立标准、28 边界案例、当前 `PROJECT_TYPE_REGISTRY`、`ontology.yaml`。
   - 明确当前代码 ID 是短期运行权威。

2. 建立 `space_classification_schema.md`
   - 冻结 `SpaceClassificationResult v1` 字段。
   - 明确四层分类核心与 `spatial_zones` 的关系。

3. 清查 `physical_context.space_type`
   - 至少采样 100 条真实或历史结构化数据；
   - 标注它到底是项目类型、空间区域、显示名、混合词还是未知；
   - 形成迁移策略。

4. 确认首批 active 类型
   - 不扩到 60-80；
   - 以现有 `PROJECT_TYPE_REGISTRY` 为基础；
   - 标记 alias、candidate、deprecated、active。

交付：

```text
TYPE_NAMING_MAP.md
space_classification_schema.md
space_type_field_audit.md
active_project_type_registry_v1.md
```

验收：

- 能解释每个现有 `project_type` 对应的父桶、ontology fallback、问卷 profile；
- 能明确哪些类型只是 alias 或 tag；
- 能明确 `space_type` 迁移风险等级。

### Phase 1：旁路分类服务 MVP

目标：不破坏主链，先生成统一分类结果。

任务：

1. 新增 `space_classification_service.py`。
2. 包装现有 `ProjectTypeDetector.detect_with_details()`。
3. 生成 `SpaceClassificationResult`：
   - `primary_bucket`
   - `project_type`
   - `specialty_tags`
   - `secondary_candidates`
   - `runtime_modifiers`
   - `ambiguity`
   - `routing`
   - `evidence`
4. 填充 `all_matches`，避免从 reason 字符串反解析次候选。
5. 首批接入 8 个高风险边界案例，但只做提示和澄清问题，不做强中断。
6. 保留旧 `project_type` 输出。

不做：

- 不改 deliverable 命名；
- 不重写问卷；
- 不新增大批类型；
- 不引入 embedding；
- 不让 LLM 做主分类。

验收：

- 20-50 条典型输入可输出稳定 schema；
- 类型枚举合法率 100%；
- 低置信度不会硬选而不标记；
- 边界案例能输出 `needs_clarification` 或 `boundary_risk`。

### Phase 2：状态双写与下游轻接入

目标：让新对象进入状态，但仍可回滚。

任务：

1. `state.py` 新增：

```python
space_classification: Optional[Dict[str, Any]]
```

2. requirements 主链写入：

```text
project_type 继续写
space_classification 新增写
project_classification 暂不作为新入口
```

3. `output_intent_detection.py` 优先读取 `space_classification`，无则回退 `project_type`。
4. `ontology_loader` 或调用层增加 `project_type_to_ontology` 映射。
5. `task_completeness_analyzer` 支持 `questionnaire_profile`，但保留旧 fallback。

暂缓：

- `deliverable_id_generator_node.py` 的 `space_type` 替换，必须等 Phase 0 的 `space_type_field_audit.md` 完成后再做。

验收：

- 新旧字段对齐率可检查；
- 没有 ontology 找不到导致的阻断错误；
- 无新字段时旧流程仍可运行；
- 可通过 feature flag 或配置回退到旧读取路径。

### Phase 3：下游真实消费

目标：让分类结果真正提升方案生产质量。

任务：

1. 问卷按 `questionnaire_profile` 动态补问。
2. 交付命名改用：

```text
routing.deliverable_label
→ physical_context.space_type
→ project_type_name
```

3. 类型知识包最小化建设：
   - 先做 `commercial_hospitality`
   - `healthcare_wellness`
   - `brand_experience`
   - `rural_construction`
   - `residential_renovation`
   - `commercial_office`
   - `commercial_retail`

4. 平面沙盘只消费：
   - `project_type`
   - `runtime_modifiers`
   - `extracted_spatial_zones`
   - 不把空间部位反写成项目类型。

5. 方案画布消费 visual prompt profile：
   - 类型误区；
   - 禁止偏差；
   - 类型特有视觉约束。

验收：

- 同一个项目在项目底盘、问卷、交付命名中分类一致；
- 民宿不会被生成成住宅客厅逻辑；
- 医疗康养不会只输出疗愈氛围；
- 品牌体验不会退化为普通陈列零售；
- 旧 `space_type` 不再主导整体项目命名。

### Phase 4：治理闭环与智能裁决

目标：把分类系统变成长期可维护基础设施。

任务：

1. 建立 `classification_error_cases.yaml`。
2. 建立新类型评审模板。
3. 为类型增加状态：

```text
active / candidate / alias_only / deprecated / merged
```

4. 对高歧义案例启用 LLM 兜底裁决。
5. 增加可观测指标：
   - 主类型准确率；
   - 用户修正率；
   - 边界触发率；
   - 下游重判率；
   - ontology fallback 率；
   - 交付命名回退率。

验收：

- 新类型不能绕过评审直接进入 active；
- 错判案例能回流规则；
- LLM 裁决失败时可降级为追问；
- 分类系统能解释“为什么这么判”和“如果判错会偏到哪里”。

## 7. 最终执行原则

这套空间分类系统的合理化推进，应遵循以下顺序：

```text
先对齐事实
再冻结协议
再旁路生成
再双写接入
再下游消费
最后智能裁决与治理闭环
```

一句话：

> 先把“类型不确定性、混合性、边界性、字段漂移”变成可表达、可回退、可追问的结构化协议，再让它逐步驱动项目底盘、问卷、本体、平面沙盘和方案画布。

这比单纯扩清单更稳，也比一口气重构全链路更现实。
