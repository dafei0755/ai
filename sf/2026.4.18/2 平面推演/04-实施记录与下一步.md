## 4. 当前可用路径

用户在平面推演界面：

```text
上传图纸
→ 生成 FloorPlanIR 候选或保留手动底盘
→ 点击“新建推演”
→ 前端组装 SPG + FloorPlanFacts
→ 后端生成 3 个 LayoutVariant
→ 前端展示方案卡片与空间块覆盖层
→ 用户可选择版本、冻结版本、回写底盘、注入高参
```

## 5. 当前限制

### 5.1 几何仍是粗块

当前 `LayoutIR.spaces` 是 0-1 归一化矩形块，不是墙线、门洞、家具级平面。

这是刻意设计：

```text
先验证多版本选择与高参解释闭环，
再做更高精度的局部几何生成。
```

### 5.2 SPG 是前端临时组装

当前 `buildSandboxSpgPayload()` 根据 activeSpace 临时组装空间清单。

后续应接入真实项目底盘：

```text
AlignedBrief
SPG
用户问卷
项目类型
预算和约束
```

### 5.3 FloorPlanFacts 映射仍轻量

当前 `buildSandboxFactsPayload()` 从前端候选元素抽取墙、柱、门、窗。

后续应由几何编译器直接输出：

```text
CarrierIR / FloorPlanFacts
```

避免前端二次拼装事实。

### 5.4 暂未支持自然语言指令推演

当前支持“生成版本”，尚未支持：

```text
把客厅放大
减少走廊
保留 A 的公共区
融合 B 的私密性
老人房靠近卫生间
```

下一步需要把自然语言解析为 `LayoutOperation`。

## 6. 下一步路线

### P0：前端体验闭环

目标：

```text
用户能稳定看见多版本、选版本、冻结版本、回写底盘。
```

任务：

```text
给 LayoutVariant 加专门的视觉图例
版本卡片显示评分差异
冻结版本时同步 LayoutVersionGraph 状态
回写底盘时带上 layout_id / strategy / risks / score
```

### P1：从几何编译输出 Carrier Facts

目标：

```text
route.ts 的编译结果不只返回 draftFloorPlanIR，
还返回可直接推演的 FloorPlanFacts。
```

任务：

```text
提取外轮廓、柱、核心筒、入口、窗面、不可动墙
输出 confidence 与 review_flags
formalPromotionAllowed=false 时也允许 carrier_ready
```

### P2：用户指令推演

目标：

```text
自然语言 → LayoutOperation → 局部重生成 → Diff + 高参解释
```

优先支持：

```text
lock_space
resize_space
move_space
merge_strategy
reduce_corridor
increase_privacy
improve_view
reduce_cost
```

### P3：知识底盘和硅基分身注入

目标：

```text
让多版本不只是几何采样，而是带平台经验和用户偏好。
```

输入：

```text
项目类型方法论
历史案例
用户偏好
设计师硅基分身
被选择/被否定的版本记录
```

输出：

```text
更贴近用户和项目类型的 DesignIntentSet
```

### P4：求解器升级

触发条件：

```text
用户开始依赖自动生成版本
粗块布局不能满足真实评审
需要面积、邻接、动线、采光更稳定
```

可选路线：

```text
规则模板 + 局部搜索
BSP / 网格切分
constraint propagation
OR-Tools / mixed integer programming
```

暂不建议过早引入重型求解器。

## 7. 验收标准

短期验收：

```text
用户点击一次“新建推演”能看到 3 个策略不同版本
画布上出现对应空间块覆盖层
版本卡片有不同命名、摘要、评分和风险
冻结/回写/注入高参仍可用
前端类型检查通过
后端单元测试通过
```

中期验收：

```text
用户能用自然语言修改版本
系统能解释修改影响
系统能记录版本分叉
系统能把最终版本回写项目底盘和方案画布
```

长期验收：

```text
系统能根据用户历史偏好和项目类型，
自动生成更符合其判断习惯的初始多版本。
```
