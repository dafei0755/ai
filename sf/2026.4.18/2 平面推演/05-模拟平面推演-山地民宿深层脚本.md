# 05 模拟平面推演：山地民宿深层脚本

版本：v0.1  
日期：2026-04-30  
定位：产品体验脚本 + 工程机制校验 + 风险门禁说明

## 0. 脚本目标

本文不是展示“AI 自动画平面图”，而是模拟用户如何在平面推演系统中完成一次真实的空间价值取舍。

重点验证：

```text
1. 用户是否始终保有主导权。
2. 系统是否能提出多个空间判断，而不是一个所谓最优解。
3. 图纸事实、布局提案、经营假设是否被清楚区分。
4. 用户指令是否能转成可追踪的 LayoutOperation。
5. 每次推演是否有 Diff、风险、替代方案和来源链。
6. 冻结版本是否形成决策档案和平台沉淀。
```

核心提醒：

```text
好的平面推演不应过于顺滑。
真实设计过程一定包含误解、犹豫、反悔、冲突和重新确认。
系统的高参感，恰恰体现在它能把这些摩擦变成可判断的信息。
```

# 二、Step 0：项目快检

## 系统输出

```text
在生成平面版本前，我先做一次项目快检。

项目类型：山地民宿改造
建筑面积：约 800㎡
目标客房：12 间
核心诉求：记忆点大堂 / 景观公区 / 客房看山 / 预算控制 / 后勤分流

初步判断：
12 间客房具备可行性，但会在三个目标之间产生冲突：

1. 景观公区越强，客房看山率可能下降。
2. 后勤越隐蔽，运营面积和动线成本越高。
3. 低改造越强，入口首感和空间记忆点越受限制。

我不会先给一个最优方案，而会先生成几种取舍方向。
```

## 面积快检

```text
总建筑面积：约 800㎡
目标客房数：12 间
平均建筑面积：约 66.7㎡ / 间

但这不是净客房面积。
扣除大堂、公区、走廊、后勤、设备、墙体后：
可用于客房的面积可能约 420–520㎡。

预计平均客房建筑分摊面积：
约 35–43㎡ / 间。

初步判断：
12 间客房可行，但如果景观公区过强，客房面积或客房看山率会被压缩。
```

## 当前形成的产品价值

这一段让用户感受到：

```text
系统不是在急着画图，而是在判断项目是否成立。
```

这也是平面推演区别于普通绘图工具的第一步。

# 五、Step 3：生成多策略版本

系统生成四个民宿语境版本。

如果 Phase 0 只能支持三版，可先生成 A/B/C；但完整产品应支持 D。

## A · 低改造稳妥版

关键词：

```text
少拆改 / 快落地 / 低风险
```

系统解释：

```text
这一版优先保留原有结构和空间秩序。
大堂、接待、公区基本沿原入口组织。
客房沿既有分隔逻辑展开，减少大范围重排。
```

适合：

```text
预算严格
工期紧
业主更重视稳妥落地
```

主要代价：

```text
到达首感弱
传播记忆点不足
景观公区不够强
```

主导角色：

```text
实施边界 + 风险总控
```

角色语言：

```text
实施边界：A 版优先减少拆除动作，当前不把疑似不可动墙作为可拆对象。
风险总控：这版最稳，但对品牌溢价的帮助有限。
```

## B · 运营效率优先版

关键词：

```text
客房管理 / 后勤分流 / 清扫效率
```

系统解释：

```text
这一版优先优化后期运营。
服务台、备品、清扫、补给路径被重新组织。
客人动线和服务动线尽量分离。
```

适合：

```text
长期运营
团队管理复杂
重视复购和服务稳定性
```

主要代价：

```text
度假松弛感偏弱
公共区记忆点不如 C
空间表达更理性
```

主导角色：

```text
商业运营 + 用户研究
```

角色语言：

```text
商业运营：B 版的重点不是好看，而是减少三个月后运营爆雷。
用户研究：客人未必会记住动线效率，但会感受到服务动作是否打扰。
```

## C · 景观记忆点强化版

关键词：

```text
到达首感 / 山景公区 / 传播价值
```

系统解释：

```text
这一版优先强化入口到景观公区的记忆点。
入口进入后先经过一个压缩空间，再释放到面向山景的公共核心。
```

主要优势：

```text
第一眼更有记忆点
适合拍照传播
更适合高客单价民宿
景观公区成为品牌核心节点
```

核心风险：

```text
景观公区越强，越可能挤压客房看山率。
如果项目主要依赖高客单价客房收益，需要确认：
公共区传播价值是否足以补偿部分客房景观资源的让渡。
```

主导角色：

```text
品牌总监 + 用户研究
```

角色语言：

```text
品牌总监：C 版的入口压缩到景观释放，是最容易形成传播记忆的空间结构。
风险总控：但这版会和“客房尽量看山”发生资源争夺，不能只看公区好不好看。
```

## D · 客房看山率优先版

关键词：

```text
房价溢价 / 客房体验 / 复购舒适
```

系统解释：

```text
这一版优先把山景资源分配给客房。
公区保持必要记忆点，但不占用最多景观面。
客房朝向、开窗、停留面成为核心。
```

适合：

```text
客房单价驱动
强调住中体验
复购和口碑优先
```

主要代价：

```text
大堂和公区传播性弱于 C
到达首感没有 C 强
公共空间更克制
```

主导角色：

```text
用户研究 + 商业运营
```

# 六、民宿专属指标

每个版本不只显示通用分数，还显示民宿指标。

## 通用指标

```text
改造友好度
运营效率
施工风险
项目匹配度
预算可控性
```

## 民宿指标

```text
客房数量满足率
客房看山率
景观公区强度
到达首感
传播记忆点
后勤低干扰
复购舒适度
淡旺季运营弹性
```

## 指标表达原则

优先使用区间、等级和依据，避免虚假精度。

例如：

```text
客房数量满足率：12/12，满足
客房看山率：中高，约 8–10 间具备有效山景面
景观公区强度：高，公区占用主要南侧景观面
改造友好度：中低，涉及公共区重构
后勤低干扰：中，依赖侧入口是否可用
```

如果必须显示数字，必须提供来源说明。

# 七、Step 4：用户选择倾向，但系统先澄清

用户说：

```text
我喜欢 C 的景观公区，但担心成本太高。
能不能保留 C 的公共区，同时用 A 的低改造逻辑控制预算？
```

## 错误做法

系统不应立刻生成融合版。

因为“保留 C 的公共区”至少有四种含义：

```text
1. 保留位置
2. 保留面积
3. 保留视野朝向
4. 保留压缩前场 → 景观释放的空间序列
```

这四种含义的成本差异很大。

## 正确做法：反诘者介入

```text
你说“保留 C 的公共区”，我想确认你更想保留哪一层：

1. 位置：仍在南面，但内部布局可以调整。
2. 视野：山景资源仍优先给公区。
3. 空间序列：保留“压缩前场 → 景观释放”的体验节奏。
4. 面积：保持 C 版公区规模。

这四层的拆改强度不同，空间序列和面积保留的成本最高。
你希望保留哪几层？
```

用户回答：

```text
保留视野和空间序列，但面积可以收一点。
```

系统记录：

```json
{
  "operation": "merge_strategy",
  "source_layouts": ["C", "A"],
  "keep": [
    "C.public_core_view_orientation",
    "C.arrival_compression_release_sequence"
  ],
  "relax": [
    "C.public_core_area"
  ],
  "regenerate": [
    "guestroom_zone",
    "service_path",
    "transition_zone"
  ],
  "priority": "high"
}
```

# 八、Step 5：生成融合版并显示 Diff

系统生成：

```text
C-1 · 景观公区保留 + 低改造收敛版
```

## 系统解释

```text
这一版保留 C 的核心体验：
入口压缩后释放到山景公区。

但不完整保留 C 的公区面积。
系统压缩了公区规模，把部分景观资源回让给客房，
并尽量沿原墙体组织客房区，降低拆改强度。
```

## Diff 展示规则

画布上必须显示：

```text
绿色描边：保留空间块
蓝色描边：调整空间块
橙色填充：被压缩区域
虚线：改变后的动线
红色警示：风险区域
```

如果没有可视 Diff，用户会怀疑融合版只是文案变化。

## 指标变化

使用“区间 + 依据”表达：

```text
景观公区强度：高 → 中高
依据：公区仍占南侧景观面，但面积收敛。

客房看山率：中 → 中高
依据：部分南侧景观面回让给客房。

客房数量满足率：12/12，保持。

改造友好度：中低 → 中高
依据：客房区尽量沿原隔墙组织。

后勤低干扰：中，待侧入口确认。

传播记忆点：高 → 中高
依据：保留入口序列，但公区尺度降低。
```

# 九、Step 6：用户指令推演

用户说：

```text
后勤不要穿过大堂，清扫车不能和客人迎面撞上。
```

## 指令解析

```json
{
  "operation": "separate_flow",
  "target": "service_path",
  "avoid": "guest_arrival_path",
  "priority": "hard",
  "raw_instruction": "后勤不要穿过大堂，清扫车不能和客人迎面撞上。"
```

## 系统不直接承诺

系统先检查：

```text
当前图纸未稳定确认独立后勤入口。
侧入口置信度 0.58，不能直接作为硬事实。
```

## 系统输出替代路径

```text
可选处理：

1. 使用侧入口作为低干扰后勤入口，但需现场确认。
2. 设置分时后勤策略，避开入住高峰。
3. 在大堂背侧增加隐蔽服务通道。
4. 保留局部交叉，但通过屏风、墙体、备品节点降低可见度。
```

用户选择：

```text
先按侧入口可用来推，但标记为待现场确认。
```

系统生成：

```text
C-1-1 · 侧入口后勤分流版
```

## 影响说明

```text
后勤低干扰：中 → 中高
运营效率：中高 → 中
施工风险：中 → 中高

主要变化：
- 服务路径绕开大堂正面。
- 清扫路径增加。
- 备品间位置需要靠近侧入口。
- 侧入口可用性成为下一步现场复核点。
```

# 十、Step 7：系统反诘升级为商业模式确认

系统不只问“体验还是效率”，而是问更上游的问题。

```text
这里不是单纯的动线问题，而是民宿经营取向问题。

如果选择“客人完全无感知”，
空间会更高级，但后勤面积和路径成本会上升。

如果选择“运营效率优先”，
员工管理更轻，但客人在部分节点可能感知到服务动作。

如果选择“两者折中”，
系统会采用“低感知后勤”策略：
不追求完全隐藏，而是避免正面冲突、降低视觉暴露、控制交叉时段。

在继续前，我想确认这个项目最不能接受的失败是哪一种：

1. 客人觉得不像精品民宿，传播失败。
2. 运营成本超预算，三年内难回本。
3. 员工路径太累，服务质量下降。
4. 缺少记忆点，房价撑不起来。
```

用户回答：

```text
最不能接受的是不像精品民宿，但运营也不能太重。
```

系统记录：

```json
{
  "business_assumption_update": {
    "primary_failure_to_avoid": "weak_boutique_guest_perception",
    "secondary_failure_to_avoid": "operation_overload",
    "service_strategy": "low_perception_not_full_invisible"
  }
}
```

系统生成：

```text
C-1-2 · 景观公区强化 + 低改造 + 低感知后勤版
```

# 十一、Step 8：系统必须能反对用户

真实场景中，用户可能继续说：

```text
那能不能做到 15 间客房？
```

系统不应顺从生成。

## 系统反对

```text
我不建议直接把目标改为 15 间。

按 800㎡ 总面积估算，
15 间会把平均建筑分摊压到约 28–34㎡ / 间。

如果同时保留景观公区、低感知后勤和精品民宿定位，
15 间会带来三个风险：

1. 客房面积跌出高客单价预期。
2. 客房看山率下降。
3. 后勤和走廊占比被进一步压缩，运营压力变高。

如果你坚持 15 间，我可以生成“高房量压力测试版”，
但我会把它标记为收益假设待验证，而不是推荐方案。
```

## 可选分支

```text
继续 12 间深化
生成 15 间压力测试版
生成 13–14 间折中版
回到项目底盘修改经营假设
```

这一步体现系统不是高级助手，而是高参。

# 十四、异常用户行为处理

## 1. 用户拒绝所有版本

用户说：

```text
这几个都不喜欢，再给我三个。
```

系统不应随机再生成。

应反问：

```text
我需要知道你不喜欢的是哪一类问题：

1. 都太保守
2. 都太激进
3. 公区不够有记忆点
4. 客房收益感不够
5. 后勤考虑太重
6. 不是我想要的民宿气质
```

用户回答后，再生成反向或补充版本。

## 2. 用户中途换项目定位

用户说：

```text
我想想，还是做亲子家庭客群比较稳。
```

系统应判断为上游变化：

```text
这会改变 SPG 和经营假设。
当前版本不应直接继续推演，而应标记为“前提失效”，回到项目底盘更新客群。
```

## 3. 用户加入新功能

用户说：

```text
顺便加一个温泉区。
```

系统不应直接塞进平面。

应问：

```text
温泉区是住客专属，还是对外售票？
面积预算是多少？
是否牺牲客房数量？
是否需要独立更衣和设备空间？
```

然后回到项目底盘更新 SPG。

## 4. 用户问为什么

用户问：

```text
为什么 C 版公区要放南面？
```

系统必须给来源链：

```text
因为：
1. 图纸事实：南侧连续窗面被识别为主要山景面。
2. 用户目标：你强调有记忆点的大堂和景观公区。
3. 项目类型：山地民宿的溢价型策略通常需要一个公共传播节点。
4. 策略取舍：C 版优先把景观资源给公共记忆点，而 D 版则优先给客房。

所以 C 版把公区放南面。
这不是唯一正确答案，只是“景观记忆点强化”这个假设下的布局选择。
```

# 十五、产品机制总结

这个模拟流程最终要让用户感受到：

```text
系统不是替我画了一张平面，
而是把“我要做什么样的民宿”这件事，
拆成了空间、经营、景观、预算、后勤之间的可选择关系。
```

## 必须保留的机制

```text
项目快检
基线复核卡
多策略版本
行业指标
用户意图澄清
视觉 Diff
系统反对
商业模式反诘
结构化冻结
硅基分身学习记录
SourceTrace 来源链
```

## Demo 不应误导用户

必须明确：

```text
当前是策略推演层，不是正式施工图。
疑似不可动墙需要复核。
数值为估算或相对排序，不是假装精确计算。
融合版本必须有可见 Diff。
```
