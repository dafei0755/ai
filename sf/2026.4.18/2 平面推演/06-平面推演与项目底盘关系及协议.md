# 06 平面推演与项目底盘关系及协议

版本：v0.2  
日期：2026-04-30  
定位：项目底盘模块与平面推演模块的关系定义、接口协议与执行规则

## 1. 核心裁决

项目底盘和平面推演不是简单的前后串行关系。

从方法论上看，项目底盘应该先于平面推演，因为项目底盘负责回答：

```text
这个项目是什么？
为什么做？
服务谁？
靠什么成立？
预算和边界是什么？
核心判断是什么？
```

平面推演负责回答：

```text
在这些定位、目标、约束和图纸事实下，
空间可以如何组织？
有哪些成立版本？
每个版本牺牲什么？
用户如何选择、融合和继续推演？
```

但真实用户经常不会按理想链路进入。

他可能直接说：

```text
这是我的民宿平面图，你帮我看看怎么改。
```

或者：

```text
先别问那么多，我就想看这个平面能不能做。
```

因此系统不能把项目底盘理解成“必须先填完的表单”。

更准确的关系是：

```text
项目底盘是判断母体；
平面推演是空间验证场和生成场；
图纸基线是事实约束；
用户选择是底盘进化证据。
```

最终裁决：

```text
方法论顺序：项目底盘 → 平面推演
真实入口：图纸 / 对话 / 底盘 都可以触发平面推演
治理顺序：最终判断必须回到项目底盘确认
```

一句话：

```text
项目底盘不是平面推演的单次前置表单，
而是与平面推演共同演化的 ProjectContext。
```

## 2. 为什么不能强制完整底盘先行

### 2.1 图纸先到手

设计师拿到甲方发来的 PDF / CAD，第一反应往往是看图、读结构、判断空间可能性。

这是设计工作的真实习惯，不是方法论缺失。

如果系统强制用户先填完整项目底盘，会打断工作节奏。

### 2.2 从空间反推商业

有些项目不是先有完整定位，而是先看到建筑条件：

```text
这个建筑南面采光好，但有 3 根柱子挡着。
这个空间适合做什么？
能不能做民宿？
能不能做 12 间客房？
```

这时平面不是项目底盘的输出，而是项目判断的输入。

### 2.3 业主带半成型判断进来

用户可能已经说：

```text
我想做民宿，12 间房，预算 200 万，平面图在这里。
```

这些信息已经构成底盘核心字段，但并没有结构化。

系统应快速承接，而不是要求用户重新填表。

## 3. 基本原则

平面推演不应强制等待完整项目底盘，但必须区分不同推演状态。

系统不能因为项目底盘不完整就拒绝用户开始，也不能在底盘缺失时假装已经理解项目定位。

正确原则是：

```text
允许从图纸直接进入；
但所有超出图纸事实的判断都必须标注为假设；
推演过程中形成的定位、目标、偏好和风险，应反向沉淀为项目底盘草稿或补丁；
项目底盘仍是正式真相源，补丁必须经用户确认后才能升版。
```

也就是：

```text
项目底盘是正式真相源。
平面推演可以作为项目底盘的反向生成器。
```

## 4. ProjectContext：活的项目认知状态

建议在 `AlignedBrief` 与平面推演之间引入 `ProjectContext`。

区别：

```text
AlignedBrief / FrozenProjectBase 是阶段性结晶产物。
ProjectContext 是活的项目认知状态。
```

`ProjectContext` 不要求完整，可以随推演持续演化。

示例：

```json
{
  "context_id": "pc-001",
  "completeness_level": "L1",
  "fields": {
    "project_archetype": "mountain_homestay",
    "gross_area_m2": 800,
    "target_room_count": 12,
    "profit_model": null,
    "target_customer": null,
    "budget_tolerance": "medium",
    "operation_model": null
  },
  "source_trace": {
    "project_archetype": {
      "source": "user_explicit",
      "confidence": 1.0
    },
    "gross_area_m2": {
      "source": "user_explicit",
      "confidence": 0.9
    },
    "budget_tolerance": {
      "source": "inferred_from_user_phrase",
      "confidence": 0.55
    }
  },
  "pending_questions": [
    "target_customer",
    "profit_model",
    "operation_model"
  ],
  "inferred_assumptions": [
    {
      "field": "profit_model",
      "value": "premium",
      "confidence": 0.6,
      "requires_confirmation": true
    }
  ]
}
```

核心要求：

```text
不能把系统推测写成用户确认。
不能把图纸疑似事实写成硬约束。
不能把轻底盘推演包装成正式判断。
```

## 5. 底盘完备度分层

底盘不应是“有 / 没有”，而应是逐步成熟。

### L0：无底盘

已有：

```text
图纸或一句问题
```

允许：

```text
图纸基线识别
空间事实摘要
明显风险提示
中性空间可能性
```

不允许：

```text
强项目推荐
项目匹配度判断
正式方案冻结
方案画布正式回写
```

### L1：轻底盘

已有：

```text
项目类型
大致面积
主要目标
少量硬约束
```

允许：

```text
多版本粗推演
策略差异说明
关键风险提示
初步评分
```

要求：

```text
必须标注哪些判断是系统假设。
```

### L2：可用底盘

已有：

```text
客群
预算
运营目标
功能约束
空间优先级
风险偏好
```

允许：

```text
正式多版本推演
DesignConstraintGraph 编译
用户指令推演
版本对比
高参反诘
底盘回查
```

### L3：冻结底盘

已有：

```text
关键项目判断已确认
平面版本已冻结
底盘补丁已确认
风险已记录
```

允许：

```text
正式回写方案画布
生成汇报骨架
进入效果图 / 材料 / 概念深化
沉淀到项目记忆和硅基分身
```

## 6. 四种入口路径

### 6.1 路径 A：项目底盘先行

链路：

```text
用户描述项目
→ ProjectContext 达到 L1 / L2
→ 上传图纸或人工绘制
→ FloorPlanFacts
→ DesignConstraintGraph
→ LayoutVariant
```

系统行为：

```text
直接使用底盘字段选择策略池
版本解释引用底盘来源
若推演发现矛盾，触发底盘回查
```

示例语言：

```text
我会基于你已确认的项目底盘进行推演：
定位为高客单山地民宿，12 间客房为硬目标，
优先平衡景观记忆点、客房看山率和低改造成本。
```

### 6.2 路径 B：图纸先行

链路：

```text
用户上传图纸
→ FloorPlanFacts
→ ProjectSeed
→ 底盘缺口卡
→ 用户回答 1-3 个关键问题
→ Light ProjectContext
→ Exploratory LayoutVariant
```

系统行为：

```text
不阻断用户
不假装理解完整项目
显式展示临时假设
只进入轻推演
```

轻问询示例：

```text
在生成版本前，我需要先确认三件事，很快：

1. 这是什么类型的项目？民宿 / 餐饮 / 办公 / 零售 / 其他
2. 你更偏高端品牌、效率运营，还是还没定？
3. 你最在意什么？一句话即可。
```

### 6.3 路径 C：对话先行

链路：

```text
用户先提问题
→ ProjectSeed
→ 请求图纸或补关键事实
→ Light ProjectContext
→ 平面推演
```

示例：

```text
用户：800㎡ 山地民宿做 12 间客房合理吗？
系统：可以先做面积与经营快检。如果你有平面图，我可以进一步判断客房看山率和后勤分流。
```

### 6.4 路径 D：中途变更

用户中途改变客群、预算、房间数或定位。

系统不能立刻覆盖原版本，应先显化影响：

```text
这个调整会改变当前版本的根本逻辑：
- 客房面积分配
- 公区强度
- 后勤路径
- 预算风险

你希望：
1. 完全重新生成
2. 在当前版本上局部调整
3. 保留当前版本，开第二条分支
4. 先回到底盘把这个变化确认
```

## 7. 图纸先行时的轻底盘机制

当用户直接从平面进入时，系统不应阻断，也不应直接进入正式判断。

应生成一张“底盘缺口卡”或“最小项目假设卡”。

示例：

```text
当前可推演，但底盘不完整。

已知：
- 项目类型：山地民宿
- 面积：约 800㎡
- 目标：12 间客房
- 诉求：景观公区、预算控制、后勤分流

缺口：
- 目标客群未知
- 客单价定位未知
- 改造预算上限未知
- 运营模型未知
- 景观优先级未确认

系统处理：
- 先生成 3 个方向
- 所有结果标注为“轻底盘推演”
- 关键假设将在版本卡片中展示
```

这张卡的作用不是增加流程负担，而是防止系统把未经确认的判断包装成结论。

用户可以选择：

```text
1. 接受这些假设，先进入粗推演
2. 修改关键假设
3. 先只看图纸问题，不生成方案
```

## 8. 假设链展示规范

每个 `LayoutVariant` 应显示它依赖的假设链。

示例：

```text
基于这些假设：
✓ 民宿：用户确认
◇ 800㎡ 山地建筑：用户输入 + 图纸读取
⚠ 溢价型：系统推测，置信度 60%
⚠ 周末度假客群：系统推测，置信度 50%
⚠ 中等预算容忍度：从“预算不能太失控”推测

[这些假设有问题？告诉我]
```

符号规则：

```text
✓ 用户确认
◇ 图纸事实
⚠ 系统推测
? 尚未确认
```

要求：

```text
假设链必须出现在版本解释或版本卡片中。
用户修改假设时，应更新 ProjectContext。
推演版本需要记录当时绑定的 ProjectContext 版本。
```

## 9. 底盘回查触发条件

平面推演过程中出现以下情况，应触发底盘回查。

### 9.1 用户反复否定同类风险

例如用户连续否定高拆改、高预算、高施工风险。

系统提示：

```text
我注意到你反复拒绝“高拆改成本”风险。
这意味着预算约束可能比我原先假设更严格。
要不要更新项目底盘里的“预算严格度”？
```

### 9.2 用户补充上游定位

例如：

```text
其实这个项目主要做亲子家庭。
```

系统提示：

```text
这会影响当前平面版本的根本逻辑。
是否更新项目底盘并重新生成相关版本？
```

### 9.3 底盘与图纸矛盾

例如底盘说：

```text
6 间精品客房
```

但图纸面积显示：

```text
1200㎡，按民宿密度可做 18-25 间。
```

系统提示：

```text
你的底盘目标和图纸容量存在明显差异。

你是要：
1. 保持 6 间，做超宽松精品房
2. 调整到 12-15 间，接近标准密度
3. 重新评估项目是否不只是民宿
```

### 9.4 用户要求新增大功能

例如：

```text
顺便加一个温泉区。
```

系统应回到底盘确认：

```text
温泉区会改变功能结构和经营模型。
它是住客专属，还是对外售票？
是否牺牲客房数量？
是否需要独立更衣和设备空间？
```

## 10. 平面推演反向回填项目底盘

很多时候，用户一开始并不知道自己项目定位。

他可能通过看版本，才意识到：

```text
我其实更在意客房溢价。
我不是要极致传播，我要稳妥运营。
我愿意为景观公区多花钱。
我不愿意动结构。
我接受后勤低感知，但不接受完全隐藏导致运营成本过高。
```

这些判断虽然发生在平面推演中，但它们不属于平面推演本身。

它们应该被回写到项目底盘。

回写内容包括：

```text
项目定位
经营假设
用户优先级
风险容忍度
功能目标
空间策略
被否定方向
关键约束
```

### 10.1 BriefBackfillEvent

```json
{
  "event_id": "backfill-001",
  "source": "plan_sandbox",
  "source_version_id": "C-1-2",
  "trigger": "freeze_layout_version",
  "backfilled_fields": {
    "project_positioning": "景观记忆点驱动的中高端山地民宿",
    "layout_strategy": "景观公区核心 + 低改造收敛 + 后勤低干扰",
    "budget_attitude": "中等改造强度",
    "operation_priority": "客人低感知后勤"
  },
  "evidence": [
    "selected_C_public_view_core",
    "rejected_A_weak_memory_point",
    "rejected_C_cost_risk_high",
    "accepted_low_perception_service_flow"
  ],
  "requires_user_confirmation": true
}
```

### 10.2 ProjectBasePatch

```json
{
  "patch_id": "pbp-001",
  "source": "plan_sandbox",
  "source_layout_version": "C-1-2",
  "confidence": 0.78,
  "patch_type": "positioning_and_priority",
  "changes": {
    "positioning": "high_value_mountain_homestay",
    "risk_tolerance": "medium",
    "priority": [
      "arrival_memory",
      "public_view_core",
      "room_experience",
      "cost_control"
    ],
    "service_strategy": "low_perception_not_full_invisible"
  },
  "scope": "current_project",
  "requires_user_confirmation": true
}
```

规则：

```text
ProjectBasePatch 不能静默写入正式底盘。
必须经用户确认。
用户可选择：写入本项目 / 写入长期偏好 / 不写入。
```

## 11. 权限边界：谁是正式真相源

必须明确：

```text
项目底盘是正式真相源。
平面推演是空间验证与策略生成场。
```

平面推演可以产生项目底盘补丁，但不能直接静默覆盖项目底盘。

正确流程：

```text
平面推演产生 ProjectBasePatch
→ 用户确认
→ 项目底盘升级版本
→ 平面推演绑定新的底盘版本继续工作
```

例如：

```text
平面推演发现用户更偏向“有记忆点但成本可控”。
系统不能直接改项目底盘。
它应提示：

“是否把本次选择沉淀为项目底盘偏好？
偏好：有记忆点但成本可控。
适用范围：本项目 / 长期硅基分身 / 不沉淀。”
```

## 12. 冻结时同步检查

每次冻结平面版本时，系统必须执行底盘同步检查。

示例：

```text
平面版本已冻结：C-1-2 · 景观公区强化 + 低改造 + 低感知后勤版

我从这次推演里学到了几件关于这个项目的事：
- 你倾向于“有记忆点但不极端”
- 拆改成本是核心约束
- 后勤要低感知，但不追求完全隐藏
- 12 间客房是硬目标

是否写入项目底盘？

[同步到底盘] [仅本次有效] [先不同步]
```

冻结后：

```text
如果同步到底盘：ProjectContext 升级并生成新版本号。
如果仅本次有效：记录在 LayoutVersionGraph，不更新底盘。
如果不同步：保留为 rejected backfill suggestion。
```

## 13. 推演状态

### 13.1 Exploratory

探索态。

条件：

```text
缺少完整项目底盘
用户直接从图纸开始
关键经营假设未确认
```

系统行为：

```text
可以生成粗版本
必须标注假设
不输出强推荐
不冻结正式策略
可以生成项目底盘草稿
```

### 13.2 Anchored

锚定态。

条件：

```text
已有项目底盘
核心定位、客群、预算、功能目标已确认
```

系统行为：

```text
可以生成策略版本
可以做方案比较
可以提出高参反诘
可以回写方案画布
```

### 13.3 Committed

冻结态。

条件：

```text
用户选择并冻结某一版本
项目底盘补丁已确认
关键风险已记录
```

系统行为：

```text
生成正式决策档案
回写项目底盘
发往方案画布
进入后续深化
```

## 14. UI 协议

平面推演界面必须显示：

```text
项目底盘完备度
当前推演模式
是否绑定 ProjectContext
假设链
底盘缺口卡
回写底盘按钮
底盘补丁预览
```

建议常驻指示：

```text
项目底盘：L1 轻底盘  ●●○○  [展开补全]
推演状态：Exploratory
```

状态颜色建议：

```text
L0 红色：仅可事实识别
L1 黄色：可粗推演
L2 绿色：可正式推演
L3 蓝色：已冻结，可下游输出
```

图纸先行时的界面提示：

```text
你现在是从图纸直接开始。
我可以先做空间粗推演，但项目定位、预算、客群和运营模型仍是临时假设。
我会把这些假设显式列出，后续由你确认是否写入项目底盘。
```

## 15. 后端协议

后端应新增或预留以下对象：

```text
ProjectContext
ProjectSeed
BriefGap
AssumptionRegister
BriefBackfillEvent
ProjectBasePatch
```

建议新增桥接服务：

```text
ProjectBriefBridge
```

职责：

```text
ProjectSeed / ProjectContext / 用户补充
→ LightProjectBrief
→ SpatialProgramGraph
→ DesignConstraintGraph
```

这样 `generate-variants` 不再长期依赖前端临时拼 SPG，而是逐步接入真实项目底盘。

短期可行改造：

```text
1. 前端新增 PlanSandboxMode 状态。
2. generate-variants 请求体增加 project_context 可选字段。
3. 后端响应增加 assumption_register / brief_gap。
4. 冻结版本时生成 ProjectBasePatch preview。
5. 用户确认后写入项目底盘存储。
```

## 16. 高参语言协议

高参解释必须知道当前底盘成熟度。

### L0 / Exploratory

语言风格：

```text
多用“假设”“可能”“建议确认”。
少用强推荐。
```

禁止：

```text
宣布最优方案
冻结正式判断
输出施工级建议
```

### L1 / Light Brief

语言风格：

```text
可以生成方向，但要持续暴露假设。
```

示例：

```text
如果按“中高客单山地民宿”这个临时假设，C 版更能建立传播记忆点。
但如果你其实更重视复购舒适，D 版会更值得展开。
```

### L2 / Anchored

语言风格：

```text
可以明确比较和建议。
```

示例：

```text
基于你已确认的精品托管运营和 12 间客房目标，我建议优先比较 C-1 与 D。
```

### L3 / Committed

语言风格：

```text
输出决策档案、风险监控和下游任务。
```

## 18. 最终规则

系统规则应固定为：

```text
没有项目底盘，也允许进入平面推演；
但只能进入轻推演模式。

轻推演模式可以生成可能性；
不能做最终判断。

用户选择、否定、修改、冻结的过程，
必须反向回填项目底盘。

项目底盘成熟后，
平面推演才能进入正式冻结和方案画布输出。
```

最终表达：

```text
系统允许用户从图纸开始，
但会自动生成轻项目底盘；
允许先推演，
但会把每次选择、否定和修改回填为项目判断；
最终冻结的不是一张平面，
而是一套经过空间验证的项目底盘。
```
