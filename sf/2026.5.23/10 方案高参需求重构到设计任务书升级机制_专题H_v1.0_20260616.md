# 专题 H：需求重构到设计任务书的升级机制

版本：v1.0
日期：2026-06-16
定位：方案高参第一阶段产品定义与开发纲领

---

## 0. 定盘判断

方案高参第一阶段只对外售卖一个核心产品：

> 设计任务书 2.0

“需求重构”是替代原入口概念后的统一名称，前台阶段应定义为：

> 需求重构

需求重构不是第二产品，也不是普通问答。它是设计任务书的购买前理解力证明形态，也是设计任务书生成前的需求预结构层。

它的作用不是给用户一个完整答案，而是在付费前把用户的模糊表达重构成一张“行动蓝图”，让用户看到系统是否真正读懂了他的真实需求。

核心边界：

> 需求重构让用户看见真实问题；设计任务书才告诉用户这个问题怎么处置。

本次升级后的更精确定义：

> 需求重构是设计任务书正式问诊前的理解力证明阶段。它不先追问用户，而是先把用户模糊表达重构成一个更清楚、更深、更有专业判断的项目命题，让用户产生“对，这才是我真正想说的”的确认感。只有在这个确认感之后，系统再提出关键追问，并自然衔接到原有设计任务书的一二轮追问机制。

因此，需求重构的第一目标不是“收集信息”，而是：

```text
先命中真实问题
↓
建立“你懂我”的信任
↓
拉起用户对正式任务书的期待
↓
再进入正式追问
```

这也是方案高参与普通大模型问答的第一分界。普通模型急着回答；方案高参先重构问题。普通问答给建议；方案高参先建立专业判断关系。

## 1. 产品总链路

```text
用户模糊表达
↓
需求重构：先命中真实问题，生成行动蓝图
↓
用户获得“它懂我”的确认，形成信任与期待
↓
少量关键追问：只问会改变判断的问题
↓
转换确认：是否进入设计任务书
↓
正式一二轮追问：任务书冻结前问诊
↓
阶段结论 / 目录重心 / 深度建议
↓
设计任务书 2.0
↓
项目图谱 / 活档案 / 后续更新
```

这条链路的产品含义：

1. 需求重构先证明理解力和判断力，不急于索要资料。
2. 需求重构后的少量追问只服务于继续校准，不进入正式问诊语气。
3. 一二轮追问锁定任务书方向，不重复需求重构已确认信息。
4. 设计任务书负责完整展开、依据补齐、缺口治理与可交付表达。

---

## 2. 三个阶段的责任

| 阶段 | 产品责任 | 用户体感 | 系统产物 |
|---|---|---|---|
| 需求重构 | 重构真实需求，形成行动蓝图 | “它把我没说清楚的事说清楚了” | 行动蓝图 |
| 一二轮追问 | 锁定任务书方向和交付边界 | “它开始正式问诊” | 显性锚点 + 隐性矛盾 |
| 设计任务书 | 完整交付项目结构 | “这可以交给别人继续推进” | 设计任务书 2.0 |

一句话定义：

> 需求重构让用户相信“它懂我”；一二轮追问让系统确认“这份任务书该怎么写”；设计任务书负责把这套判断完整交付。

三者不是并列产品，而是同一条设计任务书生产链的三个成熟动作：

```text
需求重构：先让用户愿意被追问
一二轮追问：正式确认任务书该怎么写
设计任务书：完整交付可沟通、可追溯、可执行的项目结构
```

## 3. 需求重构定义

### 3.1 产品定位

需求重构不是普通问答，也不是轻版任务书。

它是：

```text
设计任务书的购买前理解力证明形态
+
设计任务书生成前的需求预结构层
```

对外产物统一称为：

```text
行动蓝图
```

内部字段统一使用 `demand_reconstruction_blueprint` / `demand_reconstruction_context` / `blueprint` 等需求重构命名；前台主阶段名为“需求重构”，产物名为“行动蓝图”。

### 3.2 体验顺序：先重构，再追问

需求重构不能一上来变成问卷。用户给出的往往不是完整任务，而是一团未成形的需求、情绪、目标和矛盾。

错误顺序：

```text
用户模糊表达
↓
系统立刻问面积、预算、风格、场地
↓
用户感到：你还没懂我，就开始要资料
```

正确顺序：

```text
用户模糊表达
↓
系统先重构真实问题
↓
用户感到：它把我没说清楚的东西说清楚了
↓
系统再提出一两个关键追问
↓
用户愿意继续回答
```

需求重构阶段最重要的瞬间，是用户产生：

> “对，我就是这个意思，但我没说明白。”

这个瞬间不是靠名称制造，而是靠输出质量制造。名称只负责不掉价、不把用户拉回“又一个 AI 问答”的预期。

### 3.3 动态需求重构协议

需求重构不能做成固定栏目模板。固定的是后台判断责任，不固定前台输出结构。

后台每次都必须完成以下判断动作：

```text
1. 识别用户字面表达。
2. 重构用户真实需求。
3. 判断应继续需求重构、进入任务书，还是进入深度研究。
4. 找到最关键变量或头号风险。
5. 暴露会改变判断的信息缺口。
6. 给出下一步路径。
7. 保持“看见命门但不完整处置”的边界。
```

前台输出按问题类型动态组织，不强制每次出现同一组标题：

| 问题类型 | 前台重点 |
|---|---|
| 人生身份型 | 身份结构、生活路径、作品化风险、家庭/原乡关系 |
| 商业经营型 | 客群、坪效、出品效率、峰值动线、经营分叉 |
| 风格语义型 | 语义边界、风格误区、表达强度、符号禁区 |
| 硬约束型 | 参数边界、隐藏开关、待确认条件 |
| 文化研究型 | 研究边界、证据缺口、是否进入深度研究 |

必要时仍可出现以下模块，但它们是模块池，不是固定表格：

```text
真实需求重构 / 项目成立判断 / 头号风险 / 结构拆解 / 变量假设 /
关键分叉 / 未知边界 / 路径分流 / 任务书承接预览
```

判断标准：

> 后台协议稳定，前台结构随问题变化。

### 3.4 受控 LLM 洞察层

需求重构不能只靠规则模板。纯规则可以稳定分诊、复用本体论和保护边界，但面对开放式问题时，容易出现“整理很快，但不够懂”的体感。

因此运行时采用组合结构：

```text
既有语义理解 / 空间分类 / 主矛盾 / 本体论 / 知识包
↓
规则蓝图：确定类型、路由、缺口、任务书承接槽位
↓
LLM 洞察层：重写真实需求、核心判断、头号风险、一个关键追问
↓
边界守卫：拒绝完整方案、完整任务书、施工级建议、伪证据
↓
规则兜底：LLM 不可用、低质或越界时继续返回规则蓝图
```

这不是新建第二套算法，也不是让 LLM 接管入口判断。分工必须固定：

| 层 | 负责 | 不负责 |
|---|---|---|
| 规则 / 本体论层 | 空间分类、语义轴、主矛盾、路由、任务书承接 | 写出“懂我”的第一屏表达 |
| LLM 洞察层 | 把结构化上下文写成更锋利、更像专业顾问的需求重构 | 改路由、改任务书字段、生成完整方案 |
| 边界守卫 | 拒绝越界内容，压回计划、路径、缺口 | 提高内容深度 |
| 规则兜底 | 保证入口不断、响应可用 | 追求最好表达 |

LLM 可以增强“直入人心”的表达，但不能决定用户该去哪一层。路由、handoff、任务书承接字段仍由既有语义理解、入口分诊和规则蓝图控制。

运行时应暴露 `insight_source`：

```text
llm           = 使用受控 LLM 洞察层
rule          = 未启用 LLM，使用规则蓝图
rule_fallback = LLM 不可用、低质或越界，被降级为规则蓝图
```

这让后续排障可以直接判断：当前输出“一般”，到底是洞察层未启用、LLM 失败、质量门槛拒绝，还是规则蓝图本身颗粒度不足。

需求重构 LLM 必须使用独立短超时配置，不能复用正式对话态的长等待策略：

```text
DEMAND_RECONSTRUCTION_LLM_TIMEOUT=8
DEMAND_RECONSTRUCTION_LLM_MAX_RETRIES=0
```

产品原则：第一屏允许调用 LLM 增强洞察，但入口不能因为 LLM 连接失败而“掉链子”。失败时立刻回到规则蓝图，前台仍然可用。

### 3.5 需求重构前台输出的三内核

前台结构可以动态，但任何一次有效的需求重构都必须至少完成三个内核：

```text
1. 真实问题重写
   你表面在问什么，实际在解决什么。

2. 关键判断
   这个项目真正卡在哪里，或者最值得抓住的命门是什么。

3. 下一步追问
   只问最能改变判断的一两个问题。
```

注意：这里的“下一步追问”不是正式一二轮追问，而是需求重构后的轻追问。它的语气仍然是探索性的，目的仍然是加深理解，而不是锁定任务书字段。

以“50岁男性室内设计师，背井离乡，想在老家建一栋民居”为例，需求重构不应先问面积、预算、宅基地，而应先命中：

```text
这不是一个“在老家建房子”的问题，而是一个长期离乡的专业设计师，如何在职业后半段重新安放自己与故乡、家族、职业身份之间关系的问题。
```

然后给出关键判断：

```text
这个项目最大的风险，不是风格做不好，而是把它做成一个“设计师作品”，却无法承载真实的日常生活、家族关系和长期维护。
```

此时再问：

```text
我建议先确认一个关键点：这栋民居更像你的长期居所、阶段性返乡居所，还是带有工作室/接待属性的精神据点？
```

这个追问才成立。因为它不是索取资料，而是沿着刚才的判断继续推进。

### 3.6 需求重构中的“问”

需求重构可以和用户对话，但它的问是探索性问。

允许的表达：

```text
你更想解决的是返乡居住、精神寄托，还是家族关系？
```

不允许使用正式任务书问诊语气：

```text
请提交首轮判断。
请确认决策边界。
请选择任务书版本。
```

需求重构的问题不是为了冻结项目，而是为了把零散表达转成一张可讨论的行动蓝图。

需求重构阶段的问，必须满足三条：

1. 问题必须来自刚才的重构判断，而不是字段清单。
2. 问题数量要少，优先问一个最能改变判断的问题。
3. 问法要让用户感觉“你在继续理解我”，而不是“你在让我填表”。

### 3.7 需求重构边界

需求重构允许：

- 重写问题；
- 重构真实需求；
- 指出命门；
- 排序关键分叉；
- 标注未知边界；
- 给推进路线；
- 建立进入任务书的信心。

需求重构禁止：

- 输出完整任务书；
- 输出完整空间方案；
- 展开完整风险矩阵；
- 伪装完成证据研究；
- 替代正式一二轮追问；
- 把需求重构变成普通大模型问答。

## 4. 一二轮追问定义

### 4.1 是否保留

保留，而且更重要。

需求重构加入后，一二轮追问不被取代，而是位置更清楚：

```text
需求重构的问：为了继续校准真实问题，让用户愿意进入正式问诊。
一二轮追问：为了把行动蓝图变成正式设计任务书。
```

需求重构与一二轮追问的关系：

| 环节 | 问的目的 | 用户体感 | 输出结果 |
|---|---|---|---|
| 需求重构阶段 | 证明理解，指出真实问题 | “它懂我” | 项目命题、主矛盾、关键方向 |
| 第一轮追问 | 补齐显性事实 | “开始正式问诊” | 项目对象、场地、面积、人群、目标 |
| 第二轮追问 | 锁定隐性取舍 | “开始收敛决策” | 优先级、冲突、边界、不可接受风险 |

所以，需求重构不取代一二轮追问。它的作用是让一二轮追问不再像冷冰冰的表单，而像专业顾问在已经理解项目的基础上继续问诊。

### 4.2 第一轮追问

第一轮属于正式任务书入口，目标是承接显性锚点。

它确认：

- 项目对象；
- 使用方式；
- 场地条件；
- 业主画像；
- 目标动机；
- 当前任务范围；
- 已有资料；
- 交付意图。

### 4.3 第二轮追问

第二轮确认隐性矛盾和关键取舍。

它追问：

- 哪个目标优先；
- 哪个风险不能接受；
- 哪个表达必须克制；
- 哪个未知会改变任务书方向；
- 哪个设计假设可以成立，哪个只是愿望。

### 4.4 无损继承

需求重构已经问出的内容，进入任务书后不重问。

| 需求重构产物 | 任务书承接 |
|---|---|
| 任务重写 | 项目核心命题 |
| 项目成立判断 | 项目背景 / 成立判断 |
| 头号风险 | 风险边界 |
| 关键分叉 | 关键取舍 |
| 未知边界 | 资料缺口 |
| 推进路线 | 目录重心 |
| 用户补充 | 任务书预填字段 |

## 5. 两类测试输入

### 5.1 需求重构级输入

```text
50岁男性室内设计师，背井离乡，想在老家建一栋民居，给出建议
```

期望：

- 进入需求重构；
- 输出行动蓝图；
- 不触发正式一二轮追问；
- 可以继续需求重构对话；
- 可提示整理成设计任务书。

核心判断示例：

```text
这不是一个民居风格问题，而是一个离乡多年的专业设计师，如何重新安放自己与故乡关系的问题。
```

### 5.2 任务书级输入

```text
四川广元农村300㎡田园民居，业主为50岁男性室内设计师，长期离家在外发展，内心存在对乡土的复杂情感。请以“安藤忠雄为其设计”为假设前提，提出完整室内设计概念框架，围绕光的控制、混凝土与在地材料的张力、空间的沉默感、与自然对话的界面关系，以及如何在朴素乡村环境中实现精神性空间的建构，避免形式化模仿。
```

期望：

- 进入正式任务书入口；
- 识别为概念框架型设计任务书；
- 启动一二轮追问；
- 不停留在普通建议；
- 不形式化模仿安藤忠雄；
- 将需求重构判断升级为任务书目录重心。

## 6. 后端实现纲领

需求重构不新建第二套语义大脑。它复用既有项目语义理解、空间分类、语义轴、本体论、知识包与任务书入口能力，只新增一层薄编排。

总体结构：

```text
SchemeAdvisorContextIntelligence / SpaceClassificationService / semantic axes / ontology / knowledge
↓
DemandReconstructionContextAdapter
↓
DemandReconstructionOutputPlanner
↓
Controlled LLM Insight Layer
↓
DemandReconstructionBoundaryGuard
↓
DemandReconstructionService
```

收敛需求重构总入口：

```text
DemandReconstructionService
```

职责：

- 判断是否进入需求重构；
- 调用上下文适配器；
- 生成动态行动蓝图；
- 沉淀 `demand_reconstruction_context`；
- 判断是否出现任务书意向；
- 把需求重构产物交给正式任务书入口。

新增服务：

```text
DemandReconstructionContextAdapter
```

职责：

- 调用 `SchemeAdvisorContextIntelligence`；
- 复用空间分类、语义轴、本体论、知识包上下文；
- 生成需求重构用的 `adapter_context`；
- 不独立建立空间分类或主矛盾算法。

```text
DemandReconstructionOutputPlanner
```

职责：

- 根据 `adapter_context` 选择输出模块；
- 生成动态 `sections`；
- 避免固定八段式；
- 避免针对单个测试题硬编码答案。

```text
Controlled LLM Insight Layer
```

职责：

- 在规则蓝图和上下文包约束下增强真实需求重写；
- 只改写洞察表达，不改写系统路由；
- 只提出一个最关键追问；
- 不输出完整方案、完整任务书、施工级建议或伪证据；
- 低质、越界、失败时必须回退到规则蓝图。

```text
DemandReconstructionBoundaryGuard
```

职责：

- 防止需求重构输出完整任务书；
- 防止需求重构输出完整方案；
- 防止需求重构伪装深度研究；
- 将越界内容压回“计划、路径、缺口”。

建议字段：

```text
demand_reconstruction_blueprint:
  reconstruction_type: demand_reconstruction
  artifact_name: action_blueprint
  display_title: 需求重构
  display_artifact_name: 行动蓝图
  task_reframe
  project_viability_judgment
  primary_risk
  sections
  key_forks
  unknowns
  routing
  routing_recommendation
  brief_handoff_slots
  context_source
  insight_source
  archetype
```

会话层新增兼容字段：

```text
dialogue_layer: demand_reconstruction | brief_intake | project
handoff_available: boolean
demand_reconstruction_context: optional object
```

注意：这些是系统字段，不应作为前台术语教育用户。

## 7. 前端实现纲领

新增需求重构展示形态：

```text
需求重构卡 / 行动蓝图卡
```

需求重构卡片不使用：

```text
提交首轮判断
提交决策判断
关键确认
决策确认
```

正式任务书卡片继续使用：

```text
关键确认
决策确认
阶段结论
版本选择
```

前端必须让用户感知到两种“问”的差别：

1. 需求重构是在帮他把模糊需求说清楚。
2. 一二轮追问是在正式生成设计任务书。

需求重构卡片应支持动态 `sections`：

```text
section:
  title
  body
  items
  emphasis
```

不同问题可以显示不同 section 组合，不允许为了界面整齐强行补空栏目。

## 8. 工程验收清单

后端：

- 需求重构样例不触发正式首轮问诊；
- 任务书样例触发正式首轮问诊；
- 需求重构判断复用既有上下文能力；
- 不保留针对单个测试题的答案硬编码；
- 不同问题输出不同 section 组合；
- 需求重构上下文可带入任务书；
- 已进入正式问诊的会话不会被需求重构重新截获；
- 返回字段保持旧客户端兼容。

前端：

- 能渲染 `demand_reconstruction_blueprint` 卡片；
- 用户可见标题为“需求重构”；
- 需求重构卡片不出现正式问诊按钮文案；
- 正式问诊卡片原有文案不被改坏；
- 卡片提交能携带选项与结构化响应。

产品：

- 第一阶段仍只对外售卖设计任务书 2.0；
- 需求重构免费展示理解力和判断力存在，但不完整交付判断处置；
- 用户前台不出现内部层级、闸门、冻结等工程术语；
- 任务书承担完整展开、依据补齐、缺口治理、可交付责任。
