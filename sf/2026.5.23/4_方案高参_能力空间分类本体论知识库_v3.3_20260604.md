## 0｜本次更新的核心结论

### 0.1 v3.3 的一句话定盘

```text
v3.1 让系统会像高参一样使用知识；
v3.3 让系统知道：知识只是素材，转化才是设计，交付才是产品。
```

方案高参不再只是：

```text
空间分类 + 本体论 + 知识库 + 能力链 + AdvisorAgent 姿态
```

而应升级为：

```text
素材层 → 转化层 → 交付层
        ↑
      主体轴贯穿
```

其中：

```text
素材层回答：有什么可用？
转化层回答：如何立意？
交付层回答：如何组织成产物？
主体轴回答：为谁、为何、谁说了算？
输出模式回答：这次应交付什么形态？
```

### 0.2 v3.3 对 v3.1 的覆盖声明

v3.1 已经完成以下内容：

```text
空间分类：context facet vector + missing_slot 分流机制。
本体论：lens × layer 网格 + 事实层 / 判断层边界。
知识库：知识卡系统 + judgment_bet 可验证判断字段。
能力：动作链 + AdvisorAgent guardrails。
外部搜索：证据介入机制 + AdvisorAgent 检索纪律。
记忆系统：会话同步轨 + 全局异步轨。
质量治理：AdvisorAgent Eval 维度。
```

v3.3 全部保留，并在此基础上新增：

```text
1. AdvisorArchitecture Skeleton Interface｜素材 · 转化 · 交付总骨架接口
2. context_packet｜从 context_vector 升级为完整上下文包
3. source_role｜被转化的源 / 转化的边界 / 转化的工具料 / 转化方法 / 项目产物
4. knowledge_species｜知识物种：Domain / CrossSystem / Meaning / Operation / Lens / Case / TranslationMethod
5. Subject Axis｜主体轴：主体精神结构 + 权力决策关系
6. Meta-Context Drivers｜元语境驱动
7. Translation Engine｜转译引擎：源 → 手法 → 空间策略
8. Output Mode Selector｜输出模式选择器
9. Discipline Switch｜spatial_extent 触发学科切换
10. 入库边界重定：素材入库，转化方法入库，项目立意与交付产物不入通用库
```

### 0.3 产品层纪律

v3.3 明确区分：

```text
对外产品层：
  第一阶段只有一个对外产品名——设计任务书 2.0。

内部系统层：
  可以识别并组织多种输出模式，包括任务书、方法论、竞标策略、研究框架、概念矩阵、规划策略、产品线策略、未来情景原型等。
```

因此：

```text
Output Mode Selector 是内部编排器，不是前台产品货架。
```

对外仍统一表达为：

```text
设计任务书 2.0
```

但内部可以生成：

```text
任务书型设计任务书
方法论型设计任务书
竞标策略型设计任务书
研究框架型设计任务书
概念矩阵型设计任务书
规划策略型设计任务书
```

## 1｜版本关系与职责边界

### 1.1 v3.0 的职责

v3.0 负责定义系统结构：

```text
Context Facet Vector
Lens × Layer Grid
Grid-Tagged Knowledge Cards
Capability Chain
External Evidence Intervention
Knowledge Promotion / Demotion
```

它回答：

```text
系统由什么构成？
知识如何分层？
空间分类如何输出语境？
本体论如何组织对象与关系？
知识卡如何绑定问题、证据和迁移属性？
能力如何调度理解、检索、推理、生成、沉淀？
```

### 1.2 AdvisorAgent v1.2 的职责

AdvisorAgent v1.2 负责定义运行姿态：

```text
先定位，别急着答。
信息不全不卡死，也不硬猜。
分层捞货，因为要复用。
综合出那个会要命的点，排优先级。
只问不答不下去的那几个问题。
给结论封顶，不装。
顺手记账。
```

它回答：

```text
LLM 拿到分类、本体、知识卡和项目上下文后，应该怎样思考？
```

### 1.3 v3.1 的职责

v3.1 建立系统骨架与高参心法之间的接口：

```text
分类结果如何影响回答姿态？
missing_slots 如何触发缺口处理动作？
capability 调用时应挂哪些思考纪律？
事实层哪些可以硬编码，判断层哪些必须交给 AdvisorAgent？
外部搜索如何服从“不硬猜”和“结论封顶”？
项目记忆如何区分会话连贯性与全局沉淀？
知识卡如何记录可验证判断？
系统如何评估回答是否像高参？
```

一句话：

```text
v3.1 是“系统有什么”和“系统怎么想”之间的运行接口补丁。
```

### 1.4 v3.3 的职责

v3.3 在 v3.1 基础上接入更上位骨架：

```text
素材 · 转化 · 交付
```

它回答：

```text
空间分类、本体论、知识卡、能力链、主体轴、转译引擎、输出模式，如何在同一套认知操作系统中各归其位？
```

一句话：

```text
v3.3 是“高参运行接口”进一步接入“转化中心架构”的本体论总版。
```

v3.3 的完整运行链如下：

```text
用户问题
→ 对话识别
→ 问题编译
→ 空间分类输出 context_packet
→ Subject Axis 识别
→ Meta-Context Drivers 识别

→ missing_slots 结构化与三分流
→ 本体论激活 lens × layer 网格
→ 知识库按 grid_coordinate 召回素材
→ 必要时触发 External Evidence Intervention
→ Translation Engine 解码 / 映射 / 求解 / 防滑
→ AdvisorAgent Runtime Discipline 装配
→ 能力系统执行理解、检索、推理、生成、沉淀
→ 输出任务书 / 方法论 / 竞标策略 / 研究框架 / 概念矩阵 / 规划策略等内部模式
→ 对外统一组织为设计任务书 2.0 或其变体

→ 全局异步轨处理知识升降级
→ Feedback & Evolution 回写
```

其中：

```text
Context Packet 负责语境定位。

Translation Engine 负责把素材转化成立意。
Capability Chain 负责动作执行。
Output Mode Selector 负责确定产物类型。
AdvisorAgent Runtime Discipline 负责现场判断姿态约束。
Memory Tracks 负责会话连贯与长期沉淀。
Eval Dimensions 负责质量治理。
```

## 3｜AdvisorArchitecture Skeleton Interface｜素材 · 转化 · 交付总骨架

### 3.1 三段结构

方案高参总骨架分三段：

```text
素材层 · 料与边界
转化层 · 设计本体
交付层 · 组织产物
```

### 3.2 素材层

回答：

```text
有什么可用？
```

素材层内部必须分三类：

```text
A. 被转化的源
B. 转化的边界
C. 转化的工具料
```

#### A. 被转化的源

会被编译成空间立意。

```text
人格
品牌
大师方法
诗性意象
文学
音乐
自然意象
学科理论
文化传统
精神结构
```

#### B. 转化的边界

不被编译，而是限定编译。

```text
预算
法规
场地
物理
机电
消防
伦理
工期
安全
尺度
学科边界
```

#### C. 转化的工具料

供转化调用。

```text
业态
构件
横向系统
材料
灯光
动线
空间手法
案例
透镜
规格卡
```

### 3.3 转化层

回答：

```text
如何立意？
```

转化层由以下部分组成：

```text
Subject Axis｜主体轴
Translation Engine｜转译引擎
Design Grammar｜设计语法
Constraint Negotiation｜约束协商
Anti-Slippage Check｜防滑检查
AdvisorAgent Runtime｜现场判断
```

转译引擎四步：

```text
1. 解码：源 → 不变结构
2. 映射：不变结构 → 手法
3. 求解：手法意图 → 在真实约束下落地
4. 防滑：检查是否退化成符号、套路、伪高级、伪国风
```

### 3.4 交付层

回答：

```text
如何组织成产物？
```

包括：

```text
Output Mode Selector｜输出模式选择器
Design Brief Compiler｜任务书编排器
Project Graph Compiler｜项目图谱编排器
Version Snapshot｜版本快照
Export Layer｜导出层
Feedback Loop｜反馈回写
```

### 3.5 两个反向回路

#### 回路一：转化拉动采集

```text
转化一启动，立刻暴露缺料；
缺料再触发 Deep Research、测绘、访谈、案例拆解、透镜调用。
```

这意味着：

```text
素材不是必须先填满的前置仓库；
素材是被转化拉动的库存与按需补货系统。
```

#### 回路二：交付回写修正

```text
任务书生成后、项目执行后、用户反馈后，反向修正判断、降级或升级知识卡、补充转译方法卡。
```

### 3.6 入库判据

```text
素材层：入库。
转化层：方法入库，立意不入库。
交付层：产物不入通用库，只入项目档案。
```

更精确地说：

```text
转化方法卡可以入库。
某个项目的概念主线不入通用库。
交付文件不入通用知识库。
交付文件可作为 ProjectInstance / CaseObject 回流，拆解后提炼新知识。
```

## 5｜missing_slots 结构化与三分流

v3.3 完整保留 v3.1 的 missing_slots 机制。

### 5.1 missing_slot 字段

```yaml
missing_slot:
  name: string
  type: physical_constraint | subjective_preference | business_fact
  severity: critical | high | medium | low
  action: certainty_ceiling | option_menu | branch_answer_plus_followup
  priority: P1 | P2 | P3
  affected_lens: []
  unlock_condition: ""
  user_visible_note: ""
```

### 5.2 缺口三分流

#### A. 物理硬约束缺口

示例：

```text
给排水点
消防红线
通道宽度
柱网
场地边界
商场公共通道
设备机电条件
```

处理动作：

```text
certainty_ceiling
```

#### B. 主观偏好缺口

示例：

```text
调性
风格
是否要强打卡
是否偏新中式
是否偏克制高级
是否重社交
```

处理动作：

```text
option_menu
```

#### C. 经营事实缺口

示例：

```text
外卖占比
是否有鲜果
是否有奶盖
是否做轻食
峰值订单
客单价
目标回本期
```

处理动作：

```text
branch_answer_plus_followup
```

### 5.3 串行优先级

```text
P1 物理硬约束
P2 经营事实
P3 主观偏好
```

规则：

```text
只要存在 P1 物理硬约束缺口，本轮强制熔断 P2 与 P3；
先封顶并问物理头号问题，不展开经营分叉与风格选项。

物理底盘相对确定后，再处理经营事实分叉。
基础事实完备后，才处理主观偏好分餐。
```

## 6｜Subject Axis｜主体轴

### 6.1 定义

主体轴回答：

```text
这个空间为谁而做？
谁真正受影响？
谁说了算？
谁被照顾？
谁被展示？
谁被排除？
```

主体轴不是普通用户画像。它是转译引擎的缰绳。

主体轴包括两部分：

```text
Subject Psyche｜主体精神结构
Stakeholder Power｜权力与决策关系
```

### 6.2 Subject Psyche｜主体精神结构

用于识别：

```text
生命阶段
身份焦虑
成就象征
回归需求
疗愈需求
自我表达
精神结构
审美人格
```

示例：

```text
一代创业者
独立女性
00 后富二代
哲学教授
宇航员
诗人
艺术策展人
退休干部
高净值客户
```

### 6.3 Stakeholder Power｜权力与决策关系

用于识别：

```text
谁付钱
谁拍板
谁使用
谁被照顾
谁有否决权
家庭 / 组织 / 品牌中的权力结构
公共 / 私密 / 接待 / 展示等级
```

示例：

```text
父亲偏红木，母亲偏北欧，儿子希望调和。
再婚家庭两个无血缘青春期孩子。
企业家私宅中的男主人主导权。
总部空间中的老板、员工、客户、投资人关系。
```

### 6.4 主体轴在转译两端把关

入口端：

```text
授权源：这个源是否与主体精神结构共振？
定终局：本次转译到底服务什么真实目的？
```

出口端：

```text
权力裁决：多主体冲突时谁说了算？
验收：空间立意是否能回到主体终局？
```

## 13｜Translation Engine｜转译引擎接口

### 13.1 定义

转译引擎负责：

```text
把源，在主体与约束的限定下，转译成设计手法与空间策略。
```

它不是内容库，不是图像生成器，不是风格匹配器。

### 13.2 四步编译

```text
1. 解码：源 → 不变结构
2. 映射：不变结构 → 手法
3. 求解：手法意图 → 在真实约束下落地
4. 防滑：检查是否退化成符号、套路、浅层表达
```

### 13.3 五类源

```text
PersonalitySource｜人格 / 精神源
BrandSource｜品牌源
MasterMethodSource｜大师方法源
PoeticImagerySource｜诗性意象源
DisciplineTheorySource｜学科理论源
```

### 13.4 转译产物的边界

```text
转译方法可以入库；
转译产物不入通用知识库。
```

例如：

```text
“如何把诗性意象转为空间策略”的方法可入库。
“某书房的月亮落在结冰湖面上概念”不入通用库，只入项目档案。
```

### 13.5 防滑检查

防滑检查用于识别：

```text
符号化
主题化
脸谱化
表面装饰
伪高级
伪国风
堆砌文化符号
用品牌颜色替代品牌精神
用风格标签替代空间逻辑
```

## 23｜最终定稿口径

v3.3 不是推翻 v3.1，而是完整覆盖并升级 v3.1。

```text
v3.1 的意义：把“会组织知识的系统”校正为“会像高参一样使用知识的系统”。
v3.3 的意义：把“会像高参一样使用知识的系统”进一步升级为“能把素材转化成立意，并组织成交付物的空间问题认知操作系统”。
```

最终一句话：

```text
空间分类、本体论、知识库、能力链不是终点；
它们只是素材与工具。
方案高参真正的中轴，是把这些素材在主体与约束中转化成立意，再组织成设计任务书 2.0 或其内部输出模式。
```

更短版本：

```text
素材是料，转化是设计，交付是产品。
```
