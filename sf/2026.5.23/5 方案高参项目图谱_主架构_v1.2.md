## 0. 主架构总纲

### 0.1 一句话总纲

> **项目图谱是以项目认知对象为节点、以对象间真实关系为边的活的认知网络。它是项目认知关系的唯一前台母体,但不是所有项目对象的真相源。它的核心智能价值在于主动显现"用户没看到但应该看到的事"——结构空白、关键瓶颈、隐藏盲区。它通过 source_refs 与对象链相连,通过 Graph-aware AI 与用户对话,通过焦点子图承接日常工作。**

### 0.2 命名体系

| 层级 | 名称 |
|---|---|
| 用户前台功能名 | **项目图谱** |
| 文档主架构名 | 项目图谱主架构 |
| 技术对象名 | **Project Cognition Graph(PCG)** |
| 内部关系机制 | **问题依赖图** |
| 默认呈现 | **分组网络** |
| 观察呈现 | **自由网络** |
| 局部工作态 | **焦点子图** |
| 右侧详情区 | 节点白板 / 白板 |
| 智能机制 | **结构空白引擎** + **Graph-aware AI** |

"项目图"作为口语简称允许使用,但不作为正式产品名。

### 0.3 主架构铁律

**铁律 1:前台反线性,后台有治理**
- 项目图谱不以阶段作为主视觉,不以"先 A 再 B"作为用户的操作主轴
- 后台保留 Node3 / Node4 / 深化分支等治理协议,用于冻结、回退、审阅、版本控制
- "反传统流程"不等于"没有流程治理"

**铁律 2:节点是项目认知对象,问题节点为核心**
- 节点不是通用知识概念,而是当前项目的认知对象
- 问题节点是核心,目标、约束、依据、风险、决策都是围绕问题展开的支撑节点
- 项目图谱前台展示的是项目当前要处理的"事",不是设计领域的"知识"

**铁律 3:项目图谱是认知关系的母体,不是所有对象的真相源**
- 项目图谱不替代 AlignedBrief / SPG / FloorPlanIR / VizSpec / InitialDesignPack
- 它通过 `source_refs` 机制引用对象链,做节点化索引、关系映射、状态投影
- 不复制冻结对象的内容形成并行真相

**铁律 4:图是组织者和索引,不是终端展示**
- 节点上只显示标签和状态,所有细节在右侧白板里展开
- 节点保持视觉精炼,不因"想展示更多信息"而越画越密

**铁律 5:图与白板双向联动**
- 点击节点 → 白板更新
- 白板里做决策 → 图状态更新

**铁律 6:网络可有多种呈现态,但只有一套数据本体**
- 两态切换不创造新数据,只换观察姿态
- 数据地位对等,使用分工不同

**铁律 7:节点位置一次初始化后稳定**
- 保护用户的空间记忆
- 新增节点找空位插入,不重排已有节点
- 大项目下,稳定的空间记忆是设计师不迷失的唯一安全感

**铁律 8:焦点子图是真正的工作态**
- 日常使用 80% 的时间在焦点子图里,不在全图里
- 全图用于看整体,工作发生在子图

**铁律 9:产品智能的核心是"显现盲区",不是"自动总结"**
- 系统的真正价值是让用户看到"没问但应该问"的问题
- 结构空白引擎是产品智能的核心落点
- 比"AI 自动生成任务书"远更有价值

**铁律 10:AI 必须基于子图上下文,不是全项目泛答**
- 所有 AI 动作的回答上下文严格限定于当前可见子图
- 这是 Graph-aware AI,不是泛泛的对话助手
- 让用户感受到"系统真的懂我项目当下的处境"

## 1. 网络的两种呈现态

### 1.1 呈现态 A:自由网络态

**视觉特征**:节点按整体网络力学初始化分布(一次性,之后稳定),不按问题域聚类。边的视觉强度反映关系强度——强依赖的边更粗、更短、更紧。

**适用场景**:
- 项目初期的认知探索:"看这个项目都涉及什么"
- 项目复盘:"展示这个项目的整体认知图谱"
- 寻找隐藏关联:"看哪些跨域问题被忽视了"
- 寻找孤立节点或断裂区域

**不适用场景**:日常聚焦工作(密度高,导航成本大)。

### 1.2 呈现态 B:分组网络态

**视觉特征**:节点按问题域聚类到几个虚线区域内,域间用相对位置呈现关系。跨域的强依赖边依然保留,作为半透明实线显示。

**问题域分类(默认六类)**:
1. **为什么做**——目标、价值、成功标准
2. **在哪里干**——场地、建筑、地域、约束
3. **现在卡什么**——当前活跃的核心阻塞问题
4. **可以怎么做**——设计判断、策略、立场、表达
5. **谁来拍板**——决策点、责任位、审阅角色
6. **影响什么成果**——成果物、对外交付、外部产物关联

**分组维度可切换**:用户可以在"按问题域"、"按状态"、"按紧迫性"等不同维度间切换,分组本身是一种思考工具。

**适用场景**:日常工作的默认态——结构清晰、空间记忆稳定、导航高效。

### 1.3 数据同源与使用分工

**数据层**:两态共享同一份 PCG 数据,不产生新数据。
**使用层**:分组网络是默认工作视图,自由网络是观察/复盘/探索视图。

**初始默认态**:首次打开项目时,系统默认进入**分组网络态**。
**用户偏好记忆**:用户切换后,系统记住此次会话的偏好。下次默认进入用户上次选择的态。

### 1.4 两态切换的视觉过渡

切换通过单一按钮触发(右上角)。切换不是瞬时跳变,而是节点位置的平滑过渡动画(约 0.6 秒):

- 从 A 到 B:节点像受到磁场吸引,流畅地迁移到各自的问题域虚线区域内
- 从 B 到 A:节点从聚类位置松开,流向网络力学的稳定位置

数据完全不变,只是节点的视觉位置变化。所有边、所有状态、所有焦点都保持不变。

## 2. 焦点子图机制

### 2.1 焦点子图作为真正的工作态

**根本判断**:用户日常工作的 80% 时间不是看全图,是在焦点子图里——聚焦某个具体问题节点,处理它和它的关联节点。

**焦点的触发**:用户点击任意节点 → 该节点成为焦点(硬切换,不是悬停软切换)。

### 2.2 焦点态下的视觉表现

- **焦点节点**:放大、高亮、带光晕
- **一跳关联节点**:保留色彩、轻微放大
- **二跳关联节点**:保留色彩、原始大小
- **远关联或无关节点**:整体灰化、半透明、退到背景(降噪率约 85%)
- **焦点节点对应的白板**:右侧白板自动切换显示该节点的详细内容

### 2.3 焦点态的工具集(默认收起)

焦点态下,屏幕右上角出现一个小型工具图标。**默认收起为单一图标,鼠标悬停或点击展开**。展开后支持以下子图过滤:

1. **只看一跳**——隐藏所有二跳及更远节点
2. **只看二跳**——保留二跳关联
3. **显示阻塞链**——从焦点节点回溯,显示所有阻塞当前节点的上游链
4. **显示影响范围**——从焦点节点正向追踪,显示所有被它影响的下游节点
5. **显示依据来源**——显示焦点节点的所有支撑依据节点
6. **隐藏已冻结节点**——把已确认/已冻结的节点淡化或隐藏,只关注未解决的部分

### 2.4 退出焦点

用户点击焦点节点之外的画布空白处,或按 Esc 键,退出焦点态,回到全图态。

## 3. 节点本体

### 3.1 节点类型(六类)

| 类型 | 含义 | 视觉编码(示意) |
|---|---|---|
| **目标节点** | 项目终局、价值定位、成功标准 | 较大圆形,深色填充 |
| **约束节点** | 不可改的硬约束(场地、建筑、法规、预算) | 方形,灰色填充 |
| **问题节点** | 待处理的核心问题 | 圆形,按状态变色 |
| **决策节点** | 已做出或待做出的判断 | 菱形,边框较粗 |
| **依据节点** | 支撑某些判断的资料、案例、规范、引用知识库卡片 | 较小圆形,细边框 |
| **风险节点** | 已识别的风险点 | 圆形,红色边框警示 |

**视觉编码原则**:类型用形状区分,状态用颜色区分,**中心性用尺寸权重区分**。形状+颜色+尺寸组合可以同时表达"是什么类型 + 处在什么状态 + 有多关键"。

### 3.2 节点状态(五类最小集,可扩展)

**最小可用集(立即实现)**:

| 状态 | 含义 | 颜色编码 |
|---|---|---|
| **未启动** | 已识别但还没开始处理 | 灰色 |
| **进行中** | 当前在处理 | 蓝色 |
| **已解** | 处理完成,有当前解 | 绿色 |
| **冲突** | 发现与其他节点冲突,需仲裁 | 红色 |
| **阻塞** | 因前置条件不满足而被卡住 | 红色虚线环 |

**颜色系统的关键裁决**:**节点颜色唯一由状态决定**。外部产物对账的结果通过节点状态变化体现,不另立颜色系统。部分匹配缺口用黄色"待复核"小角标补充。

**待后续专题深化的扩展状态**(暂不实现,但语义保留):
- 待识别 / 待补资料 / 待分析 / 待决策 / 待验证 / 已确认 / 已冻结 / 已失效 / 高风险

### 3.3 节点位置稳定性

**根本规则**:节点位置一次初始化后稳定保存,不漂移。

**具体行为**:
- 项目首次打开:算法计算一次节点位置,作为该项目的稳定布局
- 新节点增加:在邻近相关节点的空位中插入(焦点节点附近优先)
- 节点删除:留下空位,不重排其他节点
- 用户拖动调整某个节点:系统记住调整,作为该节点的新稳定位置

**工程实现要求**:节点坐标必须在后端稳定保存,绝对禁止因为刷新、重新加载或新数据接入而导致位置乱转或重排。

### 3.4 节点的视觉权重(中心性编码)

除了类型(形状)和状态(颜色)外,节点的**视觉尺寸**反映节点的中心性——被多少个其他节点依赖、影响多少下游。

**中心性的视觉规则**:
- 高中心性节点(被 5+ 节点依赖):节点默认尺寸 +20%、光泽略亮
- 中等中心性节点(被 2-4 节点依赖):默认尺寸
- 低中心性节点(被 0-1 节点依赖):节点默认尺寸 -10%、稍暗

**这件事的产品价值**:用户一眼看到项目的关键瓶颈节点——视觉上自然凸显的就是最重要的事。**不需要用户操作,系统自动呈现**。

中心性是从边数据自动计算的,**不需要用户维护**。每次节点或边变化时,系统重新计算并刷新视觉权重。

### 3.5 节点的最小数据结构

```yaml
node:
  id: string                     # 节点唯一标识
  type: enum                     # 六类节点类型之一
  status: enum                   # 五类节点状态之一
  title: string                  # 节点标题(显示在图上)
  summary: string                # 节点摘要(显示在白板)
  source_refs: [object_ref]      # 指向后台对象链的引用列表
  confidence: float              # 系统判断置信度(0-1)
  confirmation_status: enum      # 人工确认状态:待确认/已确认/已复核
  linked_objects: [object_ref]   # 关联的外部产物(CAD、效果图等)
  position_profiles: object      # 节点在两态下的稳定坐标
  centrality: float              # 中心性(系统自动计算)
  abstraction_level: enum        # 抽象层级:具体问题 / 中层概念 / 抽象大词
  created_from: enum             # 创建来源:系统预设/用户手动/外部产物驱动
  version: string                # 版本号
  created_at: timestamp
  updated_at: timestamp
```

**新增字段说明**:
- `centrality`:由系统从边数据自动计算,用于视觉权重编码
- `abstraction_level`:用于"隐藏大词"功能(详见第 13 章)

## 4. 边的本体

### 4.1 边的类型(初始三类,可扩展)

**最小可用集(立即实现)**:

| 边类型 | 含义 | 视觉编码 |
|---|---|---|
| **依赖** | A 解决前 B 无法处理 | 实线 + 箭头 |
| **冲突** | A 与 B 的解互相矛盾 | 红色虚线,无箭头(双向) |
| **派生** | 处理 A 时发现了 B | 细实线 + 箭头,较淡 |

**待后续专题深化的扩展类型**:
- 支撑(supports)
- 影响(impacts)
- 产出(derives_to)
- 验证(validates)
- 归属(belongs_to)

### 4.2 边的视觉编码(strength 维度)

每条边都有 `strength` 字段(0-1)。视觉上,strength 通过边的**粗细 + 长度**联合编码:

| strength 范围 | 视觉表现 | 含义 |
|---|---|---|
| 0.8 - 1.0 | 粗、短、紧(节点间距压缩至 40-60px) | 强依赖 / 硬冲突 |
| 0.4 - 0.7 | 中等粗细、中等长度 | 中依赖 |
| 0.1 - 0.3 | 细、长、半透明(150px+) | 弱关系 |

**这件事的产品价值**:用户一眼看到"哪些是关键依赖、哪些是次要关联"。强依赖把节点拉近,视觉上自然显示项目的核心矛盾结构。

**关键约束**:strength 影响的是视觉编码,**不影响节点的稳定坐标**。节点坐标在初始化时已锁定,strength 只控制边的渲染粗细和长度感。

### 4.3 边的分级显示

避免分组态变回毛球态的关键约束:**不要把所有关系都画出来**。

- **默认显示**:强依赖(strength ≥ 0.7)、硬冲突
- **焦点态下显示**:中依赖、派生、共因等次级关系
- **永远不默认显示**:弱关联(strength < 0.3)、远派生

### 4.4 跨域强依赖的特别处理

在分组网络态下,跨问题域的强依赖关系**必须保留为长跨域连线**——不能因为分组而切断项目的整体血缘。

**视觉规范**:跨域连线用**半透明实线**,既保留可见性又不破坏分组态的秩序感。**不用红色**(红色专属于"冲突"状态)。

### 4.5 边的最小数据结构

```yaml
edge:
  id: string                     # 边唯一标识
  type: enum                     # 三类边类型之一
  from: node_id                  # 起点节点
  to: node_id                    # 终点节点
  strength: float                # 关系强度(0-1)
  status: enum                   # 边的状态(活跃/失效)
  evidence_refs: [object_ref]    # 支撑这条边存在的依据
  confidence: float              # 系统判断置信度(0-1)
  created_from: enum             # 创建来源:系统预设/用户手动/系统推荐
  created_at: timestamp
```

### 4.6 问题依赖关系的来源(混合模式)

边不是凭空出现的。三种来源混合:

1. **预设依赖**:根据项目类型和本体论,系统自动创建部分常见依赖
2. **用户手动添加**:用户可在白板中为两个节点添加依赖/冲突/派生关系
3. **系统推荐**:基于结构空白识别(详见第 11 章),系统主动推荐"本该连接但未连接"的关系

所有边的 `created_from` 字段必须明确记录来源,便于后续追溯和调整。

## 5. 项目图谱 vs 知识图 —— 根本区分

### 5.1 这是最容易滑落的方向

项目图谱的视觉气质可能让人误以为它是知识图——节点很多、关系密集、看起来像大脑。**但本质上这是两种完全不同的对象**:

| 维度 | 知识图(后台) | 项目图谱(前台) |
|---|---|---|
| 节点 | 设计领域的概念(品牌表达、文化叙事、自然生态) | 当前项目的具体认知对象(目标/约束/问题/决策/依据/风险) |
| 关系 | 概念之间的语义关联 | 认知对象之间的依赖、冲突、派生 |
| 服务对象 | AI 的世界理解(底层) | 用户的项目工作(前台) |
| 演化方式 | 跨项目通用、缓慢演化 | 每个项目独有、持续演化 |

### 5.2 主架构裁决

**项目图谱的前台主视图必须是项目认知对象,不是知识概念**。

知识图作为 AI 内部的世界理解,在后台存在,但不进入前台展示。它通过"问题节点挂载知识卡片作为依据"的方式,间接服务于项目图谱。

**这条判断需要在所有后续设计中反复强调**,因为视觉惯性会不断把图拉回概念图。任何看到节点是"品牌表达"、"自然生态"这种抽象概念的设计,都是滑回知识图的信号。

## 6. 图与白板的联动机制

### 6.1 角色分工

- **左侧/中央:项目图谱**——组织者、索引、广度导航
- **右侧:节点白板**——深度承载、内容展示、工作场

### 6.2 联动规则(双向)

**图→白板**:
- 用户点击节点 → 白板切换显示该节点的详细内容
- 用户切换焦点 → 白板内容跟随切换
- 用户在图上做任何选择 → 白板上下文跟随更新

**白板→图**:
- 用户在白板里完成某项决策 → 对应图节点状态变为"已解"
- 用户在白板里识别新问题 → 图上自动增加新节点(待用户确认)
- 用户在白板里上传外部产物 → 图上对应节点出现"已挂载产物"的视觉提示
- 用户在白板里标记冲突 → 图上对应连线变红

### 6.3 白板的内部架构(待专题深化)

白板不只是一个文档框,是一个可嵌套展开的多视图容器,包含:
- 节点的讨论历史
- 挂载的外部产物(平面、效果图、聊天记录等)
- 该节点的局部子图视图
- 决策记录、推理链
- 链接到其他节点的白板
- 用户的笔记和工作记录
- **Graph-aware AI 对话面板**(详见第 12 章)

白板的详细架构在"专题 C"里深化。

## 7. 项目初始化流程

### 7.1 用户进入项目的几种姿态

用户进入项目图谱有三种典型姿态:

**姿态 A:从一句话开始**——用户输入"我想做一个山地民宿",别的什么都没有。

**姿态 B:带着片段资料进入**——用户上传一份建筑平面,或一份甲方需求文档,或一段聊天记录。

**姿态 C:从对话延伸成项目**——用户在浅滩对话中和方案高参聊了几轮,系统识别"这是一个连续项目",提示升级为项目档案。

### 7.2 从零到问题图谱的过程

无论哪种进入姿态,系统都通过以下流程把它编译为初始项目图谱:

1. **意图解析**:调用 AI 理解用户输入(文本/文件/对话历史),识别项目类型和核心要素
2. **生成初始节点**:基于项目类型,自动创建 3-5 个初始问题节点。典型如:
   - "明确项目目标"
   - "获取建筑条件"
   - "确定预算范围"
   - "识别核心人群"
   - "梳理关键约束"
3. **填充已知信息**:把用户已经提供的信息填入对应节点
4. **生成预设依赖**:基于项目类型,自动建立常见依赖关系
5. **展示初始图**:用户进入分组网络态,看到 3-5 个节点和它们的关系
6. **用户可增删改**:用户可以删除不相关的初始节点、添加新节点、调整依赖

### 7.3 预设依赖与系统推荐

**预设依赖**:由项目类型模板决定。系统预先维护每种项目类型(民宿/办公/餐饮/商业/展厅等)的"典型问题清单"和"典型依赖关系"作为初始化模板。

**系统推荐**:在项目演化过程中,每当用户创建新节点,系统根据该节点的语义,推荐:
- 可能相关的其他节点
- 可能的依赖关系
- 可能挂载的知识卡片

推荐只是建议,用户可以接受、拒绝、修改。

### 7.4 外部产物驱动的初始化

如果用户上传了建筑平面、需求文档等外部产物,系统执行额外步骤:

1. **外部产物理解**:调用对应能力(FloorPlanIR 编译器、文档解析器等)理解产物语义
2. **自动创建相关节点**:例如理解到"建筑面积 2400 平米、有 8 个柱位",自动创建"建筑承载"约束节点并填入信息
3. **关联到 source_refs**:节点的 `source_refs` 指向该外部产物的对象引用
4. **置信度标注**:系统对外部产物的理解质量给出置信度,标注"待确认"状态等待用户审阅

## 8. 项目图谱与后台语义层的衔接

### 8.1 项目图谱不是真相源,是认知索引层

**根本定位**:

```
项目图谱(前台) = 认知关系索引层
对象链(后台) = 真相源(AlignedBrief / SPG / FloorPlanIR / VizSpec / InitialDesignPack)
知识库(后台) = AI 世界理解的资源池
本体论(后台) = 项目类型与问题结构的模板
```

项目图谱的节点和边,通过引用机制与后台三者发生关系,**不复制后台内容形成并行真相**。

### 8.2 与对象链的关系

每个项目图谱节点都有 `source_refs` 字段,指向对象链中的具体对象:

```
目标节点    → 引用 AlignedBrief 中的目标/成功标准条目
约束节点    → 引用 SPG 中的硬约束、BuildingCarrierBaseline
问题节点    → 引用 SPG 中的待解决项、AlignedBrief 中的待确认项
决策节点    → 引用 InitialDesignPack 中的冻结决策
依据节点    → 引用知识库卡片、规范条文、案例参照
风险节点    → 引用 AlignedBrief / SPG 中标注的风险条目
```

**关键规则**:
- 节点的 `source_refs` 是只读引用,不可在项目图谱中直接修改对象链内容
- 修改对象链内容必须走对象链自身的治理流程(冻结/升版/回退)
- 对象链版本变化时,通过 `source_refs` 反向通知相关节点更新状态

### 8.3 与知识库/本体论的关系

**知识库作为依据节点的来源池**:
- 每个问题节点可以挂载多个知识库卡片作为"依据节点"
- 系统根据问题文本语义,自动从知识库检索相关卡片,在白板中推荐
- 用户可以选择接受推荐,把卡片转化为依据节点

**本体论作为初始问题图谱的模板**:
- 本体论中按项目类型组织的"问题结构"和"`ask_yourself` 维度",作为生成初始问题图谱的模板
- 例如本体论里"民宿"类型下定义的关键问题维度,自动转化为该项目的初始问题节点

### 8.4 source_refs 机制的工程要求

- 所有节点必须有 `source_refs`(可以为空数组,但不能没有该字段)
- 对象链对象升版时,相关节点的状态自动变为"待复核"
- 节点删除时,只删除引用关系,不删除被引用的对象链对象
- 节点的内容显示优先级:本节点 summary → source_refs 中对象的对应字段

## 9. 外部产物对账机制

### 9.1 对账作为节点状态变化(不另立颜色)

**关键裁决**:外部产物对账的结果**不另立颜色系统**,而是通过节点状态变化体现。

具体规则:

- **对账成功**:外部产物自洽地解决了某个问题节点 → 节点状态变为"已解"(绿色)
- **对账冲突**:外部产物违反了已有判断 → 节点状态变为"冲突"(红色),白板详细说明
- **部分匹配有缺口**:外部产物部分解决某节点但有信息缺口 → 节点状态保持原状,**增加黄色"待复核"小角标**

### 9.2 置信度与确认状态(双字段)

对账结果不只有状态变化,还要带置信度和确认状态:

| confidence(置信度) | confirmation_status(确认状态) | 含义 |
|---|---|---|
| 高 | 已确认 | 绿色 + 锁定 |
| 高 | 待复核 | 绿色 + 小角标 |
| 中 | 待复核 | 颜色保持 + 黄色角标 |
| 低 | 待补资料 | 黄色角标 + 提示补充 |
| 高(冲突方向) | 阻断 | 红色 |

**根本判断**:AI 不会 100% 准确判断外部产物,必须留下"系统判断 + 人工确认"的两层。

### 9.3 节点的事件视觉提示(克制版 + 级联传导)

外部产物进入或冲突发生时,系统通过克制的视觉提示让用户注意到:

- **外部产物进入对应节点**:节点边框轻微闪烁一次(不是持续脉冲)
- **冲突发生**:相关节点和连线红色显示,**不抖动**
- **级联传导**:改动一个节点,牵动的其他节点视觉上跟随渐变过渡(0.5 秒),用临时高亮(2 秒后淡化)显示"牵动了什么"
- **关键原则**:用户能注意到事件,但视觉不夸张

### 9.4 白板自动同步

任何对账事件发生时,右侧白板自动滚动到相关节点,展示:
- 事件说明
- 冲突详情(如果是冲突)
- 系统判断的置信度
- 系统建议的处理路径
- 等待用户确认的操作选项

## 10. 语义缩放(MVP 简化版)

### 10.1 MVP 简化方案

完整语义缩放工程量大且需要先定义节点重要性算法。MVP 阶段采用简化版:

**三级缩放**:

| 缩放层级 | 显示内容 | 适用场景 |
|---|---|---|
| **最小缩放(俯瞰)** | 只显示问题域聚类块,不显示内部节点 | 看项目整体状态 |
| **中等缩放(默认)** | 显示所有节点和主要关系 | 日常工作 |
| **最大缩放(深入)** | 显示所有节点、所有边、节点元信息 | 深入处理一组相关问题 |

### 10.2 缩放的实现要点

- 缩放通过滚轮、双指、或界面按钮触发
- 缩放过程平滑过渡,不卡顿
- 节点位置在缩放过程中保持相对稳定
- 用户可以一键回到默认缩放层级

### 10.3 暂缓的能力(后续版本)

- 按节点重要性动态过滤
- 节点合并后的关系抽象表达
- 多布局持久化
- 自动影响范围推演的可视化

## 11. 结构空白引擎(产品智能的核心)

### 11.1 产品智能的真正落点

项目图谱的产品智能不在于"画得多漂亮",在于**主动显现用户没看到的事**。

传统工具回答用户问的问题。项目图谱**显现用户没问但应该问的问题**——主题簇之间的连接缺失、本该有但没有的节点、被大词遮蔽的真实问题、孤立的飞地节点。

这是产品的核心差异化,远比"AI 自动生成任务书"更有价值。

### 11.2 四类结构空白

**类型 A:孤立节点(Isolated Node)**

某个节点没有任何边连接到其他节点。这通常意味着:
- 这个节点是冗余的(应该删掉)
- 或者是项目里的"飞地"(它的关联没被识别)

**系统行为**:在该节点旁显示"孤立提示"小标记。用户聚焦该节点时,白板提示:**"这个节点目前是孤立的。它和其他哪些问题有关?"** 并推荐 3-5 个语义相关的节点供用户选择是否建立连接。

**类型 B:本该连接但未连接(Missing Link)**

基于项目类型和知识库,系统识别"两个节点应该有连接但没有"的情况。例如:
- "HAY 气质" 节点和"材料耐久" 节点之间应该有连接,但没有
- "客群定位" 节点和"房型配置" 节点之间应该有连接,但没有
- "效果图方向" 节点和"平面版本" 节点之间应该有连接,但没有

**系统行为**:在自由网络态下,这类"潜在连接"以**虚线灰色**显示(区别于实线的已有连接)。用户聚焦其中一个节点时,白板提示:**"它和 X 节点可能有关联,要不要建立连接?"**

**类型 C:本该有节点但没有(Missing Node)**

系统从项目类型的本体模板出发,识别"这类项目通常有 X 节点,但当前项目没有"。例如:
- 山地民宿项目通常有"维护成本"节点,但当前项目没有
- 茶饮店项目通常有"员工后勤"节点,但当前项目没有
- 高端私宅通常有"声环境"节点,但当前项目没有

**系统行为**:在项目图谱的某个侧边面板(可折叠)显示"建议补充的节点"列表。用户可以一键添加或忽略。

**类型 D:被大词遮蔽的盲区(Abstract Cover-up)**

当项目里出现大量抽象大词(高级感/疗愈/东方/自然/松弛/在地性等)时,真实的具体问题可能被遮蔽。系统识别这种情况并提示。

**系统行为**:见第 13 章"隐藏大词机制"。

### 11.3 实现路径

**MVP 阶段**(规则 + 模板):
- 孤立节点识别:简单的图论遍历,O(n) 复杂度
- 缺失连接识别:基于项目类型预设的"典型关系模板"做模式匹配
- 缺失节点识别:基于项目类型预设的"典型节点清单"做差集计算
- 大词识别:基于大词词典做语义判断

**后续阶段**(算法 + AI):
- 缺失连接识别可升级为基于语义相似度的推荐
- 缺失节点识别可升级为基于历史项目模式的智能推荐
- 大词识别可升级为基于语义嵌入的精确判断

### 11.4 与用户的交互方式

结构空白识别的提示**克制呈现,不打扰**:

- 不弹窗、不强制
- 在自由网络态下用虚线/灰色显示潜在连接
- 在侧边面板(可折叠)显示建议补充节点
- 用户聚焦相关节点时,白板里给出友好提示
- 用户可以一键采纳、一键忽略、永久关闭某类提示

**核心姿态**:系统主动显现,但用户自由决定。

### 11.5 结构空白识别的产品价值

对用户的真实价值不是"系统帮我想到了 X 个我没想到的问题",而是:

- **降低盲区焦虑**:用户不再担心"我有什么没想到的"——系统会主动指出
- **专业感的代偿**:即使经验不足的设计师,也能在系统引导下覆盖到关键问题
- **决策质量的兜底**:项目图谱不会因为某个关键问题被遗漏而崩盘

## 12. Graph-aware AI(AI 的图谱上下文)

### 12.1 AI 必须基于子图上下文,不是全项目泛答

**根本判断**:方案高参的 AI 不是泛泛的对话助手。所有 AI 动作的回答上下文**严格限定于当前可见子图**——即当前焦点节点 + 它的关联子图。

这件事让用户感受到"系统真的懂我项目当下的处境",而不是"AI 在对我说一些放之四海的通用建议"。

### 12.2 触发场景

Graph-aware AI 在以下场景被触发:

**场景 1:用户聚焦某个节点后,问 AI 问题**
AI 的上下文限定于:该节点 + 一跳关联 + 二跳关联 + 它们的状态和属性。

**场景 2:用户框选多个节点,请求 AI 分析**
AI 基于这组节点的图结构,回答类似:
- "这组节点的核心矛盾是什么?"
- "这组节点里最关键的阻塞是什么?"
- "这组节点之间还缺什么连接?"
- "基于这组节点,下一步应该处理什么?"

**场景 3:系统主动触发(基于结构空白识别)**
当系统识别到关键盲区时,AI 主动在白板里给出针对性的解读和建议。

**场景 4:对账事件发生时**
外部产物进入并触发对账冲突时,AI 基于冲突涉及的节点子图,给出冲突分析和建议处理路径。

### 12.3 输出形态

Graph-aware AI 的输出有几种典型形态:

- **子图解读**:这组节点的状态、关系、矛盾、可能性
- **盲区追问**:"我注意到 X 和 Y 之间没有连接,是不是…"
- **关键瓶颈识别**:"在这组节点里,X 是最大的阻塞,因为…"
- **下一步建议**:"基于当前状态,建议先处理…"
- **历史对照**(基于跨项目接口,后续):"类似项目里,X 通常和 Y 有关…"

### 12.4 文理分流原则的延续

Graph-aware AI 依然遵循文理分流:

- **理科问题**(尺度计算、规范查询、影响范围分析):AI 直接给答案
- **文科问题**(立场判断、风格选择、价值取舍):AI 只给可能性集合,不替用户决定
- **文理交界**:AI 给出客观分析 + 主观可能性

**关键约束**:即使有了 Graph-aware AI,系统也不替用户做最终判断。AI 的角色始终是"放大用户的认知",不是"替代用户的判断"。

### 12.5 技术实现要点

- AI 的 prompt 必须把当前子图状态(节点列表、边列表、状态分布、关键属性)作为结构化上下文传入
- **不**把整个项目的完整数据传入(避免噪音 + 节省 token)
- 子图序列化为简洁的结构化文本格式(YAML 或 JSON)
- AI 的回答必须可被回写到节点白板,并标注"AI 生成 / 待用户确认"

## 13. 隐藏大词机制

### 13.1 大词遮蔽是设计行业的真问题

设计行业大量使用抽象大词:**高级感、轻奢、松弛、东方、自然、疗愈、未来感、在地性、克制感、生活方式…**

这些词让讨论显得有深度,但**它们常常掩盖了项目的真实问题**。一个项目讨论了 50 次"高级感",可能完全没讨论过"层高、预算、材料耐久"。

### 13.2 大词清单与识别

系统维护一份"设计行业大词清单",作为可隐藏的对象。清单包含两类:

**类型 1:风格大词**——高级感、轻奢、松弛、东方、未来感、复古、工业…
**类型 2:情绪大词**——疗愈、温馨、宁静、生机、克制、自然…

每个节点的 `abstraction_level` 字段标记它是"具体问题 / 中层概念 / 抽象大词"——这个字段在节点创建时由系统判断,用户可以手动调整。

### 13.3 隐藏与还原的交互

**入口**:项目图谱的工具栏有一个"隐藏大词"切换按钮(或绑定快捷键)。

**隐藏后**:
- 所有 `abstraction_level = 抽象大词` 的节点变灰、半透明
- 这些节点的边也淡化
- 用户看到的是"剥离大词后的真实问题骨架"

**还原**:再次点击切换按钮,大词节点恢复正常显示。

### 13.4 价值

**对设计师的价值**:让设计师立刻看到"剥离漂亮话后,我项目里到底剩下什么真问题"。如果剥离后图谱明显萎缩,说明项目讨论被大词遮蔽——这是系统给的真实警示。

**对甲方的价值**:汇报时切到"隐藏大词"模式,甲方看到的是项目的具体决策和约束,不是空泛的形容词。

**产品价值**:这个功能工程代价小,商业故事极强——"它居然能帮我看穿大词遮蔽下的真实问题"。

## 14. 跨项目图谱接口(长期愿景,留接口)

### 14.1 单项目认知 vs 设计师经验系统

**单个项目图谱**:这个项目的认知工作面——做完一个,就是一个完整的项目交付资产。

**跨项目图谱**:设计师做的所有项目的集合——这是设计师的**经验系统**,是真正的长期资产。

跨项目图谱让用户能问:
- "我过去有哪些项目也出现过'预算压缩影响材料策略'的情况?"
- "类似'山地民宿 + 年轻客群 + 低预算'的项目,我之前怎么处理的?"
- "我做过的所有民宿项目里,哪些节点是高频出现的?"
- "我的设计立场倾向于克制还是张扬?基于历史项目的判断模式来看…"

### 14.2 接口预留(MVP 不实现)

虽然 MVP 不实现跨项目能力,但**主架构必须为它留出接口**:

- 每个项目图谱有 `project_id` 和 `designer_id`
- 节点和边的语义编码可跨项目共享(节点类型、状态、问题域等)
- 项目图谱的归档机制要支持"长期可检索"(不是关闭即销毁)
- 设计师的偏好、风格、判断模式从项目图谱中可被提取(reservoir for 硅基分身)

### 14.3 与硅基分身的天然衔接

跨项目图谱是硅基分身的**基础数据**:

- 硅基分身的"立场镜像"——从设计师历史项目的所有决策节点反推
- 硅基分身的"风格画像"——从设计师历史项目的所有立场选择反推
- 硅基分身的"经验代偿"——基于历史项目相似性提供建议

**这条接口立住,方案高参就具备了"用户做的越多、系统越懂他"的长期复利**。这是产品真正的护城河。

### 14.4 长期愿景的产品形态

跨项目能力激活后(可能在产品 v2.0 或 v3.0),用户的体验是:

- 开始新项目时,系统主动检索"你历史上类似的项目"
- 处理某个问题时,系统提示"你上次类似情况是这样判断的"
- 项目结束时,系统自动萃取本项目的经验回流到设计师经验池
- 设计师能查看自己的"决策风格画像"、"常用判断模式"、"擅长领域分布"

**这件事不实现,只留接口**。但它是产品长期价值的根本锚点。

## 15. 主架构的边界与不做的事

### 15.1 不做的事

1. **不做五层堆叠或任何层级堆叠的视觉表达**
2. **不做文本列表作为与项目图谱并列的第二套世界观**(列表只作为筛选结果、节点详情、白板子视图、导出形态出现)
3. **不做力导向算法实时驱动节点位置**(位置必须稳定)
4. **不做节点的剧烈抖动、华丽动效**(克制视觉)
5. **不在前台主图谱展示知识概念节点**(知识图在后台,不进前台)
6. **不让用户必须填表才能开始**(初始化流程承接)
7. **不强制流程顺序**(用户可以处理任何节点)
8. **不把项目图谱当作所有对象的真相源**(项目图谱是认知索引层,真相在对象链)
9. **不做两套颜色系统**(颜色唯一由状态决定)
10. **不做 AI 替用户最终判断**(文理分流,文科 AI 退后)
11. **不做实时 Louvain 算法重新聚类**(用预定义六大问题域,系统稳定)
12. **不做词语共现作为边**(节点不是文本词,边不是共现关系)
13. **不做"AI 自动生成项目认知"的过度承诺**(系统是认知放大器,不是替代品)

### 15.2 必须做的事

1. **网络作为唯一前台视觉**(两态切换)
2. **节点位置稳定**(空间记忆)
3. **节点中心性自动视觉编码**(关键节点自动凸显)
4. **边的 strength 视觉编码**(强依赖更紧、弱关系更松)
5. **焦点子图作为工作态**(80% 时间在子图)
6. **图与白板双向联动**
7. **节点和边的类型、状态系统**(最小集先实现)
8. **跨域强依赖在分组态保留为半透明实线**
9. **外部产物对账机制**(带置信度和确认状态)
10. **简化版语义缩放**(三级)
11. **项目初始化流程**(三种姿态都能承接)
12. **与对象链的 source_refs 引用机制**
13. **结构空白引擎**(四类盲区识别)
14. **Graph-aware AI**(基于子图上下文)
15. **隐藏大词机制**
16. **跨项目接口预留**(为硅基分身留出路径)

## 18. 一句话收束

> **项目图谱是方案高参的认知中枢——以项目认知对象为节点,以问题间真实关系为边,以稳定位置保护空间记忆,以焦点子图承接日常工作,以双向联动连接图与白板,以 source_refs 与对象链衔接而不复制真相,以前台反线性、后台有治理保持工程严谨。它的核心智能不在于"画得多漂亮",在于"主动显现用户没看到的事"——结构空白引擎识别孤立节点、缺失连接、缺失节点、大词遮蔽四类盲区;Graph-aware AI 基于子图上下文给出针对性洞察;隐藏大词让设计师看穿漂亮话遮蔽下的真实问题。它对内严谨保留所有工程对象,对外极简归入"设计任务书 2.0"的能力;它为跨项目能力和硅基分身留出长期接口,让用户做的越多、系统越懂他。这不是更好的设计工具,是 AI 时代设计行业前所未有的认知操作系统底盘。**
