## 1. 交叉校验与冲突排查

### 1.1 冲突一：第二步是自动展示，还是用户点击进入？

主架构早期表述倾向于：

```text
两轮问诊后直接看到三档版本选择界面。
```

参考意见提出：

```text
第二轮回答后先出阶段结论，再由用户点击进入版本选择与目录预成型。
```

排查：

```text
如果自动展示三档卡，容易从“问诊”突然跳到“购买/会员页”，压迫感较强。
如果重新要求用户确认一堆信息，又会破坏“第二步不再问诊”的纪律。
```

结论：

```text
系统后台自动准备三档版本选择包；
前台先展示阶段结论和“查看三档版本”CTA；
用户点击 CTA 后展开版本选择界面。
```

这不是新增问诊，也不是提前付费弹窗，而是一个“主动展开”的体验缓冲。

### 1.2 冲突二：是否新增独立接口，还是复用现有对话接口？

参考意见提到在对话主路由中新增第二步编排节点。此前执行思路倾向复用 `/api/v2/conversation/message` 的 `guidance_card`。

排查：

```text
新增独立接口有利于协议清晰，但会增加前端调用路径和状态同步复杂度。
复用现有对话接口可减少改动，且当前前端已经支持 guidance_card 和 card response。
```

结论：

```text
第一期复用 /api/v2/conversation/message；
用 guidance_card.card_type 区分 first_round、second_round、stage_conclusion、version_selection；
只有进入正式生成、支付或项目态升级时，再考虑独立接口。
```

### 1.3 冲突三：第一步是否必须补齐准入项？

三档版本差异文档中有“准入闸口”，参考意见也强调状态扩展与规则冻结。

排查：

```text
如果把准入闸口前台化，会导致两轮问诊后继续补表；
如果完全不管准入，又可能生成不可靠目录。
```

结论：

```text
准入判断系统内部完成；
第一步双回合尽量覆盖目录生成必需项；
第二步不再继续追问；
缺失项进入假设、待确认和正式阶段校准。
```

只有项目身份级硬缺失才阻断，例如无法判断是否为设计项目、空间/业态对象、项目目标或产品边界。

### 1.4 冲突四：是否立即改造正式任务书生成链？

参考意见列出了 `main_workflow.py`、`progressive_questionnaire.py` 等核心工作流文件。

排查：

```text
若第一期直接改正式任务书深层算法，风险大、联调长、回退困难。
当前目标只是入口问诊到版本选择，不是正式任务书生成。
```

结论：

```text
第一期只做入口态和版本选择态；
不重构 CAD 解析；
不重写正式任务书生成；
不接支付结算；
不重构深层工作流。
```

### 1.5 冲突五：当前代码中已有 Advisor 子图，是否直接接入？

现有 `advisor_workflow.py` 是独立 AdvisorAgent 子图，偏对象读路径和 AdvisorViewModel；首页当前实际走 `/api/v2/conversation/message`。

排查：

```text
直接把本次入口流塞进 Advisor 子图，会混淆“方案高参首页入口”和“项目态 AdvisorAgent”。
继续沿用 conversation message 更贴近当前用户路径。
```

结论：

```text
第一期入口流放在 conversation 主链；
Advisor 子图后续可复用为项目态能力，但不作为本次入口实现主线。
```

### 1.6 冲突六：三档卡片是否像会员页？

用户参考图是会员卡片样式，但方案高参不是普通订阅会员。

排查：

```text
视觉上可借鉴会员卡的清晰对比；
内容上不能变成“年费会员权益”，必须是专业服务版本选择。
```

结论：

```text
采用卡片式三档选择界面；
卡片内容使用“版本定位 / 适合对象 / 核心价值 / 包含内容 / 限制 / 价格占位 / 选择按钮”；
不使用普通会员话术。
```

### 1.7 冲突七：Feature Flag 是否必要？

参考意见建议 Feature Flag 灰度。

排查：

```text
本次改动影响首页首次体验、对话状态、版本选择 UI 和后端协议；
风险集中在入口转化链路，必须可回退。
```

结论：

```text
必须使用 Feature Flag；
关闭后完全回到旧 conversation message 路径和旧 guidance_card 渲染。
```

## 2. 实施总目标

实现一条从首页输入到三档版本选择的闭环：

```text
首页输入
→ 首次信心响应 + 第一轮追问
→ 用户回答
→ 二次信心强化 + 第二轮追问
→ 用户回答
→ 阶段结论 + 查看三档版本 CTA
→ 三档版本选择卡片 + 目录预成型
→ 用户选择基础版 / 标准版 / 专业版
→ 进入后续正式生成阶段
```

第一期只覆盖：

```text
文本输入；
茶饮空间；
两轮问诊；
阶段结论；
三档版本卡；
标准版推荐；
版本选择记录。
```

第一期不覆盖：

```text
支付结算；
CAD 解析；
正式完整版任务书生成；
多业态泛化；
完整知识库检索；
深度研究实际执行。
```



## 6. 验收标准

### 6.1 产品体验验收

```text
用户初始输入后，首响有洞察，不是表单；
第一轮和第二轮每轮不超过 3 问，复杂项目最多 5 问；
第二轮后稳定进入阶段结论，不继续问诊；
阶段结论后有“查看三档版本”CTA；
点击 CTA 后展示基础版 / 标准版 / 专业版；
标准版可被系统推荐高亮；
未上传 CAD 不阻断版本选择和目录预成型；
选择版本后会话状态能记录。
```

### 6.2 技术验收

```text
Feature Flag 关闭可无损回退旧流程；
刷新页面后可恢复当前入口阶段；
guidance_card 协议向后兼容旧卡片；
后端状态可追踪每轮回答和版本选择；
异常时降级为普通对话，不阻塞用户；
旧会话列表、旧 analysis 页面不被破坏。
```

### 6.3 内容质量验收

```text
不暴露空间分类、本体论、知识库等后台术语；
不把三档说成三个产品；
不把基础版贬低成低配；
不把标准版推荐写成硬销售；
不对未读 CAD、未确认设备、未确认回本数据做伪确定结论。
```

## 7. 风险与缓解

| 风险 | 表现 | 缓解 |
|---|---|---|
| 入口状态与旧会话冲突 | 旧 session 解析失败 | Feature Flag + 兼容旧 guidance_card |
| 卡片协议过重 | 前后端联调慢 | Phase 1 先 mock version_cards |
| 三档卡片像普通会员页 | 降低专业感 | 卡片文案使用版本定位和任务书模块，不用会员权益话术 |
| LLM 输出不稳定 | 追问跑偏、字数失控 | 结构化字段 + 模板约束 + 质量守卫 |
| 第二轮后仍想追问 | 破坏机制纪律 | 缺失项后置为待校准，不继续问 |
| 标准版推荐被认为硬推 | 用户不信任 | 同时说明基础版可用、专业版触发条件 |
| 过早触发上传/付费 | 转化压迫 | 当前阶段只展示版本选择，不触发 CAD 上传和付费弹窗 |

## 8. 合理化执行思路

执行顺序应遵循：

```text
先协议，后 UI；
先 mock，后智能；
先茶饮，后多业态；
先入口体验，后正式任务书生成；
先 Feature Flag 内测，后灰度扩量。
```

推荐最小闭环：

```text
1. 后端返回固定茶饮三档卡片 mock；
2. 前端渲染三档卡片并可选择；
3. 后端记录 selected_version；
4. 再接入双回合状态机；
5. 最后接入 LLM 洞察和规则推荐。
```

这样可以先验证关键用户体验：

```text
用户是否愿意完成两轮回答；
阶段结论是否增强信心；
```

## 10. 定盘表述

本实施计划的核心不是重写方案高参，而是在现有对话态入口上增加一个可灰度、可回退的“双回合问诊 → 阶段结论 → 三档版本选择”闭环。

第一期只把用户带到“看懂项目、完成两轮投入、理解三档差异、选择版本”的节点；正式任务书生产、CAD 解析和支付结算留在后续阶段。

```text
先把入口转化链跑顺，再把正式生产链接上。
```
