# 方案高参一二轮追问专题机制

版本：v1.0
日期：2026-06-16
适用范围：方案高参入口阶段，从用户初始项目描述到正式任务书生成前的两轮追问机制。
开发定位：这是通用追问框架，不是茶饮空间、菜市场空间或任何单一空间类型的专属模板。

---

## 0. 与需求重构阶段的关系

需求重构加入后，一二轮追问仍然保留，而且位置更清楚。

需求重构负责第一次“懂我”：

```text
用户模糊表达
↓
需求重构先命中真实问题
↓
用户产生信任和期待
```

一二轮追问负责正式“问诊”：

```text
需求重构行动蓝图
↓
第一轮：承接显性锚点，补齐任务书事实基础
↓
第二轮：追问隐性矛盾，锁定任务书取舍边界
↓
阶段结论 / 目录重心 / 版本深度
```

因此，一二轮追问不再承担“从零证明你懂我”的全部压力。这个动作已经由需求重构在前一拍完成。一二轮追问的职责，是在用户已经愿意继续的前提下，把行动蓝图转换成正式设计任务书所需的稳定输入。

核心纪律：

1. 需求重构阶段已经确认的信息，一二轮不重问。
2. 第一轮追问不是冷启动问卷，而是承接行动蓝图后的正式校准。
3. 第二轮追问不重复需求重构的命题判断，而是把命题背后的取舍问清。
4. 如果用户直接输入任务书级问题，可跳过需求重构，直接进入一二轮追问。

---

## 1. 专题背景

方案高参入口阶段不能把用户刚提出的问题直接拆成泛化选项，也不能把系统内部分类、语义轴或英文 key 暴露给用户。

这次蛇口菜市场案例暴露的问题，本质不是“选项文案不够好”，而是追问机制没有按用户认知顺序展开：

1. 第一轮没有正面接住用户原题中的显性信息。
2. 第二轮没有进入用户未说出口、但方案必然要面对的隐藏矛盾。
3. 选项语义不清，单选、多选、优先级选择混在一起。
4. 标题和选项出现内部化、英文 key 化、凑数化。
5. 某一类空间的修正容易污染通用系统，产生“茶饮化”或“菜市场化”风险。

因此，一二轮追问要被定义为一个稳定的通用机制：

- 第一轮：原题显性锚点承接。
- 第二轮：隐性矛盾与底层取舍追问。
- 后续正式任务：展开未追问的细节、模块、清单和执行项。

---

## 2. 核心原则

### 2.1 第一轮不是选择题，而是正式校准显性锚点

在没有需求重构前，第一轮承担“我听懂了什么”的主要职责。需求重构加入后，这句话需要更精确：

> 第一轮不是第一次证明“我懂你”，而是在需求重构之后，正式确认“哪些显性事实要进入设计任务书”。

第一轮的首要目标不是马上让用户选择，而是让用户感到系统没有丢掉他原题和需求重构中已经形成的判断。

系统应先逐条回应用户明确说出的内容：

- 项目对象
- 对标对象
- 在地文化
- 服务对象
- 目标动机
- 任务范围
- 额外约束
- 特殊风险
- 阶段要求
- 交付要求

这些都是用户已经给出的显性锚点。系统必须先接住，再进入追问。

如果前置需求重构已经形成了项目命题、头号风险或关键未知，第一轮应以“已继承行动蓝图”的方式进入，不应重新问用户“你想做什么项目”。

### 2.2 第一轮不固定 3 点或 4 点

第一轮显性锚点数量不应硬编码。

规则：

1. 用户原题有几条关键显性锚点，就尽量逐条对应。
2. 不强行压成 3 点或 4 点。
3. 如果显性锚点超过 6 条，只展示前 6 条。
4. 超过 6 条的部分，用备注告诉用户：
   “其余未追问部分将在正式任务中展开。”

这样既避免遗漏用户关心的问题，也避免入口阶段过度发散。

### 2.3 第二轮不是复述任务清单，而是追问隐藏矛盾

第二轮要避开用户已经明说的内容，转向用户没有直接说、但逻辑上必须面对的问题。

第二轮关注：

- 潜在冲突
- 真实取舍
- 成本承担
- 运营边界
- 体验优先级
- 风险阈值
- 价值排序
- 决策前提
- 失败点

例如用户说“兼顾老居民、香港访客、外籍客群与社区居民”，第二轮不应再问“你要兼顾谁”，而应问：

- 如果老居民买菜便利和游客体验冲突，谁优先？
- 如果文化展示增加维护成本，谁承担？
- 如果城市标杆提高形象，但推高摊贩成本，是否接受？

### 2.4 不把系统带到某一空间分类

任何空间类型都只能贡献语义轴和案例知识，不能劫持追问框架。

茶饮、菜市场、酒店、住宅、办公、展馆、医疗、乡建等，都应共享同一个追问骨架：

- 原题显性锚点
- 隐性矛盾推理
- 用户可理解的选择语义
- 结构化答复回收
- 正式任务展开

空间分类只决定具体词汇、风险轴和追问候选，不决定通用流程。

## 3. 第一轮机制：显性锚点承接

### 3.1 第一轮目标

第一轮要完成三件事：

1. 继承需求重构中已经形成的项目命题和关键判断。
2. 把原题中的关键内容逐条转成可确认锚点。
3. 告诉用户哪些内容现在确认，哪些内容正式任务中展开。

第一轮不是为了快速收集答案，而是为了把已经建立的信任转成正式任务书输入。

### 3.2 显性锚点类型

| 锚点类型 | 识别来源 | 用户可见表达 |
| --- | --- | --- |
| 项目对象 | “某某项目 / 空间 / 店 / 馆 / 市场 / 中心” | 先确认这是什么项目、什么尺度、什么阶段 |
| 对标对象 | “对标 / 参照 / 借鉴” | 哪些可迁移，哪些不能照搬 |
| 在地文化 | “融入 / 转译 / 传统文化 / 文脉 / 记忆” | 如何从符号变成空间秩序 |
| 服务对象 | “兼顾 / 面向 / 服务” | 谁的使用不能被牺牲 |
| 目标动机 | “成为 / 打造 / 目标是” | 项目最终靠什么成立 |
| 任务范围 | “包括 / 涵盖 / 说明” | 哪些内容进入正式任务 |
| 额外约束 | “另需 / 还需 / 同时还需” | 记录为后续深化约束 |
| 阶段要求 | “概念阶段 / 竞标 / 施工 / 改造” | 影响输出深度和确定性 |

### 3.3 第一轮输出格式

推荐格式：

```text
我会继承刚才的需求重构判断，先按你原题里的显性锚点逐条校准：

1. 项目对象：……
2. 对标对象：……
3. 在地文化：……
4. 服务对象：……
5. 目标动机：……
6. 任务范围：……

备注：还有……等未追问部分，我会在正式任务中展开，不在第一轮把问题问散。
```

如果用户没有经历需求重构，而是直接给出任务书级输入，则可去掉“继承刚才的需求重构判断”，直接进入显性锚点校准。

### 3.4 数量规则

| 情况 | 处理 |
| --- | --- |
| 1-2 条锚点 | 全部展示，可补一句“当前信息还较少” |
| 3-6 条锚点 | 全部展示 |
| 超过 6 条 | 展示前 6 条，剩余放备注 |
| 没有明确锚点 | 回退到项目类型、使用者、目标、边界四类基础校准 |

### 3.5 第一轮选项规则

第一轮可以有选项，但选项必须服务于显性锚点确认，不能成为固定流程按钮。

选项必须标明语义：

- 单选：只能确认一个主导方向。
- 多选：可以确认多个并列锚点。
- 优先级选择：用户点击顺序代表优先级。
- 可跳过：允许信息不足时进入下一步。
- 可补充：允许用户用自由文本纠偏。

不允许出现：

- “选择判断路径”
- “先看项目靠什么成立”
- 英文 key
- 和标题不对应的凑数选项
- 用户无法判断单选还是多选的 UI

## 4. 第二轮机制：隐性矛盾追问

### 4.1 第二轮目标

第二轮要进入用户没有直接说出口，但方案一定要面对的问题。

第一轮问：“你说了什么，我是否理解对？”

第二轮问：“你没说但必须决定的取舍是什么？”

如果前置需求重构已经指出了主矛盾，第二轮不应重复那个判断，而应继续追问：

```text
这个主矛盾成立后，哪一个取舍最不能含糊？
```

换句话说，需求重构负责“看见命门”，第二轮负责“确认命门牵动的取舍边界”。

### 4.2 隐性矛盾来源

| 隐性来源 | 典型问题 |
| --- | --- |
| 多客群冲突 | 不同人群的动线、价格、停留和体验是否冲突 |
| 标杆目标冲突 | 形象传播是否挤压真实运营 |
| 文化表达冲突 | 文化是日常线索，还是拍照符号 |
| 商业可持续冲突 | 谁付成本，谁获得收益 |
| 运营后勤冲突 | 后勤、消防、清洁、排污是否会拖垮体验 |
| 预算与目标冲突 | 目标很高，但投入、周期和维护是否支撑 |
| 阶段深度冲突 | 入口阶段能判断什么，正式阶段再展开什么 |

### 4.3 第二轮输出格式

推荐格式：

```text
第二轮不重复你已经说出的对标、文化和功能模块，而是确认背后没有明说、但会决定方案成败的隐含冲突。

如果只能先判断两件事，哪两件最不能含糊？

1. ……
2. ……
3. ……
4. ……
```

### 4.4 第二轮选项规则

第二轮选项应来自隐性推理，而不是原题表层词汇。

选项类型：

- 冲突对：A 与 B 谁优先。
- 风险阈值：什么情况下不能继续按理想方案推进。
- 成本承担：谁为体验、形象、维护买单。
- 失败点：哪个判断错了会拖垮后续方案。
- 优先级：只能先保住哪几件事。

第二轮常用 `priority_pick` 或 `multi_select`，不宜默认单选。

## 5. 蛇口菜市场案例示范

用户原题：

```text
深圳蛇口20000㎡菜市场更新改造项目，希望对标苏州黄桥菜市场，同时融入蛇口渔村传统文化。需兼顾老居民、香港访客、外籍客群与社区居民，成为城市更新标杆。请提出整体改造框架，包括动线组织、冷链系统、文化展示策略、社交空间植入与商业可持续模型。
```

### 5.1 第一轮应接住的显性锚点

1. 项目对象：深圳蛇口 20000㎡ 菜市场更新改造项目。
2. 对标对象：苏州黄桥菜市场。
3. 在地文化：蛇口渔村传统文化。
4. 服务对象：老居民、香港访客、外籍客群与社区居民。
5. 目标动机：成为城市更新标杆。
6. 任务范围：动线组织、冷链系统、文化展示策略、社交空间植入与商业可持续模型。

第一轮应该让用户感到：

“系统确实围绕我的问题展开，不是在套通用问卷。”

### 5.2 第二轮应追问的隐藏矛盾

1. 民生底盘 vs 城市传播
   老居民日常买菜便利，是否优先于游客体验和标杆形象？

2. 摊贩生计 vs 改造品质
   改造后租金、维护、设备和管理成本是否会挤压摊贩？

3. 文化真实使用 vs 表皮打卡
   蛇口渔村文化是日常市场秩序的一部分，还是外加展示节点？

4. 访客体验 vs 后勤效率
   香港访客、外籍客群的停留体验是否会影响高频采购、补货、清洁和冷链？

5. 公共性 vs 商业可持续
   社交空间和公共展示带来的成本，由谁承担、如何回收？

这些不是用户原题里的模块，而是模块背后的真实取舍。

## 6. 通用开发契约

### 6.1 后端语义层

核心职责：

1. 提取显性锚点。
2. 生成第一轮锚点承接文案。
3. 根据空间类型和语义轴推理第二轮隐性矛盾。
4. 给前端返回明确的选择模式。

关键字段建议：

```json
{
  "prompt_anchors": [
    {
      "label": "对标对象",
      "value": "苏州黄桥菜市场",
      "response": "需要先拆哪些原则可迁移，哪些不能照搬"
    }
  ],
  "response_mode": "multi_select",
  "max_select": 2,
  "hidden_tradeoff": true
}
```

### 6.2 前端交互层

前端必须明确呈现选择语义：

- 单选
- 多选
- 优先级选择
- 可跳过
- 可补充

前端提交时不能只提交拼接文本，应提交结构化卡片响应：

```json
{
  "pages": [
    {
      "page_index": 0,
      "page_title": "哪组隐含冲突最容易撕裂项目",
      "response_mode": "priority_pick",
      "selected_option_ids": ["livelihood_practicality", "vendors"],
      "selected_options": [
        {"option_id": "livelihood_practicality", "priority": 1},
        {"option_id": "vendors", "priority": 2}
      ],
      "freetext": "价格感不能丢，摊贩也不能被挤走"
    }
  ]
}
```

### 6.3 记忆与正式任务衔接

第一轮未展开的锚点不能丢失，应进入正式任务阶段。

前置需求重构产物同样不能丢失，应进入正式任务阶段：

| 需求重构产物 | 一二轮承接方式 |
| --- | --- |
| 真实问题重写 | 第一轮开场继承为项目命题 |
| 关键判断 / 头号风险 | 第二轮转为取舍或风险边界追问 |
| 关键未知 | 第一轮显性锚点或第二轮隐性矛盾 |
| 用户认同的方向 | 阶段结论与目录重心 |
| 行动蓝图路径 | 版本深度与任务书范围 |

建议状态字段：

```json
{
  "deferred_formal_work": [
    "消防验收",
    "夜间运营",
    "租户分级",
    "数字化导览",
    "分期施工计划"
  ]
}
```

## 7. 验收标准

### 7.1 第一轮验收

- 能逐条显示用户原题中的显性锚点。
- 不固定 3 点或 4 点。
- 超过 6 条时只展示前 6 条，并备注其余正式任务展开。
- 不出现内部英文 key。
- 不出现“选择判断路径”等流程词。
- 不把某一空间类型的词汇扩散到其他空间。

### 7.2 第二轮验收

- 不重复第一轮显性锚点。
- 不重复用户原题的模块清单。
- 能提出隐含冲突、真实取舍或风险阈值。
- 能说明选择方式是单选、多选还是优先级。
- 追问能影响后续目录、版本深度或正式任务边界。

### 7.3 回归测试建议

至少覆盖：

1. 蛇口菜市场：显性锚点 6 条完整承接。
2. 超过 6 条锚点：前 6 条展示，其余备注。
3. 第二轮：包含“背后/隐含/取舍/冲突”等隐性判断语言。
4. 非市场项目：不能出现菜市场、摊贩、冷链等误入词。
5. 茶饮项目：不能因茶饮知识库导致所有项目茶饮化。
6. 公共文化、住宅、酒店、办公、医疗等空间类型压力测试。

## 9. 后续开发清单

1. 把显性锚点提取从正则逐步升级为规则注册表。
2. 为不同空间类型补充隐性矛盾候选库。
3. 给每个隐性矛盾增加“为什么必须问”的解释字段。
4. 在前端 UI 明确显示选择模式：单选、多选、优先级。
5. 将第一轮未展开的锚点写入正式任务的 deferred list。
6. 在任务书目录生成阶段引用第一轮锚点和第二轮隐性取舍。
7. 建立跨空间压力测试集，防止茶饮化、菜市场化、酒店化等单空间污染。

---

## 10. 一句话定义

需求重构先让用户确认“你懂我”；第一轮追问负责把用户明说的内容正式带入任务书；第二轮追问负责揭示用户没说但方案必须面对的真实取舍。
