# 方案高参任务书 2.0 产品编排机制

> **文件性质**：产品编排机制定盘稿 / 研发执行稿  
> **适用对象**：方案高参第一阶段产品、任务书生成链路、项目图谱联动、导出与版本治理  
> **核心定位**：把 AdvisorAgent 的运行结果组织成可预览、可确认、可冻结、可导出、可回写、可复盘的 **设计任务书 2.0**。

---

## 0. 总纲

### 0.1 一句话定义

```text
方案高参任务书 2.0 产品编排机制，负责把空间项目中的事实、判断、风险、缺口、选项、决策和证据，组织成一份可交付、可更新、可追踪的设计任务书 2.0。
```

它不是普通文档生成机制，而是空间项目前策阶段的认知交付机制。

它的目标是让一个空间项目在正式画图、汇报、深化、施工和协作之前，先形成一份稳定的项目认知底盘：

```text
项目为什么成立；
谁在使用、运营和拍板；
空间必须承载什么；
现实约束在哪里；
核心矛盾是什么；
设计方向如何收束；
平面前策略如何展开；
哪些风险不能忽视；
哪些判断需要人确认；
哪些事项必须后续验证。
```

### 0.2 产品主语

```text
用户启动空间项目，方案高参生成设计任务书 2.0。
```

所有入口、问诊、图谱、外部产物、知识调用、导出、版本、分档和协作能力，都围绕这个主语组织。

### 0.3 内外两层语言

对外只出现一个产品：

```text
设计任务书 2.0
```

对内保留工程对象：

```text
AdvisorAgent Runtime
Project Cognition Graph
Brief Section Projection
source_refs
structured_missing_slots
maturity_ceiling
snapshot_version
in_session_memory
async_knowledge_governance
```

用户不需要理解这些内部概念。用户感知到的是：

```text
它看懂了我的项目；
它知道哪里不能猜；
它能指出真正的风险；
它能把混乱需求收束成任务书；
它能持续跟踪项目变化；
它能导出给甲方、团队和施工方使用。
```

### 0.4 产品铁律

```text
凡是不提升设计任务书 2.0 生成质量、追踪质量或交付质量的能力，第一阶段不做。
```

## 1. 系统职责边界

### 1.1 本机制负责什么

本机制负责以下产品动作：

```text
1. 把用户输入组织成项目启动语境。
2. 把运行时输出投影到任务书章节。
3. 把信息缺口转化为成熟度封顶、追问、分叉答案或选项。
4. 把项目事实、判断、风险、建议、选择和待验证项区分写入任务书。
5. 把任务书内容映射为项目图谱节点、边、状态和 source_refs。
6. 把外部产物纳入任务书和图谱的对账机制。
7. 把用户确认的事实和决定即时同步到当前项目上下文。
8. 把正式输出冻结为版本快照。
9. 把同一份认知数据导出为 PDF、Word、HTML、汇报摘要和图谱视图。
10. 把不同商业档位映射为不同深度的任务书能力。
```

### 1.2 本机制不负责什么

本机制不定义：

```text
1. LLM 如何进行高参式思考。
2. 知识库、本体论和空间分类的底层结构。
3. 项目图谱的完整视觉与交互架构。
4. 施工图、完整 CAD、正式效果图和专业审图能力。
5. 供应链交易、材料采购、完整项目管理平台。
6. 任何独立于设计任务书 2.0 的第二产品入口。
```

### 1.3 任务书 2.0 的产品身份

设计任务书 2.0 同时具备六重身份：

```text
项目启动文件；
概念方案剧本；
初步设计骨架；
项目风控台账；
活的项目档案；
团队协作与对外汇报基准。
```

但它始终不是最终设计方案，不替代：

```text
施工图；
专业机电深化；
消防审查；
结构复核；
正式效果图渲染；
完整 CAD / SU 建模。
```

## 2. 产品运行链路

### 2.1 总链路

```text
用户输入
→ 项目语境识别
→ 缺口结构化
→ 成熟度封顶
→ AdvisorAgent 输出事实 / 判断 / 风险 / 建议 / 选项 / 待验证项
→ 任务书章节投影
→ 项目图谱映射
→ 用户确认与状态更新
→ 版本快照
→ 多形态导出
→ 项目后续更新与复盘
```

### 2.2 输入层

允许用户以任意形式进入：

```text
一句话想法；
甲方需求；
聊天记录；
品牌手册；
场地照片；
CAD / 平面图；
效果图；
竞品案例；
预算信息；
现场问题；
已有方案；
汇报材料。
```

输入可以不完整、混乱、带偏见、带大词、带矛盾。系统不要求用户先整理成表格。

### 2.3 运行层

运行层输出不直接等于任务书正文，而是先形成可编排对象：

```yaml
runtime_output:
  context_vector: object
  missing_slots: [structured_missing_slot]
  maturity_ceiling: L1 | L2 | L3 | L4
  payloads:
    facts: []
    assumptions: []
    judgments: []
    risks: []
    options: []
    recommendations: []
    decisions_required: []
    verification_items: []
    source_refs: []
    judgment_bets: []
```

### 2.4 产品投影层

产品投影层负责把 `runtime_output` 放入四类出口：

```text
1. 对话即时输出：本轮给用户看的判断、提醒、追问和路径。
2. 任务书草稿：进入 17 章结构，但未冻结。
3. 项目图谱：形成节点、边、状态、证据和待确认项。
4. 正式快照：用户主动冻结后成为可导出的版本。
```

### 2.5 状态层

每个进入任务书或图谱的内容，都必须有状态：

```text
待确认；
已确认；
条件级；
待复核；
已冻结；
冲突；
阻塞；
已失效；
已替换。
```

状态不是装饰，而是后续导出、版本、对账和图谱联动的依据。

## 4. 用户入口与旅程

### 4.1 唯一主入口

首页主入口只保留一个：

```text
生成你的设计任务书 2.0
```

不并列暴露：

```text
项目图谱；
平面评审；
效果图复核；
材料雷达；
空间诊断；
AI 设计助手。
```

这些能力可以存在于内部，但不作为第一阶段独立产品入口。

### 4.2 三种进入姿态

| 进入姿态 | 用户状态 | 系统动作 | 可达成熟度 |
|---|---|---|---|
| 只有想法 | 用户只有一句项目描述或模糊愿望 | 建立项目初判、识别空间类型、输出关键风险和核心追问 | L1 |
| 已有资料 | 用户有需求文档、品牌信息、预算、聊天记录、部分场地信息 | 编译任务书草稿、生成缺口清单、建立项目图谱雏形 | L2 |
| 已有平面 / 图片 / 方案 | 用户上传场地、平面、效果图或已有方案 | 进行外部产物理解、对账、成熟度提升和图谱映射 | L3-L4 |

### 4.3 用户旅程

```text
1. 用户输入项目。
2. 系统给出项目初判、当前成熟度和最关键缺口。
3. 系统只追问会改变下一步判断的问题。
4. 用户补充核心信息。
5. 系统生成任务书草稿目录与关键章节预览。
6. 用户上传场地或项目资料后，进入正式任务书生成。
7. 系统生成任务书 2.0，并同步建立项目图谱。
8. 用户确认、修改、冻结关键判断。
9. 用户导出 PDF / Word / HTML / 汇报摘要。
10. 项目变化后，图谱更新并可生成新版本任务书。
```

### 4.4 免费与付费触发

免费阶段允许输出：

```text
项目初判；
当前成熟度；
核心风险提醒；
任务书目录预览；
部分章节样例；
关键资料缺口清单。
```

付费触发点：

```text
用户要求生成完整任务书；
用户上传具体建筑底盘或场地资料；
用户要求导出正式文件；
用户要求建立可持续更新的项目图谱；
用户要求保存正式版本快照。
```

付费提示表达：

```text
当前项目已具备生成设计任务书 2.0 的基础条件。
系统可按当前资料生成 Lx 级任务书；补充以下资料后可提升到更高成熟度。
```

不得表达为：

```text
请先买标准版才能继续。
```

## 5. 缺口、追问与成熟度

### 5.1 缺口三类

| 缺口类型 | 示例 | 产品动作 |
|---|---|---|
| P1 物理硬约束 | 给排水点、层高、柱网、消防红线、通道宽、场地边界、设备机电条件 | 结论封顶，必要时阻断平面锚定输出 |
| P2 经营事实 | 外卖占比、产品结构、峰值杯数、客单价、目标回本期、运营模式 | 给分叉答案，并说明为什么需要确认 |
| P3 主观偏好 | 风格、调性、是否打卡、材料气质、品牌性格 | 给选项，不替用户选择 |

### 5.2 串行处理规则

```text
只要存在 P1 物理硬约束缺口，本轮不展开 P2 和 P3。
```

执行方式：

```text
1. 先说明当前结论封顶到哪一级。
2. 指出 P1 缺口会影响什么。
3. 只问一个最关键的物理问题，或给出最小资料清单。
4. 不同时追问经营细节和风格偏好。
```

当 P1 相对稳定后，再处理 P2。P2 相对稳定后，再处理 P3。

### 5.3 追问规则

每个追问必须通过自检：

```text
用户回答 A 和回答 B，我下一句判断会不会不同？
```

会不同，才问。不会不同，只标注为待补，不打断用户。

每轮追问数量：

```text
常规：1-3 个；
复杂任务书启动：最多 5 个；
不得一次甩出长表单。
```

### 5.4 首轮信息抓取

首轮只抓决定项目方向和模块激活的核心变量。

通用首轮字段：

```text
1. 空间类型或业态；
2. 项目目的；
3. 主要使用者 / 运营者 / 决策者；
4. 面积或规模；
5. 场地状态：有图 / 部分有图 / 无图；
6. 预算级别；
7. 当前最不能失败的点；
8. 已有资料类型；
9. 关键经营事实；
10. 用户当前最想解决的问题。
```

场地详查不放在首轮长表单里。场地详查包括：

```text
给排水点；
层高 / 净高；
柱网；
消防边界；
入口方向；
门面宽深；
排风 / 补风；
电力负荷；
物业条件；
公共通道关系。
```

这些在进入相关章节或平面前策略时逐步拉取。

### 5.5 成熟度等级

| 成熟度 | 名称 | 用户资料状态 | 可输出 | 不可输出 |
|---|---|---|---|---|
| L1 | 概念级 | 只有想法，无场地和平面 | 项目初判、核心问题、概念方向、资料清单 | 平面布局、具体尺寸、确定材料 |
| L2 | 条件级 | 有空间类型、面积、预算、使用者、部分场地信息 | 功能需求、设计策略、风险清单、初步空间逻辑 | 完整平面、确定材料系统、施工前判断 |
| L3 | 平面前策略级 | 有场地、面积、建筑基本条件、主要接口 | 功能拓扑、动线优先级、泡泡图、分区原则 | 施工图、深化节点、机电定案 |
| L4 | 初步设计输入级 | 有平面、较完整需求、预算、场地条件 | 平面逻辑、关键空间节点、效果图控制要求、材料策略、评审标准 | 施工详图、专业盖章、最终审查 |

### 5.6 成熟度封顶表达

任务书封面、章节和关键判断都应显示成熟度影响。

推荐表达：

```text
当前章节为 L2 条件级判断。
由于缺少给排水点和设备清单，本章节只输出原则级吧台组织逻辑，不输出确定布局。
补充上述资料后，可升级为 L3 平面前策略级。
```

不得表达为：

```text
资料不足，仅供参考。
```

封顶不是免责，而是明确告诉用户：

```text
哪些可以判断；
哪些不能越级；
补什么可以升级；
当前成果能用于什么。
```

### 5.7 用户拒答处理

当用户明确拒绝提供关键事实时，对应槽位进入：

```text
User_Refused_Frozen
```

前台表达必须中性：

```text
由于当前缺少 X，本段按条件级判断处理；后续补充 X 后，可升级为更高确定性判断。
```

不得表达为：

```text
因为你拒绝提供 X，所以本段降级。
```

## 6. 任务书 17 章产品投影结构

任务书 17 章不是用户对话顺序，而是输出投影结构。用户可以从任何问题进入，系统将内容映射到对应章节。

### 6.1 17 章目录

```text
01 项目基本信息
02 项目成立判断与终局标准
03 决策方 / 使用方 / 运营方分析
04 业态逻辑与商业模型
05 场地 / 建筑 / 地域条件
06 功能需求与行为场景
07 核心矛盾识别与设计取舍
08 概念主线与空间叙事
09 文化 / 品牌 / 生活方式转译
10 功能拓扑与平面思路
11 动线 / 视线 / 空间节奏
12 材料 / 色彩 / 氛围与感官物性指标
13 风险清单与待验证事项
14 多专业边界与一票否决项
15 设计取舍账本
16 后续设计任务分解与评审标准
17 项目图谱
```

### 6.2 章节通用结构

每章统一由六类内容构成：

```text
事实：已经确认或来自资料的客观信息。
判断：系统基于事实和知识给出的专业判断。
建议：当前可执行的方向或做法。
选择：需要人拍板的取舍。
风险：若不处理会导致的后果。
待验证：必须后续补资料或专业复核的事项。
```

### 6.3 章节投影表

| 章节 | 核心作用 | 进入内容 | 成熟度控制 |
|---|---|---|---|
| 01 项目基本信息 | 记录项目识别信息 | 空间类型、地点、面积、资料状态、版本信息 | L1 即可 |
| 02 项目成立判断与终局标准 | 判断项目为什么成立 | 项目目的、成功标准、经营目标、不可失败点 | 缺项目目的时只输出初判 |
| 03 决策方 / 使用方 / 运营方分析 | 看清人和权力关系 | 决策链、使用者、运营者、外部角色、冲突 | 缺角色时不得默认谁拍板 |
| 04 业态逻辑与商业模型 | 明确业务如何运转 | 价格带、客单价、渠道、回本压力、运营模式 | 缺经营事实时给分叉答案 |
| 05 场地 / 建筑 / 地域条件 | 建立物理底盘 | 场地类型、平面、层高、接口、物业、市政 | P1 缺口直接封顶 |
| 06 功能需求与行为场景 | 明确空间承载什么 | 功能清单、行为路径、设备关系、时间状态 | 缺设备清单时不定后场布局 |
| 07 核心矛盾识别与设计取舍 | 找出真正难题 | 冲突、代价、取舍路径、头号风险 | 必须给路径，不只指出问题 |
| 08 概念主线与空间叙事 | 形成设计抓手 | 概念方向、空间故事、体验主线 | 偏好缺失时给选项，不替选 |
| 09 文化 / 品牌 / 生活方式转译 | 把软目标转为空间语言 | 品牌气质、文化意象、生活方式、表达边界 | 不能把大词当结论 |
| 10 功能拓扑与平面思路 | 进入平面前策略 | 功能关系、泡泡图、布局原则、平面方向 | 无平面或接口时只到原则级 |
| 11 动线 / 视线 / 空间节奏 | 控制体验与效率 | 人流、物流、视线、节奏、停留与通过 | 缺场地边界时不画确定动线 |
| 12 材料 / 色彩 / 氛围与感官物性指标 | 把氛围变成可执行控制 | 主材、色彩、灯光、触感、维护、成本 | 指标必须来自依据，不伪精确 |
| 13 风险清单与待验证事项 | 建立风险台账 | 风险、原因、后果、等级、处理路径 | 每条风险必须有下一步动作 |
| 14 多专业边界与一票否决项 | 保护工程底线 | 消防、结构、机电、物业、法规、审批 | 高风险项必须从严封顶 |
| 15 设计取舍账本 | 记录关键选择 | 选择项、理由、代价、责任方、后续验证 | 未确认选择不得写成已定结论 |
| 16 后续设计任务分解与评审标准 | 让项目进入下一步 | 平面任务、效果图任务、材料任务、甲方决策 | 必须具体到下一步动作 |
| 17 项目图谱 | 展示项目认知关系 | 节点、边、状态、依据、风险、决策 | 文档内为快照，在线版为活体 |

### 6.4 章节写作规则

每章禁止只写空泛描述。必须至少满足以下之一：

```text
给出明确判断；
列出关键缺口；
指出风险及路径；
形成可选择方案；
生成待验证事项；
沉淀为图谱节点；
转化为后续任务。
```

不得出现的内容形态：

```text
泛泛的设计原则；
无来源的行业常识堆砌；
无项目条件的风格套话；
无代价说明的建议；
无下一步动作的风险；
没有成熟度标注的确定性表达。
```

## 7. 模块体系

### 7.1 模块不是章节

章节是任务书的导出结构。模块是生成内容的产品能力单元。

```text
章节回答：任务书怎么呈现。
模块回答：当前项目需要哪些能力来生成有价值内容。
```

一个模块可以投影到多个章节，一个章节也可以由多个模块共同生成。

### 7.2 三层模块

| 层级 | 名称 | 定义 | 是否默认进入 |
|---|---|---|---|
| 基础模块 | 最小可设计闭环 | 缺了它，项目无法稳定启动设计、报审或施工前判断 | 全档进入 |
| 标准模块 | 质量增强层 | 缺了仍能启动，但会降低效率、表达、运营或协作质量 | 标准版起进入 |
| 自定义模块 | 项目特殊需求 | 来自具体场地、客群、运营、品牌或用户特殊诉求 | 用户选择后进入 |

### 7.3 唯一判定线：缺角测试

判断模块归属，只问一个问题：

```text
缺了它，项目设计会不会缺角？
```

会缺角：基础模块。  
不会缺角但显著增值：标准模块。  
只对本项目特殊成立：自定义模块。

### 7.4 软但决定性的内容可以进入基础模块

基础模块不等于硬工程清单。以下内容虽然偏软，但可能是基础模块：

```text
经营定位；
目标客群；
决策方 / 使用方 / 运营方；
核心用户体验；
概念锚定；
材料氛围基调；
成功标准；
最不能失败点。
```

原因：缺少这些，设计师拿到的不是设计任务书，而只是可行性检查或工程风险清单。

### 7.5 模块数据结构

```yaml
module:
  module_id: string
  module_name: string
  module_layer: essential | recommended | optional
  applicable_space_types: []
  triggered_by_context_facets: []
  required_slots: []
  optional_slots: []
  related_lenses: []
  output_sections: []
  graph_node_templates: []
  knowledge_card_types: []
  maturity_ceiling_rule: string
  deletable: true | false
  releases_custom_slot: true | false
```

### 7.6 模块激活规则

```text
空间类型决定模块候选池。
项目语境决定模块排序。
核心缺口决定成熟度。
商业档位决定起点模块集。
用户选择决定自定义模块。
项目图谱状态决定后续复核。
```

### 7.7 自定义模块治理

自定义模块用于查漏补缺，不直接改变空间类型本体。

当用户多次添加相似自定义模块时，系统动作是：

```text
生成知识缺口工单；
进入推荐池候选；
等待人工评审与样本验证；
成熟后再进入标准模块或行业模板。
```

禁止：

```text
用户添加一次就自动升入本体论；
把个别项目经验误当通用规律；
让自定义模块污染基础模块。
```

## 8. 高参证据点

用户不是等最后才感知价值。任务书生成过程中必须持续出现高参证据点。

### 8.1 项目本质判断

系统应在早期给出一句项目本质判断。

示例结构：

```text
这个项目表面是 X，本质是 Y。
因此第一优先级不是 A，而是 B。
```

要求：

```text
不能只是复述用户输入；
不能夸张包装；
必须能影响后续任务书方向。
```

### 8.2 头号风险识别

系统必须指出当前最值得优先处理的风险。

结构：

```text
头号风险是什么；
为什么是它；
它会影响什么；
现在可走的路径是什么。
```

禁止：

```text
列十条并列风险；
只说风险不说路径；
把用户兴奋点里的真实风险说轻。
```

### 8.3 核心取舍展开

系统必须把关键取舍从“好不好”改写为“代价是什么”。

```text
选 A：得到什么，失去什么。
选 B：得到什么，失去什么。
暂缓：会造成什么不确定。
```

### 8.4 概念方向选项

偏主观的设计方向不能替用户拍板。

输出方式：

```text
2-3 个方向；
每个方向的气质；
每个方向的空间代价；
每个方向适合的项目条件；
需要用户确认的判断。
```

### 8.5 成熟度封顶说明

系统不问用户“要不要生成 L2 或 L3”，而是直接判断当前只能生成哪一级。

用户可以选择：

```text
现在导出当前成熟度成果；
继续补资料后升级成熟度。
```

但用户不能通过选择改变事实成熟度。

## 9. 项目图谱协同机制

### 9.1 图谱定位

项目图谱是任务书 2.0 的活体认知结构。

它负责展示：

```text
项目目标；
硬约束；
问题；
决策；
依据；
风险；
它们之间的依赖、冲突和派生关系。
```

### 9.2 图谱与任务书的关系

```text
任务书是项目认知在某一时刻的结构化快照。
项目图谱是项目认知关系的实时工作面。
```

二者共享同一套认知数据，但使用方式不同。

### 9.3 source_refs 机制

任务书和图谱都不是所有事实的真相源。关键事实必须通过 `source_refs` 引用来源对象。

```yaml
source_ref:
  object_id: string
  object_type: user_input | uploaded_file | floor_plan | brief_section | graph_node | external_source | knowledge_card
  version: string
  confidence: high | medium | low
  confirmation_status: pending | confirmed | needs_review
```

规则：

```text
任务书引用事实，不复制真相源；
图谱索引关系，不替代对象链；
对象升版后，相关章节和节点进入待复核；
删除节点不删除原始对象。
```

### 9.4 章节到图谱的映射

| 任务书内容 | 图谱对象 |
|---|---|
| 项目目标 / 成功标准 | 目标节点 |
| 场地 / 预算 / 法规 / 机电 | 约束节点 |
| 关键问题 / 待解决事项 | 问题节点 |
| 用户拍板 / 设计选择 | 决策节点 |
| 案例 / 规范 / 文件 / 知识卡 | 依据节点 |
| 风险 / 一票否决 / 待验证项 | 风险节点 |

### 9.5 图谱快照与在线图谱

```text
全档任务书包含第 17 章项目图谱快照。
标准版起包含可持续访问和更新的在线项目图谱。
专业版包含多人协作、权限、审批、节点责任人和变更治理。
```

图谱快照用于交付。在线图谱用于项目持续推进。

### 9.6 Graph-aware AI

在项目图谱中，AI 回答必须基于当前焦点子图，而不是泛答全项目。

上下文范围：

```text
当前焦点节点；
一跳关联节点；
必要的二跳关联节点；
相关 source_refs；
相关缺口和成熟度；
相关风险和决策状态。
```

输出必须能够回写到：

```text
节点白板；
任务书章节；
风险记录；
决策记录；
待验证事项。
```

### 9.7 结构空白

图谱必须主动显现四类盲区：

```text
孤立节点；
缺失连接；
缺失节点；
大词遮蔽。
```

提示方式：

```text
不弹窗；
不强迫；
在节点白板或侧边建议中克制提示；
用户可采纳、忽略或延后。
```

## 10. 外部产物与证据编排

### 10.1 外部产物类型

```text
CAD / 平面图；
效果图；
施工图；
场地照片；
品牌手册；
竞品资料；
甲方聊天记录；
需求文档；
预算表；
物业条件；
法规或标准资料；
市场报告；
社交平台截图。
```

### 10.2 四重动作

外部产物进入系统后，必须经过四个动作：

```text
理解：识别资料内容、类型、版本、置信度。
关联：挂接到任务书章节和图谱节点。
校验：对照已有判断，发现冲突、缺口、过期和风险。
回写：更新章节、节点、状态、待验证项和版本影响。
```

### 10.3 对账结果

| 对账结果 | 系统动作 |
|---|---|
| 支撑已有判断 | 增加 source_ref，提高置信度 |
| 修正已有判断 | 标记相关章节和节点待复核 |
| 发现冲突 | 节点进入冲突状态，生成风险记录 |
| 信息不足 | 增加 missing_slot 或待验证项 |
| 资料过期 | 标记来源失效，不再作为强依据 |

### 10.4 外部证据等级

| 来源类型 | 可用于 |
|---|---|
| 官方法规 / 标准 | 支撑硬约束，但需确认适用范围 |
| 物业 / 项目方文件 | 支撑项目事实，需记录版本 |
| CAD / 实测图 | 支撑物理判断，需标置信度 |
| 行业报告 | 支撑趋势或市场判断，不直接替代项目事实 |
| 品牌宣传 | 作为品牌线索，不作为硬证据 |
| 社交平台 / 点评 / 地图 | 作为现象线索，需交叉验证 |

### 10.5 外部检索纪律

```text
查不到，不脑补；
查到弱证据，不装确定；
查到冲突信息，必须标注冲突；
查到项目事实，只进入项目证据，不自动变成通用知识；
查到可复用规律，先进入候选知识，不直接写入正式知识库。
```

### 10.6 商业边界

外部产物接入不是独立评审服务。

对用户的表达是：

```text
把已有资料纳入设计任务书 2.0，重新校准项目前策逻辑。
```

不表达为：

```text
帮你审图；
帮你修方案；
帮你改施工图；
帮你收拾残局。
```

## 11. 记忆与沉淀编排

### 11.1 会话同步轨

会话同步轨用于保证本次对话的连贯性。

可以进入同步轨：

```text
用户明确确认的事实；
用户明确确认的决定；
用户明确确认的偏好；
用户明确拒答形成的冻结槽位；
用户明确修改或否定的内容。
```

不得进入同步轨：

```text
系统自己的推断；
系统暂定假设；
未验证的外部搜索结果；
模型猜测出的偏好；
未经用户确认的结论。
```

### 11.2 项目状态轨

项目状态轨记录当前项目中的稳定认知对象：

```text
章节状态；
图谱节点状态；
决策记录；
风险记录；
source_refs；
版本快照；
待验证项；
冲突和复核状态。
```

### 11.3 全局异步轨

全局异步轨处理长期沉淀：

```text
候选知识卡；
知识升降级事件；
项目复盘结果；
可验证判断结果；
跨项目经验；
用户偏好画像；
设计师经验系统。
```

它不阻塞前台对话，不由 Live 对话层直接写入正式知识库。

### 11.4 用户画像使用边界

用户画像只用于：

```text
排序；
提醒；
表达风格；
默认展示偏好；
历史项目对照；
减少重复解释。
```

不得用于：

```text
替用户做审美选择；
把历史偏好固化为唯一答案；
忽略新项目差异；
让系统讨好用户偏见。
```

## 12. 输出形态与版本治理

### 12.1 输出形态

| 输出形态 | 用途 | 是否消耗正式版本 |
|---|---|---|
| PDF | 正式交付、打印、归档、合同附件 | 否 |
| Word | 可编辑、团队二次整理 | 否 |
| HTML 实时页 | 项目持续查看与内部协作 | 否 |
| HTML 正式快照 | 对外分享的冻结页面 | 是 |
| 汇报摘要 | 4-6 页给甲方、投资人、决策人快速阅读 | 否 |
| 项目图谱 | 活体认知结构与工作面 | 否，图谱快照随正式版本冻结 |

### 12.2 正式版本

计入正式版本：

```text
用户主动点击“存为正式版本”；
用户发布 HTML 正式快照；
用户冻结任务书用于对外交付。
```

不计入正式版本：

```text
实时编辑；
草稿保存；
PDF 导出；
Word 导出；
汇报摘要导出；
HTML 实时页查看；
图谱日常更新。
```

### 12.3 版本冻结内容

每个正式版本必须冻结：

```text
任务书 17 章内容；
当前成熟度；
关键缺口；
用户确认项；
source_refs；
图谱节点与边状态；
风险清单；
决策记录；
待验证事项；
导出时间和版本号。
```

### 12.4 单章导出

第一阶段不开放对外正式单章独立导出。

允许：

```text
章节内容复制；
汇报摘要选择重点章节；
内部局部投影；
节点白板局部分享；
标准版以上的图谱局部查看。
```

不允许：

```text
把某一章作为正式独立 PDF 快照对外发布；
让单章快照绕开整体版本治理；
让局部导出脱离成熟度和 source_refs。
```

### 12.5 版本数

| 档位 | 正式版本数上限 |
|---|---:|
| 基础版 | 10 |
| 标准版 | 20 |
| 专业版 | 30 |

超出后：

```text
购买版本包；
基础版 / 标准版可升档；
升档后已有正式版本继承。
```

## 13. 商业分档编排

### 13.1 三档不是三个产品

```text
基础版、标准版、专业版都是设计任务书 2.0，只是深度、容量、协作和生成强度不同。
```

### 13.2 三档定义

| 档位 | 定位 | 适用场景 | 核心能力 |
|---|---|---|---|
| 基础版 | 基础设计启动版 | 早期项目、独立单店、小预算、资料有限 | 生成基础闭环任务书、图谱快照、PDF/Word/摘要、有限版本 |
| 标准版 | 完整设计启动版 | 大多数正式项目 | 基础 + 标准模块、功能拓扑、平面前策略、在线项目图谱、深度内容生成 |
| 专业版 | 复杂项目协作版 | 首店、旗舰店、连锁、投资汇报、多方协作 | 标准版全部 + 多人协作、权限、审批、人工复核接口、汇报增强 |

### 13.3 三档共同能力

```text
设计任务书 2.0 主体；
成熟度标注；
风险清单；
待验证事项；
PDF / Word / 汇报摘要；
项目图谱快照；
补充资料上传；
正式版本管理；
外部搜索单点补缺；
章节与图谱 source_refs。
```

### 13.4 三档差异

| 能力 | 基础版 | 标准版 | 专业版 |
|---|---|---|---|
| 起点模块集 | 基础模块 | 基础 + 标准模块 | 基础 + 标准模块 |
| 自定义模块位 | 4 | 6 | 10 |
| 在线项目图谱 | 不含活体更新，仅含快照 | 1 年访问与更新 | 协作级访问与治理 |
| 深度研究 | 不默认触发 | 标准模块背后可触发 | 标准模块 + 图谱节点可触发 |
| 多人协作 | 不支持 | 不支持或轻量查看 | 支持 |
| 变更审批 | 不支持 | 不支持 | 支持 |
| 人工复核接口 | 不含 | 可选 | 包含或优先 |
| 正式版本数 | 10 | 20 | 30 |

### 13.5 升档规则

```text
基础版可升标准版；
标准版可升专业版；
已生成内容、source_refs、图谱快照和正式版本继承；
升档不改变历史版本内容，只开启更高深度能力；
升档后可基于当前项目状态生成新版本。
```

## 14. 质量治理

### 14.1 任务书质量标准

一份合格的设计任务书 2.0 必须满足：

```text
1. 项目本质判断清楚。
2. 使用者、运营者、决策者关系清楚。
3. 物理硬约束缺口不被掩盖。
4. 经营事实缺口被分叉处理。
5. 主观偏好不被 AI 替用户决定。
6. 每个核心判断都有来源、假设或待验证项。
7. 风险有优先级，不平铺。
8. 指出风险后有可走路径。
9. 成熟度标注真实，不越级。
10. 图谱节点和任务书章节能够相互追溯。
11. 下一步任务明确，能支撑真实推进。
```

### 14.2 不合格输出

以下输出视为不合格：

```text
没有场地条件却给确定布局；
没有设备清单却确定后场；
没有预算却写死材料等级；
没有客群和经营定位却给完整概念；
把“高级感”“松弛感”“疗愈感”直接当设计结论；
列很多风险但不说明哪个优先；
只指出问题不给路径；
用“仅供参考”稀释所有判断；
把用户未确认的系统推断写成事实；
外部搜索结果没有来源和置信度；
章节内容无法映射到图谱或 source_refs。
```

### 14.3 高参行为检查

每次重要输出都应检查：

```text
定位是否适度；
缺口处理是否正确；
头号风险是否明确；
追问是否克制；
成熟度是否封顶；
判断是否可追溯；
风险后是否给路径；
是否尊重人的主观选择；
是否避免讨好、怯懦和话痨。
```

### 14.4 大词处理标准

出现以下大词时，系统不得直接顺从：

```text
高级感；
松弛感；
疗愈感；
东方；
年轻化；
自然；
未来感；
轻奢；
在地性；
克制；
社交感；
生活方式。
```

处理方式：

```text
1. 承接用户意图。
2. 拆成空间条件、材料、灯光、尺度、声环境、维护、成本、运营等维度。
3. 给出可能路径。
4. 说明每条路径的代价。
5. 需要用户选择时，不替用户选。
```

## 15. MVP 执行路线

### 15.1 数据与对象

MVP 必做：

```text
Project 对象；

BriefBlock 对象；
MissingSlot 对象；
RiskRecord 对象；
DecisionRecord 对象；
source_refs；
brief_snapshot；
```

### 15.2 生成机制

MVP 必做：

```text
单主入口；
三种进入姿态；
首轮轻量问诊；
structured_missing_slots；
P1/P2/P3 缺口分流；
L1-L4 成熟度封顶；
17 章任务书投影；
基础模块 / 标准模块 / 自定义模块规则；
章节状态；
正式版本冻结；
PDF / Word / 汇报摘要导出。
```

### 15.3 图谱机制

MVP 必做：

```text
第 17 章图谱快照；
任务书章节到图谱节点映射；
source_refs 追溯；
基础节点类型：目标 / 约束 / 问题 / 决策 / 依据 / 风险；
基础边类型：依赖 / 冲突 / 派生；
节点状态：未启动 / 进行中 / 已解 / 冲突 / 阻塞；
结构空白基础提示；
大词遮蔽基础识别。
```

标准版起做：

```text
在线项目图谱；
节点白板；
图谱状态持续更新；
基于焦点子图的 AI 回答；
图谱变更触发任务书复核。
```

专业版做：

```text
多人协作；
权限；
节点责任人；
变更审批；
正式版本复核；
人工专家接口。
```

### 15.4 外部产物

MVP 必做：

```text
文档上传解析；
图片 / 截图作为证据挂载；
CAD / 平面图基础人工确认入口；
外部产物 source_refs；
对账结果进入待复核 / 冲突 / 缺口状态。
```

暂缓：

```text
复杂 CAD 自动理解；
完整施工图审查；
自动机电复核；
自动效果图一致性评分。
```

### 15.5 导出与版本

MVP 必做：

```text
正式 PDF；
Word；
汇报摘要；
HTML 实时页；
HTML 正式快照；
版本数规则；
成熟度水印；
source_refs 附录；
待验证项附录；
图谱快照页。
```

暂缓：

```text
正式单章独立导出；
跨版本差异可视化；
自动生成 PPT；
全量图谱版本比较。
```

## 16. UI 与交互要求

### 16.1 主入口界面

必须简单：

```text
一个输入框；
一个主按钮；
三种进入姿态弱提示；
一个交付样本入口。
```

不展示内部工程术语。

### 16.2 任务书生成界面

界面应展示：

```text
当前成熟度；
已确认信息；
关键缺口；
正在生成的章节；
需要用户确认的判断；
可导出的形态；
项目图谱入口。
```

### 16.3 缺口提示

缺口提示必须说明影响：

```text
缺什么；
影响哪个章节；
会把成熟度封到哪一级；
补充后能升级什么；
现在是否可以继续生成。
```

### 16.4 章节确认

用户可以对章节内内容执行：

```text
确认；
修改；
标记待定；
拒绝；
请求解释；
上传依据；
生成替代方案。
```

确认后的内容进入会话同步轨和项目状态轨。

### 16.5 图谱入口

图谱不作为首页主入口，但在任务书中明确出现：

```text
第 17 章图谱快照；
标准版以上的在线图谱入口；
章节内相关节点链接；
风险 / 决策 / 待验证项的图谱回跳。
```

## 18. 执行验收清单

### 18.1 产品验收

```text
用户能从一句话开始；
系统能识别当前成熟度；
系统能指出最关键缺口；
系统能生成 17 章任务书草稿；
系统能区分事实、判断、建议、选择、风险、待验证项；
系统能把章节内容映射到图谱；
系统能冻结正式版本；
系统能导出 PDF / Word / HTML / 汇报摘要；
系统能在资料变化后标记待复核；
系统能阻止越级输出。
```

### 18.2 研发验收

```text
所有 BriefBlock 有 block_type；
所有关键判断有 source_refs 或假设说明；
所有 missing_slot 有 type、priority、action；
所有正式版本有 snapshot_id；
所有图谱节点有 source_refs 字段；
用户确认项能同步进入当前项目上下文；
系统推断不会直接进入会话同步记忆；
外部资料进入后可触发章节和节点状态变化；
导出文件带版本号和成熟度；
HTML 正式快照消耗正式版本数。
```

### 18.3 内容验收

```text
没有空泛章节；
没有无依据参数；
没有大词直出；
没有资料不足时的假确定性；
没有平铺风险；
没有只破不立；
没有让用户承担系统判断等级的选择；
没有把偏好写成结论；
没有把外部弱证据写成硬事实。
```

## 19. 最终定盘句

```text
设计任务书 2.0 不是一份漂亮文档，
而是空间项目在正式设计前形成的认知总控成果。
```

```text
任务书 2.0 产品编排机制不负责替系统思考，
它负责把高参判断变成可交付、可追踪、可复盘的产品结果。
```

```text
硬的部分，系统要封顶、提醒、追溯；
软的部分，人要选择、确认、承担；
硬软交界，AI 拆清代价，任务书记录选择。
```

```text
最终目标只有一个：
让每一个空间项目，从第一份任务书开始，就更清醒、更可靠、更可推进。
```
