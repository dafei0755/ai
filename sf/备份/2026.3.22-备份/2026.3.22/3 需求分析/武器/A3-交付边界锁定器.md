# A3 — 交付边界锁定器

> **组别**：A 组（接收核验）| **阶段**：S1 | **类型**：后台·必执行
> **原始编号**：P2 交付边界映射 | **消费方**：S4 确认任务书

---

## 一分钟定义

根据输入信号，**自动圈定「这个项目能交付什么、不能交付什么」的边界**，防止流程推进过程中范围悄悄蔓延，导致到 S4 编译任务书时才发现范围远超原始预期。

---

## 功能详述

A3 产出三类清单：

| 清单 | 内容 | 举例 |
|------|------|------|
| 可交付清单 | 该项目范围内的输出 | 全套室内设计方案、施工图、材料清单 |
| 超出范围清单 | 不在本次服务内 | 建筑改造、市政审批手续、景观设计 |
| 建议拆分方向 | 若范围过大，建议如何分阶段 | 「一期只做公共区域，二期做卧室」 |

**A3 的判断依据**：
- A1 约束信号（预算/时间上限 → 自然限制了交付量）
- 项目类型（住宅室内 ≠ 软装 ≠ 商业空间）
- A2 充足度等级（信息「不足」时边界判断更保守）

---

## 输入

```
structured_requirements   # A1 信号包
information_sufficiency   # A2 评估结果
```

---

## 输出

```python
delivery_boundary: {
    "deliverables": [...],          # 可交付清单
    "out_of_scope": [...],          # 超出范围清单
    "split_suggestions": [...],     # 拆分建议（可为空）
    "confidence": 0.0~1.0           # 边界判断的置信度
}
```

---

## 激活条件

A2 完成后立即触发，强制执行。

---

## 执行方式

- **执行器**：LLM 调用（需要语义理解判断范围）
- **代码锚点**：`requirements_analyst_agent.py` → `_map_delivery_boundary()`
- **S4 验证**：S4 确认任务书时，对照 A3 的边界包，检查任务书中是否有超出 `out_of_scope` 的内容

---

## 用户交互

**无**（S1 阶段不与用户交互）。边界在 S4 时由用户最终确认，A3 是初始草案。

---

## 协作关系

```
上游（依赖）：
  ← A1 需求信号解析器
  ← A2 信息充足度评估器

下游（供给）：
  → S4 确认任务书（A3 边界包是任务书「边界核验」的基准）
  → F8 下游专家问题生成器（边界清单决定为哪些专家生成问题）
```

---

## 常见误用

1. **把 A3 的「超出范围」直接告知用户，导致误解**
  纠偏：A3 在 S1 后台运行，不向用户展示；超出范围的声明只在 S4 任务书确认时出现

2. **把边界视为固定合同，不允许修改**
  纠偏：A3 只是 S1 时的初始草案，用户在 S4 有权扩大或缩小范围，A3 是参考基准不是锁定合同

---

## 扩展优化方向

- **项目类型模板**：主流项目类型预置边界模板，减少 LLM 推断成本
- **历史范围蔓延检查**：定期分析历史项目「S4 定版范围」vs「A3 初始边界」的差距，倒推 A3 的提前识别能力
