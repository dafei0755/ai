> **组别**：D 组（前提挑战）| **阶段**：S3 | **类型**：互动·必说
> **原始编号**：整合新建（原散落于 P0 信号和 gap_filling）| **发声顺序**：S3 第 2 件

---

## 一分钟定义

让用户**显式确认三类约束**（绝对红线 / 硬限制 / 软性偏好），把 S1 自动识别的约束信号从「AI 的推断」升级为「用户的承诺」。D2 完成后，所有后续武器和专家必须尊重这些约束。

---

## 功能详述

D2 处理三类约束，含义各不相同：

| 约束类型 | 含义 | 对后续的影响 | 举例 |
|---------|------|------------|------|
| **绝对红线（never-do）** | 任何情况下都不可触碰 | 后续所有建议中自动排除 | 「不拆承重墙」「不用大理石地面」 |
| **硬限制（hard-limit）** | 有可能变通，但有上限 | 触碰需要明确说明原因 | 「预算最多超出 10%」「工期不超过 5 个月」 |
| **软性偏好（soft-preference）** | 期望但可协商 | 记录为优先参考，可在冲突时主动牺牲 | 「最好是木地板」「希望有植物角落」 |

**D2 的核心贡献**：S1（A1）也识别了约束信号，但那只是「AI 推断的约束」；D2 让用户主动说「这是我的约束」，从而建立**可被后续步骤引用**的约束契约。

## 激活条件

- D1 responded 之后执行，S3 必说，不可跳过

## 执行方式

- **展示素材**：A1 的约束信号汇总为候选清单，用户在其上做分类和确认，不需要从零输入
- **新约束入口**：用户可在 D2 中添加 A1 未识别到的约束
- **用户可降级**：把「AI 预判为 never-do」的项降级为 hard-limit，但不可跳过确认环节
- **不可逆原则**：D2 确认后写入 `confirmed_constraints`，设为只读——后续阶段若要修改，需走「约束变更」流程

## 用户交互

**有**。展示格式：

```
基于你的描述，我识别出以下约束——请帮我分类：

「绝对不碰的」（any situation）：
  • [候选 1] ✓ 还是需要调整？
  • [候选 2] ✓ 还是需要调整？

「有上限的」（可变通但有底线）：
  • 预算 [X] 万 — 可以接受多少浮动？

「最好有，但可协商」：
  • [候选 3]

有什么我漏掉的约束，也可以在这里补充。
```

## 协作关系

```
上游（依赖）：
  ← A1 需求信号解析器（约束信号候选）
  ← D1 设计前提校验器（假设挑战可能暴露隐含约束）
  ← F1 事实推断分离器（[FACT]标注的约束最可靠）

下游（供给）：
  → S4 张力冻结（confirmed_constraints 与冲突对并列进入决策矩阵）
  → F8 下游专家问题生成器（专家必须在提案中说明约束合规性）
  → F9 创新边界授权生成器（never-do 列表 = 绝对不可突破边界）
  → S4 任务书（约束清单是任务书的核心条款之一）
  → project_director（分配专家时参考约束匹配能力）
```

## 常见误用

1. **D2 只展示 AI 推断约束，不留入口让用户补充**
   纠偏：很多重要约束 A1 无法识别（家庭成员隐性协议、和物业的非正式约定），D2 必须有「补充约束」入口

2. **把 D2 结果当作「建议」而不是「承诺」**
   纠偏：D2 确认的约束对后续所有武器和专家有约束力，不是「参考」——凡是触碰 never-do 的建议，系统必须拦截

3. **D2 和 D1 合并成一次交互**
   纠偏：D1 是认知层（假设是否正确），D2 是行动层（约束是什么）；合并会导致用户在认知挑战和约束确认之间跳来跳去，造成混乱

## 扩展优化方向

- **约束冲突检测**：D2 完成后自动检查「约束清单内部是否有矛盾」（如：「预算 50 万」vs「要求全套进口材料」）
- **约束可视化**：在 S4 任务书中以「约束清单」模块明确展示，防止确认后遗忘
- **历史约束频率分析**：统计哪类约束在哪类项目中最常出现，帮助 D2 提高候选约束的命中率
