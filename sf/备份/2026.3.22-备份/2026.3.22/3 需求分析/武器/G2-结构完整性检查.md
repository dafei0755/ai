# G2 — 结构完整性检查

> **组别**：G 组（质量门控）| **阶段**：全流程·各阶段收口 | **类型**：门控·Schema 验证器
> **原始编号**：Q2 Schema 完整性自检 | **消费方**：流程控制器（stage transition）

---

## 一分钟定义

在每个阶段（S2/S3/S4）结束时，**检查 requirements Schema 的必填字段是否全部有值**，发现空缺时触发 G3（自动填充）、E1（向用户补缺）或回退流程。

---

## 功能详述

G2 是 Schema 完整性的守门员，确保流程向下一阶段推进时，不带着空洞的必填字段：

| Schema 字段级别 | 为空时的处理策略 |
|----------------|---------------|
| **核心字段**（S4 必须确认） | 在 S2 可触发 E1；若到 S4 仍缺失则必须回退 |
| **重要字段**（影响专家工作） | 优先触发 E1；如用户跳过 → G3 自动填充 + `[推断]` 标记 |
| **辅助字段**（锦上添花） | 直接由 G3 自动填充，不打扰用户 |

---

## 输入

```
current_requirements: RequirementsSchema  # 当前完整状态
stage_closing: str                        # "S2" | "S3" | "S4"
```

---

## 输出

```python
completeness_report: {
    "stage": "S3",
    "complete": False,
    "missing_critical": ["confirmed_constraints"],   # 强制走 E1
    "missing_important": ["tension_candidates"],     # 优先 E1 / 可 G3
    "missing_auxiliary": ["behavior_mode_profile"],  # 直接 G3
    "action": "trigger_E1"  # | "trigger_G3" | "pass"
}
```

---

## 激活条件

每个阶段的 **exit condition 满足后、向下一阶段转移前**，自动运行 G2。

---

## 执行逻辑

```
阶段退出信号 → G2 检查 → 全字段齐全 → 放行
                         → 缺核心字段且仍在 S2 → 触发 E1（阶段不关闭，直到补完）
                         → 缺核心字段但已准备进 S4 → 回退到 S2 / S3
                         → 缺重要字段 → 视影响决定 E1 或 G3
                         → 缺辅助字段 → 直接触发 G3
```

---

## 用户交互

**无**（G2 本身不向用户展示内容）。但 G2 的检查结果可能触发 E1，E1 再与用户互动。

---

## 协作关系

```
上游（被检查）：← 全量 RequirementsSchema（所有阶段写入）
下游（触发）：→ E1 关键缺口补全器（问用户）
             → G3 空字段自动兜底（自动填充）
             → 流程阶段推进器（pass 后才允许进下一阶段）
```

---

## Schema 字段优先级参考

| 优先级 | 字段名（示例） | 不可绕过 |
|-------|-------------|---------|
| 核心 | `problem_framework`, `confirmed_constraints`, `deliverables`, `tension_decisions` | 是 |
| 重要 | `stakeholder_map`, `constraint_signals`, `identity_mode` | 否，可 G3 |
| 辅助 | `behavior_mode_profile`, `complexity_score`, `fact_inference_tags` | 否，直接 G3 |

---

## 常见误用

1. 用 G2 检查 F 组后台输出（F 组是内部处理结果，不需要完整性检查）
2. 在 S4 确认后才运行 G2（太晚，流程已走完，缺口无法补救）
