# X2 — 工程约束分类器

> **组别**：X 组（场景扩展·新增）| **阶段**：S1（与 A1 并行）| **类型**：后台·约束预分类器
> **优先级**：P0 | **触发**：A1 完成后立即运行 | **消费方**：D2、F9

---

## 一分钟定义

在 D2 接收约束之前，**把「物理法则/行业规范类约束」从「用户偏好类约束」中分离出来**，防止两种性质完全不同的约束被混同处理——偏好可以被挑战，物理法则不行。

---

## 功能详述

D2（约束条件识别器）的三级模型（never_do / hard_limit / soft_preference）本质上是**偏好强度的分级**，适用于用户意志范围内的约束。但有一类约束来自「世界的规律」，不来自用户的意志：

| 约束来源 | 举例 | 能否被 F9 挑战 |
|---------|------|-------------|
| **物理法则** | 声速与混响关系、热力学传热 | 不能 |
| **行业规范** | 杜比全景声声场标准、消防疏散距离、医疗洁净等级 | 不能（通常） |
| **法规强制** | 无障碍通道宽度、建筑结构荷载 | 不能 |
| **用户意志** | 「不要白色」「预算 60 万」「不想拆承重墙」 | D2 可接收，F9 可评估 |

### X2 的核心动作：约束来源标注

X2 不替代 D2，而是在 D2 之前运行，给每条约束打「来源标签」：

```
来源标签: "physics" | "code_regulation" | "industry_standard" | "client_preference"
```

D2 只接收 `client_preference` 类约束。其余三类由 X2 直接写入 `engineering_constraints` 字段，F9 的「可挑战列表」**绝对不允许引用** `engineering_constraints` 中的内容。

---

## 输入

```
raw_input_text            # 原始输入（含技术需求描述）
structured_requirements   # A1 输出（已提取的约束信号）
project_type              # X1 判断的项目类型（技术主导型项目触发更严格的扫描）
```

---

## 输出

```python
engineering_constraints: [
    {
        "constraint": "混响时间 RT60 ≤ 0.3s（杜比全景声标准）",
        "source_type": "industry_standard",
        "source_ref": "Dolby Atmos Home Theater Specification v3.0",
        "challengeable": False,
        "relevant_weapons": ["D2（告知不可挑战）", "F9（禁止列入授权挑战）"]
    },
    {
        "constraint": "房间比例避免平行墙（声学驻波）",
        "source_type": "physics",
        "challengeable": False,
        "relevant_weapons": ["D2（直接锁定）"]
    }
]

# D2 接收的约束清单（已过滤，仅含 client_preference 类）
client_constraints_for_D2: [
    {
        "constraint": "业主希望设备全部隐藏",
        "source_type": "client_preference",
        "challengeable": True
    }
]
```

## 激活条件

**触发信号**（任一满足即激活深度扫描）：
- 项目涉及声学、光学、热工、结构、供电等物理工程词汇
- 项目类型为：医院/实验室/演出空间/极端气候/特殊防护
- A1 的 `constraint_signals` 中包含数字规格（如「3800m 海拔」「杜比标准」「0dB 隔音」）

**不触发信号**：标准住宅/常规办公室 → 仅做轻量扫描，不深度展开

---

## 执行方式

- **识别机制**：规则引擎（关键词匹配：标准名称/规范编号/物理量词）+ LLM 语义判断
- **不确定时**：保守处理，将约束标注为 `engineering_constraints`，待 F8 生成专家交接问题时由专家确认

---

## 用户交互

**无**。X2 是静默后台预处理，用户不感知。

---

## 协作关系

```
上游（依赖）：← A1 约束信号 ← X1 项目类型判断
下游（供给）：→ D2（只接收 client_preference 类约束）
             → F9（engineering_constraints 字段：禁止引用）
             → F8（工程约束会被生成为专家确认问题）
```

---

## 关键守则

**F9 的「授权可突破」列表，必须在生成前由 X2 做一次反向过滤：**  
任何出现在 `engineering_constraints` 中的条目，不得出现在 F9 的输出中。这是硬性约束，不受覆盖。

---

## 常见误用

1. 把「业主说这面墙不能动」（意志型）和「这面墙是承重墙」（物理型）都归入 `engineering_constraints`——前者是偏好约束，应归 D2
2. 在不确定时把工程约束归入 `client_preference`（方向错了，保守方向应是归入工程约束而非偏好）
